# keeper-librarian admission 통과선과 기준선, 2026-11-09

keeper-librarian Lane Add-on의 `admission` 출력을 Tinker에서 학습한 Inkling 2 Small LoRA가 맡을 수 있는지 판정하려 한다.
학습한 쪽이 평가를 고르지 못하도록, 학습 전에 평가 세트, 검사기, 통과선을 고정했다.
이 묶음은 그 고정과 기본 모델의 기준선을 남긴다.

처음 고정(#50068) 뒤 리뷰에서 E-synth의 지름길이 나왔다.
심은 낡은 fact는 30개 모두 날짜와 시각을 달고 있었고, 나머지 fact는 0.024만 날짜를 달았다.
생성기와 라벨 감사를 고친 뒤 E-synth를 다시 만들고 다시 고정했다(#50140).
그다음 G4·G5 통과선을 넓히고, 라벨 밖 삭제를 판정 때 블라인드 판정자에게 묻도록 한 번 더 고정했다(#50181).
아래 값은 모두 마지막 고정 기준이다.

- E-synth: 생성기 평가 split(seed 20261109)으로 만든 144건 중 라벨 감사를 통과한 119건이다.
  요청 파일 sha256은 `33060b5e764be42982486b36f79a53b44a00908d7962cf37c45f3f90229edc13`이다.

## 통과선과 기본 모델 값

기본 모델은 `thinkingmachines/Inkling-2-Small:peft:262144`다.
아래 기본 모델 값은 참고값이다.
G4와 G5는 판정 실행에서 후보와 같은 run으로 다시 잰 기본 모델과 비교한다.

| 통과선 | 기준 | 기본 모델 |
| --- | --- | --- |
| G1 E-real 유효율 | 0.95 이상 | run1 0.929, run2 0.960, run3 0.929 |
| G2 E-real에서 라이브가 지우지 않은 기억을 `dropped`로 지운 수 | 합쳐 2건 이하 | run1 0, run2 1, run3 1 |
| G3 E-synth 판정 정확도 | 0.95 이상 | 129/169 = 0.763 |
| G3 E-synth 삭제 정밀도 | 1.0 | 40/40 = 1.0 |
| G3 E-synth 심은 낡은 fact 삭제 재현율 | 0.9 이상 | 20/112 = 0.179 |
| G4 E-real 라이브 답 일치율의 기본 모델 대비 차이 | −0.06 이상 | 기본 모델끼리 −0.014 (아래 「같은 모델을 세 번 잰 E-real」) |
| G5 E-real 응답 시간 중앙값의 기본 모델 대비 비율 | 1.16 이하 | 기본 모델끼리 1.01 (같은 절) |

- G2의 라이브 쪽 삭제는 `dropped`와 `absorbs`로 지운 기억을 합친 것이다.
  라이브가 지우지 않은 기억을 모델이 `absorbs`로 묶은 수는 따로 센다. 기본 모델은 run마다 5, 7, 6건이었고 통과선에는 넣지 않았다.
- G3은 무효 답의 후보와 심은 fact를 틀린 것으로 센다. 기본 모델은 E-synth 119건 중 10건이 무효였다.
- 유효한 답이 심은 낡은 fact도 고침 대상도 아닌 fact를 지우면 라벨 밖 삭제다.
  판정 때 블라인드 판정자가 그 fact를 같은 기억의 다른 fact 사이에서 다시 본다.
  한 기억의 case는 모두 같은 fact를 전문으로 보인다. 그래서 case를 나란히 놓아도 어느 fact를 지웠는지 드러나지 않는다.
  이 집합에는 라벨 감사가 그 기억의 어느 요청에서든 고르는 fact가 들어간다. 심은 fact, 후보의 대상, 후보와 가장 비슷한 fact 3개다.
  그래서 후보가 바꿔 말한 fact를 지워도, 그 fact 말고도 후보와 이어진 fact가 전문으로 보인다.
  판정자도 빼면 그 기억의 요청을 모든 타깃에서 빼고 G3을 센다.
  판정자가 남기면 틀린 삭제다. 같은 기억이 다른 삭제 때문에 빠져도 그 삭제는 정밀도에 틀린 것으로 들어간다.
  기본 모델은 남은 119건에서 라벨 밖 삭제가 없었다(감사 전 144건에서는 1개).
- G4는 후보와 기본 모델이 둘 다 유효하게 답한 항목에서만 센다.
  라이브 답도 다른 모델이 낸 답이라 정답이 아니다. G4는 기본 모델보다 라이브 답에서 0.06 넘게 멀어지지 않았는지만 본다.
- G5는 같은 항목의 기본 모델 호출과 후보 호출이 1,800초 안에 나갔을 때만 판정한다.
  측정 호출 앞에 출력 1토큰 호출로 대상마다 prefix 캐시를 데운다.
  E-real 호출의 0.9 이상이 프롬프트의 0.9 이상을 캐시에서 읽어야 판정한다. 세 run 모두 1.0이었다.
- 두 갈래가 다 통과하면 A(답만 학습)를 고른다.
  B(교사의 생각까지 학습)가 E-synth 정확도와 G4 차이에서 둘 다 0.03 이상 앞서면 B를 고른다.

기본 모델이 무효로 답한 사유:

- E-real run2의 4건: 입력에 없는 근거 1건, 근거 없는 새 claim 2건, 새 claim의 `board` 형식 1건이다. 출력이 잘린 답은 없었다.
- E-synth 119건 중 10건: 근거 없는 새 claim 5건, 근거 없는 변경 3건, 기억에 없는 `memory_claim` 2건이다.

- lead 퍼짐은 항목을 다시 뽑아 잰 표준편차다(bootstrap 4,000번, seed 20261109).

- 같은 판정은 둘 다 유효한 항목의 후보 중 두 run이 같은 판정을 낸 수다.
  기본 모델은 같은 입력에도 후보 여섯 개 중 하나꼴로 다른 판정을 낸다.
- run2 → run3이 판정 실행과 같은 조건이다. 두 호출이 1,800초 안에 나갔다.
  기본 모델과 똑같은 후보도 G4 lead가 0.030쯤, G5 비율이 0.08쯤 흔들린다.
  처음 통과선(G4 0 이상, G5 1.0 이하)에서는 그런 후보가 각각 절반쯤만 통과한다.

- run1과 나머지 둘은 5시간 떨어져 있다. 그사이 응답 시간 p50이 13.75초에서 8초로 줄었다.

## E-synth 라벨 감사

생성 모델이 요청한 종류와 다른 후보를 쓸 수 있어서, 라벨을 독립 판정자에게 확인받았다.

- 판정자는 Claude 하위 에이전트 8개다. 한 기억의 case는 한 판정자가 모두 맡았다.
  판정자는 라벨도 모델 답도 보지 못했다.
- case마다 기억의 fact 12개를 전문으로 보였다.
  라벨이나 답이 가리키는 fact, 심은 낡은 fact, 후보마다 글자 trigram이 가장 많이 겹치는 fact 3개가 들어가고, 나머지 자리는 무작위 fact로 채운다.
  나머지 fact는 후보의 카테고리에 있는 것만 앞 90자를 보였다.
- 144건 모두 판정했다. 기본 모델이 유효하게 답했는데 라벨과 달랐던 94건과, 나머지 50건(라벨과 맞은 39건, 무효 11건)이다.
- 판정이 라벨과 다른 요청 25건을 뺐다.

| 라벨 → 판정 | 후보 수 |
| --- | --- |
| 새 사실 → 기존 fact를 바꿔 말함 | 23 (그중 21개는 기존 fact 여러 개를 함께 듦) |
| 고침 → 바꿔 말함 | 1 |
| 고침 → 다른 fact를 고침 | 1 |
| 바꿔 말하기 → 라벨의 fact 말고 다른 fact도 같은 지식 | 1 |

- 바꿔 말하기는 라벨의 fact만 들어야 남긴다. 채점이 그 fact의 claim으로 답을 맞추기 때문이다.
- 심지 않은 fact를 지워야 한다거나 심은 낡은 fact를 남겨야 한다는 판정은 없었다. 그래서 기억 단위로 뺀 것은 없다.
- 불일치 94건 중 22건, 나머지 50건 중 3건(0.06)이 라벨과 달랐다.
  불일치 72건은 판정자가 라벨과 같았다. 기본 모델이 틀린 경우다.
- 판정자마다 뺀 비율이 크게 달랐다. 판정자 1~8 순서로 1/19, 10/19, 3/19, 5/19, 3/16, 2/16, 1/18, 0/18이다.

case별 결과는 `e-synth-audit.json`에 ID로만 있다.

### 판정자 사이 일치도

원래 판정자 8명이 맡은 기억에서 하나씩, 모두 8개를 골랐다. 그 기억의 case 31건을 새 판정자 2명이 같은 case 파일과 기준으로 다시 판정했다.
새 판정자도 라벨, 모델 답, 원래 판정을 보지 못했다. 이 측정은 뺄 요청을 바꾸지 않는다.

| 대상 | 수 | 같은 분류 | Cohen's κ |
| --- | --- | --- | --- |
| 후보 분류 | 48 | 46 (0.958) | 0.951 |
| 전문으로 보인 fact 분류 | 372 | 371 (0.997) | 0.984 |
| 요청을 뺄지 | 31 | 28 (0.903) | −0.045 |

- 분류가 갈린 곳은 두 종류다.
  - 기억에 일반 규칙이 있고, 후보가 그 규칙을 새 상황에 적용한 결정일 때(2건). 원래 판정자는 바꿔 말하기로, 새 판정자는 새 사실로 봤다. 라벨은 새 사실이다.
  - 역할 자료를 옮겨 적은 fact(1건). 새 판정자는 역할 자료에서 복구되니 지워야 한다고 봤다. 라벨은 남김이다.
- 그래서 뺀 요청은 한 건도 겹치지 않았다. 원래 판정이 뺀 2건을 새 판정자는 남겼다.
  새 판정자는 원래 판정이 남긴 29건 중 1건을 뺐다(0.034, 95% 구간 0.001~0.178).
  요청을 뺄지는 드문 경계 판단 하나로 정해지고, 그 판단은 판정자마다 다르다. κ가 0 근처인 까닭이다.
- fact 쪽 불일치는 G3 삭제 정밀도(1.0)에 바로 걸린다. 학습한 모델이 새 판정자처럼 그 fact를 지우면, 라벨로는 틀린 삭제다.
  그래서 판정 때 라벨 밖 삭제를 블라인드 판정자에게 다시 묻는다(「통과선과 기본 모델 값」).

case별 분류 짝은 `e-synth-audit-agreement.json`에 ID와 분류 값으로만 있다.

E-synth 기본 모델은 감사 전 144건을 가리키는 임시 고정으로 돌았다. 감사가 이 답으로 case를 고르기 때문이다.
임시 고정은 커밋하지 않았다.
기본 모델 run 뒤 고정 대상 파일 가운데 `pass_lines.json`과 `eval_admission.py`가 바뀌었다.
`eval_admission.py`는 E-synth 행에 라벨 밖 삭제 ID 칸을 더했다. 저장된 답 144건을 지금 코드로 다시 매기면 기존 칸 값은 하나도 바뀌지 않는다.
`audit_decisions.py`와 `e_synth_audit.py`는 마지막 고정 때 고정 대상에 들어갔다.
고친 `e_synth_audit.py`로 감사를 다시 만들면 case, key, 감사 결과, 최종 요청 파일이 바이트까지 같다.

## 확인하지 못한 것

- E-synth 요청 파일(약 13MB)은 저장소에 넣지 않았다. 운영자 컴퓨터의 `artifacts/`에 있고 sha256으로 고정했다.
  생성 호출 기록(`calls.jsonl`)이 있으면 같은 파일을 다시 만들 수 있다. 기록이 없으면 모델이 다른 글을 쓴다.
- E-real 원문과 답은 운영 저장소에만 있다. 같은 기록이 없는 곳에서는 E-real과 `surface_rates.py real`을 다시 잴 수 없다.
- run1과 run2 사이에 endpoint에서 무엇이 바뀌었는지 모른다.
- 남은 119건에도 다른 판정자라면 뺄 요청이 남아 있다. 일치도 표본 29건에서 1건이라, 크기는 0.001~0.178 사이로만 안다.
- 라벨 밖 삭제의 블라인드 판정은 판정 실행에서 처음 돈다. 판정자 한 명의 판단이라 판정자마다 갈릴 수 있다.
