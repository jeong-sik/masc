# 도구 인자 채택 측정 (2026-11)

도구에 선택 인자를 더하는 개선은 모델이 그 인자를 넣어야 효과가 나요.
`measure_argument_adoption.py` 는 도구 호출 원장(`<base-path>/.masc/tool_calls`)에서 한 도구의 한 인자를 넣은 호출이 얼마나 되는지, 그 호출의 결과가 몇 바이트인지를 창(window)별로 재요.
원장을 읽기만 해요.

## 다시 측정하기

```bash
python3 -I -B docs/evidence/tool-argument-adoption-2026-11/measure_argument_adoption.py --base-path ~/me \
    --tool keeper_artifact_read --argument contains \
    --from 2026-11-03T00:00:00Z --split 2026-11-05T02:19:09Z --until 2026-11-05T20:00:00Z \
    --json-out after.json
```

- 이 폴더의 `result-*.json` 은 2026-11-05T20:49Z ~ 20:57Z 에 읽은 값이에요. `--until` 을 20:00Z 로 고정해서, 다시 돌려도 같은 창이면 같은 값이 나와요.
- 시험은 `python3 -B -m unittest discover -s docs/evidence/tool-argument-adoption-2026-11` 로 돌려요. Python 3.11 이상이 필요해요.
- `--split` 을 빼면 창이 하나(`all`)예요.

## 센 방법

- 호출: 원장 한 줄이에요. 도구 이름이 `--tool` 과 같은 줄만 세요.
- 인자를 넣은 호출: `input` 객체에 그 키가 있고 값이 null 도 빈 문자열도 아닌 호출이에요. `false`, `0`, `[]` 는 넣은 것으로 세요.
- 창은 반쯤 열려 있어요. `--split` 시각의 호출은 뒤 창(`after`)에 들어가요.
- 결과 크기: 원장 줄의 `result_bytes` 예요. 값이 없거나 음수인 줄은 바이트 계산에서 빼고 `calls_without_size` 에 세요.
- `first_use_utc`: `--from` ~ `--until` 안에서 그 인자를 넣은 가장 이른 호출이에요. `--split` 이 이보다 늦으면 인자를 넣은 호출이 `before` 에 들어가니, `before` 의 `calls_with_argument` 가 0인지 보면 나눈 시각이 늦지 않았는지 알 수 있어요.

### 나눈 시각을 정한 방법

PR 이 병합된 시각이 아니라 새 바이너리가 요청을 받기 시작한 시각으로 나눠요.
서버는 부팅할 때 `tool assets synced from binary: N copied, M overwritten (tools/…toml, …)` 줄을 쓰고, 몇 초 뒤 `boot stage=listening_banner.end` 줄을 써요(`~/me/.masc/logs/system_log_YYYY-MM-DD.jsonl`).
앞의 줄에 바뀐 도구 TOML 이름이 들어 있어요. 뒤의 줄이 그 바이너리가 요청을 받기 시작한 시각이에요.

| 변경 | 병합(UTC) | 도구 TOML 이 덮어써진 줄 | `listening_banner.end` (나눈 시각) |
|---|---|---|---|
| `keeper_artifact_read` 에 `contains` (#48282) | 11-05T01:15:26Z | 11-05T02:19:03Z | 11-05T02:19:09Z |
| `masc_schedule_notes_list` 에 `contains` (#48291) | 11-05T06:58:57Z | 11-05T08:31:25Z | 11-05T08:31:30Z |

- 11-04 ~ 11-05 로그에서 `keeper_artifact_read.toml` 이 덮어써진 부팅은 02:19:03Z 한 번이고, `masc_schedule_notes_list.toml` 은 08:31:25Z 한 번이에요.
- 11-05 에는 부팅이 9번(00:41, 02:19, 06:02, 06:46, 07:11, 08:31, 09:29, 09:37, 11:32 UTC) 있었어요. 병합 시각이나 "그날 배포"로 나누면 실제로 뜬 바이너리와 어긋나요.
- `system_log` 는 8일 정도만 남아요. 위 시각은 이 표에 적어 둔 값이 기록이에요.

## 인자가 아닌 변경: `masc_keeper_delegate_status` 결과 크기 (스크립트로 재지 않음)

#48343 은 이 도구의 결과에서 제출한 요청(`input`, `source`, digest 필드)을 뺐어요. 결과를 줄이는 변경이라 모델이 따라 하지 않아도 줄어요.
같은 상태(`Running`)끼리 견줘요. 창은 11-03T00:00Z ~ 11-05T21:00Z 이고, 원장 줄의 `output` 을 열어 센 값이라 `measure_argument_adoption.py` 로는 재지 않아요.

## 기준선 33.2% 는 하루가 만든 값이에요

`docs/evidence/tool-efficiency-baseline-2026-11/` 의 "같은 결과를 다시 받은 호출"은 11-01 ~ 11-04 합계로 결과 바이트의 33.2%(310.3 MB / 933.7 MB)예요.
`scripts/measure-tool-efficiency.py` 를 하루씩 돌려 나눠 보면 이 값은 11-01 하루가 만들어요.

| UTC 날짜 | 호출 | 재조회 바이트 | 그날 결과 바이트 중 | `masc_schedule_notes_list` 호출 (그중 재조회) | Execute 시간 중 대기(휴리스틱) |
|---|---:|---:|---:|---:|---:|
| 11-01 | 58,600 | 230,954,240 | 58.02% | 19,707 (17,553) | 3.43% |
| 11-02 | 49,075 | 67,680,706 | 19.02% | 768 (492) | 36.25% |
| 11-03 | 18,315 | 3,158,312 | 3.26% | 6 (0) | 38.70% |
| 11-04 | 25,797 | 9,476,408 | 7.50% | 10 (0) | 44.46% |
| 11-05 (20:42Z 까지) | 19,422 | 1,548,162 | 3.33% | 27 (0) | 42.89% |

- 11-01 의 재조회 바이트 230.95 MB 는 기준선 재조회 바이트(310.31 MB)의 74.4% 예요. 11-01 을 빼면 11-02 ~ 11-04 합계는 79.36 MB / 535.64 MB = 14.82% 예요.
- 11-01 에는 `code-reviewer` 한 Keeper 가 `masc_schedule_notes_list` 19,707번 중 19,586번(99.4%), `keeper_artifact_read` 10,070번 중 7,711번(76.6%)을 불렀어요. 이 두 호출 흐름이 한 날에 몰렸다가 11-02 ~ 11-03 에 끝났어요. 끝난 이유는 보지 않았어요.
- 기준선 README 의 11-04 는 19:10Z 에서 끊겨서 호출 18,192개, 재조회 10.27% 예요. 위 표의 11-04 는 하루가 끝난 뒤 다시 읽은 값이에요. 11-01 ~ 11-03 은 둘이 같아요.
- 11-05 이후 값을 기준선 합계 33.2% 와 견주면 안 돼요. 합계에서 11-01 을 빼도 14.82% 이고, 11-03 은 이미 3.26% 였어요. 배포 전에 내려온 몫이 개선의 효과로 읽혀요. `contains` 는 11-05 02:19Z 와 08:31Z 에 서버에 들어갔어요(위 표).
  견줄 때는 11-01 을 빼고 날짜를 맞춰 보고, 호출당 값이나 이 폴더의 채택 몫처럼 일의 양에 덜 흔들리는 값을 써요.
- 마지막 열은 `scripts/measure-tool-efficiency.py` 의 대기 휴리스틱(`sleep`, `until … do`, `--watch` 가 명령에 있는지)이에요. 대기 시간은 11-01 2,142.3초, 11-02 48,101.4초, 11-03 31,382.3초, 11-04 44,716.4초, 11-05 47,480.5초예요. 11-02 이후 줄지 않았어요. 이 대기 시간은 위 인자들이 다루는 비용이 아니에요.

## 이 측정이 말하지 못하는 것

- 창마다 Keeper, 모델, 일이 달라요. 전과 후의 호출 수와 바이트 차이는 변경의 효과가 아니에요. `keeper_artifact_read` 의 시간당 호출이 13.67 에서 7.69 로 내려간 것도 같아요.
- `contains` 를 넣은 호출의 결과가 작은 것(755바이트 대 6,262바이트)은 `contains` 가 걸러서 돌려주는 인자라서 생기는 값이에요. 같은 질문을 `contains` 없이 했다면 얼마였는지는 몰라요. 줄인 양이 아니에요.
- 인자 설명 문구가 채택을 만들었는지는 몰라요. 같은 부팅에 다른 도구 변경도 함께 들어갔어요.
- 후 창이 17.68시간, 136호출이에요. 며칠 쌓인 뒤에 같은 명령으로 다시 재야 몫이 안정돼요.
- 같은 호출에 함께 든 다른 인자(`max_matches`, `ignore_case`)는 세지 않아요.
- 호출 결과 바이트는 원장에 기록된 값이에요. 모델에게 간 글과 같은지는 확인하지 않았어요.
