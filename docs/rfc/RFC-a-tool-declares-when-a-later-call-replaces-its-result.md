# RFC: 도구가 "뒤 호출이 내 앞 결과를 대체한다"고 스스로 선언한다

- 상태: Draft. 코드는 쓰지 않는다. 사용자가 후보와 선언 값을 정하기 전에는 구현하지 않는다.
- 값은 모두 읽기만 해서 얻었다. 창, 분모, 출처는 값 옆에 적었다. 코드 좌표는 `origin/main` `3c89f0114cea` 에서 읽었다.

## 이 문서가 말하는 것

1. 같은 턴에서 같은 입력으로 다시 불려 앞 호출이 된 결과가 72시간에 장부 크기로 34.7 MB 다(범위 안 결과의 10.0%). 81.1% 가 `masc_dos_*` 세 도구다.
2. 그 34.7 MB 의 89.6% 는 뒤 결과와 본문이 다르다. 중복이 아니라 지난 상태다. 본문이 같은 몫은 3.6 MB(10.4%)이고 절반이 `keeper_artifact_read` 다.
3. 지금 코드는 턴 안의 결과를 크기 거절을 받은 뒤 한 번만 마커로 바꾼다. 뒤 호출이 생겨 앞 결과가 쓸모없어졌다는 사실은 어디서도 쓰지 않는다.
4. 후보는 넷이다. (가) 도구가 대체를 선언한다. (나) 도구가 수명 세 값을 선언한다. (다1) 서버가 입력이 같으면 대체한다. (다2) 서버가 입력과 본문이 모두 같을 때만 대체한다.
5. (다2)는 선언이 필요 없고 잃는 정보가 없다. 닿는 몫은 10.4% 다. 나머지 89.6% 는 지난 상태를 마커로 보내는 일이다. 그 상태를 모델이 다시 볼 일이 없는지는 도구를 만든 쪽만 안다. 그 몫은 (가)가 맡는다.
6. 옳은지는 되읽은 바이트와 줄어든 바이트로 가른다. 되읽기를 장부에 적는 typed 코드는 사용자가 따로 승인하기 전에는 쓰지 않는다.

## 배경 (측정)

창은 11-08T05:40Z ~ 11-11T05:40Z (72시간)다. 분모는 장부에서 `result_bytes` 가 2,048 ~ 65,536 B 인 도구 결과 346,298,022 B 다. 출처는 `docs/evidence/tool-efficiency-1111-2026-11/result-long-turn-shapes-2026-11-08T05-40_11-11T05-40.json` 이다(Draft #51284, 병합 전). 정의는 같은 폴더 README 의 「정의」에 있다. 같은 턴에서 (`tool`, `input_fingerprint`)가 같은 호출들 가운데 마지막을 뺀 호출의 결과를 센다.

셋째 열은 이 문서가 더했다. 같은 묶음에서 시간순으로 이웃한 뒤 호출과 장부의 `output_fingerprint` 가 같은 앞 결과의 바이트다. 이웃한 쌍만 견줬으므로 하한이다. 일회용 읽기 스크립트로 쟀고 저장소에 없다. 같은 스크립트가 위 JSON 의 34,686,650 B 와 호출 141,353개를 그대로 냈다. `keeper_tasks_list` 줄도 이 스크립트의 값이다.

| 전체 | 34,686,650 (10.0%, 3,085호출) | 3,601,729 (10.4%) |

`masc_dos_*` 도구는 서로 같은 기계의 현재 상태를 돌려준다. 입력이 같은 앞 결과만 세면 이 관계가 빠진다. 같은 창과 같은 분모에서 `masc_dos_*` 결과는 47,189,300 B(13.6%)다. 그중 같은 턴에 뒤 `masc_dos_*` 호출이 하나라도 있는 앞 결과는 45,332,687 B(3,929호출)다. 입력이 같은 앞 결과는 28,406,546 B(2,455호출)다. 이 묶음은 도구 이름이 `masc_dos_` 로 시작하는 것을 센 측정용 분류이며 제품 규칙이 아니다.

값을 읽을 때 알아야 할 것은 넷이다.

- **장부 크기는 요청에 실린 크기가 아니다.** 장부 `result_bytes` 는 결과의 평문 사본 길이다. 요청에 실리는 것은 블록 본문이다(RFC-0363 §3.1.1). `masc_dos_press` 한 호출(`call_5e179593742d420cabd555f5`)에서 장부와 저장된 요청의 `text_content` 는 11,470 B 이고, 블록 본문(마커의 `bytes=`)은 5,563 B 다(48.5%). 평문 사본은 MCP 봉투여서 `structuredContent` 와 같은 JSON 을 `content[0].text` 에 한 번 더 담는다(이 호출에서 두 값이 같음을 확인했다). RFC-0363 §3.1.1 은 `masc_dos_*` 실린 바이트의 54.7% 가 평문 사본이라고 적었다(10-29 ~ 11-04, 저장 크기 기준). 그래서 `masc_dos_*` 에서 위 값은 요청에 실린 바이트보다 크다. 한 호출만 확인했다.
- **결과는 같은 턴의 뒤 요청마다 다시 실린다.** 상한 아래의 결과는 기록에 남아 이후 모든 요청에 다시 직렬화된다(`lib/keeper/keeper_model_input_demotion.mli:7-9`). 위 값은 결과를 한 번씩 센 값이다. 요청에 실린 누적과 다르다. Agent Core 레인의 턴은 요청을 평균 17개(중앙값 6) 보낸다(11-05T03:00Z 이후 24시간, `RFC-tool-results-age-out-of-context` 「RFC-0363 §3.4.1 개정과의 관계」).
- **범위의 두 끝은 빌린 값이다.** 2,048 B 는 끝난 턴 규칙의 하한(`aged_result_min_bytes`)이고 65,536 B 는 인라인 상한(`Common.max_agent_core_inline_result_bytes`)이다. 스크립트가 고른 값이 아니다. 이 문서의 후보는 하한을 넘기지 않으므로 2,048 B 미만의 결과도 대상이 된다. 그 몫은 재지 않았다.
- **끝난 턴 마커의 되읽기 몫은 턴 안의 값이 아니다.** 요청 2,619개(`ollama_cloud.`·`glm-coding.` 프로필, 11-08 ~ 11-10 UTC)에 실린 늙은 마커 17,829개 중 236개(1.32%)를 모델이 `keeper_artifact_read` 로 읽었다. `msx-retro-mania` 는 3,705개 중 1개다. 출처는 `docs/evidence/aged-tool-results-2026-11/README.md` 의 「끝난 턴의 마커를 다시 읽는 몫」(Draft #51284)이다. 같은 README 가 턴 안에서 바꿨을 때 모델이 방금 만든 결과를 다시 찾는 몫은 이 측정으로 알 수 없다고 적었다.

같은 창에서 턴 8,017개 중 호출이 100개 이상인 164개가 호출의 23.3% 를 차지한다(같은 폴더 README 의 「긴 턴의 모양」). 대체된 결과가 긴 턴에 몰려 있는지는 재지 않았다.

## 문제

1. 턴 안에서 도구 결과가 요청에서 줄어드는 길은 크기 거절을 받은 뒤의 한 번뿐이다. 같은 입력으로 다시 부른 앞 결과도 턴이 끝날 때까지 모든 요청에 실린다.
2. 앞 결과가 쓸모없어졌는지는 입력 지문만으로 알 수 없다. 읽기 도구는 같은 입력에 같은 대상의 더 새 상태를 돌려준다. 키 입력 도구는 같은 입력이 다른 사건이다. constitution `magic_number`(`docs/constitution.xml:442-449`)는 반복 횟수를 정체의 근거로 삼지 않고, 같은 브라우저 키 입력의 반복이 편집 상태를 계속 바꿀 수 있다고 적는다. 같은 이유로 서버는 같은 입력이 같은 뜻이라고 단정할 수 없다. 뜻은 도구를 만든 쪽이 안다.
3. 같은 입력은 `masc_dos_*` 의 뜻을 못 잡는다. `masc_dos_press` 의 결과는 그 키를 누른 뒤의 기계 상태다. `{"keys":["1"]}` 뒤에 `{"keys":["enter"]}` 를 부르면 두 번째 결과가 첫 번째를 대신하지만 입력이 다르다. 같은 입력의 28.4 MB 와 같은 묶음의 45.3 MB 가 그 차이다.
4. 사용자는 맞춘 상수와 최근성 규칙(최근 K 개, 2 KB, 596 B 위에 세운 턴 안 규칙)을 이미 거절했다. 규칙은 선언된 의미나 측정된 시스템 사실에서 나와야 한다.
5. 선언한 뜻이 틀릴 수 있다. 틀림이 어디서 드러나는지 정하지 않으면 선언은 믿음이다.

## 지금 코드가 하는 일

- **끝난 턴.** `finished_turn_results_for ~reader_available` 가 읽는 도구가 있는 Keeper 에만 `Finished_turns_as_markers` 를 준다(`lib/keeper/keeper_turn_driver_try_provider.ml:1025-1027`, `:1036-1037`). 없는 Keeper 는 원문을 둔다. 마커 조립은 `:1416` 이다. 하한 `aged_result_min_bytes = 2_048`(`:1045`)의 주석이 이 값을 재생이 값을 매긴 문턱이라고 적는다.
- **턴 안.** `current_turn_results` 는 `Current_turn_verbatim` 과 `Current_turn_demoted of { refused_atom_count }` 둘이다(`:1009-1011`). 마커가 되는 것은 크기 거절 뒤 한 번이다. 이미 보낸 메시지는 보낸 그대로 다시 나가고, 예외는 끝난 턴의 결과와 크기 거절 뒤의 재전송, 두 자리뿐이다. 이유는 그 메시지부터 제공자 캐시를 잃기 때문이다(`:977-1008`, `keeper_model_input_demotion.mli:11-18`, RFC-0363 §3.4.1). `RFC-keeper-context-window-in-tokens` §10.4 의 마지막 항목도 같다.
- **계획.** `Keeper_model_input_demotion.plan`(`lib/keeper/keeper_model_input_demotion.mli:94-100`)은 `demote_before:int`, 곧 atom 번호 아래의 결과를 고른다(`:117`). `tool_use_id` 로 고르는 입구는 없다.
- **크기 판정.** 마커가 본문보다 엄격히 작을 때만 바꾼다. 레인의 인코더로 잰다(`:134-148`). `min_result_bytes` 는 호출자가 더하는 하한이고 생략하면 0 이다(`:131`, `:149-151`). 마커 길이는 미리보기에 따라 약 125 B 에서 1,154 B(JSON 한 겹), 약 1,530 B(두 겹)다. 그래서 아래 후보는 하한을 넘기지 않아도 되고, 새 상수가 필요 없다.
- **이미지.** 이미지·문서·오디오 블록은 마커 형이 없다(`:109-111`, RFC-0363 §3.1.2). 대체해도 이미지는 요청에 남는다.
- **마커를 읽는 길.** `keeper_artifact_read` 가 sha256 으로 읽는다. 쪽당 최대 16,384 B 이고 `contains` 로 검색할 수 있다(`config/tools/keeper_artifact_read.toml`). 마커는 제공자로 가는 복사본에만 쓰고 체크포인트는 원문을 둔다(`RFC-tool-results-age-out-of-context` 「구현 방향」).
- **도구 정의.** `config/tools/*.toml` 은 217개다. `Tool_definition_toml.tool_of_pairs`(`lib/tool_surface/tool_definition_toml.ml:785`)가 허용 키 목록(`:891-906`)으로 읽고, 모르는 키는 에러다. 선택 키의 전례는 `defer_loading` 이다(`:830-834`, 없으면 `Always_loaded`). 파라미터의 `role = "path"` 는 호출이 건드린 경로를 선언하는 닫힌 값이고 런타임이 읽는다(`:112-121`, #49742). 둘 다 도구 쪽이 뜻을 선언하고 런타임이 읽는 전례다.
- **`identity_fields` 는 자원 키가 아니다.** 이 키는 호출자 신원을 묶는 입력 필드 이름이다(`bin/gen_board_tool_registry.ml:133-140`, `lib/mcp_tool_runtime_board.mli:18-28`).

## 후보 설계

네 후보에 공통인 것이 있다.

- 바뀌는 것은 제공자로 가는 복사본이다. 체크포인트 원문과 blob 은 그대로다.
- 마커, blob, `keeper_artifact_read` 는 끝난 턴 규칙의 것을 그대로 쓴다. 새 마커 형은 없다.
- 읽는 도구가 없는 Keeper 는 대체하지 않는다(`keeper_turn_driver_try_provider.ml:1836`).
- 이미 마커인 결과는 다시 바뀌지 않는다(`keeper_model_input_demotion.mli:113` 의 `Decoded`).
- 규칙은 메시지 목록만 보고 같은 답을 낸다. 한 번 대체된 결과는 뒤 요청에서도 같은 바이트다. 뒤 호출이 목록에 남기 때문이다. 새로 저장하는 상태는 없다.
- 도구 이름을 문자열로 비교하지 않는다. 선언은 toml 에 있고, 소비하는 곳은 닫힌 variant 를 빠짐없이 `match` 한다(constitution `closed_sum_over_string` `:211-215`, `string_matching` `:452-458`).
- (가), (다1), (다2)는 캐시에 대가가 있다. `keeper_model_input_demotion.mli:11-18` 이 적은 두 자리에 세 번째가 늘어난다. 앞 결과가, 뒤 호출의 결과가 처음 실리는 요청에서 한 번 바뀐다. 끝난 턴 규칙은 바뀌는 메시지가 기록의 끝쪽이라 대가가 작다고 적었다(`RFC-tool-results-age-out-of-context` 「RFC-0363 §3.4.1 개정과의 관계」). 턴 안의 앞 호출과 뒤 호출 사이가 멀수록 이 대가가 커진다. 하네스 M3 가 잰다.

### 가. 도구가 대체를 선언한다

- **선언.** `config/tools/<tool>.toml` 의 키 하나이고 값은 닫힌 집합이다. 키가 없으면 선언이 없다. 제안은 `result_replaced_by = "later_call_with_same_input"` 이다. 이름과 값은 사용자가 정한다.
- **서버가 하는 일.** 선언한 도구에서 같은 턴의 `(도구, 입력)` 이 같은 뒤 호출의 결과가 목록에 생기면, 앞 호출의 결과를 마커로 보낸다. 뒤 호출의 결과가 오류(`is_error`)이면 바꾸지 않는다. 가장 뒤 호출의 결과는 원문이다.
- **사건 도구.** 선언하지 않는다. `Execute` 는 입력이 같아도 사건이 다르다. 선언이 없으면 지금과 같다.
- **틀리면 잃는 것.** 선언이 맞아도 지난 상태는 마커가 된다. 측정한 앞 결과의 89.6% 가 뒤 결과와 본문이 다르다. 선언이 뜻하는 것은 모델이 그 지난 상태를 다시 볼 일이 없다는 것이다. 틀리면 모델이 `keeper_artifact_read` 로 되읽는다. 본문은 blob 과 체크포인트에 남는다. 대가는 되읽기 호출과, 이미 보낸 메시지를 고쳐 그 메시지부터 캐시를 잃는 것이다. `anthropic` 종류 제공자에서는 뒤 assistant 메시지의 서명된 thinking 블록이 요청에서 빠질 수 있다(「확인하지 못한 것」 3).
- **틀림을 잡는 곳.** 리뷰에서 toml 한 줄의 diff 로 보인다. 로드할 때 모르는 값은 에러다. 운영에서는 하네스 M4 가 되읽은 바이트가 줄인 바이트 이상인 도구를 가린다.
- **장점.** 새 상수가 없다. 선언이 없으면 동작이 같아서 배포가 아무것도 바꾸지 않는다. 도구 하나씩 켜고 끈다. 도구 정의가 코드 밖(toml)에 있다. 뜻을 아는 쪽이 선언한다. "같다"의 정의가 장부의 `input_fingerprint` 와 같은 꼴이라 측정이 이미 있다(정규화가 같은지는 「확인하지 못한 것」 4).
- **단점.** 도구마다 사람이 선언한다. 외부 MCP 서버의 도구는 toml 이 없어 선언할 길이 없다. 의미로 고른 첫 선언은 34.7 MB 의 15.6% 에만 닿는다(「사용자가 정할 것」 4). 이미 보낸 메시지를 고치므로 캐시를 깬다. 크기 하한이 없어서 작은 결과도 대체한다. 결과가 작으면 줄어드는 바이트가 작은데 캐시 손실은 결과 크기와 상관없다. 이것을 런타임 문턱으로 막지 않는다. 재생으로 맞춘 값이 되기 때문이다. 도구별로 S 와 C 를 견주는 것(M3)으로 가린다.
- **이 설계가 틀렸다면 드러나는 곳.** 선언한 도구의 되읽은 바이트가 줄인 바이트 이상이다(M4).

**"같다"의 범위.** 셋이 있다.

- 같은 도구, 같은 입력. 지금 재는 정의다. `masc_dos_*` 에서 28,406,546 B 다.
- 같은 도구, 선언한 인자. 같은 키를 공유하는 서로 다른 입력은 서로를 대체하면 안 된다. `masc_board_post_get` 은 `post_id` 가 같아도 `comment_offset` 이 다르면 다른 쪽을 돌려준다. `Grep` 은 경로가 같아도 패턴이 다르면 다른 질의다. `role = "path"` 는 호출이 건드린 경로이지 결과의 정체가 아니라서 키로 쓰지 않는다. 장부에는 입력 전체의 지문만 있어서 입력 JSON 에서 그 인자를 뽑아 새로 계산해야 잴 수 있다(측정용).
- 같은 묶음, 도구 여럿. `masc_dos_*` 처럼 같은 기계의 현재 상태를 돌려주는 도구는 입력이 달라도 서로의 앞 결과를 대신한다. 묶음 이름은 도구 정의가 선언해야 한다. 장부에는 이 관계가 없다. 측정용 묶음으로 잰 값이 45,332,687 B 다.

첫째만 지금 잴 수 있다. 둘째와 셋째는 위험과 크기를 M1 의 별도 열로 먼저 재야 한다. 선택은 사용자가 한다(「사용자가 정할 것」 2).

### 나. 도구가 수명 세 값을 선언한다

- **선언.** 결과가 원문이어야 하는 기간이다. `turn`, `session`, `permanent` 셋이다. `turn` 은 만든 턴이 끝나면 마커이고, `session` 은 세션이 끝날 때까지 원문이며, `permanent` 는 마커로 보내지 않는다.
- **서버가 하는 일.** 끝난 턴 규칙에서 도구별로 예외를 둔다.
- **사건 도구.** `turn` 이다. 같은 턴 안의 대체는 말하지 못한다. 세 값 모두 턴 안에서는 원문이다.
- **틀리면 잃는 것.** `session`·`permanent` 를 잘못 선언하면 바이트가 줄지 않고 요청에 쌓인다. `turn` 을 잘못 선언하면 끝난 턴의 결과를 되읽는다. 지금 모든 도구가 그렇다.
- **틀림을 잡는 곳.** 저장된 요청에서 선언한 도구의 결과가 끝난 턴 뒤에도 원문으로 실린 바이트와, 그 도구의 끝난 턴 마커 되읽기 몫이다(`measure_marker_rereads.py`).
- **장점.** 끝난 턴 규칙의 예외를 도구가 말할 수 있다. 값 `permanent` 는 Anthropic context editing 의 `exclude_tools` 와 같은 모양이다.
- **단점.** 측정한 34.7 MB 는 턴 안의 값이다. 세 값은 턴 안에서 모두 같으므로 그 바이트에 닿지 않는다. `turn` 은 선언이 없을 때의 동작과 같아서 값 하나가 죽어 있다. 남는 `session`·`permanent` 는 바이트를 늘리는 쪽이다. 그 수요를 직접 잰 적은 없고, 수요가 작다는 신호만 있다. 끝난 턴 마커 17,829개 중 되읽힌 것이 236개다.
- **이 설계가 틀렸다면 드러나는 곳.** `turn` 이 아닌 값을 선언한 도구가 없거나, 있어도 그 도구의 끝난 턴 되읽기 몫이 선언 없는 도구와 같다. 필드가 쓰이지 않는 것이다.

### 다. 선언 없이 서버가 대체한다

공통: 도구가 아무것도 선언하지 않는다. 서버가 같은 턴의 메시지 목록에서 고른다. 선언이 없는 새 도구도 같은 규칙을 받는다.

**(다1) 입력이 같으면.**

- **서버가 하는 일.** 모든 도구에서 같은 턴의 `(도구, input_fingerprint)` 가 같은 뒤 호출이 있는 앞 결과를 마커로 보낸다.
- **사건 도구.** `Execute` 와 `masc_dos_press` 의 앞 결과도 대체된다. 같은 명령을 코드를 고친 뒤 다시 돌리면, 앞 출력은 고치기 전 상태를 기록한 사건인데 마커가 된다.
- **틀리면 잃는 것.** 측정한 앞 결과의 89.6% 가 지난 상태다. 선언 없이 모든 도구의 지난 상태가 마커가 된다. 배포가 모든 도구의 동작을 바꾼다.
- **틀림을 잡는 곳.** 도구별 되읽기 몫(M4)이다. 고치려면 예외 목록이 필요하다. 그 목록은 코드에 있든 설정에 있든 (가)의 선언이고 극성만 반대다.
- **장점.** 도구 저자가 할 일이 없다. 정의가 측정과 같아서 34.7 MB 가 그대로 상한이다.
- **단점.** 모르는 도구의 뜻을 편한 기본값으로 눌러 담는다. 어느 도구가 사건 도구인지 서버는 모른다.
- **이 설계가 틀렸다면 드러나는 곳.** `Execute`·`masc_dos_press` 의 대체된 결과를 되읽는 호출이 있다.

**(다2) 입력과 본문이 모두 같을 때만.**

- **서버가 하는 일.** 같은 턴에서 `(도구, 입력)` 이 같고 결과 본문이 바이트까지 같은 뒤 호출의 결과가 목록에 생기면, 앞 결과를 마커로 보낸다.
- **사건 도구.** `Execute` 와 `masc_dos_press` 도 같은 규칙을 받는다. 같은 입력의 두 호출이 같은 본문을 돌려주면 같은 정보를 두 번 싣는 것이다. 앞 결과를 마커로 바꿔도 뒤 결과가 그 본문을 그대로 싣는다. 입력이 같아도 사건이 다르다는 점은 걸리지 않는다. 본문이 같은 사건만 고르기 때문이다.
- **틀리면 잃는 것.** 정보가 줄지 않는다. 같은 출력이 두 번 나왔다는 사실이 한눈에 안 보일 뿐이다. 마커의 `bytes=` 와 미리보기는 남는다.
- **틀림을 잡는 곳.** 도구별 되읽기 몫(M4). 같은 출력의 반복 자체가 정보인 도구에서 드러난다.
- **장점.** 선언이 필요 없다. 도구 저자의 판단이 없다. 새 상수가 없다. 사건 도구에도 안전하다.
- **단점.** 닿는 몫이 작다. 34.7 MB 의 10.4%(3,601,729 B)이고 범위 안 바이트의 1.0% 다. 그중 52.4% 가 `keeper_artifact_read`, 12.8% 가 `Execute` 다. DOS 에는 0.3% 다. 이웃한 쌍만 견준 하한이다. 이미 보낸 메시지를 고쳐 캐시를 깬다. 본문을 견주는 일이 요청마다 든다.
- **이 설계가 틀렸다면 드러나는 곳.** 되읽기 몫이 0 에 가깝고 줄인 바이트도 작아서, 켜는 값어치가 없다(M3 의 S 와 C).

### 비교

| | (가) 대체 선언 | (나) 수명 세 값 | (다1) 입력이 같으면 | (다2) 입력·본문이 같으면 |
|---|---|---|---|---|
| 도구가 말하는 것 | 뒤 호출이 앞 결과를 대체하는가 | 원문이어야 하는 기간 | 없음 | 없음 |
| 선언이 없을 때 | 지금과 같다 | 지금과 같다 | 대체한다 | 본문이 같으면 대체한다 |
| 닿는 바이트(34.7 MB 중) | 선언한 도구의 본문이 다른 몫. 첫 선언은 15.6% | 닿지 않는다 | 100% | 10.4% |
| 잃는 정보 | 지난 상태(되읽기로 복구) | 없음(바이트가 쌓임) | 지난 상태 | 없음 |
| 사건 도구 | 선언하지 않으면 그대로다 | 말하지 못한다 | 같은 규칙으로 바꾼다 | 본문이 같을 때만 바꾼다 |
| 새 상수 | 없다 | 없다 | 없다 | 없다 |

**추천은 (다2) 다음에 (가)다.** (다2)는 선언 없이 정보를 잃지 않는 몫을 먼저 가져간다. (가)는 지난 상태를 마커로 보내는 몫을 도구 저자의 선언이 있는 도구에만 연다. 근거는 셋이다. 새 상수가 없다. 선언이 없으면 동작이 같거나 정보가 줄지 않는다. 정의가 측정과 같아서 하네스가 이미 있다. 대가도 있다. 닿는 바이트가 작다. (다2)는 범위 안 바이트의 1.0%, (가)의 첫 선언은 1.6% 다. 이미 보낸 메시지를 고쳐 캐시를 깬다. 그래서 켜기 전에 M3 가 도구별로 S 와 C 를 견준다. 이 안의 값어치는 `masc_dos_*` 의 묶음 선언(45.3 MB, 범위 안 바이트의 13.1%)을 어떻게 다루느냐에 크게 달렸다. 그 결정은 첫 라운드의 되읽기 몫을 본 뒤 사용자가 한다.

## 이 RFC 가 서는 자리

- **`tool-results-age-out-of-context`(끝난 턴 마커, #49185).** 같은 마커, 같은 blob, 같은 읽기 도구를 쓰고 끝난 턴 규칙은 바꾸지 않는다. 그 규칙은 "턴이 끝났다"는 사실로, 이 RFC 는 "뒤 호출이 있다"는 사실로 마커를 만든다. 두 사실이 한 결과에 겹쳐도 이미 마커인 결과는 다시 바뀌지 않는다. 그 RFC 의 「턴이 길 때」 절(Draft #51284)이 후보로 적은 "도구가 결과의 수명을 선언한다"를 이 문서가 받는다. 같은 절의 첫 후보인 턴을 일의 단위에서 끝내는 길은 PR 을 다루는 Keeper 에 맞다. 34.7 MB 의 81.7% 인 `msx-retro-mania` 의 긴 턴에는 단위가 정해지지 않았다.
- **`keeper-context-window-in-tokens` §13.6 (Active).** 같은 자리를 건드린다.
  - 부딪치는 곳. §13.6 의 도구 결과 항목(`docs/rfc/RFC-keeper-context-window-in-tokens.md:601`)은 지금 턴의 결과도 조립 때 마커로 나가게 한다고 적는다. 같은 RFC 의 §10.4 마지막 항목은 지금 턴 강등을 크기 거절 뒤 한 번으로 두고, 코드도 그렇다(`keeper_turn_driver_try_provider.ml:977-1008`). 한 RFC 의 두 절이 다르다.
  - 보완하는 곳. §13.6 은 모든 결과를 한 부류로 다루고 되읽기 비용을 모든 결과에 건다. 이 RFC 는 본문이 같은 결과나 도구가 선언한 결과에만, 뒤 호출이 생긴 뒤에만 건다. §13.6 이 먼저 구현되면 이 RFC 가 고르는 결과는 이미 마커여서 선언이 겹친다.
  - 낡은 근거. §13.6 은 `keeper.model_input_demotion_enabled` 를 쓴다. 이 키는 #38986 이 지웠고(`CHANGELOG.md:12715`) 11-11 에 `rg` 로 `lib/`·`config/` 에서 찾지 못했다. 이 RFC 는 그 키에 기대지 않는다. §13.6 을 고치는 일은 그 RFC 의 몫이라 여기서 하지 않는다.
- **`0363` 과 `retained-results-carrier-shrinks-to-an-address`.** 마커 형, 측정기, 이미지 제외(§3.1.2)를 그대로 쓴다. 마커의 blob 에는 지속하는 참조자가 없다. 본문이 체크포인트에 그대로 있어서 blob 은 다시 만들 수 있는 파생 데이터다(`keeper_model_input_demotion.mli:235-245`).

## 하네스

모델이 인라인 원문의 어느 부분을 참조했는지는 관측할 수 없다. 그래서 마커로 보내고 되읽기를 센다. 되읽기는 모델이 고른 행동이다. 읽지 않은 것은 미리보기로 충분했거나 필요 없었다고 센다. 이 가정은 RFC-0363 §3.1.1 이 재지 않은 것으로 적은 것과 같다.

키는 이미 있는 typed 값만 쓴다.

| 키 | 출처 |
|---|---|
| `trace_id`, `keeper_turn_id` | 장부 `tool_calls` 행. 턴을 가른다. |
| `tool`, `input_fingerprint`, `output_fingerprint`, `result_bytes` | 장부 행 |
| `tool_use_id` | 장부 행과, 저장된 요청의 메시지 blob(`messages[].artifact.content_ref`)이 담은 `tool_call_id`. 한 호출(`call_5e179593742d420cabd555f5`)에서 맞았다. |
| `sha256`, `bytes` | 저장된 요청의 마커, `keeper_artifact_read` 장부 행의 `input.sha256` |

저장된 요청(`keepers/<keeper>/provider-inputs/`)에는 한계가 있다. `msx-retro-mania` 는 11-08 ~ 10 UTC 에 `turn_ref` 마다 요청 하나, 모두 118개다. 확인한 한 요청의 마지막 메시지는 user 메시지였다. 턴 안의 뒤 요청은 저장되지 않는 것으로 읽는다. 그래서 턴 안의 양은 장부로 센다.

- **M1 대체된 결과의 바이트(장부 크기).** 세 가지로 센다. ① (`trace_id`, `keeper_turn_id`, `tool`, `input_fingerprint`)가 같은 호출들에서 마지막을 뺀 호출의 `result_bytes` 합이다. `long_turn_shapes.py` 의 `superseded` 와 같은 정의다(34,686,650 B). ② ① 가운데 시간순으로 이웃한 뒤 호출과 `output_fingerprint` 가 같은 것(후보 (다2)의 몫)과 다른 것(후보 (가)의 몫)이다. ③ 측정용 묶음과 선언한 인자 키의 열이다(후보 (가)의 "같다"의 범위 둘째와 셋째). ③ 은 측정용이며 제품 규칙이 아니다. `--min-bytes 2048` 과 `--min-bytes 0` 으로 두 번 돌린다. 선언한 도구만 따로 합한다.
- **M2 요청에 실린 몫.** 대체된 결과의 `tool_use_id` 를 다음 턴 첫 요청의 메시지 blob 이 담은 `tool_call_id` 와 맞춘다. 그 메시지의 마커가 적은 `bytes=`(본문 크기)를 장부 `result_bytes` 로 나눈다. 도구별 비와 맞춘 호출 수 n 을 적는다. 한 호출은 5,563 / 11,470 이다. 그 턴의 요청이 저장되지 않은 호출은 n 에서 뺀다. 이 조인은 측정용이며 제품 규칙이 아니다.
- **M3 줄어든 바이트 S 와 캐시 하한 C.** 대체 사건 하나(앞 결과 r, 뒤 호출 c)마다 S = (r 의 본문 − r 의 마커) × (c 의 결과가 요청에 실린 뒤 그 턴이 보낸 요청 수)다. 마커 길이는 같은 도구의 저장된 마커의 실제 길이다. C 는 r 부터 c 앞까지 호출들의 `result_bytes` 합이다. 제공자가 캐시에서 다시 읽던 바이트의 하한이다. assistant 글과 도구 입력은 장부에 없다. S 와 C 는 한 수로 합치지 않는다. 합치려면 공급자의 캐시 읽기·쓰기 값이 필요하고, 그 값은 공식 문서로 확인한다(확인 필요). 요청 수는 장부의 `execution_id`·`batch_size` 묶음으로 센다(확인 필요).
- **M4 되읽은 바이트 R 와 되읽은 몫.** (Keeper, sha256) 쌍으로 `keeper_artifact_read` 장부 행을 대체된 결과의 마커와 잇는다. `measure_marker_rereads.py` 가 끝난 턴 마커에 하는 조인과 같다. 되읽은 몫은 되읽힌 대체 결과 수를 대체 결과 수로 나눈 값이다(끝난 턴은 236 / 17,829). 같은 턴에서 대체가 일어난 뒤의 호출만 센다. 턴이 끝난 뒤의 읽기는 끝난 턴 규칙의 몫이다. R = 되읽은 호출의 `result_bytes` × (그 호출이 실린 뒤 그 턴의 요청 수)다. 대체된 결과의 sha256 은 다음 턴 첫 요청의 마커에서 찾는다. 같은 본문은 같은 sha256 이다. typed 기록이 없는 동안의 측정용 조인이다.

**판정.** 도구마다 R ≥ S 이면 그 도구의 선언을 지운다. 선언한 도구 전체의 합이 R ≥ S 이면 (가) 전체를 접는다. R < S 이면 남긴다. 이것은 바이트의 필요조건이다. 통과한 선언도 C 와 `anthropic` 종류의 thinking 손실을 따로 본다. R 이 0 이어도 통과가 아니다. 모델이 마커만 보고 되읽지 않은 채 틀린 판단을 했는지는 이 값으로 알 수 없다.

이 판정은 정의가 닫힌다. S 와 R 은 단위가 같다. 둘 다 요청에 실려 간 바이트다. 두 항은 장부와 저장된 요청의 typed 키로만 정해진다. 열린 입력은 둘이다. 하나는 요청 수를 세는 키(M3)이고 다른 하나는 대체된 결과의 sha256 을 찾는 길(M4)이다. 둘을 확인하기 전에는 판정을 내리지 않고 값만 적는다.

**창과 고정.**

- 창은 선언을 켠 빌드가 `/health` 의 `build.commit` 으로 올라온 시각부터 72시간이다. 시작 시각은 스크립트 인자이고 결과 JSON 의 `window` 에 적는다. 길이 72시간은 지금 재고 있는 창과 맞춘 것이다.
- 스크립트는 `docs/evidence/tool-result-replacement-2026-11/` 에 둔다. 판정 함수와 창의 길이는 스크립트 머리에 둔다. 합성 장부 시험(`long_turn_shapes.py` 시험과 같은 방식)이 판정 함수를 고정한다.
- 선언을 더하거나 지우는 PR 은 이 스크립트와 시험을 고치지 않는다. 고쳐야 하면 별도 PR 로 사용자 리뷰를 받는다.
- 켜기 전에 같은 스크립트를 같은 도구에 돌려 M1 과 M2 의 값을 PR 본문에 적는다.

## 하지 않는 것

- 도구를 가로지르는 대체의 구현. 「사용자가 정할 것」 2 가 묶음을 고르기 전에는 하지 않는다. 쓰기가 앞 읽기를 대체하는 것도 같다. 둘 다 도구 사이의 관계를 새로 선언해야 한다.
- 입력이 달라도 본문이 같은 결과의 중복 제거. 재지 않았다.
- 크기, 개수, 최근성 규칙. 최근 K 개, 2 KB, N 회 뒤를 만들지 않는다. 끝난 턴 규칙의 2,048 B 는 바꾸지 않는다.
- Keeper 프롬프트나 도구 설명에 새 문장을 넣는 것. 모델이 아는 것은 마커와 `keeper_artifact_read` 의 기존 설명이다.
- 이미지·문서·오디오 블록의 대체. 마커 형이 없다.
- 되읽기를 기록하는 typed 코드. 대체한 결과의 sha256 과 `tool_use_id` 를 장부에 적는 코드는 사용자가 따로 승인하기 전에는 쓰지 않는다. 없는 동안 M4 는 다음 턴 첫 요청의 마커로 하한을 낸다.
- 옛 형식을 위한 reader, converter, migration. 선언이 없으면 지금과 같으므로 옮길 것이 없다.
- 도구 출력을 줄이는 길. 결과가 큰 원인을 도구에서 고치는 방법이다. `masc_dos_press` 한 호출의 블록 본문 5,563 B 중 `screen_text` 가 2,052 B, `frame_ascii` 가 2,462 B, `files` 가 627 B 다(한 호출). 이 길이 더 단순할 수 있다. 이 RFC 는 정하지 않고, 사용자가 판단하도록 적어 둔다.
- Anthropic context editing(`clear_tool_uses_20250919`)을 후보로 올리지 않는다. 지울 때(`trigger`, 기본 100,000 입력 토큰)와 남길 개수(`keep`, 기본 3)와 최소 지움량(`clear_at_least`)을 호출자가 맞추는 숫자다. 지운 자리에는 자리표시 글만 남는다고 문서가 적는다. Anthropic 요청 매개변수라서 측정된 바이트가 도는 `glm-coding.` 프로필(`msx-retro-mania` 의 `runtime_profile`)에는 쓸 수 없다고 읽는다. 공식 문서 `platform.claude.com/docs/en/build-with-claude/context-editing` 을 2026-11-11 에 원문으로 확인했다(신뢰도 High, 베타 기능이라 바뀔 수 있다).

## 사용자가 정할 것

1. **후보.** (가) 대체 선언, (나) 수명 세 값, (다1) 입력이 같으면, (다2) 입력·본문이 같으면. 추천은 (다2) 다음에 (가)다. 근거와 대가는 「비교」 아래에 적었다.
2. **"같다"의 범위((가)에 한정).** 같은 도구·같은 입력(측정이 있는 유일한 정의), 같은 도구·선언한 인자(측정 없음, 구간이나 질의가 다른 호출이 서로를 대체할 위험), 같은 묶음(측정은 측정용 묶음의 45.3 MB 뿐). 추천은 같은 입력이다. 이유는 측정이 거기에만 있어서다. 묶음은 `masc_dos_*` 의 뜻에 맞는 범위이므로 M1 ③ 을 보고 정한다.
3. **키 이름과 값 집합.** 제안은 `result_replaced_by` 와 값 하나 `"later_call_with_same_input"` 이다. 값이 하나인 닫힌 집합이라 두 번째 뜻은 variant 하나와 `match` 갈래 하나로 더한다.
4. **(가)의 첫 선언 도구.** 뜻으로 고른다. 읽기만 하고, 같은 입력의 뒤 호출이 같은 대상의 현재 상태를 돌려주는 도구다. `keeper_artifact_read` 는 (다2)가 닿으므로 뺀다.
   - `masc_dos_screen`: 시간을 움직이지 않고 화면을 읽는다.
   - `masc_board_post_get`, `keeper_wiki_read`: 글과 위키 쪽의 현재 내용을 읽는다.
   - `masc_browser_read`: 장부에는 `BrowserRead` 로 찍힌다(`lib/keeper/keeper_tool_descriptor.ml:1168`, 대응은 확인 필요).
   - 이 넷의 합이 5,404,185 B 로 34.7 MB 의 15.6% 다. 그중 본문이 다른 몫은 5,021,564 B(14.5%)다. `masc_browser_read` 를 빼면 4,223,649 B 다. 효과 도구 `masc_dos_press`·`masc_dos_step` 와 `Execute` 는 첫 선언에서 뺀다. 이유는 뜻이다. 두 DOS 도구의 결과는 기계의 현재 상태이고, 앞 프레임이 키 입력 전후를 견주는 데 쓰이는지는 사용자가 그 도구의 뜻을 보고 정한다. 바이트로 정당화하지 않는다. 첫 라운드의 되읽기 몫을 본 뒤 정한다.
5. **되읽기 기록 코드의 승인.** 대체한 결과의 sha256 을 장부에 적는 typed 코드를 쓸지. 승인 전에는 쓰지 않는다.
6. **`keeper-context-window-in-tokens` §13.6 과의 순서.** 이 RFC 를 먼저 정할지, §13.6 의 도구 결과 항목과 합칠지.

## 확인하지 못한 것

1. `masc_dos_*` 의 요청에 실린 몫. 한 호출(48.5%)과 다른 창의 값(평문 사본 54.7%, RFC-0363 §3.1.1)만 안다. 도구별 비는 M2 가 잰다.
2. 이미지 블록이 든 결과의 이미지 몫이 장부 `result_bytes` 에 들어 있는지. 11-01 ~ 05 에 이미지가 붙은 도구 결과 58,660개 가운데 58,532개가 `msx-retro-mania` 의 것이었다(`docs/evidence/aged-tool-results-2026-11/README.md`). 11-08 이후의 한 요청(`glm-coding.glm-5.3-flash`)에서 읽은 결과 하나(메시지 7)는 글 블록 하나였다. 이미지가 있는 결과는 대체해도 이미지가 요청에 남는다.
3. `anthropic` 종류 제공자에서 앞 결과를 바꾸면 뒤 assistant 메시지의 서명된 thinking 블록이 요청에서 빠지는 일(`packages/agent_core/lib/llm_provider/backend_anthropic.ml:600`의 `verify_prefix_binding`)의 크기. 끝난 턴 규칙에서 이미 적힌 같은 문제를 이 RFC 도 재지 못했다. Anthropic 문서(context editing 페이지, 2026-11-11 확인)는 클라이언트가 앞 턴을 고치면 뒤 assistant 턴의 thinking 블록이 무효가 될 수 있다고 적는다. 이 제공자에서 켜기 전에 재야 한다.
4. 장부 `input_fingerprint` 와 `output_fingerprint` 의 정규화. 제품 규칙의 같은 입력과 같은 본문이 같은 정규화를 써야 측정과 같은 집합이다. `output_fingerprint` 가 요청에 실리는 블록 본문과 일대일인지도 안 맞춰 봤다.
5. 본문 분할 값(같은 본문 3,601,729 B 등)과 `masc_dos_*` 묶음 값(45,332,687 B 등)은 일회용 읽기 스크립트로 쟀고 저장소에 없다. 근거 JSON 과 같은 총합을 내는지로 확인했다. M1 이 같은 정의로 다시 낸다.
6. 모델 요청 수를 세는 키(M3). 장부의 한 묶음이 요청 하나인지 맞춰 보지 않았다.
7. 턴 안의 뒤 요청이 저장되는지. 한 요청만 확인했다.
8. 마커의 미리보기만으로 모델이 충분한지. RFC-0363 §3.1.1 도 재지 않았다.
9. `keeper-context-window-in-tokens` §13.6 의 "지금 턴의 결과"가 가장 새 결과를 포함하는지.
10. 외부 MCP 서버의 도구에 선언하는 길. toml 이 없어서 이 RFC 밖이다.
