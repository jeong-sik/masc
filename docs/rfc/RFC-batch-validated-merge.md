# RFC: 결합 트리 검증 병합 (batch-validated merge)

## 0. 요약

현재 채택된 R1은 PR마다 "run 생성 이후 main이 PR 파일을 건드리지 않았다"를 요구한다. #39421의 공통 검사 입력까지 넓히는 규칙은 제안이며 아직 채택되지 않았다.
main이 자주 움직이는 날에는 거의 모든 PR이 병합 직전에 다시 CI 한 주기(약 25분)를 기다린다.
#39421의 제안된 입력 모델에서 공통 입력 범위를 좁혀도 재생 결과 무효화가 107건에서 106건으로 줄 뿐이다(아래 1절). 이 재생 수치는 채택된 운영 규칙의 실측 무효화 건수와 다르다.

이 RFC는 입력 목록을 손보는 대신 **병합 경로**를 바꾼다.

- 여러 PR의 head를 main의 한 지점(BASE) 위에 합친 결합 트리(ROLL)에서 CI를 한 번 돌린다.
- ROLL PR 자체를 독립적으로 검토·승인하고 한 번의 squash로 main에 넣는다. A, A+B 같은 중간 멤버 조합은 main에 쓰지 않는다.
- 멤버마다 바뀌지 않는 증거(40자 head, 그 head 자신의 PR-check run을 가리키는 PASS 판정 줄, 그 head에 묶인 승인)를 붙인다. ROLL run을 멤버 head의 run이라고 적지 않는다.
- 착지 직전에 BASE 이후 main 변화, 모든 멤버와 ROLL의 판정·승인, 최종 트리를 대조한다. 실제 착지 증명 뒤 원래 PR들을 흡수된 변경으로 닫는다.

이 문서는 **Draft 제안**이다. #39421/#39553의 정책 HOLD를 해제하거나 운영 규약을 채택하지 않는다. r3는 신선도 증거뿐 아니라 병합 대상과 원래 PR 처리 방식도 바꾼다.

실패는 면제하지 않는다. 결합 트리가 빨가면 그 배치는 착지하지 않는다.

## 3. 설계

### 3.1 배치 단위와 한 번의 착지

- 배치 = (BASE, ROLL, MEMBERS).
  - BASE: 자르는 시점의 main 40자 SHA.
  - MEMBERS: `(PR, head40)` 목록. 순서는 결합 트리를 재구성하는 순서이며 개별 병합 순서가 아니다.
  - ROLL: BASE 위에 명시된 멤버 head들을 차례로 합친 커밋.
- ROLL PR은 main을 대상으로 하는 **실제 병합 PR**이다. 이 PR의 고정된 head에서 필수 검사 5개가 모두 성공한 PR-check run을 받는다.
- ROLL PR 하나만 병합 대상으로 삼고, 명령 한 번 실행에 head가 고정된 squash 요청을 최대 한 번 보낸다. 멤버 PR들을 순차 병합하는 경로는 제공하지 않는다.
- 결합 전체가 성공해도 중간 조합은 실패할 수 있다. 예를 들어 A/B/C가 각각 a/b/c를 켜고 테스트가 `not (a and b and not c)`를 요구하면 단독 A/B/C와 A+B+C는 성공하지만 A+B는 실패한다. 한 번의 ROLL 착지는 이 중간 상태를 main에 쓰지 않는다.
- 검사 입력 경로는 재구성 과정의 각 멤버 적용 전후 diff의 **합집합**이다. 뒤 멤버가 원상복구한 경로도 포함한다. 최종 BASE→ROLL diff는 별도로 비어 있지 않아야 한다.
- 고정된 멤버 수 제한이나 중간 조합별 새 CI를 요구하지 않는다. 필수 검사 5개 실패는 그대로 거부한다(3.5).

### 3.2 멤버와 ROLL의 독립 증거

착지 전 모든 멤버는 아래 조건을 만족해야 한다. 하나라도 없으면 rc 6이다.

1. 현재 head가 MEMBERS의 head40과 정확히 같다. 이 구현은 main을 충돌 없이 합친 새 head도 같은 것으로 취급하지 않는다. head가 바뀌면 새 배치를 만든다.
2. 현재 head 자신의 성공한 PR-check run을 인용하는 신뢰 가능한 최신 PASS가 있다. 첫 줄은 `verdict: PASS head: <head40> run: <run> by: <Keeper>`다. ROLL run을 멤버 run으로 적지 않는다.
3. 필수 검사 5개와 기존 워크플로·check gate가 모두 성공한다. 멤버 run의 main 신선도만 결합 증거로 대신한다.
4. 독립된 승인 계정이 작성한, 코드 리뷰 줄(`review: APPROVE head: <head40> by: <Keeper>`)과 approve-guard footer가 head에 묶인 유효한 승인이 있다. 승인 세션은 그 PR에 push하지 않은 세션이어야 한다.
5. PR이 open이고 Draft가 아니며 base는 main이다. 열린 CR이나 최신 FAIL/HOLD가 없어야 한다.

**ROLL도 별도의 실제 PR로서 자기 head와 자기 run의 PASS, 필수 검사 5개, 독립된 footer-bound 승인, 열린 CR/FAIL 없음이 필요하다.** 멤버들의 승인이나 배치 줄만으로 ROLL 승인을 대신하지 않는다.

### 3.2a 매니페스트와 계약 변경

리더가 ROLL PR과 모든 멤버 PR에 동일한 줄을 게시한다.

```
batch: PASS landing: ROLL roll: <ROLL40> base: <BASE40> run: <ROLL PR-check run> members: <PR>@<head40>,<PR>@<head40>,... by: <Keeper>
```

- `landing: ROLL`은 실제 병합 대상이 ROLL이라는 명시적 계약이다. 이 필드가 없는 줄은 받지 않는다.
- ROLL PR 번호는 해당 run의 PR/branch 연결로 유일하게 확인한다. 외부에서 번호를 추측하지 않는다.
- 가드는 BASE에 고정된 멤버들을 적용한 Git 트리가 ROLL과 같은지 다시 계산한다.
- 배치 줄은 멤버/ROLL의 판정 줄이나 승인을 대신하지 않는다. 승인 본문의 첫 코드 리뷰 줄과 마지막 footer는 head에 묶인다. 코드 승인은 CI 판정과 별개다.

| 조건 | PR별 경로 | 제안된 배치 경로 |
|---|---|---|
| 현재 head 자신의 PR-check 5개 성공·PASS·독립 승인 | 해당 PR | 모든 멤버와 ROLL 각각 |
| main 변경 신선도 | 해당 run 이후 입력 겹침 없음 | BASE 이후 외부 커밋과 멤버 적용 경로·공통 입력 겹침 없음 |
| main에 쓰는 대상 | 해당 PR | 검증한 ROLL PR 하나 |
| 원래 멤버 PR 상태 | 개별 병합됨 | 착지 증명 뒤 별도로 흡수됨을 기록하고 닫음 |

r3는 신선도 조건 하나만 바꾸는 제안이 아니다. 실제 병합 대상, ROLL의 독립 승인, 멤버 PR의 흡수 처리도 계약 변경이다. 월드 조항 a-7e31026d 등 운영 규약은 별도의 명시적 채택 절차를 거쳐야 하며 이 구현 PR은 규약·런타임 설정을 고치지 않는다. GitHub ruleset 우회나 관리자 병합은 사용하지 않는다.

### 3.3 착지와 도착 증명

1. ROLL과 모든 멤버의 현재 head/run/체크/판정·배치 게시를 읽고 결합 트리를 재구성한다.
2. BASE 이후 main의 첫 부모 이력을 읽는다. 멤버 적용 경로나 공통 검사 입력을 건드린 외부 커밋이 있으면 rc 5로 거부한다. 상관없는 외부 변경만 보존할 수 있다.
3. 비용이 큰 검사와 마지막 head/main/판정 읽기 **뒤에 모든 멤버와 ROLL의 footer-bound 승인을 다시 확인한다**. `DISMISSED`나 승인 소실은 rc 6이다. CR이 없다는 사실만으로 승인이 있다고 판단하지 않는다.
4. `merge-guard --batch`는 ROLL만 받는다. 원래 멤버를 지정한 착지 요청은 거부한다. Keeper만 ROLL의 고정 head로 squash 요청 한 번을 보낸다.
5. 요청 뒤 한 번 읽어 아직 미병합이면 rc 7이다. 기다리거나 반복 조회하지 않고 다음 작업 경계에서 같은 명령을 다시 실행한다. 재개 때도 아직 open이면 같은 ROLL head 요청을 다시 제출할 수 있다. 서버의 요청 식별자나 영속 제출 영수증이 없으므로 여러 실행을 통틀어 요청이 정확히 한 번이라는 보장은 하지 않는다.
6. ROLL의 API 병합 커밋이 main의 첫 부모 이력에 실제로 있는지, 부모가 하나인지, 그 부모 위에 ROLL을 적용한 트리와 같은지 확인한다. 같은 호출에서 바로 완료되면 요청 전 관측한 main과 부모도 대조한다. 불일치는 rc 4다.
7. 중단 뒤 재개도 실제 병합 커밋·부모·트리·main 이력을 다시 증명한다. PR의 `merged=true`만으로 완료하지 않는다. 이미 도착했으면 병합 요청을 반복하지 않는다.
8. 증명 뒤에만 `absorption_candidates`를 반환한다. 스크립트는 원래 PR을 닫지 않는다. Keeper가 증명된 ROLL/병합 커밋을 적어 원래 PR을 닫는 별도의 재개 가능한 메타데이터 작업을 한다. 이는 각 원래 PR이 개별 병합되었다는 뜻이 아니다. 영수증의 각 멤버 head/run과 ROLL head/run/병합 커밋을 함께 기록한다. 호출 전 preflight에서 관측한 승인 ID는 그 관측 시점의 자료이며 최종 쓰기 순간의 승인 스냅샷이라고 표시하지 않는다. 병합 뒤 재개한 호출에 저장된 이전 영수증이 없으면 역사적 승인 ID 연결은 unavailable로 표시한다.

GitHub의 개별 API 읽기와 병합 요청에는 체크·승인·main을 한꺼번에 고정하는 CAS가 없다. 마지막 재확인은 관측 사이 경쟁을 줄이지만 없애지 못한다. 도착 증명은 실제 Git 결과를 증명하며, 과거 순간의 전체 승인 상태를 재구성했다고 주장하지 않는다.

### 3.4 가드 연결

- `approve-guard.sh --batch`는 멤버 또는 ROLL의 코드 승인에 배치 줄을 기록하며 CI·신선도를 검증하지 않는다. 결합 신선도 검증은 `--integration-check --batch`와 병합 단계가 담당한다. 판정·승인 계정 독립성은 그대로다.
- `ci-freshness.py --batch`는 모든 멤버의 고정 head와 ROLL 결합 트리, 외부 main 입력을 검사한다.
- `merge-guard.sh --batch`의 `--check`와 실제 쓰기는 모두 ROLL 착지와 모든 유효한 승인을 마지막 경계에서 요구한다.
- `land-batch.sh`는 ROLL 쓰기 하나와 도착 증명을 관리한다. 미병합 prefix 복구나 개별 멤버 병합 경로를 두지 않는다.
- 단독 PR 경로의 동작과 종료 코드는 바꾸지 않는다. 배치 종료 코드는 0 성공, 1 인프라, 2 입력 오류, 3 ROLL 검사/판정 실패, 4 착지 트리/부모 오류, 5 외부 main 입력 충돌, 6 멤버·승인 증거 부족, 7 비동기 병합 진행 중이다.

### 3.5 예산을 넘긴 스위트

현재 PR check의 edited-tests 단계는 `.github/workflows/pr-check.yml`의 `--budget-seconds 1800`을 사용한다. 2.1의 1080초는 당시 실행 기록이다. 멤버가 많으면 일부 스위트가 "(not run: the step budget ran out)"으로 남고, 그 단계가 속한 필수 체크가 failure로 끝난다.
- **예산 초과도 ROLL run의 실패다.** 3.1의 "필수 5개 success"를 채우지 못하므로 배치는 성립하지 않는다(rc 3).
- 같은 ROLL head의 targeted Test run(`test.yml -f suite=…`)으로 빠진 스위트를 모두 초록으로 덮어도 필수 체크 실패를 면제하지 않는다. 근거는 두 가지다. 월드 조항 a-7e31026d는 필수 체크 5/5 성공을 요구한다. 운영자 제약(Board c-f3f73a24ebbd97a4a01a6a9eb6af10a0 4번)은 실패를 면제해서 속도를 올리지 않는다고 정했다.
- targeted run은 원인을 가르는 진단으로만 쓴다.
- 대신 배치를 작게 다시 자른다. 컷 전에 멤버들이 고친 스위트 수를 세어 한 run 예산 안(09-25 r1 실측 244개 실행)에 들도록 멤버를 나눈다. 7절 3번은 이를 관측하는 운영 질문이며 고정 멤버 수 제한을 도입하지 않는다.
- 2.1의 r1d(09-25)는 이 RFC 전의 기록이다. 그때는 예산 미도달을 targeted run으로 덮고 착지했다. 이 RFC 아래서는 rc 3이며, 선례로 쓰지 않는다.

### 3.6 PR마다 그대로 남는 것

- FAIL 판정과 CR, 운영자 HOLD, hold 단어(Breaking / Fresh state required / now rejected) 검사
- changelog 조각 요구
- 승인 계정·세션 독립성
- 워크플로 파일 스코프 제약

멤버들의 변경은 ROLL로 한 번에 착지한다. 판정과 승인은 멤버와 ROLL 각각 따로이며, 원래 PR의 닫기는 도착 증명 뒤의 메타데이터 작업이다.

## 4. 불변식 (배치 경로가 PR별 경로보다 약해지지 않는 이유)

1. 이 배치가 main에 쓰는 트리는 단 하나다. 실제로 CI가 돈 ROLL과 같거나, 멤버 적용 경로·공통 입력과 겹치지 않는 외부 변경만 보존한다. 검증되지 않은 A+B 같은 중간 prefix를 쓰지 않는다.
2. 쓰기 전 모든 멤버와 ROLL의 자기 head 판정·승인을 마지막 경계에서 확인한다. 원래 PR은 실제 도착 증명 전에 흡수 완료로 표시하지 않는다.
3. 빨간 run은 어떤 경로로도 근거가 되지 않는다. 멤버 하나가 빨강이면 그 멤버를 빼고 다시 자른다(tdune-r2 선례).

## 5. 과거 순차 방식의 재생 추정과 새 방식의 미측정 항목

r3의 단일 ROLL 착지는 아직 운영하지 않았다. 아래 수치는 과거 순차 방식에 대한 것이며 새 방식의 CI 절감량·처리량·승인 시간 실측이 아니다.

- 과거 롤업 7번의 실측: 결합 트리 run 7번으로 25건이 착지했다. 멤버는 롤업 예약(sched-705766a8)의 선정 기준대로 "자기 head의 초록 run이 main 이동으로 stale이 됐거나, 서로 같은 파일을 건드려 순차 병합하면 뒤 PR이 stale이 되는 PASS PR"에서 골랐다. 25건 모두 PR별 경로에서 착지 전 새 run이 한 번씩 필요했다면 **재실행 18번을 아낀 셈**이다. 이 기준이 멤버마다 성립했는지는 이 RFC에서 다시 세지 않았다. 반대 방향으로, 순차 병합 중 다시 stale이 되어 생기는 추가 재실행도 세지 않았다. 멤버의 첫 run은 두 경로 모두 필요하므로 이 셈에 넣지 않았다.
- #39421 재생과 같은 09-26~27 병합 집합에 대한 추정은 이 레인에서는 **계산할 수 없다**. root 세션의 packet(`/private/tmp/masc-ci-throughput-20260928/`)을 Keeper 샌드박스에서 읽을 수 없기 때문이다. 같은 packet으로 "그 시각 열려 있던 PASS PR을 배치로 묶었을 때 필요한 결합 run 수"를 root 세션에 요청한다.

## 6. 비목표

- GitHub merge queue 도입: 개인 계정 저장소라 쓸 수 없다(2026-09-24 확인).
- 모든 병합을 배치로 강제하기: 단독으로 신선한 PR은 지금처럼 PR별 경로로 착지한다.
- 공통 입력 목록 자체의 설계: #39421에서 다룬다.

## 7. 열린 질문

1. 배치 줄 원본을 어디에 둘까. 후보는 실제 ROLL PR 코멘트와 저장소 안 파일이다. 코멘트는 편집 이력이 남지만 형식 강제가 약하다. 어느 쪽이든 가드는 트리 재계산으로 확인한다.
2. 배치를 누가 자를까. 지금은 리더가 사람 판단으로 멤버를 고른다. 자동 후보 선정(PASS·승인 있음, 서로 파일이 겹치거나 모두 stale)의 기준을 정해야 한다.
3. edited-tests가 예산에 도달하기 전 얼마나 실행되는지 관측한다. 09-25 r1은 244개 실행·54개 미도달이었으며, 이를 모든 배치에 통하는 숫자 상한으로 쓰지 않는다.
4. 단일 ROLL 착지의 실제 CI 재실행 수·처리량과 별도 흡수 처리 완료 시간을 어떻게 측정할지 정한다.

## 8. 구현 순서

1. 이 RFC 채택(내부 규약 개정 절차).
2. scripts/review/land-batch.sh를 단일 ROLL 착지로 구현하고, 세 멤버 중간 조합 실패·한 번 쓰기·비동기 재개·도착 증명을 검사한다.
3. #39421의 가드와 명시적 landing: ROLL 매니페스트를 연결하고, 빨간 ROLL·움직인 멤버 head·외부 입력 겹침·마지막 승인 취소가 쓰기를 막는 음성 대조를 넣는다. 코드 검토와 규약 채택은 별도 절차다.
