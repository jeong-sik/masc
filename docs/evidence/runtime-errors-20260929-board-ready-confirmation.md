# Board Ready confirmation evidence (task-1827)

`confirm_ready` now writes one cursor-fenced JSONL row containing both the unchanged Ready partition and a `ready_confirmation` observation. The observation records `confirmed_at` from the append boundary and `runtime_instance_id` from the server process. An incomplete final row is discarded by the existing process-start torn-tail recovery; a complete row contains both state and observation. Process-start compaction retains the observations as separate JSONL records while compacting partition states.

`confirmed_at` is sampled before append, not after fsync. The append API returns a `write_outcome` to its caller, but that outcome is not stored in the confirmation record. In particular, a `Visible_sync_unconfirmed` return can leave a readable confirmation row after restart. Per-boot row counts therefore measure observed Ready confirmations, not confirmed fsync successes. A later confirmation of the same generation may produce another row; the consumer must keep row counts separate from distinct Ready generations and from successful write outcomes. This evidence does not claim that every observed row was durably acknowledged at its original call boundary.

The partition tests exercise Blocked → requeue → Ready confirmation, a repeated confirmation of the same generation after process-start recovery, deferral to a later Ready generation, another process-start recovery, and final settlement. One test checks same-process compaction and strict rejection of a duplicate confirmation key. A second test launches three distinct child processes against one isolated ledger and checks that the first two confirmations share a generation, the third boot performs deferral to a later generation, confirms it, and settles the root, while all three boot identities differ. The original parent reads the observation bytes after spawning the children but performs no ledger operation with its pre-restart cache. The existing worker scenario for an operator-authorized quarantine requeue now also checks that two repeated reconciliations append two observations for the deferred generation, recovery of an interrupted run adds a later-generation observation, and owner settlement preserves all three. A successful initial requeue or deferral does not itself call `confirm_ready`; the recorded events reflect actual confirmation calls.

The original 12 affected rows have no confirmation time or boot identity. This change does not backfill them or assign them to earlier restarts. The 68 newly quarantined candidates in the 2026-09-29 A1 observation had no authorized requeue as of 03:04:37Z, so they provide no live Ready confirmation proof yet.
