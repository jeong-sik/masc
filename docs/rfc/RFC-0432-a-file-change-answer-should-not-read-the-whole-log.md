## 1. 문제

`GET /api/v1/keepers/<name>/file-changes?window_hours=24` 가 **호출당 1.8~8.8초**다.
돌려줄 것이 없는 키퍼도 1.8초가 걸린다. 만드는 비용이 아니라 훑는 비용이다.

2026-09-06 이 워크스페이스에서 잰 값이다.

| 키퍼 | 시간 | 응답 |
|---|---|---|
| analyst | 2,234 ~ 8,839ms | 61KB |
| code-reviewer | 1,953 ~ 3,078ms | **0KB** |
| critic | 1,797 ~ 2,175ms | **0KB** |
| edgar.a.poe | 1,916 ~ 2,607ms | 119KB |
| geek-scout | 1,877 ~ 1,912ms | 7KB |

할당 프로파일에서도 1위다. `Dated_jsonl.read_range` 가 major heap 직행 할당의
**2.62GB(17%)** 를 쓰고, 콜스택이 이 핸들러로 곧장 이어진다.

```
Dated_jsonl.read_range
  ← Keeper_tool_call_log.read_window
    ← Server_dashboard_http_keeper_api.handle_keeper_get_subroutes
```

major 직행 할당은 도메인마다 minor heap 의 1/5 를 넘길 때 전역 major 슬라이스를
요청하고, 그것은 모든 도메인이 멈추는 구간이다. 그래서 이 질의의 비용은 이
엔드포인트만 무는 것이 아니라 서버 전체가 나눠 문다.

## 2. 왜 이렇게 되는가

`read_window` 는 창이 걸치는 날짜 파일을 **전부 파싱해 리스트로 만든 뒤** 거른다.

```ocaml
Dated_jsonl.read_range store ~since:since_date ~until:until_date
|> List.filter (fun json -> in_window json && keeper_matches name json)
```

24시간 창의 실제 크기다.

```
파일 2개  237MB  40,268행  키퍼 15명
```

한 키퍼는 행의 7~19% 다. 그런데 더 중요한 것은 이쪽이다.

| | 행 | 바이트 |
|---|---|---|
| 창 전체 | 40,268 | 237MB |
| **파일을 바꾼 행** | **2,798 (6%)** | **14.9MB (6%)** |
| 그중 한 키퍼 | 약 280 | 약 1.5MB |

**237MB 를 읽어 1.5MB 로 답한다. 160배다.**

행 자체도 크다. 표본 4,000행의 필드 구성이다.

| 필드 | 비중 | 이 질의가 읽나 |
|---|---|---|
| `output` | 33% | **안 읽음** |
| `route_evidence` | 29% | 읽음 |
| `runtime_contract` | 21% | **안 읽음** |
| `action_radius` | 4% | 읽음 |
| `input` | 3% | 읽음 |

파싱한 바이트의 **54% 는 이 질의가 한 번도 보지 않는다.**

엔드포인트 주석은 이 비용을 이미 알고 있었다 — "one keeper's changes took 4.4s
over 24h, 8.3s over 48h and 11.0s over 72h", 그리고 "Reading further back is a
different feature and wants an index, not a wider scan". 운영자가 한 번 묻는
용도로 설계됐고, #33457 이 그것을 TUI 주기 새로고침에 걸면서 드러났다(#33479 로
타이머에서 뺐다).

## 3. 제안

**로그는 append-only 다. 붙은 만큼만 읽는다.**

24시간 창의 답은 두 가지로만 바뀐다 — 끝에 붙은 행, 그리고 창 밖으로 빠지는 행.
그런데 지금은 호출마다 창 전체를 다시 판다.

키퍼별로 누적값과 커서를 들고, 호출마다 커서 이후만 읽는다.

```ocaml
(* 이미 있는 것으로 만든다 *)
val fold_appended_lines
  :  path:string -> from:int -> init:'acc -> f:('acc -> string -> 'acc)
  -> 'acc * int
```

- **새 저장 구조가 없다.** 파생도 아니고 그냥 프로세스 안의 누적값이다.
- **쓰기 경로를 안 건드린다.** 버전도, 재생성도, 두 저장소의 어긋남도 없다.
- 창 밖으로 빠지는 행은 누적값이 행마다 시각을 들고 있으므로 떨어뜨린다.
- 파일이 회전하거나 잘리면 커서를 버리고 다시 읽는다. 판정은 파일 정체성과
  크기로 하며, 접두가 그대로인지 digest 로 증명한다.

이 저장소가 이미 두 번 쓴 모양이다. `#33334`(activity 파일이 하루치를 다시
파싱하던 것)과 `#33340`(큐 스냅샷을 쓸 때마다 다시 파싱하던 것)이 같은 패턴이고,
`Activity_graph.parse_current_day_events_cached` 가 회전·절단 판정까지 포함한
참고 구현이다.

첫 호출은 여전히 창 전체를 읽는다. 두 번째부터가 새 행만큼이다.

### 3.1 왜 이것이 먼저인가

희석을 이기지는 못한다 — 첫 호출은 여전히 0.6% 를 위해 100% 를 읽는다. 대신
**반복 비용을 없앤다.** 이 질의는 사람이든 화면이든 반복해서 부르는 질의이고,
반복이 사라지면 남는 것은 부팅 후 한 번뿐이다.

그 한 번마저 문제가 되면 그때 사이드카(7절 (a))를 한다. 순서가 반대면 새 저장
구조와 재생성 계약을 먼저 지고 시작하게 된다.

### 3.2 이득의 크기 (실측)

로그가 자라는 속도를 재면 증분이 얼마나 작은지 나온다. 2026-09-06,
`tool_calls/2026-09/05.jsonl`: 150MB / 24,837행 / 23.8시간. 바쁜 시간대가
시간당 2,464행, 약 15MB 다.

| 호출 간격 | 읽어야 할 증분 | 창 전체(242MB) 대비 |
|---|---|---|
| 10초 | 0.04MB | **5,808배 적음** |
| 1분 | 0.25MB | 968배 적음 |
| 10분 | 2.50MB | 97배 적음 |

사이드카(5절)의 160배보다 크다. 그쪽은 첫 호출까지 줄이는 대신 새 저장 구조를
지고, 이쪽은 첫 호출을 그대로 두는 대신 아무것도 새로 만들지 않는다.

### 3.3 필요한 것

`Dated_jsonl` 이 파일 경로나 오프셋을 내주지 않는다 — `iter_range` 는 파싱된 행만
준다. 경로 계산은 `day_file_paths_oldest_first` 로 이미 있고 `mli` 에 없을 뿐이다.
증분 커서는 그 경로와 `Fs_compat.fold_appended_lines` 로 만든다.

## 4. 죽은 안 — `iter_range` 로 흘려 읽기

revision 2 는 `read_window` 가 "창 전체를 리스트로 만든 뒤 거른다"고 적고 그것을
고치자고 했다. **틀렸다.** 코드 모양만 보고 그 아래를 안 읽었다.

`read_range` 는 이미 `iter_range` 위에 있고, `iter_non_empty_lines` 가
`input_line` 으로 한 줄씩 읽는다. 한 번에 존재하는 트리는 하나이고 리스트는
포인터만 모은다. 걸러질 트리는 이미 즉시 쓰레기다.

바꿔서 재봤다(4,000행, 한 키퍼가 10%, 각 3회):

| | 시간 | 할당 | live |
|---|---|---|---|
| 원래 | 279ms | 140.2MB | 4.65MB |
| `iter_range` | 290ms | 140.0MB | 4.65MB |

이득이 없다. 구현은 버렸고, 그 과정에서 `read_window` 에 테스트가 하나도 없다는
것이 드러나 계약을 고정하는 테스트만 남겼다(#33537).

## 5. 접힌 제안 — 파생 사이드카

3절이 반복을 없애도 첫 호출이 문제로 남으면, 그때 이것이다.

**파일을 바꾼 사실만 담는 파생 사이드카를 둔다.**

도구 호출이 파일 변경을 남길 때, 그 사실을 별도 append-only 저장소에 같이 쓴다.
엔드포인트는 도구 호출 로그 대신 이것을 읽는다.

- 하루 약 15MB(함대 전체), 키퍼 하나로 좁히면 약 1.5MB.
- 형식은 지금 응답이 담는 것과 같은 모양이다. 분류를 읽는 시점이 아니라 쓰는
  시점에 한 번 한다.

**이것은 파생 상태다.** 도구 호출 로그가 원본이고, 사이드카는 언제든 로그에서
다시 만들 수 있다. 원본을 대체하지 않으므로 durable truth 를 건드리지 않는다.

### 3.1 분류가 바뀌면

사이드카는 쓰는 시점의 분류 결과를 담으므로, 분류 규칙이 바뀌면 옛 행은 옛
규칙의 답이다. 버전을 행에 적고, 버전이 다르면 **사이드카를 버리고 로그에서 다시
만든다.** 변환 코드는 만들지 않는다(hard cut). 재생성은 로그 한 번 훑기이고,
지금 질의 한 번이 그 일의 절반을 이미 하고 있다.

### 3.2 쓰기 경로

도구 호출 로그에 한 줄 쓸 때 사이드카에 최대 한 줄이 더 붙는다. 6% 의 호출만
해당하므로 대부분의 호출은 아무것도 더 쓰지 않는다.

## 6. 무엇을 하지 않는가

- **도구 호출 로그의 형식을 바꾸지 않는다.** `output`·`runtime_contract` 가 큰 것은
  별개 문제다.
- **보존 기간을 만들지 않는다.**
- **다른 질의를 옮기지 않는다.** `read_window` 의 다른 호출자는 그대로 둔다.
- **인덱스(오프셋 표)를 만들지 않는다.** 아래 대안 (b) 참조.

## 7. 검증

| 무엇 | 어떻게 |
|---|---|
| 답이 같다 | 같은 창에 대해 옛 경로와 새 경로의 응답 JSON 이 일치 |
| 두 번째 호출이 싸다 | 연속 호출의 두 번째부터 100ms 미만 |
| 붙은 것을 본다 | 호출 사이에 행이 붙으면 두 번째 답에 그것이 있다 |
| 창 밖은 빠진다 | 창 경계를 넘긴 행이 답에서 사라진다 |
| 회전을 견딘다 | 파일이 회전·절단된 뒤 답이 전체 재읽기와 같다 |
| 할당이 준다 | memprof 에서 `read_range` 가 major 직행 상위에서 사라진다 |

첫 줄이 성패다. 새 경로가 옛 경로와 다른 답을 내면 이 RFC 는 틀린 것이다.

## 8. 위험

**쓰기가 하나 는다.** 6% 의 호출에만 해당하고 한 줄이지만, 도구 호출 경로는
뜨겁다. 쓰기 실패가 도구 호출을 실패시켜서는 안 된다 — 사이드카는 파생이므로
쓰기 실패는 기록하고 넘어가며, 그 경우 다음 재생성이 메운다.

**두 저장소가 어긋날 수 있다.** 어긋남은 사이드카가 로그보다 적은 방향으로만
일어난다(쓰기 실패). 많은 방향은 로그가 원본이므로 불가능하다. 재생성이 답이다.

**분류를 쓰는 시점으로 옮긴다.** 지금은 읽을 때마다 분류하므로 규칙을 바꾸면 옛
데이터에도 즉시 적용된다. 사이드카는 그렇지 않다. 3.1 의 버전+재생성이 값이다.

## 9. 대안

**(a) 파생 사이드카.** 5절로 접었다. 희석을 완전히 이기는 유일한 안이지만 새 저장
구조와 재생성 계약을 진다. 3절이 반복을 없앤 뒤에도 첫 호출이 문제일 때 한다.

**(b) 오프셋 인덱스.** 키퍼 → (파일, 오프셋) 표를 두고 해당 행만 읽는다. 분류와
무관해서 버전 문제가 없고 더 단순하다. 다만 이득이 5~14배(행 비율)에 그친다 —
그 키퍼의 행은 여전히 전부 파싱하고, 그중 94% 는 파일을 바꾸지 않은 행이다.

**(b2) 잘라 읽고 경계를 답에 적는다.** `read_range_recent` 가 이미 있고 mli 가
`read_range` 대신 쓰라고 적어 놨다. 계산하면 약하다: 원하는 것이 전체 행의
0.6%(파일변경 6% × 한 키퍼 10%)이므로, 한 키퍼의 변경 50건에 함대 행 8,300개를
훑는다. 5배지 160배가 아니다.

**(b3) git 에게 묻는다.** 지금은 도구 호출 증거로 파일 변경을 *재구성*한다.
파일이 바뀐 사실은 파일시스템이 알고, 키퍼가 워크트리에서 일한다면 git 이 더 싸고
더 진실에 가깝다. 다만 답의 의미가 바뀐다 — 로그는 "누가 시도했나", git 은
"결과가 무엇인가"다. 실패한 편집은 로그에만 있다. 별도 결정이 필요하다.

**(b4) 로그에서 `output` 을 뺀다.** 행의 33% 가 `output`, 21% 가
`runtime_contract` 이고 이 질의는 둘 다 안 읽는다. 빼면 모든 독자가 2.5배
빨라지고, 더하는 대신 지우는 쪽이다. 다만
`tool_call_quality_benchmark_loader.ml:171` 이 `output` 을 읽으므로 공짜가 아니다.
별개 축이다.

**(c) 키퍼별 파티션.** 저장소를 키퍼마다 나눈다. 읽기가 가장 단순해지지만 함대
전체를 보는 질의가 병합을 해야 하고, 쓰기 경로가 바뀐다.

**(d) 그냥 둔다.** #33479 로 타이머에서 뺐으므로 사람이 누를 때만 2~9초다. 다만
할당 프로파일 1위이고, 누를 때마다 서버 전체가 멈춘다.

(b) 는 (3) 이 하는 일의 일부만 한다. (c) 는 원본의 배치를 바꾼다. (3) 은 파생만
더하고 원본을 건드리지 않는다.
