# Addon-backed Workspace Curator owner

The server's public `Server_workspace_memory_curator.start` now drives the
original capture/worker/Exact/domain recovery path. The former direct HTTP/CLI
Curator executor and injected execute/summarize owner APIs are removed. This is
an intermediate E02 source change, not installed extraction or UI parity.

## Authority and durable frontier

One owner per physical workspace preserves its existing pending wake, scoped
Keeper commit subscription, in-flight revision deduplication and switch lifetime.
Each domain pass first strictly discovers the entire original forest and locally
repairs only already durable successor intentions. Malformed inventory fails the
whole pass; it cannot authorize an empty replacement frontier. Classification
and Briefing then independently advance their unique active original. Ambiguous
active frontiers fail rather than picking file order. Separate passes preserve
classification failure versus existing Briefing progress.

The owner uses public `capture`, `resume`, `settle`, `narrow` and typed observer
preparation. Strict retained host terminals and accepted local domain commits
can progress Off. Open/missing/unknown work parks with its original ID. Mere
inventory discovery is never worker or model authority. An immediate follow-up
pass requires an actual state change, not an unchanged waiting observation.

Rejected original source identities do not become new requests when unrelated
facts arrive. Completed classifications use the actual current ledger's typed
pending facts, allowing genuinely pending work after source removal/readdition.
Briefing preserves its original prepared pass and whole selected/remainder input;
unchanged terminal work is not reminted. Historical size refusals are filtered
by fresh semantic destination plus the actual current captured domain and
readable selected sources before choosing a unique continuation. A known
mismatch is historical; an authority or domain read failure remains an error.
Two genuinely current continuations still fail as ambiguous. This observation
is not a grant: narrowing performs fresh admission again. Before any replacement after a failed
successor publication the owner discovers again: a failed return is not absence.

## New work versus accepted recovery

Runtime's `with_tool_request_destination` acquires configuration then action
serialization, strictly rereads the actual declaration inventory and rechecks the
live export after offloaded reads. A saved Off declaration refuses new work even
before reconcile removes its cached export. A complete inventory is required;
unreadable unrelated configuration can therefore defer fresh work too.

The callback can publish only the local original journal and cannot reenter
Runtime, dispatch a worker/model, save a domain or deliver registry observations.
It runs cancellation-protected after acquiring both locks. Callback exceptions
release those serializers without poisoning them. Publication may have occurred
before an error, so recovery must retain original IDs and strict rereads.

A new successor also requires original logical installation/package/tool and
semantic configuration revision. Changed worker inputs refuse that new intent.
Comments, formatting and Off/On do not change semantic worker input; original raw
source provenance remains immutable. Existing Subdividing/Subdivided recovery
uses only the already retained exact child and remains local Off. This is server
serialization, not a transaction against external file editors.

Actual configured Addon lifecycle/result events wake this owner. Exact route
subscriptions use actual installation IDs and both declared outputs, including
IDs recovered from retained originals. The old builtin configured boolean and
builtin Exact route are no longer production model-selection authority.

## Observation and verification limits

Original registration/completion intents remain independently durable. Registry
compare/reconcile/delivery and durable ACK are still pending; removing the old
direct executor also removes its old registry writes. Until that follow-up is
implemented, these Curator runs do not have complete Exact registry/Dashboard/TUI
observation parity. The old builtin Curator lane/configuration projections also
need removal or explicit Addon ownership in the same integration follow-up;
they are no longer an executable model-selection path. No elapsed time, provider-start, cache usage or cost is
invented to fill that gap. No old direct provider route is kept as a workaround.

The replacement fixture starts the actual public owner, real configured Runtime,
real persistent Python worker/MCP protocol, shared Exact semantic selection and
loopback HTTP provider. Resource launch/cleanup is substituted and a lost-result
delivery case controls that one transport boundary. Size/crash-window fixtures
explicitly seed original journal facts; they do not prove a real provider size
refusal. This is not Docker cleanup, live provider, installed UI or deployment
proof. Parser/source checks and any selected compiled execution are recorded
separately; the previous injected 34-case suite does not certify this new owner.
