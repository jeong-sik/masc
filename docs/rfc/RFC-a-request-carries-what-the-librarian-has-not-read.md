# RFC: 요청이 Librarian 이 읽지 못한 이력을 싣는 자리

- 상태: Draft. 운영자 결정 전이다. §1 은 결정할 것, §2 는 실측, §3 은 원인, §4 는 설계, §5 는 고르지 않은 안, §6 이후는 범위·검증·확신도다.
- 근거: `docs/evidence/request-size-20261006/`. 라이브 base path 를 읽기만 한 측정이다. 모든 숫자의 명령이 그 README 에 있다. 10-06 로그는 아직 쓰이는 중이어서, 그날 숫자는 00:00~15:00Z 기준이다.
- 이 RFC 는 새 규칙을 따로 들고 있지 않는다. 운영자가 정하면 각 규칙은 §1 표의 "규칙이 갈 곳"으로 옮긴다. 이 문서에는 근거와 결정 기록만 남는다(창 RFC §1 의 5).

## 0. 요약

2026-10-05 18:00 부터 10-06 02:50 까지 Keeper 하나(sangsu)가 토큰 13억 3천만 개를 썼다. 호출마다 입력과 출력을 더한 값이다. 대부분 Ollama Cloud 였고, 그 계정은 19:57 부터 세션 한도(429)에 걸렸다.

가장 큰 몫은 루프였다. 같은 사실을 `keeper_memory_write` 로 계속 다시 쓴 턴이 429 로 끝났고, 다음 턴이 그 일을 이어받아 같은 쓰기를 776번 더 했다. 이어받은 턴은 앞 턴의 atom 1,609개를 호출마다 원문으로 실었다. 그 몫은 약 5억 700만 토큰으로 추정한다. 루프는 #41377 로 남겼고, 이 RFC 의 어떤 결정도 루프를 멈추지 않는다.

이 RFC 가 다루는 것은 요청이 커지는 세 자리다.

1. 끝나지 못한 턴의 일은 다음 턴이 이어받는다. 이어받은 구간은 도구 결과까지 원문으로 실린다. 일부러 정한 동작이다(#37602, Librarian RFC §4.6). 같은 날 재기동만 11번이었다.
2. 턴 안에서는 지금 턴의 도구 결과가 크기 거절 뒤에만 마커가 된다. 창 RFC §13.6 은 조립 때 마커로 보내기로 정했지만, 그 코드는 아직 없다.
3. 공식 클라이언트는 씨앗을 강등 없이 싣고, 호스트 세션을 턴마다 이어 쓴다.

## 1. 결정할 것

| # | 물음 | 제안 | 규칙이 갈 곳 |
|---|---|---|---|
| D1 | 지금 턴의 도구 결과는 언제 마커가 되나 | 모델이 이미 답한 결과는 조립 때 마커로 보낸다. 아직 답하지 않은 결과는 원문으로 둔다. 이어받은 구간에도 같은 규칙을 쓴다 | 창 RFC §13.6, RFC-0363 §3.4.1·§6, `docs/librarian-continuity-snapshot.md` 의 작은 입력 절, `keeper_turn_driver_try_provider.mli` 의 `completed_history_end` 설명 |
| D2 | 턴 도중에 창을 옮기나 | 지금은 옮기지 않는다 | Librarian RFC §7 (나), 그대로 |
| D3 | 공식 클라이언트는 무엇을 바꾸나 | 씨앗 강등은 RFC-0460 §9 가 정한 값을 먼저 잰다. 세션은 official-client-conversation §5.6 다음에 §5.7 의 정책으로 간다 | RFC-0460 §7.2·§9, official-client-conversation §5.7 |

구현 순서 제안은 D1 → D3 의 측정 → D3 의 세션 정책이다.

## 2. 무슨 일이 났나

### 2.1 이어받은 턴 (2026-10-06)

- 끝나지 못한 턴이 저장한 atom 은, 다음에 끝까지 간 턴의 줄이 자기 시작 위치로 적을 때까지 마지막 완료 경계 뒤에 남는다. 그동안 그 뒤의 턴들이 그 atom 을 이어받아 싣는다.
- 00:00~15:00Z 에 Keeper 20개에서 이런 구간이 88개, atom 5,467개였다(`unfinished.json`). 공식 클라이언트 턴 줄 바로 뒤의 틈 17개(atom 1,119개)는 그 턴 자신의 Agent Core 후보가 남긴 atom 일 수 있어 따로 세고 이 숫자에서 뺐다. 구간마다 앞 줄과 뒷줄 사이에는 그 atom 이 마지막 완료 경계 뒤에 있었다. 그동안의 요청이 실제로 그 atom 을 실었는지는 이 파일로 알 수 없다. 공식 씨앗이나 `Past_librarian_point` 에서 연 요청은 그 뒤에서 시작했을 수 있다.
- 서버가 11번 기동했다. 기동 직후 각 Keeper 의 첫 Agent Core 요청 189건 가운데 143건이, 끝나지 못한 턴의 atom 을 실었다(`restarts.json`). 그 143건 가운데 32건은 범위가 완료 경계보다 앞에서 열렸다(polisher 12597 < 12606, masc-pro-builder 2856 < 2968). 그 요청들은 Librarian 이 아직 읽지 못한 끝난 턴도 실었다.
- you-never-change 를 따라가면 이렇다.
  - 05:21 에 운영자 채팅 턴이 시작됐다.
  - 서버가 06:46, 07:21, 07:52, 08:58 에 다시 떴고, 그때마다 돌던 턴이 취소됐다.
  - 취소된 턴은 턴 번호를 올리지 않는다. 그래서 다섯 턴이 모두 `total_turns=612` 로 찍혔다. 재기동 뒤 네 턴은 모두 `turn_boundary=boundary:3887` 을 썼다.
  - 그 네 턴의 첫 요청은 atom 45, 89, 157, 275개였다(194 KB, 325 KB, 557 KB, 971 KB).
  - 09:00 에 시작한 턴이 09:17 에 끝났다. 다음 요청의 경계는 4210 이었고, 다섯 턴의 atom 324개(3887..4211)가 강등되어 570 KB 로 나갔다(`carried-you-never-change.txt`).
- 앞선 측정에서 "한 턴이 234분 동안 319번 호출했다"고 적은 것은 이 다섯 턴을 하나로 센 것이었다. 기동마다 나눠 세면 10-06 의 턴은 1,291개다. 턴당 호출은 p50 1, p90 23, p99 80, 최대 123 이다(`turns.json`).

- 기동마다 나눠 센 10-06 에 호출 50번 이상인 턴은 35개, 100번 이상은 3개였다. 공식 클라이언트 턴은 한 번으로 센다(그 턴은 `turn=` 줄을 턴마다 한 번 쓴다).

### 2.4 공식 클라이언트

- 10:11 에 첫 atom 이 같은(4238) 요청 둘이 나갔다. Agent Core 런타임으로는 atom 136개 191,230 바이트, Muse 씨앗으로는 atom 137개 848,823 바이트였다(`seed-by-path.txt`). 공식 쪽은 atom 하나와 하던 일 메시지를 더 실으므로, 같은 입력의 비교는 아니다.
- Muse 세션 하나가 Keeper 턴 33개를 이어 돌았다. 모델 호출 447번, 입력 1억 3,980만 토큰(94.7% 캐시), 호출당 평균 312,796, 최대 393,922 토큰이었다(`muse-session.json`).
- 33턴이 각각 7만·10만·13만 토큰 씨앗으로 새 세션을 열었다면, 같은 호출이 실제 입력의 28%·38%·48% 를 실었을 것이다. 턴 안의 캐시와 호스트 기억이 나빠지는 비용을 빼서 새 세션이 실제보다 싸 보인다. 절감의 상한이다(`muse-fresh.json`).

### 2.5 이 측정이 보여주지 못하는 것

- 구독 quota(Muse, Claude Code, Ollama Cloud)는 캐시 토큰을 어떻게 세는지 공개하지 않는다. 토큰 합계는 quota 가 아니다.
- 로그의 `tokens=` 는 입력과 출력 합이다(`keeper_hooks_agent_core.ml` 의 `total_tok`). 입력만 따로 더하지 않았다.
- `transmitted_bytes` 는 masc 의 메시지 인코딩으로 잰 값이고 reasoning 블록을 포함한다. 와이어 직렬화는 모델 행이 재전송하지 않는 reasoning 을 뺀다. ollama_cloud 의 deepseek-v4 행은 마지막 user 메시지 뒤의 도구 호출 메시지에만 reasoning 을 싣는다(`reasoning_replay = "latest_user_turn_tool_calls"`). §2.1 의 요청은 모두 user 메시지에서 열렸으므로, 기록된 바이트는 와이어보다 그 reasoning 만큼 크다.
- 21:00 턴이 앞 턴의 호출을 실었기 때문에 루프를 이어 갔다는 것은 가설이다. 잰 것이 없다.

## 3. 왜 이렇게 되나

### 3.1 끝나지 못한 턴은 다음 턴이 이어받는다

- 턴 끝 줄은 끝난 턴만 쓴다. 실패하거나 취소된 턴은 줄을 쓰지 않는다(창 RFC §13.9, `keeper_turn_boundaries.mli`).
- 단계 저장 뒤에 실패하면 같은 시도에서 다시 하지 않는다. 다음 Keeper 사이클이 그 일을 잇는다(`keeper_turn_driver.ml` 의 "retry deferred after typed AGENT_CORE checkpoint stage … the next keeper cycle remains eligible").
- 그래서 경계는 마지막으로 끝난 턴에 선다. #37602 가 이것을 일부러 정했다. 끝난 턴의 증거로 경계를 정하고, 이어받은 일은 강등하지 않는다(`test_completed_boundary_protects_resumed_work`). Librarian RFC §4.6 도 "턴의 시작은 적지 않는다"고 적는다. resume·HITL 턴은 user 메시지가 이미 checkpoint 에 들어간 채로 시작하므로, 턴의 시작이 안전한 하한이 아니다.
- Librarian 은 줄이 적은 위치만 읽는다(I1, I3). 이어받은 구간은 다음에 끝까지 간 턴의 줄이 시작 위치(`Continued_history_from`, #37061)를 적을 때 읽을 수 있게 된다.
- 이 설계의 비용에는 바닥이 없다. 턴이 계속 끊기면 이어받는 구간이 계속 자란다. 재기동이 잦은 날(10-06 에 11번)이나, sangsu 처럼 끊긴 턴 자체가 1,600번 넘게 호출한 경우가 그렇다.

### 3.2 크기 거절은 quota 를 지켜 주지 않는다

- 크기는 공급자가 판정한다(창 RFC §1 의 2). Librarian 지점보다 앞에서 연 요청이 크기로 거절되면 턴 경계부터 한 번 더 보낸다. 이 규칙은 #38316(2026-09-24)이 넣었다(Librarian RFC §4.10 의 1·2).
- 1M 토큰 창 모델은 거의 1M 토큰까지 받아 준다. sangsu 의 glm-5.3-flash 호출은 입력과 출력 합 1,015,783 토큰까지 받아들여졌다. 거절은 그 언저리에서야 오고, 그 전의 호출은 모두 quota 를 쓴다.
- you-never-change 와 sangsu 의 큰 요청은 Librarian 이 밀려서가 아니었다. 범위는 둘 다 Librarian 스냅숏에서 열렸고, 그 자리는 마지막 완료 경계와 같았다(3887, 2077). 크기는 그 뒤의 이어받은 구간에서 나왔다. 기동 직후 요청 가운데 32건은 경계보다 앞에서 열렸으므로(§2.1), 다른 Keeper 에서는 Librarian 밀림도 함께 있었다.

### 3.3 턴 안

- RFC-0363 §3.4.1: 강등 경계는 지금 턴의 첫 atom 이다. 지금 턴의 결과는 원문으로 나가고, 크기 거절 뒤에만 마커가 된다(#28845 를 거절 경로로 옮긴 것, 창 RFC §11 의 1d).
- 창 RFC §13.6(Active)은 지금 턴의 결과도 조립 때 마커로 보내기로 정했다. 그 코드는 아직 없다.
- §13.6 의 시작 조건(§13.7)은 둘이다. Librarian RFC §7 (라)의 스냅숏은 라이브 요청이 `origin=librarian_snapshot` 으로 쓰고 있다. 밀린 턴 수(I4)는 `unread_turns` 로 TUI 와 대시보드에 뜬다. 둘 다 채워진 것으로 보인다. 구현 PR 이 다시 확인한다.
- Draft 인 durable-tool-result-markers §6 은 지금 턴의 결과를 원문으로 저장하라고 적는다. 그 이유로 든 문장은 전송 이야기다. 쓰고 있는 결과를 마커로 받으면 모델이 자기 출력을 읽으려 artifact read 를 부른다는 것이다(RFC-0363 §4 안 B 의 문제).

### 3.4 공식 클라이언트

- 공식 레인은 강등하지 않는다(`context_owner=official_client applied=false`). RFC-0460 §7.2 는 "얼마나 줄어드는지 먼저 재고 착수한다"고 적었고, 잴 값은 §9 의 넷째 항목이 정했다. 요약을 싣지 못한 턴 가운데 강등이 살릴 턴의 몫이다. `docs/librarian-continuity-snapshot.md` 도 공식 클라이언트에는 그 투영을 쓰지 않는다고 적는다.
- 호스트 세션은 턴을 넘어 이어진다. 호스트가 자기 compaction 을 할 때까지 앞 턴이 모두 남는다. official-client-conversation §5.7 이 매 턴 새 세션을 제안했고, 그 앞에 §5.6(공식 턴의 대화를 Keeper 체크포인트에 남기기)이 있어야 한다.

## 4. 설계

### 4.1 D1 — 모델이 답한 도구 결과는 조립 때 마커가 된다

- 규칙: 경계 뒤의 구간에서, 뒤에 assistant 메시지가 온 도구 결과는 조립 때 마커로 나간다. 모델이 읽고 답한 결과다. 마지막 assistant 메시지 뒤의 결과는 원문으로 나간다. 크기 조건은 RFC-0363 §3.1 의 4 그대로다.
- 경계는 고른 숫자가 아니라 일어난 일(모델의 답)이다.
- 턴 경계는 옮기지 않는다. 경계를 끝난 턴의 증거로 정하는 #37602 와, 턴의 시작을 적지 않는 Librarian RFC §4.6 은 그대로다. D1 은 경계 뒤 구간 안에서 "답했는가"로만 가른다. 그래서 이어받은 구간에도 같이 쓰인다.
  - 규칙은 위치로만 가른다. 뒤에 assistant 메시지가 없는 결과, 곧 마지막 단계의 결과만 원문으로 남는다.
  - 이어받은 구간에서 이미 답한 결과는 마커가 된다. you-never-change 에서 재기동 뒤 네 턴이 그대로 싣던 결과가 여기에 든다.
  - 지연 결과도 같은 규칙을 따른다. 일반 지연(`Deferred_tool_result`)은 provider 루프를 멈추지 않으므로, 모델이 그 뒤에 답하면 그 자리표시 결과도 답한 결과가 된다. 포화 마커보다 크면 마커로 나간다. typed external-effect defer 만 루프를 멈추고 마지막에 남는다(`keeper_tools_agent_core_bundle.ml`). finalize 가 그 뒤에 assistant 메시지를 붙이는지는 확인하지 않았다.
  - HITL 이 풀린 턴에서도 같다. 승인 전에 모델이 이미 답한 결과(예: 승인 대상 쓰기를 이끈 읽기)는 마커가 된다. 일부러 좁힌 것이다. 지연 결과를 타입으로 늘 원문에 둘지는 §9 에 남긴다.
- 바뀌는 것도 있다. #37602 는 경계 뒤의 일을 모두 원문으로 지켰다. D1 뒤에는 그 가운데 모델이 이미 답한 결과를 지키지 않는다. 지금 턴의 결과를 조립 때 마커로 보내는 것은 창 RFC §13.6 이 이미 정한 방향이다. D1 은 그 범위를 "답했는가"로 좁힌 것이다. 옛 보호를 적은 두 곳도 같이 고친다. `docs/librarian-continuity-snapshot.md` 의 "완료 경계 뒤의 진행 중인 작업 … 생략하지 않는다", 그리고 `keeper_turn_driver_try_provider.mli` 의 "callers retain original bodies when no proof exists"(같은 뜻의 `.ml` 주석 포함)다.
- 창 RFC §13.6 셋째 항목에 이 경계를 적는다. RFC-0363 은 두 군데를 고친다.
  - §3.4.1 의 prefix cache 논증은 "경계는 턴당 한 번만 움직이므로"에 기댄다. D1 에서는 단계마다 바로 앞 단계의 결과가 원문에서 마커로 바뀐다. 메시지 하나의 바이트는 한 번만 바뀌고, 바뀌는 자리는 끝에서 두 단계 안쪽이다. 그 앞의 바이트 prefix 는 그대로다. 명시적 breakpoint 를 쓰는 캐시(Anthropic 의 `cache_control` 같은)에서도 맞는지는 재지 않았다. 그래서 D1 을 켜기 전에 재는 것을 착수 조건으로 둔다(아래 "착수 조건", §7).
  - §6 의 prefix 불변식("머리는 `drop` 이 바뀔 때만 바뀐다")은 D1 과 맞지 않는다. "메시지의 바이트는 원문에서 마커로 한 번만 바뀌고, 그 때는 모델이 그 결과에 답한 다음 요청이다"로 바꾼다.
- 안 B 의 걱정은 논증으로 풀리지 않는다. 모델이 같은 턴 안에서 앞 결과를 다시 보려고 `keeper_artifact_read` 를 부를 수 있다. 그래서 턴당 `keeper_artifact_read` 수와, 그 읽기가 돌려준 토큰을 D1 전후로 잰다. 다시 읽기가 돌려준 토큰이 마커가 줄인 토큰보다 많으면 D1 을 되돌린다.
- 착수 조건. 위 둘 가운데 명시적 breakpoint 캐시는 D1 을 켜기 전에 잰다. D1 을 먼저 켜고 나중에 되돌리면, 캐시 재사용이 깨지는 레인은 배포 뒤에야 손실을 드러낸다. 이 RFC 가 다루는 요청은 수십만~백만 토큰이라 그 손실이 마커의 절감을 지울 수 있다. 그래서 지원하는 provider 마다 breakpoint 위치별 cached 토큰 비율을 D1 없이 먼저 재고, 그 위치가 바뀐 결과 자리(끝에서 두 단계 안쪽)를 넘는지 본다. breakpoint 가 그 안쪽에 놓여 마커로 바뀌는 바이트를 포함하는 레인은 D1 을 켜지 않는다. 재지 못한 레인은 D1 을 켜지 않은 채로 둔다. §7 의 착수 조건이 이를 받는다.
- durable-tool-result-markers 는 저장을 다룬다. D1 은 저장을 바꾸지 않는다. 그 §6 의 이유 문장(전송 이야기)은, D1 이 정해지면 §13.6 을 가리키게 고친다.
- 효과. 결과가 큰 턴과 이어받은 구간(you-never-change 처럼 결과 p90 4.3 KB)은 줄어든다. 결과가 작은 루프(sangsu, 중앙값 641 B)는 거의 줄지 않는다. 그 경우는 #41377 이 답이다.

### 4.2 D2 — 턴 도중에는 창을 옮기지 않는다 (그대로)

- Librarian RFC §7 (나)의 두 이유가 그대로다. 방금 받은 결과를 잃고, prefix cache 가 깨진다.
- 기동마다 나눠 세면 긴 턴은 앞선 측정보다 훨씬 적다(§2.1, §2.3).
- 1,608번 호출한 턴은 루프였다. 창을 옮기면 루프가 싸질 뿐 짧아지지 않는다.
- 이어받은 구간이 자라는 문제는 D1 이 줄이는 만큼만 준다. 다음 턴이 Librarian 이 읽은 죽은 구간을 건너뛰고 시작하게 하려면, 끝나지 못한 턴의 끝을 줄로 먼저 적어야 한다. 그 안은 §5 첫 줄의 이유로 고르지 않았다. (나)의 두 이유는 턴 도중에 창을 옮기는 일에 대한 것이라 이 경우와는 따로다.
- D1 이 라이브에 들어간 뒤, 턴 길이별·이어받은 구간별 입력 토큰에서 그 몫이 여전히 크면 다시 연다. 검토할 물음이지 Gate 가 아니다.

### 4.3 D3 — 공식 클라이언트

- 씨앗 강등. §2.4 의 바이트는 참고 자료일 뿐, RFC-0460 §9 가 정한 값이 아니다. 먼저 그 값을 잰다. 요약을 싣지 못한 턴(`masc_keeper_librarian_working_state_not_carried_total`, RFC-0460 §7.1) 가운데, 강등했다면 요약이 들어갔을 턴의 몫이다.
  - 그 몫이 0 이 아니면, 그만큼이 씨앗 강등을 착수할 근거다.
  - 그 게이트는 레인이 바이트 창을 선언할 때만 값이 생긴다. 공식 레인에 창이 없으면(창 RFC §13.2) 늘 0 이고, 그때는 강등을 판단하지 못한다. 이 RFC 가 강등을 보는 이유는 요청 크기와 quota 다. 그래서 같은 첫 atom 의 씨앗 바이트와 공식 세션의 호출당 입력 토큰을 RFC-0460 §9 의 측정에 더하자고 제안한다.
  - 착수하게 되면 조건이 하나 있다. 그 공식 클라이언트에 `keeper_artifact_read` 가 실제로 주어져 있어야 한다. #37602 가 Agent Core 에 건 조건과 같다.
  - 착수하면 `docs/librarian-continuity-snapshot.md` 의 "공식 클라이언트에는 적용하지 않는다" 문장도 같이 고친다.
- 세션. official-client-conversation §5.6 을 먼저 하고, §5.7 의 세션 정책을 따른다. 묶인 이어가기만 resume 하고, 그 밖에는 새 세션을 연다.
  - 새 세션의 씨앗은 창 RFC §10.4 의 이어 보낼 범위다. §5.7 의 "씨앗을 토큰으로 자른다"는 `W` 를 전제로 했다. 창 RFC §1 의 1 이 창 크기 숫자를 없앴으므로, 그 부분은 구현 때 §5.7 에서 지운다.
  - 호스트 compaction 은 호스트의 LLM 요약이다. 매 턴 새 세션이면 거의 닿지 않는다.

## 5. 고르지 않은 안

| 안 | 고르지 않은 이유 |
|---|---|
| 턴이 시작할 때 시작 위치를 줄로 적어, 끝나지 못한 턴의 끝을 바로 적는다 | Librarian RFC §4.6 이 일부러 적지 않기로 했다. resume·HITL 턴은 user 메시지가 이미 저장된 채로 시작하므로, 그 뒤에 적힌 시작은 그 입력을 경계 앞으로 밀어낸다. #37602 의 보호(`test_completed_boundary_protects_resumed_work`)도 무너진다. atom 을 저장한 뒤 실패한 턴마다 시작 줄이 Librarian 을 깨우면, 바닥난 quota 에 회차가 하나씩 붙는다 |
| Librarian 의 마지막 회차가 실패면 이번 턴 경계부터 싣는다 | you-never-change 와 sangsu 의 큰 요청은 Librarian 이 밀려서 생긴 것이 아니었다(§3.2). "마지막 회차"가 durable·continuity·queue 갱신 중 무엇인지 정해지지 않고, `Official_range_stopped` 로 끝나는 Keeper 에서는 늘 참이 된다. 크기 거절 뒤의 경계 재전송은 #38316 이 이미 한다 |
| 바이트·토큰·호출 수 상한 | 창 RFC §1 의 1·2, 헌법의 `budget_gate`. official-client-conversation §6 도 `--max-turns` 를 고르지 않았다 |

## 6. 범위 밖으로 기록한 것

- sangsu 의 `keeper_memory_write` 루프: #41377. 도구는 `ok:true` 와 `identity_disposition: "reobserved"` 를 돌려줬고, 모델은 같은 제목을 다시 썼다.
- `keeper_chat_store: user append-once failed … Non_eio_mutex_context`. 10-05 에 39,900번, 마지막은 10-06 00:14:49Z 였다. #41237 이 고쳤다.
- Ollama Cloud 세션 한도 자체는 운영자 계정의 일이다.

## 7. 검증

착수 조건(D1 을 켜기 전에 채운다): 지원하는 provider 마다 명시적 breakpoint 위치별 cached 토큰 비율을 D1 없이 잰다(§4.1 착수 조건). breakpoint 가 마커로 바뀌는 결과 자리를 포함하거나 재지 못한 레인은 D1 을 켜지 않는다. 아래 표의 캐시 비율은 켠 뒤의 회귀 확인이지 착수 판단이 아니다.

| 결정 | 테스트 | 라이브에서 볼 값 |
|---|---|---|
| D1 | 답한 결과는 마커, 마지막 단계의 결과는 원문. 이어받은 구간과 HITL 이 풀린 턴에서도 같다. 메시지 하나의 바이트는 한 번만 바뀐다(고친 RFC-0363 §6 불변식). 경계(`demote_before`)는 그대로다. `test_completed_boundary_protects_resumed_work` 는 답한 결과와 마지막 결과로 나눠 다시 쓴다 | 턴당 `keeper_artifact_read` 수와 그 읽기가 돌려준 토큰. 호출 50번 이상인 턴과 재기동 직후 턴의 호출당 입력 토큰. 명시적 breakpoint 캐시 레인의 cached 토큰 비율 |
| D3 | 씨앗 강등을 착수하면, 공식 씨앗의 강등과 reader 제공 확인. §5.7 의 세션 정책 표 | RFC-0460 §9 넷째 항목의 몫. 세션당 호출당 입력 토큰 |

## 8. 확신도

- 높음: §3.1 의 원인(코드, 앞선 RFC, 로그가 같은 말을 한다). §2.2 의 호출 수와 토큰(로그). §2.1 의 구간 수(경계 파일).
- 중간: 21:00 턴의 79%. 고정 부분이 같다는 가정에 기대고, `reserved_bytes` 가 그 가정을 받친다.
- 낮음: D1 이 늘리는 `keeper_artifact_read` 비용. 재지 않았다.
- 낮음: 앞 턴의 호출을 실은 것이 루프를 이어 가게 했다는 가설.

## 9. 열어 둔 물음

- 이어받은 구간은 턴이 계속 끊기는 동안 바닥 없이 자란다(§3.1). D1 은 답한 결과만 줄인다. 도구 호출 인자와 assistant 텍스트는 그대로다. 끊긴 일을 지키는 것(#37602)과 이 비용 사이의 선은 운영자가 정한다.
- 재기동 하나가 Keeper 마다 돌던 턴을 끊는다(10-06 에 11번). 재기동 자체를 줄이는 일은 이 RFC 밖이다.
- 지연 결과를 타입으로 늘 원문에 둘까. 지금 D1 은 위치로만 가르므로, 모델이 답한 일반 지연 결과도 크면 마커가 된다(§4.1).
