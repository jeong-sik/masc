## 11-12 갱신: 영수증을 기다리는 비동기, 통계 시계열의 결과 바이트, 하지 않은 변경

11-12 13:40 KST(04:40Z) 기록이에요. 이 갱신이 서술하는 PR 가운데 #51412, #51424, #51429, #51375 는 열려 있고 승인 상태예요. 제품 코드를 바꾸지 않은 변경은 이 보고서 한 파일뿐이에요.

**비동기: 사용자가 (나)를 골랐고 상태 기계 RFC 가 병합됐어요.**
- 「11-11 갱신」은 비동기를 다시 열지가 사용자 결정이라고 적었어요. 사용자가 [RFC-a-keeper-works-while-a-long-execute-runs](../rfc/RFC-a-keeper-works-while-a-long-execute-runs.md)(#51303, 11-11T12:53Z 병합)의 후보 (나)를 골랐어요. 모델이 영수증 하나를 기다리겠다고 부르면 턴이 끝나고, 그 영수증이 올 때까지 같은 작업을 claim 하지 않는 설계예요.
- 코드보다 상태 기계 RFC 와 TLA+ 모델을 먼저 냈어요(#51381, 11-12T04:37Z 병합). 채팅 작업 상태에 waiting 과 ready 를 더하고 둘 다 reducer 에서는 `Queued` 로 둬요. 새 저장 필드는 실행 기록의 `receipt_obligations` 하나이고 waiting 과 ready 는 거기서 읽는 파생 상태예요. 영수증은 기다리는 작업이 소유하고 작업이 끝나는 전이에서 풀려요.
- 사용자가 정한 것: 소유 기록은 실행 기록의 새 필드(형식 `v2` 에서 `v3`), `Outbox.load` 의 소유자 인자 `~viewer` 는 필수, 출처가 없어진 request 는 typed `Source_lost` 로 닫기, 기다림은 `Execute` 의 모드가 아니라 별도 도구, 출처를 잃은 영수증의 `arguments` 는 빈 값으로 채우지 않고 `Known | Unknown` 으로 적기(outbox 영수증 형식이 바뀌어요), 다른 작업이 이미 기다리는 request 는 도구가 호출 때 거절하기.
- 영수증을 읽는 곳은 RFC 를 쓸 때 센 여섯이 아니라 구현에서 열이에요(「비동기」의 넷도 낡았어요). `~viewer` 를 필수로 두어서 호출처를 하나 빠뜨리면 컴파일이 안 돼요.
- TLA+ 모델 `KeeperReceiptWait`: cfg 14개. 정상 모델은 위반이 없어요(생성 93,108, 서로 다른 34,029 상태, 깊이 20, `-workers 1`, 작업 2·request 2·재시작 1·순찰 run 2). 버그·가드 13개는 모두 의도한 불변식이나 속성을 깨는 반례를 내요. 독립 리뷰가 모델에 재개한 작업의 재시작(소유를 지킨 채 큐로 돌아가는 길)과 한 번에 request 여럿을 기다리는 경우가 없다고 짚어서 둘 다 모델에 넣고 다시 돌렸어요. CI 는 이 모델을 돌리지 않아요(`model-check.yml` 은 수동 실행이고 `scripts/tla-check.sh` 는 `bug-models/` 를 다루지 않아요). 모델과 구현이 어긋나도 PR 검사가 알려 주지 않아요.
- 구현은 세 층이고 모두 승인됐고 PR 검사가 통과했어요(작성 시점에 병합 전). L1 #51412(소유를 보는 읽기, `~viewer`, 기록 형식 `v3`), L2a #51424(저장소와 Owner 가 waiting·ready 를 다룸), L2b #51429(기다리는 도구, 영수증이 오면 같은 작업이 이어감, `Known | Unknown`, 호출 때 거절).
- 리뷰가 잡은 결함 둘이 구현 하네스의 값을 보여 줘요. 한 턴에 wait 도구를 두 번 부르면 첫 번째만 소유 기록에 남고 두 번째 영수증을 다른 run 이 읽고 지울 수 있었어요. 낡은 sweep 이 이미 소비된 request 에 `Unfinished` 영수증을 다시 쓸 수 있었어요. 각각 목록 기록과 Owner 직렬 명령으로 고쳤고, 변이 3개(두 번째 wait 버리기, 첫 wait 만 기록, 항목 상태 무시)와 호출 때 거절을 빼는 변이 1개를 새 시험이 모두 잡았어요.

| AWS Step Functions 콜백, docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html | task token 을 외부 시스템이 받아 결과와 함께 돌려줄 때까지 기다려요. 하트비트 시간 안에 토큰이 안 오면 `States.Timeout` 으로 실패하고, 하트비트가 없으면 실행 한도(1년)까지 기다려요. 같은 토큰을 두 번 쓰면 어떻게 되는지는 페이지에 없어요 | 소유 키가 토큰이 아니라 request ID 라는 점이 달라요. 이 설계는 하트비트 시간 대신 상태(출처가 없어졌는지)로 `Source_lost` 를 판정해요. 같은 영수증 통지가 여럿 오는 경우는 모델의 `duplicate-resolve` 변이로 다뤘고, 토큰 재사용 쪽 비교는 페이지가 말하지 않아서 못 했어요 |
