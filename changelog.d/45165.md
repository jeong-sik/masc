### Fixed

- A Lane Add-on installation that failed, or is starting, stopping or detaching, is no longer reported as absent. The export and browser readings return every visible installation that cannot serve with its reason from the same read as the usable exports, and the browser host names it ("Add-on installation browser-work (package browser) failed: ...") instead of "no browser Add-on is attached". A held tool export that ended names its own installation's state, a machine screen read reports a detaching producer that no replacement serves, and a consumer's upstream read keeps the producer's failure (#45156, #45165).
- Releasing the DOS controller no longer reports success while the DOS Add-on installation is failed, starting, stopping or detaching. Its state may still hold the controller, so Keeper removal, seat departure and invite revocation now record a failed release that names the installation and why; "nothing to release" is left for when no installation declares the controller. Shared machine calls name such an installation too, and the play controller lookup keeps the call's own error (#45157, #45165).
- MCP `tools/call`, the candle appraiser and the workspace curator name a Lane Add-on installation that declares the tool but cannot serve, with its reason, instead of reporting that no Add-on provides it. The MCP answer keeps only tools the caller could have called, and a Keeper's effective tool surface lists such installations as `lane_addon_unavailable` (#45158, #45165).

### Internal

- `test_lane_addon` compiles again: the caller-marker test waited on `Lane_addon_runtime.tool_exports`, which #45158 removed, and now waits on `tool_export_reading`. The two unready-installation tests of #45156 and #45157 wait for their never-started installation to leave Inspect after Detach, since such an installation keeps no detached record. The changelog fragments of #45156, #45157 and #45158 land with this change (#45165).
