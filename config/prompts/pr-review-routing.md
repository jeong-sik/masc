# 리뷰 요청 라우팅

이 순서는 리뷰 작업 선택에 적용한다. 이번 턴의 `scheduled_admission_at_turn_entry`가 `known`이고 예약이 선택됐다면 각각 원본 요청의 대상·범위·제약·완료 조건대로 처리한다. 일반 연속이나 순회로 다른 예약을 합치지 않고 예약별 결과를 구분한다. 선택된 예약이 있는 동안 새 순회는 그 원본 요청이 허용한 범위에서만 한다. 현재 직접 요청과 보유 Task·Goal은 별도의 실제 요청·작업 범위와 제약에 따라 처리한다. 한 요청이나 작업의 결과를 다른 예약의 완료로 세지 않는다. `known`의 빈 선택이나 `unknown`만으로 과거 예약을 재개하지 않으며, `unknown`을 빈 선택으로 단정하지 않는다. 현재 요청·Task·Goal에 이어갈 일이 없고 확인된 선택 예약이나 다른 제약이 역할 순회를 제한하지 않으면 역할에 맞는 새로운 리뷰 후보를 고를 수 있다. 새 순회를 미확인 예약의 후속이나 완료로 취급하지 않는다. 리뷰 기준·독립성·기능/논리/코드 청결도 검토와 승인 가드는 그대로 따른다.

1. 직접 메시지나 Board 요청 또는 보유 Task의 PR은 먼저 GitHub REST에서 현재 `state`, `draft`, head/base와 Native Stack을 읽는다. 이미 병합되거나 닫힌 PR은 처리 종료를 한 번 알린다. 같은 턴에 다음 PR로 가는 것은 위의 작업 선택 범위에서 허용할 때뿐이다. 옛 head를 승인하거나 닫힌 PR의 요청을 반복 처리하지 않는다.
2. 그 밖의 후보 중 인증된 `gh` 계정의 `requested_reviewers`에 있는 열린 Ready PR을 먼저 처리한다. 여러 건이면 생성 시각이 오래된 순이다. 같은 head의 재검토 요청도 명시적 요청이므로 읽는다. 기존 승인 때문에 가드가 `SKIP`하면 요청도 완료됐다고 단정하지 말고 현재 요청과 리뷰를 다시 확인한다. 요청이 남았는데 승인에 영향을 주지 않고 완료할 방법을 확인하지 못했다면 미해결로 남기고 무작정 재게시하지 않는다. GitHub 요청은 배정 사실이며, 실행 중·리뷰 완료·승인이라는 뜻은 아니다.
3. 같은 GitHub 계정을 공유하는 Keeper는 공식 요청을 공동으로 가진다. 담당 대표가 최종 요청 처리를 맡고, 다른 Keeper는 자신의 렌즈를 직접 검토해 근거를 보탠다. 다른 렌즈가 같은 PR을 봤다는 이유만으로 자기 렌즈의 검토를 생략하지 않는다. Keeper 이름을 다른 독립 계정으로 세지 않는다.
4. 위의 작업 선택 범위에서 배정된 요청이 없으면 전체 열린 PR을 모든 페이지에서 읽는다. 공유 계정의 공식 요청이 같은 계정의 리뷰 제출로 목록에서 사라진 경우, 자신의 렌즈 검토나 맡은 최종 판정이 없는 범위도 후보로 찾는다. 요청과 제출은 타임라인과 리뷰 객체의 계정·시각으로 확인하고, 서명은 개별 Keeper의 완료 여부를 구분하는 데 쓴다. 이는 원래 계정 요청의 후속이므로 다른 계정·팀의 동시 요청이 있어도 그 요청을 대신 처리하지 않고 자기 역할을 수행할 수 있다. 타임라인의 명시적 요청 철회는 그 철회 범위의 후속에도 존중한다. 철회 뒤의 새 직접 요청·공식 재요청·명시적 인계는 새 지시의 범위에서 처리한다. 자신의 issue comment는 GitHub 작성 계정, 서명과 실제 렌즈 검토 근거를 확인하고, 자기 소유를 확인할 수 없으면 미확인으로 기록한다. 자신의 서명된 issue comment가 있고 현재 head·reviewed base·canonical diff identity·Native Stack scope에 결속된 자신의 제출·재조회 COMMENT 리뷰가 없거나, 그 리뷰에 반영되지 않은 새 지적·미검토 범위가 있는 PR은 다른 계정·팀의 현재 요청과 무관하게 자신의 후속 후보로 삼는다. 현재 범위를 다시 검토하고 이전 의견과의 관계를 밝힌다. 이 후속은 다른 계정의 요청이나 판정을 대신 완료하지 않는다. 과거 공식 요청 없이 같은 계정의 서명된 리뷰만 있는 경우에는 다른 계정·팀의 현재 요청이 없는 PR에서 후속 후보를 찾는다. 그 밖에는 아무에게도 공식 리뷰가 없고 사용자·팀 리뷰 요청도 없는 Ready PR을 고른다. 이력이나 범위를 읽지 못했다면 미검토나 완료로 단정하지 않고 미확인으로 기록한다. 읽은 리뷰에 서명이 없다면 이전 렌즈의 담당자는 미확인으로 두고 자신의 렌즈를 직접 검토할 수 있다. 각 후보는 오래된 순으로 처리한다. 다른 계정에 배정된 PR을 대신 맡는 것은 직접 요청, 기존 Task, 그 계정의 요청 실패 또는 명시적 인계가 있을 때뿐이다. 게시가 막히면 원인을 한 번 기록하고, 위의 작업 선택 범위에서 허용할 때만 다음 후보로 간다.
5. CR은 실제 작성한 Keeper가 담당한다. 코드가 바뀌면 원작성 Keeper에게 재리뷰를 요청한다. 같은 GitHub 계정을 공유해도 다른 Keeper의 CR을 대신 대체하거나 해제하지 않는다. 리뷰 서명은 작성자에 대한 주장이므로 실제 작성자를 확인할 수 없다면 미확인으로 남긴다. 같은 head의 CR은 기본적으로 작성자의 수정/설명 대기이며, 명시적 재검토 요청이 있으면 다시 읽는다. 원작성 Keeper의 후속 판정이나 권한 있는 해제 결과를 재조회한다. 다른 계정의 PASS나 초록 CI로 CR이나 미해결 FAIL/HOLD가 해제됐다고 보지 않는다.
6. 검토·게시 직전에 head/base/diff/stack을 다시 읽는다. 이전 검토는 같은 범위에서만 재사용한다. 요청이 목록에서 사라졌다고 완료로 세지 말고 실제 GitHub 리뷰를 확인한다. 승인·CR·COMMENT·미게시·조회 실패를 구분해 보고한다.

라우팅 담당자는 `scripts/review/review-worklist.py --repo OWNER/REPO --reviewer LOGIN`을 사용한다. 여러 독립 GitHub 계정은 `--reviewer`를 반복한다. 이 목록은 렌즈별 리뷰 본문을 대신하지 않으므로 실제 리뷰 이력도 모든 페이지에서 읽는다. 기본은 읽기만 하고, `--request`를 붙인 명시적 실행만 누락된 GitHub 리뷰 요청을 게시하고 재확인한다. 사용자·팀의 기존 요청은 지우지 않는다. 새로운 타이머나 상시 실행기를 추가하지 않는다.

## 관점별 COMMENT와 판정

- 직접 받은 요청과 이미 맡은 Task의 범위를 우선한다. 여러 PR을 요청받았다면 각 PR에서 확인한 결과와 막힌 사유, 남은 목록을 기존 Task나 턴 기록에 남기고 다음 PR로 이어 간다.
- COMMENT 전담자는 자신의 렌즈로 diff와 필요한 원문·직접 소비자를 읽는다. 같은 head·reviewed base·canonical diff identity·Native Stack scope에 대해 자신이 같은 렌즈로 제출하고 재조회한 서명된 COMMENT 리뷰가 있고 새 지적이나 미검토 범위가 없으면 중복 게시하지 않는다. 자신의 일반 issue comment만 있다면 현재 범위와 기존 근거를 다시 확인하고 COMMENT 리뷰를 제출한다. 명시적 재검토 요청은 읽고, 새 근거가 있으면 기존 검토와의 관계를 밝힌다. 다른 Keeper의 리뷰나 같은 계정의 다른 렌즈 COMMENT는 자신의 리뷰를 대신하지 않는다.
- 렌즈 검토를 마치면 GitHub PR reviews API에 `event=COMMENT`와 검토한 head의 `commit_id`를 넣어 제출한다. 역할에 지정된 서명, reviewed base SHA·canonical diff identity·Native Stack scope, 실제 읽은 범위와 근거, 확인하지 못한 사항을 적는다. 막음 의견을 찾지 못했다면 해당 렌즈의 결과로 밝힌다. 막음 COMMENT 자체는 공식 변경 요청이나 가드가 인식한 차단 판정이 아니다. 현재 계정의 담당자나 명시적으로 인계받은 판정자가 PR 작성자·내용 커밋과 독립적인지 및 권한이 있는지 확인한다. 가능하면 그 담당자에게, 불가능하면 독립적인 다른 담당자에게 근거를 인계한다. 재판정 확인 전까지 미해결로 기록하고, 독립적인 담당자를 확인하지 못하면 미확인으로 둔다. 일반 issue comment와 스레드 답글은 제출된 COMMENT 리뷰와 구분한다.
- COMMENT 본문은 검토 의견이나 인계로 표현하고 공식 APPROVE나 CHANGE REQUEST를 이미 제출한 것처럼 쓰지 않는다. 제출한 리뷰의 ID·`state=COMMENTED`·`commit_id`·서명과 현재 head·reviewed base·canonical diff identity·Native Stack scope를 다시 확인한다. 어느 범위라도 바뀌었다면 제출한 리뷰는 그때의 이전 범위로 기록한다. 제출 결과가 불명확하면 실행 영수증과 기존 리뷰를 확인한다. 리뷰가 보이지 않는다는 조회만으로 미게시를 단정하지 않으며 효과의 성공 또는 미실행이 확인되기 전에는 재게시하지 않는다. 읽지 못한 범위나 인증·실행 장애는 완료로 보고하지 않는다.
- 최종 판정자는 기존 승인 가드와 판정 규칙을 따른다. 공식 판정의 첫 줄과 가드 footer는 판정에만 쓴다. `approve-guard.sh --body`에는 판정과 리뷰 근거만 적고 `review-scope:`와 `approve-guard:` 줄을 넣지 않는다. 가드가 게시할 때 두 줄을 붙인다. `--print-footer`는 확인용이며 그 출력을 `--body`에 복사하지 않는다. Draft나 작성자 계정 때문에 판정을 제출할 수 없더라도 실제 렌즈 검토를 마쳤다면 렌즈 서명으로 시작하는 COMMENT를 남긴다. 역할에 별도 서명이 없다면 첫 줄을 `[<Keeper 이름>] head <40자 sha>`로 쓴다. 인계가 필요하면 실제 인증된 GitHub 계정과 PR 작성자·내용 커밋을 확인해 독립적으로 판정할 수 있는 담당자를 찾고, 확인할 수 없다면 미확인으로 둔다. COMMENT는 승인이나 변경 요청을 대신하지 않는다.
- 아티팩트를 읽을 때 성공적으로 받은 동일 `sha256`·`offset`·`max_bytes` 페이지는 현재 턴의 결과를 재사용한다. 이어 읽어야 할 때만 응답의 `next_offset`으로 진행한다. 다른 길이의 요청이나 실패 응답은 동일한 성공 페이지로 취급하지 않는다.
