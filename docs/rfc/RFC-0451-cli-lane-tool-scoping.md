# RFC-0451 — CLI 레인의 도구 집합은 턴 시작에 정해진다

- Status: Draft
- 선행: RFC-attached-service-tool-scoping (Accepted, 2026-08-31). 이 문서는 그 RFC 가 **범위 밖으로 남긴 한 줄**을 다시 연다.
- 경계: 그 RFC 는 "매 요청 전량 적재를 그만둔다" 를 agent_core 레인에서 닫았다. 이 문서는 닫히지 않은 레인만 다룬다. 지연 적재를 CLI 레인에 이식하자는 것이 **아니다** — 그건 전송 제약상 불가능하고, §2 가 왜인지 적는다.

## 0. Summary

선행 RFC 의 실측표 마지막 줄은 이렇다.

| keeper | 전 | 후 |
|---|---|---|
| analyst | 133개 127,314B | 86개 85,967B |
| edgar.a.poe | 145개 141,702B | 94개 94,325B |
| **rondo · taskmaster** | **133개** | **133개 — CLI 레인, 지연 불가(설계대로)** |

CLI 레인은 아무것도 못 돌려받았다. 그리고 오늘 함대의 주력이 그 레인이다.

지금 모델이 보는 표면은 **113,822 바이트 / 133개**다. 그중 **77개, 선언 텍스트 82,269 바이트**가 자기 파일에 `defer_loading = true` 라고 적어 두었다. 즉 **매 요청의 약 72% 가 "나는 매 요청에 실릴 필요 없다" 고 스스로 선언한 도구들**이고, CLI 레인에서는 그 선언이 아무 일도 하지 않는다.

이 문서의 제안: **CLI 레인에서 `defer_loading` 을 "턴이 시작될 때 고른다" 로 읽는다.** 턴 중에 넓히는 것이 아니라, 턴이 시작되기 전에 이 Keeper 가 무엇을 들고 갈지 정한다.

**개정 1 (2026-09-16).** 무엇을 들고 갈지는 **호출 기록이 도구 하나 단위로** 정한다. 무리 단위 선언(옛 §4.2)은 뺐다. 무리로 주면 안 쓰는 것이 같이 실린다 — critic 은 `masc_msx_press` 를 매 요청에 지고 다니면서 2주 동안 한 번도 부르지 않았다(§8).

그 사이 표면은 더 커졌다. 2026-09-16 기준 CLI 레인은 Keeper 마다 **145~203개, 128,968~191,011 바이트**를 싣는다. 145개·128,968 바이트짜리 표면은 공급자 캐시에서 **50,210 토큰**으로 읽혔다. 선언한 전송 창이 85,000 토큰이므로, 도구 스키마만으로 창의 59~87% 다.

## 1. 지금 무엇이 도구를 고르는가

Keeper 하나의 턴 도구 집합은 `Keeper_capability_surface.create` 가 정한다. 인자는 하나뿐이다.

```ocaml
val create : tool_deny:string list -> ... -> t
```

`tool_deny` 는 **거부 목록**이다. 프로필이 이름을 대고 빼지 않으면 모든 Keeper 가 모든 모델 가시 도구를 든다. 허용 목록은 없다.

그래서 표면 증가를 막는 유일한 장치가 전역 바이트 상한(`test_keeper_tool_schema_bytes.ml`)이다. 상한은 범위 지정의 대역이지 범위 지정이 아니다. 도구가 하나 늘 때마다 숫자를 올리고 "무엇을 샀는지" 를 적는 일이 반복되는 이유다 — 파일에 그 기록이 아홉 번 쌓여 있다.

## 2. 왜 CLI 레인은 지연 적재를 못 하는가 (기존 판단은 옳다)

agent_core 레인의 지연 적재는 턴 중간에 도구를 **넓히는** 것으로 동작한다 (`Agent.extend_tools`). CLI 레인에는 그 동작을 실어 나를 채널이 없다. `runtime_official_client_mcp.ml` 이 그 이유를 정확히 적어 두었다:

- `handle_message` 는 `response : Yojson.Safe.t option` 을 돌려준다 — 요청에 답할 뿐 먼저 말하지 않는다.
- HTTP 전송은 GET 에 405 로 답한다. SSE 스트림이 없다.
- Claude Code 전송은 `control_response` 만 되돌린다.

그래서 이 서버는 `listChanged` 능력을 선언하지 않는다. MCP 2025-11-25 가 "선언했으면 `notifications/tools/list_changed` 를 보내야 한다(SHOULD)" 고 하는데 보낼 길이 없기 때문이다. **이 판단을 뒤집자는 제안이 아니다.** 전송에 서버→클라이언트 채널을 내는 일은 별도 축이고, 이 문서는 그것 없이 얻을 수 있는 것을 다룬다.

## 3. 그런데 고를 수는 있다

`tools/list` 응답은 이미 함수다.

```ocaml
tool_specs : (unit -> Yojson.Safe.t list) -> ...
```

같은 주석이 "`tool_specs` 는 턴이 시작될 때 묶인 불변 목록을 닫는다" 고 적는다. 그러니 **그 목록을 무엇으로 묶느냐**는 열려 있다. 턴이 시작될 때 정해지기만 하면 된다.

`call_tool` 도 목록과 독립이다.

```ocaml
call_tool : (name:string -> call_id:string -> arguments:Yojson.Safe.t -> tool_result option)
```

이름으로 디스패치하고, 목록에 있었는지 묻지 않는다. 즉 좁힌 목록은 모델이 **보는** 것을 줄이지 부를 수 있는 것을 끊지 않는다. (그 성질에 기대는 설계를 하자는 뜻은 아니다. 다만 좁히기가 디스패치를 깨지 않는다는 사실이다.)

## 4. 제안

### 4.1 CLI 레인에서 `defer_loading = true` 는 "이 Keeper 가 부른 적 있으면 탄다"

`Always_loaded` 도구는 지금처럼 전부 탄다. `Deferrable` 도구는 **그 Keeper 의 호출 기록이 이름을 대는 경우에만** 탄다.

허용 목록을 사람이 적지 않는다. 적게 하면 아무도 안 적는다는 판단은 그대로 맞다. 다만 적어 줄 것이 이미 있다 — `tool_calls/` 에 어느 Keeper 가 무엇을 언제 불렀는지 남는다.

### 4.2 무리가 아니라 도구 하나씩

턴 시작에 묶는 목록은 이렇게 만든다.

```
목록 = Always_loaded
     + 이 Keeper 가 최근 K턴 안에 부른 Deferrable 도구 (이름 하나씩)
     + 이름을 찾는 목록 도구 하나
```

- **무리는 쓰지 않는다.** 무리는 "browser 를 켜면 여섯 개가 같이 탄다" 인데, 실제로는 Keeper 마다 그중 한두 개만 쓴다. critic 은 145개를 싣고 55개를 썼다(§8).
- **못 실린 도구도 부를 수 있다.** `call_tool` 은 목록에 없어도 이름으로 디스패치한다(§3). 그 호출이 기록에 남으면 **다음 턴 목록에 그 도구 한 개만** 들어온다. 무리가 따라오지 않는다.
- **이름을 찾는 길**은 이름과 한 줄 설명만 주는 목록 도구 하나다. 스키마 하나 값으로 "무엇이 있는지" 를 연다.
- **빠지는 길**은 같은 규칙의 뒷면이다. 최근 K턴 안에 호출이 없으면 다음 턴부터 안 탄다. 날짜가 아니라 **턴 수**로 센다.

읽는 자리: 턴 시작에 필요한 것은 "이 Keeper 가 최근 K턴 안에 부른 도구 이름" 하나다. 원본은 `tool_calls/` 이고, 매 턴 전부 훑을 수는 없다. 대시보드가 이미 Keeper 별 파생 캐시를 그 기록 위에 두고 자기 append 에만 무효화한다(#36762). 같은 자리에서 답한다.

### 4.3 기본값은 무엇인가

선언할 값은 **K 하나**다. 새 Keeper 는 호출 기록이 없으므로 `Always_loaded` 와 목록 도구로 시작하고, 자기가 부른 것을 하나씩 얻는다.

- K 는 턴 수다. 시작값은 500턴을 제안한다. 근거는 §8 의 사용 분포이고, §5 의 "없는 도구 호출" 수로 맞춘다.
- 옛 A/B 갈래(전부 빼기 / 전부 넣기)는 필요 없다. 둘 다 무리 단위 판단이었다.
- 회귀 위험은 "조용히 못 쓰게 된다" 가 아니라 "한 턴 늦게 실린다" 로 바뀐다. 첫 호출은 목록 없이도 실행되기 때문이다.

## 5. 판정 기준

- CLI 레인 Keeper 하나의 요청 스키마 바이트가 줄어야 한다. 2026-09-16 시작점은 Keeper 마다 128,968~191,011B / 145~203개다(§8).
- 같은 Keeper 의 도구 호출 실패가 늘지 않아야 한다. 목록에 없는 도구를 부른 횟수는 따로 센다. 그 수가 0 에 가까우면 K 가 넉넉한 것이고, 계속 늘면 K 를 올린다. 이 호출은 실행되므로 실패가 아니다.
- 2주에 한 번 부른 도구가 Keeper 마다 6~17개 있다(§8). 이 도구들이 K턴 창에서 살아남는지 본다.
- 전역 상한(`ceiling_bytes`)은 **CLI 레인 최악값**으로 남는다. 이 RFC 가 성공해도 그 숫자는 안 줄어든다 — 줄어드는 건 Keeper 하나가 실제로 지는 무게다. 상한 주석이 그 구분을 말해야 한다(§6).

## 6. 지금 바로 할 수 있는 것 (이 RFC 없이)

상한 가드의 메시지가 지금 이렇게 말한다: "Every Keeper turn carries this." 사실이 아니다 — agent_core 레인 Keeper 는 선행 RFC 이후 그보다 훨씬 적게 진다(133개 → 86·94·98개). 그 숫자는 **CLI 레인 청구서**다.

가드는 그대로 두되 무엇을 재는 숫자인지 적는다. 다음 사람이 "왜 걸리는가" 를 묻는 자리가 거기다.

## 7. 하지 않는 것

- CLI 전송에 서버→클라이언트 채널을 내지 않는다. 그건 이 문서의 축이 아니다.
- provider 스키마를 줄여 쓰지 않는다 (선행 RFC §6 그대로).
- 상한을 올려서 해결하지 않는다. 올리는 일은 도구가 늘 때의 기록이지 이 문제의 답이 아니다.
- 무리 선언을 만들지 않는다(개정 1). 도구 하나가 단위다.
