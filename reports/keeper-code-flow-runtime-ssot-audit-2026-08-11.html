1. 코드 레벨 순서도

화살표는 함수 호출/내구 commit/owner handoff 순서다. 점선이 아니라 명시적 종료 경계가 있는 곳만 “완료”로 취급한다.

1-A. 부팅과 설정 해석

01 / BOOT CLI base path와 HTTP listener 소켓을 먼저 열되, owner readiness 전에는 mutation capability를 공개하지 않는다.
02 / CONFIG config root 해석 MASC_CONFIG_DIR 또는 <base>/.masc/config에서 runtime TOML을 읽는다.
03 / DEFAULTS env > TOML > hardcoded startup-only boot override를 reader에 공급한다. hot reload는 없다.
04 / OVERRIDE typed runtime params 복원 등록 후 runtime_params.json override를 restore한다. 이는 default layer보다 우선한다.
05 / READY owner install → publish → loops single-owner actor를 설치하고 Gate/persistence를 붙인 뒤 ready, 이후 auxiliary lane을 시작한다.

근거: server_runtime_bootstrap.ml, keeper_runtime_config.mli, runtime_params.ml.

1-B. 입력에서 Keeper turn까지

01 / INTAKE chat 또는 async signal Chat은 invocation turn으로 직접 간다. Board, schedule, HITL, connector 등은 stimulus를 만든다.
02 / DURABLE FIRST event queue commit enqueue_stimulus_if_absent 성공 후에만 pending projection을 publish한다.
03 / WAKE transient wake hint payload authority는 queue다. wake은 실행 fiber를 깨우는 hint이며 payload 대체물이 아니다.
04 / OWNER CYCLE single owner + phase gate queued operation / durable stimulus 우선순위를 보고 cancel, skip, error, proceed를 결정한다.
05 / TERMINAL runtime 결과와 source 정산 success FSM, typed failure, receipt와 source ACK가 각각의 종료 contract를 닫는다.

Async lane의 실제 실행 순서

  1. Producer가 typed stimulus를 만든다.

    예: schedule은 keeper name, payload digest, due time, urgency를 가진 Schedule_due로 투영한다.

  2. persistent queue가 idempotent하게 수락한다.

    enqueue_stimulus_durable_result는 durable intake fence 안에서 저장하고 after-commit projection을 갱신한다.

  3. owner가 wake을 받고 cycle을 시작한다.

    autonomous cycle은 queued operation과 queue snapshot을 보고 waiting stimulus에 yield할 수 있다. chat lane은 이 cycle로 들어가지 않는다.

  4. phase gate 후 실제 provider/runtime adapter를 수행한다.

    runtime은 Codex app-server, Claude Code, Antigravity 또는 provider route를 선택한다. provider health 관측은 실행 결과를 대체하지 않는다.

  5. 성공·실패를 typed terminal로 정산한다.

    성공 FSM transition은 단일 success handler에서 한 번만 내고, queue source terminal/ACK는 durable commit 뒤 projection을 갱신한다.

부작용(Gate)과 resume의 별도 경로

  1. 모델이 tool/effect를 요청한다.

    일반 읽기와 외부 부작용을 같은 재시도 규칙으로 다루지 않는다.

  2. durable approval queue가 work SSOT가 된다.

    auto judge의 atomic map은 process projection일 뿐이다. approval 원본을 대체하지 않는다.

  3. 승인된 exact operation/input만 one-shot replay한다.

    indeterminate이면 재실행하지 않고 target inspection을 요구한다. 이 제약은 실세계 중복 실행을 피하기 위한 것이다.

  4. official-client resume은 native store가 소유한다.

    Codex/Claude Code adapter는 AGENT_CORE checkpoint payload를 흉내 내어 replay하지 않는다. provider의 durable session store가 start-or-resume한다.

근거: durable enqueue, terminal ACK, yield decision, single success/phase gate, official client adapter.

5. GitHub 기준: 범용 에이전트 하네스와의 타당성 비교

아래는 벤치마크 성능 비교가 아니라 각 공식 GitHub README가 드러내는 역할 경계로부터의 설계 추론이다. 즉, “일반 하네스의 해피패스에 무엇이 최소인가”를 판단하는 기준이다.

공식 하네스 공개된 역할 경계 MASC Keeper에 주는 기준 판정
OpenAI Codex 로컬 terminal에서 작업하는 coding agent/CLI 중심 프로젝트다. 한 번의 interactive request가 tools와 작업공간을 거쳐 명시적 결과를 내면 해피패스는 성립한다. fleet-wide exactness는 전제하지 않는다. 기준 충족
Keeper의 direct runtime adapter는 이를 재구현하지 않고 호출한다.
Claude Code terminal/IDE에서 codebase와 git workflow를 수행하는 agent이며 custom commands/agents 확장점을 둔다. provider-native session과 tool semantics가 존재한다. MASC가 이들의 checkpoint를 동일 형식으로 복제할 이유는 없다. 기준 충족
official-client session store가 resume을 소유하도록 한 코드와 맞다.
Orca 기존 CLI agent를 worktree/PTy에서 실행·관찰·조정하는 orchestration shell로 자신을 위치시킨다. orchestrator는 underlying agent의 semantics를 transport해야지 똑같이 재구현할 필요가 없다는 강한 비교 사례다. 정합
MASC adapter + owner/queue 경계가 이 방향과 맞다.
OpenClaw 하나의 Gateway가 sessions, tools, events, channels를 연결하는 persistent assistant/runtime을 표방한다. 다채널·비동기 입력이면 durable intake와 wake/recovery는 유용하다. 그러나 모든 derived status를 transactionally identical하게 만들 필요는 없다. 필요한 복잡도
queue-first/wake-hint 분리는 타당하다.
Hermes Agent persistent skills/memory와 자율적 agent workflow를 강조한다. 세션을 넘는 memory/skill은 필요할 수 있지만, 모델 실행 결과의 범용 exactly-once 보장은 일반 전제가 아니다. 범위 제한
durability는 input, human approval, irreversible effect에 집중해야 한다.
해피패스의 충분 조건.
(1) 입력이 한 owner에 admission 된다. (2) 필요한 workspace/session context가 전달된다. (3) 실제 runtime/tool loop가 실행된다. (4) 결과가 사용자가 이해할 terminal outcome으로 정산된다. (5) 재시작 경계에서는 intake와 이미 승인된 외부 effect만 보존적으로 회복한다.
해피패스에 불필요한 요구.
모든 provider session·dashboard·ledger·registry가 항상 동일한 스냅샷을 가져야 한다는 요구, LLM 생성 자체의 global exactly-once, 또는 Codex/Claude Code의 내부 resume을 MASC 형식으로 다시 구현하는 요구는 비용만 늘리고 truth boundary를 흐린다.

6. 발견 사항과 최소 검증 프로토콜

P1 / live
11개 runnable durable input이 3 keeper에 남아 있어 현재 end-to-end clean health는 증명되지 않았다.

14:40 KST health에서 analyst 2, rondo 4, sangsu 5였다. oldest는 약 21분이었고, queue read error와 transition outbox는 0이었다. owner summary에는 6개 in-flight turn이, 실제 로그에는 analyst가 done 및 agent completed에 도달한 trace가 있다. 14:54 KST에는 9개/5 in-flight로 감소했으므로 실행은 진행 중인 정황이다. 따라서 “storage 손상”이 아니라 liveness/settlement를 계속 확인해야 하는 운영 상태다. ACK 전후의 event-id trace 없이는 deadlock이라고 단정하지 않는다.

P1 / UX
keeper_event_queue.status=ok와 keeper_reaction_ledger.status=degraded가 같은 backlog에 대해 함께 보인다.

모순은 아니다. 전자는 queue 구조/읽기/owner 분류가 정상이라는 뜻이고, 후자는 stale policy가 durable work liveness를 degraded로 평가한 것이다. 하지만 같은 필드명 status는 operator에게 false green을 만들 수 있다. 기존 저장소를 늘리지 말고 동일 health projection에서 storage_status와 work_liveness_status를 구분하거나 reason을 상위로 승격하는 것이 최소 수정이다.

P2 / config
startup precedence 문서에 persisted Runtime_params override layer를 함께 노출할 필요가 있다.

소스상 process env > TOML > hardcoded은 default 계산 규칙이고, 이후 restore되는 typed override가 있으면 effective value를 바꾼다. 이번 라이브 값은 모두 override 없음이라 현재 불일치는 아니다. API에 has_override가 있으므로, config preview/health에도 resolved source를 한 줄로 제공하면 된다.

P2 / config
unknown runtime TOML key 무시는 forward compatibility와 operator typo 사이의 trade-off다.

unknown key를 무조건 boot failure로 바꾸기보다, exact runtime version에서 unknown key 목록을 health/boot log에 노출하고 allow-list version upgrade일 때만 suppress하는 편이 안전하다. 새 fallback chain이나 별도 SSOT는 필요 없다.

P3 / scope
profile file, installed owner, queue participant의 count가 다르다는 것은 그 자체로 버그가 아니다.

disabled/probe/lifecycle 범위가 다를 수 있다. 다만 UI가 count만 보여준다면 confusing하므로, 이름별 membership reason을 read-only export하면 운영 점검이 쉬워진다.

해피패스 타당성을 실제로 닫는 최소 6개 검증

1Path / config

health의 base path·masc root·config root가 한 base에 붙고, resolved setting source를 확인한다.

2Direct chat

단일 chat input이 owner turn → native runtime → terminal receipt를 남기는지 correlation id로 추적한다.

3Async intake

schedule 또는 board event 하나가 durable queue commit을 먼저 남기고, restart 뒤에도 동일 input이 보이는지 확인한다.

4Acceptance ≠ completion

Work_accepted 뒤 source ACK/turn terminal을 별도 assertion으로 기다린다.

5Gate recovery

승인된 effect는 exact input으로 한 번만 처리하고 indeterminate case에는 target inspection을 요구하는지 확인한다.

6Projection semantics

queue storage status와 work-liveness status를 따로 assert한다. dashboard 값은 command authority로 쓰지 않는다.

범위 결론. 이 감사에서 source-level P0 결함은 증명하지 못했다. 다만 현재 live backlog가 남아 있으므로 “모든 Keeper happy path가 정상 완료됐다”는 운영 결론도 내리지 않는다. 다음 검증은 같은 event-id에 대해 producer → queue revision → owner turn → terminal receipt/source ACK를 한 줄로 묶는 읽기 전용 trace여야 한다. 그 후에도 queue가 남으면 그때 원인별 repair를 설계한다.

7. 근거와 방법

정적 근거는 이 checkout의 exact HEAD를 대상으로 읽었고, 런타임 근거는 /health?full=1, /api/v1/runtime/params, durable queue state, 동일 세션의 structured log를 읽기 전용으로 조회했다. 어떠한 queue, config, process도 변경·재시작하지 않았다.

  • MASC exact source HEAD — 이 보고서의 local code anchor 기준.
  • single-owner install — loop ownership과 actor 설치.
  • schedule accepted boundary — enqueue acceptance는 final completion이 아님.
  • Gate projection vs work SSOT 및 indeterminate replay policy.
  • OpenAI Codex — local terminal coding-agent comparison boundary.
  • Anthropic Claude Code — terminal/IDE agent and plugin boundary.
  • Stably Orca — worktree/PTy orchestration over existing CLI agents.
  • OpenClaw — gateway/session/tool/event/channel runtime comparison.
  • Nous Hermes Agent — persistent skill/memory agent comparison.
