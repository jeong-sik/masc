# RFC: Board attention 은 이벤트 하나를 Jev 에게 한 번에 묻는다

Board 이벤트 하나는 관심사가 있는 Keeper 약 24명에게 복사되고, 복사본마다 Jev(TypeSafe AI)를 한 번씩 부른다.
이 RFC 는 이벤트가 기록될 때 Jev 를 한 번만 부르고, Keeper 마다 질문 하나씩을 한 요청에 싣자고 제안한다.
확신 있는 답은 그 자리에서 확정하고, 대기열에는 LLM 이 필요한 후보만 남긴다.

- 다루는 것: 이벤트 단위 Jev 호출, 그 호출을 어디서 하는지, 실패했을 때의 경로, 남은 병목.
- 다루지 않는 것: Jev 판정 기준(`[typesafeai] board_attention_confidence_floor`), 판정 프롬프트, 원장 크기(RFC-0424).
- 근거 기준: `origin/main` = `246e335ade` (2026-10-01). 데이터는 이 컴퓨터에서 도는 서버의 `~/me/.masc` 에서 읽었다.
- 측정 스크립트: `docs/evidence/board-attention-jev-20261001/measure.py`.
  `before.txt` 는 #40413 전(2026-09-30T16:30Z), `after-jev-gate.txt` 는 #40413·#40428 배포 뒤(2026-09-30T21:13Z)다.
  †가 붙은 값은 스크립트가 아니라 같은 날 로그에서 따로 잰 값이다.
- 표시: **[사실]** 은 코드나 데이터에서 확인한 것, **[제안]** 은 이 RFC 가 정하려는 것, **[확인 필요]** 는 아직 확인하지 못한 것이다.

## 0. 앞선 판과 달라진 것

2판은 LLM 레인에 (Keeper, 글) 단위로 묶어 보내자고 했다. 판정 대부분이 GLM 한 슬롯을 거쳤기 때문이다.
그 뒤 #40413 과 #40428 이 Jev 의 확신 있는 답을 그대로 확정하게 했고, GLM 으로 가는 후보가 3~4% 로 줄었다.
LLM 묶음 판정은 동기가 사라져서 뺐다(3절). 이 판은 남은 비용인 Jev 호출 수와, 새로 드러난 병목을 다룬다.

## 1. 지금 모양

### 1.1 흐름

**[사실]**

1. push 경로가 Board 이벤트마다 등록된 Keeper 를 모두 돈다(`lib/keeper/keeper_keepalive_signal.ml:672-680`).
   판정이 필요한 Keeper 마다 후보를 하나씩 기록하고 그 Keeper 의 워커를 깨운다(`:743-750`, `record_board_attention_candidate` `:398-420`).
2. Keeper 마다 워커 하나가 가장 오래된 후보부터 하나씩 처리한다.
3. 워커는 후보마다 Jev 를 부른다. 요청에는 후보 하나와 그 Keeper 의 이름·관심사가 들어간다
   (`lib/typesafeai/typesafeai_board_attention.ml` `judge_candidate`).
4. Jev 답의 confidence 가 기준 이상이면 확정하고, 아니면 `board_attention_exact` LLM 레인으로 보낸다(#40413).
   재큐된 후보도 같다(#40428).

### 1.2 측정

**[사실]**

| 항목 | #40413 전 | 배포 뒤 |
|---|---|---|
| Board 이벤트 / 판정 후보 (24시간) | 776 / 18,338 | 837 / 19,587 |
| 정산 출처 (24시간) | LLM 7,122, Jev 3,260 | LLM 7,047(대부분 배포 전), Jev 21,613 |
| 배포 뒤 판정 17,274건의 Jev 답† | — | 관련 없음 14,555, 관련 있음 1,918, 기준 아래 795, 실패 6 |
| 처리량† | 분당 5~10건 | 분당 수십~수백 건 |
| 실행 가능한 대기 후보 | 16,627 | 1,336 |
| 새 후보가 확정되기까지(최근 1시간 기록분)† | 중앙값 13.5시간(정산분 기준) | 중앙값 0.4초, p90 958초 |

남은 대기 1,336건 가운데 669건은 일시정지된 `rust-hwp-guy`, 395건은 설정이 지워진 `lane-smith` 의 것이다(1.3의 다).

### 1.3 남은 것

**가. Jev 호출 수가 후보 수와 같다.** 이벤트 837개에 호출 약 19,600번이다. 같은 신호를 24번 보낸다.

**나. p90 958초.** Keeper 워커는 후보를 차례로 처리한다. 앞 후보가 LLM 으로 가면 GLM 칸을 기다리는 동안,
Jev 로 바로 끝날 뒤 후보들도 함께 기다린다. 그 GLM 칸은 태스크 검증 레인이 거의 늘 차지하고 있다.

- `glm-coding` 계정은 동시 4칸이다. 칸은 (provider 종류, base_url, API 키) 로 나뉘어서
  `board_attention_exact`, `verifier_exact`, `hitl_auto_judge`, 턴 failover 가 한 줄에 선다
  (`packages/agent_core/lib/llm_provider/provider_admission.ml:12-17`, FIFO `slot_scheduler.mli:1-3`).
- 배포 뒤 3시간 40분 동안 검증 레인이 이 슬롯에서 "900초 동안 진전 없음"으로 76번 실패했다†.
  24시간으로는 326번이고, Task 검증 한 건의 p50 은 815초다†.
- **[확인 필요]** 한 번 실패할 때마다 칸을 900초 잡는지. 그렇다면 평균 4칸을 넘는 양이라 줄이 늘 찬다.

**다. 판정 대상이 아닌 Keeper 의 후보가 쌓인다.**

- 일시정지된 Keeper 도 후보를 받는다. 워커는 깨우지 않는다. `rust-hwp-guy` 는 669건이 쌓였다.
- 설정이 지워진 `lane-smith` 는 후보 원장과 파티션 395건이 남아 있고, 한 파티션은 582분째 실행 중으로 기록돼 있다.

## 2. 제안

### 2.1 이벤트가 기록될 때 Jev 를 한 번 부른다

**[제안]** push 경로가 이벤트의 판정 대상 Keeper 를 모두 모은 뒤, Jev 요청 하나를 보낸다.

- state 에는 신호 하나만 넣는다.
- 질문은 Keeper 마다 하나다. 질문 문장에 Keeper 이름과 관심사를 넣고, 선택지는 지금과 같다(relevant, not_relevant, uncertain).
- 기준 이상인 답은 후보를 Jev 판정이 붙은 상태로 기록한다. 판정 출처는 지금과 같은 `Vendor_system_one` 이고, 요청 본문 해시는 N개 후보가 같이 쓴다.
- 기준 아래 답, uncertain, 호출 실패는 지금처럼 대기 후보로 기록한다. 워커와 LLM 레인이 이어받는다.
- `excluded_keepers` 에 있는 Keeper 는 질문에서 뺀다. 그 Keeper 의 후보는 대기 후보로 기록한다(지금 동작과 같다).

근거:

- TypeSafe 문서는 한 요청의 질문들이 같은 state 를 공유하고 동시에 평가돼서, 질문을 늘려도 응답 시간이 거의 늘지 않는다고 한다
  (https://docs.typesafe.ai/patterns/fan-out.md).
- 공식 예제는 54KB 문서에 질문 13개를 한 번에 물어서, 따로 13번 부를 때보다 12.2배 싸고 10배 빨랐다
  (https://docs.typesafe.ai/cookbooks/parallel_questions.md). 이득은 문서를 한 번만 보내는 데서 온다.

기대 효과:

- Jev 호출은 하루 약 19,600번에서 이벤트 수(약 840번) 근처로 준다. 재생(replay) 경로는 제외한 추정이다.
- Jev 로 끝나는 후보는 대기열에 들어가지 않는다. 1.3의 나에서 뒤 후보들이 앞 LLM 후보를 기다리는 일이 사라진다.

지켜야 할 것:

- push 경로의 전달을 네트워크 호출로 막지 않는다. 이벤트를 먼저 기록한 뒤, 별도 fiber 에서 Jev 를 부르고 결과로 후보를 기록한다.
  Jev 가 늦거나 실패하면 대기 후보로 기록되고 지금 경로를 탄다.
- 한 요청의 질문 수 상한은 문서에 없다. 거절되면 그 이벤트는 대기 후보 경로로 보낸다. 질문 수를 임의로 잘라 나누지 않는다.

**4단계 1번 결과 [사실]** (2026-10-01, `docs/evidence/board-attention-jev-20261001/jev-request-shape-eval.txt`):

- 실제 이벤트 13개에 Keeper 21~24명분 질문을 한 요청으로 보냈다. 모두 받아들여졌고(HTTP 200), 0.24~0.55초 걸렸다.
  입력 토큰은 이벤트당 약 5,200~6,400개로, 같은 이벤트를 Keeper 마다 따로 물은 24번(약 28,000개)의 약 1/4~1/5 이다.
- 질문을 여러 개 실어도 답은 달라지지 않았다. 같은 문구로 질문 하나씩 보낸 요청과 24명 중 23명이 같았다.
- 대신 state 모양이 답을 바꿨다. 그때 운영 요청은 state 맨 위에 그 Keeper 의 `keeper_role` 을 두었고, 그 모양에서 Jev 는 "관련 있음"을 훨씬 자주 답했다.
  최근 이벤트 10개(Keeper 228쌍)에서 두 모양이 26쌍 갈렸다. 어느 쪽 답인지 숨긴 판정자가 운영 판정 기준으로 판정하자
  신호만 둔 모양이 23건, 운영 모양이 3건 맞았다.
- #40505 가 단건 요청도 신호만 두는 모양으로 바꿨다. 그래서 2.1 을 넣어도 판정은 다시 흔들리지 않는다.
- cursor replay 경로(`keeper_world_observation.ml` 의 post_created 재생)는 지금처럼 후보 단위로 둔다.

### 2.2 검증 레인은 GLM 칸을 나눠 쓰지 않는다

**[제안]** 운영 설정에서 `verifier_exact` 를 다른 칸으로 옮긴다. 코드 변경은 없다.

- 검증 레인은 Jev 에 맞지 않는다. 읽기 도구로 증거를 확인하는 여러 턴 에이전트이고, 거절에는 이유 문장이 필요하다
  (`lib/task/anti_rationalization.mli:39-45,64-70`). Jev 답에는 자유 서술 이유가 없다.
- 설정 주석은 검증 레인에 맞는 공식 클라이언트가 Claude Code 뿐이라고 적는다(`runtime.toml` 의 `verifier_exact` 위 주석).
  지금 `cli_slots` 는 비어 있다.
- 선택지는 둘이다. Claude Code CLI 슬롯을 더하거나, 다른 API 키의 슬롯으로 옮긴다. 이미지 입력 거절 54건†도 함께 줄어든다.
- `hitl_auto_judge` 는 2026-09-23부터 게이트가 `always_allow` 라서 호출이 0건이다†. 지금은 손대지 않는다.

### 2.3 판정할 Keeper 에게만 후보를 만든다

**[제안]**

- 일시정지된 Keeper 는 후보를 만들 때 빼지 않는다. 다시 켜졌을 때 그동안의 소식을 판정받아야 한다.
  2.1 이 들어가면 이 후보들도 기록할 때 Jev 로 대부분 끝나서, 쌓이는 것은 LLM 이 필요한 후보뿐이다.
- 설정이 지워진 Keeper 의 Board attention 원장과 파티션은 Keeper 를 지울 때 함께 지운다.
  **[당시 관측, #40508 이전]** Keeper 를 지울 때 쓰는 정리 목록(`dashboard_purge_artifact_plan`)에
  Board attention 후보 원장과 파티션 원장이 없었다. 같은 목록의 주석은 메모리 파일에 대해, 남은 파일을 같은 이름의 새 Keeper 가
  물려받는다고 경고했다. 당시 Board attention 도 같은 경로여서, 같은 이름으로 `lane-smith` 를 다시 만들면 대기 395건과 격리 기록을 물려받을 수 있었다.
  **[구현 완료]** #40508 이 두 원장을 정리 목록에 더했다(`lib/keeper/keeper_shutdown_types.ml:655–661`). 같은 이름으로 다시 만든 Keeper 에게 이전 원장을 남기지 않는다.

## 3. 하지 않는 것

- LLM 레인의 (Keeper, 글) 묶음 판정(2판 제안). GLM 으로 가는 후보가 3~4% 라서 얻는 것이 작다.
- 검증 레인과 자동 승인 판정에 Jev 를 붙이기. 2.2 의 이유다.
- Keeper 마다 다른 confidence 기준.
- 질문 수 상한을 우리가 정해서 요청을 나누기.
- 오래된 후보를 시간 기준으로 버리기, 격리 자동 재큐.

## 4. 단계

1. **Jev 요청 크기 확인.** 끝났다(2.1 의 결과). 요청 모양은 #40505 로 맞췄다.
2. **push 경로 fan-out.** 2.1. 대기 후보 기록과 Jev 판정 기록을 같은 후보 원장 계약으로 쓴다.
3. **검증 레인 칸 분리.** 2.2. 운영자가 설정을 바꾸고, 바꾸기 전후로 검증 레인의 900초 실패 수를 잰다.
4. **지워진 Keeper 정리.** 2.3.

## 5. 검증

- 단위 테스트: 이벤트 하나에 Keeper N명일 때 Jev 요청이 한 번 나가고 질문이 N개인지.
  기준 이상 답은 확정으로, 아래 답·uncertain·실패는 대기로 기록되는지. `excluded_keepers` 가 질문에서 빠지는지.
  Jev 가 늦어도 push 경로 전달이 기다리지 않는지.
- 운영 측정: `measure.py` 와 로그의 `jev=` 집계. 볼 값은 하루 Jev 호출 수, 새 후보 확정 시간의 중앙값과 p90, 실행 가능한 대기 후보 수다.
- 목표 수치는 정하지 않는다.

## 6. 운영자가 정할 것

1. 2.1 처럼 이벤트 기록 시점에 외부 호출(Jev)을 하는 것을 받아들이는가. 호출은 별도 fiber 에서 하고, 실패하면 지금 경로로 간다.
2. 2.2 에서 검증 레인에 줄 칸: Claude Code CLI 슬롯인가, 다른 API 키의 슬롯인가.
3. 2.3 에서 일시정지된 Keeper 도 계속 후보를 받게 둘 것인가.

## 7. 관련 관측 (이 RFC 범위 밖)

라이브러리안 레인(`librarian_exact`)의 첫 슬롯인 `ollama_cloud` deepseek-v4-1-flash 는 Ollama 계정의 주간 한도가 다 차서
(`seven_day = 1.0`, 2026-09-30 06:33 KST부터) 한 건도 답하지 못한다†. 그래서 호출 대부분이 CLI 대체 슬롯인
`claude-sonnet-5-5-high`(약 60%)와 `codex-gpt-6-1-sol-low` 로 간다†. CLI 대체가 성공하면 앞선 429 가 로그에 남지 않는다.
