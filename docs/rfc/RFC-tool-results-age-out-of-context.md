# RFC: 도구 결과는 만든 턴에서만 원문이다

## 배경

히스토리에 쌓인 누적을 뒤에서 줄이는 장치는 없다. 그런데 인라인 상한값들은
아직 "누적은 나중에 정리된다"를 전제한다.
`max_agent_core_inline_result_bytes = 65_536` 의 주석이 그 전제를 그대로 말한다
— "This bounds context growth rather than avoiding a spill". 한 결과당 상한이지
누적 상한이 아니다.

## 측정 (sangsu, trace-1788310783624-00004, 2026-09-03)

체크포인트 7,488,862 B / 3,834 메시지.

| 역할 | 바이트 | 비중 | 개수 |
|---|---|---|---|
| tool | 3,031,526 | 59.4% | 1,750 |
| assistant | 2,006,993 | 39.3% | 1,779 |
| user | 63,465 | 1.2% | 305 |

도구 결과가 지배항이고, 그 안에서 분포가 극단적이다.

```
p50 = 204 B      p90 = 2,685 B      max = 71,785 B
16KB 초과: 50개 (2.9%) 가 tool 전체의 54.9%
16–64KB 구간: 45개, 1,315,928 B, 중앙값 26,323 B
```

**1,750개 중 45개가 도구 결과의 43%를 차지한다.** 그 45개는 CLI 레인 상한
(16KB)은 넘고 agent-core 상한(64KB)은 안 넘어 인라인으로 남은 것들이다. 종류는
`artifact_read` 페이지가 아닌 것 39개, 웹 검색 11개.

## 무엇이 틀렸나

64KB 상한 자체가 아니다. 그 값의 근거는 측정에 서 있다 — 16KB 로 낮추면 3일에
491개 결과가 blob 이 되고, 그건 "같은 턴이 만든 결과를 그 턴이 다시 가져오는"
왕복이다.

틀린 것은 **원문을 언제까지 들고 있느냐에 대한 답이 없다**는 것이다. 지금은
"영원히"다. 만든 턴에서 왕복이 아까운 것과, 200턴 뒤에도 26KB 를 지고 가는 것은
다른 질문인데 값 하나가 둘 다 답하고 있다.

## 제안

도구 결과에 수명을 준다. 만든 턴에서는 인라인 원문, 그 턴이 끝나면 blob 참조.

- 생성 턴: 지금과 동일. 모델이 바로 읽고 왕복이 없다.
- 이후 턴: `Tool_output.Stored` 마커. 필요하면 artifact 라우트로 읽는다.
- 임계값은 그대로 64KB. 바뀌는 것은 상한이 아니라 보존 기간이다.

blob 저장과 마커 인코딩은 이미 있다(`Tool_blob_store`, `Tool_bridge`,
`Tool_output.encode_for_agent_core`). 새로 만드는 것은 "턴 경계에서 지난 결과를
마커로 교체" 하나다.

무엇을 버릴지 고르는 판단은 없다. 원문은 사라지지 않고 blob 에 그대로 있으며,
컨텍스트에는 같은 내용을 가리키는 참조가 남는다. 대상은 "오래된 것"이 아니라
"이 턴이 만들지 않은 것"이고, 그 경계는 시간이 아니라 턴이다.

## 열린 질문

1. 마커로 바꾼 결과를 모델이 실제로 되읽는 빈도. 높으면 왕복을 뒤로 미룬 것뿐이다.
2. 16KB 미만 결과(1,700개, 1.37MB)는 그대로 둘 것인가. 개별로는 작지만 합은 크다.
3. assistant 메시지 2MB(39.3%)는 이 RFC 범위 밖이다. 그중 일부는 accept 가 거부한
   응답이었고 #32817 이 닫았다. 나머지의 성격은 따로 측정해야 한다.

## 측정 재현

```
python3 - <<'PY'
import json, pathlib, statistics
msgs = json.loads(pathlib.Path("<checkpoint>.json").read_text())["messages"]
tool = sorted((len(json.dumps(m, ensure_ascii=False))
               for m in msgs if m.get("role") == "tool"), reverse=True)
print(sum(tool), len(tool), statistics.median(tool))
print(sum(t for t in tool if t > 16384))
PY
```

## 측정 추가 (msx-retro-mania, 2026-11-01 ~ 2026-11-04T19:10Z)

위 측정은 글자 도구 결과(sangsu)예요. 이미지가 쌓이는 Keeper 를 같은 방식으로 쟀어요.
스크립트와 정의는 `docs/evidence/request-context-2026-11` 에 있어요. 모델에 보낸 요청의 본문 바이트(턴마다 하나 저장한 요청)와 모델 응답마다 남는 토큰 수를 읽어요.

- `msx-retro-mania` 의 저장된 요청 255개는 본문 중앙값 11.6 MB, p90 24.4 MB, 최대 118.4 MB예요. 요청마다 이미지가 중앙값 113장, 최대 1,186장 실려요. 본문 합계 상위의 다른 Keeper 7명은 중앙값 1.03~1.83 MB 이고 이미지는 거의 없어요.
- 가장 최근 이미지 1장만 남긴다고 치면, 나머지 이미지(base64 크기)가 본문에서 차지하는 몫은 이 Keeper 요청 중앙값이 81.2%예요. 이런 규칙이 지금 코드에 있다는 뜻은 아니에요.
- 이 Keeper 의 요청당 평균 입력 토큰은 491,503이고, 입력 토큰 상위의 다른 Keeper 다섯은 320,685~429,023이에요. 본문 바이트는 6~11배인데 입력 토큰은 1.15~1.53배라서, 이미지의 바이트 몫이 입력 토큰의 몫은 아니에요. 이미지 한 장의 토큰 수는 재지 못했어요.
- 지난 턴의 이미지를 지우는 코드는 이미지를 못 받는 런타임에서만 돌아요(`Keeper_vision_ingest.evict_message`). 이미지를 받는 런타임은 지난 이미지를 그대로 들고 가요.
- 11-03 07:17Z ~ 11-04 00:00Z 의 23개 요청은 본문이 118.4 MB 안팎(113.0 MiB, 14개는 바이트까지 같아요), 이미지가 1,186장이었고 그 턴은 모두 모델 응답(`usage`)을 한 번도 받지 못했어요. 한 턴(8350번)의 trace 는 시작 21초 뒤 `sse_stream_incomplete` 로 끝났어요. 같은 Keeper 가 0.8~1.9 MiB 로 보낸 8366~8375번 턴도 같은 오류로 끝나서, 요청 크기가 원인인지는 가리지 못했어요.

## 측정 추가 (저장된 요청 재생)

저장된 요청에 이 RFC 의 규칙("만든 턴이 끝나면 마커")을 대어 봤어요. 스크립트와 정의, 한계는 `docs/evidence/aged-tool-results-2026-11` 에 있어요. 바이트이고 토큰이 아니에요.

- 11-01 ~ 11-05 의 요청 4,344개(Keeper 25명, 프롬프트 8.19 GB)에서 도구 결과가 프롬프트 바이트의 57.4%(`msx-retro-mania` 제외 45.6%)이고, 현재 턴보다 앞선 도구 결과가 50.3%(43.5%)예요. 그중 2 KB 이상을 596 B 마커로 바꾸면 33.7%(22.1%)가 줄어요.
- 이 평균은 오르던 값이에요. 같은 스크립트를 하루씩 돌리면 줄어드는 몫이 11-01 1.1%, 11-02 14.8%, 11-03 41.9%, 11-04 43.5%, 11-05 51.9%예요. 오른 이유는 가리지 못했어요.
- 11-04T12:00Z 이후 창(1,650개, 3.23 GB)은 48.2%(제외 45.6%), 11-05T03:00Z 이후 24시간(824개, 1.77 GB)은 51.5%(49.4%)예요.
- 열린 질문 2: 문턱을 16 KB 에서 2 KB 로 내리면 `msx-retro-mania` 를 뺀 몫이 8.7% 에서 22.1% 로 늘어요(11-01 ~ 11-05 평균). 16 KB 미만 결과의 합이 커요.
- 요청마다 보면 줄어드는 몫이 p50 1.3%, p75 45.9%, p90 58.5%예요(11-01 ~ 11-05). 줄어드는 바이트는 1 MB 넘는 요청에 모여 있어요.

### RFC-0363 §3.4.1 개정과의 관계

이 RFC 의 "만든 턴이 끝나면 마커" 는 §3.4.1 개정(#48123, #48124, 11-04T08:53Z 병합)이 없앤 턴 경계 강등과 같은 모양이에요. 그 개정은 턴마다 캐시를 한 번 버리는 비용을 이유로 들었고, 요청이 커지는 비용(메시지 바이트 0 ~ 153%)은 캐시되니 받아들인다고 적었어요.
`keeper_turn_driver_try_provider.ml` 의 주석도 이미 보낸 메시지가 보낸 그대로 다시 나가야 한다는 규칙을 적어요. 이 RFC 는 그 규칙에 예외를 하나 달자는 제안이라서, 그 이유에 숫자로 답해야 해요.

1. 캐시. 이 규칙의 비용은 작아요.
   - 새로 늙는 결과는 직전 턴이 만든 것이라 히스토리 끝쪽에 있어요. 제공자가 다시 읽는 몫은 처음 바뀐 메시지부터 현재 턴 앞까지이고, 11-05T03:00Z 이후 24시간에 프롬프트 바이트의 1.0%(요청별 p90 3.1%, p99 16.3%)예요. 제공자가 이전 히스토리를 전부 캐시에 들고 있다고 친 상한이에요.
   - 같은 창에서 Agent Core 레인의 턴이 요청을 평균 17개(중앙값 6) 보내요. 캐시 읽기 값이 캐시 없는 읽기의 c 배일 때 손익분기 c 는 턴당 요청이 1개면 1.9%, 5개면 0.4%예요.
   - 턴 첫 요청의 캐시 적중은 이전 턴이 끝난 지 10분이 넘으면 절반 미만인 턴이 절반을 넘어요(`glm-5.3-flash` 는 30 ~ 60분 간격에서 적중 2.2%). 이 턴은 다시 읽는 비용이 거의 없어요.
   - 그래서 "턴마다 캐시를 한 번 버린다" 는 이 규칙의 비용이 아니에요. §3.4.1 개정 전 코드가 무엇을 다시 썼는지는 이 재생이 말하지 않아요.
   - front 가 움직일 때만 바꾸는 방법은 다시 읽는 비용이 0 이지만 재지 않았어요. 아낄 수 있는 것이 위 1.0% 뿐이고, 바꾸지 못하는 턴에는 줄어드는 몫을 못 얻어요.
   - 이 숫자는 앞 접두가 같으면 읽는 제공자를 가정해요. 위 24시간의 모델은 모두 `openai_compat`·`glm`·`ollama` 종류 제공자로 갔어요(`packages/agent_core/models.toml`). Anthropic API 는 breakpoint 마다 20칸까지만 일치하는 항목을 찾아요. 자동 캐싱도 같아요(Prompt caching 문서의 "How automatic prefix checking works"와 "Automatic caching", 11-06 원문 확인). 앞쪽 결과가 바뀌면 20칸 안에 이전 요청이 쓴 항목이 없을 때 메시지 부분을 다시 처리할 거예요. 문서에 이 경우의 예시는 없고 규칙에서 따진 추정이에요. `anthropic` 종류(`claude.claude-sonnet-5-5` 프로필)로 가는 Agent Core 시도는 11-05T03Z 이후 도구 호출 원장에 202턴(도구를 부른 턴 14,991개의 1.3%, 프로필 이름 기준)이고, 이 규칙의 손해는 재지 못했어요. 이 제공자에는 규칙을 나눌지 정해야 해요. `anthropic` 종류에는 손해가 하나 더 있어요. 서명된 thinking 블록은 만들어질 때의 prefix 와 달라지면 요청에서 빠져요(`reasoning_history_projection.mli` 의 `verify_prefix_binding`). 끝난 턴의 결과가 마커로 바뀌면 그 앞 턴들의 thinking 블록이 여기에 걸려요. 인자를 바꿀 때는 이 손실을 막는 점검이 있는데(`request_view` 의 `retained_prefix_reasoning_indices`) 결과에는 걸려 있지 않아요. 이 손해도 재지 못했어요.
2. 모방. §3.4.2 의 `_blob` 모양 호출은 강등된 호출 인자에서 나왔어요. 이 RFC 는 결과만 바꿔요. 모델이 결과 마커를 따라 쓰는지는 아직 안 쟀어요.

### 열린 질문 1: 끝난 턴의 마커를 되읽는 빈도 (11-08 ~ 11-10, UTC)

규칙(#49185)이 켜진 뒤의 저장된 요청에서 쟀어요. 스크립트와 정의, 한계는 `docs/evidence/aged-tool-results-2026-11` 의 `measure_marker_rereads.py` 에 있어요. Agent Core 레인(`ollama_cloud`·`glm-coding`)이고 바이트예요.

- 요청 2,619개에 실린 끝난 턴의 늙은 마커(원본 2 KB 이상 64 KB 이하) 17,829개 중 236개(1.32%)를 같은 Keeper 가 `keeper_artifact_read` 로 읽었어요. 원본 바이트로는 110.83 MB 중 1.74 MB(1.57%)이고, 읽기가 돌려준 바이트는 1.57 MB(1.42%)예요. 읽은 호출은 279번이에요.
- 원본 크기별로 읽힌 몫은 2~4 KB 1.70%, 4~8 KB 0.73%, 8~16 KB 1.63%, 16~32 KB 2.48%, 32~64 KB 3.04%예요. Keeper별로는 `sangsu` 가 883개 중 41개(4.6%)로 가장 높고, `context-reviewer` 는 2,855개 중 4개(0.14%)예요.
- 그래서 끝난 턴의 마커는 왕복을 뒤로 미룬 것이 아니에요. 늙은 마커를 다시 읽은 호출은 요청을 센 Keeper 의 `keeper_artifact_read` 3,788번 중 279번(7.4%)이에요.
- 이 값은 끝난 턴에서 마커가 된 결과의 것이에요. 만든 턴 안에서 마커로 바꾸면 모델이 방금 만든 결과를 다시 찾는 몫이 달라질 수 있고, 그 몫은 못 쟀어요. 재려면 마커로 바꾼 사건과 그 뒤의 읽기를 typed 기록으로 남겨야 해요. 장부 행에는 둘을 잇는 칸이 없어요.

## 턴이 길 때 (11-11 측정, 제안 아님)

이 RFC 의 규칙은 턴이 끝나야 일해요. 한 턴이 오래 이어지면 그 턴이 만든 결과는 끝까지 원문이에요. 도구 호출 원장(`~/me/.masc/tool_calls`)의 11-08T05:40Z ~ 11-11T05:40Z(72시간)에서 본 모양이고, 스크립트와 정의는 `docs/evidence/tool-efficiency-1111-2026-11` 의 `long_turn_shapes.py` 에 있어요.

- 원장 141,353행·8,017턴 중 100번 이상 부른 턴(긴 턴) 164개가 호출의 23.3%(32,899행)를 차지해요. 이 100은 보고서를 가르는 숫자일 뿐 어떤 규칙도 쓰지 않아요. 턴당 호출 수는 중앙값 6, p90 43, 최대 833이에요.
- 긴 턴의 호출이 많은 Keeper 는 `rondo`(긴 턴 24개, 자기 호출의 58.8%), `context-reviewer`(23개, 37.5%), `wkbl-data`(22개, 57.6%), `masc-productor-owner`(15개, 51.6%), `wkbl-front`(15개, 35.0%)예요.
- 도구 입력에서 PR 번호처럼 보이는 글(`#12345`, `/pull/12345`, `gh pr view 12345` 꼴)을 센 서로 다른 PR 수는 긴 턴에서 `context-reviewer` 가 중앙값 24개(p90 54, 최대 69), `masc-productor-owner` 13개, `rondo` 10개, `code-reviewer-uncle` 5개예요. `context-reviewer` 의 100번 미만 턴 353개는 중앙값 3개예요. 글자 세기라서 PR 마다 리뷰했는지는 몰라요. 이 Keeper 들은 긴 턴 하나가 PR 수십 개를 이어서 다뤄요.
- `wkbl-data`·`wkbl-front`·`wkbl-web-leader`·`msx-retro-mania` 의 긴 턴(합 10,899행)에는 도구 입력에 PR 번호처럼 보이는 글이 없어요. 이 Keeper 들의 일의 단위가 무엇인지는 이 측정으로 못 가렸어요.
- 같은 턴에서 같은 입력으로 다시 부른 호출이 앞 결과를 대신한 바이트는 2 KB 이상 64 KB 이하 결과 346.3 MB 중 34.7 MB(10.0%)예요. 그중 28.3 MB(82%)는 `msx-retro-mania` 의 `masc_dos_press`·`masc_dos_step`·`masc_dos_screen` 이고, `context-reviewer` 는 상위 여덟 Keeper 에 들지 않아요.

고르지 않은 규칙: "마지막 K개만 원문"이나 "N바이트가 넘으면 마커"는 이 RFC 가 제안하지 않아요. K 와 N 은 재생으로 골라야 하는 숫자라서 근거가 없어요. `RFC-keeper-context-window-in-tokens` 의 §13.2 가 창 크기 숫자(100000/70000)를 같은 이유로 없애요. 제공자가 요청이 크다고 거절한 사건에 답하는 턴 안 강등(`Current_turn_demoted`)은 지금도 있어요.

숫자 없이 갈 수 있는 구조 후보 둘이에요. 둘 다 아직 만들지 않았고 사용자가 정해요.

1. 턴을 일의 단위에서 끝내요. 순찰 턴이 PR 마다 깨움을 만들고 그 턴은 끝내면, 이 RFC 의 끝난 턴 규칙이 PR 하나가 끝날 때마다 일해요. 새 숫자가 없고 단위는 PR 번호예요. `RFC-0379-keeper-monitor-event-wake` §6.6 의 PR head 깨움과 이어져요. 단위가 PR 인 Keeper 는 위 측정에서 `context-reviewer`·`rondo`·`masc-productor-owner`·`code-reviewer-uncle` 이고, 긴 턴의 호출 32,899행 중 16,448행(50.0%)이 이 넷의 것이에요. 나머지 긴 턴의 단위는 정해지지 않았어요. 대가는 둘이에요. 턴이 늘어서 턴마다 첫 요청에 시스템 프롬프트와 도구 스키마가 다시 실려요. 제공자 캐시 적중이 내려가는지는 못 쟀어요. 그리고 PR 사이에 이어지던 맥락이 끊겨요.
2. 도구가 결과의 수명을 선언해요. `config/tools/<tool>.toml` 에 닫힌 값을 적고, 기준은 "같은 입력의 더 새 결과가 있다"는 사건이에요. 위 측정이 가리키는 곳은 `msx-retro-mania` 의 DOS 도구예요. `context-reviewer` 의 긴 턴에는 닿지 않아요.

정해야 하는 것: (가) 후보 1을 만들지. RFC-0379 §6.6.2 의 결정과 겹쳐요. (나) 후보 2를 만들지. (다) 만든 턴 안의 되읽기율을 재는 typed 기록을 코드로 넣을지.

## 공식 클라이언트의 새 세션 씨앗 (11-12 측정과 제안)

끝난 턴의 결과를 마커로 보내는 규칙은 Agent Core 레인에만 있어요. 공식 클라이언트(Muse, Antigravity, Claude Code, Codex)가 새 세션을 열 때 싣는 씨앗은 결과를 원문으로 실어요.

### 측정 (sangsu, `system_log_2026-11-12.jsonl`)

같은 Keeper 가 같은 Librarian 지점에서 6분 사이에 두 레인으로 보낸 범위예요. `model input carried range` 줄의 값이에요.

| 시각 | 런타임 | 범위 | 보낸 크기 | 결과 |
|---|---|---|---|---|
| 07:01:06Z | `glm-coding.glm-5.3-flash` | atom 9581~, 1,051개 | 1,196,225 B | 받아들임(293,218 토큰) |
| 07:07:22Z | `muse_d242bc1a.muse-spark-1.3_75bc5a82` | atom 9581~, 1,053개 | 4,563,176 B | 거절(1,241,651 토큰, 창 1,048,576) |

- glm 줄에는 `current_turn_results=verbatim finished_turn_results=markers` 가 찍혀요. Muse 줄에는 그 칸이 없어요.
- 07:55Z 에 같은 일이 다시 났어요. glm 1,034,110 B(07:44Z), Muse 4,653,929 B.
- 같은 날 Muse 입력 초과 거절은 20건이고, 15건이 새 세션 씨앗(4.6~5.1 MB)이었어요(00:00Z~08:07Z).

한계예요. Keeper 한 명의 두 쌍이에요. 4.56 MB 중 얼마가 끝난 턴의 결과인지는 따로 재지 않았어요. 두 레인의 차이가 그 한 가지라는 것은 로그 칸과 코드에서 읽은 것이에요.

### 원인 (코드)

- `Keeper_official_client_host.plan_arguments` 는 `Keeper_model_input_demotion.plan` 을 `~demote_before:0` 과 `~measure_wire_bytes:(fun _ -> None)` 으로 불러요. 결과 본문은 하나도 고르지 않고, 끝난 턴의 호출 인자만 주소 꼴로 바꿔요.
- Agent Core 는 `compose_carried_model_input` 이 턴 경계를 `demote_before` 로, 2,048 을 `min_result_bytes` 로 넘겨요.

### 왜 문제인가

- 두 레인이 같은 범위를 다른 크기로 실어요. RFC-librarian-lifecycle §4.10 의 "받아들여진 시작점"은 두 레인이 같이 써요. glm 이 받아들인 범위를 Muse 가 거절하면, glm 의 응답이 가장 새 관측이 되어 Muse 는 같은 범위를 다시 받아요. §4.10 의 거절 표시(#51625, #51626)도 이 경우에는 가려져요.
- 이 RFC 의 캐시 비용은 새 세션에 없어요. 새 세션에는 provider 가 쥔 앞 접두가 없어서 다시 읽을 것이 없어요.

### 제안

공식 클라이언트의 새 세션 씨앗에서, 끝난 턴(턴 경계 앞)의 결과 중 본문이 2,048 B 이상인 것을 마커로 보내요. Agent Core 와 같은 규칙, 같은 문턱이에요.

- 자리는 `plan_arguments` 예요. `demote_before` 에 `argument_source.completed_before`(끝난 턴의 끝 atom)를, `min_result_bytes` 에 Agent Core 가 쓰는 상수를 넘겨요.
- 켜는 조건은 인자 주소 꼴과 같아요. `argument_projection` 이 `Keeper_recovery_transmission.require_reader tools` 를 이미 요구하고, 턴 경계를 모르거나 끝난 턴이 없으면 `create_argument_source` 가 `None` 을 줘요. 새 조건을 더하지 않아요.
- 크기 비교(`measure_wire_bytes`)에는 씨앗의 인코딩(`measure_message_bytes`)을 써요. 공식 클라이언트는 MASC 가 만든 글을 그대로 넘겨받아요.
- 이어 쓰는 세션은 바뀌지 않아요. 그 요청은 이력을 싣지 않아요.
- 체크포인트는 원문 그대로예요. 클라이언트로 가는 복사본에서만 바꿔요.
- 턴 경계는 이번 턴의 입장(admission)을 거친 이력에서 검증한 atom 번호예요. 입장은 답이 없던 호출에 Tool 결과만 더하고, Tool 줄은 새 atom 을 열지 않아요. 그래서 같은 번호가 raw 씨앗과 요청에서 같은 atom 이에요. 씨앗이 요청에 묶이지 않으면(`bind_completed_arguments` 실패) 인자와 결과 모두 원문이에요(#51657).

대가예요.

- 모델이 마커를 되읽는 호출이 늘 수 있어요. Agent Core 에서 잰 값은 마커 17,829개 중 236개(1.32%)예요(위 "열린 질문 1"). 공식 클라이언트에서는 재지 않았어요.
- Claude Code 와 Codex 는 씨앗을 선언된 용량으로 자른 뒤에 실어요. 마커가 되면 같은 용량에 더 많은 atom 이 들어가요. 범위가 넓어지는 쪽이에요.

### 운영자가 정할 것

1. 적용 범위. 권하는 쪽은 공식 클라이언트 넷 모두예요. 넷이 `start_range_projection` 한 경로를 같이 써서, 런타임별로 나누면 그 경로에 런타임 분기가 생겨요. 대가는 Claude Code·Codex 의 씨앗도 같이 바뀌는 것이에요. 좁히려면 Muse·Antigravity(바이트 창이 없는 둘)만 켜요.
2. 문턱. 권하는 쪽은 Agent Core 와 같은 2,048 B 예요. 두 레인이 같은 범위를 같은 크기로 싣게 하는 것이 목적이라서예요.

결정(2026-11-12): 넷 모두, 2,048 B 예요. 이 두 질문에 운영자가 따로 답한 기록(Board 글, ask)은 없어요. 둘을 권고값 그대로 넣은 구현 PR #51657 을 운영자 계정(jeong-sik)이 Ready 로 바꿨고, 그 PR 이 12:32Z 에 병합됐어요. 그래서 권고대로 정해진 것으로 적어요. 운영자가 다르게 정하면 이 절과 상수를 같이 고쳐요.

### 시험과 배포 뒤 측정

- 시험: 끝난 턴에 2,047 B 와 2,048 B 결과가 있는 이력으로 씨앗을 만들어, 2,048 B 쪽만 마커이고 이번 턴의 결과는 원문인지 봐요. 리더 도구가 없으면 둘 다 원문인지 봐요.
- 측정: 같은 Keeper 의 연속한 glm 요청과 Muse 씨앗에서 `transmitted_bytes` 를 견줘요. Muse 입력 초과 거절 수를 날짜별로 세요.

## 구현 방향 (RFC 승인 뒤)

구현은 PR #49185 에 있어요. GitHub 스택 #49240 의 맨 위 층이에요.

- 규칙: 현재 턴(마지막 user 메시지)보다 앞이고, 이미지가 없고, 크기가 문턱 이상인 도구 결과를 마커로 바꿔요. 이 문턱은 늙은 결과를 바꾸는 문턱이고, 만들 때 blob 으로 넘기는 상한(64 KB)과 별개예요. 재생은 2 KB 로 했어요.
- 한 번 바뀐 결과는 이후 요청에서도 같은 바이트여야 해요. 히스토리는 뒤로만 자라니 요청마다 같은 함수를 부르면 그렇게 돼요. 저장된 체크포인트는 원문 그대로 두고, 제공자로 가는 복사본에서만 바꿔요.
- 자리: `current_turn_results` 에 변종을 더하지 않고 `compose_carried_model_input` 에 `?finished_turn_results`(`Finished_turns_verbatim` / `Finished_turns_as_markers`, 기본은 verbatim)를 더했어요. `Current_turn_verbatim` 일 때 `Keeper_carried_front` 의 턴 경계(끝난 턴의 끝 atom)를 `Keeper_model_input_demotion.plan` 의 `demote_before` 로 넘겨요. 크기 거절에 답하는 재전송(`Current_turn_demoted`)은 이 값과 상관없이 전과 같아요. 드라이버의 요청 조립은 `artifact_read` 를 쓸 수 있을 때만 켜요. `completed_arguments` 를 빼서 호출 인자는 그대로 남아요.
- 문턱: `plan` 에 `?min_result_bytes`(기본 0)를 더했고 드라이버가 2,048 을 넘겨요. 본문이 문턱보다 짧은 결과는 건너뛰어요. 호출 인자에는 이 문턱을 적용하지 않아요. 문턱을 더 낮추거나 없애는 것도 선택지예요(재생 값은 1 KB 35.7%, 2 KB 33.7%예요. 11-01 ~ 11-05 평균이고, 1 KB 아래는 재지 않았어요).
- 확인: 같은 히스토리의 두 요청에서 앞 메시지 바이트가 같은지(prefix 안정성), 이미 마커인 결과를 다시 바꾸지 않는지.
- 효과: 규칙을 넣은 뒤 `measure_aged_tool_results.py` 로 "현재 턴보다 앞선 도구 결과의 몫" 이 0 에 가까워졌는지, `measure_turn_requests.py` 로 첫 요청의 캐시 적중이 같은 간격 구간에서 안 내려갔는지 봐요. 적중이 내려가면 규칙을 되돌려요.
