# RFC: Keeper 전송 창은 토큰으로 정하고, 요청 본문 상한은 창을 만들지 않는다

- 상태: Active. §1~§9 는 문제 정의와 적대적 검토, §10~§12 는 해결 설계·이행·측정이다.
- 작성: 2026-09-15. §1~§9 는 코드 origin/main 5fb0fbe190 대조와 논문·업계·기억 구조 조사(§6.2~6.4)를 거쳤다. §10 이하는 같은 날 1단계 구현 PR 과 함께 적었다.
- 관련: RFC #26534 (Memory OS 2.0 bounded working set), RFC-0363 (옛 도구 결과 강등), #26545, #26800, #24838, #27320, #28845, #31684

## 1. 결정 (운영자, 2026-09-15)

1. Keeper 전송 창의 크기는 토큰으로만 정한다.
2. 요청 본문 바이트 상한(`max-request-body-bytes`)은 공급자가 그 요청을 받아 주는지만 판정한다. 창 크기와 요청 구성(무엇을 얼마나 담는지)을 바꾸지 않는다.
3. masc 에는 컴팩션(LLM 요약)이 없다. librarian 이 수시로 기억을 정리하고, 창은 최근 원문만 담는다. 그래서 librarian 이 창 밖으로 밀려난 것 중 무엇이 살아남을지를 결정한다.
4. 입력할 자료 자체가 많은 경우를 빼면, 턴마다 보내는 컨텍스트는 가능한 한 줄인다. 컨텍스트가 커질수록 효율이 급격히 떨어진다고 본다. 근거는 §6.2~6.4 에 있다. 증거가 받쳐 주는 형태는 "관련 없는 것은 빼고, 필요한 것은 넣는다"이다. 모든 과제에 맞는 길이 기준은 증거에 없다.

### 2.1 이 측정이 보여주지 못하는 것

- **캐시 영향을 나누지 않았다.** 지연 p50 은 토큰이 8배가 돼도 거의 그대로였다. 캐시가 앞부분 비용을 흡수했다는 해석과 맞는다. p90·최대가 늘어난 게 창 크기 때문인지, 캐시 실패 요청·rate limit 폴백·재시도 때문인지는 캐시 입력 토큰으로 나누기 전에는 말할 수 없다.
- **구간별 Keeper·런타임 구성이 다르다.** 10:00 이후에는 glm rate limit 과 kimi 주간 한도 소진으로 deepseek 폴백이 몰렸다.
- **답 품질은 재지 않았다.**

## 3. 현재 동작

HTTP 경로(`runtime_model_input_tail_window.ml`, `keeper_turn_driver_try_provider.ml`):

```
C  = max-request-body-bytes
C' = (Keeper, 런타임)이 마지막으로 성공한 용량이 C 이하면 그 값, 아니면 C
     (성공마다 기록, 프로세스 메모리, 재기동하면 사라짐 — keeper_context_overflow_shrink_state.ml)
R  = 도구 스키마 바이트 + 시스템 프롬프트 바이트 + C' / 10
U  = 고정 메시지(System, extra-system-context — 브리핑 포함) 바이트 + 생략 안내문 바이트
A  = C' − R − U

d = { 0, 60, 120, … } 중 남은 atom 바이트 합 ≤ A 인 가장 작은 값
    (없으면 1 단위로 다시 찾는다)
보내는 atom = N − d
그다음 RFC-0363 강등이 옛 atom 을 줄이고, 줄어든 크기로 다시 자른다.
공급자가 ContextOverflow 를 돌려주면 C' 를 절반으로 줄여 같은 런타임에 다시 보낸다.
```

- 토큰 수와 모델 창(`max-context`)은 이 계산에 들어가지 않는다.
- **C 를 선언하지 않은 바인딩에는 창이 아예 없다.** `uncapped_model_input_projection` 은 이력을 전부 보낸다(`keeper_turn_driver_try_provider.ml:902-908, 1137-1146`). 2026-09-08 기준 저장소 바인딩 155개 중 117개가 상한을 선언하지 않았다(`keeper_vision_tool.ml` 주석). 즉 지금은 창이 있느냐 없느냐부터 C 가 정한다. 라이브 설정은 HTTP 바인딩 8개 전부에 C 가 있다.
- 설계(RFC #26534 §3.1)는 전송 창을 "최근 K턴 원문, 구성상 유계"로 정했다. 구현(#26545 atom 수 → #26800 측정 바이트)은 "본문 바이트 상한까지 채우기"로 들어갔다. atom 무게가 0.3KB~8.7KB 로 달라 atom 수로는 요청 크기를 막을 수 없다는 이유였다.
- 그 결과 창 크기는 명시된 적 없이, 7월 사고(#24838) 때 넣은 거절 방지 상한의 부작용으로 정해져 왔다.

## 4. 결함: 바이트 상한이 요청 구성을 바꾸는 곳

origin/main 기준이다. 설정 검증, 최종 전송 바이트 검사, 로그처럼 판정이나 관측만 하는 곳은 뺐다.

| # | 곳 | 바이트 상한이 하는 일 | 판정 |
|---|---|---|---|
| 1 | HTTP 이력 창 `keeper_turn_driver_try_provider.ml:605, 822` | 이력 = `C' − R − U`, 예비분 `C'/10` | 부당 |
| 1a | 상한 없는 HTTP 바인딩 `:902-908, 1137-1146` | 창 자체가 없어진다 | 부당 |
| 2 | 브리핑 자르기 `keeper_unified_turn.ml:812-821` | 예산 = `min(max-prompt-bytes, C) × share`(기본 50, `keeper_config.ml:165-171`). 첫 런타임 기준이라 더 작은 C 로 폴백해도 다시 맞추지 않는다 | 부당 |

| 6 | Codex 이력 창 `keeper_codex_runtime.ml:1288-1311` | 평소엔 무제한, overflow 뒤 바이트로 자르고 기억한다 | 부당 |
| 7 | 현재 턴 도구 결과 강등 #28845 `:657-681` | C 기준으로 자를 수 없으면 이번 턴의 도구 결과까지 강등한다 | §7.3 참조 |

### 4.1 곳별 적대적 판정

**1·1a. 이력 창**
- 부당한 이유: 창 크기는 의도(토큰)인데 전송 한도(바이트)로 정해진다. 상한이 없으면 창이 사라지고, 상한을 스펙으로 올리면 창이 넓어진다.
- 반론: 창이 C 를 넘으면 요청이 거절되므로 C 는 창의 위 한계여야 한다.
- 재반론: 위 한계와 크기를 정하는 값은 다르다. 토큰 창을 바이트로 환산한 값이 C 를 넘으면 설정이 모순된 것이다. 이 모순은 드러내야 한다. 조용히 줄이면 숨은 결합이 다시 생긴다.
- 예비분 `C'/10` 도 부당하다. 측정하지 못한 필드의 크기는 상한이 아니라 실제 보내는 내용에 비례한다. 상한이 512KB 에서 4MB 가 되자 예비분은 52KB 에서 419KB 가 됐다.

**2. 브리핑**
- 1번과 **같은 결합**이다. 브리핑은 고정 메시지로 붙어 U 에 들어가고, 그만큼 A 를 줄인다(`agent_turn.ml:34-52`).
- 부당한 이유:
  - 브리핑 크기는 정보 설계이지 전송 한도가 아니다.
  - 창과 다른 모수(C 의 share)라서, 창을 토큰으로 바꿔도 브리핑은 여전히 C 를 따라간다.
  - Claude Code 는 masc 가 HTTP 본문을 만들지 않는데도 C 가 들어간다.
- 반론: 브리핑은 창에서 자를 수 없으니 예산이 없으면 창을 잡아먹는다.
- 결론: 예산은 필요하다. 다만 같은 토큰 창 안의 토큰 예산이어야 한다.

**3. HTTP overflow shrink**
- 부당한 이유:
  - **생성자 하나(`ContextOverflow`)가 두 가지를 싣는다.** 하나는 공급자의 모델 창(토큰) 초과이고, 다른 하나는 masc 가 자르지 못해 스스로 거절한 바이트 초과다(`limit = None`, `runtime_model_input_tail_window.ml:72-86`, `try_provider.ml:838`). shrink 는 둘 다 C' 절반으로 대응한다.
  - 공급자의 본문 크기 초과(`Request_body_too_large`)는 따로 분류돼 shrink 를 타지 않는다(`keeper_turn_driver_try_runtime.ml:98-116`).
  - 성공마다 기록되는 기억 값은 설정 밖의 숨은 상태다. 상한을 올려도 창이 넓어지지 않고, 재기동하면 갑자기 넓어진다(§2). 운영자는 설정만 봐서는 지금 창이 어떤 크기인지 알 수 없다.
- 반론: 모델 창이 잘못 선언된 경우를 버티는 안전장치이고, #31684 처럼 기억 값이 틀리면 `forget` 한다.
- 결론: 안전장치는 유지할 가치가 있다. 먼저 오류 두 종류를 타입으로 나누고, 토큰 초과는 토큰 창으로 대응해야 한다.

**4·5·6. 공식 클라이언트 경로**
- `max-prompt-bytes` 는 공식 클라이언트에 입력을 넘길 때의 실제 전송 한도라 판정 근거로는 정당하다.
- 부당한 부분:
  - 그 한도를 창 크기 결정에 쓴다.
  - Claude Code 에는 HTTP 본문이 없는데 C 가 섞인다.
  - Codex 는 overflow 뒤 바이트로 자른 값을 기억한다.

**8. librarian 입력**
- 1판의 "타깃 바이트 상한까지 채운다"는 틀렸다. 실제로는 메시지 수 상한에서 시작해 바이트로만 줄인다.
- 실제 결함: **쓸 수 있는 사다리 슬롯 전부**의 상한에 맞춰야 한다(`:348-359, 437`). 그래서 실제로 쓰일 슬롯의 상한이 크더라도, 사다리에서 가장 작은 상한이 librarian 프롬프트 크기를 정한다.
- 타깃 상한은 overlay `[[targets]]` 의 별도 선언이다. runtime.toml 바인딩 상한과 맞추는 코드는 찾지 못했다(미확인).
- 창을 작게 할수록 librarian 이 더 중요해진다(결정 3). 그런데 librarian 자신이 보는 입력이 가장 작은 슬롯의 바이트 상한에 묶여 있다. 이 부분은 Keeper 창보다 먼저 봐야 할 수 있다.

**9. Vision 이미지**
- 이미지는 그대로 전송 바이트다. 상한에 맞춰 줄이는 것은 전송 적응에 가깝다.
- 전역 크기 한도가 이미 있다(`MASC_KEEPER_VISION_MAX_DIMENSION`, 기본 1568, `env_config_keeper.ml:410-420`).
- 반론: 줄이면 모델이 보는 내용이 조용히 바뀐다. Claude Code 는 요청이 너무 크면 이미지·문서를 빼고 재시도한다고 문서에 적는다(code.claude.com/docs/en/errors#request-too-large).
- 결론: 해상도는 모델 스펙과 전역 한도가 먼저 정하고, 상한에 맞춰 줄였다면 그 사실을 기록할 때만 정당하다.

## 5. 결정 자체에 대한 적대적 검토

결정을 뒤집자는 것이 아니다. 결정이 풀어야 할 난점을 숨기지 않으려는 것이다.

**A. chat-completions 호환 공급자는 보내기 전에 토큰을 셀 수 없다.**
- agent_core 는 Anthropic `count_tokens`, OpenAI Responses `input_tokens`, Gemini `countTokens` 로는 보내기 전에 센다(`input_token_count.mli`).
- glm, deepseek, kimi, ollama 같은 chat-completions 호환 공급자는 받은 뒤에야 알려준다.
- 이런 공급자에서는 토큰 창이 추정에 기반한 목표이지 보장이 아니다. 조사한 다섯 에이전트 모두 추정한 뒤 넘치면 사후 처리한다.
- "추정 계수를 코드에 박지 않는다"를 지키면, 첫 턴이나 모델 교체 직후처럼 실측이 없는 요청을 무엇으로 자를지 정해야 한다.

**B. 앞부분이 생각보다 덜 고정돼 있다.**
- 60 atom 양자화는 R, U, 강등 크기가 고정일 때만 앞부분을 지킨다.
- 브리핑은 한 턴의 첫 라운드에만 붙는다(`prompt_block_id.ml:67-69`). 그래서 같은 턴 안에서 라운드 1과 2의 A 가 달라져 자르는 위치가 움직일 수 있다.
- 강등 경계는 턴마다 움직여 남은 atom 크기를 줄이므로, 자르는 위치가 뒤로 갈 수도 있다.
- 토큰 예산을 턴마다 바뀌는 실측 비율로 환산하면 흔들림이 더 커질 수 있다.
- 요청마다 자르는 위치가 얼마나 자주 바뀌는지 먼저 재야 한다.

**C. 창 선언 위치와 폴백.**
- C 는 이미 바인딩별이라, 오늘도 폴백하면 창이 바뀐다(`runtime_adapter.ml:698`). 바인딩별 토큰 창이 새 비용을 만드는 것은 아니다.
- 다른 공급자로 폴백하면 창 크기와 상관없이 프롬프트 캐시가 사라진다. 같은 공급자 안에서 폴백할 때만 창 크기 차이가 새 비용이 된다.
- 창의 필요량은 모델보다 Keeper 의 일에 가깝다. pr-updater 는 41K 로도 돌았다. 선언 위치는 따져 볼 여지가 남아 있다.

**D. 85K 는 체감이다.**
- 측정한 것은 지연과 사용량뿐이고, 캐시 영향도 나누지 않았다(§2.1).
- 창 크기별 답 품질을 비교하는 하네스가 필요하다.

**E. 창이 작은 모델이 있다.**
- local-granite 의 창은 131,072 토큰이다. 85K 에 브리핑·도구 스키마·출력 예약을 더하면 넘을 수 있다.
- 토큰 창은 모델 창에서 고정 부분을 뺀 값을 넘지 못해야 한다. 이는 토큰 대 토큰 결합이라 결정 2와 부딪히지 않는다.

**F. librarian 의 틈.**
- librarian 은 전송 절단과 무관하게 checkpoint 를 읽는다(RFC #26534 §3.2). cadence 는 3턴이다(§3.3).
- 그래서 Keeper 창을 줄여도 librarian 이 읽는 재료는 줄지 않는다.
- 틈을 실제로 넓히는 것은 librarian 자신의 입력이 가장 작은 슬롯 상한에 맞춰 줄어드는 것이다(§4.1 8번).

**G. 바이트 상한은 계속 필요한가.**
- 조사한 다섯 곳 중 요청 전에 막는 바이트 상한이 있는 곳은 Claude Code(32MB)뿐이다. 나머지는 413 을 사후 처리한다.
- masc 는 ollama.com 이 5.7MB 에서 이유 없는 400 을 내서(#24838) 상한을 둔다.
- 판정만 한다면 남겨도 해가 없다.

**H. 큰 창이 싸 보이는 경우.**
- polisher #3887 은 입력의 99.3% 가 cache read 였다. 공급자가 캐시 토큰을 싸게 받거나 사용량에 덜 세면, 큰 창의 비용 논거는 약해진다.
- 반대 방향의 논거는 다르다. 캐시는 입력 재계산 비용과 첫 토큰 지연만 줄이고, 모델이 긴 입력을 다루는 어려움은 줄이지 않는다(§6.3). 결정 4의 근거는 비용이 아니라 효율과 품질이다(§6.2).

**I. 창을 줄이면 librarian 이 아직 안 적은 사실이 먼저 빠질 수 있다.**
- F 는 librarian 이 읽는 재료가 줄지 않는다고 했다. 그러나 재료를 읽는 것과 사실을 이미 적어 둔 것은 다르다.
- RFC #26534 §3.2 는 절단과 librarian 사이의 동기화 장치(watermark)를 두지 않았다. 근거는 librarian 이 절단과 무관하게 checkpoint 를 읽는다는 것이다.
- 조사(§6.4)는 정리가 늦으면 점수가 떨어진다고 보고한다. 창의 하한을 "librarian 이 아직 안 읽은 턴"으로 두라는 결론도 있다(직접 잰 논문은 없음).
- 평소에는 틈이 작다. cadence 가 3턴이고 85K 창에는 보통 그보다 많은 턴이 들어간다.
- 틈이 커지는 때는 두 경우다. 턴 하나가 커서 창에 3턴이 안 들어갈 때, 그리고 librarian 이 밀릴 때다. librarian 런타임이 실패하거나 사용량 한도에 걸리면 밀린다. 2026-09-15 에 ollama cloud 한도가 34번 났다.
- 이 틈이 실제로 사실을 잃게 하는지는 아직 재지 않았다. 잰 뒤에야 §3.2 를 다시 볼지 정할 수 있다. 동기화 장치는 새 상태를 추가하는 일이라, masc 원칙(없으면 durable truth 가 손상될 때만 추가)을 먼저 따져야 한다.

### 6.3 업계 권고와 비용 (2026-09-15 확인)

- Anthropic(2025-09-29)은 "가장 작은, 신호가 강한 토큰 집합"을 권한다. 100턴 웹검색 평가에서 context editing 으로 토큰 −84%, 성능 +29%, memory tool 병행 시 +39% 였다(claude.com/blog/context-management).
- Chroma Context Rot(2025-07, 18개 모델): LongMemEval 요약본(~300 토큰)이 전체본(~113K)보다 성능이 높았다.
- Manus(2025-07-18)는 KV 캐시 적중률을 가장 중요한 지표로 본다. 앞부분을 고정하고 뒤에만 붙인다.
- 턴당 몇 토큰을 권하는 곳은 없다. 나온 수치는 요약 트리거 기본값(Anthropic 100K·150K, OpenAI 예시 200K)뿐이고, 요약이 있는 구조를 전제로 한다.
- Prefill: Llama3 405B 에서 128K → 1M(7.8배)에 TTFT 3.8초 → 77초(약 20배)(arXiv 2411.01783). 100K 대 700K 직접 비교값은 없다.
- 캐시는 입력 재계산 비용과 TTFT 만 줄인다. 모델이 긴 입력을 다루는 어려움은 그대로라는 게 공급자 문서의 공통 설명이다(Anthropic·OpenAI 문서). §5 H 의 비용 논거는 효율 논거를 대신하지 못한다.
- ollama cloud:
  - 신규 요금제(2026-08-31)는 캐시 토큰도 cached 단가로 사용량에 넣는다.
  - 레거시 요금제는 5시간·주간 한도가 있고 "캐시를 공유하면 덜 쓴다"고만 적는다.
  - 2026-09-15 에 받은 "session usage limit" 은 레거시 5시간 한도로 보인다(추정).

- **정리가 늦으면 점수가 떨어진다.** 조사 결론은 "원문 창의 하한은 librarian 이 아직 안 읽은 턴 전부"다. 이를 직접 잰 논문은 없다.
- **정리는 항목 단위로 조금씩 고쳐야 한다.** 통째 재작성은 내용이 무너진다(사례 1건). 우리 librarian 계약(retain / drop+사유 / new_claim)은 이 방향이다.

## 7. 어떤 해결이든 지켜야 할 것

1. 창 크기는 토큰으로 선언되고, 요청 본문 상한 값이나 상한 선언 여부에 따라 변하지 않는다.
2. 요청 본문 상한은 전송 가능 판정과 그에 따른 폴백·거절에만 쓰인다.
3. **예외 후보**: atom 하나가 그 자체로 C 를 넘는 경우(#28845 현재 턴 강등, Vision 축소)는 어떤 토큰 창으로도 풀리지 않는다. 이때 바이트가 "강등할지 거절할지"를 고르는 것까지 허용할지, 그런 요청은 거절할지 정해야 한다.
4. 창 크기와 요청 본문 상한 사이의 모순은 조용히 줄이지 않고 드러낸다.
5. 공급자 프롬프트 캐시를 위해 전송 앞부분의 흔들림을 재고, 그 이상 늘리지 않는다.
6. 도구 호출과 그 결과는 같이 남거나 같이 빠진다.
7. 컴팩션(LLM 요약)을 되살리지 않는다.
8. 추정 계수를 코드에 박지 않는다.
9. 모델 창을 넘는 토큰 창은 허용하지 않는다(토큰 대 토큰).
10. 운영자가 설정만 보고 지금 창 크기를 알 수 있어야 한다. 성공 용량 기억 같은 숨은 상태가 창을 바꾸면 그 사실이 보여야 한다.

## 8. 열린 질문

1. chat-completions 호환 공급자에서 실측이 없는 요청(첫 턴, 모델 교체 직후)은 무엇으로 자르나.
2. 토큰 예산으로 자르면서 앞부분 흔들림을 어떻게 지금 이하로 유지하나. 지금 흔들림은 얼마인가.
3. 창을 바인딩별로 둘지, Keeper별로 둘지.
4. 브리핑 예산을 토큰 창 안에서 어떻게 나누나. 폴백 뒤 다시 맞추나.
5. `ContextOverflow` 의 두 경우(공급자 토큰 초과, masc 바이트 거절)를 어떻게 나누나. 토큰 초과 뒤 줄인 창을 기억할지.
6. librarian 입력은 사다리의 가장 작은 슬롯이 아니라 무엇에 맞춰야 하나. overlay 타깃 상한과 바인딩 상한의 이중 선언을 어떻게 하나.
7. Vision 해상도는 모델 스펙과 전역 한도 중 무엇을 기준으로 하나.
8. 85K 가 맞는지 판단할 품질 하네스를 무엇으로 만드나. 캐시 입력을 나눈 지연 측정을 어떻게 붙이나.
9. 상한을 선언하지 않은 바인딩(창 없음)에 토큰 창을 새로 적용하는 것은 동작 변경이다. 이행을 어떻게 하나.
10. 창의 하한을 librarian 진행 위치로 둘지(§5 I). 둔다면 RFC #26534 §3.2 를 어떻게 고치나.
11. Keeper 가 창 밖 원문을 필요할 때 찾는 경로가 지금 있나. 없다면 창을 줄이기 전에 필요한가.
12. 창 크기 하네스는 무엇을 재나. 후보는 Keeper 과제 성공률, 지연(캐시 입력 분리), 사용량, librarian 사실의 갱신·모순 오류다.

## 9. 범위 밖

- librarian 의 기억 정리 방식 자체 (입력 크기 결정은 범위 안)
- 공급자별 요청 본문 상한 값 자체

범위 안에 있지만 따로 다룰 것:
- RFC-0363 강등은 "같은 바이트 예산 안에서 더 깊은 이력"을 목적으로 한다(§0). 창이 토큰이 되면 그 목적이 달라지므로 상호작용을 다시 적어야 한다.
- `recovery_view` 턴이 창과 shrink 를 건너뛰는 경로.

## 10. 설계

### 10.1 한 줄로

창은 `[turn] context_window_tokens` 로 선언한 토큰 수다. 요청마다 그 토큰을 바이트로 바꾸는 값은 코드 상수가 아니라 실측 밀도다. 밀도는 그 런타임의 직전 응답이 보고한 입력 토큰을, 그 요청을 masc 가 잰 바이트로 나눈 값이다. 요청 본문 상한은 전송 가능 판정에만 남는다.

### 10.2 선언

- `runtime.toml [turn] context_window_tokens = N` (env `MASC_KEEPER_CONTEXT_WINDOW_TOKENS`). 다른 `[turn]` 값과 같은 경로(설정 레지스트리 → 부트 오버라이드 → `Keeper_runtime_resolved`)로 읽고, 재기동해야 반영된다.
- 코드에 기본값은 없다. 선언이 없으면 HTTP 레인의 모든 후보가 디스패치 전에 typed 설정 오류(`turn.context_window_tokens` undeclared)로 거절되고, 부팅 로그가 error 로 키 이름을 찍는다. 운영자가 파일에 적는 값이 창의 전부다. 라이브 값 85,000 의 근거는 §2 의 512KB 구간 측정(중앙값 약 85K)과 운영자 체감이고, §5 D 가 말하듯 하네스(§12)로 다시 잰다. 부팅 로그가 값과 출처(env/toml)를 한 줄로 남긴다.
- 후보별 검사(§7.9): 창이 그 런타임의 `max-context` 보다 크면 그 후보는 디스패치 전에 typed 설정 오류(`turn.context_window_tokens`)로 거절되고 레인은 다음 후보로 돈다. 토큰 대 토큰이며 바이트 상한은 보지 않는다.
- Keeper 별 선언은 이 RFC 범위 밖이다(§11 6단계).

### 10.3 요청 구성 (HTTP 레인)

기호는 §3 을 잇는다.

```
W  = 선언한 창 (토큰)
R  = 도구 스키마 바이트 + 시스템 프롬프트 바이트            (같은 인코더, 예비분 없음)
d  = (직전 응답 input_tokens, 그 요청의 masc 측정 바이트)   런타임별, 프로세스 메모리
B  = W × d.bytes / d.tokens                                 이번 요청의 바이트 용량
A  = B − R − 핀 − 서문
자르기 = 60 atom 양자화 그대로. 남은 atom 바이트 합 ≤ A 인 가장 작은 경계.
경계가 없으면 거절하지 않는다: 가장 새 atom 만 보내고 overrun 을 기록한다.
```

- 예비분 `C/10` 은 없앤다. 밀도가 masc 측정 바이트 위에서 관측되므로, 와이어가 더 붙이는 바이트는 이미 비율 안에 있다.
- 밀도가 없는 런타임(재기동 뒤 첫 요청, 처음 쓰는 런타임): 핀 + 가장 새 atom 만 보낸다(floor). 그 응답의 usage 가 밀도가 되고, 같은 턴의 다음 요청부터 창을 쓴다. 추정 계수를 코드에 두지 않는 대가이며 §12 로 빈도를 잰다.
- 밀도는 응답마다 갱신되고 런타임 id 로 묶여 모든 Keeper 가 공유한다. 프로세스 밖에 남기지 않는다.
- RFC-0363 강등은 그대로다. 다만 #28845 의 현재 턴 강등은 바이트 축에만 남는다. 가장 작은 뷰(핀 + 가장 새 atom + 서문)가 요청 본문 상한 C 를 넘을 때만, 그리고 그때만 현재 턴의 도구 결과를 강등한다. 이것이 §7.3 이 허용한 유일한 예외다. 강등할 것이 없으면 그대로 보내고 와이어가 typed 로 거절한다.
- 창을 바이트로 읽은 값이 C 보다 크면(§7.4 의 모순) 시도당 한 번 경고를 남기고 조용히 줄이지 않는다. 창을 채운 요청은 와이어가 거절하고 레인이 돈다.

### 10.4 공급자 overflow

- 같은 런타임 재시도는 창을 토큰으로 반으로 줄인다. `(Keeper, 런타임)` 별 성공 창 기억은 유지하되 단위가 토큰이고 선언 창 이하로만 쓰인다.
- 창은 출처를 지닌다. `declared` 또는 `shrunk_after_overflow{declared_tokens}` 다. 로그와 manifest 에 선언 창과 유효 창이 나란히 남으므로 §7.10 을 만족한다.
- 줄인 창이 이력 자리를 남기는지는 R 을 밀도로 토큰 환산해 판정한다. 밀도가 없으면 판정할 근거가 없으므로 공급자에 맡긴다.
- 모든 shrink 가 실패하면 기억을 지운다(#31684 그대로).

### 10.5 관측

- 시도마다 한 번: 창(선언·유효·출처), 용량(밀도 포함), R. `model input window runtime=… window={…} capacity={…} reserved_bytes=…`
- overrun 과 창–상한 모순은 시도당 한 번 경고.
- shrink 재시도 manifest 에 `previous_window_tokens`, `window_tokens`, `declared_window_tokens`.
- 턴 레코드의 `model_input_window`(atom 수)와 `usage.input_tokens` 는 그대로다. 창을 토큰으로 되돌아보는 데는 이 둘로 충분하다.

### 10.6 §7 대조

| §7 | 어떻게 지키나 |
|---|---|
| 1 | 창은 `[turn]` 토큰 선언 하나에서 나온다. 상한 선언 여부는 창에 들어가지 않는다 |
| 2 | 상한은 `validate_request_body_cap` 과 와이어 관측, 그리고 §7.3 예외 판정에만 쓰인다 |
| 3 | 예외는 "가장 작은 뷰 > C" 한 경우로 좁혔다. 그때 바이트가 강등 여부를 정한다 |
| 4 | 창(바이트) > C 는 경고로 드러낸다 |
| 5 | 60 atom 양자화 유지. 밀도 변동이 경계를 옮기는 빈도는 §12 로 잰다 |
| 6 | atom 단위 자르기 유지 |
| 7 | 요약 없음 |
| 8 | 밀도는 관측값이다. 첫 요청은 추정 대신 floor 를 보낸다 |
| 9 | 후보별 `max-context` 검사 |
| 10 | 창 출처와 밀도가 로그·manifest 에 남는다 |

### 10.7 하지 않은 것과 이유

- 공급자 count 엔드포인트(Anthropic, Responses, Gemini)를 요청 전에 부르지 않는다. 밀도 하나로 모든 공급자를 같은 길로 다루는 편이 단순하고, 정확도 차이는 §12 로 잰 뒤 정한다.
- 밀도를 디스크에 남기지 않는다. 턴 레코드에 이미 `usage.input_tokens` 와 `request_wire_observation.body_bytes` 가 있어 재기동 뒤 씨앗으로 읽을 수 있다(§11 5단계). 새 durable 상태를 만들 이유가 없다.
- 브리핑·librarian·공식 클라이언트 레인은 이 PR 에서 바꾸지 않았다(§11).

## 12. 배포 후 측정

- 요청별 입력 토큰 분포(중앙값·p90)가 85K 부근으로 모이는지. §2 의 표와 같은 방법.
- floor 요청 수/일: `capacity_bytes=null` 로그 줄. 재기동 수 × HTTP 런타임 수를 넘으면 밀도 갱신에 구멍이 있다.
- overrun 경고 수/일과 원인 비율(고정부 / 가장 새 atom).
- 창–상한 모순 경고 수. 0 이어야 한다. 아니면 C 를 올리거나 창을 내린다.
- shrink 재시도 수/일과 `shrunk_after_overflow` 로 도는 턴 비율. 0 에 가까워야 한다. 아니면 `max-context` 선언이 틀렸다.
- 전송 앞부분이 바뀐 요청 비율(§5 B). 밀도 변동으로 경계가 옮겨간 횟수를 캡처에서 센다.
- 지연 p50/p90 을 cache read 토큰으로 나누어 본다(§2.1).
- ollama cloud `session usage limit` 횟수.
