# RFC finished-turn-result-plans-are-computed-once: 끝난 턴의 메시지는 Keeper 마다 한 번만 잰다

- 상태: **초안(2026-11-27). 2026-11-28 1단계·후속 단계로 다시 씀.**
- 1단계는 #55268·#55397 의 현재 구현이다(§3). 남은 항목은 후속 단계로 Task 가 추적한다(§9).
- 11-27 18:35 에 다시 띄운 masc 서버에서, 11분 뒤 CPU 풀 스레드 둘이 5초 표본 내내 쉬지 않았다.
- 두 스레드는 끝난 턴의 큰 도구 결과를 요청마다 다시 직렬화해서 크기를 잰다.
- 이 RFC 는 그 측정을 끝난 메시지 하나에 한 번으로 줄인다.

## 0. 요약

- Keeper 는 provider 요청을 보낼 때마다 `Keeper_model_input_demotion.plan` 으로 durable 기록 전체를 훑는다.
- 끝난 턴에서 2,048바이트를 넘는 도구 결과를 만나면 preview 를 만든다.
- 그다음 요청 본문을 직렬화해서 marker 로 바꾼 쪽이 더 작은지 잰다.
- Agent Core lane 은 잰 크기를 provider 시도(attempt) 하나 동안만 기억한다. 시도가 바뀌면 처음부터 다시 잰다.
- 공식 클라이언트 lane(Claude Code·Codex·Antigravity·ACP)은 잰 크기를 기억하지 않는다.
- 끝난 턴의 메시지는 다시 바뀌지 않는다. 메시지만 읽는 인코더의 측정값은 메시지로만 정해진다.
- 결정
  - D1. 메시지로만 정해지는 측정값을 (Keeper 이름, 인코더)별 표에 보관한다. 1단계는 모듈 전역 표이고, 소유자 수명과 키 동일성은 후속 단계다.
  - D2. 공식 클라이언트 lane 네 곳은 인코더가 하나라서 표 하나를 같이 쓴다.
  - D3. 1단계는 표마다 직렬화 길이 64 MiB 한도만 둔다. 메모리가 Keeper × 인코더 수만큼 자라는 것을 받아들인다. 프로세스 합산 힙 한도는 후속 단계다.
  - D4. provider 설정을 읽는 wire 인코더의 측정과 preview 는 2단계다. 설정을 키로 쓸 투영을 먼저 정한다.
- 바뀌지 않는 것: 어떤 결과가 marker 가 되는지, marker 글자, 요청 크기, durable 기록, checkpoint.

### 1.4 기억에 드는 값 (11-27 20~22시)

- run 을 시작할 때 넘겨받은 checkpoint 가 없으면 디스크에서 다시 읽는다(`keeper_run_context.ml:192-203`).

- 기록을 셌다. 11-26 이후 snapshot 을 쓴 trace 14개의 history segment 와 turn bundle 을 읽었다.
  - 도구 결과 글이 2,048바이트 이상인 메시지: Keeper 하나에 많게는 3,295개(저장 JSON 28.6MB), 14개를 합치면 19,905개(206.1MB).

    - 띄운 지 1시간 59분: 8,045,856KiB(7.7GiB)
    - 3시간 12분(21:47): 10,642,176KiB(10.1GiB)

## 2. 원인

- 끝난 턴의 메시지는 durable 기록에서 바뀌지 않는다.
- history 인코더와 공식 lane 인코더의 측정값은 메시지로만 정해진다.
- 그런데 Agent Core lane 은 측정값을 provider 시도 하나 동안만 기억한다. 공식 클라이언트 lane 은 기억하지 않는다.
- 그래서 CPU 는 새로 끝난 결과 수가 아니라 「durable 기록에 쌓인 큰 결과 수 × 시도 수」를 따라 는다.
- Fresh state 뒤에는 끝난 턴이 없어서 `plan` 이 497-498 에서 바로 끝난다. 15:10 에 이 경로가 없던 까닭이다.
- 18:35 재시작 뒤에는 11분 만에 나타났다. 비용이 가동 시간이 아니라 남은 기록을 따른다는 뜻이다.

## 3. 결정

### D1. (Keeper 이름, 인코더)별 표에 측정값을 보관한다

**1단계 (#55268·#55397, 착지하는 구현)**

- `Keeper_message_measurement_memo` 의 모듈 전역 표 `tables : (string * int, table) Hashtbl.t` 가 Keeper 이름과 인코더 번호로 표를 하나씩 둔다. 표는 프로세스가 끝날 때까지 남는다. Keeper 를 지우거나 이름을 바꾸거나 런타임을 내려도 해제하는 경로는 없다.
- 키는 메시지 값이고, 같음은 `Agent_core.Types.Message_value` 의 구조 비교다. 인코더가 읽는 role·origin·content·name·tool_call_id·metadata 가 모두 키에 들어간다.
- raw JSON 의 `0.0` 과 `-0.0` 은 구조 비교로 같아서 한 항목을 같이 쓴다. 인코딩은 1바이트 다르다. 기존 시도 단위 memo 도 같은 오차를 허용했다. 그 영향은 §5 에 적는다.
- 걸음은 기록 한 번 순회다. Agent Core 는 provider 시도, 공식 레인은 턴이 단위다. 걸음마다 측정기를 새로 만들어 버퍼를 걸음끼리 나누지 않는다.
- 레지스트리와 각 표의 조회·갱신은 잠금 안에서 하고, 측정은 잠금 밖에서 한다. 놓친 값은 잠금 밖에서 잰 뒤 잠금 안에서 다시 조회해 넣는다. 겹친 걸음은 같은 값을 두 번 잴 수 있지만 항목은 한 번만 넣는다.
- 적중하면 키를 이번 걸음의 메시지로 바꾼다. 앞 run 이 디코드한 사본을 더는 붙잡지 않는다(§1.4).
- provider 설정을 읽는 wire 측정은 시도 단위 memo 그대로다(D4).

**후속 단계**

- 소유자 수명(task-4169): 표를 Keeper 런타임 상태가 소유하거나, Keeper 를 지우거나 이름을 바꾸거나 해제할 때 그 Keeper 의 표를 반환하는 경로를 둔다. 프로세스 전역에서 Keeper 이름으로 메시지 사본을 붙잡는 레지스트리는 이 단계에서 없앤다.
- 키 동일성(task-4168): 키 비교가 같다고 본 메시지는 인코딩 길이도 같아야 한다. 이를 보장하지 못하는 값(`0.0`/`-0.0` 이 섞인 raw JSON, 비정상 부동소수점)은 표를 조회·갱신하지 않고 직접 잰다. 해시와 키 비교는 같은 키 규칙을 따른다. 비슷한 머리말을 공유하는 큰 본문이 한 버킷으로 몰리는지 확인한다. 값 키 대신 턴·메시지 순번과 내용 다이제스트를 쓰는 안도 이 단계에서 비교한다. durable 기록 형식은 바꾸지 않는다.

### D2. 공식 클라이언트 레인은 인코더 하나로 표를 같이 쓴다

- 네 런타임의 측정 식이 같다(§1.3). 공유 인코더는 그 인코딩을 정의한 모듈에서 한 번 만들고 토큰은 모듈 인터페이스에서 불투명하게 둔다. 레인이 토큰을 직접 구성하거나 다른 측정기를 대입할 수 없게 한다.
- 공유 식이 달라지는 레인은 기존 토큰을 재사용하지 않는다. 별도의 인코더를 정의하고 바이트 동일성을 따로 확인한다.
- `start_range_projection`이 걸음을 연다. 런타임이 측정기를 따로 넘기지 않게 인자를 없앤다.

### D3. 1단계는 표마다 직렬화 길이 한도만 둔다

**1단계 (#55268·#55397, 착지하는 구현)**

- 표 하나의 한도는 `per_keeper_retained_bytes` = 64 MiB 다. 항목은 인코더가 잰 직렬화 길이로 센다. 키가 붙잡는 힙(Yojson 노드, variant, 해시 테이블 슬롯)은 세지 않는다. 그래서 실제 점유는 직렬화 길이보다 클 수 있다.
- 새 항목이 한도를 넘으면, 이번 걸음과 바로 앞 걸음이 모두 묻지 않은 항목을 먼저 뺀다. 그래도 자리가 없으면 값을 재서 돌려주고 표에는 넣지 않는다. 걸음은 매번 같은 순서로 기록을 돌기 때문에, 가장 오래 안 쓴 항목부터 빼면 기록이 표보다 커진 뒤 모든 조회가 빗나간다.
- 프로세스 전체의 합산 한도는 없다. 합산 상한은 Keeper 수 × 인코더 수 × 64 MiB(직렬화 길이 기준)다.
- **판단: 이 단계는 Keeper × 인코더 수만큼 메모리가 자라는 트레이드오프를 받아들인다.** 근거는 이렇다.
  - 11-27 가장 큰 Keeper 기록의 측정 대상은 28.6 MB 로 표 한도 아래다(§1.4).
  - 측정 CPU 는 같은 표본에서 바쁜 시간의 32~45% 였다(§1.1).
  - 메모리가 늘어나는지는 배포 뒤 RSS 관측(§8)으로 확인한다.

**후속 단계 (task-4167)**

- 모든 활성 Keeper 의 모든 인코더 표를 합한 프로세스 보관 힙 한도를 둔다. 삽입 때 프로세스 예약을 먼저 확보하고, 퇴출·소유자 해제 때 반환한다. 한도를 확보하지 못하면 값을 재서 돌려주고 표에는 넣지 않는다.
- 점유는 키 문자열뿐 아니라 힙 블록 헤더, 포인터 슬롯, 키·값 레코드, 해시 테이블 저장 공간을 포함한 보수적 추정치로 센다.
- 한도 값과 추정식은 아직 정하지 않았다. task-4167 을 맡은 구현자가 §8 의 힙 실측(추정치 대 실측 힙)을 근거로 정한다. 그 PR 의 리뷰에서 확정하고, 이 RFC 의 후속 단계 절에 값을 적는다.

### D4. wire 측정과 preview 는 2단계에서 다룬다

- wire 측정기는 `Provider_config.t` 에 따라 다르다. 설정을 키로 쓰려면 §1.4 의 `cache.ml` 처럼 필드를 펼쳐 고른 투영이 필요하다.
- preview(`Tool_blob_store.make_preview`)는 본문으로만 정해진다. 그러나 시도를 넘어 기억하려면 본문 사본이나 다른 키가 필요하다.
- 이 둘은 D1~D3 의 1단계를 배포해서 잰 뒤 다룬다. 17:30 표본에서 wire 는 memo 아래 369 중 112 다.

## 4. 바뀌는 동작

- 같은 메시지에서 marker 선택과 요청 크기는 직접 측정과 같다. 예외는 `0.0`/`-0.0` 만 다른 raw JSON 이 한 항목을 같이 쓰는 경우다(§5). 후속 단계(task-4168)에서 이 예외를 없앤다.
- Keeper의 첫 걸음은 값을 직접 잰다. 다음 걸음은 보관된 키와 같을 때 표에서 값을 읽는다. 키가 빠졌거나 표 한도(64 MiB)를 넘으면 값을 다시 잰다.
- 표는 프로세스가 끝날 때까지 남는다. 지운 Keeper 의 표도 남는다(task-4169).
- 11-27 기록에서 전체 표본의 직렬화 길이는 약 206MB였다. 이 수치는 프로세스가 보관하는 힙 크기의 측정값으로 사용하지 않는다.

## 5. 경계 조건과 한계

- 1단계에서는 구조 비교가 raw JSON 의 `0.0` 과 `-0.0` 을 같다고 보고 한 항목을 같이 쓴다. 먼저 잰 쪽의 길이가 나가므로, 2,048바이트나 창 경계에 걸린 메시지는 1바이트 차이로 marker 와 창 선택이 바뀔 수 있다.
  - 기존 시도 단위 memo 도 같은 오차를 허용했다. 1단계는 그 오차를 시도에서 걸음 사이로 넓힌다.
  - 후속 단계(task-4168)에서 이런 값을 표에서 빼고 직접 잰다.
- 조회마다 해시와 비교 비용이 생긴다. 비슷한 큰 결과에서 충돌과 비교 비용이 이득을 상쇄하는지는 §8에서 확인한다.
- 4,096바이트 이하 결과는 #54361 뒤로 줄지 않는다. preview 가 본문 전체라 marker 가 더 크다.
  - 그래도 `plan` 은 그 결과를 재고, 표는 그 크기를 담는다. 11-27 기록으로 측정 대상의 37.6%(7,492개)다.
  - 하한을 preview 경계에 맞추는 일은 #55296 이 다룬다. 이 RFC 의 표와 함께 쓸 수 있다.
- 18:46 표본은 경로가 잘려서 직렬화의 호출자를 다 보여 주지 않는다.
  - 근거는 17:30 표본의 경로와 코드다. 확신도는 Medium 이다.

## 6. 하지 않는 것

- 어떤 결과를 marker 로 바꿀지의 규칙(`tool-results-age-out-of-context`)은 바꾸지 않는다.
- durable 기록과 checkpoint 에 marker 를 쓰지 않는다. 기록은 지금처럼 본문 전체를 가진다.
- carried 창을 `plan` 앞에서 자르지 않는다. 창 경계는 marker 로 줄어든 크기로 정해지기 때문이다.
- 반응 원장 읽기(#55146, #55173)와 TUI 설정 TOML 파싱(#55254)은 다루지 않는다.
- 조회마다 메시지 하나를 다시 인코딩하는 `runtime_model_input_tail_window.ml:222-244` `digest_for_labelled` 도 다루지 않는다.

## 7. Fresh state required

- 아니다. 표는 메모리에만 있고 저장 형식이 바뀌지 않는다.

## 8. 검증

- 1단계에는 이 절의 항목 가운데 운영 관측과 기준선만 적용한다. 프로세스 상한, 해제, signed zero 제외 시험은 해당 후속 단계의 PR 에서 한다.

- 기준선
  - 같은 Keeper 기록과 인코더로 변경 전후의 요청 수, 걸음 수, 실제 측정과 직렬화 호출 수, 한 걸음의 wall time을 기록한다. 18:46 표본은 후속 운영 참고로 사용한다.
- 동작
  - 같은 Keeper의 다음 걸음에서 인코딩 길이가 같은 메시지는 값을 재사용한다. 다른 Keeper와 인코더는 표를 공유하지 않는다.
  - signed zero와 캐시에서 제외되는 값으로 2,048바이트 및 창 경계에 걸리는 입력을 만들어, 직접 측정과 marker 및 범위 결과를 대조한다.
  - 공통 머리말을 가진 큰 도구 결과를 넣어 최대 버킷 길이와 조회 시간을 기록하고, 값 키와 안정 식별자 후보를 동일 기록에서 비교한다.
  - 두 걸음을 겹치고 한 키를 동시에 놓치게 해, 항목과 예약이 한 번만 생기고 늦게 끝난 걸음이 마지막 사용 번호를 되돌리지 않는지 확인한다.
  - 여러 Keeper를 채워 프로세스 상한에 도달한 뒤에도 측정값이 반환되는지, 삭제·개명·해제 뒤 해당 표의 힙 예약을 반환하는지 확인한다. 추정한 보관 힙과 실측 힙을 같은 기록에서 비교한다.
- 운영
  - 배포 뒤 11분과 2시간 무렵에 CPU 표본과 RSS를 관측한다. 요청 바이트는 같은 기록으로 직접 측정했을 때와 대조한다.
