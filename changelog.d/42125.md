### Added

- A workspace whose `runtime.toml` has `[browser.live.bidi]` (`firefox`, `profile`, `port`, default 9222) has its Keeper Firefox and BiDi host started by the MASC server when the server starts. It starts only what is missing: no Firefox when the port already answers, and no host while one holds the host lock. It starts neither while no host could be attached, because Firefox's port lets any local process drive it: the browser lane is not installed as its installation wrote it, or the running host was given another port. Both run apart from the server, so a restart leaves them up; they write to `.masc/browser-lane/keeper-firefox.log` and `bidi-host.log`, and each start moves the last run's log to `<name>.1`. The host is not given the server's `MASC_HTTP_BASE_URL` or `MASC_HTTP_PORT`. `[browser.live] enabled = false` starts nothing. The dashboard's Browser activity editor reads the table and keeps it. Write the table only after deploying a server that reads it (#42125).
