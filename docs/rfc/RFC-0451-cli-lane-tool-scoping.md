# RFC-0451 — CLI 레인의 도구 목록은 이름으로 정한다

- Status: Draft
- 선행: RFC-attached-service-tool-scoping (Accepted, 2026-08-31).
- 경계: 이 문서는 **무엇을 목록에 올릴지**만 다룬다. 스키마를 언제 싣는지는 클라이언트가 이미 스스로 한다(§2).

## 0. Summary

**개정 2 (2026-09-16). 이 RFC 가 세웠던 비용 논리는 죽었다.** 그때는 CLI 레인이 도구 스키마를 매 요청에 통째로 실었고, 그게 이 문서의 출발점이었다. 원인은 masc 가 `--tools` 에 Claude Code 의 `ToolSearch` 를 빼먹어 CLI 의 지연 적재가 통째로 꺼져 있던 것이었다. #36798 로 고쳤고, 요청당 176,928 → 8,926 토큰이다(§8.6). codex 레인은 원래부터 켜져 있었다.

그래서 "도구를 많이 실으면 비싸다" 는 더 이상 참이 아니다. 실어도 **이름만** 간다. 두 레인 모두 모델이 부른 도구의 스키마만, 부른 만큼만 들어온다 — 측정으로 확인했다(§8.6).

남는 이유는 둘이다.

1. **고르는 정확도.** 모델은 이름과 한 줄 설명만 보고 고른다. 203개 중에서 고르는 일과 40개 중에서 고르는 일은 같지 않다.
2. **도구 집합이 흔들리면 세션이 끊긴다.** 집합 digest 가 바뀌면 CLI 세션을 새로 열고, 그 Keeper 는 세션에만 있던 일을 잃는다. 2026-09-15 하루에 Keeper 마다 도구 수가 여섯 가지였다(§8.4).

제안은 그대로다: **CLI 레인에서 무엇을 들고 갈지는 프로필이 도구 하나 단위로 정한다.** 바뀐 것은 근거지 제안이 아니다.

### 개정 이력

| | 무엇이 바뀌었나 |
|---|---|
| 개정 1 (2026-09-16) | 무리 단위 선언을 뺐다. 무리로 주면 안 쓰는 것이 같이 실린다. 붙임 도구가 이미 도구 하나 축으로 돈다(`attached_tool_allow`, RFC-0403). |
| 개정 2 (2026-09-16) | 비용 근거를 뺐다(#36798 로 해소). §2·§3 의 사실 오류를 고쳤다 — CLI 레인은 지연 적재를 **한다**, 그리고 목록에 없는 도구는 부를 수 **없다**. |

## 1. 지금 무엇이 도구를 고르는가

Keeper 하나의 턴 도구 집합은 `Keeper_capability_surface.create` 가 정한다. 인자는 하나뿐이다.

```ocaml
val create : tool_deny:string list -> ... -> t
```

`tool_deny` 는 **거부 목록**이다. 프로필이 이름을 대고 빼지 않으면 모든 Keeper 가 모든 모델 가시 도구를 든다. 허용 목록은 없다.

그래서 표면 증가를 막는 유일한 장치가 전역 바이트 상한(`test_keeper_tool_schema_bytes.ml`)이다. 상한은 범위 지정의 대역이지 범위 지정이 아니다. 도구가 하나 늘 때마다 숫자를 올리고 "무엇을 샀는지" 를 적는 일이 반복되는 이유다 — 파일에 그 기록이 아홉 번 쌓여 있다.

## 2. CLI 레인은 지연 적재를 한다 (개정 2 — 앞 판정을 뒤집는다)

**앞 개정은 "CLI 레인은 지연 적재를 못 한다" 고 적었다. 틀렸다.** 못 하는 것은 masc 가 턴 **중간에 목록을 넓히는** 일이고, 클라이언트가 **자기 쪽에서 스키마를 미루는** 일은 원래 되고 있었다. 둘은 다른 축인데 한 문장으로 묶여 있었다.

masc 가 넓히지 못하는 것은 여전히 사실이다. `runtime_official_client_mcp.ml` 이 이유를 적어 두었다 — `handle_message` 는 요청에 답할 뿐 먼저 말하지 않고, HTTP 전송은 GET 에 405 로 답하며, Claude Code 전송은 `control_response` 만 되돌린다. 그래서 이 서버는 `listChanged` 를 선언하지 않는다. **그 판단은 그대로 둔다.**

그런데 지연 적재에 그 채널은 필요 없었다. 클라이언트는 masc 가 턴 시작에 준 목록을 그대로 두고, 그 안에서 이름만 먼저 보여주고 본문은 모델이 부를 때 채운다.

| | 미루는 방식 | 켜는 스위치 |
|---|---|---|
| Claude Code | 이름만 싣고 `ToolSearch` 로 고른 것만 채움 | CLI 내장 도구 목록에 `ToolSearch` 가 있어야 함 (#36798) |
| Codex | 이름만 싣고 모델이 부른 것만 채움 | masc 가 도구마다 `deferLoading: true` (이미 그렇게 함) |

측정은 §8.6 에 있다. 실어 놓고 안 쓰면 값이 안 붙고, 쓰면 그 도구 스키마만큼만 붙는다.

## 3. 목록에 없는 도구는 부를 수 없다 (개정 2 — 앞 판정을 뒤집는다)

**앞 개정은 "못 실린 도구도 이름으로 부를 수 있다" 고 적었다. 틀렸다.** 그 문장은 masc 쪽 `call_tool` 만 보고 쓴 것이다.

```ocaml
call_tool : (name:string -> call_id:string -> arguments:Yojson.Safe.t -> tool_result option)
```

masc 는 목록에 있었는지 묻지 않는 것이 맞다. 그러나 호출이 masc 에 닿기 전에 클라이언트가 끊는다. Claude Code 는 자기가 모르는 이름에 `<tool_use_error>Error: No such tool available` 을 돌려주고 끝낸다.

그래서 좁히기는 **보는 것과 부를 수 있는 것을 같이** 줄인다. 안전망은 없다. 목록에서 뺀 도구가 필요해지면 그 턴은 실패하고, 목록을 고쳐야 다음 턴에 쓸 수 있다. 이 사실이 §4.3 의 "빈 목록으로 시작한다" 를 더 무겁게 만든다 — 목록 도구 하나로 시작한 Keeper 는 이름은 찾을 수 있어도 부를 수는 없다.

`tools/list` 응답이 턴 시작에 묶인 함수라는 점은 그대로다.

```ocaml
tool_specs : (unit -> Yojson.Safe.t list) -> ...
```

그러니 **그 목록을 무엇으로 묶느냐**는 열려 있다. 턴이 시작될 때 정해지기만 하면 된다.

## 4. 제안

### 4.1 CLI 레인에서 목록을 정하는 것은 프로필이 댄 이름이다

CLI 레인에서 무엇을 싣는지는 **그 Keeper 의 프로필이 댄 이름**이 정한다. `defer_loading` 은 agent_core 레인의 축으로 남고, 이 레인에서는 축이 아니다. 내장이든 붙임이든 이름을 대지 않은 도구는 안 탄다.

새 축을 만들지 않는다. 붙임 서비스 도구가 이미 이 모양으로 돈다 — `attached_tool_allow` 가 프로필이 댄 이름만 남기고, 없는 이름은 `unnamed` 로 보고한다(`Keeper_identity_tool_allow`, RFC-0403).

### 4.2 무리가 아니라 도구 하나씩

```
목록 = 프로필이 이름을 댄 내장 도구 (하나씩)
     + 프로필이 이름을 댄 붙임 도구 (지금 그대로)
     + 이름을 찾는 목록 도구 하나
```

- **무리는 쓰지 않는다.** 무리는 "browser 를 켜면 여섯 개가 같이 탄다" 인데, 실제로는 Keeper 마다 그중 한두 개만 쓴다. critic 은 145개를 싣고 2주 동안 55개를 썼다(§8.2).
- **이름은 사람이 처음부터 짜내지 않는다.** `tool_calls/` 기록이 Keeper 별 후보 목록을 만든다(§8.2). 운영자는 그 목록을 보고 고친다.
- **목록은 고정이다.** 턴마다 다시 계산하지 않는다. 계산하면 집합이 흔들리고, 집합이 바뀌면 CLI 세션을 새로 열어야 한다(`tool_surface_sha256`, §8.4).
- **뺀 도구는 그 턴에 못 쓴다.** §3 대로 클라이언트가 끊는다. 그래서 목록에서 빼는 판단은 "안 쓰더라" 가 아니라 "없어도 턴이 끝나더라" 여야 한다. 2주에 한 번 부른 도구가 Keeper 마다 6~17개 있다(§8.3) — 그 한 번이 어떤 턴이었는지 보고 정한다.
- **이름을 찾는 길**은 이름과 한 줄 설명만 주는 목록 도구 하나다.

### 4.3 아무 이름도 대지 않은 프로필은

**전부 싣는 기본값은 두지 않는다.** Keeper 가 지는 것은 그 프로필이 이름을 댄 도구뿐이다.

- 목록이 없는 Keeper 는 **목록 도구 하나**로 시작한다. 무엇이 있는지는 찾을 수 있다. 다만 §3 대로 부를 수는 없으므로, 이 상태는 출발점이지 운영 상태가 아니다.
- 부팅 로그가 "이 Keeper 는 도구를 선언하지 않았다" 를 한 줄로 남긴다.
- 살아 있는 Keeper 의 목록 초안은 §8.2 의 호출 기록에서 뽑아 **같은 변경에 함께 넣는다.** 그래서 이 변경으로 지금 도는 Keeper 가 도구를 잃지 않는다.
- 초안은 기계가 만들고 판단은 운영자가 한다.

## 5. 판정 기준

비용은 판정 기준에서 뺀다(개정 2). 요청 크기는 이미 #36798 이 정리했고, 목록을 줄여도 요청은 이름 몇 개만큼만 줄어든다.

- **고르는 정확도.** 목록에 없는 도구를 부르려다 `No such tool available` 을 받은 횟수를 센다. 이 값이 늘면 목록이 잘못 좁혀진 것이다.
- **찾기 실패.** 목록 도구를 부르고도 아무 도구를 못 고른 턴을 센다(agent_core 레인의 `Loaded_unused` 와 같은 질문).
- **세션 수명.** 도구 집합 digest 가 바뀌어 새 세션을 연 횟수가 줄어야 한다. 2026-09-15 하루에 CLI 새 세션이 115개였다(§8.4).
- **2주에 한 번 부른 도구**(Keeper 마다 6~17개, §8.3)가 목록에 남았는지 본다.
- 전역 상한(`ceiling_bytes`)은 **CLI 레인 최악값**으로 남는다. 이 RFC 가 성공해도 그 숫자는 안 줄어든다.

## 6. 지금 바로 할 수 있는 것 (이 RFC 없이)

상한 가드의 메시지가 지금 이렇게 말한다: "Every Keeper turn carries this." 사실이 아니다 — agent_core 레인 Keeper 는 선행 RFC 이후 그보다 훨씬 적게 지고, CLI 레인은 #36798 이후 이름만 진다. 가드는 그대로 두되 무엇을 재는 숫자인지 적는다.

## 7. 하지 않는 것

- CLI 전송에 서버→클라이언트 채널을 내지 않는다(§2).
- provider 스키마를 줄여 쓰지 않는다 (선행 RFC §6 그대로).
- 상한을 올려서 해결하지 않는다.
- 무리 선언을 만들지 않는다(개정 1). 도구 하나가 단위다.
- **namespace 로 묶지 않는다(개정 2).** codex 레인은 도구마다 namespace 를 따로 줘도 값이 같다(§8.6). namespace 는 이름 색인이지 스키마를 채우는 단위가 아니다.

- 그래서 §4.2 의 목록은 고정이어야 한다.

### 8.5 붙임 도구에서 같은 판단을 이미 했다

RFC-0403 이 적은 실측(2026-09-02): 한 Keeper 가 붙임 도구 122개·140KB 를 지고 있었고, 그중 84개·94.4KB 는 8일 동안 한 번도 불리지 않았다.

### 8.6 스키마는 부른 만큼만 들어온다 (2026-09-16)

가짜 MCP 서버(도구 203개, 도구당 약 2.7KB 스키마)를 두 클라이언트에 붙여 **요청 하나**의 입력 토큰을 쟀다. 턴 전체 합이 아니라 요청 하나다 — 합으로 읽으면 요청 수만큼 부풀어 잘못된 결론이 나온다.

**Claude Code** — masc 가 쓰는 argv 모양(`--strict-mcp-config`, `--permission-mode dontAsk`) 그대로.

| `--tools` | ToolSearch | 요청 하나 |
|---|---|---|
| `Read,Glob,Grep` (#36798 이전) | 없음 | 176,928 |
| `ToolSearch` (#36798 이후) | 있음 | 8,926 |
| 위 상태에서 도구 하나를 실제로 부름 | 있음 | 한 요청 최대 10,281 |

**Codex** — `codex app-server --stdio` 를 masc 와 같은 파라미터로 직접 두드려, `dynamicTools` 203개를 `deferLoading: true` 로 실었다.

| 배치 | 요청별 입력 토큰 |
|---|---|
| `deferLoading: false` | 120,205 |
| `deferLoading: true`, 도구 안 씀 | 24,829 |
| 도구 1개 호출 | 24,839 → **25,464** → 25,518 |
| 도구 3개 호출 | 24,858 → **26,538** → 26,592 → 26,646 → 26,700 |
| 도구마다 namespace 를 따로 준 뒤 1개 호출 | 25,528 (한 namespace 일 때와 같음) |

- 1개를 부르면 두 번째 요청에서 **+625**(스키마 하나), 3개를 부르면 **+1,680**(세 개)이 들어온다. 그 뒤 증가분은 도구 결과값뿐이다.
- namespace 를 어떻게 묶든 값이 같다. 그래서 §7 에 "namespace 로 묶지 않는다" 를 적었다.
- 재현: `codex_dynamic_probe.py`, `fat_mcp.py` (세션 scratchpad).
