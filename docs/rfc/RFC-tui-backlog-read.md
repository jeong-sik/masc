# TUI 는 작업 목록에서 바이트가 바뀐 task 만 다시 푼다

- 이슈는 #53568 이다. 측정 방법은 #53518 의 닫는 댓글을 따랐다.
- 측정한 파일은 살아 있는 `.masc/tasks/backlog.json` 의 사본이다. 5,278,018 바이트, task 1,487개다.
  사본에는 내부 데이터가 있어서 저장소에 넣지 않았다.

## 0. 결정

- TUI 는 `Workspace_backlog.read_backlog_observation_with_source_r` 대신 `Masc_tui_backlog_read.read` 로 작업 목록을 읽는다.
- 새 reader 는 파일을 통째로 읽는다. 하지만 각 task 의 바이트가 지난번 읽기의 바이트와 같으면, 그때 푼 task 값을 그대로 쓴다.
  바이트가 다른 task 만 다시 파싱하고 디코드한다.
- 답은 전체 reader 의 답과 같다.
  새 reader 가 바이트에서 직접 답하지 못하는 경우는 전체 reader 에게 그대로 넘긴다.
  넘기는 경우: 파일이 없을 때, 읽을 수 없을 때, 문서 모양이 다를 때, 디코드가 안 되는 줄이 있을 때, UTF-8 이 잘못됐을 때, 복구 사본을 써야 할 때.
- 서버가 쓰는 `lib/workspace` 코드는 바꾸지 않는다.

## 1. 문제

- 키퍼나 서버가 작업 목록을 commit 하면 파일 버전이 바뀐다. 파일 버전은 device, inode, size, mtime 이다(#53335).
- 바쁜 fleet 에서는 거의 모든 새로고침이 이 경우다. 한 번 commit 은 task 한두 개만 바꾼다.
- 그런데 TUI 는 그때마다 파일 전체를 문자열로 읽고, 트리로 파싱하고, 1,487개 task 를 모두 디코드했다.
- OCaml 5 에서는 minor 수집이 돌 때마다 모든 도메인이 멈춘다.
  그래서 작업자 도메인을 4M heap 에 묶어 두었다(`Masc_tui_domains`, Worker=Tuned).

## 2. 측정

읽기 한 번에 드는 비용이다. 방법마다 25번 쟀다.
시각은 부하가 높은 호스트에서 재서 흔들린다. 그래서 표에는 할당량과 수집 횟수만 적는다.

| 방법 (heap 256k) | minor 할당 | 바로 major | minor 수집(평균) | major 수집 |
|---|---|---|---|---|
| 지금: 전체 읽기 | 1.297 Mw | 0.812 Mw | 6.28 | 2 |
| 파일 읽기만 | 0 | 0.660 Mw | 2.00 | 1 |
| 트리 파싱만 | 0.846 Mw | 0.812 Mw | 4.12 | 1 |
| (a) task 단위로 흘려 읽기 | 1.288 Mw | 0.812 Mw | 6.00 | 2 |
| (c) 그리는 칸만 디코드 | 0.480 Mw | 0.708 Mw | 3.04 | 2 |
| lexer 로 건너뛰기만 | 0.019 Mw | 0.664 Mw | 2.00 | 1 |
| **(b) 바뀐 줄만 디코드 + 버퍼 재사용 (이 RFC)** | **0.085 Mw** | **0.006 Mw** | **0.32** | **0** |

- (b) 는 실제 `Masc_tui_backlog_read.read` 로 쟀다. 사본 두 개를 번갈아 rename 해서 파일 버전을 매번 바꿨다.
  6번 모두 답이 전체 reader 와 같았다.
- heap 이 4M 이면 전체 읽기는 minor 수집 1.68번, (b) 는 0.08번이다.

## 3. 고른 이유

- (a) 는 할당을 거의 줄이지 못한다. task 마다 트리를 만들고 디코드하는 일이 그대로 남는다.
- (c) 는 절반만 줄인다. 그리고 TUI 가 새 칸을 그릴 때마다 reader 를 같이 고쳐야 한다.
- (b) 는 바뀐 task 만 할당한다. 파일 버퍼도 두 개를 번갈아 다시 써서, 5 MB 문자열의 major 할당도 없어진다.
- (b) 의 단점:
  - 파일을 한 번 더 훑는다. lexer 로 task 줄의 경계를 찾고, 줄마다 바이트를 비교한다. 이 비용은 할당 없는 CPU 시간이다.
  - 버퍼 두 개(파일 크기의 1.125배씩)를 계속 쥔다. 지금 파일이면 약 12 MB 다.
  - 전체 reader 와 같은 답이라는 근거는 시험이다. `backlog_of_yojson` 이 `tasks` 의 원소를 하나씩 `task_of_yojson` 으로 풀고, 다른 검사는 원소를 읽지 않는다는 사실에 기댄다. 이 사실이 바뀌면 시험이 잡아야 한다.

## 4. 같은 답이라는 근거

- `test_tui_backlog_read` 는 한 reader 로 아래 단계를 차례로 읽는다. 단계마다 전체 reader 의 답과 비교한다.
  - task 추가, 변경, 같은 길이에서 변경, 삭제, 순서 바꿈, 반복
  - 디코더가 모르는 칸, 줄 사이 주석
  - 디코드 안 되는 줄(복구 사본이 있을 때와 없을 때), 객체가 아닌 줄, `tasks` 가 목록이 아님, `tasks` 두 번
  - 잘린 문서, 문서 뒤에 남은 것, 빈 파일, 0 이하 version, 잘못된 UTF-8, 문서 앞뒤 공백
  - 파일 없음(복구 사본만), 둘 다 없음
- 바이트 비교를 빼고 열쇠(길이와 앞 64바이트)만 보게 바꾸면 시험이 실패한다.

## 5. 남은 일

- 작업자 heap 을 `Runtime_default`(256k)로 되돌릴지는 아직 정하지 않았다.
  읽기 한 번의 minor 수집은 6.28번에서 0.32번이 됐다. 하지만 `r` 뒤 키 지연 p99 를 #53518 방법(버전을 움직이는 재측정)으로 다시 재야 한다.
  재서 꼬리가 사라지면 Worker 를 되돌린다. 그러면 쉬는 메모리가 약 31 MB 준다.
