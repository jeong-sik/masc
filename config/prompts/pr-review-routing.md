# 리뷰 요청 라우팅

이 순서는 리뷰 작업 선택에 적용한다. 리뷰 기준·독립성·기능/논리/코드 청결도 검토와 승인 가드는 그대로 따른다.

1. 직접 메시지나 Board 요청을 받으면 먼저 GitHub REST에서 그 PR의 현재 `state`, `draft`, head/base와 Native Stack을 읽는다. 이미 병합되거나 닫힌 PR은 처리 종료를 한 번 알리고, 같은 턴에 다음 열린 PR로 간다. 옛 head를 승인하거나 닫힌 PR의 요청을 반복 처리하지 않는다.
2. 인증된 `gh` 계정의 `requested_reviewers`에 있는 열린 Ready PR을 먼저 처리한다. 여러 건이면 생성 시각이 오래된 순이다. 같은 head의 재검토 요청도 명시적 요청이므로 읽는다. GitHub 요청은 배정 사실이며, 실행 중·리뷰 완료·승인이라는 뜻은 아니다.
3. 같은 GitHub 계정을 공유하는 Keeper는 공식 요청을 공동으로 가진다. 담당 대표가 처리 중인 범위를 중복 수행하지 않고, 다른 Keeper는 자신의 렌즈 근거를 보탠다. Keeper 이름을 다른 독립 계정으로 세지 않는다.
4. 배정된 요청이 없으면 전체 열린 PR을 모든 페이지에서 읽는다. 아무에게도 공식 리뷰가 없고 사용자·팀 리뷰 요청도 없는 Ready PR을 오래된 순으로 고른다. 다른 계정에 배정된 PR은 그 계정의 요청이 실패했거나 인계가 명시된 경우에만 대신 맡는다. 게시가 막힌 PR에서 멈추지 말고 원인을 한 번 기록한 뒤 다음 미검토 PR로 간다.
5. CR은 그 작성 계정의 책임이다. 코드가 바뀌면 그 계정으로 재리뷰를 요청한다. 같은 head의 CR은 기본적으로 작성자의 수정/설명 대기이며, 명시적 재검토 요청이 있으면 다시 읽는다. 다른 계정의 PASS나 초록 CI로 CR을 해제하지 않는다.
6. 검토·게시 직전에 head/base/diff/stack을 다시 읽는다. 이전 검토는 같은 범위에서만 재사용한다. 요청이 목록에서 사라졌다고 완료로 세지 말고 실제 GitHub 리뷰를 확인한다. 승인·CR·COMMENT·미게시·조회 실패를 구분해 보고한다.

라우팅 담당자는 `scripts/review/review-worklist.py --repo OWNER/REPO --reviewer LOGIN`을 사용한다. 여러 독립 GitHub 계정은 `--reviewer`를 반복한다. 기본은 읽기만 하고, `--request`를 붙인 명시적 실행만 누락된 GitHub 리뷰 요청을 게시하고 재확인한다. 사용자·팀의 기존 요청은 지우지 않는다. 새로운 타이머나 상시 실행기를 추가하지 않는다.
