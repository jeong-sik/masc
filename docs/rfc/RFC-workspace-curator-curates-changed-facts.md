# workspace curator 는 바뀐 사실만 큐레이션한다

## 1. 문제

workspace curator(`workspace_curator_exact` lane)는 Keeper 들의 기억을 모아 공유 주장(shared claim)과 충돌(conflict)을 제안한다. 지금은 한 번 부를 때 **모든 Keeper 의 모든 사실**을 프롬프트 한 장에 넣는다 (`workspace_memory_context.ml` `collect`, `server_workspace_memory_curator.ml` `run`).

2026-09-28 라이브에서 이 방식은 한 번도 성공하지 못했다.

| 항목 | 값 |
|---|---|
| 실행 | 13:30:22Z–14:05:58Z 에 134번, 성공 0번 |
| 실패 이유 | 창 초과 83번 (`1261 Prompt exceeds max length`), 속도 제한 51번 |
| 렌더링한 프롬프트 | 4.59MB (3,367,474자) |
| 들어간 사실 | Keeper 27명의 3,366개, source 3,408개 |
| 사실 본문(claim) | 3.1MB |
| source 마다 붙는 메타데이터 | 0.76MB (스냅샷 해시 64자, revision, fact_index 를 사실마다 반복) |

크기만의 문제가 아니다. 구조가 세 곳에서 작업공간 크기에 묶여 있다.

- **입력.** 사실이 늘면 프롬프트가 같이 는다. 메타데이터를 다 지워도 claim 만 3.1MB 라, 어느 모델의 창에도 들어가지 않는다.
- **출력.** 프롬프트는 "모든 source ID 를 공유 주장, 충돌, 제외 가운데 하나에 넣어라" 고 요구한다 (`config/prompts/workspace_memory_curator.md`). 입력이 창에 들어가더라도 답이 3,408개를 모두 분류해야 한다.
- **결과물.** 제안(proposal)은 인벤토리 전체(source, 스냅샷)를 품는다 (`Workspace_memory_context.proposal_json`). 읽는 도구(`keeper_workspace_memory_read`)가 id 를 주고 읽으면 MB 단위를 받는다.

게다가 대부분의 실행은 할 일이 없었다. 연속한 두 실행의 입력을 비교하면, 바뀐 사실은 중앙값 0개, 많아야 추가 3개·삭제 5개였다 (마지막 30번). 요청 정체(request identity)가 스냅샷 revision 과 메타데이터를 포함해서, 사실이 그대로여도 새 입력으로 보고 전체를 다시 보냈다.

운영자는 2026-09-28 14:06Z 에 라이브 `runtime.toml` 에서 이 lane 의 구간을 빼서 멈췄다. 이 RFC 가 들어가기 전까지 켜지 않는다.

## 2. 결정

### 2.1 큐레이션 단위는 사실 하나다

사실의 정체(`fact_ref`)는 스토어가 사실 한 줄을 따로 두는 기준을 그대로 따른다. 그래서 스토어마다 모양이 다르다.

```ocaml
type fact_ref =
  | Ordinary of { keeper_id : string; claim_sha256 : string }
  | Source_bound of { keeper_id : string; path : string; claim_sha256 : string }
```

`claim_sha256` 은 claim 바이트의 SHA-256 이다.

- **ordinary.** 이 값이 `memory_id` 와 같다 (`lib/keeper/keeper_memory_os_types.ml:717-719`, `"sha256:" ^ SHA-256(claim)`). 같은 claim 을 다시 적으면 새 줄을 만들지 않고 있던 줄을 다시 본 것으로 친다 (`lib/keeper/keeper_memory_os_current.ml:2643-2668` `insert_or_reobserve`). 한 스토어 안에 같은 claim 은 한 줄뿐이라, claim 해시로 충분하다.
- **source_bound.** 이 스토어는 경로마다 사실 한 줄을 둔다. 같은 경로에 다시 쓰면 그 경로의 줄만 빼고 새 줄을 붙인다 (`lib/keeper/keeper_memory_source_current.ml:578-582`). 그래서 한 Keeper 의 두 파일이 같은 claim 을 가지면 스토어에는 두 줄이 있다. claim 해시만으로 정체를 정하면 이 두 줄이 하나로 합쳐진다. 그러면 한 파일만 바뀌거나 사라져도 같은 키가 남아 있어서, 원장에서 그 파일의 처분을 지울 수 없다. 그래서 `path` 를 정체에 넣는다.
- `path` 는 스토어가 저장한 `source.path` 그대로다. `upsert_file_fact` 는 앞뒤 공백만 자르고 (`lib/keeper/keeper_memory_source_current.ml:531`), 줄을 바꿀지는 이 값의 `String.equal` 로 정한다 (`:580`, 같은 파일). 정체도 같은 비교를 쓴다. 스토어보다 더 정규화하면(예: `./a.md` 와 `a.md` 를 하나로) 스토어의 두 줄이 다시 한 키로 합쳐진다.
- claim 이 바뀌면 새 사실이 되고, 옛 claim 은 사라진 사실이 된다. 파일 내용이 바뀌면 다음 재검증이 그 줄을 빼고 무효 기록을 남긴다 (`lib/keeper/keeper_memory_source_current.ml:720`).

지금의 `s1`, `s2` 같은 인벤토리 안 번호는 실행마다 바뀌어서 쓰지 않는다.

### 2.2 작업공간 원장

curator 는 자기 결과를 원장 하나에 모은다 (`<base>/.masc/workspace-memory/ledger.json`).

- 공유 주장: `{ claim_id, claim }`
- 충돌: `{ conflict_id, description }`
- 사실마다 처분: `fact_ref -> Claim_member claim_id | Conflict_member conflict_id | Excluded reason`

멤버 목록은 따로 적지 않는다. 어떤 주장의 id 를 처분으로 가진 사실이 그 주장의 멤버다. 멤버를 주장 쪽과 처분 쪽에 둘 다 적으면 두 기록이 어긋날 수 있다. 읽을 때는 처분이 없는 주장, 없는 id 를 가리키는 처분을 거절한다 (`lib/workspace_memory/workspace_memory_ledger.mli`).

원장은 모델의 해석이다. Keeper 기억을 바꾸지 않고, 의미를 검증하지 않는다. 지금 제안의 성격과 같다.

### 2.3 할 일은 집합 차이로 정한다

할 일은 두 가지다.

- **새 사실**: 지금 스토어에 있는데 원장에 처분이 없는 사실
- **사라진 사실**: 원장에 처분이 있는데 지금 스토어에 없는 사실

둘 다 현재 스토어와 원장을 `fact_ref`(2.1) 끼리 비교해서 구한다. 커밋 알림이나 journal 을 거슬러 읽지 않는다. 알림을 놓쳐도 다음 실행이 같은 차이를 다시 구한다.

읽지 못한 스토어(`Unavailable`)는 비교에서 뺀다. 그 스토어의 사실은 새로 넣지도, 사라진 것으로 보지도 않는다. 파일이 없는 스토어와 목록에 없는 Keeper 의 사실은 사라진 것으로 본다.

keepers 디렉터리가 없으면 실행하지 않는다. keepers 디렉터리 위치는 base 경로와 환경변수의 설정 디렉터리로 정해진다 (`Config_dir_resolver.inputs_for_base_path`). 그래서 설정이 다른 프로세스는 Keeper 를 0명으로 보고, 원장 전체를 사라진 사실로 지울 수 있다. 지금 `Workspace_memory_context.collect` 는 없는 디렉터리를 Keeper 0명으로 읽는다. 3단계 실행기는 이 둘을 구분해서 받는다.

사라진 사실은 모델 없이 처리한다. 처분을 지우면 멤버에서도 빠진다. 멤버가 하나도 남지 않은 주장·충돌은 지운다. source_bound 에서는 같은 Keeper 의 다른 경로가 같은 claim 을 계속 가져도, 바뀐 경로의 사실만 사라진다.

**할 일이 없으면 모델을 부르지 않는다.** 1장의 측정에서는 실행 대부분이 여기에 해당한다.

### 2.4 한 번 부를 때 넣는 것

새 사실을 오래된 순으로 한 묶음 고르고, 사실마다 비교할 거리를 붙인다.

- **이웃**: 다른 Keeper 의 현재 사실 가운데 이 사실과 가까운 K개. `Keeper_memory_search_index` 와 같은 SQLite FTS5 trigram 의 BM25 순위로 찾는다. 새 인프라가 필요 없고, 같은 입력에 같은 답을 준다 (`RFC-memory-search-beyond-substring.md` §3.1).
- **관련 주장·충돌**: 이웃이 이미 멤버인 원장 항목

#### 요청의 모양 (2026-10-22 개정)

요청은 표 모양이다. 같은 사실과 같은 주장은 한 요청에 한 번만 싣는다.

- `facts`: 요청에 나오는 사실 전부. 새 사실이든 이웃이든 한 번씩, 요청 안에서만 쓰는 짧은 id 와 Keeper, claim, 원장 소속(주장·충돌의 짧은 id 또는 없음)을 싣는다.
- `new_facts`: 분류할 사실의 짧은 id 와 그 사실의 이웃 짧은 id 목록.
- `claims`, `conflicts`: 실린 사실의 소속으로 참조된 원장 항목을 한 번씩 싣는다.

`fact_ref` 해시와 원장의 `claim_id`·`conflict_id` 는 모델에 보내지 않는다. 짧은 id 와의 대응은 호스트가 캡처한 묶음에만 둔다. 답(2.5)의 id 도 짧은 id 이고, 호스트가 대응표로 바꾼다.

요청 크기는 `묶음 크기 + 서로 다른 이웃 수 + 참조된 항목 수` 에 비례한다(N+M). 이전 모양은 사실마다 이웃 본문을 다시 실어서 `묶음 크기 × (1 + K)` 에 비례했다(9장).

#### 묶음 고르기 (2026-10-22 개정)

- **순서.** 분류할 사실은 Keeper 스냅샷의 `first_seen` 이 오래된 것부터 처리한다. 같은 시각이면 `fact_ref` 순서다.
- **첫 묶음.** 오래된 순 접두사를, 받는 add-on 이 선언한 `max_reply_bytes` 안에 들어가는 만큼 고른다.
  - 이 한도는 모델 창을 바이트로 어림한 값이 아니다. Curator worker 는 받은 요청을 `lane_host_requests` 답장에 그대로 담아 돌려준다. 그 답장이 `max_reply_bytes` 의 뜻인 "worker 가 보낸 메시지" 한도에 걸린다(`RFC-0471-max-reply-bytes-bounds-one-thing.md` 표 1번).
  - 호스트는 자기가 보낼 submit 인자의 바이트를 잰다.
- **모델 창.** 요청이 모델 창에 들어가는지는 provider 의 typed 크기 거절로만 안다. 거절되면 지금처럼 오래된 쪽 절반으로 줄여 다시 보낸다.
- **다음 묶음.** 마지막으로 끝난 묶음 사슬이 근거다.
  - 크기 거절 뒤 줄인 묶음이 답을 받았으면, 다음 묶음은 그 사실 수로 시작한다.
  - 거절 없이 답을 받았으면 그 사실 수의 두 배를 시도한다.
  - 어느 경우든 첫 묶음 한도를 넘지 않는다. 새로 저장하는 값은 없다. 남아 있는 묶음 사슬에서 매번 다시 구한다.
  - 크기와 상관없는 거절(잘못된 출력 등)은 근거로 쓰지 않는다.

이웃을 찾는 색인 비용은 따로 막는다.

- 지금의 `Keeper_memory_search_index.rank` 는 부를 때마다 받은 텍스트 전부로 `:memory:` FTS5 표를 새로 만들고, 채우고, 닫는다 (`lib/keeper/keeper_memory_search_index.ml:111-131`). 새 사실마다 이 함수를 부르면 처음 채우기(2.6) 전체에서 3,366 × 3,366, 약 1,133만 행을 넣는다. 작업공간 크기의 제곱으로 는다.
- 그래서 2단계는 같은 모듈에 "표를 한 번 만들고 질의를 여러 번 하는" 함수를 더한다. 실행 하나는 현재 사실 전부로 표 하나를 만든다. 묶음 안 새 사실마다 그 표에 질의하고, 같은 Keeper 의 사실을 뺀 앞의 K개를 쓴다.
- 실행 하나의 색인 비용은 현재 사실 수에 비례한다. 라이브 기준으로 3,366행(3.1MB)을 한 번 넣는다. 할 일이 없는 실행(2.3)은 표를 만들지 않는다.
- 지속 색인은 두지 않는다. 표는 실행이 끝나면 닫는다. 색인이 스토어와 어긋날 수 없게 한 지금 모듈의 결정을 그대로 따른다 (`lib/keeper/keeper_memory_search_index.mli:4-10`).

### 2.5 답의 모양

답은 묶음 안의 새 사실만 분류한다. 사실마다 하나를 고른다.

- 기존 주장에 합류: `claim_id`
- 새 주장: `claim`. 같은 묶음에서 같은 문구의 새 주장을 고른 사실은 결정론적인 같은 ID에 묶인다.
- 충돌: 기존 `conflict_id` 또는 새 설명. 같은 묶음에서 같은 설명을 고른 사실은 같은 ID에 묶인다.
- 제외: 이유

사실과 기존 주장·충돌은 요청의 짧은 id 로 가리킨다(2.4). 호스트는 캡처한 대응표로 실제 `fact_ref`·`claim_id`·`conflict_id` 로 바꾼다. 표에 없는 id 는 거절한다.

이웃은 판정 맥락이다. 이웃이 이미 원장 항목에 속했다면 기존 ID에 합류할 수 있지만, 이웃이라는 이유만으로 그 사실의 배정을 바꾸지 않는다. 묶음 밖의 사실은 분류하지 않는다. 그래서 답의 크기도 묶음 크기에 묶인다. 적용은 결정론적이다. 기존 ID 합류는 요청 시작 시점의 원장 항목만 허용한다. 없는 id 를 가리키거나 묶음에 없는 사실을 분류한 답은 의미 검증 거절(`Reject_and_advance`)로 다음 슬롯에 넘긴다.

### 2.6 처음 채우기

처음에는 3,366개가 모두 새 사실이다. 한 번에 한 묶음씩 처리하고, 남은 사실은 다음 실행이 이어서 한다. 묶음은 2.4 대로 오래된 사실부터 고른다. 별도의 일괄 작업은 두지 않는다.

Curator 가 멈췄다가 다시 켜질 때도 같다. 밀린 사실은 오래된 순으로 묶음마다 처리한다. 한 Keeper 의 사실이 순서 때문에 늘 뒤로 밀리지 않는다.

### 2.7 게시와 읽기

게시는 원장 스냅샷이다. `keeper_workspace_memory_read` 는

- id 없이 부르면 주장과 충돌을 멤버 참조와 함께 돌려준다.
- 주장이나 충돌 id 를 주면 멤버를 원래 사실 본문으로 풀어 준다.

인벤토리 전체를 결과물에 넣지 않는다.

## 3. 다른 방법과 비교

| 방법 | 장점 | 단점 |
|---|---|---|
| **바뀐 사실 + 이웃 (이 RFC)** | 요청 크기가 변경 크기에 묶인다. 할 일이 없으면 부르지 않는다 | 이웃 검색이 놓친 관계는 못 찾는다. 원장이라는 저장소가 새로 생긴다 |
| 묶음으로 나눠 map-reduce | 구현이 단순하다 | 매 실행마다 4.6MB 전체를 다시 보낸다. 다른 묶음에 있는 공유·충돌은 놓친다 |
| Keeper 별 요약 뒤 합치기 | 입력이 작다 | 주장이 원래 사실을 가리켜야 한다는 계약을 지키기 어렵다 |
| 메타데이터만 줄이기 | 바꿀 곳이 적다 | claim 만 3.1MB 라 여전히 넘친다. 출력 전체 분류도 그대로다 |
| 창이 큰 모델로 바꾸기 | 코드 변경이 없다 | 들어가더라도 작업공간과 같이 커지고, 출력 3,408개 분류는 남는다 |

이웃 검색의 한계는 실제 문제다. 표현이 많이 다른 같은 뜻의 사실은 BM25 가 가깝게 보지 않을 수 있다. 이 RFC 는 결정론적인 lexical 검색으로 시작하고, 놓친 비율을 7장의 하네스로 잰 뒤에 다른 검색을 고른다.

## 4. 이미 저장된 데이터 (hard cut)

- 지금 형식의 제안(`<base>/.masc/workspace-memory/*.json`)과 게시 기술자(`publication.json`)는 새 형식과 호환하지 않는다. 호환 reader 는 만들지 않는다. 라이브에는 성공한 제안이 없다 (1장).
- `Workspace_memory_context` 의 인벤토리 투영(source 번호 매기기, `proposal_json`)은 원장으로 대체되어 없어진다.
- 스냅샷의 `change`·`invalidations` 를 가리키던 `evidence_path` source 도 없어진다. 철회되거나 무효가 된 사실은 스토어에서 빠지므로 2.3 의 사라진 사실로 처리된다.
- 새 원장은 빈 상태에서 시작해 2.6 대로 채워진다.

## 5. 나눠 올리는 순서

1. **원장과 할 일 계산.** 원장 저장소, 사실 정체, 집합 차이, 사라진 사실 처리. 모델을 부르지 않는다.
2. **요청 만들기.** 묶음 자르기, 실행마다 한 번 만드는 이웃 색인과 검색, 관련 항목 붙이기, 크기 한도.
3. **답 적용과 lane 교체.** 새 출력 스키마, 결정론적 적용, 새 프롬프트, 게시와 읽기 도구. 옛 제안·인벤토리 코드는 이 단계에서 지운다.
4. **다시 켜기.** 운영자가 라이브 `runtime.toml` 에 lane 구간을 되돌린다.

## 6. 정할 것

- **Q1. 이웃 검색은?** 결정 (운영자, 2026-09-29): 있는 lexical 검색(`Keeper_memory_search_index` 의 FTS5 trigram BM25)으로 시작한다. 색인은 2.4 대로 실행마다 한 번 만든다. embedding 검색은 새 인프라와 외부 호출이 필요하다.
- **Q2. 묶음 크기는 어떻게 정하나?** 결정 (운영자, 2026-10-22, #41927): 2.4 "묶음 고르기" 대로 정한다. 첫 묶음은 받는 add-on 이 선언한 frame 까지 채우고, 모델 창은 provider 의 typed 거절로만 판단하며, 다음 묶음은 마지막으로 맞았던 크기로 시작한다. 2026-09-29 의 "context window 에서 바이트 상한을 계산한다"는 결정은 2026-10-06 운영 규칙(프롬프트 바이트 상한을 두지 않는다)으로 대체됐다.
- **Q3. 이웃 K 는?** 초기 구현은 발견한 다른 Keeper 수를 상한으로 쓴다. 이 수는 다른 Keeper마다 한 개씩 보장하는 분배 규칙은 아니고 BM25 전체 순위의 앞 K개다. 요청 크기와 놓친 관계 사이의 실제 교환은 7장의 사람이 표시한 쌍 하네스와 canary 로 검증해야 한다.
- **Q4. source_bound 스토어도 넣나?** 결정 (운영자, 2026-09-29): 넣는다. 지금도 두 스토어를 모두 읽는다.
- **Q5. 같은 Keeper 안의 사실끼리도 비교하나?** 결정 (운영자, 2026-09-29): 하지 않는다. 한 Keeper 안의 중복은 그 Keeper 의 Librarian 이 흡수(absorb)로 다룬다.

## 7. 검증

- **요청 모양.** 같은 사실이 여러 새 사실의 이웃이어도 `facts` 에 한 번만 실린다. 요청 바이트가 받는 add-on 의 frame 이하다. 같은 fixture 에서 실행 하나가 색인 표를 묶음마다 한 번만 만든다.
- **순서.** 새 사실은 `first_seen` 오래된 순으로 고르고, 줄일 때도 오래된 쪽 절반이 남는다.
- **다음 묶음.** 크기 거절 뒤 s 개로 맞은 다음 묶음은 s 개, 거절 없이 s 개로 끝난 다음 묶음은 2s 개(frame 안)로 시작한다.
- **할 일 없음.** 사실은 그대로고 revision 만 오른 커밋에서 모델 호출도, 색인 구축도 0번이다.
- **집합 차이.** 알림을 건너뛴 뒤의 실행이 빠진 사실을 모두 찾는다. 사라진 사실은 처분과 멤버에서 빠지고, 빈 항목은 지워진다.
- **같은 claim, 두 경로.** 한 Keeper 의 source_bound 스토어에서 두 파일이 같은 claim 을 가진 fixture. 한 파일만 바꾸거나 지우면, 원장에서 그 경로의 처분과 멤버만 빠지고 다른 경로의 처분은 남는다.
- **적용 거절.** 없는 id, 묶음 밖 사실, 중복 분류는 거절되어 다음 슬롯으로 넘어간다.
- **처음 채우기.** 라이브 3,366개 규모의 fixture 가 묶음 단위로 끝까지 채워지고, 모든 사실이 처분을 가진다.
- **이웃 검색 하네스.** 사람이 표시한 공유·충돌 쌍 표본에서 이웃 K개 안에 짝이 들어오는 비율을 잰다. Q1·Q3 의 근거다.
- **라이브 canary.** 다시 켠 뒤 한 시간 동안 실행 수, 모델 호출 수, 요청 바이트, 성공률을 1장의 값과 비교한다.

## 8. 다루지 않는 것

- 제안의 의미 검증과 Keeper 기억으로의 승격. 지금처럼 하지 않는다.
- lane 의 슬롯 구성. 이 RFC 는 무엇을 보내는지만 바꾼다.
- 이웃 수 K. 9장의 수치처럼 요청 크기의 대부분은 이웃이다. K 를 바꾸는 일은 분류 품질과 바로 이어져서, 6장 Q3 대로 사람이 표시한 쌍 하네스로 잰 뒤 따로 정한다.
- 원본마다 남는 원장 사본(캡처, commit 전후, 관찰 상태, 완료 영수증, 실행 기록). 원장 이력을 판본 digest 와 변경분으로 남기는 일은 `RFC-shared-memory-appends-a-log-and-keepers-read-from-their-position.md` Q6 과 함께 따로 정한다.

## 9. 개정 기록 (2026-10-22)

2026-10-07 커밋(b2679f6fd91, 218a61e33c1)이 첫 묶음을 "분류 안 된 사실 전부"로 바꿨다. 크기를 줄이는 길은 provider 의 크기 거절 뒤 반으로 나누는 것뿐이었다. #41927 이 그 결과를 10-08 에 쟀다. 143번 중 7번 성공했고, 사실 32개를 분류하려고 거절을 6번 받았다.

2026-10-22 에 Curator 를 add-on worker(메모리 128MiB, `max_reply_bytes` 4MiB)로 옮긴 뒤 잰 값이다.

| 항목 | 값 |
|---|---|
| 분류 안 된 사실 | 1,492개 (현재 사실 2,365개, 처분 873개) |
| 한 요청에 담긴 사실 | 1,481개 |
| 요청 입력 | 159.8MB. 이웃 본문 119.4MB, 관련 주장 37.9MB, 새 사실 2.1MB |
| 이웃 참조 / 서로 다른 이웃 | 57,750 / 2,351 (사실마다 이웃 39개 = Keeper 수 − 1) |
| 같은 내용의 표 모양 요청(시뮬레이션) | 4.6MB |
| 표 모양으로 오래된 순 4MiB 까지 | 새 사실 578개 |
| 표 모양으로 오래된 순 25개 | 1.06MB (함께 실린 사실 549개) |
| 결과 | worker 가 submit 을 읽다가 메모리 부족으로 죽었다(exit 137). frame 거절과 전송 실패는 타입 없는 오류라 크기 거절로 이어지지 않았고, 원본은 dispatch 대기에 갇혔다 |

순서도 문제였다. 새 사실은 Keeper id 알파벳 순으로 나왔고, 반으로 줄이면 늘 앞쪽 절반이 남았다. 2026-10-22 기준 알파벳 앞쪽 Keeper 19명은 사실의 70%, 뒤쪽 19명은 7%만 분류돼 있었다.

그래서 2.4 의 "요청의 모양"과 "묶음 고르기"를 고쳤다. 같은 내용을 한 번만 싣고, 오래된 사실부터, 받는 add-on 이 선언한 frame 까지 담고, 다음 묶음은 맞았던 크기로 시작한다. 원본 저장과 패스마다 하는 일은 `docs/design/workspace-curator-addon-execution.md` 에서 같은 원칙으로 고친다: 원본 하나는 요청 본문을 한 번만 저장하고, 한 패스는 할 일이 있는 원본만 연다.
