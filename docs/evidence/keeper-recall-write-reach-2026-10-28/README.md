## 읽을 수 있는 것

- 대기열에 들어간 쓰기는 Librarian 이 처리해야 검색에 나오고, 그때까지 시간이 걸린다. ok 영수증 341건 중 116건(34.0%)은 대기열을 거치지 않는 직접 쓰기다. 대기열을 거친 쓰기는 쓴 뒤 처리 pass 의 저널 시각까지 중앙값이 7분~22분, 90퍼센타일이 14.0시간~15.8시간이다(판정에 걸린 시간은 빠졌을 수 있어서 실제는 더 길 수 있다). 쓴 직후에 검색하면 이 시간 동안은 안 나온다. #46507 의 보고가 모두 이 경우인지는 모른다.
- 대기열 전체가 막힌 것은 아니다. 대기열에 들어간 쓰기 225건 중 대기 중은 6건이고, Keeper 40명 중 대기열 행이 있는 곳은 1곳이며 행은 모두 7건이다. 그 한 곳은 msx-retro-mania 이다. 마지막 Librarian commit 은 15.2시간 전이고, 행은 모두 그 뒤에 쓰였다(가장 오래된 행이 11.4시간 전). 저널은 pass 가 돌았는지 적지 않는다. 판정이 전부 `Deferred` 이면 행은 대기열에 남고 저널 행은 생기지 않는다(`lib/keeper/keeper_librarian_runtime.ml:906`, `lib/keeper/keeper_librarian_admission_owner.ml:242`). 그래서 이 Keeper 는 pass 가 안 돈 것일 수도, 돌았는데 전부 보류한 것일 수도 있고 저널로는 가를 수 없다. 원인은 못 봤다.
- 후보의 33.9%는 대상 없이 닫혔다. 코드를 읽으면 `Not_durable` 판정이다.
- Keeper 가 쓴 문장이 그대로 남는 일은 드물다. 대상이 있는 후보의 97.5%는 Librarian 이 다른 문장(다른 memory id)으로 붙였다. #46507 의 "썼는데 검색에 안 나온다"는 보고와 맞는 수치이지만, 그것이 원인이라고 확인한 것은 아니다.
- 대상은 대부분 쓴 뒤에 새로 생긴 사실이다. 쓰기 전에 있던 사실에 붙는 일은 많아야 6.4%다(저널 시각이 쓴 시각보다 앞선 30건과 어느 commit 도 더하지 않은 1건). 어느 행도 더하지 않은 사실은 드물지만 있다. 현재 사실 2,343개 중 43개(1.8%)다. 저널이 시작되기 전부터 있던 사실일 수 있고, 확인하지는 못했다.
- 대상이 지금 그대로 현재 사실인 것은 35.6%다. 개정과 흡수 기록을 따라가면 73.5%가 현재 사실에 닿는다. 닿은 사실이 원래 내용을 담는지는 읽지 않아서 모른다.
- 현재 사실에 안 닿은 129건이 사라졌다고 단정할 수 없다. 철회 6건을 뺀 123건은 마지막 id 를 commit 이 뺐다. 123건 모두 Librarian pass 가 뺐다. 그중 90건(73.2%)은 같은 commit 이 다른 사실도 더했다. 같은 종류의 id 1,204개(현재 사실이 아니고, 개정·흡수·철회 기록이 이어지지 않고, 10-19 이후 Librarian pass 가 뺀 것)에서는 그 비율이 80.1%라서 이 90건이 특별히 높지 않고, 다른 문장으로 남았다는 근거가 되지 않는다. 이유가 적힌 비율은 이 123건이 36.6%이고 같은 종류가 29.5%다. 이유가 적혔다고 사실이 남은 것은 아니다. 이유 문장과 더한 사실은 읽지 않았다.
- 처리 시간은 판정이 끝난 시각이 아니다. 아래 "수치를 센 방법"에 이유를 적었다.

원인은 모른다. 왜 대상 없이 닫는지는 영수증에 판정 이유가 없어서 이 측정으로는 볼 수 없다.

## 무엇을 했나

`scripts/keeper-recall-write-reach.py`(읽기 전용)를 돌렸다. 명령은 이렇다.

```bash
python3 -I scripts/keeper-recall-write-reach.py <base-path>/.masc/keepers \
  --memory-dir <base-path>/.masc/config/keepers --since 2026-10-02 \
  --now 2026-10-28T15:31:23Z \
  --exclude lab-sangsu --exclude taskmaster --exclude microvm-probe-829
```

`--now` 는 출력의 읽은 시각에만 쓴다. 제외한 셋은 기준선과 같은 시험·실험 Keeper 다. 카나리 Keeper 가 아직 없어서 전체를 쟀다. `--only <Keeper>` 로 좁힐 수 있다. `--since` 는 호출을 호출 시각으로, 후보를 쓴 시각으로 거른다. 출력 맨 끝 줄은 쓰지 못한 입력(JSON 이 아닌 줄, 시각이 없거나 달력 밖인 행, 이름에서 시각을 못 읽은 trace 파일)의 수인데 이번에는 없었다.

읽은 파일은 이렇다.

| 파일 | 쓰는 곳 |
|---|---|
| `<keepers-dir>/<keeper>/raw-traces/*.jsonl` | 쓰기 호출과 영수증. `tool_execution_finished` 기록의 첫 줄이 영수증 JSON 이다. 파일 이름(`turn-<밀리초>-...`)에서 그 턴의 시작 시각을 얻는다. |
| `<memory-dir>/<keeper>.librarian-range-commit.json` | Librarian 이 처리한 후보마다 영수증 하나. `admission_recall_binding` 이 있으면 대상 사실에 붙인 것이고, `explicit_candidate_id` 만 있으면 대상 없이 닫은 것이다. |
| `<memory-dir>/<keeper>.memory-admission.json` | 아직 대기열에 있는 후보. |
| `<memory-dir>/<keeper>.memory-journal.jsonl` | commit 행. 영수증의 `snapshot_revision` 과 같은 revision 의 Librarian 행에서 시각을, 모든 commit 행에서 사실이 처음 더해진 시각과 마지막으로 빠진 행(이유 유무, 같은 행이 더한 사실)을 얻는다. |
| `.memory-current.json`, `.memory-events.jsonl`, `.memory-absorbed.jsonl` | 대상이 지금 현재 사실인지, 개정·흡수·철회 기록이 어디로 이어지는지. |

## 수치를 센 방법

- 후보를 "대상 없이 닫은 것"이라 부르는 근거는 코드다. Librarian 런타임은 `Incorporated` 와 `Already_represented` 에만 대상 binding 을 만들고 `Not_durable` 에는 만들지 않는다(`lib/keeper/keeper_librarian_runtime.ml:920-933`). `Deferred` 는 처리된 것이 아니라서 영수증이 없다(`lib/keeper/keeper_memory_admission_judgment.ml:104`). 영수증에는 판정 이름이 없다.
- 영수증은 처리한 pass 가 아니라 Memory revision 을 적는다. 사실이 바뀌지 않은 pass 는 새 revision 을 만들지 않고, 유지된 revision 으로 저널에 행을 하나 더 쓴다. 대상이 있는 영수증 486건 중 177건은 그 revision 에 Librarian 시각이 둘 이상 있다(`report.txt`). 그래서 시각은 하나로 못 정하고 범위로 센다. 가장 이른 값은 쓴 시각 이후의 첫 시각이고, 가장 늦은 값은 그 revision 의 마지막 시각이다.
- 저널 행의 시각은 판정이 끝난 시각이 아니다. 대기열을 거친 pass 는 판정 전에 `now` 를 잡고 commit 이 그 값을 그대로 쓴다(`lib/keeper/keeper_librarian_admission_owner.ml:128`, `lib/keeper/keeper_librarian_admission_commit.ml:221`). 그래서 위 시간은 "쓴 뒤 그 pass 가 대기열을 읽기까지"이고 판정에 걸린 시간이 빠져 있다. 다른 경로의 Librarian commit 은 commit 시각을 적고, 영수증은 행이 어느 경로인지 말하지 않는다. `source.kind` 가 `librarian` 인 행만 pass 로 센다. Keeper 가 직접 쓴 행(`explicit_write`)은 pass 가 아니다.
- "쓰기 전/후"는 대상을 처음 더한 commit 행의 시각을 원문 사실의 `first_seen`(Keeper 가 쓴 시각)과 견준 값이다. 그 시각 이후로 찍힌 행은 그 pass 가 쓴 뒤에 대기열을 읽었다는 뜻이라서 정확하다. 그 이전으로 찍힌 행은 pass 가 쓰기 전에 시작해 쓴 뒤에 끝났을 수 있어서 "많아야"로 센다. 어느 commit 행도 더하지 않은 대상은 저널이 시작되기 전부터 있던 사실일 수 있다. 사실을 더하는 commit 은 저널 기록이 실패하면 복구 대기로 남았다가 다음 쓰기에 다시 쓰여서(`lib/keeper/keeper_memory_os_current.ml:1654-1680`), 기록 실패로 행이 빠졌다고 보기는 어렵다. 현재 사실 중에도 어느 행이 더했는지 모르는 것이 43개(1.8%) 있고 원인은 확인하지 못했다. 그래서 "쓰기 전에 이미 있던 사실일 수 있는 것"은 시각이 앞선 행과 어느 행도 더하지 않은 경우를 더한 값이다. 영수증의 쓴 시각을 못 읽을 때도 이 칸에 들어간다. 대상이 사실에서 빠졌다가 돌아온 경우는 처음 더한 시각으로 센다. 영수증은 어느 pass 가 대상을 더했는지 말해 주지 않아서, 한 pass 가 더한 사실을 여러 후보가 같은 대상으로 쓸 수 있다.
- memory id 는 claim 의 SHA-256 이다. Librarian 이 문장을 바꾸면 id 가 달라진다. 그래서 "쓴 문장 그대로"는 영수증이 가진 Keeper 의 원문 claim 과 대상의 id 가 같은 경우만 센다.
- 대상의 지금 상태는 `keeper-recall-baseline.py` 의 회수 id 추적과 같은 규칙으로 따라간다. 현재 사실이면 거기서 끝난다. 아니면 개정 기록(`superseded_by`)이나 흡수 기록(`into`)을 따라 현재 사실, 철회, 기록 없는 id 중 하나에 닿을 때까지 간다. 같은 id 에 개정과 흡수 기록이 둘 다 있으면 개정을 먼저 따라간다. 철회된 뒤 같은 claim 이 다시 더해졌으면 현재 사실로 센다.
- 현재 사실이나 철회에 닿지 못한 대상은 기록이 끝난 id 를 뺀 commit 행을 찾는다. 행의 `dropped` 목록이 그 id 를 비어 있지 않은 이유와 함께 적었으면 "이유를 적었음"이다. 이유 문장은 비어 있는지만 보고 출력하지 않는다. 같은 행의 `change.added` 가 비어 있지 않으면 "다른 사실도 더했음"이다. 한 id 를 여러 번 뺐으면 마지막 행을 쓴다. 이 두 값만으로는 사실이 남았는지 알 수 없어서, 같은 종류의 id 에서 같은 두 값을 세어 견준다. 같은 종류란 현재 사실이 아니고, 개정·흡수·철회 기록이 이어지지 않고, 마지막으로 뺀 행이 첫 쓰기(10-19) 이후의 Librarian pass 인 id 다. 위 123건 중 이 조건을 채우는 것은 123건이다(표의 "같은 종류의 조건을 채우는 것" 줄). 명시 쓰기 행은 `dropped` 에 이유를 적지 않아서 섞지 않았다.
- `--since` 는 후보를 쓴 시각으로 거른다. 영수증에 쓴 시각이 없는(대상 없이 닫은) 후보는 쓴 시각이 아니라 처리된 시각, 곧 그 revision 의 Librarian 시각으로 자리를 정한다. 시각이 모두 `--since` 이전이면 오래된 것이고, 모두 이후면 창 안이다. 창 시작 전에 쓰고 창 안에서 처리된 후보도 창 안에 들어간다. 양쪽에 걸치면 어느 pass 가 처리했는지 몰라서 자리를 정하지 못한 것으로 세고 표에서 뺀다. 이번 읽기에서는 자리를 정하지 못한 것이 0건, `--since` 보다 오래된 것이 0건이었다.
- 시각이 달력 밖이면(밀리초 단위로 적힌 값 등) 그 기록은 읽지 않고 마지막 줄에 센다. 영수증의 쓴 시각이 없거나 그런 경우는 쓴 시각이 없는 것으로 읽는다.
- revision 번호는 격리 뒤에, 그리고 스냅샷이 없을 때 1부터 다시 시작한다(`lib/keeper/keeper_memory_os_support_core.ml:210`). 격리 행은 검사 없이 덧붙여서 빠질 수 있다. 그래서 격리 행(`quarantined`)을 만났을 때와, 앞의 commit 행보다 revision 이 작은 commit 행을 만났을 때 그 앞의 revision 시각을 버리고, Keeper 표 맨 오른쪽에 횟수를 적는다. 번호가 앞 행과 같게 다시 시작하면 가려내지 못한다. 이번 읽기에는 다시 시작한 Keeper 가 없었다.
- 읽는 Keeper 는 쓰기 호출이 있거나 영수증, 대기열, 저널, 현재 사실 파일 중 하나라도 있는 곳이다. 대기열 행 수는 대기열 파일의 `pending` 행을 모두 센다. 행이 있는 Keeper 마다 가장 오래된 행의 나이(`fact.first_seen`)와 그 Keeper 저널의 마지막 Librarian commit 시각을 함께 적는다. 쓸 수 없는 `fact.first_seen` 은 나이에서 빼고 마지막 줄에 센다. 저널 파일이 없으면 "알 수 없음"이고, 파일은 있는데 Librarian 행이 없으면 "저널에 없음"이다. 호출과 맞대는 쪽(대기 중 6건)은 요청 id 로 맞추고, 이 수는 오래된 행과 trace 에 호출이 없는 행도 센다.
- Keeper 별 trace 파일 수의 중앙값은 Keeper 수가 짝수면 가운데 두 값의 평균이다.
- 표에서 뺀 영수증 103건은 후보가 아니다. Librarian 이 자기 읽기 범위에 쓴 `range_id` 66건, `official_range_id` 37건이다. 이 건수는 `--since` 와 관계없이 센다.
- 호출 하나는 한 칸에만 들어간다. 호출 표의 합이 호출 수와, 대기열 표의 합이 대기열 쓰기 수와 같은지 시험이 확인한다.

## 못 잰 것

- **카나리 Keeper 한정 값.** 카나리가 정해지지 않았다. Keeper 별 표는 `report.txt` 에 있고 40명이 모두 나온다. 읽지 못한 파일은 표 맨 오른쪽에 이름으로 적힌다. 6명은 `memory-admission.json` 이 없다.
- **판정이 끝난 시각.** 저널 시각은 pass 가 대기열을 읽은 시각이라서 쓴 뒤 판정이 끝날 때까지 걸린 시간은 모른다.
- **호출 결과 유실(RFC §5 의 5).** 남은 trace 에서 시작 기록만 있고 끝 기록이 없는 쓰기 호출은 0건이다. "적용됐는데 결과를 못 받은" 호출은 trace 의 영수증과 원장의 후보를 맞대야 한다. 공식 클라이언트의 호출 12건은 trace 에 결과가 없어서 맞댈 수 없다. trace 가 남은 기간에 쓴 후보 185건 중 호출이 안 맞은 7건의 이유는 못 찾았다. 재시도로 생긴 중복도 재지 않았다.
- **오래된 쓰기의 호출.** raw trace 가 Keeper 마다 최근 200개가량이라서 쓴 시각을 아는 후보 486건 중 301건(61.9%)은 쓸 때의 trace 가 지워졌다. 쓴 시각을 모르는 213건도 호출이 없다. 호출 표는 남은 trace 만 센 값이다.
- **판정 이유.** 대상 없이 닫은 249건이 왜 닫혔는지. 대상이 사라진 123건 중 78건은 저널에 이유가 없다.
- **멈춘 대기열의 원인.** 06:06Z, 07:04Z, 07:39Z, 13:23Z, 15:31Z 에 읽었을 때 대기 중인 쓰기는 msx-retro-mania 에만 있었고 각각 1건, 1건, 4건, 6건, 6건이다. 왜 처리되지 않는지는 보지 못했다.
- **이어진 사실의 내용.** 개정·흡수 기록을 따라 현재 사실에 닿은 184건과, 같은 commit 이 다른 사실을 더한 90건이 원래 내용을 담는지는 읽지 않았다.
