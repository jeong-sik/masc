# `_blob` 인자 호출 측정 (2026-11)

`measure_blob_inputs.py` 는 Keeper 가 도구 인자를 `{"_blob": ...}` 모양으로 보낸 호출을 세요(이슈 #47642).
모델에 보낸 요청에서 지난 호출의 인자가 그 모양으로 줄어 있었는지, 어느 모델이 그 모양을 따라 했는지도 재요.
`.masc` 아래의 세 저장소를 읽기만 해요.

| 저장소 | 쓰는 곳 |
|---|---|
| `tool_calls/YYYY-MM/DD[.NNN].jsonl` | 도구 호출 원장이에요. `input` 은 도구 계층이 받은 인자 객체예요 |
| `keepers/<keeper>/provider-inputs/YYYY-MM/DD.jsonl` | 턴마다 요청 하나를 저장한 기록이에요. 메시지마다 `content_ref` 가 있고, `wire.model` 이 모델 이름이에요. 같은 턴의 다른 요청은 저장하지 않아요 |
| `tool_blobs/<sha 앞 두 글자>/<sha>` | `content_ref` 가 가리키는 메시지 JSON 과, 강등된 호출의 원본 인자예요 |

## 다시 재기

```bash
docs/evidence/blob-input-2026-11/measure_blob_inputs.py --base-path ~/me \
    --from-date 2026-10-19 --to-date 2026-11-04 --until 2026-11-04T19:10:00Z \
    --split 2026-11-04T09:00:00Z --json-out after.json
```

이 폴더의 `result-2026-10-19_11-04.json` 이 위 명령의 결과예요. 원장 17일치를 읽어서 90초쯤 걸려요. 시험은 `python3 -m unittest discover -s docs/evidence/blob-input-2026-11` 로 돌려요.

`--split` 은 그 시각 전과 후를 따로 요약해요. 정각인 호출이나 요청은 후로 세요. 여기서 쓴 11-04T09:00Z 는 저장된 강등이 마지막으로 보인 시각(08:59:00Z) 바로 뒤의 정각이에요. 배포를 가르는 값으로 쓸 때는 배포 시각을 넣어요.

## 센 방법

- `_blob` 호출: 창 안(`--from-date` 자정 UTC 부터 `--until` 까지)의 원장 행 중 `record_kind` 가 `tool_call` 이고 `input` 이 `_blob` 키를 가진 객체인 행이에요.
  - `alone`: `_blob` 이 `input` 의 유일한 키예요. `mixed`: 다른 키가 같이 있어요.
- 결과: `refused_before_run` 은 `disposition` 이 없고 `wire_outcome` 이 `error` 인 행(도구가 실행되기 전에 거절된 호출)이에요. `completed` 는 `disposition` 이 `completed` 인 행이고, 나머지는 `other` 예요.
- 봉투: `bytes`(0 이상의 정수), `mime`(공백이 없는 글), `preview`(글), `sha256`(소문자 16진수 64자) 네 필드만 있는 객체예요. OCaml 쪽 `Tool_output.normalized_artifact_ref_of_json` 이 받아들이는 모양과 같아요.
  - `_blob` 값이 봉투면 `complete_envelope`, 다른 객체면 `wrapped_arguments`(진짜 인자를 `_blob` 아래에 넣은 호출), 객체가 아니면 `not_an_object` 예요.
- 해시가 저장소에 있다: 봉투의 `sha256` 이름으로 `tool_blobs/<sha 앞 두 글자>/<sha>` 파일이 있어요. `Keeper_model_input_demotion` 이 만든 강등은 이 blob 을 항상 써요.
- 강등된 인자: 저장된 요청의 메시지에서 assistant 의 `tool_use` 블록 중 `input` 이 `_blob` 키 하나뿐이고 그 값이 봉투인 것이에요. 줄인 바이트는 봉투의 `bytes` 에서 그 객체의 압축 JSON 크기를 뺀 값이에요.
- 강등된 결과: `tool_result` 블록 중 `content` 가 `[masc:blob` 로 시작하는 것이에요. 줄인 바이트는 마커의 `bytes=` 값에서 마커 길이를 뺀 값이에요.
- 같은 크기로 저장됨: 해시의 blob 파일이 있고 크기가 봉투의 `bytes` 와 같아요.
- 저장된 강등: 같은 크기로 저장된 강등된 인자예요. 요청의 강등된 인자 중 하나라도 그렇다면 그 요청에 저장된 강등이 있어요. 모델이 지어낸 `_blob` 호출이 이후 요청에 되돌아온 것도 강등된 인자로 세지만, 그 해시는 blob 이 없어서 저장된 강등이 아니에요.
- 턴: 한 Keeper 의 저장된 요청 두 개 사이(앞 요청 시각 초과, 뒤 요청 시각 이하)에 든 `alone` 호출은 뒤쪽 요청이 끝낸 턴의 호출이에요. 턴이 저장된 요청을 남기지 않았으면 구간이 여러 턴을 덮어요. Keeper 의 첫 저장된 요청은 턴을 끝내지 않은 것으로 보고, 그 앞이나 마지막 저장된 요청 뒤의 호출은 턴에 넣지 않아요.
- 호출의 모델: 그 호출 앞뒤의 저장된 요청 두 개가 같은 모델이면 그 모델이에요. 한쪽에 저장된 요청이 없거나(`unattributed: no stored request on one side`) 두 모델이 다르면(`unattributed: the stored requests on both sides use different models`) 모델을 정하지 않아요. 턴 표의 모델은 그 턴을 끝낸 요청의 `wire.model` 이에요.
- 몫과 중앙값은 강등된 인자가 있는 요청끼리 센 값이에요. 줄인 바이트의 본문 몫은 요청마다 `줄인 바이트 ÷ wire.body_bytes` 를 구해 중앙값을 냈어요.

## 조심할 것

- 저장된 요청은 턴마다 하나라서 모델 요청의 일부예요. 어느 요청을 저장하는지는 확인하지 못했어요.
- 해시가 저장소에 없는 봉투는 모델이 지어낸 값일 수 있고, 지워진 blob 일 수도 있어요. 시스템이 만든 해시의 95.8%가 같은 창에서 저장소에 있어서, 지워진 몫은 많아야 4.2%예요(저장된 요청에서 본 해시만 센 값이에요).
- 원장 행에는 모델이 없어요. 호출의 모델은 앞뒤 저장된 요청으로 정한 값이라서, 저장된 요청이 없던 10-28T11:08Z 까지의 호출 1,487건은 모델을 몰라요.
- 턴 표는 같이 나타난다는 것까지만 보여요.
  - 모델마다 쓰는 Keeper 가 달라서 모델 차이만으로 읽을 수 없어요.
  - 턴을 끝낸 요청은 그 턴 앞쪽 호출의 줄인 인자도 담아서, 호출이 많은 턴에 저장된 강등이 더 많이 보일 수 있어요.
  - 구간이 여러 턴을 덮는 경우가 있어서 `turns` 와 `calls` 의 비율은 턴당 호출 수의 근사예요.
- 모델이 진짜 해시를 그대로 베껴 보낸 호출은 7건이에요. 이 호출이 되돌아온 기록은 저장된 강등으로 세어져요.
- 11-04T09:00Z 는 병합(#48123 과 #48124, 11-04T08:53Z) 직후의 시각이지만, 서버를 언제 다시 띄웠는지는 기록에서 찾지 못했어요. 배포 전후를 비교할 때는 실제 시각을 `--split` 에 넣어요.
- 강등된 인자가 요청의 84%에 있던 이유는 이 측정이 직접 가르지 않아요. 저장된 강등이 11-04T08:59Z 를 마지막으로 모든 모델에서 사라진 것이 #48124 병합 시각과 맞을 뿐이에요.
- 시험 130개가 통과하고, 계산을 틀리게 바꾼 변형 179개를 모두 잡았어요.
