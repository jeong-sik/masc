# `Execute` 기다림 측정 (2026-11)

`measure_execute_waits.py` 는 `Execute` 호출이 얼마나 오래 걸리는지, 오래 걸린 호출이 무엇을 기다리는지, Keeper 가 기다리는 대신 `masc_schedule_create` 로 나중에 깨우는지를 재요.
도구 호출 원장(`.masc/tool_calls/YYYY-MM/DD[.NNN].jsonl`)을 읽기만 해요.
`docs/rfc/RFC-keeper-async-fleet-continuity.md` 가 풀려는 기다림이 얼마나 되는지 재요.
`docs/rfc/RFC-0379-keeper-monitor-event-wake.md` §6 이 제안하는 `Github_run_completed` 트리거가 겨냥하는 기다림도 재요.
`measure_schedule_slack.py` 는 Keeper 가 자기를 깨우려고 만든 일정이 실행의 끝을 놓친 크기를 재요("일정이 실행의 끝을 놓친 크기" 절).
`measure_watched_wakes.py` 는 `until_github_run` 을 단 일정이 실행의 끝에서 Keeper 의 새 턴까지 가는 길을 단계마다 재요(맨 아래 절).

## 다시 측정하기

```bash
docs/evidence/execute-waits-2026-11/measure_execute_waits.py --base-path ~/me \
    --from-date 2026-11-01 --to-date 2026-11-05 --until 2026-11-05T05:00:00Z --json-out after.json
```

이 폴더의 `result-2026-11-01_11-05.json` 은 위 명령의 결과예요. `after.json` 과 비교해 보세요. 원장 5일치와 trace 파일을 읽는 데 20~40초쯤 걸려요.
원장은 오래된 날짜 파일을 지워요. 2026-11-05 에 보니 10월은 06일부터 남아 있었어요. 그래서 같은 창은 그 안의 날짜 파일이 지워지기 전까지만 같은 값이 나와요. trace 파일(`.masc/keeper_turn_events`)이 지워져도 턴 시간이 달라져요. 서버는 `jsonl_retention_days`(저장소 기본값은 30일)보다 오래된 trace 파일을 지워요.
지워진 날은 `days_without_file` 에 나오고, 파일을 하나도 못 읽으면 에러로 끝나요.
아직 쓰고 있는 날이 창에 걸리면 조각 파일이 늘어서 `files_read` 가 달라져요. 11-05 창을 다시 재니 55개에서 56개로, 또 57개로 늘었고 다른 값은 같았어요. 파일 목록을 읽은 뒤에 조각이 나뉘면 그 행이 빠질 수도 있어요. 값을 확정할 때는 끝난 날까지만 재세요.
`skipped_lines` 는 날짜 파일 전체의 깨진 줄을 세서, 원장에 깨진 줄이 새로 생기면 달라져요.
시험은 `python3 -B -m unittest discover -s docs/evidence/execute-waits-2026-11` 로 돌려요. Python 3.11 이상이 필요해요(`StrEnum`, `Z` 로 끝나는 시각을 읽는 `datetime.fromisoformat`).

## 센 방법

- 창: `--from-date` 자정(UTC)부터 `--until` 앞까지예요. `--until` 을 안 주면 `--to-date` 다음 날 자정이에요. 시간대가 없는 `--until` 은 UTC 로 읽어요.
- `Execute` 호출: 창 안의 원장 행 중 `record_kind` 가 `tool_call` 이고 `tool` 이 `Execute` 이며 `duration_ms` 가 0 이상의 유한한 숫자인 행이에요. 실패한 호출도 세어요. 실패해도 턴은 기다렸으니까요. 초는 `duration_ms ÷ 1000` 이에요.
- 시각: 행의 `ts` 는 호출이 끝나고 행을 쓴 시각이에요. 호출은 끝난 날과 끝난 창에 들어가요.
- 명령: `input.command` 가 글이면 그 글이고, 아니면 `input.argv` 의 항목을 글로 바꿔 공백으로 이은 글이에요. `scripts/measure-tool-efficiency.py` 의 `command_text` 와 같은 규칙이에요. 둘 다 없는 호출은 명령이 없어서 `calls_without_command` 에만 세고 `sleep`·실행 번호가 없는 호출로 봐요.
- `sleep` 든 호출: 명령에 `sleep` 다음 공백과 숫자가 있는 호출이에요.
- 실행 번호: GitHub Actions 실행의 번호예요. `actions/runs/` 뒤, 또는 `run `·`runs ` 뒤의 10~11자리 숫자예요. 사이에 `view `·`watch `·`rerun `·`cancel ` 이 하나 있어도 돼요. 더 긴 숫자는 번호로 안 봐요. 셸 반복문 변수로 번호를 넘기는 호출은 번호를 못 읽어요.
- 저장소: `repos/`·`-R `·`--repo `(또는 `--repo=`)·`github.com/` 뒤의 `owner/name` 이에요. 소문자로 바꾸고 끝의 `.git` 은 떼요. 저장소가 여럿인 명령은 저장소마다 들어가요. `-R ` 는 `cp -R a/b` 같은 다른 도구의 옵션에도 맞아서, 그 이름도 저장소로 세어요.
- 종류: 아래에서 명령에 처음 맞는 하나예요. `names_a_run`: 실행 번호가 있어요. `gh_without_run`: 단어 `gh` 가 있어요. `build_or_test`: 단어 `dune`, `opam`, `make`, `npm`, `pnpm`, `yarn`, `cargo`, `pytest`, `vitest`, `tsc` 중 하나나 `python -m unittest` 가 있어요. `rest`: 그 밖이에요. 명령이 없는 호출도 여기예요.
- 오래 걸린 호출: 60초 이상 걸린 `Execute` 호출이에요.
- GitHub 호출: 오래 걸린 호출 중 종류가 `names_a_run` 이나 `gh_without_run` 인 호출이에요. `sleep` 이 있든 없든 세어요. JSON 의 `long_calls.github_*` 가 오래 걸린 호출 전체에 대한 값이고, `long_calls.sleeping_github_*` 는 `sleep` 든 호출에 대한 값이에요.
- 폴링 호출: `sleep` 이 들어 있고 실행 번호가 하나 이상 있는 호출이에요.
- 실행 기다림: 한 Keeper 가 같은 실행 번호를 가리킨 폴링 호출들이에요. 번호가 여럿인 호출은 번호마다 기다림에 들어가요. 기다림의 시간은 그 호출들의 시간 합이고, 60초보다 짧은 폴링도 들어가요. 기다림이 가리키는 저장소는 폴링 중 하나라도 이름을 댄 저장소예요.
- 합계 방식: 폴링 수, 막힌 시간, Keeper 와 저장소별 막힌 시간은 폴링 호출을 한 번씩만 세어요. 기다림 하나하나의 값(기다림당 폴링, 기다림당 막힌 시간)은 한 호출이 속한 기다림마다 따로 세어요. 기다림별로 더한 값은 `polls_summed_over_waits`, `blocked_hours_summed_over_waits` 에 따로 있어요. 저장소별 값은 저장소 이름이 여러 개 든 호출을 저장소마다 세어서, 그런 호출이 있으면 저장소별 합이 막힌 시간보다 커져요. 이 창에는 그런 호출이 없어요.
- 일정 깨움: `masc_schedule_create` 행 중 기록된 결과가 성공이고 `input.keeper_name` 이 행의 Keeper 와 같은 것이에요(Keeper 가 자기를 깨우는 일정). 성공은 `scripts/lib/recorded_tool_outcome.py` 의 규칙이에요. `disposition` 이 있으면 `completed` 만 성공이고, 없으면 `wire_outcome` 이 `ok` 일 때 성공이에요. 메시지에 실행 번호가 있으면 실행 번호를 가진 일정이에요.
- 턴 구간: Keeper 의 trace 파일(`.masc/keeper_turn_events/<Keeper>/` 안의 파일 하나)의 첫 줄과 끝 줄 시각 사이이고, 창 안으로 잘라요. 읽는 코드는 `measure_lane_time.py` 의 `read_runs` 하나를 같이 써서 두 스크립트가 같은 턴 시간을 세요. 한 Keeper 의 턴 시간은 그 구간들의 합집합이고, 전체 턴 시간은 Keeper 별 합집합의 합이에요. trace 파일이 없는 턴은 구간이 없어요.
- 턴 구간 안·밖: 호출 시간 중 그 Keeper 의 턴 구간에 드는 초가 안이고 나머지가 밖이에요. trace 파일이 없는 턴의 호출은 이 창에서 턴 구간 안에 든 초가 0이에요(`lane-time-2026-11/result-2026-11-01_11-05.json` 의 `turn_time.calls_without_trace_file.tool_time_inside_turns_s` 가 0.0). 그 Keeper 에 trace 파일이 있으면 잰 값이고, trace 파일이 하나도 없는 Keeper 는 턴 구간이 없어서 정의상 0이에요. 턴 시간에 대한 비율은 안의 시간으로만 세요. 분모인 턴 시간에 밖의 시간이 없으니까요. 값은 JSON 의 `turn_time` 에 있어요.
- 날짜: 행의 `ts` 를 UTC 날짜로 바꾼 값이에요. 창이 날 중간에 끝나면 그날은 끝나기 전까지만 들어 있어요.
- 백분위는 가까운 순위(nearest rank)예요. 값 n개를 정렬해서 `올림(p × n)` 번째 값을 써요.
- 위 분류는 이 보고서에서 호출에 이름을 붙이는 용도예요. 서버가 이 값을 읽고 무언가를 정하지 않아요.

## 조심할 것

- 분류는 명령 문자열로 붙여요. `echo "sleep 5"` 처럼 글 안에 `sleep` 만 있어도 `sleep` 든 호출로, `echo gh` 도 `gh` 를 쓴 호출로 세어요.
- `gh` 를 쓴다고 GitHub 를 기다린 것은 아니에요. `sleep` 이 든 호출만 기다림으로 읽어요. `sleep` 이 없는 `gh` 호출은 `gh api` 를 반복문으로 여러 번 부르느라 오래 걸린 호출일 수도 있고, 이 측정이 가르지 못해요.
- 실행 번호는 명령 문자열에 그대로 보일 때만 읽어요. 번호를 반복문 변수로 넘기는 호출은 `gh_without_run` 에 들어가서, `names_a_run` 의 비율(74.0%)은 하한이에요.
- `sleep` 없이 기다리는 호출(`gh run watch <번호>`)도 번호가 있으면 `names_a_run` 이에요. 이 종류 246건 중 `sleep` 이 없는 것은 7건이에요.
- 빌드·시험 도구는 위 열한 가지만 봐요. 목록에 없는 도구를 쓰는 호출은 `rest` 에 들어가요. `rest` 가 무엇인지는 이 측정이 가리지 않아요.
- 저장소 이름은 `repos/`, `-R`, `--repo`, `github.com/` 뒤에서만 읽어요. 이름이 안 보이는 기다림 32개는 작업 디렉터리로 저장소가 정해졌을 수 있어요.
- 일정 깨움은 메시지에 실행 번호가 있는 것만 세어요. 실행을 기다리려고 만든 일정의 하한이에요.
- 같은 실행을 `sleep` 으로도 기다리고 일정으로도 깨울 수 있어서 기다림 188개와 일정 쌍 68개를 더하면 안 돼요. "둘 다 가진 Keeper"는 Keeper 단위로 겹친다는 뜻이고 같은 실행을 둘 다 썼다는 뜻이 아니에요.
- `due_in_sec` 는 일정을 만들 때 적은 값이에요. 실제로 깨운 시각이 아니에요.
- `duration_ms` 가 실행 시간인지 기다림까지 섞인 값인지는 이 측정이 가리지 않아요(`docs/reports/2026-11-05-tool-efficiency.md` §2, §8).
- 턴 시간은 trace 파일의 첫 줄과 끝 줄 시각으로 어림한 값이에요(`docs/evidence/lane-time-2026-11/README.md`). 호출 시간의 22.3%가 구간 밖이에요. 26.16시간 중 24.72시간은 trace 파일이 없는 턴의 호출이고, 1.44시간은 trace 파일이 있는 턴에 달린 `direct` 호출이에요. 구간 밖 호출은 턴 시간에 대한 비율에서 뺐고, 시간 합계에는 그대로 들어 있어요.
- 날마다 모습이 많이 달라요. 배포 전후를 비교하려면 날짜마다 따로 보고, 같은 일수로 재야 해요.
- 시험은 `python3 -m unittest discover -s docs/evidence/execute-waits-2026-11` 로 돌려요.

## 일정이 실행의 끝을 놓친 크기

`measure_schedule_slack.py` 는 Keeper 가 자기를 깨우려고 만든 일정이 메시지에 적은 GitHub Actions 실행의 끝과 얼마나 어긋나는지 재요. 일정의 깨우는 시각(due)과 실행의 끝을 견줘요. `docs/rfc/RFC-0379-keeper-monitor-event-wake.md` §6.5 의 `until_github_run` 이 줄이려는 어긋남이에요.
원장은 위 스크립트와 같은 규칙으로 읽고(`measure_execute_waits.py` 의 함수를 가져다 써요), 실행은 `gh api repos/<owner>/<name>/actions/runs/<id>` 로 GitHub 에 물어요. 그래서 물어본 날과 `gh` 로그인이 읽을 수 있는 저장소에 따라 값이 달라져요.

```bash

    --from-date 2026-11-01 --to-date 2026-11-05 --until 2026-11-05T05:00:00Z --json-out after.json
```

`result-schedule-slack-2026-11-01_11-05.json` 이 위 명령의 결과예요. 물어본 시각은 JSON 의 `probed_at`(2026-11-05T14:56Z)이에요. 일정 240건과 그중 실행 번호가 있는 81건은 위 "일정으로 깨우는 쪽" 표와 같아요. 53초쯤 걸려요.

### 센 방법

- 일정: 위 "일정 깨움"과 같아요. `masc_schedule_create` 행 중 기록된 결과가 성공이고 `input.keeper_name` 이 행의 Keeper 와 같은 것이에요. 메시지에 실행 번호가 있거나 `until_github_run` 이 있으면 잴 대상이에요.
- 깨우는 시각(due): 입력이 가진 첫 필드예요. `ts + due_in_sec`, 없으면 `due_at_unix`, 없으면 `due_at_iso`(시간대가 없으면 UTC)예요. `ts` 는 행을 쓴 시각이라 호출이 끝난 뒤예요. 셋 다 없는 일정(날마다 또는 cron 반복)은 깨우는 시각이 없어요.
- 실행: `--repos`(기본 `jeong-sik/masc`, `jeong-sik/wkbl`)를 차례로 물어서 처음 답한 저장소의 실행이에요. 실행의 끝은 `updated_at` 이에요.
- 판정은 처음 맞는 하나예요. `watched`: 입력에 `until_github_run` 이 있어요. 서버가 그 실행이 끝날 때 일정을 깨우니, 깨우는 시각은 폴백일 뿐이라 실행과 견주지 않아요. `several_runs`: 메시지에 실행 번호가 여럿이라 어느 실행을 기다리는지 글에서 알 수 없어요. `no_due_time`. `run_unreadable`: 어느 저장소도 답하지 않았어요(404, 권한 없음, 네트워크 모두 같아요). `rerun`: 시도가 둘 이상이라 `updated_at` 이 기다린 시도의 끝이 아닐 수 있어요. `not_completed`: 실행이 아직 안 끝났어요. `already_complete`: 실행이 행의 `ts` 이전에 끝났어요. `late`: 일정을 만들 때 실행이 돌고 있었고 깨우는 시각이 끝과 같거나 뒤예요. 어긋남은 깨우는 시각에서 끝을 뺀 값이에요. `early`: 깨우는 시각이 끝보다 앞이에요. 어긋남은 끝에서 깨우는 시각을 뺀 값이에요.
- 남은 시간(`remaining_min`): 실행의 끝에서 행의 `ts` 를 뺀 값이에요. 깨우는 시각까지의 시간(`due_in_min`)과 견주려고 `late`·`early` 일정만 세요.

## 감시한 일정이 깨우기까지

`measure_watched_wakes.py` 는 `until_github_run` 을 단 일정이 실행의 끝에서 Keeper 의 새 턴까지 가는 길을 단계마다 재요. `docs/rfc/RFC-0379-keeper-monitor-event-wake.md` §6.5 의 감시가 배포된 뒤에 쓰는 스크립트예요.
읽는 곳은 도구 호출 원장(일정을 만든 행), 서버 로그(`.masc/logs/system_log_YYYY-MM-DD.jsonl`, 깨움 하나에 세 줄), Keeper 의 trace 파일이에요. 실행의 끝은 위 스크립트처럼 `gh api` 로 GitHub 에 물어요. 아무것도 쓰지 않아요.

```bash
python3 docs/evidence/execute-waits-2026-11/measure_watched_wakes.py --base-path ~/me \
    --from-date 2026-11-06 --to-date 2026-11-06 --until 2026-11-06T12:40:00 --json-out after.json
```

`result-watched-wakes-2026-11-06.json` 이 위 명령의 결과예요. 물어본 시각은 JSON 의 `probed_at`(2026-11-06T12:46Z)이고 25초쯤 걸려요.
서버 로그는 날짜 파일이고 오래된 날부터 지워져요. 감시 줄은 서버가 감시를 돌리기 시작한 08:53:09Z 이후에만 있어요.

### 센 방법

- 감시한 일정: `masc_schedule_create` 행 중 기록된 결과가 성공이고, `input.keeper_name` 이 행의 Keeper 와 같고, `input.until_github_run` 에 실행 번호가 하나 든 행이에요. 원장은 창보다 하루 앞에서부터 읽어서 전날 저녁에 만든 일정도 짝을 찾아요.
- 깨움: 서버 로그의 감시 줄 `schedule_run_watch: woke <일정 번호>, <owner/name> run <번호> completed: <결과>` 예요. 감시가 시도를 가리키면 `run <번호> attempt <n>` 으로, 결과가 없으면 `completed with no conclusion` 으로, 실행을 못 읽으면 `woke <일정 번호> early, ... cannot be read: ...` 로 찍혀요. 이 둘은 결과 칸에 `no_conclusion`·`unreadable` 로 들어가요. 어느 모양과도 안 맞는 감시 줄은 깨움으로 세지 않고 `unrecognized_watcher_lines` 에 세요. 일정 번호는 호출자가 고른 글자일 수 있어서(공백과 쉼표가 없는 것) `sched-` 로 시작하는 줄만 읽지 않아요. 일정 번호마다 첫 줄만 세요. 같은 일정 번호의 러너 줄(`schedule_runner: ... dispatch=succeeded`)과 전달 줄(`scheduled wake delivered schedule_id=... (keeper=<이름>)`)은 감시 줄보다 60초 앞 이후에 찍힌 첫 줄이에요. 감시는 한 번 돌 때 읽은 실행을 모두 처리한 뒤에 줄을 찍어서 러너가 먼저 그 일정을 가져갈 수 있어요. 감시한 일정은 한 번만 도는 일정이라 러너 줄이 하나이고, 60초는 호출자가 같은 번호를 다시 썼을 때 앞 사용의 줄을 거르는 용도예요. 11-06 로그의 감시 줄 24개는 모두 러너 줄이 감시 줄보다 1~29초 뒤에 찍혔어요. 전달 줄이 없으면 러너 줄까지만 재요(`without_delivery_line`).
- 실행의 끝: GitHub 실행의 `updated_at` 이에요. 끝나지 않았거나, 실행의 마지막 시도가 감시가 가리킨 시도(가리키지 않았으면 1)가 아니거나, GitHub 이 답하지 않으면 끝을 몰라서 첫 단계가 비어요(`end_unknown`).
- 단계: 로그 시각이 초 단위라 차가 0보다 작으면 0으로 읽어요. `end_to_woke` 는 감시 줄에서 실행의 끝을 뺀 값이에요. `woke_to_dispatch` 는 러너 줄에서 감시 줄을, `dispatch_to_delivered` 는 전달 줄에서 러너 줄을, `end_to_delivered` 는 전달 줄에서 실행의 끝을 뺀 값이에요.
- 러너 줄 때 턴 안: 전달된 Keeper 의 턴 구간(`measure_lane_time.py` 와 같은 구간)이 러너 줄이 찍힌 초의 시작 순간을 덮어요. 러너는 그 순간 Keeper 에게 깨움을 넘기고, 턴 안의 Keeper 는 턴이 끝날 때 받아요. 그 초의 나머지는 안 봐요. 깨움이 시작하는 턴이 그 초 안에서 시작할 수 있어서예요. 턴 구간이 하나도 없는 Keeper 와 러너 줄이 없는 깨움은 `turn_state_unknown` 이에요. 턴 구간은 창보다 하루 앞에서부터 읽어요. trace 파일을 남기지 않는 턴(운영자가 직접 말을 거는 턴)은 구간이 아니라서, 그 안의 Keeper 는 턴 밖으로 읽히고 그 턴은 아래 "다른 턴"에도 안 세요.
- 기다린 시간(JSON 의 `parked`): 전달 줄에서 일정을 만든 행의 `ts` 를 뺀 값이에요. 짝은 전달된 Keeper 가 같은 실행 번호로, 감시 줄 이전에 만든 일정 중 다른 깨움이 아직 안 가져간 `ts` 가 가장 늦은 행이에요. 감시 줄이 이른 깨움부터 가져가므로, 한 Keeper 가 한 실행에 일정 둘을 걸면 하나씩 가져가요. 원장에 일정 번호가 없어서 취소된 일정의 행이 맞는 행 대신 짝이 될 수 있어요. 짝이 없는 깨움은 `without_create` 예요.
- 빠진 날: JSON 의 `server_log` 가 읽은 서버 로그 파일 수(`files_read`)와 창 안에서 파일이 없는 날(`days_without_file`)을 알려 줘요. 파일이 없는 날의 깨움은 말없이 빠지기 때문이에요.
- 그동안 시작한 다른 턴: 같은 Keeper 의 턴 구간 중 일정을 만든 `ts` 뒤, 전달 줄 2초 앞 전에 시작한 구간의 수예요. 깨움이 시작하는 턴은 안 세요. 턴 구간이 없는 Keeper 의 깨움은 `parked` 에서 빠져요.
- 백분위는 위와 같이 가까운 순위예요. 짝짓기는 이 보고서에서 깨움에 이름을 붙이는 용도예요. 서버가 이 값을 읽고 무언가를 정하지 않아요.

### 조심할 것
