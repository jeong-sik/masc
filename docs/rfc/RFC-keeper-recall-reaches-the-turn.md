# RFC: Keeper 가 기억을 매 턴 받게 한다

- 상태: 초안. 판정 방식(D2)은 운영자가 2026-10-28 에 "LLM 판단 Jev 판단을 적극 사용"으로 정했다. Keeper 17명의 의견은 [증거 문서](../evidence/keeper-recall-board-feedback-2026-10-28/README.md)에 있고 반영은 §2.4 에 적었다. 나머지는 §8 에 열려 있다. 진행판은 #46556 이다.
- 날짜: 한국 시간(KST). Board 와 metrics 의 시각은 UTC 이고 `Z` 를 붙인다.
- 운영자 요청 (2026-10-28): 모든 Keeper 의 기억 Recall 이 턴 대화에서 쓰여야 한다. 지금은 사실상 쓰이지 않아 Librarian 이 의미를 잃는다. Skill 처럼 기억을 찾게 하고, 위계와 트리로 연결된 기억을 따라가게 하고, 기성 제품과 논문을 보고 빠진 구현을 채우라고 했다.
- 근거: 측정은 [기준선 증거](../evidence/keeper-recall-baseline-2026-10-28/README.md), 기성 제품과 논문은 [연구 r1](../research/2026-10-28-keeper-recall-prior-art-r1.md)과 [r2](../research/2026-10-28-keeper-recall-prior-art-r2.md). 코드는 이 브랜치의 트리다(분기점 `origin/main` `68b6cd521cb`). 수치는 모두 시험용 Keeper 3명을 뺀 40명 기준이고 2026-10-28 04:01Z 에 셌다.

## 0. 요약

Keeper 의 기억 본문은 프롬프트에 없다. 모델이 `keeper_memory_search` 를 직접 불러야 나온다. 모델은 거의 부르지 않는다. 도구 호출 276,804건 중 기억 검색은 2,201건(0.80%)이고, 검색의 28.3%는 아무것도 못 찾는다. Librarian 이 하루 1,000건 넘게 기억을 커밋한 14일에, 같은 날 검색은 커밋의 1/11~1/39 였다.

이 RFC 는 호스트가 이번 턴 입력을 보고 필요한 기억을 고르게 한다. 고르는 일은 Jev(TypeSafe)가 한다. Keeper 의 현재 사실 전체를 Jev 에게 보여 주고 후보마다 `possibly_needed` 또는 `not_needed` 중 하나를 받는다. `possibly_needed` 인 후보를 요약 없이 본문 그대로 프롬프트에 넣는다. 점수, 키워드, 상위 N개는 쓰지 않는다. Jev 를 못 쓰는 턴은 "판정 못 함"이라고 알리고 Keeper 가 직접 검색한다.

in-house exact-output 레인은 이 경로에 넣지 않는다. 레인의 지연이 너무 크다(§4.8). 레인이나 다른 LLM 은 오프라인 하네스에서 Jev 의 판정을 다시 판정해 놓침을 재는 데 쓴다(§7). 레인을 실행 경로에 넣을지는 운영자 결정이다(§8-8).

먼저 만드는 것은 측정 하네스다(층 0). 이 설계가 recall 을 올리는지, Jev 가 같은 입력에 같은 답을 내는지, 큰 요청이 Jev 한도에 들어가는지는 아직 모른다. 하네스 결과 없이 제품 코드를 쓰지 않는다. 제목, 안정 id, 연결, 트리 같은 저장 계약 변경은 §5 에 방향만 적는다.

## 1. 결정

- **D1.** 기억을 모델이 찾아야만 나오는 구조를 그대로 두지 않는다. 호스트가 이번 턴에 맞는 기억을 골라 넣는다.
- **D2.** 고르는 일은 LLM 판단이다. 실행 경로의 판정자는 Jev 하나다. 후보 전체를 `possibly_needed`·`not_needed` 로 가르고 `not_needed` 만 뺀다. 확률이나 확신도 숫자로 가르지 않는다. 다른 LLM 은 오프라인에서 Jev 의 판정을 재판정하는 기준으로 쓰되 무작위 표본에만 쓴다(§5 의 3).
- **D3.** 고른 기억은 요약 없이 본문 그대로 넣는다. 블록은 둘이다. 매 턴 가는 상태 줄 블록 `Recalled_memory_status` 와, 고른 집합이 바뀔 때만 가는 본문 블록 `Recalled_memory` 다(§4.4).
- **D4.** 스위치 기본값은 꺼짐이다. 카나리 Keeper 로 먼저 켜고 측정한 뒤 넓힌다.
- **D5.** 효과는 오프라인 하네스가 잰다. 라이브 카나리는 운영 지표(지연, 바이트, 실패)와 R1~R12 를 본다.
- **D6.** 판정을 끝내지 못하면 "없음"이라고 쓰지 않는다. "판정 못 함"과 이유, 전체 몇 개 중 몇 개를 봤는지 적는다.
- **D7.** 이 RFC 는 저장 계약(제목, 안정 id, 연결, 트리)과 쓰기 도구를 바꾸지 않는다.

## 2. 무슨 일이 났나

수치는 `scripts/keeper-recall-baseline.py` 와 `scripts/keeper-recall-store.py` 로 2026-10-28 라이브 base path 에서 셌다. 10-02 이후 기록이다. 오래된 로그가 지워져서 실제보다 적게 센 값이다. 회수 이벤트(§2.2의 4)와 사실이 빠지는 경로(§2.5)는 파일 전체를 읽은 값이라 기간이 다르다.

### 2.1 기억이 거의 안 읽힌다

- 도구 호출 276,804건 중 `keeper_memory_search` 2,201건(0.80%). `keeper_memory_write` 4,790건(1.73%)이라 쓰기가 읽기의 두 배가 넘는다. 위키 읽기 도구 177건(0.06%), `keeper_workspace_memory_read` 38건(0.01%).
- 도구를 쓴 턴 100개당 검색한 턴은 `claude_code` 1.45, `codex` 5.13, `ollama_cloud` 5.01, `muse` 6.04, `glm-coding` 10.97, `antigravity` 12.91 다.
- 검색 2,198건 중 622건(28.3%)이 아무것도 못 찾았다. 없는 것을 찾았을 수도 있어서 품질의 상한선만 알려 준다.
- LLM 이 골라 주는 `keeper_memory_select` 는 Jev 전용이고 스위치가 꺼져 있으면 `unavailable` 을 돌려준다(`workspace_memory_selection_enabled` 기본값 false, `lib/runtime/runtime_schema.ml:577`). 10-02 이후 호출은 1번이다(`report.txt`).

### 2.2 왜 그런가

1. **본문이 프롬프트에 없다.** 라이브 프롬프트에 들어가는 기억 정보는 "사실 N개" 안내문(`lib/keeper/keeper_memory_os_recall.ml:115`, 약 1.1KB)뿐이다. 본문은 10-01~02 에 뺐다(#40473, #40782). 빼기 전 측정(2026-09-08, Keeper 한 명의 386턴)에서 기억 블록은 조립된 88,177B 중 51,518B 였고 캐시 생성 토큰이 314,080, 읽기가 50,788 이었다(`lib/types/prompt_block_id.mli`).
2. **개인 기억을 호스트가 고르는 길이 없다.** 선택기(`lib/keeper/keeper_memory_select.ml`)는 모델이 도구로 불러야만 돈다(`lib/keeper/keeper_tool_runtime.ml:362`). 호스트가 턴마다 고르는 `Keeper_workspace_memory_host_recall`(`lib/keeper/keeper_run_tools_hooks.ml:1061`)은 공용 기억용이다.
3. **공식 클라이언트는 같은 내용을 다시 받지 않는다.** `Prompt_block_id.resent_when_held`(`lib/types/prompt_block_id.ml:102`)가 `Memory_os_recall` 에 false 라서, 이미 보낸 바이트는 건너뛴다(`lib/keeper/keeper_official_client_context_projection.ml:351`, `:559`). 안내문은 세션을 시작할 때 한 번만 들어가고 그 뒤 턴에는 다시 오지 않는다. 같은 모델 `muse-spark-1.3` 안에서 안내문이 새로 실린 실행은 13.3% 에서 검색했고 아닌 실행은 2.3% 였다. `claude-sonnet-5-5` 는 새로 실린 56번 중 0번 검색했다. 안내문이 새로 실린 실행은 세션을 새로 시작했거나 내용이 바뀐 실행이라, 안내문 말고 다른 차이도 섞여 있다. 전달 횟수가 한 원인일 수 있지만 전부는 아니다. API 레인이 매 턴 첫 라운드에 받는다는 것은 코드를 읽어 안 것이고 잰 것은 아니다.
4. **기억의 id 가 자주 사라진다.** 기억 id 는 claim 의 SHA-256 이다(`lib/keeper/keeper_memory_os_types.ml:734`). 회수 이벤트 19,234건이 가리키는 id 의 행방은 아래와 같다. 사용 이력과 연결을 걸 끈이 지금은 없다(§5).

   | 회수 이벤트가 가리키는 id | 비율 |
   |---|---|
   | 지금도 현재 사실 | 15.5% |
   | 다시 쓰기 기록만으로 현재 사실로 이어짐 | 2.0% |
   | 흡수 기록을 거쳐 현재 사실로 이어짐 | 23.3% |
   | 기록을 따라가도 사라진 id 에서 끝남 | 21.9% |
   | 철회 | 1.8% |
   | 개정·흡수·철회 기록 없이, 커밋된 저널 행이 그 사실을 뺌 | 32.5% |
   | 어느 파일에도 없음 | 3.0% |

5. **밖에서도 같다.** OpenClaw, Hermes, Pi, Codex, Claude Code 모두 "색인과 모델의 도구 호출" 구조에서 안 당긴다는 보고가 있다. 본문까지 호스트가 넣는 곳은 OpenClaw, Hermes 외부 provider, 예전 Claude Code 뿐이다(연구 r1 §2).

### 2.3 이미 있는 것과 빠진 것

- 이미 턴에 들어간다: 월드 프레임(`Active_goals`, `Current_task`, `Scheduled_automation`, `Recent_work` 등, `lib/keeper/keeper_context_layers.mli`)과 Librarian working state(요약으로 접은 대화 구간을 여는 고정 메시지, `lib/runtime/runtime_model_input_tail_window.ml:28`). 둘 다 지금 하는 일의 문맥이다. 오래 두고 쓰는 교훈·절차·제약(현재 사실 2,338개 중 `lesson` 803개, `constraint` 466개)은 이 길로 오지 않는다. 그래서 효과는 이 길로 답할 수 없는 질문에서만 잰다(§7).
- 있다: 후보 전체를 한 요청으로 판정하는 타입 있는 선택기(`lib/keeper/keeper_workspace_memory_selection.ml` 의 `assess_batch`). 이 RFC 는 이 요청 모양을 그대로 쓰지 않는다. 질문마다 지시문 1,663B 와 선택지 설명 802B 가 붙어서 후보 55개면 질문만 약 138KB 가 된다(§4.2).
- 없다: 개인 기억에 호스트가 판정을 부르는 길. recall 효과를 재는 정답 세트와 하네스.
- 출처 결속 사실은 별도 저장소(`memory-source-current.json`)에 있고 148개, 185KB, 24명 분이다. 이 RFC 의 후보가 아니다(§4.2).
- 따로 끌 수 없는 경로가 있다. 기본 `keeper_memory_search` 는 후속 기억을 고를 때 원문을 TypeSafe 로 보낸다(`lib/keeper/keeper_memory_successor_selection.ml:79`). 레인 스위치와 제외 목록만 본다(`:82-83`). 지금까지 요청 1,623건이 20명의 Keeper 에서 `api.typesafe.ai` 로 나갔다. 회사 데이터를 다루는 `kidsnote-incoming-dd-manager` 49건과 `kidsnote-job-manager` 4건이 들어 있다(`scripts/keeper-recall-store.py`). 운영자가 Jev 를 쓰기로 했으니 문제는 반출 자체가 아니라, 이 경로만 끌 스위치가 없고 제외 목록이 한 명뿐이라는 점이다(§8-1, §8-3).

### 2.4 Keeper 의견

Board 글에 Keeper 17명이 댓글 22개로 답했다. 7명은 RFC 원문을 읽지 않았다고 밝혔다. 원문과 Keeper 별 요지는 [증거 문서](../evidence/keeper-recall-board-feedback-2026-10-28/README.md)에 있다. 댓글은 지금과 다른 설계(Jev 와 레인 두 단계)에 대한 답이다. 자발적 응답이고 LLM 에이전트의 자기 보고라서 통계가 아니라 사례다. 답을 요청한 역할 열 중 여섯(`ocaml-agent-ic`, `context-reviewer`, `masc-pro-builder`, `ocaml-refactor-woman`, `code-reviewer`, `glossary-maniac`)은 답하지 않았다. 층 1a 전에 묻는다. 요지는 다섯이다.

- 16명이 지금도 유효한 제약·절차가 알아서 실리면 도움이 된다고 했다. 15명이 낡은 값이 현재값처럼 실리는 것을 해로 꼽았다(옛 head SHA, 병합된 PR 의 판정, 지난 측정 수치).
- 14명이 "판정 못 함"과 "필요한 기억 없음"을 가르자고 했다. 5명은 "필요 없음"과 "찾았지만 없음"까지 셋으로 가르자고 했다.
- 11명이 Jev 가 놓칠 곳을 짚었다: 어휘가 다른 기억, 발동 조건형 사실, 표면이 닮지 않은 실패 교훈, 길고 조건이 많은 절차 기억, 정확한 식별자.
- 회사 데이터 Keeper 를 Jev 에서 빼는 데 10명이 찬성했다. 그중 5명은 "레인만 쓴다"를 전제로 찬성했는데, 이 RFC 는 제외한 Keeper 에 recall 을 주지 않는다. 6명은 이름 나열이 아니라 데이터 분류 속성으로 정하자고 했다.
- 쓴 기억이 검색에 안 나온다는 보고가 있다(§2.6).

| 의견 | 반영 |
|---|---|
| 낡은 값 | 항목마다 기록 시각, 출처 좌표, `Time_bound` 표시, 블록 머리의 "기록 시각 기준" 문구(§4.4). 대체·정리는 층 2(§5) |
| 세 가지 "없음" | 상태 넷과 "N개 중 M개 판정"(§4.4). 결과는 평가 기록에 `turn_ref` 로 남긴다(§4.6) |
| Jev 가 놓침 | 애매한 후보도 `possibly_needed` 로 고르게 묻는다(§4.3). 오프라인 재생에서 놓침을 잰다(§7). 식별자·발동 조건형 사실의 별도 통로는 만들지 않는다(§8-4) |
| Jev 반복 안정성 | 층 0 전제 측정(§5, §7) |
| 제외, 속성 기준 | Keeper 별 반출 정책으로 #46555 에서 정한다(§8-1). 그 전까지 recall 은 `memory_recall_scope = "listed"` 테스트 Keeper 에만 켠다(§4.7) |
| 비용, 읽기 API p99 | §4.8. 카나리 밖으로 넓히기 전 조건 |
| 월드 프레임과 겹침 | 문항 조건과 R7(§7) |
| 쓰기 도달, 결과 유실 | §2.6, 층 0 전제 측정. 쓰기 도구는 #46507 |
| 검색 결과 형식 | 이 RFC 밖. #46507 |
| 실렸지만 안 읽음, 재조회 회피, 틀린·낡은 기억 | R2~R5(§7) |
| 증거 좌표, `memory:` 인용, 판단 재료와 증거의 경계 | 블록 머리(§4.4), 열린 결정 7 |
| 예약 노트, Task 문맥 | 열린 결정 5 |
| 요약이 아닌 본문 | §4.3 |
| 질문 묶음과 지표(PO) | §7 |
| 사용 가이드 | 층 1b(§5), §9 |

받지 않은 요청이 둘이다.

- 발동 조건형 사실이 Jev 를 건너뛰는 안(3명). 규칙을 먼저 더하지 않고 `possibly_needed` 로 시작한다. 오프라인 재생에서 `constraint` 가 `not_needed` 로 가는 비율을 먼저 센다(§8-4).
- "필요 없음" 상태를 아예 보이지 않게 하는 안(3명). 줄이 없으면 기능이 꺼진 턴, 판정이 깨진 턴, 필요 없던 턴이 서로 같아 보인다. 한 줄은 남기고 짧게 쓴다.


### 2.5 싣는 기억이 낡았을 위험

현재 사실 2,338개(Keeper 40명)의 `last_seen` 은 중앙값이 7.2일 전, 상위 10%가 21.5일 전, 가장 오래된 것이 56.1일 전이다. 14일 넘게 다시 관찰되지 않은 사실이 20.7%다. `last_seen` 은 같은 claim 을 마지막으로 본 시각이라 그 사실이 지금도 맞다는 뜻이 아니다(RFC-0418). 출처로 Board 글 좌표가 있는 사실은 24.0%이고 나머지는 대화 기록에서 뽑아 좌표가 없다.

호스트가 이 사실을 매 턴 싣기 시작하면 낡은 사실이 눈에 띄는 횟수가 는다. 그래서 층 1 은 사실을 고치거나 지우지 않고 기록 시각, 출처 좌표, 시간에 묶인 값 표시를 붙인다.

낡은 사실은 지금도 Librarian 이 지운다. 10-02 이후 다른 사실로 흡수한 것이 7,178건이고, 이유를 적어 버린 것이 8,940건이다(예: 완료된 시간 한정 배정 기록). 이 RFC 는 그 판정을 바꾸지 않는다.

### 2.6 쓰기가 읽기보다 먼저 막힌다

recall 이 실어 줄 수 있는 기억은 쓰기를 통과한 것뿐이다.

- 사실의 98.8%를 Librarian 이 쓴다. 현재 사실 2,338개 중 `origin` 이 `injected` 인 것이 2,309개, `authored` 가 29개다. 10-02 이후 Librarian 시도의 39.4%가 레인 실패였다. 날짜별로 10-11 이 84%, 10-15 가 89%, 10-22 가 43% 이고 10-26 이후는 1~3% 다.
- Keeper 의 명시 쓰기 `keeper_memory_write` 는 승인 대기열에 들어간다. 영수증은 "승인이나 현재 memory id 를 확인해 주지 않는다"고, "worker 가 이미 처리했을 수 있다"고 적는다(`lib/keeper/keeper_tool_memory_runtime.ml:1743`). 승인 판정의 지시문은 반복되거나 양립하는 관찰을 기존 기억에 흡수할 수 있다고 한다(`lib/keeper/keeper_memory_admission_judgment.ml`).
- 2026-10-28 에 처음 잴 때(`scripts/keeper-recall-store.py`) Keeper 34명의 승인 대기열은 모두 비어 있었다. 그 뒤의 행방은 Librarian 영수증으로 쟀다(`scripts/keeper-recall-write-reach.py`, [증거](../evidence/keeper-recall-write-reach-2026-10-28/README.md)). 대기열에 들어간 쓰기는 Librarian 이 처리해야 현재 사실이 되고, 쓴 뒤 처리 pass 의 저널 시각까지 중앙값 7분~22분, 90퍼센타일 14.0시간~15.8시간이 걸린다(판정에 걸린 시간은 빠졌을 수 있어서 실제는 더 길 수 있다). 대기열 전체가 막힌 것은 아니다. 15:31Z 에 대기열 행이 있는 Keeper 는 40명 중 1명이고 행은 모두 7건이다. 다만 msx-retro-mania 한 곳은 마지막 Librarian commit 이 15.2시간 전이고 행 7건은 모두 그 뒤에 쓰였다. 저널은 pass 가 돌았는지 적지 않아서(판정이 전부 보류면 행이 남고 저널 행은 없다) 안 돈 것인지 보류만 한 것인지 가를 수 없고 원인은 못 봤다. Librarian 이 처리한 후보 735건 가운데 486건(66.1%)은 대상 사실에 붙었고 249건(33.9%)은 대상 없이 닫혔다. 대상이 있는 486건 중 Keeper 가 쓴 문장 그대로인 것은 12건(2.5%)이다. 대상의 지금은 이렇다. 현재 사실이 173건(35.6%), 개정·흡수 기록을 따라가면 현재 사실에 닿는 것이 184건(37.9%), 닿지 못한 것이 129건(26.5%)이다. 닿지 못한 129건 중 철회 6건을 뺀 123건은 마지막 id 를 Librarian pass 가 뺐다. 그중 90건은 같은 commit 이 다른 사실도 더했지만, 같은 종류의 id 1,204개에서는 그 비율이 80.1%라서 특별히 높지 않고 다른 문장으로 남았다는 근거도 못 된다. 이유를 적은 비율은 이 123건이 36.6%, 같은 종류가 29.5%다. 이어진 사실의 내용과 이유 문장은 읽지 않았다. 왜 대상 없이 닫는지는 영수증에 판정 이유가 없어서 모른다.
- 10-02 이후 저널이 커밋한 Keeper 의 명시 쓰기는 4,765건이다. 이 숫자는 큐가 생긴 뒤의 쓰기를 거의 담지 못한다. 커밋은 10-05 에 3,182건이고 10-13 부터는 하루 0~2건이다. 큐를 거친 쓰기는 다른 경로로 기록된다. 그 경로는 Librarian 의 `<keeper>.librarian-range-commit.json` 영수증이다. 3,110건은 한 Keeper(`sangsu`)의 한 번의 실행이었고 거의 다 사라졌다. 그 실행을 뺀 1,655건(Keeper 30명)의 행방은 이렇다. 52.2%는 다시 쓰였고, 8.1%는 다른 사실에 흡수됐고, 38.5%는 개정·철회·흡수 기록 없이 현재 집합을 떠났고, 1.1%만 쓴 그대로 남아 있다.
- `supersedes` 는 `origin` 이 `authored` 인 사실만 가리킬 수 있다(같은 영수증 문구). 사실의 98.8%가 `injected` 라서 Keeper 가 스스로 고칠 수 있는 사실이 적다.
- 이 RFC 는 쓰기 도구의 계약을 바꾸지 않는다. "승인 대기 N건" 줄도 넣지 않는다. 대기열 행은 Keeper 40명 중 1명에게만 있어서 대부분 0 이고, 쓰기 경로의 문제를 보이게만 할 뿐 고치지 않는다. 대기 중 기억이 검색에 안 보이는 문제, 결속 실패, 호출 결과 유실은 #46507 에서, `supersedes_not_authored` 거절은 #39191 에서 추적한다. #46507 에서 승인 판정이 Keeper 의 명시 쓰기를 흡수하는 단계가 헌법의 Gate 제거 기준(없어도 지속하는 진실이 유지되면 제거 대상)에 맞는지도 묻는다.
- 사실을 뺀 기록이 저널에만 있고 `memory-events` 에는 개정·흡수·철회 사건이 없는 경우가 있다. 회수 이벤트의 32.5%가 여기에 해당한다(§2.2의 4). 이것이 설계인지 빠진 것인지 모르겠다. #46547 에서 확인한다.

## 4. 설계

### 4.1 흐름

```text
턴 입력 + Keeper 지침 + 턴 참조 ─┬─> (a) 후보 판정   Jev, 후보 전체
키퍼의 현재 사실 전체 ────────────┘                 후보마다 possibly_needed / not_needed
                                  ├─> (b) 턴 질문    Jev, 후보 없이
                                  │                 이번 턴이 저장된 지식을 필요로 하는가 yes / no / unsure
                                  └─> (c) 시간 표시  Jev, (a)가 고른 후보만
                                                    Standing / Time_bound
                                       v
        selected / none_found / none_needed / unavailable(이유)   (일부만 판정하면 "N개 중 M개")
                                       v
        Recalled_memory_status (첫 라운드, 매 턴)  +  Recalled_memory (첫 라운드, 고른 집합이 바뀔 때)
```

(a)와 (b)는 동시에 보낸다. (c)는 (a) 뒤에 보내고, 실패해도 (a)의 결과는 그대로 쓴다.

### 4.2 후보와 요청

- 후보는 Keeper 의 현재 사실이다(`memory-current.json`). 미리 걸러 내지 않는다. 낱말 겹침이나 점수로 줄이는 것은 헌법의 `string_matching`·`magic_number` 에 걸린다.
- 출처 결속 사실(148개, 185KB, 24명)은 층 1 의 후보가 아니다. 별도 저장소에 있고, 읽기 전에 출처 파일을 다시 읽어 SHA 를 비교해야 하며(`keeper_memory_source_current.mli`), 항목에 category 와 last_seen 이 없다. 지금처럼 검색 도구로만 전달된다. 층 2 에서 후보에 넣는다.
- 후보 한 줄: `question_id`(memory id), `category`, `claim` 전문, `first_seen`, `last_seen`, `origin`. 날짜는 UTC 일 단위이고, 날짜로 나타낼 수 없는 시각은 `null` 로 두되 후보는 빼지 않는다. `origin` 은 종류(`authored`, `injected`)만 쓰고 trace id 는 보내지 않는다. 요약이 아니라 전문을 본다. 요약만 보고 `not_needed` 를 내면 원문에만 있는 예외를 놓친다는 지적이 있었다.
- 목적(purpose)은 이번 턴 입력, Keeper 지침, 턴 참조로 시작한다. 월드 프레임(`dynamic_context`)을 넣을지는 층 0 에서 판정 품질과 요청 크기를 같이 보고 정한다. 프레임을 넣으면 요청이 커지고 회사 데이터가 더 나간다(§8-1).
- 요청 모양을 `assess_batch` 와 다르게 한다. `state` 에는 목적과 후보만 두고, 질문마다 짧은 `instructions`(약 0.5KB)로 규칙을 적는다. `assess_batch` 는 질문마다 지시문 1,663B 와 선택지 설명 802B 를 붙여서 질문당 약 2.5KB 다. Jev 문서는 `state` 를 Jev 가 읽는 내용으로, 질문의 `instructions` 를 규칙을 적는 자리로 설명한다. 규칙을 `state` 에 두면 신뢰할 수 없는 claim 과 같은 자리에 들어간다. 이 요청 모양(질문 수십 개와 큰 `state`)은 라이브에서 보낸 적이 없다. 지금까지 Jev 로 나간 기억 판정 1,623건은 모두 질문이 하나였다.
- **한도.** Jev 문서(docs.typesafe.ai/models, 2026-10-28 확인)는 요청당 문맥을 "`state` 와 모든 질문의 합"(64k 토큰), 질문당 문맥을 "`state` 와 질문 하나의 합"(32k 토큰)이라고 정의한다. 후보가 모두 `state` 에 들어가므로 32k 토큰이 실제 한도다. 입력 한 토큰의 바이트 수는 요청마다 다르다. 이미 보낸 작은 판정 요청 1,623건에서는 중앙값 2.04바이트였고(요청의 73%가 한 Keeper 것이고 영어 질문 문구가 섞인 값이다), recall 크기 요청에서는 `won-chik` 가 2.91~2.97바이트, `goo-yang-bong` 이 3.04~3.07바이트였다([층 0 시험](../evidence/keeper-recall-jev-probe-2026-10-28/README.md)). 그래서 32k 토큰은 65KB 에서 95KB 사이다. `goo-yang-bong` 의 `state` 159.7KB 요청은 HTTP 400 으로 거절됐고, 반으로 나눈 `state` 77.9KB 와 82.1KB 요청은 받아들여졌다. 받아들여진 가장 큰 요청은 입력이 32,980토큰이라서 32k 는 질문을 모두 합친 입력에 거는 한도가 아니다. 요청에 실리는 후보 줄을 Keeper 별로 합치면 중앙값 73KB, 상위 10% 159KB, 최대 197KB 다(후보가 있는 Keeper 42명, 2026-10-28 04:18Z). 상한을 65KB 로 보면 23명이, 95KB 로 보면 15명이 후보를 한 요청에 못 보낸다. Jev 에는 한도를 262k 토큰으로 올리는 긴 문맥 헤더(`TypeSafe-Danger-Zone-Long-Context: true`)가 있고 토큰당 값은 같지만, 문서가 "느리고 정확도가 낮다"고 적어서 쓰지 않는다(docs.typesafe.ai/models, 2026-10-28 확인).
- **보내기 전에 나눈다.** 한 조각의 후보를 일정 크기 이하로 자르고(상수 `STATE_BYTES_PER_PIECE`) 조각을 동시에 보낸다. 후보 줄의 바이트(압축 JSON 의 UTF-8 길이)를 앞에서부터 더하다가 한도를 넘으면 새 조각을 연다. 혼자 한도를 넘는 후보는 조각 하나를 혼자 차지한다. 1KB 는 1000바이트이고 프로브와 같다. 조각 크기는 후보 줄만 센다. 질문마다 붙는 지시문과 키는 세지 않는다. 요청당 문맥 한도는 `state` 와 모든 질문의 합이라서, 후보 줄이 짧아 후보가 많은 Keeper 는 이 한도에 먼저 닿을 수 있다. 거절되면 반으로 나누므로 요청 수가 늘어난다. 나누는 방식이 고르는 양을 바꿀 수 있어서(아래) 결과가 같다고 보지는 않는다. 얼마나 자주 그런지는 층 1c 에서 `capacity` 거절 수로 잰다. 초깃값은 80KB 로 둔다. 시험에서 받아들여진 가장 큰 `state`(82.1KB)보다 작은 값이다. 80KB 로 나누면 후보가 있는 Keeper 42명 중 1조각이 24명, 2조각이 13명, 3조각이 5명이고 평균 1.55조각이다. 60KB 로 나누면 평균 1.88조각이다(`scripts/keeper-recall-jev-probe.py` 의 나누기로 센 값, 2026-10-28 04:18Z). 이 조각 수는 프로브의 무게로 센 값이다. 프로브는 질문 키가 12자이고 JSON 에 공백이 있다. 코덱의 후보 줄은 id 가 71자이고 JSON 에 공백이 없다. id 가 59바이트 길고 공백이 11바이트 적어서 후보마다 48바이트 더 무겁다(claim 이 `a` 하나일 때 프로브 144바이트, 코덱 192바이트). 같은 후보를 코덱의 줄로 나누면 조각이 더 늘 수 있다. 실제 조각 수는 층 1c 에서 잰다. 입력 토큰당 3.0바이트이면 80KB 는 약 27k 토큰이라 32k 한도에 여유가 있다. 2.5바이트 이하인 Keeper 는 80KB 에서 한도에 닿는다. 그런 Keeper 가 있는지 모른다(층 0 의 1). 코덱 모양의 합성 요청은 입력 토큰당 2.56바이트였다. 이 값이면 80KB 는 약 31k 토큰이라 32k 한도에 가깝다. 합성 문장이라 실제 claim 과 다를 수 있다. 조각 크기는 용량만이 아니라 고르는 양도 바꾼다. 같은 후보를 한 조각으로 보낼 때와 두 조각으로 나눠 보낼 때 고르는 양이 달랐다는 측정이 있다([증거](../evidence/keeper-recall-jev-probe-2026-10-28/README.md)). 어느 쪽이 맞는지는 층 0 의 3과 6이 정답을 줄 때까지 모른다. 나눈 뒤에도 거절되면 반으로 나눈다(§4.6).

### 4.3 판정

- **(a) 후보 판정.** 후보마다 질문 하나. 답은 `possibly_needed` 와 `not_needed` 다. 이번 턴이 이 기억을 쓸 수 있거나 쓸지 애매하면 `possibly_needed`, 확실히 관련 없을 때만 `not_needed` 를 고르게 묻는다. 이번 입력과 쓰는 말이 다른 기억이 있다. 조건이 맞을 때만 쓰는 규칙이나 실패에서 얻은 교훈이 그렇다. Jev 가 이런 기억을 확신하지 못해도 `possibly_needed` 로 남는다. `possibly_needed` 를 고른 것으로 본다. 개수 상한은 두지 않는다. 숫자 바닥값이 아니라 모델이 스스로 고르는 닫힌 선택이다. 선택 기준 문장은 뜻을 적은 말이고 목표 개수에 맞춰 고치지 않는다. 선택 여부만 묻는 이유는 측정에 있다(아래 측정).
- **(b) 턴 질문.** 이번 턴이 저장된 지식(교훈, 절차, 제약, 이전 결정)을 필요로 하는가. 답은 `yes`, `no`, `unsure` 다. 고른 기억이 없을 때 "필요 없음"과 "찾았지만 없음"을 가른다. 후보 요청과 따로, 후보 없이 보낸다. 후보 요청이 나뉘어도 한 번만 묻는다.
- **(c) 시간 표시.** 고른 후보만 보내서 시간에 묶인 값(수치, SHA, head, 판정, 진행 상태)을 담았는지 `Standing` 과 `Time_bound` 중 하나로 받는다. 요청의 `state` 에는 고른 후보만 있고 이번 턴 입력은 없다. 시간에 묶였는지는 기억 내용만으로 가른다. 이 표시도 모델의 판단이고 낱말 일치로 정하지 않는다. 요청이 실패하면 `Unjudged` 로 싣고, 항목에 "시간 표시를 판정하지 못했다. 값은 기록 시각 기준이다"를 붙인다. 표시가 없는 항목이 `Standing` 처럼 보이면 안 된다.
- 개인 사실에는 공용 기억 선택기의 역할 구분(`current_decision`, `comparison`, `inspect_source`)을 쓰지 않는다. 개인 사실의 75.9%는 출처 좌표가 없어서 `inspect_source` 에 답할 근거가 없고, 선택지 설명이 질문마다 붙어 요청이 커진다. 역할 구분이 필요한지는 층 0 에서 본다.
- **Jev 로 가는 것.** 이번 턴 입력, Keeper 지침, 턴 참조, 후보의 id·category·claim 전문·시각·origin. (c) 요청에는 고른 후보만 가고 이번 턴 입력, Keeper 지침, 턴 참조는 가지 않는다. 회사 데이터를 다루는 Keeper 는 §8-1 에서 정한다.
- **모델 버전.** `[typesafeai] model` 에 버전 id 를 적는다(`Custom of string`을 이미 받는다). 별칭 `jev-latest` 는 새 릴리스로 옮겨 가서 코드를 안 바꿔도 답이 바뀐다고 문서가 적는다. Jev 1.14 가 2026-10-14 에 나왔다. 지금 라이브 설정에는 `model` 줄이 없어 기본값 `jev-latest` 다(`lib/runtime/runtime_schema.ml:551`). `jev-latest` 로 요청하면 응답의 `model` 필드에 실제 버전이 온다. 2026-10-28 의 첫 시험에서 `jev-1.14.0` 이었다. 안정성을 잰 버전(지금은 `jev-1.14.0`)을 카나리에도 쓴다.
- **확신도는 기록하고 선택에는 쓰지 않는다.** Jev 응답의 확률과 확신도는 평가 기록에 남긴다. 응답 해석(`decode_choice`)도 확신도를 수락 임계값으로 쓰지 않는다고 적는다(`lib/typesafeai/typesafeai_types.mli`). 기록이 쌓인 뒤 바닥값이 필요한지 §7 에서 다시 본다.
- **측정.** `won-chik` 한 Keeper, 합성 목적 하나, 후보 56개를 한 요청으로 10번 보낸 결과다. 라벨이 바뀐 후보는 3개(5.4%)이고 선택 집합이 같은 쌍은 45쌍 중 12쌍(26.7%)이다. 평균 선택 확률이 0.5 를 넘는 후보 23개는 21개가 매번, 2개가 때로 선택되고 빠진 후보가 없다. 남은 흔들림은 선택 확률이 0.5±0.05 인 후보 3~4개에서 나온다. 질문 모양과 상관없는 바닥이다. 한 번에 선택되는 수는 평균 22.9개이고 claim 으로 약 26KB(`won-chik` claim 합 66.5KB의 40%)다. 이 양이 필요한 기억인지는 정답이 없어서 모른다. 양과 효율은 정한 뒤에 잰다(§4.8, §5 의 6). 질문 모양을 비교한 기록은 [증거](../evidence/keeper-recall-jev-probe-2026-10-28/README.md)에 있다.
- **라벨과 확률이 어긋난 답.** Jev 클라이언트의 해석(`decode_choice`)은 라벨이 가장 높은 확률의 선택지가 아니면 그 답을 받아들이지 않는다. 그 후보는 판정하지 못한 것(`invalid_answer`)으로 센다. 두 선택지 시험에서 라벨이 바뀐 후보의 칸 중 1등이 분명한 29칸을 확인했고 어긋난 칸은 없었다. 그 밖의 칸은 확인하지 않았다. 세 선택지 시험에서는 같은 기준의 183칸 중 2칸이 어긋났다. 카나리에서 `invalid_answer` 건수를 센다.
- **(b)와 (c)의 문구.** 질문 문구는 (a)만 층 0 에서 쟀다. (b)와 (c)는 Jev 로 아직 시험하지 않았고 층 1a-2 의 평가 기록으로 처음 본다.
- **`not_needed` 는 그 턴에 최종이다.** 다른 모델이 다시 보지 않는다. 비슷한 질문의 참고 수치가 있다. Board attention 에서 Jev 의 "관련 없음" 답 36,807건을 LLM 레인이 다시 판정해 1,304건(3.5%)을 뒤집었다(2026-09-23~30, `lib/runtime/runtime_schema.ml` 의 주석). 확신도 0.3 미만 답은 7.3%였는데 뒤집힌 것의 41%가 거기서 나왔다. 질문이 다르므로 예측이 아니라 참고 수치다. 같은 비율이면 `not_needed` 로 간 후보의 약 3.5%를 재판정 모델이 다시 고른다. 재판정 모델이 맞는지는 정답 세트로 따로 본다. 오프라인 재생이 이 값을 우리 질문에서 잰다(§7).
- 판정 타입(`candidate_decision`, `turn_need`, `time_nature`, `unjudged_reason`)은 TypeSafe 타입에 기대지 않는 모듈에 둔다. 오프라인 하네스의 재판정 모델이 같은 타입으로 답한다.

### 4.4 싣기

블록이 둘이다. 하나는 매 턴 가는 짧은 상태 줄이고 하나는 고른 기억의 본문이다. 본문을 매 턴 다시 보내면 공식 클라이언트 세션이 턴마다 그만큼 커진다(§3). 본문은 고른 집합이 바뀔 때만 보낸다. 고른 집합이 턴마다 바뀌면 이 절약은 없다. 같은 입력을 10번 판정했을 때도 집합이 같은 경우는 45쌍 중 12쌍이었다(`won-chik` 한 Keeper, §5 의 2). 입력이 같아도 선택 확률이 0.5 근처인 후보 몇 개가 매번 들락거리기 때문이다. 연속한 두 턴에서 집합이 같은 비율은 층 0 의 재생에서 잰다. 이때 판정이 흔들려서 생기는 변화를 따로 뺀다(§5 의 7).

| 블록 | 내용 | `injected_on_post_tool_round` | `resent_when_held` | `cache_rank` |
|---|---|---|---|---|
| `Recalled_memory_status` | 상태 한 줄과 선택한 id 목록 | false | true | `Dynamic_context` 와 `Temporal_summary` 사이 |
| `Recalled_memory` | 고른 기억 본문 | false | false | `Dynamic_context` 앞 |

순위는 두 블록의 내용 변화 빈도를 층 1c 에서 잰 뒤 확정한다(`cache_rank` 문서의 방식). 상태 줄 블록은 `Admitted_scheduled_input` 처럼 세션을 이어 갈 때마다 간다. 본문 블록은 세션이 같은 바이트를 이미 가졌으면 건너뛴다.

상태 줄은 아래 넷 중 하나다. 줄마다 `turn_ref` 가 있다. 세션 기록에 여러 턴의 줄이 쌓여도 어느 턴의 판정인지 알 수 있어야 한다.

- `selected`: "후보 N개 중 K개 선택" 과 선택한 id 목록. 본문은 `Recalled_memory` 블록이거나 이 세션이 앞서 받은 같은 블록에 있다.
- `none_found`: 판정했고 고른 기억이 없는데 턴 질문의 답이 `yes` 또는 `unsure` 다. "후보 N개를 판정했고 이번 턴에 맞는 기억을 찾지 못함." 뒤에 턴 질문의 답을 적는다. `yes` 이면 "저장된 지식이 필요해 보인다는 답이었다.", `unsure` 이면 "저장된 지식이 필요한지는 가리지 못했다는 답이었다." 다음에 "정확한 낱말(PR 번호, run id 등)은 `keeper_memory_search` 로 찾을 수 있다."를 붙인다. 상태는 yes 와 unsure 를 가르지 않으므로 싣는 층(1b)이 턴 질문의 답을 상태와 함께 받는다.
- `none_needed`: 판정했고 고른 기억이 없는데 턴 질문의 답이 `no` 다. "후보 N개를 판정했고 이번 턴은 저장된 지식이 필요 없다는 답이었다. 정확한 낱말은 `keeper_memory_search` 로 찾을 수 있다."
- `unavailable(이유)`: 판정하지 못했다. 이유는 `capacity`, `rate_limited`, `provider_failed`, `invalid_answer`, `not_recorded`, `turn_question` 중 하나다. "기억이 없다는 뜻이 아니다. `keeper_memory_search` 로 직접 찾을 수 있다"를 적는다. 다른 세 상태보다 눈에 띄는 문구를 쓴다.

판정된 후보가 0개(M=0)이면 `none_*` 가 아니라 `unavailable` 이고, 이유는 후보 순서로 첫 번째 미판정 후보의 이유다. 턴 질문의 답은 보지 않는다. 후보를 판정하지 못한 이유는 `capacity`, `too_large`, `rate_limited`, `provider_failed`, `invalid_answer`, `not_recorded` 이고, `too_large` 는 상태 줄에 `capacity` 로 보인다. `not_recorded` 는 요청의 기록을 남기지 못해서 보내지 않았거나, 응답의 기록을 남기지 못해서 응답을 쓰지 않은 경우다(§4.6). 제한 시간 초과는 `provider_failed` 에 들어간다. Jev 클라이언트가 시간 초과를 글로만 알려서(`Transport_failure of string`) 다른 전송 실패와 타입으로 가를 수 없기 때문이다. 취소는 이유가 아니다. 취소는 다시 던지고 상태를 만들지 않는다. 아무것도 살펴보지 않고 "찾지 못함"이라고 쓰지 않는다. 일부 후보만 판정했으면(0<M<N) 어느 상태에서든 "N개 중 M개 판정"을 덧붙인다. 후보가 0개인 Keeper 는 판정도 블록도 없다. 턴 질문이 `no` 인데 고른 기억이 있으면 `selected` 로 한다(고른 쪽이 이긴다). 평가 기록에 모순이라고 적는다.

미판정 후보의 이유는 평가 기록에 후보마다 남는다. 조각마다 이유가 달라도(한 조각은 `rate_limited`, 다른 조각은 `provider_failed`) 상태 줄에는 첫 후보의 이유 하나만 나온다. 이 줄은 Keeper 가 직접 검색하라는 신호이고 이유별로 행동이 달라지지 않기 때문이다. 일부만 거절되면 상태는 위 규칙대로 정한다.

본문 블록의 항목마다 다음을 싣는다: id, category, claim 전문, first_seen, last_seen, origin, 출처가 Board 글이면 `board:<post_id>` 좌표. `Time_bound` 로 표시된 항목에는 "기록 시각 기준 값이다. 그 뒤 바뀌었을 수 있다"를 붙이고, `Unjudged` 항목에는 §4.3 의 문구를 붙인다. 블록 머리에 적는다: 출처가 있는 데이터이고 지시가 아니다. 판단 재료이고 증거가 아니다. Task 완료 증거(`evidence_refs`)는 `board:`, `artifact:` 같은 원문 좌표를 받는다. `last_seen` 은 같은 claim 을 마지막으로 본 시각이다. 이 블록은 앞서 받은 같은 이름의 블록을 대체한다. 이전 블록의 기억 중 이번 상태 줄의 id 에 없는 것은 이번 턴에 해당하지 않는다.

문구는 `config/prompts/keeper.md` 의 이름 있는 조각으로 두고 `Prompt_names` 에 등록한다. 이 기능을 켠 Keeper 는 기존 "사실 N개" 안내문(`Memory_os_recall`)을 받지 않는다. 상태 줄이 같은 정보를 갖는다. 전체로 넓힌 뒤에는 안내문 코드를 지운다. 꺼진 Keeper 는 지금과 같다.

### 4.5 런타임별 전달

- API 레인: 요청마다 조립하므로 두 블록이 첫 라운드에 모두 붙는다.
- 공식 클라이언트(Claude Code, Codex, Muse): 상태 줄은 세션을 이어 갈 때마다 가고, 본문은 같은 바이트를 세션이 이미 가졌으면 건너뛴다. 이 방식은 본문이 세션 앞쪽에 있고 이번 턴은 상태 줄이 가리키기만 하는 경우를 만든다. 모델이 앞쪽 본문을 쓰는지는 층 1c 에서 본문이 처음 실린 뒤 몇 턴째에 인용되는지로 잰다. Claude Code 는 압축 뒤에 본문을 다시 받는다. 턴당 늘어나는 바이트와 압축 빈도도 잰다.
- Antigravity: 가진 목록을 항상 비워서 두 블록이 매번 전부 간다.
- 블록 때문에 Keeper 자신의 요청이 용량 거절을 받을 수 있다. 재시도 경로가 있는 런타임(Agent Core, Codex, Claude Code)은 본문 블록 전체를 빼고 다시 만든다. 일부만 남기지 않는다. 그러면 순위가 되기 때문이다. 뺀 항목의 id 는 상태 줄에 남기고 "본문 N개 생략(요청 용량)"을 적는다. Muse·Antigravity 에는 이 재시도 경로가 없다고 설정 주석이 적는다(`config/runtime.toml` 의 `workspace_memory_selection_enabled` 주석). 이 둘에서는 거절이 나면 그 턴이 실패한다. 층 1c 에서 블록 바이트 분포와 거절 수를 본다.

### 4.6 실패와 기록

- 입력과 응답을 호출 전후에 키퍼별 `memory-recall-evaluations.jsonl` 에 남긴다. `started`, `response_received`, `provider_failed`, `cancelled` 모양은 `memory-selection-evaluations.jsonl` 과 같다. 확률, 확신도, 토큰 사용량, `turn_ref`, 결과 상태와 이유를 적는다. 줄마다 어느 질문의 요청인지(`kind`: `candidates`, `turn`, `time`)도 적는다. 헌법의 `persist_before_model_call` 이다. 요청을 보내기 전에 입력을 남기지 못하면 요청을 보내지 않고, 응답을 받은 뒤에 응답을 남기지 못하면 그 응답을 쓰지 않는다. 두 경우 모두 그 요청의 후보는 판정하지 못한 것(`not_recorded`)으로 센다. 판정이 끝나면 마지막 줄(`judgment_completed`)에 상태와 범위, 이유, 고른 id, 턴 질문의 답, 후보별 결과와 시간 표시를 적는다. 이 줄을 남기지 못하면 그 판정은 쓰지 않고 모든 후보를 `not_recorded` 로 센다. 이 파일이 재생 세트가 된다. 요청 전문을 남기면 Keeper 당 하루 약 13MB 다(하루 claim 387MB 를 29명으로 나눈 값). 다른 Keeper 로그와 같은 한도(10MB, `MASC_KEEPER_METRICS_MAX_BYTES`)에서 회전한다. 회전은 판정마다 첫 줄을 쓰기 전에 한 번만 확인해서 한 판정의 줄이 두 파일로 나뉘지 않는다. 회전을 못 하면(예: 이전 파일 자리가 디렉터리) 그 판정의 요청은 보내지 않고 `not_recorded` 로 센다. 이전 파일은 `MASC_KEEPER_METRICS_MAX_ROTATED`(기본 1)개를 두므로 하루 남짓의 줄이 남는다. 층 0 의 재생 세트는 카나리 기간 것을 따로 복사해 둔다. 보존 기간은 정하지 않았고 위 개수만 있다.
- 턴 기록(`decisions.jsonl` 의 `turn`, `Turn_record`)에는 새 필드를 더하지 않는다. `Turn_record.blocks` 가 블록이 실렸는지를 바이트·digest 와 함께 이미 남긴다(`turn_record.mli`). 평가 기록이 결과와 이유를 갖는다. 둘을 `turn_ref` 로 이어 "기억 없이 판단한 턴"을 센다.
- 후보 요청이 용량 거절을 받으면 줄 바이트의 절반을 한도로 후보를 다시 잘라 보낸다. 잘라 나온 조각은 앞쪽부터 차례로 보낸다. 후보 하나짜리 요청이 거절을 받으면 (b)의 결과로 원인을 가른다. (b)가 받아들여졌으면 목적은 한도 안이고 그 claim 이 너무 큰 것이다. 그 후보만 판정하지 못한 것(`too_large`)으로 세고 나머지를 계속 판정한다. (b)도 용량 거절이면 목적이 한도를 넘은 것이라 거기서 멈추고 `unavailable(capacity)` 로 한다. 멈춘 뒤에는 요청을 더 보내지 않고, 아직 보내지 않은 후보도 `capacity` 로 센다. (b)가 받아들여졌다는 것은 서버가 요청을 받았다는 뜻이라, 응답을 읽지 못해도(`invalid_answer`) 목적은 한도 안이다. (b)가 용량 거절이 아닌 이유(429, 제공자 실패)로 실패했으면 목적이 한도 안인지 알 수 없어서 그 후보는 `capacity` 로 세고 나머지를 계속 판정한다. 잘라 나온 조각도 같은 규칙을 따른다. 조각이 용량 거절을 받으면 다시 자르고, 후보 하나가 되면 위 규칙으로 멈춘다. 자르는 기준은 후보 수가 아니라 줄 바이트다. 조각의 줄 바이트 절반을 한도로 다시 자르므로(`split`) 큰 후보 하나가 섞인 조각에서는 그 후보가 바로 혼자 남는다. 그래서 나뉜 조각이 셋 이상일 수 있다. 후보가 N개이면 (a) 요청은 최악에 2N−1회다. 거절이 없으면 처음에 나눈 조각 수와 같다.
- Jev 가 일부 후보의 답을 빠뜨리면 그 후보는 판정하지 못한 것으로 센다.
- 턴 질문의 답이 없거나 잘못되면 `unsure` 로 대신하지 않는다. 고른 기억이 있으면 `selected` 이고, 판정된 후보가 있는데 고른 것이 없으면 `unavailable(turn_question)` 이다. 판정된 후보가 0개이면 위에서 정한 대로 첫 미판정 후보의 이유가 앞선다.
- 429, 제공자 실패(제한 시간 초과 포함)로 어떤 조각이 실패하면 그 조각의 후보는 판정하지 못한 것으로 세고 나머지 조각의 결과를 쓴다. 요청이 간 destination 이 모두 429 로 답하면 이유는 `rate_limited` 이고, 다른 실패가 하나라도 섞이면 `provider_failed` 다. 클라이언트가 용량 거절을 모든 destination 이 같은 400 을 줄 때만 용량으로 세는 방식과 같다. 취소되면 상태를 만들지 않고 취소를 다시 던진다. 평가 기록에는 `cancelled` 행만 남긴다. 판정된 후보가 0개면 `unavailable(이유)` 다.
- `unavailable` 이 아닌 판정은 Keeper 와 `turn_ref` 를 키로 그 턴이 끝날 때까지 다시 쓴다. 같은 턴의 다음 호출은 입력과 후보가 달라도 그 판정을 돌려주고 Jev 를 부르지 않는다. failover 로 컨텍스트를 다시 만들어도 마찬가지고, 지표에도 다시 세지 않는다. 일부 후보를 판정하지 못한 판정도 쓴다. 상태 줄이 "M개 중 N개 판정"으로 범위를 알린다. `unavailable` 판정은 쓰지 않아서 같은 턴의 재시도가 처음부터 다시 판정한다. 한 Keeper 에 판정 하나만 두므로 다음 판정이 앞의 것을 바꾼다. 턴 사이에는 재사용하지 않는다. 같은 입력이 반복돼도 사실이 바뀌었을 수 있다.
- **시간.** 판정은 첫 모델 요청 전에 끝나야 해서 턴 시작을 늦춘다. (a)의 조각들과 (b)는 동시에 보내고 (c)는 그 뒤에 보낸다. (c)는 (a)에서 받아들여진 요청마다 하나씩 보내고 그 요청이 고른 후보만 싣는다. 반으로 나누지 않고, 실패하면 그 후보들은 `Unjudged` 다. 요청마다 Jev 클라이언트의 요청별 제한(기본 10초)을 쓰고 새로 만들지 않는다. 이 제한은 destination 마다 따로 걸려서(`typesafeai_client.mli` 의 `timeout_sec`), 실패한 요청이 다음 destination 으로 넘어가면 거기서 다시 최대 10초를 쓴다. 제한 안에 못 끝나면 `provider_failed` 다. 그래서 거절 없이 끝나는 경우 판정 단계는 최악에 한 요청의 최악 시간의 두 배다((a)(b) 구간과 (c) 구간). destination 이 하나이면 약 20초이고 둘이면 약 40초다. 라이브 destination 수는 확인하지 못했다. 거절 뒤 나누기가 붙으면 그만큼 더 걸린다. 큰 요청이 10초 안에 끝나는지는 층 0 에서 잰다. 이 단계가 길어지는 Keeper 는 카나리에서 지연 분포를 보고 넓힐지 정한다.
- 지표(모두 Keeper label 이 붙는다): 판정마다 `masc_keeper_memory_recall_total{outcome}`(selected, none_found, none_needed, unavailable), 고른 후보 수 `masc_keeper_memory_recall_selected_total`, 판정 시간 `masc_keeper_memory_recall_judgment_seconds`. 요청마다 `masc_keeper_memory_recall_requests_total{kind,result}`, 저장한 요청 줄의 바이트 `masc_keeper_memory_recall_input_bytes_total`, 요청 시간 `masc_keeper_memory_recall_request_seconds{kind}`. 입력 바이트는 `started` 줄의 크기라서 전송 본문보다 식별 필드만큼 크다. 블록 바이트는 층 1b 에서 더한다.

### 4.7 스위치

- `[typesafeai]` 에 `memory_recall = false` 를 더한다. 데이터를 TypeSafe 로 보내는 기능마다 스위치를 따로 두는 기존 방식이다(`absorb_gate`, `skill_applicability`, `workspace_memory_selection_enabled`). 스위치를 켜면 범위도 같은 표에 쓴다. `memory_recall_scope = "all"` 이거나 `memory_recall_scope = "listed"` 와 비어 있지 않은 `memory_recall_keepers = [...]` 다. 켜는데 범위가 없거나, `"listed"` 인데 이름이 없거나, `"all"` 옆에 목록을 두면 설정을 읽을 때 거절한다. 목록이 비어 있다고 전원이 켜지는 일은 없다. 스위치와 범위는 하나의 값(`Runtime_schema.memory_recall`)이라 "켰는데 범위 없음"을 만들 수 없다. 모르는 이름은 부팅 때 알린다(제외 목록 검사와 같다). `[typesafeai]` 의 키는 설정 레지스트리(`keeper_runtime_setting_registry`)에 올리지 않는다.
- 새 이유(`Memory_recall_disabled`)는 `unavailable_reason` 을 `match` 하는 곳마다 짝을 맞춘다: `typesafeai_config`, `keeper_board_attention_exact_flow`, `keeper_librarian_absorb_gate`. `absorb_gate` 쪽 디코더는 문자열이라 컴파일러가 못 잡는다.
- Keeper 별 모드는 `Typesafeai_config.memory_recall_destinations` 의 답이다. `Error` 면 `Off`, `Ok` 면 판정한다. 스위치가 꺼져 있거나 범위 밖이면 `memory_recall_disabled`, `[typesafeai] excluded_keepers` 에 있으면 `keeper_excluded`, 레인이 꺼졌거나 키가 없으면 그 이유로 `Off` 다. 범위 밖인 Keeper 가 제외 목록에도 있으면 앞의 이유가 나온다. `Off` Keeper 는 판정도 상태 줄도 없고 기존 안내문을 그대로 받는다.
- 라이브 설정은 이 RFC 의 PR 이 바꾸지 않는다. 카나리를 켤 때 운영자가 정한다.

### 4.8 비용과 지연

판정은 턴마다 한다. 호출 수는 (a) 조각 수(80KB 기준 평균 1.55개, 1~3개), (b) 1회, (c) 고른 후보가 있는 (a) 요청마다 1회다. 조각마다 고른 후보가 있으면 턴당 평균 최대 약 4.1회다(1.55 + 1 + 1.55). 고른 후보가 없는 조각은 (c)를 보내지 않아서 실제 평균은 이보다 낮다. 거절 뒤 나누기가 붙으면 더 는다.

| 날짜(UTC) | 턴 | 턴을 낸 Keeper | 턴당 claim 평균 |
|---|---|---|---|
| 10-24 | 1,501 | 32 | 101KB |
| 10-26 | 4,253 | 30 | 96KB |
| 10-27 | 3,793 | 29 | 102KB |

claim 바이트는 그날 턴을 낸 Keeper 의 현재 사실 바이트를 턴 수만큼 더했다. 과거 날의 실제 사실 수와 다를 수 있다.

- 어제(10-27) 기준 하루 3,793턴이고 Keeper 당 약 131턴이라 호출은 하루 최대 약 15,600회다(3,793 × 4.1). 300명이 되고 Keeper 당 턴 수와 사실 수가 같으면 하루 약 39,200턴, 최대 약 161,000회(평균 초당 1.9회)이고 claim 만 약 4.0GB 다.
- 비용은 입력만 든다. (c) 요청의 입력도 빠져 있다. (c)는 고른 후보만 싣지만(`won-chik` 에서 claim 의 약 40%) 같은 후보 조각이면 본문이 (a)보다 후보당 약 143~146바이트 길다. 코덱이 만든 요청을 직렬화해 후보 10개와 100개, claim 60바이트와 300바이트에서 쟀다(2026-10-29, 스크래치 하네스). 입력 토큰으로는 재지 못했다.
- 지연: 이미 보낸 기억 판정은 `state` 중앙값 7.6KB(최대 43.0KB)에서 중앙값 0.24초, 상위 10% 0.48초, 최대 14.51초였고 1,623건 중 6건이 실패했다. recall 크기 요청은 Keeper 둘로 재 봤다. `won-chik` 는 본문 81.4KB(입력 27k 토큰)가 0.34~0.52초, 23.1KB(8k 토큰)가 0.24~0.31초에 끝났고, 두 조각을 동시에 보낸 전체가 0.34~0.53초였다. `goo-yang-bong` 은 본문 96.6KB(입력 32k 토큰)가 0.35초, 101.4KB(33k 토큰)가 0.52초에 끝났고, 거절된 197.7KB 요청은 0.28초 만에 돌아왔다. `won-chik` 를 한 요청(104.1KB, 입력 35k 토큰)으로 10번씩 두 번 보내면 0.39~0.64초, 두 조각으로 10번 보내면 회차마다 0.38~0.97초였다. 호출당 제한 시간 기본값 10초에 비해 여유가 크다. 다른 Keeper 와 여러 Keeper 가 동시에 보낼 때는 모른다. 질문당 한도에 얼마나 가까웠는지는 재지 못했다. 조직별 요청 한도를 넘으면 429 가 오는데 한도 값은 확인하지 못했다. 문서는 토큰과 요청을 초당으로 센다고만 적는다.
- Keeper 쪽 프롬프트: 본문 블록의 크기는 고른 수가 정한다. `won-chik`(claim 합 66.5KB)에서 한 번에 고르는 claim 은 10번 평균으로 약 26KB(40%)였다. 이 양은 Jev 비용이 아니라 각 Keeper 요청의 입력으로 간다. 개수 상한은 두지 않는다(§4.3). 용량을 넘을 때는 §4.4 가 줄인다. 효율은 정한 뒤에 잰다. 고른 기억 중 Keeper 가 답에 인용한 몫과 프롬프트에 들어간 바이트를 카나리에서 함께 낸다(§5 의 6). 이 둘은 LLM 호출 비용이 없다.
- in-house 레인은 실행 경로에 넣을 수 없다. `board_attention_exact` 는 입력 2KB 에 걸린 시간이 중앙값 169.0초, 상위 10% 379.0초다. 입력이 이렇게 작으니 대부분 허가 대기다. `librarian_exact` 는 입력 중앙값 33KB 에 중앙값 10.8초, 상위 10% 32.1초, 상위 1% 368.4초다. 첫 요청을 보내기 전에 레인이 끝나야 하는데, 레인은 밀리면 줄을 서서 기다리고 실패로 치지 않아서 레인이 느리면 턴이 시작하지 못한다. `Priority` 대기열은 `admission-priority-run-limit` 을 선언한 계정에서만 순서를 바꾸는데(`lib/runtime/standalone_lane.mli`) 라이브 `runtime.toml` 에는 이 선언이 없다. 새 레인의 슬롯은 운영자가 정하는데, 지금 레인들은 `glm-coding`, `ollama_cloud`, `claude_code` CLI 슬롯을 쓴다.
- 사실 파일 읽기는 지금도 턴마다 IO 풀에서 한다(`Memory_os_recall` 렌더, `keeper_run_tools_hooks.ml:1108`). 판정은 그 렌더가 읽은 사실 목록을 다시 쓰고 파일을 한 번 더 읽지 않는다.
- [RFC-0474](RFC-0474-gc-stop-budget.md)는 2026-10-27 의 `Pool.request: timeout` 을 GC 정지에서 찾았고, 큰 문자열이 major heap 에 쌓이면 모든 domain 이 기다린다고 적는다. 판정 입력은 턴당 수십~수백 KB 의 문자열이라 원본을 다시 검증할 때보다 작을 것으로 보지만 아직 측정하지 않았다. 카나리 전후로 그 RFC §8 의 계기를 같이 본다.
- 카나리 밖으로 넓히기 전 조건: 카나리에서 판정 지연의 p50·p99, 호출 수, 429 와 읽기 API p99(Goal `goal-read-api-p99-300-keepers-20261027`)를 전후로 재고, 300명 환산 값을 이 절에 덧붙인다. 이 값이 없으면 넓히지 않는다.

## 5. 단계

한 층에 PR 하나(층 1a 는 둘), 층마다 20k 토큰 이하다.

**층 0 — 측정 하네스와 전제 측정.** 제품 코드를 바꾸지 않는다. `scripts/` 와 시험 디렉터리에 둔다. 실제 Keeper 기억을 밖으로 보내는 측정(1, 3)은 운영자가 이름으로 허용한 Keeper 에만 한다. 허용 목록은 recall 의 `memory_recall_scope = "listed"` 와 같다. `scripts/keeper-recall-jev-probe.py` 는 `--allow-send-for` 로 Keeper 이름을 받고 `excluded_keepers` 에 있는 Keeper 는 거절한다.

1. Jev 용량: 중앙값 크기와 상위 10% 크기 Keeper 로 조각 크기(`STATE_BYTES_PER_PIECE`)를 맞춘다. 한 조각이 받아들여지는 가장 큰 크기, 조각을 동시에 보냈을 때 걸리는 시간이 제한 시간 안인지, 한도를 넘은 요청이 돌려주는 오류 본문을 기록한다. 시험은 둘 했고 결과는 [증거](../evidence/keeper-recall-jev-probe-2026-10-28/README.md)에 있다. `won-chik`(claim 66KB, 중앙값 크기)은 조각 둘이 모두 받아들여졌고 0.5초 안에 끝났다. `goo-yang-bong`(claim 149KB, 상위 10% 크기)은 `state` 159.7KB 요청이 HTTP 400 으로 거절됐고(프로브는 `max_tokens_exceeded` 일 때만 반으로 나누므로 용량 거절이다) 반쪽 둘(`state` 77.9KB, 82.1KB)은 받아들여졌다. 코덱이 만드는 요청 모양은 합성 후보로 따로 시험했다([증거](../evidence/keeper-recall-jev-shape-2026-10-28/README.md)). 71자 `sha256:` 질문 키로 질문 120개를 한 요청에 실은 요청(본문 100.5KB)은 HTTP 200 이었고 입력이 39,334토큰이었다. 질문 300개 요청(본문 250.8KB)은 HTTP 400 이었고 `detail` 이 `{"error_type": "max_tokens_exceeded"}` 였다. 클라이언트가 용량 거절로 인정하는 모양이다. 150개씩 나눈 두 요청은 둘 다 HTTP 200 이었다. 후보 120개 요청의 입력 토큰당 바이트는 12자 키가 2.91, 71자 키가 2.56 이다. 아직 못 본 것은 입력 토큰당 2.5바이트 이하인 Keeper 에서 80KB 조각이 거절되는지, 여러 Keeper 가 동시에 보낼 때다. 문서는 오류 이름을 적지 않고 클라이언트는 400 `max_tokens_exceeded` 만 용량 거절로 인정한다.

- 1a-1 부품: 닫힌 판정 타입(`candidate_decision`, `turn_need`, `time_nature`, 판정 못 한 이유 `unjudged_reason`), 후보 한 줄 만들기, `STATE_BYTES_PER_PIECE` 로 조각 나누기, Jev 요청·응답 코덱(§4.2, §4.3), 결과를 상태 줄 넷으로 줄이는 규칙(§4.4). 순수 함수이고 시험이 같이 간다.

**층 1b — 싣기.** 새 블록 id 둘과 그 id 를 쓰는 자리 전부, 블록 렌더와 문구, 공식 클라이언트 전달(§4.5), 컨텍스트 조립 연결을 더한다. 블록 id 를 쓰는 OCaml 자리는 `prompt_block_id.ml` 의 타입, `equal`, `to_string`, `of_string`, `all_known`, `cache_rank`, `injected_on_post_tool_round`, `resent_when_held` 와 `.mli`, 컨텍스트 조립, 다음 요청 예보, 제출 연결, 공식 클라이언트 전달, TUI 인스펙터다. 컴파일러 밖 자리는 대시보드 `dashboard-turn-records.ts` 의 블록 id 목록과 `memory-inspector.ts`, 손으로 쓴 시험 표 셋이고 같은 PR 에 넣는다. `cache_rank` 는 `Temporal_summary` 와 `Operator_note` 를 뒤로 밀어야 한다. 대시보드 화면에서 새 블록이 보이는지 확인한다. 운영자가 켜는 기능이라 사용 가이드 1장이 같은 PR 에 들어간다.

층 1a 와 1b 는 한 스택으로 올리고 스택을 통째로 병합한다. 블록 id 는 렌더하는 코드와 같은 층에 넣는다. `lib/types/prompt_block_id.mli` 가 생산자 없는 생성자를 일부러 뺀다고 적기 때문이다. 층 1a 의 호출 흐름을 부르는 곳은 시험과 층 1b 뿐이라서 1a 만 따로 병합하지 않는다.

**층 1c — 카나리.** 런타임이 다른 Keeper 셋(공식 클라이언트 둘 이상, API 하나 이상)에서 켠다. 회사 데이터 Keeper 와 PO 는 뺀다. §7 의 운영 지표를 잰다.

**층 1d — 레인(선택).** §8-8 의 결정이 나면 `Standalone_lane` 에 `Memory_recall` 을 더한다. 레인 변형은 약 16개 파일(`Exact_lane_run_registry.lane` 이 따로 닫힌 타입이다)에 걸친다.

**층 2 — 이름, 제목, 연결.** 층 0 과 1c 의 결과를 본 뒤에 정한다. 방향만 적는다.

- **안정 id.** 처음 넣을 때 정한 `fact_id` 가 다시 써도, 다른 사실에 흡수돼도 이어진다. 지금의 `memory_id`(claim 해시)는 내용 확인용으로 남긴다. 이력과 연결을 걸 끈이 먼저 있어야 "어떤 쓰기가 실제로 재사용됐는가"를 재고, 그 값으로 정리 기준을 세울 수 있다. 지금은 회수 이벤트의 84.5%가 가리키는 id 가 현재 사실이 아니다(§2.2의 4).
- **출처 좌표.** 대화 기록에서 뽑은 사실(75.9%)에는 좌표가 없다. 뽑을 때 turn 참조를 같이 남기면 `evidence_refs` 로 인용할 수 있다. `memory:<fact_id>` 종류는 안정 id 가 생긴 뒤에 더하고, basis 좌표를 같이 적게 하고 basis 없는 인용은 거절한다. Task 완료 증거 스키마를 바꾸므로 이 RFC 밖이다(§8-7).
- **타입 있는 참조.** 사실에 task id, PR 번호, 예약 id, 파일 경로를 타입 있는 값으로 같이 쓴다. 턴 참조와 같은 값이면 글자 찾기가 아니라 타입 일치라서 후보를 판정 없이 올릴 수 있다. 정확한 식별자를 키로 쓰는 Keeper 에게 필요하다.
- **제목과 "언제 꺼낼지".** 쓸 때 같이 쓴다. 판정 후보가 짧아지고 `Standing`/`Time_bound` 표시도 쓸 때 한 번 적으면 된다. 지금 `title` 은 도구 인자로 받아 claim 앞에 `**title**` 로 접힌다(`lib/keeper/keeper_tool_memory_validation.ml:466`).
- **타입 있는 연결.** 근거(`Derived`), 교체(`Supersedes`), 흡수(`Absorbs`), 관련(`Related`, 이유 포함)을 닫힌 합타입으로 둔다. 점수는 두지 않는다. 지금 `Derived` 는 현재 사실 2,335개 중 1개다.
- **이웃 따라가기.** 판정이 고른 사실의 이웃을 후보로 다시 판정에 올리고, 모델도 `id` 로 이웃을 열 수 있게 한다. 링크를 따라가는 쪽이 링크 없는 전체 목록보다 낫다는 비교 연구가 없다. 하네스의 대조군으로 직접 잰다.
- 저장 계약이 바뀐다. 백업을 확인한 뒤 hard cut 한다. 운영자 승인이 필요하다(§8-2).

**층 3 — 정리.** 전제가 사라진 `RFC-memory-os-recall-selection`(61KB, 구현 0)과 `RFC-0247` §2(연상·수면 통합·TTL, 코드 없음)를 지운다. 기본 검색 안의 후속 판정에 스위치를 달고 기본값을 정한다(§8-3). 전체로 넓힌 뒤 `Memory_os_recall` 안내문 코드를 지운다.

## 7. 검증

단위 테스트는 렌더 전의 타입 값과 보낸 요청만 본다. 문구는 보지 않는다.

- `Off` 이면 판정 호출도 블록도 없다. 후보가 0개여도 호출도 블록도 없다.
- 판정 요청의 후보 id 집합과 상태 블록의 사실 목록이 같은 사실 목록에서 나온다.
- (선택 집합, 턴 질문, 판정 개수)에서 상태가 정해진다. 고른 것이 있으면 `selected`, 없고 턴 질문이 `no` 면 `none_needed`, `yes`·`unsure` 면 `none_found`, 턴 질문이 `no` 인데 고른 것이 있으면 `selected`와 모순 표시, 턴 질문의 답이 없으면 `unavailable`.
- 판정된 후보가 0개(M=0)이면 `none_*` 가 아니라 `unavailable` 이고 이유는 첫 미판정 후보의 이유다. 0<M<N 이면 상태에 "N개 중 M개"가 붙는다.
- 용량 거절: 후보 하나짜리 요청이 거절됐을 때 (b)가 받아들여졌으면 그 후보만 `too_large` 로 세고 계속하며, (b)도 거절됐으면 멈추고 `unavailable(capacity)` 다. 요청 수는 2N−1 이하다. 보내기 전 나누기는 같은 입력에서 같은 조각을 만든다.
- 본문 블록이 Keeper 요청 용량을 넘으면 본문 블록 전체를 뺀다. 일부만 빼지 않는다. 뺀 개수가 상태 줄에 있다.
- 429, 제공자 실패(제한 시간 초과 포함), 잘못된 답이 서로 다른 이유의 `unavailable` 이 된다. 취소는 상태를 만들지 않는다. 빈 상태가 되지 않는다. 일부 조각만 실패하면 나머지 조각의 결과를 쓴다.
- 제외 목록 Keeper 와 `[typesafeai] memory_recall` 이 꺼진 설정에서는 Jev 요청이 없고 모드가 `Off` 다.
- `Time_bound` 로 표시된 항목의 타입 값이 `Time_bound` 이고, (c)가 실패한 항목은 `Unjudged` 다.
- 항목마다 first_seen, last_seen, origin, 출처 좌표 필드가 채워진다. `Unjudged` 항목은 `Standing` 으로 렌더되지 않는다.
- Claude Code·Codex·Muse 에서 세션을 이어 갈 때 `Recalled_memory_status` 는 항상 가고 `Recalled_memory` 는 같은 바이트면 건너뛴다. Antigravity 는 둘 다 다시 간다. 후속 라운드에는 실리지 않는다.
- 입력과 응답이 호출 전후에 기록되고 평가 기록과 `Turn_record.blocks` 가 `turn_ref` 로 이어진다.
- 성공한 판정이 같은 턴의 failover 에서 다시 쓰인다.
- 대시보드 디코더(TypeScript 시험)가 새 블록 id 를 받는다.

효과는 층 0 의 오프라인 하네스가 잰다. 질문 묶음과 정답은 PO(masc-productor-owner)가 고정한다.

- **팔.** (A) 기억 안내 없음, (B) 지금(안내문만), (B′) 안내문을 매 턴 보냄(본문 없음), (C1) 이 RFC(Jev 가 고른 본문), (C2) 재판정 모델이 고른 본문, (D) 사실 전체, (E) 판정 없이 id 와 첫 줄만 담은 색인을 항상 넣음. (E)는 Jev 호출도 외부 전송도 없다. "Skill 처럼"을 요청한 쪽의 기준이고, (C1)의 이득을 Jev 의 판정으로 돌릴 수 있는지 가른다(연구 r1 §3.1: 항상 보이는 8KB 색인이 호출형 Skill 보다 낫다는 벤더 평가 1건). 팔마다 새 세션에서, 같은 Keeper 에 같은 문장으로, 세 번 반복하고 순서는 무작위로 한다. 하네스는 허용한 Keeper 의 사실을 고정한 읽기 전용 복제본으로 돌려서 측정 중 Librarian 이 사실을 바꾸지 않게 한다. 세 번 반복의 흩어짐(반복 분산)도 함께 기록한다.
- **질문 묶음은 Keeper 마다 따로 만든다.** 그 Keeper 의 현재 사실에서 나이와 category 가 고르게 되도록 사실을 골라, 그 사실이 있어야 답할 수 있는 질문을 만든다. 정답이 구성상 보장된다. 같은 수의 대조군 질문은 기억이 필요 없다. 기억이 필요한 질문은 월드 프레임과 Librarian working state 로 답할 수 없어야 한다. 다음 종류를 각각 넣는다: 어휘가 다른 질문, 발동 조건형 사실, 실패 교훈, 정확한 식별자, 낡은 수치 함정(기억 속 수치와 새 측정값이 다를 때 다시 재는지). 모든 지표를 턴 종류(사용자 채팅 턴, 자율 턴)별로 나눠 낸다.
- **먼저 정하는 판정 규칙(측정 전에 못박는다).** 런타임마다 (C1)의 세 번 평균이 (B)의 세 번 중 가장 높은 값보다 높고, (C1)의 대조군 점수와 도구 호출 정확도가 (B)의 가장 낮은 값보다 낮지 않으면 그 런타임에서 효과가 있다고 본다. 모든 카나리 런타임에서 그렇고 아래 전제를 운영자가 통과로 선언하면 효과가 있다고 본다. 하나라도 아니면 층 2 를 시작하지 않고 설계를 다시 본다. 전제는 둘이다. (1) Jev 용량: 중앙값 크기 Keeper 의 후보 조각이 받아들여지고 제한 시간 안에 끝난다. (2) 반복 일치: 측정한 label-flip 비율을 운영자에게 보고하고 운영자가 통과를 선언한다. 숫자 합격선은 두지 않는다. 점수 차이의 크기에도 합격선을 두지 않고 측정값을 그대로 보고한다.
- **채점.** 정답지와 답을 PO 와 두 번째 채점 모델이 따로 매기고, 갈린 문항과 무작위 표본을 운영자가 읽는다. PO 는 LLM Keeper 라서 채점 모델만으로 점수를 확정하지 않는다. PO 는 카나리 Keeper 가 아니어야 한다. 채점은 "실렸고 읽었다 / 실렸지만 안 읽었다 / 안 실렸다"를 나눈다. 실렸는지는 평가 기록으로, 읽었는지는 답이 그 기억을 인용했는지로 본다.
- **Jev 가 놓치는 정도.** 정답 세트에서 필요한 후보를 `not_needed` 로 보낸 수와, 재판정 모델과 Jev 가 갈리는 후보 목록(PO 가 읽는다)을 센다. 참고 수치는 Board attention 의 3.5%(§4.3)다.
- **확신도 기록으로 바닥값이 필요한지** 본다. Jev 의 확신도 분포와 Jev·재판정 모델의 불일치가 겹치는 구간이 있을 때만 측정으로 정한 값을 RFC 로 따로 제안한다.
- **제외한 Keeper 의 대조.** 제외한 Keeper 가 recall 없이 일해서 잃는 점수를 보자는 의견이 있었다. 그 Keeper 의 사실로 질문을 만들면 사실이 질문 작성자에게 나가므로, #46555 가 정해진 뒤에 한다.
- 한계: Keeper 와 문항이 적고 회차당 한 번이라 통계가 아니라 사례다. 하네스는 깊은 세션에서 본문이 앞쪽에 묻히는 효과를 못 본다. 그 효과는 카나리에서 잰다.

라이브 카나리(층 1c)는 운영 지표를 본다: 판정 호출 수, 입력 바이트, 지연, 429, 상태 비율, 블록 바이트와 세션 증가, 압축 빈도, 거절 수. 거기에 PO 의 지표를 더한다. PO 의 원칙 셋이 같이 왔다. 자기 채점을 하지 않는다. "모름"을 0 으로 뭉치지 않는다. 대리 지표(기억이 턴에 들어갔는가)를 최종 지표(같은 실수를 덜 반복하는가)라고 부르지 않는다.

| R1 | 이 턴 입력에 상태 줄 블록이 있었나 | 스위치가 꺼진 턴은 분모에서 뺀다 |
| R2 | 실린 기억 중 그 턴에 인용·사용된 수와 근거 좌표 | 실렸는데 안 읽음을 직접 잰다 |
| R3 | 안 실렸으면 했을 재조회가 줄었나 | 유일한 긍정 지표 |
| R4 | 낡은 판정이나 대체된 기억을 인용해 낸 판정 사고 | 0 |
| R5 | 기억 속 수치·SHA·상태를 다시 재지 않고 전제로 깐 턴 | 0 |
| R6 | "판정 못 함"을 "없음"으로 처리한 턴 | 0 |
| R7 | 실린 기억과 World State·인계문이 겹치는 비율 | 낮을수록 좋다 |
| R8 | recall 켠 턴과 끈 턴의 같은 종류 작업 품질 | 블라인드 쌍비교 |
| R9 | 300명 환산 판정 호출 수와 p99 지연 | §4.8 의 넓히기 전 조건 |
| R10 | Jev 가 "안 고른" 수와 "못 고른" 수 | 둘을 따로 센다 |
| R11 | 쓰기가 읽기의 두 배인 비율의 추이 | recall 뒤에도 그대로인지 |
| R12 | 그 주에 Keeper 의 retract·supersede 횟수, Librarian 이 버리거나 흡수한 사실 수 | 정리 주체를 따로 센다 |

`evidence_refs` 에 인용된 기억의 수는 R2 와 따로 센다. 인용이 0 이면 기억은 판단에만 쓰였고, 증거를 낼 때 Keeper 가 원문을 다시 읽었다는 뜻이다. 같은 claim 을 다시 쓰는 비율(`explicit_write`)은 id 가 claim 해시라서 고쳐 쓴 경우를 놓치므로 안정 id(§5) 전에는 신호로 쓰지 않는다.

## 8. 운영자 결정

- 결정됨 (2026-10-28): 판정은 LLM 판단과 Jev 판단을 적극 쓴다(D2).
- **1 — Jev 로 가는 범위.** 이미 나가는 경로부터 정해야 한다.
  - 확인된 경로는 기본 검색의 후속 판정이다. 요청 1,623건이 20명의 Keeper 에서 나갔고 `kidsnote-incoming-dd-manager` 49건과 `kidsnote-job-manager` 4건이 들어 있다.
  - 켜져 있는데 전송 기록을 못 찾은 경로가 둘이다. 라이브 `[typesafeai]` 에서 `absorb_gate = true`, `librarian_preflight = true` 이고, 설정 주석은 absorb gate 가 기억을 밖으로 보낸다고 적는다(`runtime_schema.ml`).
  - 제외 목록은 `kidsnote-slack-context-collector` 하나이고, `board_attention`·`absorb_gate`·후속 판정이 같은 목록을 읽는다.
  - 이 RFC 의 recall 은 새로 하나가 더 늘어나는 경로이고 양이 다르다. 지금까지 나간 기억 판정 1,623건은 `state` 중앙값이 7.6KB 였다. recall 은 하루 3,793턴에 턴마다 Keeper 의 사실 전체(평균 약 100KB)와 이번 턴 입력을 보낸다(§4.8).
  - in-house 레인도 "레인이면 안전"이 아니다. 라이브 슬롯이 `glm-coding`, `ollama_cloud`, `claude_code` CLI 라서 외부 클라우드로 간다. Keeper 별 레인 설정은 허용된 슬롯의 순서만 바꿀 수 있어서(`keeper_exact_lane_preference.mli`) 제외 Keeper 를 자기 슬롯으로만 보내려면 새 계약이 필요하다.
  - 운영자 결정(2026-10-28): 이름 몇 개를 목록에 넣는 것보다 넓은 제외 기능이 있어야 한다. Keeper 별 반출 정책으로 #46555 에서 별도 RFC 로 정한다. 그 전까지 recall 은 `memory_recall_scope = "listed"` 로 명시한 테스트 Keeper 에만 켠다. kidsnote 4종(`kidsnote-incoming-dd-manager`, `kidsnote-job-manager`, `kidsnote-qa-hub-manager`, `kidsnote-slack-reader`)은 명시하지 않는다.
- **2 — 층 2 의 hard cut.** 안정 id·제목·출처 좌표·연결은 저장 계약을 바꿔서 백업 후 기억을 다시 쓴다. 운영자가 하기로 했다(2026-10-28). 실행은 백업을 만든 뒤 한 번 더 확인받는다.
- **3 — 기본 검색 안의 후속 판정.** 기능별 스위치를 달고 기본값을 정한다(§2.3).
- **4 — `constraint` 사실이 Jev 를 거치지 않고 항상 고른 것으로 올라가게 할지.** 20%(466개)가 `constraint` 라서 블록이 그만큼 커지고 category 로 가르는 규칙이 하나 생긴다. 제안은 하지 않는 것이다. 오프라인 재생에서 Jev 가 `constraint` 를 `not_needed` 로 보내는 비율을 먼저 센다.
- **5 — recall 범위.** 이 RFC 는 Memory OS 의 개인 사실만 다룬다. 예약 노트와 연결 Task 문맥을 넣을지. 월드 프레임에 `Scheduled_automation` 층이 있어서 어디까지 이미 들어가는지 먼저 확인해야 한다. 확인하지 않았다.
- **6 — MASC Goal·Task.** 만들면 모든 Keeper 프롬프트의 `active_goals` 에 들어간다. 만들기 전에 묻는다.
- **7 — `evidence_refs` 에 `memory:` 종류를 열지.** 지금은 `artifact`, `note`, `board`, `fusion`, `task` 다섯뿐이다(`config/tools/keeper_task_done.toml:8`). 열면 basis 좌표를 같이 적게 하고 basis 없는 인용은 거절하자는 의견이 있다. 안정 id 가 생긴 뒤에 정한다.
- **8 — in-house 레인을 실행 경로에 넣을지.** 지금 제안은 넣지 않는 것이다. 근거는 레인 지연의 실측(§4.8)이다. 넣는다면 선택지는 셋이다. (가) 전용 슬롯을 만들고 그 슬롯의 지연 분포를 잰 뒤 Jev 를 쓸 수 없는 Keeper 의 대체로 둔다. (나) 비동기로 돌려 평가 기록에만 남긴다. (다) Jev 와 직렬 또는 나란히 둔다. 결정에 필요한 값은 전용 슬롯에서의 p50·p99 지연이다. 레인 변형이 약 16개 파일이라 층 1d 가 된다.
- **9 — (a) 후보 판정의 질문 모양.** 선택 여부만 묻는 두 선택지(`possibly_needed`, `not_needed`)로 한다. 운영자가 정했다(2026-10-28). 기준은 판정이 휴리스틱(숫자 기준, 점수)에 기대지 않는 것이다. 한 번에 선택되는 양과 그 효율은 정한 뒤에 잰다(§4.8, §5 의 6). 선택 기준 문장은 뜻을 적은 말이고 목표 개수에 맞춰 고치지 않는다.

## 10. 확신도

- 문제(§2.1, §2.2의 1~4): 높음. 라이브 로그와 코드를 직접 읽고 셌다.
- "전달 횟수가 한 원인이다"(§2.2의 3): 중간 이하. 같은 모델 안의 비교는 Muse 에서만 뚜렷하고 Claude Code 는 0/56 다.
- "호스트 판정이 recall 을 올린다": 모름. 호스트가 고르는 방식과 모델이 도구로 당기는 방식을 맞붙여 잰 자료를 못 찾았다(연구 r2 §1). 우리 Keeper 에서도 아직 안 쟀다. 층 0 이 그 측정이다. 벤더 글(LambdaDB)은 참고만 한다(연구 r2 §3.7).
- "Jev 가 필요한 후보를 놓치지 않는다": 모름. 비슷한 질문(Board attention)의 참고 수치는 3.5%이고 우리 질문과 크기가 다르다.
- "질문당 한도에 `state` 가 들어간다": 높음. 문서에서 읽었고, 입력 33k 토큰 요청이 받아들여진 것과 어긋나지 않는다. 보내기 전에 나누는 크기(80KB)는 중간이다. 바이트당 토큰이 작은 요청에서 2.04, recall 크기 요청 두 Keeper 에서 2.9~3.1 이었다. 2.5 이하인 Keeper 는 못 봤다.
- "큰 요청이 제한 시간 10초 안에 끝난다": Keeper 둘에서 확인(입력 27k~33k 토큰이 0.5초 안). 다른 Keeper 와 동시 부하에서는 모른다.
- 출처 결속 사실을 후보에서 뺀 것(§4.2): 높음. 읽기 전 출처 재검증이 필요하다는 저장소 계약을 코드에서 읽었다.
- "Jev 가 같은 입력에 같은 답을 낸다": 가장자리에서는 아니다. 한 Keeper, 합성 목적, 10회에서 56개 중 3개(5.4%)의 라벨이 바뀌었고 나머지는 10번 모두 같았다. 같은 입력의 선택 집합이 같은 쌍은 45쌍 중 12쌍이었다. 선택 확률이 0.5 근처인 후보 3~4개는 어떤 질문 모양에서도 흔들린다. 벤더는 예/아니오 작업에서 500개 중 498개가 5번 반복에 일치했다고 적었다. Jev 문서에는 재현성 설명이 없다. 같은 구성을 되풀이한 편차와 다른 Keeper 가 남았다.
- "두 선택지가 고르는 양이 맞다": 모름. 한 번에 평균 22.9개(`won-chik` claim 의 40%)를 고른다. 필요한 기억인지는 정답이 없어서 모르고, 정한 뒤 인용률과 팔 점수로 잰다(§5 의 3, 6).
- "낡은 값이 가장 큰 위험이다": 높음. Keeper 15명이 따로 같은 위험을 짚었고 현재 사실의 20.7%가 14일 넘게 다시 관찰되지 않았다. `Time_bound` 표시가 오독을 줄이는지는 모른다.
- "연결을 따라가는 탐색이 낫다": 낮음. 제품과 논문 어디에도 비교가 없다.
- 레인 지연: 실측은 높음(`board_attention_exact`, `librarian_exact`). 새 레인도 같은 만큼 걸린다는 것은 중간이다. 프롬프트와 대기열이 다를 수 있다.
- Keeper 의 명시 쓰기가 쓴 문장 그대로 남는 일은 드물다(§2.6): 높음. 대상이 있는 후보 486건 중 12건(2.5%)이고, 스크립트를 쓰기 전에 따로 센 값과 같다.
- 쓰기의 절반가량이 현재 사실에 닿는다(§2.6): 중간. 처리된 후보 735건 중 357건(48.6%)의 대상이 현재 사실이거나 기록을 따라가면 현재 사실에 닿는다. 닿지 못한 123건(철회 제외) 중 90건은 같은 commit 이 다른 사실도 더했지만 같은 종류의 id 에서도 그 비율이 80.1%라서 다른 문장으로 남았는지는 알 수 없다. 이어진 사실이 같은 내용인지 읽지 않았고, 대상 없이 닫은 249건이 남겼어야 할 기억이었는지는 정답이 없다.
- 쓰기가 줄어드는 원인(§2.6): 모름. 대기열 전체가 막힌 것은 아니지만 행 7건이 모두 msx-retro-mania 한 곳에 있고 그 Keeper 의 마지막 Librarian commit 은 15.2시간 전이다. 쓴 뒤 처리까지는 중앙값 7분~22분, 90퍼센타일 14.0시간~15.8시간이 걸린다. 대상 없이 닫는 이유는 영수증에 없고, 대상이 사라진 이유는 123건 중 45건만 저널에 적혀 있다.
- 쓰기 호출 표(§5 의 4): 높음. 그러나 남은 raw trace 만 센 값이다. 후보 735건 중 호출이 trace 에 있는 것은 214건(29.1%)이다.
- 턴 질문이 "필요 없음"과 "찾았지만 없음"을 제대로 가르는가: 모름. 틀리면 상태 줄이 잘못 알린다. 상태 줄에 정확한 낱말은 직접 검색으로 찾을 수 있다고 적지만, 직접 검색은 지금 도구 호출의 0.80% 라서 복구 길은 약하다.
- 하네스를 어떻게 돌릴지: 모름. 실제 Keeper 런타임을 새 세션으로 불러 팔마다 다른 프롬프트를 넣는 길이 있는지 확인하지 않았다. 없으면 도구를 흉내 낸 약식 하네스가 되고, 그 한계를 결과와 함께 적는다.
- Keeper 의견(§2.4): 17명의 자발적 답이고 7명은 원문을 읽지 않았다. 통계가 아니라 사례다.
