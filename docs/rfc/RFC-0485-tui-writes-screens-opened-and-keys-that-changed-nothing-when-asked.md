# RFC-0485 — 열어 본 화면과 화면이 그대로였던 키를 남긴다

## 0. 요약

- TUI 의 화면과 키가 맞는지는 지금 사람이 tmux 로 하나씩 눌러 보고 확인한다. 11-05(KST)에 목록 화면 8곳의 푸터가 `Left / Esc:back` 을 안내했는데 `Left` 는 아무 일도 하지 않았다(#48341 에 6곳, #48344 에 2곳). 화면마다 `Left` 와 `Esc` 를 눌러 보고 제목 줄을 비교해서 찾았다.
- 운영자가 실제로 어느 화면을 여는지는 어디에도 남지 않는다. 한 번도 안 열리는 화면이 있는지는 코드를 읽어서만 판단했다.
- 이 RFC 는 환경 변수 `MASC_TUI_NAV_TRACE=<파일>` 을 켰을 때만 JSON 한 줄씩 덧붙이는 기록을 제안한다. 사건은 둘이다.
  - 화면이 바뀐 때.
  - 키를 누른 뒤 처음 그린 프레임이 앞 프레임과 같았던 때(`Unchanged`).
- 입력한 글자, 붙여넣기, 마우스 위치, 서버가 준 내용은 기록하지 않는다. 기록은 그 프로세스가 쓰는 파일 하나에만 간다.

## 1. 지금

### 1.1 비슷한 것이 이미 있다

| 환경 변수 | 남기는 것 | 꺼져 있을 때 |
| --- | --- | --- |
| `MASC_TUI_FRAME_TIMING` | 프레임 시간 분포. 표본마다 그린 화면(`surface_key`)을 태그로 달 수 있다. 프레임은 단계마다 앞 512개, 단계 기록은 4096개까지 | 시계를 읽지 않고 표본을 남기지 않는다 |
| `MASC_TUI_ALLOC_PROFILE` | 할당 표본 | 아무것도 하지 않는다 |

둘 다 작업 공간이 아니라 프로세스 한 번의 실행에 속하는 성질이라 `runtime.toml` 키가 아니다. 이 RFC 도 같은 자리를 쓴다.

### 1.2 코드에서 확인한 자리

- 입력은 `Masc_tui_input_decoder` 한 곳에서 나뉜다. 이벤트는 `Key of string`, `Paste`, `Mouse_*`, `Reply` 다(`bin/masc_tui_input_decoder.mli`).
- 화면에 낸 결과는 `Frame_presenter.present_result` 로 돌아온다. `Presented repaint` 거나 `Unchanged`(쓴 바이트 없음)다. 프레임에는 `surface_key` 가 있고, 프레임 시간 기록이 이미 이 값을 태그로 쓴다(`bin/masc_tui.ml` 의 `Masc_tui_frame_timing.time_tagged ... ~tag`).
- 푸터가 안내하는 키는 `Masc_tui_keys.footer_hints` 가 키 표에서 만든다.
- 화면을 바꾸는 길은 여러 갈래다. `goto_surface` 를 부르는 곳이 있고, `state.view <-` 로 직접 바꾸는 곳이 `bin/masc_tui.ml` 에 35곳 있다(`rg "state.view <-" bin/masc_tui.ml`).

### 1.3 없는 것

- 어느 화면이 몇 번 열렸는지.
- 키를 누른 뒤 화면이 그대로였던 때, 그 키를 푸터가 안내하고 있었는지.

## 2. 제안

### 2.1 사건 (JSON Lines)

```json
{"t":1762300000.120,"kind":"surface","from":"keepers","to":"changes"}
{"t":1762300004.310,"kind":"key_unchanged","surface":"changes","key":"Left","advertised":true}
```

- `surface`: 어떤 프레임의 `surface_key` 가 앞 프레임과 다를 때 한 줄이다. 화면을 여는 길이 여럿이어도 프레임 한 곳에서 잡혀서, 이동 함수마다 호출을 달다가 빠뜨릴 일이 없다.
- `key_unchanged`: `Key k` 를 처리한 뒤 처음 그린 프레임이 `Unchanged` 일 때 한 줄이다. `advertised` 는 그 프레임의 푸터 힌트에 `k` 가 있었는지다.

`Unchanged` 는 "키가 아무 일도 안 했다"가 아니라 "키 직후 프레임이 같았다"는 뜻이다. 요청을 보내고 답이 나중에 오는 키(다시 읽기)도 이렇게 찍힌다. 읽는 쪽이 `advertised=true` 인 줄만 보고, 요청을 보내는 키는 거른다.

### 2.2 키 이름은 푸터가 안내한 것만 적는다

- 이름이 있는 키(`Left`, `Esc`, `Enter`, `Tab`, 화살표, `PgUp`)는 이름을 적는다.
- 글자 키는 현재 푸터가 안내하는 글자일 때만 적는다. 그 밖의 글자는 `"key":"char"` 로만 적는다.
- 작성창, 검색, 팔레트에 친 글자는 푸터가 안내하지 않는 글자라서 이 규칙으로는 값이 남지 않는다. 구현 층에서 이 말이 맞는지, 입력을 받는 모든 곳을 한 번 점검한다.
- 붙여넣기, 마우스, 터미널 응답은 사건을 만들지 않는다.

### 2.3 한도와 꺼짐

- 환경 변수가 없으면 시계를 읽지 않고 파일을 열지 않는다.
- 한 번의 실행에 적는 줄 수에 한도를 둔다. 한도에 닿으면 세어 둔 값만 마지막 줄에 적는다.
- 파일은 덧붙여 쓴다. 열 수 없으면 기록을 끈다(`MASC_TUI_ALLOC_PROFILE` 의 보고가 열 수 없는 파일에서 조용한 것과 같다).
- 이 파일은 작업 공간 저장소(`.masc/`)가 아니라서 `docs/JSONL-CONTRACT-INVENTORY.md` 에 올리지 않는다.

## 3. 하지 않는 것

- 서버로 보내지 않는다. 다른 파일에 모으지 않는다.
- 기록을 근거로 화면이나 키의 동작을 바꾸지 않는다. 읽는 것은 사람과 스크립트다.
- `runtime.toml` 키나 새 상태를 만들지 않는다.
- 머문 시간, 키 사이 간격은 이번에 적지 않는다.

## 4. 층

1. 순수 함수와 시험. 앞 프레임의 `surface_key`, 이번 `surface_key`, 방금 받은 키, `present_result`, 푸터가 안내한 키 목록을 받아 사건을 돌려준다. 입출력도 시계도 없다. 시험은 이 함수의 결정만 본다(화면 배치를 보는 시험이 아니다).
2. 루프에 연결. 켰을 때만 이 함수를 부르고 줄을 덧붙인다. 입력을 받는 모든 곳에서 글자가 새지 않는지 점검한다.
3. 읽는 스크립트 `scripts/tui-nav-trace-report.py`. 화면별로 연 횟수, 한 번도 안 열린 화면, 안내됐는데 화면이 그대로였던 키를 센다.

## 5. 열린 질문

1. 머문 시간을 넣을까. 시계를 읽어야 해서 1층에서는 뺐다.
2. `Unchanged` 대신 "키 직후 몇 프레임 안에 바뀜"으로 비동기 키를 걸러낼까. 지금은 읽는 쪽이 거른다.
3. 파일 위치를 환경 변수가 정하는 방식 말고 고정 경로로 할까. 프레임 시간 기록과 같은 방식을 택했다.
4. tmux 증거 캡처에서 이 기록을 켜 두고, 화면별 열림 횟수를 PR 증거에 붙일까.
