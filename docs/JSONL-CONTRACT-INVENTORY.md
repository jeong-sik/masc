# JSONL Contract Inventory

Status: reference
Scope: current JSONL writer substrates and store inventory under `<base-path>/.masc/`.

## Writer Substrates

| Substrate | Current contract | Used for | Evidence |
| --- | --- | --- | --- |
| `Fs_compat.append_jsonl` | Creates parent dir, serializes appends through a per-path `Stdlib.Mutex`, writes `json + "\n"` to the path's cached `O_APPEND` descriptor. Nothing is buffered for a later append or close. The bytes of a write that fails part-way are truncated away again when the file is exactly as long as before the call plus those bytes; otherwise nothing is removed and the error says so. The row starts at a line start: the writer reads the file's last byte, and when the file ends in the middle of a line it writes a newline before the row. No fsync. | Single-file append stores and `Dated_jsonl` day files. | `lib/fs_compat/fs_compat_private_file_update.ml` |
| `Fs_compat.append_lines` | Shares the per-path mutex registry, cached descriptor, failed-write rollback and line-start rule of `append_jsonl`, and accepts one or more lines the caller already encoded, each ending in a newline. | Keeper single-file logs via `Keeper_types_support.append_jsonl_line`, task metrics, activity graph events, workspace memory log, connector name directories. | `lib/fs_compat/fs_compat_owned_file.ml`, `lib/fs_compat/fd_append_whole.ml` |
| `Fs_compat.append_file` | Shares the same per-path mutex registry, cached descriptor and failed-write rollback, and appends raw bytes right after the file's last byte. No line-start rule. | No production caller writes lines through it; tests use it to build a row in pieces. | `lib/fs_compat/fs_compat_owned_file.ml` |
| `Dated_jsonl` & `Dated_jsonl.Store` | Date-split `base_dir/YYYY-MM/DD.jsonl`, base-dir mutex registry, append guard hook, recent/range reads, malformed JSON read skip. Appends delegate to `Fs_compat.append_jsonl`. `Dated_jsonl.Store` registers date-sharded stores so the daily maintenance loop prunes them under a single `MASC_JSONL_RETENTION_DAYS` (`[maintenance] jsonl_retention_days`, default `30` days) policy. | Audit, telemetry, tool usage, keeper receipts, tool calls, runtime events, gate events, verifications, board dated posts, activity graph. | `lib/dated_jsonl/dated_jsonl.ml` |
| `Keeper_types_support.append_jsonl_line` | Optional size rotation, UTF-8 repair, then `Fs_compat.append_lines`. | Keeper memory/decision/policy/manifest single-file logs. | `lib/keeper/keeper_types_support.ml` |

## Contract Invariants

1. `Fs_compat.append_jsonl`, `Fs_compat.append_lines` and `Fs_compat.append_file` serialize mixed writes to the same path with one per-path mutex registry.
2. `Dated_jsonl.open_store` instances for equivalent base dirs share the same mutex, including trailing-slash variants.
3. `Dated_jsonl.append` writes through `Fs_compat.append_jsonl`, keeps `YYYY-MM/DD.jsonl`, and does not poison the base-dir mutex after append failure.
4. `Dated_jsonl.read_recent`, `iter_all`, and `read_range` skip malformed JSON lines instead of failing the whole read.
5. Keeper single-file helpers preserve rotation and UTF-8 repair before delegating to `append_lines`.
6. Board post/comment/reaction JSONL files remain snapshot files after mutation flush, while create paths may append.
7. Board vote rows preserve the original cast timestamp across append and rewrite.
8. Goal event rows reach `goal_events.jsonl` through one durable locked JSONL transaction, and a retried outbox delivery does not write an `event_id` that is already in the file.
9. Trajectory append stays per `(keeper, trace_id)` path and remains append-only.
10. No byte of a failed `append_jsonl`, `append_lines` or `append_file` reaches the file after the call returned. Bytes of a write that stopped part-way are removed when the file is exactly as long as before the call plus those bytes. Nothing is removed, and the error says so, when the file has another length or the truncation failed. The check is on the length, and the length is read in one call and the file cut in the next, so it is exact only while no other descriptor changes the file during the failed call. The append takes no file lock. A writer that reaches the same file through another descriptor (a second process, or this process through another name of the file) can still lose a row when it appends between the length check and the truncation. When it takes back a failed write of its own in that gap, the truncation makes the file longer again and leaves zero bytes there. A row can still join an unfinished line that such a writer leaves between the length read and the write. A failed multi-row append whose bytes stay keeps its complete rows, so writing it again repeats them. Size-based rotation counts a row as its bytes plus one newline; after an unfinished line the row is one byte longer, so a store can pass its limit by that byte.
11. `append_jsonl` and `append_lines` start at a line start. Bytes an earlier writer left without a newline stay a line of their own. When the file's last byte cannot be read, because another descriptor cut the file at that moment, the newline is written anyway and can leave an empty line. `Fs_compat.load_jsonl` and the `Dated_jsonl` reads pass over an empty line; a reader that splits a file into lines itself has to as well. The bytes an earlier writer left are not cut: readers of these files take a last line without a newline as a row when it parses, so cutting would remove a row a reader may already have shown. The durable private JSONL family (`append_private_jsonl_durable_*`) differs on purpose: there the bytes after the last newline are not a row, and its writers cut them.
