# RFC: 기다리던 메시지는 한 턴에 같이 들어간다 — 큐는 업무 종류를 모른다

11-13~16 사흘 동안 Keeper 채팅 작업이 큐에서 기다린 시간은 1,032.5시간이다. 바로 앞 사흘은 14.2시간이었다.
늘어난 몫의 대부분은 리뷰 Keeper 일곱이다(995.1시간). 여러 세션이 같은 Keeper 에게 메시지를 보내면, 메시지마다 실행을 하나씩 따로 돈다.
이 RFC 는 claim 때 기다리던 새 메시지를 줄 순서대로, 메시지마다 봉투를 단 채 한 턴에 넣자고 제안한다.
답은 요청마다 따로 간다. 큐는 업무 종류를 모르고, 묶음을 끊는 기준은 업무와 관계없는 사실뿐이다.
묶음을 넓히기 전에 큐가 멈추거나 순서를 어기는 경로 넷을 먼저 고친다.

- 다루는 것: 채팅 작업 줄(`Chat_operation_store.claim_next`)의 묶음, 요청별 답, 빈 슬롯을 누가 받는지, 큐가 멈추는 경로.
- 다루지 않는 것: 업무 종류별 갈래, 이벤트 큐 안의 순서, runtime 과 실행 시간(#52410). 끝나지 않는 턴은 따로 RFC 로 다룬다(§7-1).
- 근거 기준: 코드는 이 브랜치의 base `15e3c60e915c` 에서 읽었다.
- 측정: 2026-11-16 03:56Z 에 읽었다.
  아직 시작하지 않은 작업은 창 끝까지 기다린 것으로 세므로, 같은 창도 읽는 시각에 따라 합이 달라진다.

## 0. 요약

- **[사실]** 모든 Keeper 의 채팅 작업 대기 합은 앞 창 765건 14.2시간, 뒤 창 891건 1,032.5시간이다. 리뷰 Keeper 일곱이 995.1시간이다.
- **[사실]** 리뷰 Keeper 일곱의 작업 중 뒤 창에 기다렸고 읽은 시각까지 시작한 773건은 실행 687개로 돌았다. 다른 작업의 실행에 묶여 돈 작업은 86건(11%)이다.
- **[사실]** 채팅 작업 한 건의 평균 실행 시간이 2~6분에서 11~19분으로 늘었다. runtime 이 바뀐 Keeper 가 많지만, mother 는 앞 창에도 glm-5.3-flash 였는데 똑같이 늘었다. 원인은 확인하지 못했다(#52410).
- **[사실]** 큐에 채팅이 있는데 채팅 작업이 돈 기록이 없는 시간은 81.0시간이다. 31.1시간은 자율 턴이 돌고 있었고, 32.6시간은 직접 턴과 겹친다. 직접 턴과 겹친 몫은 대부분 측정의 빈틈이다(§3.2).
- **[결정]** 큐는 업무 종류를 모른다. 리뷰를 따로 다루지 않는다(§1).
- **[결정]** 끝나지 않는 턴은 모델이 끝을 typed 행동으로 알리게 해서 닫는다. 설계는 따로 RFC 로 쓴다(§1-5, §7-1).
- **[제안]** 1단계: 큐가 멈추거나 순서를 어기는 경로 넷을 고치고, 실행 구간을 사실로 남긴다(§4.1).
- **[제안]** 2·3단계: claim 때 기다리던 새 메시지를 봉투째 한 턴에 넣고(§4.2), 답을 요청마다 따로 보낸다(§4.3). 두 단계는 한 배포 단위다.

## 1. 운영자 결정 (2026-11-16)

1. **큐는 업무 종류를 모른다.** 리뷰만 따로 다루면 하드코딩이 생긴다. 다음엔 배포 요청, Jira 요청도 같은 식으로 늘어난다.
   큐가 아는 것은 도착 순서, 보낸 사람, 답할 곳, 지시뿐이다. 업무 종류를 가르는 코드가 있으면 지운다.
2. **메시지는 한 번에 쭉 들어간다.** 어느 메시지가 낡았는지, 무엇을 먼저 할지는 Keeper 가 함께 읽고 고른다.
3. **휴리스틱과 숫자 장치를 두지 않는다.** 글자·의미 유사도·LLM 분류기로 메시지를 가르지 않는다. debounce, 개수 상한, cooldown, 라운드 상한도 두지 않는다(constitution `magic_number`, `string_matching`, `budget_gate`).
4. **가장 중요한 것은 멈추지 않는 것이다.** 메시지는 Keeper 턴이 계속 끝나는 한 결국 어떤 턴에 닿아야 한다.
5. **턴은 모델이 typed 로 알린 끝에서 닫힌다.** 글을 읽어 끝을 판정하지 않는다. 시간이나 라운드 수로 끊지도 않는다.
   끝나지 않는 턴을 미리 알아내거나 lane 을 나누는 것보다, 모델이 끝을 알릴 통로를 주는 쪽이 싸다(§3.3).

### 1.1 다른 RFC 와의 관계

- `RFC-backlog-never-preempts-a-running-turn`(Draft): §3.1 표는 큐에 있는 채팅 작업이 도는 턴을 멈춘다고 남기고, §3.2 는 시각이 된 예약에 다음 슬롯을 먼저 준다고 남긴다.
  지금 코드에는 둘 다 없다. #47961·#48051 뒤로 `source_may_preempt`, `observe_scheduled_turn` 을 `rg` 로 찾으면 0건이다. 이 RFC 는 지금 코드를 기준으로 한다.
  그 문서의 3단계(Jev 라벨로 요약 순서를 정함)는 §1-1·§1-3 과 맞지 않아 이 PR 에서 지웠다(#52412).
- `RFC-event-queue-admit-all-ready`(Draft): 이벤트 큐의 규칙이다. 이벤트 큐 안의 순서(urgency, 대화 경계, admission 경계, 실패한 턴 뒤의 잔류)는 그 문서가 정한다.
  이 RFC 는 이벤트 쪽이 턴을 받는 것까지만 정한다(4.1-3).
  크기 거절 복구는 그 문서 §7.2-6 을 바탕으로 하고, 채팅 작업에서 달라지는 점을 적는다(§4.2). 두 큐를 한 턴에 넣게 되면(§7-3) 어느 경계를 지킬지 그때 정한다.
- RFC-0377: 이벤트 큐에서 같은 대화를 묶는 규칙이다. `claim_next` 묶음은 범위 밖이라고 적었다. 겹치지 않는다.
- `RFC-arrived-stimuli-reach-the-running-turn`(Draft): 도는 턴에 이벤트 큐 행을 보여 준다(`keeper_arrived_stimuli_reader.ml`). 채팅 작업의 본문은 보여 주지 않는다.
  채팅 작업은 Agent Core 경로에서 대기 개수만 보인다(`keeper_waiting_operations.ml`, #52264).

## 2. 지금 모양

### 2.1 한 번에 하나만 돈다

- `claim_next` 는 `running` 행이 하나라도 있으면 아무것도 꺼내지 않는다(`keeper_chat_operation_store.ml:2008-2012`).
- `semantic_executions` 에도 `running` 은 하나뿐이다(unique index `semantic_single_running`).
- 자율 턴과 직접 턴은 owner 의 슬롯 하나(`turn_in_flight`)를 나눠 쓴다. 도는 턴을 끊지 않는다(#51221, #47961).
- 운영자 명령 `Run_next_operation` 은 작업 하나를 줄 맨 앞으로 옮긴다(`keeper_owner.ml:2676-2687`).

### 2.2 묶음은 같은 출처의 연속 구간뿐이다

- `select` 는 맨 앞 작업과 출처(`external_message_id` 를 뺀 `decoded_source` 전체), 답할 곳, 지시, `surface_context` 가 같은 작업만 모은다(`keeper_chat_operation_batch.ml:12-14`, `:52-54`).
- 다른 작업을 만나면 거기서 멈춘다(`:60`). 디코딩에 실패한 작업, 같은 첨부 id 에 내용이 다른 첨부가 있는 작업에서도 멈춘다(`:21-25`, `:49-56`). 그래서 연속 구간만 묶인다.
- claim 은 대기에 걸린 작업을 건너뛰고, claim 가능한 작업만 줄 순서대로 읽는다(`keeper_chat_operation_store.ml:1846-1886`).
- 묶인 메시지는 `"\n\n"` 으로 이어 붙인 문자열 하나가 된다(`:67`). 메시지마다의 출처와 받은 시각은 실행 입력에서 사라진다.
- store 는 멤버를 claim 트랜잭션에서 고정하고, 원래 입력을 `admitted_input_json` 에 남긴다(`keeper_chat_operation_store.ml:1978-1989`). 묶음이 claim 뒤에 커지지는 않는다.
- 이어 받는 작업(continuation)을 만나면 구간이 끝난다(`:1943-1958`).

### 2.3 실행은 맨 앞 작업의 출처로 돌고, 같은 답을 모두에게 보낸다

- 실행기는 맨 앞 작업의 `source` 로 payload 를 만든다(`server_routes_http_keeper_stream.ml:2596-2601`, `:2871`). 발화자 문맥(`channel_user_*`)도 맨 앞 작업 것으로 한 번 만든다(`:618-628`).
- Keeper 가 보낸 요청이면 같은 종단 결과(`Delegate_replied` 또는 `Delegate_no_reply`)를 멤버마다 보낸다(`:2805-2830`).
- `event_for_member` 는 실행의 stream 이벤트를 멤버마다 복사한다. 도구 이벤트와 `Text_delta` 도 복사된다(`keeper_chat_operation_batch.ml:73-85`).

### 2.4 큐를 멈추게 하거나 순서를 어기는 경로

1. **실패 뒤 `Running` 이 남는다.** child 가 돌아와 실패 결과를 내고 native call 이 `Active` 로 열려 있으면, 정책은 `Leave_active_call_for_restart` 를 고른다(`keeper_owner.ml:957-975`).
   행은 `Running` 으로 남는다(`:1797-1805`). owner 의 메모리 슬롯은 비지만 `claim_next` 는 다음 작업을 꺼내지 않는다.
   child 가 예외로 끝나거나(`Child_raised`) 운영자가 중단하면 호출을 닫는다(`:959`).
   소스로 이어지는 구체 경로는 Agent Core 가 `Active` 호출을 재개하다 checkpoint 로드에 실패해 `Turn_exception` 을 돌려주는 경우다. 재시작 뒤에도 같은 로드 실패가 되풀이되면 다시 같은 상태가 된다(#52407).
   11-10~11-16 로그에는 이 경고가 0번 나왔다.
2. **다시 실행 가능해진 작업이 옛 순번을 쓴다.** `sequence` 는 접수 번호가 아니라 지금 줄 위치다. checkpoint 와 운영자 이동이 이미 바꾼다(`keeper_chat_operation_store.ml:2141-2317`, `:2801-2808`).
   runtime 재시도, 입력 대기, gate 대기, preparation 대기, 재시작 재개는 `requeue_continuation_with_db`(`:2496-2505`)만 부르고 순번을 그대로 둔다. 대기가 풀릴 때도 순번은 그대로다.
   그래서 대기가 풀린 작업이 그사이 들어온 작업보다 먼저 꺼내진다(`ORDER BY sequence`, `:1876`, #52408).
3. **슬롯이 비면 채팅이 먼저 받는다.** owner 는 턴이 끝나면 `start_child_if_needed` 로 채팅을 먼저 꺼낸다. 자율 턴은 남은 슬롯만 받는다(`keeper_owner.ml:585-599`, `:1828-1832`).
   채팅이 계속 들어오면 이벤트 큐의 결과 알림(`Tool_result_ready`, `Delegate_completed`, 일정 영수증)이 밀린다(#46120). 반대로 자율 턴이 돌 때 온 채팅은 그 턴이 끝날 때까지 기다린다.
4. **배달이 끝날 때까지 슬롯을 잡는다.** 실행기는 턴이 돌아온 뒤 `Eio.Promise.await delivery` 를 기다린다(`server_routes_http_keeper_stream.ml:2895`). 외부 채널 배달이 늦으면 다음 실행도 늦어진다(#52409).

## 3. 측정

- 접수는 `created_at` 이 창 안인 작업 수다. 대기는 창과 겹친 대기 구간의 합이다. 아직 시작하지 않은 작업은 창 끝까지, 취소된 작업은 취소 시각까지 센다.
- 시작은 대기가 뒤 창과 겹친 작업 중 읽은 시각(03:56Z)에 `started_at` 이 있는 작업이다. 창 끝 뒤에 시작한 작업도 들어간다.
- 이어 받는 작업은 재큐 때 `started_at` 을 지우고 다시 쓴다. 그래서 대기 합에는 앞 실행 시간도 섞인다.
  첫 claim 시각은 실행 기록(`semantic_executions.created_at`)에 있지만 이 기록은 11-13 11:29Z 부터만 남아 있어, 창 전체의 비교에는 쓰지 않았다.
- 평균 실행 시간은 시작한 작업 중 끝난 작업의 마지막 실행 구간 길이다.
- uncle 은 접수가 320건에서 111건으로 줄었는데 대기는 늘었다. context-reviewer 는 접수가 7배가 됐다. 대기가 늘어난 이유는 Keeper 마다 유입과 실행 시간이 다르게 섞였다.
- 실행 시간이 늘어난 시기는 runtime 이 바뀐 시기와 겹치는 Keeper 가 많다. 그런데 mother 는 앞 창에도 직접 턴 대부분이 glm-5.3-flash 였고, 실행 시간은 7.7배가 됐다(`result-runtime-by-window.json`, 17.392 / 2.272).
  이 runtime 표는 도구를 부른 턴만 센다. 평균 실행 시간과 모집단이 같지 않다.
  이 RFC 는 runtime 을 다루지 않는다(#52410).

### 3.2 채팅이 안 돈 시간

| | 시간 |
|---|---|
| 큐에 채팅이 있는데 채팅 작업이 돈 기록이 없는 시간 | 81.0 |
| 그중 자율 턴과 겹친 시간 | 31.1 |
| 그중 직접 턴과 겹친 시간 | 32.6 |
| 어느 턴과도 겹치지 않은 시간 | 17.3 |

- 턴 구간은 raw trace 파일 이름의 시작 시각부터 턴 기록의 `ts` 까지다. 창과 겹친 부분만 셌다. 배달 대기와 owner 정산 시간은 빠지므로 슬롯 점유와 꼭 같지는 않다.
- 직접 턴과 겹친 32.6시간은 대부분 측정의 빈틈이다. 이어 받는 작업은 다시 시작할 때 `started_at` 을 새로 쓰므로, 앞 실행 구간이 "채팅이 안 돈 시간"으로 보인다.
  예를 들어 11-15 uncle 의 직접 턴은 17:08Z 에 시작해 11-16 01:00:26Z 에 끝났다. 그 작업은 runtime 재시도로 줄에 돌아갔다가, 재시작 뒤 02:10:48Z 에 `started_at` 을 다시 썼다.
- 리뷰 Keeper 일곱의 턴은 자율 1,183개 155.6시간, 직접 699개 179.8시간이다. 턴 구간 합의 46% 가 자율 턴이다.

어느 턴과도 겹치지 않은 17.3시간은 서버 로그로 나눴다(`result-gap-causes-2026-11-13..16.json`). 시각은 UTC 다.

| 구간 | 시간 | 원인과 근거 |
|---|---|---|
| 11-15 13:43:51~17:06:02 | 11.2 | 13:43:51 부터 `ENOSPC`(디스크 가득 참). 15:42:29 마지막 로그 뒤 17:00:53 까지 서버가 내려가 있었다. |
| 11-13 05:08~06:31, 다섯 Keeper | 3.7 | 06:30:03 배포 재시작에 끊긴 턴. 다섯 Keeper 모두 공백 안에 `checkpoint_save` 로그가 6~45줄 있다. 턴 기록도 raw trace 도 없다. |
| 나머지 | 2.4 | 676 구간. 구간 하나가 평균 13초다. |

지금 기록만으로는 한 작업이 언제부터 언제까지 슬롯을 잡았는지 다시 셀 수 없다. 재시작에 끊긴 턴은 턴 기록을 남기지 않고, 이어 받는 작업은 `started_at` 을 덮어쓴다(§4.1-5).

### 3.3 일을 마친 뒤에도 끝나지 않은 턴

슬롯이 하나라서 턴 하나가 길면 그 Keeper 의 채팅 줄과 이벤트 큐가 함께 기다린다. 위 uncle 의 턴은 7.9시간 돌았다(raw trace `turn-1794762495928-88eb-000000.jsonl`).

- 처음 runtime(claude_code)은 한도로 바로 실패했고, glm-coding(glm-5.3-flash)으로 넘어갔다.
- 실제 일은 18:06:46Z 에 끝났다. 그때까지 `Execute` 를 8번, `masc_schedule_note_add` 를 1번 불렀다.
- 18:11:09Z~00:44:50Z 에 같은 라운드를 177번 되풀이했다. 라운드 간격은 평균 134초다.
  라운드마다 "이 턴 종료(도구 호출 없음)" 로 시작하는 글을 쓰고 `keeper_lane_status({})` 를 불렀다. 177번 모두 입력이 같고, 결과는 시각 값만 다르다.
- 턴은 01:00:26Z 에 provider 대기열 시간 초과(`timeout phase=queue`)로 끝났다. 일을 마친 뒤 슬롯을 6.9시간 더 잡았다.

모델은 끝내겠다고 글로 썼지만 같은 응답에 도구 호출을 붙였다. 턴 루프는 도구 호출이 있으면 다음 라운드를 돈다.
끝내겠다는 뜻이 글에만 있어서 시스템이 받을 수 없었다. 이 RFC 는 이를 고치지 않는다. §1-5 에 따라 따로 RFC 로 쓴다(§7-1, #52411).

## 4. 제안

### 4.1 1단계 — 큐가 멈추거나 순서를 어기는 경로 넷을 고치고, 실행 구간을 남긴다

1단계는 묶음과 관계없이 먼저 들어간다. 묶음을 넓히면 한 실행이 더 많은 요청을 안는다. 그 실행이 멈추면 더 많은 요청이 같이 멈춘다.

1. **실패한 실행은 슬롯을 놓는다.** child 가 `Active` 호출을 둔 채 실패로 끝나면, owner 가 멈추는 중이 아닌 한 호출을 「효과 모름」 영수증으로 닫고 작업을 child 가 돌려준 실패 종류로 끝낸다. journal 은 읽지 않는다. 자동으로 다시 실행하지 않는다(`restart-resumes-running-chat-operations` 4.3, 운영자 결정 2026-11-17).

   시간이 지났다는 이유로 죽은 실행으로 판정하지 않는다(constitution `no_wall_clock_death`).
   늦게 돌아온 옛 실행이 결과를 쓰지 못하게 child 종료와 native 콜백에 실행 회차 token 을 묶는다. 지금 `Operation_child_finished` 에는 이 token 이 없다(#52407).
2. **다시 실행 가능해진 작업은 줄 뒤로 간다.** `sequence` 를 줄 위치로 쓰고, 접수 시각은 `created_at` 으로 읽는다.
   - `running → queued` 공통 재큐(`:2496-2505`)에서 `sequence` 를 한 번 새로 받는다. checkpoint 가 따로 받던 재발급은 이 자리로 옮긴다. 한 사건에 두 번 받지 않는다.
   - 이미 `queued` 인 작업의 대기가 풀려 claim 가능해질 때도 새로 받는다. 입력 응답 확정, gate 결정, preparation 재시도, 마지막 영수증 도착, runtime 재시도 대기 해제가 그 사건이다.
     `not_before` 도달은 claim 트랜잭션에서 한 번만 durable 하게 반영한다.
   - 같은 요청이 다시 와도(재전송, 중복 결정) 순번을 다시 받지 않는다.
   - 실패 횟수로 벌점을 주는 일이 아니다. 이미 실행 기회를 쓴 작업과 대기가 풀린 작업이 옛 순번으로 새 작업을 앞지르지 않게 하는 일이다(#52408).
3. **빈 슬롯은 두 줄이 번갈아 받는다.** 슬롯이 비면 owner 는 직전 턴을 받지 않은 줄부터 본다. 그 줄에 시작할 입력이 있으면 그 줄이 받고, 없으면 다른 줄이 받는다.
   - 채팅 줄의 입력은 claim 가능한 채팅 작업이다. 이벤트 쪽의 입력은 ready 인 이벤트 큐 행과, 행 없이 도는 자율 실행(`Periodic_tick`, `Continue_on_deferred_lane`)이다.
   - owner 는 두 줄의 상태를 저장소에서 직접 읽고, 고른 쪽 실행을 직접 시작한다. 다른 fiber 의 답을 기다리지 않는다. 기다리면 그 fiber 가 멈출 때 슬롯도 멈춘다.
     지금 자율 턴은 heartbeat loop 가 `Run_if_idle` 로 요청해야 시작한다(`keeper_owner.ml:2955-3043`). owner 가 이벤트 쪽 실행기도 채팅 실행기처럼 직접 가져야 한다.
   - 이벤트 쪽 턴이 행을 하나도 admit 하지 못하고 끝나도 그 턴은 이벤트 쪽 차례로 친다. 다음 차례는 채팅이다.
   - 시각 비교, 가중치, 우선순위가 아니다. 두 줄 모두 입력이 있으면 같은 줄이 두 턴을 연달아 받지 않는다는 규칙 하나다.
   - 이벤트 큐 안에서 어느 행을 admit 할지는 `RFC-event-queue-admit-all-ready` 가 정한다. 이 RFC 는 이벤트 쪽이 턴을 받는 것까지만 정한다.
   - 묶음(§4.2)과 같이 들어가면 번갈아 받는 비용이 작다. 채팅 턴 하나가 기다리던 메시지를 모두 넣으므로, 채팅은 많아야 이벤트 쪽 턴 하나를 더 기다린다.
   - 운영자 명령과 Maintenance lane 은 지금처럼 둔다.

   지금 슬롯 해제 알림(`notify_turn_slot_released`)은 "채팅이 먼저 가져가고 남으면 알린다"는 뜻이라 이 뜻도 바뀐다(#46120).
4. **배달은 슬롯 밖에서 한다.** 실행의 종단 결과와 요청별 배달 의도를 같은 트랜잭션에 쓴다. 슬롯은 그때 놓는다. 배달은 그 기록을 읽어 따로 진행한다. 배달 결과는 셋으로 나눈다.
   - 보내지 않은 것이 확실하다(보내기 전 실패, 채널이 받기 전에 거절): 다시 보낸다. 모델은 다시 돌리지 않는다.
   - 받은 것이 확실하다: 끝난다.
   - 보냈는데 결과를 모른다(보낸 뒤 기록 전에 프로세스가 죽음, 응답 없음): `Delivery_uncertain` 으로 남기고 자동으로 다시 보내지 않는다. 채널이 멱등 키나 수신 조회를 주면 그것으로 확인한다.

   constitution `failure_keeps_evidence` 를 따른다(#52409).
5. **실행 구간을 사실로 남긴다.** 슬롯을 잡을 때마다 새 구간을 연다. 잡음, claim, 예약 해제, 슬롯 해제를 append-only 사건으로 덧붙인다. `started_at` 을 덮어쓰지 않는다.
   재시작에서 끝을 못 본 구간은 끝 시각을 지어내지 않고 "끝 불명"으로 남긴다. 관측용 사실이고 claim, 재시도, 정산 판정에 쓰지 않는다(#52406).

### 4.2 2단계 — claim 때 기다리던 새 메시지를 봉투째 넣는다

2단계와 3단계는 한 배포 단위다. 2단계만 들어가면 다른 답할 곳의 요청이 맨 앞 작업의 답할 곳으로 간다.

- claim 은 맨 앞 작업부터 묶음을 끊는 자리 앞까지, 기다리던 새 작업을 줄 순서대로 고른다. 보낸 사람, 답할 곳, 채널이 달라도 함께 고른다.
- 대기에 걸린 작업은 claim 가능하지 않으므로 건너뛴다. 묶음을 끊지 않는다. 대기가 풀리면 새 순번을 받아 줄 뒤로 간다(4.1-2).
- 멤버는 지금처럼 claim 트랜잭션에서 고정한다. 그 뒤에 온 메시지는 다음 claim 으로 간다.
- 메시지를 문자열 하나로 잇지 않는다. 실행 입력은 봉투의 목록이다. 봉투 하나에는 다음 칸이 있다.

  | 칸 | 출처 |
  |---|---|
  | `operation_id` | 작업 |
  | `received_at` | `created_at` |
  | 출처 전체 | `decoded_source` 의 모든 칸을 그대로 싣는다(`keeper_chat_operation_payload.mli`). 칸을 골라 싣지 않는다. |
  | 본문, `user_blocks`, 첨부 | `decoded_input` |

  업무 종류 칸은 없다. PR 번호, head, 「리뷰 요청」 표시도 없다. 발화자 문맥은 봉투마다 만든다.
- 묶음을 끊는 자리는 셋이다. 모두 업무와 관계없는 사실이다.
  1. claim 가능한 이어 받는 작업. 이미 시작한 실행을 잇는 작업이라 새 묶음에 들어가지 않는다(지금과 같다).
     줄이 `A, 이어 받는 작업 C, B` 이고 셋 모두 claim 가능하면 A, C, B 순서로 돈다. C 가 대기에 걸려 있으면 A 와 B 가 한 묶음이 된다.
  2. 실행 전체에 걸리는 문맥이 다른 작업. 지금은 지시(`turn_instructions`)와 `surface_context` 다(§7-2). `decoded_source` 의 어느 칸이 실행 전체에 걸리는지는 구현 RFC 에서 칸마다 정한다.
  3. provider 의 typed 입력 크기 거절. 아래 복구 계약을 따른다.
- `A1, B, A2` 처럼 다른 출처가 끼어도 셋을 순서대로 모두 넣는다. B 를 건너뛰고 A1·A2 만 앞당기지 않는다.
- **권한.** 지금 출처에는 인증된 권한 칸이 없고, 턴은 Keeper 자신의 권한으로 돈다. 묶음은 이 사실을 바꾸지 않는다.
  다만 도착 순서를 지킨다고 보낸 사람들의 권한이 같아지지는 않는다. 출처별 권한이 생기면 그 칸은 실행 전체 문맥이 되어 묶음을 끊는다.

**크기 거절 복구.** `RFC-event-queue-admit-all-ready` §7.2-6 을 바탕으로 한다. 채팅 작업에서 달라지는 점도 적는다.

- 시작: provider 가 typed 입력 크기 거절을 돌려주고 효과 실행 전임이 증명될 때만 시작한다. 효과 여부를 증명할 수 없는 실패는 나누지 않고 기존 안전 판정을 따른다. 그 문서와 같다.
- 기록: 거절된 요청 크기, 실행 id, 정렬된 멤버 id, runtime, 고정 문맥 해시를 durable 입력 적합성 기록에 남기고 그 실행을 닫는다.
  고정 문맥은 멤버 봉투를 뺀 모델 입력 전체다(시스템 지시, 도구, 이력). 닫힌 실행은 멤버를 이력에 남기지 않는다.
- 기록의 범위: 기록은 같은 runtime, 같은 고정 문맥 해시에서만 쓴다. 둘 중 하나가 바뀌면 기록을 버리고 보통 claim 으로 돌아간다.
- 나누기: 다음 claim 은 기록의 멤버만 순서를 지키는 비어 있지 않은 두 연속 부분으로 나누고 앞부분만 고른다. 그사이 온 메시지는 넣지 않는다.
  앞부분도 같은 typed 판정을 받고, 거절되면 다시 나눈다. 멤버는 모델 입력에 닿지 못했으므로 순번을 그대로 둔다.
  멤버 고정은 실행마다다. 닫힌 실행의 멤버는 바뀌지 않고, 앞부분은 새 실행으로 새로 고정한다(`FrozenMembership`).
- 앞부분 성공: 앞부분은 보통처럼 정산하고 기록을 지운다. 남은 멤버는 줄 순서대로 보통 claim 을 받는다. 그사이 온 메시지와 다시 묶일 수 있고, 다시 거절되면 새 기록을 연다.
- 한 작업까지: 그 작업 하나도 거절되고, 같은 runtime·같은 고정 문맥 해시로 받아들여진 요청이 있을 때만 그 작업을 `Input_too_large` 로 끝내고 보낸 쪽에 알린다.
  받아들여진 요청이 고정 문맥을 담고 있었으므로 고정 문맥은 상한 안이다.
  그 문서는 같은 경우 행을 `Admission_blocked` 로 남긴다. 채팅 작업은 기다려도 본문이 바뀌지 않고, 보낸 쪽이 줄여 다시 보낼 수 있어서 끝낸다.
- 근거가 없으면: Keeper 를 입력 부적합으로 멈추고 줄을 그대로 둔다. 운영자가 고치고 재개한다.

리뷰 상황은 일반 규칙으로 풀린다. 리뷰 요청(n), 「head 가 바뀌었다」(n+1), 「병합됐다」(n+2), 「앞 메시지 정정」(n+3)이 한 턴에 같이 보인다.
어느 요청이 낡았는지는 Keeper 가 읽고, 필요하면 GitHub 를 직접 보고 고른다.

### 4.3 3단계 — 답은 요청마다 따로 간다

- Keeper 는 답을 요청 ID 에 묶어 낸다. 자유문 답을 나중에 글자로 나누지 않는다. 묶는 방법(도구 하나, 또는 typed 구조 출력)은 구현 RFC 에서 정한다.
- 답은 그 요청의 `continuation_channel` 로 간다. 맨 앞 작업의 답할 곳을 다른 요청에 물려주지 않는다.
- 답하지 않은 요청에는 `No_reply_emitted` 라는 사실만 남긴다. 실패도, 답할 의무도 아니다. 다시 큐에 넣지 않는다.
- 요청별 stream 에는 묶였다는 사실(`Batch_bound`)과 자기 답만 간다. 도구 이벤트는 실행 journal 한 곳에 남긴다. `event_for_member` 의 복사는 없어진다.
- Keeper 사이 요청은 지금처럼 일반 메시지다. 답, 대기, 재시도 의무를 만들지 않는다.

## 5. 멈추지 않는다는 논증

| 불변식 | 뜻 |
|---|---|
| `NoLostAccepted` | 받은 작업은 대기, 실행에 묶임, 끝남 중 어디에 있는지 늘 찾을 수 있다. |
| `FrozenMembership` | claim 뒤에 그 실행의 멤버와 입력이 늘거나 바뀌지 않는다. |
| `OldestIncluded` | 새 채팅 실행은 지금 claim 가능한 채팅 작업 중 줄 맨 앞을 포함한다. 줄 순서는 `sequence` 이고, 운영자 이동도 `sequence` 를 바꾼다. |
| `Alternation` | 두 줄 모두 시작할 입력이 있으면 같은 줄이 두 턴을 연달아 받지 않는다. |
| `UniqueOwner` | 한 작업을 두 실행이 동시에 갖지 않는다. 재개는 같은 실행을 잇는다. |
| `ReplyBoundToRequest` | 답은 그 요청의 답할 곳으로만 간다. |
| `NoMessageWaitEdge` | 일반 메시지는 Keeper 사이에 기다림을 만들지 않는다. 그래서 메시지만으로 생기는 순환 대기는 없다. |

**끝 상태.** 채팅 작업 m 은 셋 중 하나로 끝난다. 모델이 m 을 봤다(`Observed`). typed 크기 거절로 끝났다(`Refused`). 취소됐다(`Cancelled`).

**진행 척도.** 채팅 작업 m 에 대해, 채팅 줄에서 m 보다 앞선 claim 가능한 작업의 수와 다음 턴이 채팅 차례인지를 함께 본다.

- m 이 claim 가능해진 순간 앞선 작업은 유한하다.
- 채팅 줄은 적어도 두 턴에 한 번 턴을 받는다(`Alternation`). 채팅 턴은 줄 맨 앞부터 끊는 자리 앞까지를 소비한다(`OldestIncluded`).
- 다시 실행 가능해지는 작업은 새 순번을 받아 m 뒤로 간다(4.1-2). 새로 들어오는 작업도 m 뒤로 간다.
- 크기 거절로 닫힌 실행은 기록의 멤버만 줄이며 되풀이된다. 앞부분이 성공하면 적어도 한 작업이 줄에서 빠진다.
  한 작업까지 줄면 그 작업이 `Refused` 로 끝나거나 Keeper 가 멈춘다.
- 묶음은 claim 때 고정되므로 새 유입이 진행을 되돌리지 못한다.

이벤트 쪽도 적어도 두 턴에 한 번 턴을 받는다. 이벤트 큐의 행이 결국 admit 되는지는 `RFC-event-queue-admit-all-ready` 의 논증에 맡긴다.

**가정.**

- 각 실행이 유한한 시간에 끝난다.
- 저장소와 provider 가 결국 계속 쓸 수 있게 된다.
- Keeper 가 입력 부적합으로 멈추면 운영자가 결국 고치고 재개한다.
- 운영자가 작업 하나를 계속 앞으로 옮기면 다른 작업은 밀린다. 이 척도는 운영자 이동을 되풀이하지 않는 구간에서 성립한다.

provider 가 잠깐씩만 열리는 경우는 이 가정 밖이다. 그때는 열린 동안 실제로 실행 기회를 배분한다는 더 강한 공정성이 필요하다.

**보장하지 않는 것.**

- 끝나지 않는 턴이 있으면 슬롯 하나 구조에서 다음 턴은 일어나지 않는다. 묶음, 순번, 번갈아 받기 모두 이 조건을 바꾸지 못한다. 따로 RFC 로 다룬다(§7-1).
- 유입이 처리량을 계속 넘으면 줄은 커진다. 굶주림이 없다는 것과 줄이 안 커진다는 것은 다른 성질이다.
- 모델이 입력을 받은 직후 기록 전에 프로세스가 죽으면 같은 입력을 다시 볼 수 있다. 다시 보는 것과 같은 효과를 두 번 내는 것은 다르다. 이 RFC 는 뒤의 것만 막는다.
- 외부 채널은 받는 쪽의 중복 제거나 조회 없이 무손실과 무중복을 함께 보장할 수 없다. 그때는 `Delivery_uncertain` 으로 남긴다.
- 고정 문맥이 provider 상한을 넘으면 Keeper 는 운영자가 고칠 때까지 멈춘다.

## 6. 하지 않는 것

- 업무 종류 갈래(`Review_request` 같은 variant), `(repo, pr, head)` 같은 업무별 키, claim 때 GitHub 조회, 업무별 우선순위.
- 메시지 본문에서 PR 번호나 「정정」을 찾는 일. LLM 으로 큐를 미리 분류하거나 정렬하는 일.
- debounce, 개수 상한, cooldown, 라운드 상한, 행동을 바꾸는 timeout.
- 도는 턴을 강제로 끊는 일.
- 응답 본문을 자동으로 합치거나 요약하는 일.

## 7. 열린 질문

1. **끝나지 않는 턴.** 방향은 정했다(§1-5). 모델이 끝을 typed 행동으로 알리면 같은 응답의 다른 호출만 처리하고 턴을 닫는다. 끝 행동이 없으면 지금과 같다.
   설계는 따로 RFC 로 쓴다(#52411). 거기서 정할 것은 다음과 같다.
   - 끝 행동의 모양. 전용 도구로 할지, §4.3 의 요청별 답 묶기로 할지.
   - 공식 클라이언트 경로에서도 같은 통로를 줄 수 있는지.
   - 닫은 뒤의 정산.
   - `RFC-arrived-stimuli-reach-the-running-turn` §4 와의 관계. 그 문서는 "닫는 말 + 도구 호출" 버릇을 고치지 않는다고 정했다. 끝 행동은 버릇을 고치는 일이 아니라 끝을 알릴 통로를 주는 일이다.

   진전 없는 라운드를 결정론으로 판정하는 안도 있다. 도구마다 읽기 전용인지, 어느 칸이 관측 시각인지 선언해야 해서 뒤로 미뤘다.
   운영자 턴 중단은 지금처럼 남는다. 일하는 도중에 막힌 턴을 턴 시작점(`seed_checkpoint`)에서 다시 돌리는 길도 그 RFC 에서 함께 본다.
2. **지시가 다른 작업.** 지시를 봉투 안으로 옮기면 묶음이 끊기지 않는다. 대신 지시의 무게가 시스템 지시에서 메시지 내용으로 내려간다.
3. **이벤트 큐 행도 같은 턴에 넣을지.** 리뷰 Keeper 의 턴 구간 합의 46% 가 자율 턴이다(§3.2). 턴 하나가 채팅 작업과 이벤트 큐 행을 함께 받으면 두 줄이 번갈아 기다리는 일이 줄어든다.
   `RFC-event-queue-admit-all-ready` 와 겹치는 범위를 먼저 읽는다.

## 8. 검증

feature 시험은 constitution `testing` 에 따라 기능 단위로 쓴다.

1. 서로 다른 보낸 사람 셋이 답할 곳을 달리해 작업 k 개를 넣는다. 그동안 턴 하나가 돈다. 다음 claim 이 k 개 전부를 줄 순서대로 봉투째 넣는지 본다.
2. 1 의 실행이 끝나면 보낸 사람마다 자기 답만 받는지, 답하지 않은 요청에 `No_reply_emitted` 만 남는지 본다.
3. 실행 중에 서버를 재시작한다. 멤버가 그대로인지 본다. 받은 것이 확실한 답은 다시 보내지 않고, 결과를 모르는 답은 `Delivery_uncertain` 으로 남는지 본다.
4. A 가 도는 동안 B 를 넣고 A 를 runtime 재시도로 돌려보낸다. B 가 먼저 claim 되는지 본다. A 가 대기하는 동안 B 를 넣고 A 의 대기를 풀었을 때도 B 가 먼저인지 본다.
5. child 가 `Turn_exception` 을 돌려주고 native call 이 열려 있어도, 행이 `Running` 으로 남지 않고 다음 작업이 시작하는지 본다.
6. 채팅 작업이 계속 들어오는 동안 이벤트 큐에 ready 행을 넣는다. 이벤트 쪽이 두 턴에 한 번 슬롯을 받는지 본다.
   이벤트 쪽 턴이 행을 하나도 admit 하지 못하고 끝나도 다음 턴을 채팅이 받는지 본다.
7. 묶음이 크기로 거절되면 기록의 멤버만 나눠 앞부분이 도는지 본다. 그사이 온 메시지가 앞부분에 들어가지 않는지 본다.
   한 작업까지 좁혀졌을 때, 같은 고정 문맥이 받아들여진 근거가 있으면 그 작업만 `Refused` 로 끝나는지 본다. 근거가 없으면 Keeper 가 줄을 그대로 둔 채 멈추는지 본다.
   runtime 이나 고정 문맥이 바뀌면 기록을 버리는지 본다.

상태 기계는 TLA+ 로 옮긴다. 모델에는 두 줄의 차례, 이어 받는 작업의 경계, 재큐와 대기 해제, 크기 거절 분할, Keeper 멈춤과 운영자 재개를 넣는다.

- 안전: §5 표의 불변식.
- 진행: `ChatClaimable(m) ~> (Observed(m) \/ Refused(m) \/ Cancelled(m))`, `EventReady ~> EventTurnStarted`.
  claim, 실행 종료, 운영자 재개에 약한 공정성을 준다. provider 와 저장소는 결국 계속 쓸 수 있다고 둔다. §5 의 가정과 같다.

`NextBuggy == Next \/ BugAction` 은 반드시 위반을 내야 spec 이 유효하다.

- claim 뒤에 멤버를 더한다: `FrozenMembership` 위반.
- 재시도나 대기 해제가 옛 순번으로 돌아온다: 진행 위반. 같은 작업이 재시도를 되풀이하는 동안 뒤의 작업이 claim 되지 않는다.
- 실패한 실행이 `Running` 을 남긴다: 진행 위반.
- 이벤트 쪽에 입력이 있는데 채팅이 턴을 연달아 받는다: `Alternation` 위반, 이벤트 쪽 진행 위반.
- 크기 거절 분할에 그사이 온 메시지를 넣는다: 진행 위반. 앞부분이 줄지 않는다.

배포 뒤에는 같은 스크립트로 접수·시작·실행 수, 대기 합, 채팅이 안 돈 시간과 턴 겹침을 다시 잰다. 원인별 나눔과 슬롯 점유는 4.1-5 기록이 생기면 그 기록으로 잰다.
평균 묶음 크기가 커졌다는 것만으로 성공이라 하지 않는다.

## 부록 A. 독립 검토 두 건

같은 질문지를 서로 다른 모델 둘(gpt-6.1-sol, gpt-6-astra, reasoning max, 읽기 전용)에게 따로 줬다. 두 답이 같게 짚은 것은 다음과 같다.

- "메시지 하나 = 실행 하나 = 답 하나" 를 풀어야 한다. claim 때 고정한 유한 집합을 원래 봉투 그대로 넣는다.
- 지금 출처에는 인증된 권한 칸이 없다. 화면용 `Owner` 를 권한 근거로 쓰면 안 된다.
- `event_for_member` 의 복사 때문에 답만 나눠서는 요청별 답이 되지 않는다.
- §2.4 의 1·2 경로. 둘 다 끝나지 않는 턴은 슬롯 하나·비선점·숫자 상한 없음으로는 진행을 보장할 수 없다고 답했다.

두 검토 모두 처음에는 리뷰 요청에 `(repo, pr, head)` 칸을 붙이는 안을 냈다. §1-1 결정으로 이 RFC 는 그 안을 쓰지 않는다.
줄 순서대로 넣으면 출처끼리 순서를 건너뛰는 문제가 생기지 않는다. 남는 조건은 둘이다. 답을 요청마다 따로 보내야 하고(§4.3), 실행 전체에 걸리는 문맥이 같아야 한다(§4.2).

## 부록 B. 적대 검토 (gpt-6.1-sol, 2026-11-16)

첫 초안을 다른 모델에게 반박하게 했다. 맞는 지적은 모두 고쳤다.

- 측정 스크립트가 취소된 작업을 창 끝까지 기다린 것으로 셌다. sister 한 Keeper 에서 대기 39시간이 부풀었다.

- 도는 턴에 채팅 본문이 보인다고 잘못 적었다. §1.1 과 §7-1 을 고쳤다.
- 배달 재시도와 무중복 약속이 어긋났다. 4.1-4 에서 배달 결과를 셋으로 나눴다.
- TLA+ 안전 불변식만으로는 진행 결함을 잡지 못한다. §8 에 진행 성질을 더했다.

## 부록 C. 2차 적대 검토 (gpt-6-astra, 2026-11-16)

부록 B 를 반영한 판(`9a4ac26f9e59`)을 다른 모델에게 다시 반박하게 했다. P0 는 없었다. 맞는 지적은 모두 고쳤다.

- 두 줄을 실행 기회 시각 하나로 합친 순서는 이벤트 큐 안의 규칙까지 증명해야 했다. urgency 정렬, admission 경계, 실패한 턴 뒤에 남는 행, 행 없이 도는 자율 실행이 그 규칙이다.
  시각을 언제 만들고 언제 비교하는지도 정하지 못했다. 4.1-3 을 두 줄이 번갈아 받는 규칙으로 바꾸고, 이벤트 큐 안의 순서는 그 RFC 에 맡겼다.
- 크기 거절 뒤 한 작업을 끝내는 근거에 "같은 입력" 조건이 없었다. 문맥이나 runtime 이 바뀐 뒤의 근거로 작업을 끝낼 수 있었다.
  기록을 runtime 과 고정 문맥 해시에 묶었다. 그 문서와 다른 점(앞부분 성공 뒤, 한 작업 거절)을 따로 적었다.
- 크기 거절로 끝난 작업은 모델에 닿지 않으므로 `Observed` 로 끝나지 않는다. 끝 상태를 셋으로 나눴다.
  Keeper 멈춤 뒤 운영자 재개를 가정에 넣고, §5 와 §8 의 공정성 가정을 맞췄다.
- 대기에 걸린 이어 받는 작업이 묶음을 끊는지 정하지 않았다. 대기 중인 작업은 건너뛴다고 적었다.
- "뒤 창에서 시작한 773건"은 틀린 말이었다. 창 끝 뒤에 시작한 작업도 들어간다. 표 머리와 설명을 고쳤다.
- mother 배율은 7.7배다. 첨부 설명과 출처 칸 설명도 코드에 맞췄다.
