# 사람이 등록한 API key 는 그 사람의 계정이고, 그 사람의 호출에만 실린다

- 상태: 초안.
- 계기: 다계정 서버에 사람을 초대해 같이 쓰려면, 구독이 없는 사람도 자기 API key 로 Keeper 를 돌릴 수 있어야 한다(2026-11-17 운영자 요청).
- 근거 기록: [연구 기록](../research/2026-11-17-person-api-key-for-claude-code.md). 공식 문서 인용, CLI 측정, 코드 좌표가 거기 있다.
- 코드 좌표는 `origin/main` `55c86a8b2ee5` 에서 읽었다.
- 먼저 있는 결정:
  - 설계 §4.2: ProviderAccount 는 주인(`owner`), 자격 참조(`credential_ref`), 세대(`credential_generation`), 상태를 가진다. Admin 도 다른 사람의 ProviderAccount 로 Runtime 을 만들지 못한다.
  - 설계 §5.4-5: 자격의 본문은 로그와 응답에 남기지 않는다. 연결이 끝난 것과 실제 호출이 성공한 것은 다른 사실이다.
  - 설계 §8.5: 지우기는 두 단계다. `Purge_pending` 을 기록한 뒤 지우고, `Purged` 나 `Purge_failed` 로 끝낸다. 끝내는 기록의 필드는 대상 종류를 따른다.
  - 계획 D2(2026-11-09): Keeper 턴을 시작하는 사람과 실행하는 사람은 Keeper 의 주인이다.
  - 계획 D3c(2026-11-09): 다계정에서는 다른 사람의 홈을 읽지 않는다고 증명된 방식만 쓴다. Claude Code 는 CLI 자체 도구를 끈 채로 돈다.
  - 계획 D4: 실행 표(`runtime.toml`)의 자격 증명은 호스트 계정이다. 다계정 프로세스는 그것으로 아무것도 보내지 않는다.
  - 운영자 결정(2026-11-17): 두 단계로 한다. 1단계는 Claude Code 다. 사람의 Anthropic API key 를 그 사람의 자리에 0600 파일로 두고, 지금의 턴 경로에 `ANTHROPIC_API_KEY` 로 싣는다. 2단계는 HTTP provider 의 키다.
- 비대상: 로그인 계정을 없애는 일, Runtime 공유, Codex 와 Muse 의 키, 키를 암호화해 보관하는 일.

## 읽기 전에 — 말의 뜻

- **계정**: 사람이 연결한 provider 자격 하나다. 설계의 ProviderAccount 다. 권한 로그의 기록이 주인을 정한다.
- **로그인 계정**: 공식 CLI 가 로그인을 자기 홈에 보관하는 계정이다. 지금 있는 것은 이것뿐이다.
- **키 계정**: 사람이 넣은 API key 를 MASC 가 보관하는 계정이다. 이 RFC 가 더한다.
- **계정 홈**: CLI 의 설정 폴더다. `<.masc>/accounts/<namespace>/official-clients/claude/<계정 id>` 이고, CLI 에는 `CLAUDE_CONFIG_DIR` 로 준다.
- **키 파일**: MASC 가 쓰고 MASC 가 읽는 0600 파일이다. 계정 홈 밖에 둔다.
- **확인**: 모델을 실제로 한 번 부르는 일이다. 통과하면 권한 로그에 Runtime 기록이 생기고, 그 뒤에 Keeper 에 배정할 수 있다.
- **template**: 운영자가 `runtime.toml` 에 적은 provider 항목이다. 사람의 계정은 이 항목에서 id 와 홈만 바꿔 만든다.

## 0. 요약

규칙은 하나다. **자격 증명은 그 주인의 호출에만 쓰인다.** 나머지는 이 규칙에서 나온다.

| 물음 | 규칙에서 나온 답 |
|---|---|
| 누가 넣고 누가 없애나 | 주인만, 자기 것만. Admin 도 남의 키를 넣거나 읽거나 쓰지 못한다 |
| 어디에 두나 | 주인의 namespace 아래. 다른 사람에게 주어지지 않는 자리다 |
| 언제 실리나 | 권한 판정이 그 계정을 그 요청에 허락한 뒤에만 |
| 계정이 키 계정인지 어떻게 아나 | 권한 로그의 기록에 적힌 값으로. 파일이 있는지로 짐작하지 않는다 |
| 누가 볼 수 있나 | 본문은 응답과 로그에 나가지 않는다. 주인에게도 다시 보여 주지 않는다 |

만드는 것은 다섯 가지다.

1. 권한 로그에 키 계정을 잇는 기록(`key_linked`)을 더한다.
2. 사람별 키 파일을 두는 자리와, 쓰고 읽는 함수 하나씩을 둔다.
3. 키 계정의 턴은 로그인 계정과 같은 경로로 돈다. 다른 것은 CLI 환경에 `ANTHROPIC_API_KEY` 가 실린다는 것 하나다.
4. 계정을 없애는 일은 설계의 purge 로 한다. 대상에 계정을 더한다.
5. 콘솔에 키를 넣는 칸과 계정을 없애는 단추를 둔다.

측정 두 가지가 설계를 정했다(연구 기록 §2).

- `claude auth status` 는 가짜 키도 "로그인됨"으로 답한다. 그래서 등록할 때 CLI 를 부르지 않는다. 키가 맞는지는 확인이 말한다.
- 잘못된 키로 부른 턴은 `api_error_status: 401` 로 끝난다. MASC 는 이 숫자를 이미 값으로 읽는다.

## 1. 지금 동작

### 1.1 사람의 계정은 로그인으로만 생긴다

- 사람의 route 에 키를 받는 것과 계정을 없애는 것이 없다(`server_login_http.ml:481`). 계정을 만드는 길은 로그인 시작 하나다.
- 로그인이 확인되면 권한 로그에 `{"event":"linked","provider_account_id","user_id"}` 를 쓴다(`server_setup_account_login.ml:125`).
- 계정이 어느 template 것인지는 로그인 영수증 파일의 `integration_id` 가 말한다. 턴과 확인이 이 파일을 읽는다(`server_setup_account_login.ml:412`).

### 1.2 CLI 는 자격 변수를 받지 못한다

- CLI 자식 프로세스의 환경은 허용 목록이다. 계정 홈이 선언된 CLI 는 이름 14개만 받는다. `ANTHROPIC_API_KEY` 는 빠진다(`runtime_claude_environment_projection.ml:6`).
- 환경을 만드는 곳은 `Runtime_official_account.capture` 하나다(`runtime_official_account.ml:123`). 호출자가 임의의 값을 환경에 넣지 못한다.
- `claude-code` provider 가 `credentials` 를 선언하면 거절한다(`runtime_adapter.ml:1057`).

### 1.3 사람의 비밀값을 둘 곳이 없다

- 운영자의 API key 저장소(`Runtime_setup_credentials`)는 단일 사용자 서버의 것이다. `runtime.toml` 이 파일 경로로 가리킨다.
- 다계정 프로세스는 실행 표의 API provider 를 부르지 않는다(`runtime_account_access.ml:365`, 계획 D4).

### 1.4 계정을 없애는 기록이 없다

- 권한 로그에 계정을 끄거나 지우는 기록이 없다. 턴 판정은 로그에 있는 계정을 모두 Active 로 본다(`authz_keeper_turn.mli`).
- 지우는 기록은 대화에만 있다(`authz_purge_event.mli`, 계획 S1b-3c).

## 2. 목표와 하지 않는 것

### 2.1 목표

- 초대받은 사람이 자기 Anthropic API key 를 넣고, 모델을 확인하고, 자기 Keeper 를 그 계정으로 돌린다.
- 그 키는 그 사람의 턴이 아닌 어떤 호출에도 실리지 않는다. 운영자의 호출과 다른 사람의 호출도 포함이다.
- 그 사람이 키를 없앨 수 있다. 없앤 뒤에는 서버에 그 키가 남지 않는다.
- 2단계(HTTP provider 의 키)가 같은 기록과 같은 파일을 쓴다.

### 2.2 하지 않는 것

- 키의 모양으로 종류를 맞히지 않는다. 접두어나 길이를 보지 않는다. 받는 쪽은 빈 값, 제어 문자, JSON 문서만 거절한다(`Runtime_setup_credentials.valid_secret` 과 같은 검사다).
- 키를 암호화해 두지 않는다. 운영자 결정대로 0600 파일이다. 서버 키가 같은 host 에 있으면 host 가 뚫렸을 때 막지 못한다.
- 로그인 계정을 없애는 일을 넣지 않는다. 같은 purge 기록을 쓸 수 있지만, Keychain 에 든 로그인을 지우는 일이 따로 필요하다. 이슈로 남긴다.
- 운영자의 키를 사람에게 빌려주지 않는다. 계획 D4 그대로다.

## 3. 설계

### 3.1 계정 종류는 기록에 적힌 값이다

`Authz_provider_account_event` 에 기록 하나를 더한다.

```text
{"event":"key_linked","provider_account_id":...,"user_id":...,"integration_id":...}
```

- `linked` 는 그대로 둔다. 본문의 멤버가 디스크에 굳어 있어서, 멤버를 더하면 이미 쓴 기록을 읽지 못한다.
- `integration_id` 는 template 의 id 다. 로그인 계정은 이 값을 영수증 파일에서 읽는다. 키 계정에는 로그인이 없어서 영수증도 없다. 영수증을 흉내 내지 않고 기록에 적는다. 키 계정이 무엇인지는 로그만 읽으면 안다.
- 쓸 수 있는 사람은 `linked` 와 같다. 활성인 사람이, 자기 이름으로, 한 id 에 한 번이다.
- 상태(`Authz_provider_account_state`)는 계정마다 주인과 종류를 준다. 종류는 `Login` 이거나 `Key { integration_id; generation }` 이다.

### 3.2 키 파일

자리는 `Runtime_account_home_layout` 이 정한다. 계정 홈의 경로를 정하는 그 모듈이다.

```text
<.masc>/accounts/<namespace>/api-keys/<계정 id>/<세대>
```

- 계정 홈 밖이다. 계정 홈은 CLI 가 쓰는 폴더이고, 키 파일은 MASC 가 쓰는 파일이다. 주인이 다른 것을 한 폴더에 섞지 않는다.
- 폴더는 0700, 파일은 0600 이다.
- 쓰는 순서는 옆에 임시 파일을 만들고, 권한을 0600 으로 정하고, 내용을 쓰고 sync 한 뒤, 덮어쓰지 않는 rename(`Fs_compat.rename_noreplace`)으로 놓고, 폴더를 sync 하는 것이다.
- 읽는 검사는 지금 있는 것을 쓴다. 현재 사용자의 소유, group·other 권한 없음, JSON 문서가 아님이다(`runtime_credential_selection.ml:25`).
- 경로에 세대를 넣는 이유는 §3.7 에 있다. 처음 넣은 키가 세대 1 이다.
- 읽은 값은 출력 함수가 없는 타입에 담는다. `Llm_provider.Secret.t` 와 같은 성질이다.

### 3.3 등록

`POST /api/v1/setup/accounts/key` 이다. 본문은 `{integration_id, key}` 이고, 로그인 시작과 같은 문을 지난다(브라우저 세션, CSRF 헤더, `Manage_own_provider`).

순서는 **기록 먼저, 파일 다음**이다.

1. 확인한다. 활성인 사람인가, namespace 가 있는가, template 이 키를 받는 것인가, 값의 모양이 맞는가.
2. 새 계정 id 로 `key_linked` 를 쓴다.
3. 계정 홈과 키 파일을 만든다.
4. 계정 id 와 종류를 답한다. 키는 답에 없다.

- 3이 실패하면 같은 요청이 그 계정의 purge(§3.6)를 시작해서 끝낸다.
- 2와 3 사이에 프로세스가 죽으면 키 파일이 없는 키 계정이 남는다. 그 계정은 쓸 때 `key_missing` 으로 읽힌다(§3.5). 사람은 그 계정을 없애고 다시 넣는다.
- 순서를 뒤집지 않는 이유: 파일을 먼저 쓰면, 죽었을 때 어느 기록도 가리키지 않는 키가 디스크에 남는다. 기록이 먼저면 모든 키 파일에 그것을 가리키는 기록이 있다. 그래서 purge 가 기록만 보고 키를 다 찾는다.
- 등록할 때 CLI 를 부르지 않는다. `claude auth status` 는 키를 검증하지 않는다(연구 기록 §2.2). 키가 맞는지는 확인이 말한다.
- 요청 본문과 키는 서버 로그에 쓰지 않는다.

### 3.4 키가 실리는 곳

키는 provider 선언을 따라간다. 옆길을 만들지 않는다.

1. `Runtime_account_runtime.of_template` 이 계정 종류를 받는다. 키 계정이면 template 을 복사할 때 `credentials = Some (File <키 파일 경로>)` 를 넣는다.
2. `Runtime_adapter` 는 `claude-code` provider 의 `credentials` 가 `File` 이면 받는다. 그 파일을 §3.2 의 검사로 읽어 `Runtime_official_account.capture` 에 넘긴다. `Env` 와 `Inline` 은 지금처럼 거절한다.
3. `capture` 는 허용 목록으로 환경을 만든 뒤 `ANTHROPIC_API_KEY=<키>` 를 더한다. 키를 받지 않은 계정의 환경은 지금과 같다.
4. 그 뒤는 지금 그대로다. 계정은 봉인된 채 실행 표에 있고, `Runtime_account_access.authorize` 가 요청을 허락해야 환경이 나온다(`runtime_account_access.mli`).

- `authorize` 는 사람의 턴이면 Keeper 의 주인과 계정의 주인을, 확인이면 요청한 사람과 계정의 주인을 맞춰 본다. 키 계정도 같은 판정을 지난다. 새 문을 더하지 않는다.
- 키 계정의 홈에는 로그인이 들어가지 않는다. 사람의 로그인 시작은 있는 계정을 고르지 못하고 매번 새 계정을 만든다(`server_setup_account_login.ml:152`). 키 계정의 홈으로 가는 길이 없다.
- 이 변경으로 단일 사용자 서버도 `claude-code` provider 에 파일 자격을 선언할 수 있게 된다(§6 D3).

### 3.5 확인과 턴

- 확인과 턴의 경로는 로그인 계정과 같다. `person_runtime`(`server_setup_account_login.ml:412`)이 계정 종류를 보고, 키 계정이면 template 을 기록에서, 로그인 계정이면 영수증에서 읽는다.
- 키 파일을 읽지 못하면 CLI 를 띄우지 않고 값으로 답한다. `key_missing`(파일이 없다)과 `key_unreadable`(소유나 권한이 다르다)이다.
- 확인이나 턴이 `api_error_status = Some 401` 로 끝나고 계정이 키 계정이면 답의 코드는 `key_refused` 다. 문장을 보고 가르지 않는다. 다른 상태 코드는 지금처럼 provider 의 문장을 그대로 싣는다.
- 한 계정은 한 번에 한 호출만 한다. 지금의 `one_call_of` 를 그대로 쓴다.

### 3.6 없애기

설계 §8.5 의 purge 로 한다. `Authz_purge_event.target` 에 계정을 더한다.

```text
{"type":"provider_account","owner":...,"provider_account_id":...}
```

1. 주인이 `Purge_pending` 을 쓴다. 이때부터 그 계정은 읽히지 않는다. 턴 판정은 계정 상태를 이미 사실로 받는데(`authz_keeper_turn.mli`), 지금은 늘 Active 를 넣는다. 이 기록이 있으면 그 값을 넣는다. 확인 요청도 같은 상태를 읽는다.
2. 그 계정의 호출 잠금 안에서 키 폴더와 계정 홈을 지운다. 도는 턴이 있으면 그 턴이 끝난 뒤다.
3. `Purged` 를 쓴다. 지우지 못했으면 `Purge_failed` 와 단계(`key_not_removed`, `home_not_removed`)를 쓴다.

- 멈춘 purge 는 두 곳이 끝낸다. 주인이 다시 없애면 이어서 끝낸다. 대화 purge 가 지금 이렇게 한다(`server_keeper_conversation_purge.mli`). 서버가 시작할 때도 남은 계정 `Purge_pending` 을 끝낸다(§8.5-5). 대상이 비밀값이라, 주인이 다시 누를 때까지 디스크에 두지 않는다.
- 지우지 못한 계정은 목록에 「지우지 못함」으로 보인다. 지우는 중이거나 지운 계정은 보이지 않는다. 대화 purge 의 세 상태와 같다.
- 끝내는 기록의 필드는 대상을 따른다(§8.5-7). 계정에는 `vendor_copy` 가 없다. MASC 가 vendor 쪽에 만든 사본이 없기 때문이다.
- 키는 vendor 에서 계속 유효하다. MASC 는 그것을 끌 수 없다. 화면이 이 사실을 말한다(§3.8).
- 그 계정으로 만든 Runtime 기록은 남는다. 계정이 읽히지 않으니 그 Runtime 의 턴은 거절된다.
- 계정 홈에는 CLI 가 쓴 대화 기록이 있다(연구 기록 §2.2). 같이 지워진다.

### 3.7 바꾸기

키를 바꾸는 기록 `key_replaced` 를 둔다. 넣을지는 §6 D1 이 정한다. 넣지 않아도 경로의 세대 자리는 처음부터 둔다. 나중에 경로를 바꾸면 이미 넣은 키를 옮기거나 버려야 하기 때문이다.

```text
{"event":"key_replaced","provider_account_id":...,"user_id":...,"generation":...}
```

- 순서는 등록과 같다. 기록을 먼저 쓰고, 새 세대의 파일을 쓰고, 그 폴더의 다른 파일을 지운다.
- 읽는 쪽은 상태가 말하는 세대의 파일만 연다. 그래서 기록과 파일이 어긋난 채로 턴이 도는 순간이 없다. 기록만 쓰고 죽었으면 `key_missing` 이다.
- 이 기록은 설계 §8.2 의 "credential 교체" 사건이다. purge 시작과 같이 바깥 저장소에 의도를 먼저 쓴다.
- Runtime 기록은 그대로 둔다. 새 키로 그 모델을 못 부르면 그 턴이 provider 의 상태 코드로 끝난다.

### 3.8 응답과 화면

- 계정 목록 응답이 계정마다 종류를 준다. `login` 이거나 `key` 다. 키 계정이면 키 파일을 읽을 수 있는지도 준다. 키의 글자는 한 자도 주지 않는다.
- 구독 목록 응답이 구독마다 연결하는 방법을 준다. `login`, `key` 가운데 받는 것이다. 1단계에서 `key` 를 받는 것은 `claude-code` template 이다.
- 콘솔은 키를 받는 구독에 입력 칸을 보인다. 칸 옆에 네 가지를 적는다.
  - 키는 이 서버에 파일로 저장되고, 서버를 운영하는 사람은 그 파일을 읽을 수 있다.
  - 저장한 뒤에는 다시 보여 주지 않는다.
  - 쓴 만큼 그 키의 조직에 과금된다.
  - 여기서 없애도 키는 Anthropic 에서 계속 유효하다. 못 쓰게 하려면 Console 에서 폐기한다.
- 키 계정의 카드에는 종류와 「없애기」가 있다. `key_refused` 는 "키가 거절됐어요"로 보인다.

### 3.9 2단계: HTTP provider 의 키

1단계가 만든 기록과 파일을 그대로 쓴다. 다른 것은 쓰는 쪽이다.

- `key_linked` 의 `integration_id` 가 HTTP provider template 을 가리킨다. 계정 홈은 없다. CLI 가 없기 때문이다.
- `Runtime_account_access` 에 사람의 API 계정을 더한다. 지금 `authorize_api` 는 호스트 자격만 알고, 다계정에서는 거절한다. 사람의 키로 봉인한 설정은 그 주인의 요청에만 풀린다. 판정은 계정 홈과 같다.
- template 에 운영자의 자격이 적혀 있어도 사람의 계정에는 따라가지 않는다. 계획 D4 는 그대로다.
- 사람의 Keeper 가 Agent_core 엔진으로 도는 경로가 먼저 있어야 한다. 그 설계는 이 RFC 밖이다. 2단계의 층은 그 설계가 병합된 뒤 이 문서에 더한다.

### 3.10 고르지 않은 길

| 길 | 고르지 않은 이유 |
|---|---|
| `apiKeyHelper` 로 넘기기 | 설정 층이 있어야 읽힌다. MASC 는 CLI 를 설정 층 없이 띄운다. 키를 찍는 프로세스도 하나 더 생긴다 |
| 로그인 영수증에 키 계정을 적기 | 영수증은 로그인 흐름이 남기는 복구용 파일이다. 로그인이 없는 계정의 등록부로 쓰면 로그와 파일 두 곳이 같은 사실을 가진다 |
| `linked` 에 종류 멤버를 더하기 | 이미 쓴 기록을 읽지 못한다 |
| 키를 실행 표에 `Inline` 으로 두기 | 실행 표는 여러 곳이 읽는다. 비밀값을 표에 두지 않는다 |
| 등록할 때 `auth status` 로 확인하기 | 가짜 키도 통과한다. 통과가 아무것도 말하지 않는다 |
| 파일을 먼저 쓰고 기록하기 | 죽으면 기록 없는 키가 남는다. 그것을 찾으려면 기동 때 폴더를 훑어야 한다 |

Console 로그인(`claude auth login --console`)은 고르지 않은 길이 아니라 옆에 있는 길이다. §6 D2 에 있다.

## 4. 남는 위험

- 서버를 운영하는 사람은 모든 사람의 키를 읽을 수 있다. 파일이 서버 사용자의 것이기 때문이다. 로그인 계정의 자격도 같다. 화면에 적는다.
- CLI 자식 프로세스의 환경에 키가 있다. 같은 사용자로 도는 프로세스는 그 환경을 읽을 수 있다. 다계정에서 사람의 턴은 CLI 자체 도구를 끄고 돈다(계획 D3c). 이 전제가 깨지면 키도 로그인 자격도 같이 노출된다.
- 계정 폴더를 백업하면 키가 백업에 들어간다.
- 관리 설정이 환경 변수 키를 막는 장비에서는 키 계정이 돌지 않는다. 확인이 실패로 끝난다. 그때의 답 모양은 재지 못했다.

## 5. 증명

시험은 경계만 본다. 문장은 보지 않는다.

- **기록**: `key_linked` 와 계정 purge 본문이 쓰고 읽은 뒤 같다. 멤버가 다르거나 순서가 다르면 거절한다. 남의 이름으로, 비활성인 사람이, 같은 id 로 두 번 쓰면 거절한다.
- **파일**: 놓인 파일이 0600 이고 그 사람의 namespace 아래다. 같은 세대에 두 번 쓰면 거절한다. 소유나 권한이 다른 파일은 읽지 않는다.
- **환경**: 가짜 CLI 가 받은 `ANTHROPIC_API_KEY` 의 digest 를 남긴다. 키 계정이면 저장한 키의 digest 와 같고, 로그인 계정이면 변수가 없다.
- **주인**: 다른 사람의 요청과 운영자의 호출은 프로세스가 뜨기 전에 거절된다. 가짜 CLI 가 불리지 않았음을 본다.
- **새는 곳**: 등록·목록·확인의 응답과 서버 로그에 시험용 키의 글자가 없다.
- **없애기**: `Purge_pending` 뒤의 턴은 거절된다. `Purged` 뒤에는 키 폴더와 계정 홈이 없다. 지우는 도중에 멈춘 것은 재기동이 끝낸다.
- **401**: 가짜 CLI 가 `api_error_status: 401` 로 답하면 확인의 답이 `key_refused` 다.

실제 키로 재는 것은 구현의 마지막 층에서 한다. 과금이 생기므로 운영자가 키를 넣는다.

- 등록 → 모델 확인 → Keeper 배정 → 두 턴 → 없애기.
- `stream-json` 출력에서 잘못된 키가 어떻게 오는지.
- Linux 한 대.

## 6. 열린 결정

정석 쪽을 먼저 적는다.

### D1. 키 바꾸기를 1단계에 넣는가

- **추천: 넣는다.** 등록과 없애기 다음 층이다.
- 근거: 키가 샜을 때 사람이 할 일은 바꾸는 것이다. 설계의 ProviderAccount 에 세대가 이미 있다.
- 대가: 기록 하나와 세대 규칙(§3.7)이 는다.
- 넣지 않으면: 바꾸려면 없애고 다시 넣는다. 그 계정의 모델 확인과 Keeper 배정을 다시 해야 하고, CLI 가 계정 홈에 둔 대화 기록이 지워진다.

### D2. Console 로그인을 같이 넣는가

- **추천: 재 본 뒤 따로 넣는다.** 이 RFC 의 층에 넣지 않는다.
- 근거: `claude auth login --console` 은 MASC 가 키를 만지지 않는 길이다. 하지만 그 자격이 계정 홈 안에 놓이는지, `auth status` 가 무엇을 답하는지 재지 않았다. 문서는 키 없는 Console 로그인이 설정 폴더 밖에 저장된다고 말한다(연구 기록 §1).
- 대가: Console 계정이 있는 사람도 그때까지는 키를 만들어 넣는다.
- 키 문자열만 받은 사람은 이 길을 쓰지 못한다. 그래서 이 RFC 를 대신하지 않는다.

### D3. 단일 사용자 서버의 `claude-code` provider 도 파일 자격을 선언할 수 있게 되는 것

- **추천: 그대로 둔다.**
- 근거: §3.4 의 길은 provider 선언 하나다. 사람의 계정에서만 받게 하려면 adapter 가 선언의 출처를 알아야 하고, 갈래가 하나 는다.
- 대가: 운영자가 로그인이 있는 홈에 키를 같이 선언하면 키로 과금된다. CLI 가 `-p` 에서 환경 변수 키를 먼저 쓰기 때문이다. 가이드에 한 줄 적는다.

### D4. 키를 구분하게 해 주는 표시

- **추천: 키의 글자를 보여 주지 않는다.** 계정은 종류와 id 로 구분한다.
- 근거: 끝자리를 보여 주려면 키의 일부를 응답에 싣거나 따로 저장해야 한다.
- 대가: 한 구독에 키를 둘 넣은 사람은 어느 것이 어느 키인지 화면에서 알지 못한다.
