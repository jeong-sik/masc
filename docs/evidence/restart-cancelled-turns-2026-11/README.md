# 서버를 내릴 때 끊기는 Keeper 턴 (2026-11-01 ~ 11-05, UTC)

서버를 내리면(SIGTERM) 도는 Keeper 턴이 끊겨요. 이 폴더는 세 가지를 세요.

- 몇 개가 끊기고, 같은 턴을 몇 번까지 되풀이해서 끊는지
- 끊기기 전에 쌓은 대화가 재시작 뒤 첫 요청에 실려 오는지, 이미 한 호출을 되풀이하는지
- 끊긴 채팅 작업이 다시 들어오는지

`measure_restart_cancelled_turns.py` 가 시스템 로그(`.masc/logs`), 비용 원장(`.masc/costs`), 도구 호출 원장(`.masc/tool_calls`)을 읽기만 해요.
채팅 작업은 스크립트 밖의 SQL 로 세요(「채팅 작업은 다시 오나」).
읽은 때는 2026-11-06T00:04Z 예요.

숫자는 시간과 토큰이에요. 끊긴 턴이 얼마나 돌았는지는 비용 원장의 모델 요청 시각으로 재요. 도구만 돌던 시간은 들어 있지 않아요.

## 어떻게 끊기나

2026-11-05 서버 로그에서 가져온 한 번의 종료예요(시각은 UTC).

- 02:17:34 `Received SIGTERM, shutting down gracefully (timeout=10s, hard_exit=124)`
- 02:17:37 `code-reviewer-father` 와 `code-reviewer-brother` 가 `keeper_chat_error ... Keeper owner stopped the active turn` 을 써요. 코드는 `lib/keeper/keeper_owner.ml` 의 `Stop_active_child` 가지예요.
- 02:17:38 `Keeper owners and workspace observation stopped (3.45s)`. Keeper 26명이 같은 초에 `running → draining → stopped`(`drain_complete`)로 가요.
- 02:17:42 `Shutdown complete`. 다음 부팅의 `listening_banner.end` 는 02:19:09 예요.

턴이 끝나길 기다리는 단계는 로그에 없어요. 이 종료에서는 신호를 받고 4초 만에 owner 가 모두 멈췄어요.

## 턴 번호는 어떻게 정해지나

- 턴을 시작할 때 `keeper_turn_id = total_turns + 1` 로 정해요(`lib/keeper/keeper_unified_turn.ml`).
- `total_turns` 는 턴이 성공이나 실패로 끝나 결과를 기록할 때 올라가요(`lib/keeper/keeper_unified_metrics_result.ml`, `lib/keeper/keeper_unified_metrics_failure.ml`, `lib/keeper/keeper_turn_spend_commit.ml` 의 `count_turn`).
- 서버가 턴을 끊으면(`Stop_active_child`) 결과를 기록하지 않고 끝나요. 그 Keeper 의 다음 턴이 같은 번호를 받아요.

그래서 아래 「같은 번호로 이어졌다」는 "그 Keeper 가 재시작 뒤 다음 턴을 돌렸다"는 뜻이에요. 끊긴 일을 이어 했다는 뜻이 아니에요.
같은 번호가 다시 안 온 턴이 실패 경로로 번호를 올린 경우인지는 확인하지 못했어요.

## 채팅 작업은 다시 오나

서버가 턴을 끊으면 그 턴이 맡은 채팅 작업(Keeper 마다 `chat-operations.sqlite3` 의 `operations`)이 `failed` / `Turn_cancelled` / `Keeper owner stopped the active turn` 으로 끝나요.
11-01 00:00 ~ 11-05 24:00 UTC 에 118개이고, 한 줄도 빠짐없이 SIGTERM 60초 안에 끝났어요. 사람이 중단한 3개(`operator interrupted the turn`)는 뺐어요.

| 보낸 쪽 | 끊긴 작업 | 같은 보낸이·같은 입력(`admission_digest`)으로 나중에 다시 들어온 작업이 있는 작업 |
|---|---:|---:|
| 다른 Keeper 가 위임(`sender_keeper` 있음) | 39 | 0 |
| MCP 에이전트(`channel = agent`, 보낸 Keeper 없음) | 50 | 0 |
| 대시보드(TUI 등) | 29 | 7 (다시 들어온 작업 10개: 성공 4, 실패 6) |

- 위임한 Keeper 는 `failed` 를 받아요. 위임받은 Keeper 의 다음 턴이 같은 일을 이어 하는지는 이 폴더가 따라가지 않아요.
- 같은 입력일 때만 "다시 들어왔다"고 세요. 문장을 바꿔 다시 보낸 경우는 안 잡혀요. 끊긴 작업의 `input_json` 이 118줄 모두 비어 있어서 입력 문장으로는 견줄 수 없어요.
- 다시 들어온 7개는 모두 사람이 보낸 대시보드 작업이에요. 위임과 MCP 작업은 다시 안 들어왔어요.

## 종료를 기다리면 얼마나 끝났을까

끊긴 턴이 e초 돌았을 때, 끊기지 않은 다른 턴 중 e초보다 길었던 턴을 모아요. 그중 길이가 e + D초 이하인 턴의 몫이에요. 끊긴 턴 전체의 평균을 적어요.

| 종료가 D초 더 기다렸다면 | 120초 열 | 600초 열 | 1800초 열 |
|---|---:|---:|---:|
| 60초 | 8.6% | 8.2% | 7.9% |
| 300초 | 30.8% | 29.9% | 29.3% |
| 900초 | 56.2% | 55.6% | 54.8% |

턴 길이를 마지막 모델 요청 끝에서 재서, 실제 턴은 이보다 늦게 끝나요. 위 값은 상한이에요.

## 이 값으로 판단할 수 있는 것

- 종료 신호 뒤에 60초를 기다려도 끝나는 끊긴 턴은 상한이 8.2% 예요. 900초를 기다려도 상한이 절반을 조금 넘어요(55.6%). 대기 시간을 늘리는 방법은 얻는 몫이 작고, 종료마다 그만큼 늦어져요.
- 처음 끊긴 것만 세면 끊긴 턴이 62개, 27.0시간(3.5%)이에요. 같은 턴을 다음 종료가 또 끊은 것까지 세면 83번, 37.4시간(4.9%)이에요.
- 재시작 뒤 첫 요청은 끊기기 전에 쌓은 대화를 대부분 싣고 와요(17턴 중 15턴). 종료 앞과 같은 호출은 거의 되풀이하지 않아요(1.25%). 끊기기 전의 도구 결과가 재시작 뒤에도 남는다는 뜻이에요.
- 시간 손실은 범위로만 말할 수 있어요. 600초 열에서 11.0시간(1.43%) ~ 42.2시간(5.49%)이에요. 어디에 가까운지는 이 폴더가 못 가려요.

## 이 숫자가 말하지 않는 것

- 끊긴 턴은 로그에 이름이 없어서 마지막 모델 요청으로 추정해요. 세 열의 차이가 그 추정의 폭이에요. 턴이 막 시작해서 요청이 아직 없었다면 앞 턴이 끊긴 턴으로 읽혀요. 서브에이전트가 같은 Keeper 의 시스템 로그 `turn_id` 와 견줘 보니 600초 열 62개 중 60개가 맞고 2개는 한 칸 낮은 번호였어요(이 견줌은 스크립트에 없어요).
- 「같은 번호로 이어졌다」는 끊긴 일이 이어졌다는 증거가 아니에요(「턴 번호는 어떻게 정해지나」). 도구 호출 원장의 `task_id` 로도 못 가려요. 이어진 턴 48개 중 앞뒤 모두에서 `task_id` 를 읽을 수 있는 턴은 20개이고 전부 같은 값이에요. 그런데 끊김에서 10분 이상 떨어진 이웃 턴 5,379쌍(양쪽에 `task_id` 가 있는 쌍)의 99.5% 가 같은 `task_id` 를 가져요. 20개가 모두 같아도 이어짐의 증거가 안 돼요. 27개는 앞뒤 어디에도 `task_id` 가 없어요(서브에이전트가 센 값이고 스크립트에 없어요).
- 끊기기 전 대화가 재시작 뒤 요청에 실려 오는 것과, 그 대화를 보고 같은 일을 이어 하는 것은 달라요. 종료 뒤 호출이 앞 호출을 거의 되풀이하지 않는 것은 이어 한다는 쪽에도 다른 일을 한다는 쪽에도 맞아요.
- 이어지지 않은 턴이 새 번호의 턴에서 다시 이루어졌는지는 몰라요. 같은 일을 했는지 따라가려면 턴이 받은 큐 행을 이어야 해요.
- 재시작 뒤 첫 요청의 캐시 손실은 이 폴더가 재지 않았어요.
- 되풀이를 "같은 도구 + 같은 입력 지문"으로 세요. 입력이 조금 다른 같은 일은 되풀이로 안 세요.
- 로그 문장(`Received SIGTERM`, `Keeper owner stopped the active turn`)에 기대요. 문장이 바뀌면 `shutdowns` 가 0 이 돼요. 그때는 스크립트 위쪽의 `SHUTDOWN_MARKER`, `STOP_MARKER` 를 로그와 맞춰요.
- 창 첫날 이전에 시작한 턴은 왼쪽이 잘려요.

채팅 작업 표는 `sqlite3` 로 Keeper 마다 센 뒤 합쳐요. 아래 출력은 `보낸 쪽 끊긴 작업 다시 들어온 작업이 있는 작업` 순서예요.

```bash
sql="select case when json_extract(source_json,'\$.sender_keeper') is not null then 'keeper'
  when json_extract(source_json,'\$.channel')='agent' then 'mcp' else 'dashboard' end,
  count(*), sum(exists (select 1 from operations r where r.admission_digest=c.admission_digest
    and r.operation_id<>c.operation_id and r.created_at>=c.completed_at))
  from operations c where state='failed' and failure_kind='Turn_cancelled'
  and failure_detail='Keeper owner stopped the active turn'
  and completed_at>=cast(strftime('%s','2026-11-01 00:00:00') as integer)
  and completed_at<cast(strftime('%s','2026-11-06 00:00:00') as integer) group by 1"
for db in ~/me/.masc/keepers/*/chat-operations.sqlite3; do
  sqlite3 -readonly "$db" "$sql" 2>/dev/null || true
done | awk -F'|' '{n[$1]+=$2; r[$1]+=$3} END {for (k in n) print k, n[k], r[k]}' | sort
# dashboard 29 7
# keeper 39 0
# mcp 50 0
```

테이블이 없는 Keeper 의 DB 는 건너뛰어요(44개 중 43개에 `operations` 가 있어요).
