# RFC: Goal 을 끝내면 Candle 을 받고, 초상화 장신구를 산다

- 범위: Candle 원장, Goal 완료 때의 지급, 기한을 넘겼을 때의 감액, 기여자 분배(논공행상), 장신구 구매. Goal 의 phase 흐름과 검증(Verifying)은 바꾸지 않는다.
- 근거 기준: `origin/main` = `f632782f8c` (2026-09-29). 줄 번호는 이 커밋 기준이다.
- 표시: **[사실]** 은 코드에서 확인한 것이다. **[제안]** 은 이 RFC 가 정하려는 것이다. **[미정]** 은 운영자 답이 필요하다.

## 1. 무슨 일이 있었나

2026-09-29 운영자가 Goal 을 끝낼 때마다 보상을 주고 싶다고 했다. 화폐 단위는 Candle 이고 `0.5 Candle` 같은 소수가 있다. 끝난 뒤에는 논공행상으로 나눈다. 대화에서 정해진 것은 다음과 같다.

| 항목 | 결정 |
|---|---|
| 총액 책정 | standalone LLM agent lane 이 한다 |
| 분배 | 심판(같은 종류의 lane)이 증거를 보고 정한다 |
| 기한 초과 | 시간이 지날수록 원래 보상에서 일정 %가 줄어든다. 감액률과 바닥은 TOML 로 정한다 |
| 받는 쪽 | keeper 만 받는다. 사람 owner 몫은 없앤다 |
| 쓰는 곳 | keeper 가 직접 Candle 을 내고 초상화 장신구를 산다 |
| 가격표 | TOML |
| 물가 | 우선 결정론적 공식. 나중에 바꿀 수 있게 함수 하나로 모은다 |
| 이번 범위 밖 | Tool·Skill·모델 구입, 현상금 Task (2단계 후보) |

## 2. 지금 코드에서 확인한 것

- **[사실]** `Completed` 는 끝이 아니다. `Completed, Reopen -> Executing` 이다 (`lib/goal/goal_phase.ml:186`). 완료 때 지급하기만 하면 재오픈 뒤 재완료마다 다시 지급된다.
- **[사실]** Goal 에는 `owner : owner` 하나뿐이고 기여자 기록이 없다 (`lib/goal/goal_store.mli:33-46`). 분배의 근거는 다른 곳에서 가져와야 한다.
- **[사실]** Goal 스키마는 닫혀 있다. 모르는 필드가 있는 행은 읽히지 않는다 (`goal_store.mli` 머리 주석). Goal 레코드에 Candle 필드를 넣지 않는다.
- **[사실]** `due_date : string option` 이 있고 overdue 판정과 알림이 이미 있다 (`goal_store.mli:50`, `notified_overdue_key`).
- **[사실]** 초상화 몸은 keeper 이름에서 나오고 저장하지 않는다. 장신구도 이름에서 시작 아이템이 나온다. 슬롯은 `face`, `neck`, `head`, `hand`, `base` 다섯이고 각각 닫힌 variant 다 (`lib/keeper_portrait/keeper_portrait_look.mli:58-70`). 전부 합쳐 20개 안팎이다.
- **[사실]** 모델이 하는 독립 작업은 `Standalone_lane.t` 의 생성자 하나이고 `[runtime.exact_output_lanes.<id>]` 표를 가진다 (`lib/runtime/standalone_lane.mli`). 생성자를 더하면 그것을 매칭하는 모든 곳이 컴파일 오류를 낸다.

## 3. 설계

### 3.1 원장

**[제안]** Candle 은 `.masc/candle-ledger.jsonl` 에 덧붙이기만 하는 이벤트로 남긴다. 금액은 정수 `milli-candle` 이다 (`1 Candle = 1000`). 소수 계산은 하지 않고, 나눌 때 남는 나머지는 규칙 하나로 정한다(3.4).

| 이벤트 | 담는 것 |
|---|---|
| `Issued` | goal_id, 기준 총액, 책정 lane 의 run id, 시각 |
| `Awarded` | goal_id, keeper, 실제 지급액, 감액 전 몫, 감액률 적용 결과 |
| `Purchased` | keeper, 아이템, 낸 금액 |

- 잔액은 이벤트를 접어서 계산한 파생값이다. 따로 저장하지 않는다.
- `Purchased` 에는 그 시점에 낸 금액을 적는다. 가격 공식이 나중에 바뀌어도 과거 기록은 그대로다.
- 원장은 사실만 기록한다. 다음 행동을 시키거나 막지 않는다.

### 3.2 지급 시점과 재오픈

**[제안]** Goal 이 처음 `Completed` 가 될 때 한 번 지급한다. 멱등 키는 `goal_id` 다.

- 재오픈 뒤 다시 `Completed` 가 되어도 추가 지급이 없고 회수도 없다.
- `Dropped` 로 끝난 Goal 은 지급액이 0이다. 원장에 `Awarded` 를 남기지 않는다.

이유: 회수 규칙을 만들면 이미 쓴 Candle 때문에 잔액이 마이너스가 될 수 있고, 그 처리 규칙이 또 필요하다. 재오픈해서 고친 Goal 은 처음 받은 몫을 그대로 가진다. 처음 완료가 부실했던 경우의 손해는 받아들인다.

### 3.3 기한 초과 감액

**[제안]** 지급액 = 몫 × max(바닥, 1 − 감액률 × 초과 시간). 초과 시간은 `due_date` 와 완료 시각의 차이다. `due_date` 가 없으면 감액하지 않는다.

- 선형이다. 복리 방식(남은 액의 %씩)은 쓰지 않는다. 사람이 얼마나 깎였는지 바로 계산할 수 있어야 한다.
- 감액률과 바닥은 TOML 에서 읽고, 값이 없으면 로드 에러다. 코드에 기본값을 두지 않는다.
- 시간 판정은 날짜 비교라서 모델이 정하지 않는다.

단위는 초과 시간당이고 초기 설정값은 1%다(운영자 결정). 이 값은 TOML 에 적는 초기 설정이고 코드 기본값이 아니다. 기준액이 10 Candle 이면 초과 10시간에 9, 50시간에 5, 100시간에 0이 된다. 그래서 바닥값이 없으면 4일 남짓 늦은 Goal 은 보상이 0이다. 바닥의 초기 설정값은 기준액의 20%이고, 초과 80시간에 도달한다. 이 값도 TOML 이다. 짧은 Goal 과 긴 Goal 에 같은 시간당 %를 쓰는 문제는 위험(6장)에 둔다.

### 3.4 총액 책정과 분배

**[제안]** 새 standalone lane 생성자 `Candle_appraiser` 하나를 더한다.

- 책정(얼마짜리인가): 일의 난이도가 근거다. Goal 의 제목, metric, target, priority 와 그 시점 비용 데이터를 입력으로 총액(milli-candle)을 낸다.
- 분배(누가 얼마씩): 기여가 근거다. 아래 세 가지를 입력으로 keeper 별 비율을 낸다.
  1. 결정론적 사실: Goal 에 연결된 Task(`Workspace_goal_index`)와 그 담당자, Task 의 완료 여부, Goal 검증에 제출된 증거(`submitted_evidence`).
  2. 산출물: 머지된 PR 과 그 작성자.
- 1단계는 이 둘만 인정한다(운영자 결정: 최소한으로 시작). 아래는 넣지 않는다.
  - 운영자 평가: 지급 흐름에 사람이 끼지 않게 하려는 결정이다.
  - board 논의: board 글에는 Goal 이나 Task 로 이어지는 필드가 없다(`lib/board_types/board_types.mli`에 `goal_id`, `task_id` 없음). 연결이 없으면 어느 Goal 의 논의인지 모델이 추측해야 하고, 글을 많이 쓴 쪽이 유리해진다. board 를 인정하려면 글이 Goal 에 붙는 구조가 먼저 필요하다.
  - 리뷰만 한 keeper 의 몫: 결정론적 근거가 없다.
- 난이도와 기여는 다른 질문이다. 난이도는 총액에, 기여는 분배에만 쓴다. 한 곳에 섞으면 어려운 일을 맡은 keeper 가 두 번 보상받는다.
- 책정과 분배는 한 lane 이 요청 종류 두 개로 처리한다(운영자 결정).
- Goal 에 연결된 Task 가 없으면 분배 근거가 없다. 이때는 owner keeper 가 전액을 받는다. owner 가 `Unknown_owner` 이면 지급하지 않고 실패로 남긴다.

경계:

- 모델이 내는 것은 비율과 총액 제안뿐이다. 금액 계산, 나머지 처리(가장 큰 몫에 더한다), 감액, 원장 기록은 결정론적 코드가 한다.
- 비율의 합이 1이 아니거나 모르는 keeper 가 들어 있으면 지급하지 않고 실패로 남긴다. 모르는 값을 편한 기본값으로 바꾸지 않는다.
- 모델이 낸 숫자가 곧 화폐 값이 된다는 점은 위험이다(6장).

사람이 없을 때의 실패 처리:

- lane 호출이 실패하거나 응답이 검증을 통과하지 못하면 같은 요청을 다시 보낸다. 재시도 횟수와 간격은 TOML 에서 읽는다.
- 재시도가 끝나도 안 되면 그 Goal 의 지급은 `Pending` 으로 원장에 남고 TUI 에 보인다. 균등 분배 같은 대체 규칙으로 지급하지 않는다. 대체 규칙이 있으면 lane 이 실패해도 돈이 나가서 실패가 드러나지 않는다.
- `Pending` 은 다음 지급 주기에 다시 시도한다. 사람의 확인을 기다리지 않는다.
- 운영자는 원장과 `Pending` 목록을 볼 수 있다. 보는 것뿐이고 승인 절차는 없다.

운영자가 하는 일은 TOML 값(감액률, 바닥, 가격표, 재시도)을 고치는 것뿐이다.

### 3.5 가격표와 물가

**[제안]** 아이템 가격은 TOML 표에 둔다. 카탈로그의 모든 아이템에 가격이 있어야 하고, 하나라도 빠지면 로드 에러다. 새 아이템을 추가하는 변경이 가격 없이는 컴파일되거나 로드되지 않게 한다.

물가는 함수 하나로 모은다.

```
price : item -> economy -> milli_candle
```

- 처음 구현은 `기준가 × f(유통 총량 ÷ keeper 수)` 이고, 기준가와 상하한을 TOML 에 둔다.
- 이 함수 하나만 바꾸면 물가 판정 lane 으로 옮길 수 있다. 다른 곳은 값을 받아서 쓰기만 한다.

### 3.6 구매와 착용

**[제안]** keeper 가 직접 사고 착용한다. 이를 위해 keeper 도구가 필요하다.

- 소유와 착용 상태는 원장의 `Purchased` 에서 파생한다. 착용은 별도 상태다.
- 초상화 렌더러는 지금 이름에서만 장신구를 정한다. 소유한 아이템이 있으면 그것을 우선하도록 입력을 늘린다. 몸은 바꾸지 않는다.
- 카탈로그가 유한하므로 다 사면 쓸 곳이 없다. 이 점은 받아들이고 2단계(현상금, 모델 변경 요청)에서 다룬다.

### 3.7 keeper 에게 Candle 을 알리는 것

**[사실]** 프로젝트 지침은 행동을 유도하거나 강제하는 장치를 기본적으로 추가하지 않는다고 한다.

**[제안]** 이번에는 예외로 둔다. keeper 는 잔액과 가격을 알고 직접 산다. 대신 범위를 좁힌다.

- Candle 로 살 수 있는 것은 장신구뿐이다. 일을 하는 능력(도구, 스킬, 모델)은 사지 못한다.
- 그래서 가난해도 Goal 을 못 끝내는 일은 생기지 않는다.
- 지급과 감액 규칙은 keeper 프롬프트에 넣지 않는다. keeper 는 자기 잔액과 가격표만 안다.

## 4. 하지 않는 것

- Goal 레코드에 Candle 필드를 넣지 않는다.
- Candle 로 도구, 스킬, 모델, 예산을 사지 않는다(2단계 후보).
- 사람 owner 의 몫을 만들지 않는다.
- 옛 Goal 에 대한 소급 지급을 하지 않는다. 원장은 비어 있는 상태로 시작한다.
- 마이너스 잔액을 만들지 않는다.

## 5. 구현 순서

1. 원장 타입과 접기(fold). 잔액 계산. 단위 시험.
2. 감액 계산. TOML 로드(값 없으면 에러). 단위 시험.
3. `Candle_appraiser` lane: 요청·응답 타입, 비율 검증. 하네스로 판정 재현성을 재는 시험.
4. Goal `Completed` 진입 지점에서 한 번 지급. 재오픈 시험.
5. 가격 함수와 구매 도구, 초상화 입력.
6. TUI·대시보드 표시.

배포: 새 TOML 키가 생기므로 바이너리를 먼저 배포하고 그 뒤에 live 파일을 고친다. 모르는 키는 로드 에러다.

## 6. 위험

- **모델 판정이 곧 화폐다.** 책정과 분배가 모델 출력이라서 같은 Goal 이 다른 금액을 받을 수 있다. 완화: 모델은 비율만 내고 계산은 코드가 하며, 하네스로 같은 입력의 분산을 잰다. 분산을 재지 않고는 3단계를 머지하지 않는다.
- **keeper 가 증거를 꾸밀 수 있다.** 분배가 board 글과 PR 을 근거로 하므로 글을 많이 쓰는 쪽이 유리하다. 완화: 심판 입력에 keeper 자기 서술이 아닌 결정론적 증거(PR 머지, 검증 결과)를 우선한다. 완전한 해결은 아니다.
- **유한한 소비처.** 20개를 다 사면 Candle 이 쓸모없다.
- **짧은 Goal 의 감액.** 시간당 감액률이 짧은 Goal 에 과하게 작동한다(3.3).
- **워크어라운드 자가 점검.** 이 RFC 에는 텔레메트리만 남기는 항목, 문자열 분류기, N-of-M 패치, cap·dedup·repair 가 없다. 멱등 키는 중복 방지 장치이지만 증상 억제가 아니라 지급이 한 번이라는 계약이다.

## 7. 미정 항목

1. board 논의와 리뷰를 기여로 인정할지. board 글이 Goal 에 붙는 구조가 생긴 뒤에 다시 다룬다.
2. 바닥 20% 가 맞는 값인지. 실제 운영에서 Goal 의 기한 길이 분포를 본 뒤 TOML 에서 조정한다.

2단계(현상금 Task, keeper 의 모델 변경 요청, Tool·Skill 구입)는 이 RFC 에서 정하지 않는다. 1단계를 운영한 뒤 별도 RFC 로 다룬다.
