# 다계정 프로세스가 Keeper 엔진을 띄우고, 엔진은 사람의 Keeper 를 그 사람의 계정으로 돌린다

- 이슈: #52989
- 사실의 근거: [연구 기록](../design/people-into-a-running-installation.md) §10~§14. main `1805632f31f6` 에서 읽었다. 띄워 보지 않았다.
- 아래에서 "설계"는 다계정 OIDC·Runtime 권한 설계(#46428), "계획"은 그 구현 계획(#46469)이다.
- 연구 기록 §8 의 빈 곳 넷 가운데 ①(엔진을 띄우는 층)과 ②(이름과 주인을 잇는 규칙)를 정한다. ③(Board)과 ④(경로마다 누구의 것을 읽는지)는 정하지 않는다.
- **정한 데까지**: 틀(§3.1~§3.3), 이음매가 지킬 것(§3.4, §3.5), 사람의 Runtime 을 두는 자리, 끝 까닭을 드는 타입. 남은 것은 둘이다(§6 의 6, 7). 사용자가 정할 것이 다섯이다(§6).

## 읽기 전에 — 말의 뜻

| 말 | 뜻 |
|---|---|
| 엔진 | 단일 사용자 서버가 띄우는 Keeper 실행부 |
| 계정 서버 | 다계정 boot 가 띄우는 서버. 사람, 로그인, 구독, 사람의 Keeper 기록이 여기에 있다 |
| 로그 | 권한 로그 `authz.jsonl` |
| 엔진 이름 | 엔진이 Keeper 를 찾는 이름. 이 RFC 가 새로 정한다 |
| 정의 | 엔진이 Keeper 하나를 띄우려고 읽는 TOML 파일과 실행 기록 |
| 실행 표 | 엔진이 Runtime 과 Keeper 의 배정을 읽는 전역 표 |
| 판정 | `Runtime_account_access.authorize`. CLI 가 어느 계정에서 시작해도 되는지 답한다 |
| 계정의 호출 | 한 계정에서 한 번에 하나만 도는 호출 |
| 이음매 | 엔진이 운영자 한 사람을 전제로 만든 타입. 사람이라는 축을 넣어야 하는 자리다 |

## 0. 요약

**엔진이 Keeper 를 이름으로 찾는 방식은 그대로 두고, 그 이름과 정의와 Runtime 이 로그에서 오게 한다.**

- 다계정 boot 는 계정 서버와 엔진을 한 프로세스에 띄운다. 계정 접근 값은 `Multi_account` 하나다.
- 엔진이 읽는 것은 셋이다. 정의, Keeper 의 Runtime, 판정이다. 셋이 로그에서 온다.
- 로그가 권한이다. 정의와 Runtime 값은 누구의 Keeper 인지 정하지 않는다. 턴마다 판정이 로그로 본다.
- 엔진은 그대로가 아니다. 이음매가 셋이다.

| 이음매 | 지금 | 넣는 것 |
|---|---|---|
| boot 의 인자(§3.1) | 단일 사용자를 받아 접근 값을 올린다 | 부르는 쪽이 접근 값을 올린다 |
| Keeper 의 Runtime 을 찾는 길(§3.4) | `runtime.toml` 에서 만든 표 하나 | 로그의 Runtime 과 배정 |
| 턴이 들고 가는 것과 돌려주는 것(§3.5) | Keeper 이름을 들고 가고, 거절을 문자열로 돌려준다 | 주인·채널·허락받은 범위를 들고 가고, 거절을 타입으로 돌려준다 |

- 이 RFC 에서 턴을 시작하는 원인은 둘이다. 주인의 메시지와 정기 턴이다.
- 사람의 메시지는 엔진의 대화 연산으로 들어간다. 지금의 직접 호출(`Server_preview_keeper_turn`)은 지운다.

## 1. 지금 동작

| 사실 | 연구 기록 |
|---|---|
| 한 boot 는 두 서버 중 하나를 띄운다. 계정 접근 값은 한 번만 올린다. 한 프로세스에 엔진은 하나다 | §10.1, §10.2 |
| 엔진은 Keeper 를 이름 하나로 찾는다. 로그는 (주인, id)로 찾는다 | §10.3 |
| 엔진이 띄울 이름을 읽는 곳은 autoboot, supervisor sweep, boot 의 credential 이다. 모두 정의 파일의 이름을 읽는다 | §11.1 |
| 엔진은 Runtime 을 세 걸음으로 묻는다. Keeper 의 route, route 의 후보, id 의 값이다. 셋째 걸음은 Keeper 를 모른다. 조회 함수는 모두 `runtime.ml` 에 있다 | §11.2, §14.1 |
| 실행 표는 `runtime.ml` 안의 한 함수가 통째로 바꿔 넣는다. 설정을 commit 할 때도 올린다. 읽는 곳은 여러 domain 이다 | §12.1, §12.8 |
| 사람의 Runtime 은 계정의 호출 안에서만 만든다. 계정의 호출은 서버 라이브러리에 있고, 잡지 못하면 거절한다 | §11.3, §12.1, §12.6 |
| 사람의 Runtime 값은 만들 때 계정 폴더의 파일을 읽는다. key 계정의 값은 key 를 든다 | §12.4 |
| 표를 나열하는 함수는 quota 와 Dashboard 로 간다. 사용량 기록은 모두 운영자의 작업 공간 파일로 간다. 배정이 없는 Keeper 는 default route 로 간다 | §12.5, §12.8 |
| 지금 사람의 턴은 `admit`, 계정의 호출, 판정 순서다. 거절 종류마다 답을 고른다. 도는 client 는 Claude Code 하나다 | §12.2, §12.8 |
| 엔진의 턴은 dispatch 전에 턴 번호를 쓰고, 판정의 거절을 문자열로 편다. 깨운 원인은 판정까지 오지 않는다 | §11.4, §12.2 |
| 엔진의 대화 연산은 실패를 닫힌 여덟 종류와 문자열로 적는다. 이어진 연산은 `source` 가 같으면 한 턴으로 묶는다. 연속이 있는 연산은 재시작 뒤 다시 줄을 선다 | §12.8 |
| 엔진에는 턴이 실패한 까닭을 드는 닫힌 타입과 codec 이 있고, 연산을 돌리는 코드가 그것을 문자열로 접는다. 지금 사람의 턴은 끝 까닭을 닫힌 타입 둘로 든다 | §13.2, §13.4 |
| 엔진을 띄우는 함수는 단일 사용자를 인자로 받는다 | §12.3 |
| 다계정 판정은 `Keeper_turn` 을 로그로 정하고, 운영자의 호출과 호스트 계정과 내장 도구를 거절한다 | §11.6 |

## 2. 목표와 하지 않는 것

목표다.

1. 다계정 프로세스에 엔진이 떠 있다.
2. 사람이 만든 Keeper 가 엔진에서 돈다. 지시문을 갖고, 주인의 메시지에 답하고, 주인이 켜면 스스로 턴을 시작한다.
3. 그 턴은 주인의 계정에서만 돌고, 계정의 호출을 지킨다.

하지 않는 것이다.

- MASC 도구. 사람의 Keeper 는 도구 없이 돈다. 도구는 Board 와 작업 공간의 것을 읽고 쓰므로 ③, ④ 와 같이 정한다.
- 내장 도구. 다계정에서 꺼진 채다(계획 D3c). 격리된 실행(설계 §7.2)은 다루지 않는다.
- 곁에서 부르는 호출(Librarian, vision, 목표 검증, Fusion). 거절된 채다(§3.7).
- Claude Code 밖의 client. 다계정에서 Codex 의 턴은 시작 전에 거절된다(연구 기록 §12.8). 내장 도구를 모두 끄는 값이 Codex 에 생긴 뒤에 다룬다.
- 다른 Runtime 으로 넘어가기(failover), 남의 Runtime 쓰기(계획 D5).
- 이미 돌던 설치의 Keeper 를 사람에게 넘기는 일(설계 §10.3, 계획 F4).
- 단일 사용자 boot. 그대로다.

## 3. 설계

### 3.1 한 프로세스에 계정 서버와 엔진을 띄운다

- 다계정 boot 는 `Server_accounts.run` 으로 간다. 계정 서버가 zone 을 열고 `Multi_account` 를 올린 뒤 엔진을 띄운다.
- 엔진을 띄우는 함수(`initialize_owner_state_blocking`)는 단일 사용자를 받지 않는다. base path 를 받고, 접근 값은 부르는 쪽이 먼저 올린다. 부르는 쪽은 셋이 된다. 단일 사용자 서버, stdio 서버, 계정 서버다.
- 경로표는 계정 서버의 것이다. 단일 사용자 서버의 경로는 열지 않는다(④).
- `runtime.toml` 을 구체화하지 못하면 엔진은 지금처럼 빈 표로 서고 Keeper 를 띄우지 않는다. 사람의 Keeper 도 그동안 돌지 않는다.
- 다계정 boot 는 정의 폴더를 본다. 로그에 없는 이름의 정의 파일이 있으면 boot 를 거절하고 그 이름을 말한다.

고르지 않은 길이다.

| 길 | 고르지 않은 까닭 |
|---|---|
| 사람마다 엔진 하나 | 두 번째 설치를 거절하는 전역이 일곱이다(연구 기록 §10.2, 하나는 조사만 함) |
| 엔진을 다른 프로세스로 띄운다 | 로그를 쓰는 프로세스와 판정을 하는 프로세스가 갈린다. 판정은 같은 프로세스의 zone 을 읽는다 |
| 엔진이 이름을 읽는 곳마다 로그로 거른다 | 읽는 곳이 셋 이상이다(§11.1). 하나를 빠뜨리면 로그에 없는 Keeper 가 뜬다 |

### 3.2 엔진 이름

- 로그의 Keeper 기록이 엔진 이름을 갖는다. Keeper 를 만드는 기록에 적는다. 바뀌지 않는다.
- 서버가 뽑는다. 정책 id 를 뽑는 것과 같은 방식이다(`lib/auth_preview_keeper.ml:145`). 사람이 고르지 않는다.
- 설치에서 하나뿐이다. 로그가 지킨다. 이미 쓰인 엔진 이름을 적은 기록은 거절한다.
- 로그 상태는 두 방향으로 찾는다. (주인, id)에서 엔진 이름을, 엔진 이름에서 (주인, id)를 찾는다.
- 엔진 이름 문자열에서 주인이나 id 를 읽는 코드를 두지 않는다.
- 로그는 엔진 이름을 문자열로 든다. 정의를 쓰는 서버가 `Keeper_name.t` 로 읽는다. 권한 라이브러리가 Keeper 라이브러리에 기대지 않는다.

| 엔진 이름이 보이는 곳 | 보는 이 | 이 RFC 에서 |
|---|---|---|
| 디스크, 로그 줄, metric label | 운영자 | 그대로 보인다. 엔진 이름으로 주인과 id 를 찾는 명령을 둔다 |
| 지시문의 "당신은 {{keeper_name}}이다" | 모델 | 서버가 쓰는 정의의 지시문 앞에 주인이 지은 id 를 적는다 |
| 도구 호출의 행위자, Board 작성자, `@이름` | 다른 사람 | 도구가 없어서 생기지 않는다. ③ 이 정한다 |

고르지 않은 길이다.

| 길 | 고르지 않은 까닭 |
|---|---|
| 엔진의 식별자를 (주인, id) 타입으로 바꾼다 | 타입이 구분을 강제하는 장점이 있다. 그런데 이름을 쓰는 곳이 11,647곳이고(연구 기록 §9), 디스크 구조와 경로와 metric label 이 같이 바뀐다 |
| id 가 비어 있으면 id 를 엔진 이름으로 쓴다 | 먼저 만든 사람만 읽기 좋은 이름을 갖는다. 엔진 이름을 보고 남이 그 id 를 썼는지 알 수 있다 |

### 3.3 정의

- 사람이 Keeper 를 만들면 서버는 로그에 기록을 쓴 뒤 엔진의 `keeper_up` 을 부른다. `keeper_up` 이 정의 파일과 실행 기록을 쓰고 Keeper 를 띄운다. Keeper 를 만드는 길을 새로 두지 않는다.
- 서버는 Runtime id 를 주지 않고 부른다. 그러면 `keeper_up` 은 배정을 쓰지 않는다(연구 기록 §12.3). 배정은 로그가 정한다.
- 정의 파일을 쓰는 것은 서버뿐이다. 사람이 정하는 값은 둘이다. 지시문과 방식(`on_demand`, `autonomous`)이다. 기본 방식은 `on_demand` 다.
- 나머지 값은 서버가 고정해 쓴다.
  - `tools.native` 는 없음이다. 다른 값은 판정이 거절한다.
  - MASC 도구는 붙이지 않는다. 지금 정의에는 도구를 통째로 끄는 키가 없다. `keeper.tools` 표에 하나 더한다.
  - `mention_targets` 와 `board_interests` 는 비운다.
- 로그의 기록은 들어갔는데 `keeper_up` 이 실패하면 Keeper 는 로그에만 있다. boot 와 다음 만들기 요청이 로그의 Keeper 가운데 정의가 없는 것을 다시 만든다.
- 주인이 Disabled 가 되면 서버가 그 사람의 Keeper 를 내린다(`keeper_down`). 이미 시작한 CLI 는 끝까지 돈다. 다음 시도는 판정이 거절한다.

### 3.4 이음매 — Keeper 의 Runtime 을 찾는 길

지킬 것이다. 오른쪽은 그것을 강제하는 사실이다(연구 기록 §12.4, §12.5, §12.8).

| 지킬 것 | 까닭 |
|---|---|
| 운영자의 표를 올리는 길은 지금 그대로다. 조회는 표를 쓰지 않는다 | 올리는 함수는 표를 통째로 바꿔 넣는다. 설정의 commit 과 겹치면 한쪽이 덮인다 |
| 사람의 Runtime 과 그 사용량은 운영자의 나열, 문서, 파일에 나오지 않는다 | 나열은 quota scope 목록, Dashboard 문서, exact-output catalog 로 간다. 사용량 기록은 모두 운영자의 작업 공간 파일로 간다 |
| 사람의 Runtime 값은 key 의 내용을 들지 않는다. 계정 폴더의 파일은 판정이 허락한 뒤 계정의 호출 안에서 읽는다 | 지금 값은 만들 때 key 를 읽어 든다 |
| 사람의 Runtime 값은 로그 상태와 `runtime.toml` 로 만든다. 둘 중 하나가 바뀌면 다음 조회가 새 값을 본다 | login 계정이 어느 integration 인지는 지금 영수증 파일에 있다. 로그의 head 는 상태 전체의 판 번호가 아니다 |
| binding 이 같은 값은 다시 만들어도 같은 backpressure 칸을 든다 | 엔진은 그 칸이 같은 물건인지로 dispatch 가 바뀌었는지 본다 |
| 사람의 Keeper 의 배정은 로그에서만 온다. 없으면 default route 로 가지 않는다 | 지금 조회는 배정이 없으면 호스트의 default route 로 보낸다(사용자 결정 2026-11-08). 그 코드가 일곱 자리에 있고 동작이 서로 다르다(연구 기록 §14.2) |

셋째 줄을 지키는 방식이다.

- 사람의 Runtime 값이 든 봉인은 계정의 이름이다. client 와 계정 id 다. 홈의 내용과 key 를 들지 않는다.
- 판정이 로그로 홈과 지금 세대의 key 파일을 적는다. 허락한 뒤에 그 파일을 읽어 CLI 에 넘긴다. 지금의 맞춰 보기(`own_home`, `own_key`)는 적기로 바뀐다.
- 값은 봉인 밖에 경로를 든다. 홈, key 파일, quota scope 다. key 를 바꾸면 key 파일의 경로가 바뀌므로 값을 다시 만든다(넷째 줄). 배정이 로그와 다르면 판정이 거절한다.
- 로그의 login 계정 기록이 integration 을 든다. S2 의 로그 형식에 넣는다.

첫째와 둘째 줄을 지키는 방식이다(연구 기록 §14.1).

- 사람의 Runtime 과 배정은 운영자의 표 옆에 따로 둔 값에 든다. `runtime.ml` 안이다. 그 값을 올리는 길은 운영자의 표를 쓰지 않는다.
- 그 값을 읽는 것은 하나를 찾는 조회 넷뿐이다. Keeper 이름으로 찾는 둘(`runtime_id_for_keeper`, `keeper_dispatch_snapshot`)과 id 로 찾는 둘(`get_runtime_by_id`, `resolve_assignment_in`)이다. 넷 다 `runtime.ml` 에 있어서 부르는 곳은 그대로다. 나열하는 함수는 그 값을 읽지 않는다. id 로 찾는 조회가 든 까닭은 엔진의 후보 단계가 Keeper 를 모르는 채 id 로 묻기 때문이다.

그 값을 언제 다시 만드는지는 정하지 않았다(§6 의 6).

### 3.5 이음매 — 턴이 들고 가는 것과 돌려주는 것

들고 가는 것이다.

- `walk_owner` 에 사람의 갈래를 더한다. 주인, Keeper id, 채널, 허락받은 범위를 든다. `account_request` 가 그것을 `Keeper_turn` 으로 바꾼다.
- 주인과 Keeper id 는 로그에서 엔진 이름으로 찾는다. 찾지 못하면 턴을 시작하지 않는다. 다계정 프로세스에서 `Fleet_keeper_turn` 은 만들지 않는다.
- 대화 연산은 요청이 허락받은 범위를 든다. 설계의 `stored_scope` 다. 재시도에서도 채널과 범위는 그대로다(설계 397행).
- 시도마다 판정은 그 범위와 원래 채널로 묻는다. 주인이 Active 인지와 배정은 로그에서 다시 본다.
- 요청을 인증한 PAT 는 `admit` 이 본다. 줄을 선 뒤에는 다시 보지 않는다. 그래서 요청 뒤에 없앤 PAT 가 줄 세운 턴은 돈다. 연속이 있는 연산은 재시작 뒤에도 다시 줄을 서서 돈다(§6 의 4).
- 범위를 든 연산이 "인증된 주인이 보냈다"는 표시다. 엔진의 `Owner` 는 인증 사실이 아니라서 쓰지 않는다. 범위는 엔진이 연산을 묶을 때 견주는 `source` 에 둔다. 그래서 범위가 다른 두 요청은 한 턴이 되지 않는다. 필드의 모양은 S2 에서 정한다. 범위가 판정까지 가려면 세 층을 지난다. 연산 id 는 이미 그 길을 간다(연구 기록 §13.1).

채널은 턴이 생긴 곳마다 하나다. 닫힌 `match` 로 쓴다.

| 턴이 생긴 곳 | 채널 |
|---|---|
| 인증된 주인의 대화 연산 | `Direct` |
| 자극 없는 정기 턴(`Proactive_tick`), `Bootstrap` 만 든 `Woken` | `Autonomous` |
| 그 밖의 `Woken`(빈 것 포함), 주인이 아닌 이의 대화 연산 | 턴을 시작하지 않는다 |

- 셋째 줄을 `Autonomous` 로 묻지 않는다. 설계 396행은 바깥에서 온 일정, Board, 위임에 DelegatePolicy 를 요구한다. 그 채널은 그 정책을 여는 문서가 정한다(2단계).

돌려주는 것이다.

- 턴이 끝난 까닭은 타입으로 읽힌다. 기다리던 요청도, 나중에 연산 id 로 읽는 요청도, 재시작 뒤에도 같은 종류를 읽는다. 문자열을 견주어 가르지 않는다.
- 끝 까닭은 판정의 거절만이 아니다. 지금 사람의 턴이 가르는 것 전부다. key 가 거절됐다, 한도가 없다, 로그인이 풀렸다가 든다.
- 서버가 지금의 표로 답을 고른다(`server_preview_keeper_turn.ml:85`). 서버 경로가 든 거절의 글은 로그로만 간다.
- 끝 까닭을 드는 타입은 새로 만들지 않는다. 엔진에 턴의 실패를 드는 닫힌 타입과 codec 이 있다(`Keeper_request_failure.t`). 판정의 거절은 엔진이 MASC 오류를 나르는 기존 길로 그 타입에 오른다. 그 값에 서버 경로가 든 글을 넣지 않는다.
- 지금 타입이 사라지는 곳은 셋이다(연구 기록 §13.2). 셋을 고친다. 그 값을 어디서 읽는지는 정하지 않았다(§6 의 7).

순서다.

1. 서버가 요청을 받으면 `admit` 에 묻는다. 연산을 넣기 전이다. 거절될 token 은 아무것도 남기지 않는다.
2. 엔진이 연산을 돌린다. dispatch 마다 계정의 호출을 기다려 잡고, 판정을 받고, CLI 를 시작한다.
3. 계정의 호출을 지키는 등록부는 서버 라이브러리에서 runtime 라이브러리로 내린다. 서버의 여덟 파일과 엔진이 같은 등록부를 쓴다.

계정이 바쁠 때다(설계 §9.1).

- 엔진의 dispatch 는 기다린다. 계정마다 온 순서대로다. 거절하면 한 구독을 쓰는 두 Keeper 가 서로를 실패한 턴으로 만든다.
- 기다림은 턴을 멈추면 같이 멈춘다. 새 시간 값은 만들지 않는다.
- 기다리다 시작하지 못한 턴은 Keeper 의 실패로 세지 않는다.
- key 바꾸기 같은 관리 요청은 기다리지 않는다. 지금처럼 409 로 답한다.

### 3.6 사람의 메시지

- `POST /api/v1/auth/keepers/turn` 과 `masc_my_keeper_turn` 은 메시지를 엔진의 대화 연산으로 넣는다.
- 요청은 연산이 끝날 때까지 기다리고 답을 돌려준다. 기다리는 시간의 상한은 지금 값(120초)이다. 넘으면 연산 id 를 돌려주고, 사람은 대화에서 답을 읽는다.
- `Server_preview_keeper_turn` 의 직접 호출과 `turns.jsonl` 은 지운다. 대화는 엔진의 기록이 갖는다. 옛 대화를 옮기는 코드를 두지 않는다.
- 사람의 대화 도구 셋(`masc_my_keeper_conversation`, `…_new`, `…_delete`)은 엔진의 대화 기록을 읽고 지운다.

## 4. 남는 위험

읽지 않은 것이다. 괄호는 그것을 읽어야 하는 단계다.

- **긴 대화**(S2). 대화 요약은 Librarian 이 하고 Librarian 은 거절된다. 대화가 창을 넘은 턴이 어떻게 되는지 읽지 않았다. 실패하면 Librarian 을 주인의 계정으로 돌리는 규칙이 S2 앞에 든다.
- **엔진이 다계정 프로세스에서 뜨는지**(S1). 연구 기록 §10.2 가 "조사만 함"으로 적은 전역, exact-output 등록표가 없는 boot, boot 의 token 과 credential 이다. Keeper loop 와 뒤 lane 을 띄우는 두 단계, 단일 사용자 경로 모듈에 있는 연산 실행기도 읽지 않았다(연구 기록 §12.8).
- **사람의 Runtime 을 다시 만드는 때**(S2 앞). 로그 상태 가운데 무엇이 바뀌면 값이 바뀌는지, 값을 만드는 코드를 `runtime.ml` 아래로 내릴 수 있는지 읽지 않았다. 읽은 뒤 §6 의 6 을 정한다.
- **끝 까닭이 사는 곳**(S2 앞). 엔진이 Claude Code 의 실패를 어느 원인으로 바꾸는지, walk evidence 를 무엇으로 찾고 얼마나 남는지, 거절된 시도 뒤에 엔진이 다음 후보로 넘어가는지 읽지 않았다. 읽은 뒤 §6 의 7 을 정한다.
- **턴 밖에서 계정 홈을 쓰는 것**(S2). dispatch 가 끝난 뒤에도 도는 사용량 읽기가 Claude Code 에 있는지, 엔진의 대화 지우기가 계정 홈의 vendor session 을 지우는지 읽지 않았다.
- **기다린 턴의 결과**(S2). 시작하지 못한 시도를 엔진이 어떻게 세는지, Runtime 의 턴 시간 제한이 기다림에도 걸리는지 읽지 않았다.
- **sandbox**(S2). 정의 파일에 `sandbox_profile` 이 꼭 있어야 한다. 도구 없는 Keeper 의 값을 읽지 않았다.
- **대화 도구**(S2). 지금 사람은 대화를 여러 개 만들고 지운다. 엔진의 대화는 Keeper 마다 하나다.
- **엔진 연산의 답 모양**(S2). 지금 경로가 사람에게 주는 답과 맞는지 읽지 않았다.

정해진 것이다.

- **hard cut 의 범위.** Keeper 기록의 형식이 바뀌면 옛 로그 전체가 재생되지 않는다. 사람, 초대, 구독 연결, PAT 를 다시 만든다. 계정의 홈(`.masc/accounts`)도 지운다.
- **저장소의 자리.** 엔진의 저장소는 `<base path>/.masc/keepers/<엔진 이름>/` 이다. 사람의 폴더 아래가 아니다. 다계정에서 그것을 내주는 경로는 없다(④).

## 5. 증명

| 주장 | 확인 |
|---|---|
| 다계정 프로세스에 엔진이 뜬다 | 다계정 boot 시험이 엔진의 server state 를 읽는다. 접근 값은 `Multi_account` 다 |
| 로그에 없는 정의는 boot 를 멈춘다 | 정의 파일 하나를 놓고 boot 한다. 거절이 그 이름을 말한다 |
| 엔진 이름은 하나뿐이다 | 같은 엔진 이름의 두 번째 기록을 로그가 거절한다 |
| 두 사람의 같은 id 는 두 Keeper 다 | 두 사람이 같은 id 로 만든다. 엔진 이름이 다르고, 엔진에 둘이 뜬다 |
| 사람의 메시지에 지시문을 가진 Keeper 가 답한다 | 가짜 CLI 로 턴을 돌린다. CLI 가 받은 system prompt 에 지시문이 있다 |
| 턴은 주인의 계정에서만 돈다 | 가짜 CLI 가 받은 홈과 key 가 로그가 적는 주인의 것이다. 표의 배정을 남의 Runtime 으로 바꿔 놓으면 CLI 가 시작하지 않는다 |
| 표에 key 가 없다 | key 계정의 Keeper 를 만든 뒤 표의 값을 본다. environment 에 key 변수가 없다 |
| 운영자 쪽은 그대로다 | 사람의 턴을 한 번 돌린다. `get_runtimes`, quota scope 목록, 운영자의 사용량 파일, 표의 판 번호가 그대로다 |
| 로그가 바뀌면 다음 조회가 새 값을 본다 | Keeper 의 배정을 바꾼 뒤 조회한다. 새 Runtime id 가 나온다. key 를 바꾼 뒤의 턴은 새 key 로 돈다 |
| 끝 까닭은 타입으로 읽힌다 | 배정을 바꾼 직후의 턴과 key 가 거절된 턴을 돌린다. 기다리던 요청과 연산 id 로 읽은 답이 같은 종류(`Runtime_reassigned`, `Key_refused`)를 말한다. 답과 기록에 서버 경로가 없다 |
| 범위가 다른 두 요청은 한 턴이 되지 않는다 | 범위가 다른 연산 둘을 줄 세운다. 턴이 둘 돈다 |
| 한 계정에서 한 번에 하나만 돈다 | 엔진의 dispatch 가 도는 동안 key 바꾸기가 409 를 받는다. 같은 계정의 둘째 Keeper 는 기다렸다가 돌고, 실패 횟수가 늘지 않는다 |
| 채널이 없는 곳에서 생긴 턴은 시작하지 않는다 | 일정 자극을 넣는다. CLI 가 시작하지 않는다 |
| 단일 사용자는 그대로다 | 기존 시험이 통과한다 |

## 6. 열린 결정

1~5 는 사용자가 정한다. 6 과 7 은 그 자리를 읽고 정해 이 문서에 적는다.

1. **엔진 이름을 따로 두는가, 엔진의 식별자를 (주인, id) 타입으로 바꾸는가.** 이 RFC 는 앞의 것을 골랐다(§3.2).
2. **사람이 정하는 값을 지시문과 방식 둘로 두는가.**
3. **기본 방식을 `on_demand` 로 두는가.** `autonomous` 가 기본이면 만든 순간부터 주인의 구독으로 정기 턴이 돈다.
4. **요청 뒤에 없앤 PAT 가 줄 세운 턴을 돌게 두는가.** 이 RFC 는 설계 397행대로 돌게 뒀다(§3.5). 주인이 멈추는 길은 대화 지우기, 배정 바꾸기, Disabled 다. 막으려면 연산이 PAT 의 id 를 들고 판정이 시도마다 로그에서 다시 읽는다. 판정의 요청 타입이 바뀐다. 재시작 뒤에 다시 줄을 선 턴도 같다. 설계 679행은 재시작 때 직접 요청이 `Cancelled_before_effect` 를 본다고 적었는데, 엔진의 연산으로 넣은 메시지는 재시작을 넘는다.
5. **운영자가 사람의 계정 사용량을 보는가.** 이 RFC 는 보지 않는 쪽이다(§3.4 둘째 줄).
6. **사람의 Runtime 값을 언제 다시 만드는가**(S2 앞). 두는 자리는 정했다(§3.4). (가) 조회가 운영자 표의 판과 로그 상태를 보고, 다르면 다시 만들어 그 값의 자리에만 넣는다. 알리는 길이 없다. 로그의 기록 하나마다 다시 만들지 않으려면 무엇을 견줄지 정해야 한다. (나) Runtime, 배정, 계정 기록을 로그에 쓰는 곳이 쓴 뒤에 다시 만든다. 쓰는 곳을 하나 빠뜨리면 낡은 값이 남는다.
7. **끝 까닭을 어디서 읽는가**(S2 앞). 드는 타입은 정했다(§3.5). (가) 연산의 끝 기록이 그 값을 든다. `source` 처럼 부르는 쪽의 JSON 이고 칸이 하나 는다. (나) 연산이 가리키는 턴의 walk evidence 에서 읽는다. 엔진이 이미 시도마다 그 값을 쓴다. 새 칸이 없다. 연산의 실패 종류에 갈래를 더하는 길은 고르지 않았다. 연산의 한살이와 턴이 실패한 까닭이 한 타입에 섞인다.

## 7. 단계

| 단계 | 하는 일 | 끝나면 보이는 것 |
|---|---|---|
| S0 | 계정의 호출 등록부를 runtime 라이브러리로 내리고 기다리는 길을 더한다. 엔진을 띄우는 함수의 인자를 바꾼다 | 없다. 동작이 그대로다. 기존 시험이 본다 |
| S1 | 계정 서버가 엔진을 띄운다. 로그에 없는 정의는 boot 를 멈춘다 | 사람에게는 그대로다. 다계정 boot 시험이 엔진의 state 를 읽는다 |
| S2 | 엔진 이름, 정의, 이음매 둘(§3.4, §3.5), 메시지의 길. 채널은 `Direct`, 방식은 `on_demand` 만 받는다. 직접 호출을 지운다 | 사람의 Keeper 가 지시문을 갖고 답한다 |
| S3 | 정기 턴이 채널 `Autonomous` 로 묻는다. 방식 `autonomous` 를 받는다 | 주인이 켠 Keeper 가 스스로 턴을 시작한다 |

- S2 부터 사람에게 보이는 것이 바뀐다. S2 는 로그의 형식을 바꾸는 hard cut 이고 한 번에 배포한다.
- S0 과 S1 은 사람에게 보이는 것을 바꾸지 않는다. S2 와 이어서 한다.
