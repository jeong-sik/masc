# Goal Candle candidate coverage

The payout ledger does not establish that every contributing Task was considered.
This report describes a source-level gap; it is not a payout audit or a claim that a particular payment was wrong.

When a verifier's proven decision is recorded, [Candle snapshot recording](../../lib/candle_runtime/candle_snapshot.ml) reads the Goal–Task link registry and stores those Task IDs with the proof request and run. [Candidate preparation](../../lib/candle_runtime/candle_candidates.ml) later reads Tasks from that stored list. If a Task is linked after that registry read, completes before human confirmation, and should count for the Goal, that Task can be absent from the candidate set. An empty captured list can also lead to an unattributed settlement. The registry read is part of proof recording; it is not an atomic observation at the verdict timestamp.

The current registry alone cannot determine whether an absent Task was linked at confirmation. It records the current links, not their commit order, and removal can erase a link. Task activity events are not a complete replacement: some are emitted after the backlog commit on a best-effort basis, and other assignment paths do not emit the same event. A read can also observe a link that a concurrent failed Task creation later rolls back. The registry and Candle ledger can use different storage backends. Consequently, neither the absence of a current difference nor a difference read without a shared fence proves historical coverage or an omitted payment.

Existing payments and outcome-unknown appraisal requests must not be replayed or adjusted merely because this gap exists. Existing historical state may lack enough evidence for an automatic correction. The operator needs the original request, terminal execution evidence and the applicable contribution history before deciding how to repair an individual case.

A forward repair needs durable link and Task-completion lineage that can establish the order of Goal creation, link changes, Task completion and first human confirmation. The decision and candidate observation need a shared, fenced commit boundary, including failed writes, rollback and restore; Keeper attribution must be captured at a defensible point as well. Old writers must not continue writing incompatible ledger or lineage state during rollout. These are requirements for a design, not an implemented guarantee.

A separate read-only comparison could show what one current registry observation contains versus a specifically identified Snapshot. It must distinguish an unreadable or conflicting Snapshot or registry from an empty set, bind the Goal and proof or payout identity, and state that the readings are not atomic. It would aid investigation only: it would not prove when a link existed, prevent a payout, determine entitlement or establish fairness. Existing v1 consumers strictly decode the current response, so such an observation needs an independently versioned or explicitly selected interface.

## Observation authority

The Goal Candle GET requires administrator authority, but its successful response does not identify an authorization generation for the resolved operator. The current Dashboard and TUI associate the displayed observation with the local credential and server instance. Reassigning the same bearer to another principal does not by itself change that local credential identity, so a cached or delayed successful observation can remain visible until the client revalidates. Explicitly refreshing and receiving a refusal withdraws the observation. Hiding unowned error bodies does not solve the successful-response case. A complete repair needs server-originated authorization-generation or revocation evidence tied to the response and current client authority; it is not provided here.
