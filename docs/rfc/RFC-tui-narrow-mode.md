# RFC: TUI 좁은 모드 (tui-narrow-mode)

## 0. 요약

작업대 RFC §5.4(#38988)는 표마다 빼는 순서(`drop_order`)와 늘어나는 열(`flex`)을 정했어요.
정하지 않은 것이 하나 남았어요. 빼는 순서를 다 써도 행이 pane 보다 넓으면 어떻게 하는가.

`Masc_tui_table.fit` 은 그 경우를 프레임이 자르게 둬요. 어떤 열이 사라질지는 표가 아니라
터미널이 정해요. 보통 오른쪽 끝 열(자주 시계)이 사라져요(task-2025, #40753 리뷰 스레드).

이 RFC 가 정하는 것은 둘이에요.

1. 빼는 순서를 다 쓰고도 안 맞는 폭에서는 자르지 않고 쌓는다.
2. 쌓기로 바꾸는 기준 폭은 표 한 곳에서 계산하고, 화면마다 숫자를 따로 적지 않는다.

## 1. 배경

`fit` 은 빼는 순서의 다음 열이 아직 보이면 없애요. 이름 없는 열과 `flex` 는 없애지 않아요.
전부 없앴는데도 안 맞으면 `flex` 는 자기 바닥 폭에 머물고 행은 pane 보다 넓어져요
(`masc_tui_table.mli` 의 계약). 프레임이 그 초과분을 잘라요.

작업대 RFC 는 표가 무엇을 먼저 내려놓는지는 정했지만, 내려놓을 것이 없을 때 무엇을
지키는지는 정하지 않았어요.

## 2. 원칙

1. 열을 접는 구간은 `fit` 의 몫이에요. 화면은 여기서 쌓지 않아요.
2. 기준 폭은 표의 열 설명(폭 함수, `flex`, `drop_order`)에서 계산해요. 화면이 자기 상수를
   따로 두고 pane 폭과 비교하지 않아요. 표의 열 폭이 바뀌면 기준 폭도 같이 바뀌어야 해요.
3. 기준 폭 미만에서는 쌓아요. 규칙은 Models pane 이 이미 따르는 것과 같아요(§3).
4. 기준 폭은 쌓은 레이아웃을 고르는 화면과 같은 PR 에서 들어와요. 읽는 화면 없이 기준
   폭만 먼저 공개하지 않아요.

원칙 4의 이유는 두 가지예요. 읽는 쪽이 없는 숫자는 틀려도 아무도 모르고, 표의 실제
배분(`flex` 외 열이 pane 에 맞춰 줄어드는 것 등)과 어긋난 채 남기 쉬워요.

## 3. 쌓기 규칙

Models pane 이 착지시킨 방식(#41213, `Masc_tui_model_runtime_table.stacked_lines`)이 기준이에요.

- 필수 읽기는 전부 보여요. 라벨과 값을 한 행에 붙여 내려요(`"max-tokens 16384"`).
  없는 값은 `-` 로 보여요.
- 행은 `wrap_words ~max_cells:pane` 으로 pane 안에 맞춰요. pane 은 표에 준 폭이 아니라 실제로
  그리는 폭이에요(#28905: 둘이 다르면 마지막 열이 자기 행으로 내려앉았어요).
- 수치는 자르지 않아요. 잘린 `1638` 은 16384 와 다른 수로 읽혀요. 이름은 가운데를 접어도
  같은 행을 가리켜요.

## 4. 이 RFC 가 맡지 않는 것

- 쌓은 레이아웃의 키 이동. 표별 후속 PR 이 정해요. Models 의 "cursor walks bindings, not
  lines" 가 선례예요.
- pane 분할 임계값(Activity 패널 102칸, roster 110칸 등). 작업대 RFC §5.9·D13 이 정했고
  이 RFC 가 바꾸지 않아요.
- 표별 기준 폭의 값과 어느 표부터 쌓을지. 각 표를 쌓는 PR 이 그 표의 실제 열 배분에서
  측정해서 정해요. 이 RFC 는 숫자를 싣지 않아요.

## 5. 확인

각 표를 쌓는 PR 이 아래를 보여요.

- 기준 폭 바로 위와 아래 한 칸씩에서 `fit` 이 그리는 열 집합과 쌓은 행이 달라지는 단위 테스트.
- 쌓은 행에서 필수 읽기가 모두 남는지 확인하는 테스트. 프레임이 이미 자른 화면의 폭을 재는
  방식으로는 넘침을 못 잡아요. 표가 만든 행을 프레임에 넣기 전에 재거나, 필수 값이 화면에
  남았는지를 봐요.
