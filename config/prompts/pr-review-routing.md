# 리뷰 요청 라우팅

이 순서는 리뷰 작업 선택에 적용한다. 이번 턴의 `scheduled_admission_at_turn_entry`가 `known`이고 예약이 선택됐다면 각각 원본 요청의 대상·범위·제약·완료 조건대로 처리한다. 일반 연속이나 순회로 다른 예약을 합치지 않고 예약별 결과를 구분한다. 선택된 예약이 있는 동안 새 순회는 그 원본 요청이 허용한 범위에서만 한다. 현재 직접 요청과 보유 Task·Goal은 별도의 실제 요청·작업 범위와 제약에 따라 처리한다. 한 요청이나 작업의 결과를 다른 예약의 완료로 세지 않는다. `known`의 빈 선택이나 `unknown`만으로 과거 예약을 재개하지 않으며, `unknown`을 빈 선택으로 단정하지 않는다. 현재 요청·Task·Goal에 이어갈 일이 없고 확인된 선택 예약이나 다른 제약이 역할 순회를 제한하지 않으면 역할에 맞는 새로운 리뷰 후보를 고를 수 있다. 새 순회를 미확인 예약의 후속이나 완료로 취급하지 않는다. 리뷰 기준·독립성·기능/논리/코드 청결도 검토를 따른다.

1. 직접 메시지나 Board 요청 또는 보유 Task의 PR은 먼저 GitHub REST에서 현재 `state`, `draft`, head/base와 Native Stack을 읽는다. 이미 병합되거나 닫힌 PR은 처리 종료를 한 번 알린다. 같은 턴에 다음 PR로 가는 것은 위의 작업 선택 범위에서 허용할 때뿐이다. 옛 head를 승인하거나 닫힌 PR의 요청을 반복 처리하지 않는다.
2. 그 밖의 후보 중 인증된 `gh` 계정의 `requested_reviewers`에 있는 열린 Ready PR을 먼저 처리한다. 여러 건이면 생성 시각이 오래된 순이다. 같은 head의 재검토 요청도 명시적 요청이므로 읽는다. 이전 승인이나 요청만으로 이번 리뷰의 완료를 단정하지 않는다. GitHub 요청은 배정 사실이며, 실행 중·리뷰 완료·승인이라는 뜻은 아니다.
3. 같은 GitHub 계정을 공유하는 Keeper는 공식 요청을 공동으로 가진다. 담당 대표가 최종 요청 처리를 맡고, 다른 Keeper는 맡은 관점에 필요한 원문을 직접 검토한다. 같은 범위에 이미 게시된 근거를 읽고 새로운 발견·검토 근거 또는 직접 요청에 대한 답이 있을 때 의견을 보탠다. 별도 세션의 실제 독립 검증은 그 범위와 결과를 새 근거로 구분한다. Keeper 이름을 다른 독립 계정으로 세지 않는다.
4. 위의 작업 선택 범위에서 배정된 요청이 없으면 전체 열린 PR을 모든 페이지에서 읽는다. 공유 계정의 공식 요청이 리뷰 제출로 사라졌더라도 자신에게 맡겨진 미완료 검토는 후보로 찾는다. 타임라인의 명시적 요청 철회와 그 뒤의 새 요청·인계는 각각 해당 범위에서 처리한다. 자신의 이전 의견과 검토 기록을 확인하고 새 지적이나 미검토 범위가 있으면 이어서 검토한다. 서명만으로 실제 작성 세션을 인증하지 않는다. 다른 계정·팀의 요청을 대신 완료했다고 보고하지 않는다. 이력이나 범위를 읽지 못했다면 미확인으로 기록한다. 후보는 오래된 순으로 처리한다. 다른 계정에 배정된 PR을 대신 맡는 것은 직접 요청, 기존 Task, 그 계정의 요청 실패 또는 명시적 인계가 있을 때뿐이다. 게시가 막히면 원인을 한 번 기록하고, 위의 작업 선택 범위에서 허용할 때만 다음 후보로 간다.
5. 코드가 바뀐 CR은 작성자가 확인될 때 그 Keeper에게 재리뷰를 요청한다. 같은 계정의 이후 정식 승인은 그 계정의 이전 CR을 대체하며 다른 계정의 CR은 남는다. 공유 계정의 리뷰만으로는 실제 Keeper 세션을 구분할 수 없다. 원래 지적이 실제로 해결됐는지도 살피고, 확인하지 못한 사실은 미확인으로 남긴다. 같은 head의 CR은 기본적으로 작성자의 수정/설명 대기이며, 명시적 재검토 요청이 있으면 다시 읽는다. 다른 계정의 승인이나 초록 CI로 CR이 해제됐다고 보지 않는다.
6. 검토·게시 직전에 head/base/diff/stack을 다시 읽는다. 이전 검토는 같은 범위에서만 재사용한다. 요청이 목록에서 사라졌다고 완료로 세지 말고 실제 GitHub 리뷰를 확인한다. 승인·CR·COMMENT·미게시·조회 실패를 구분해 보고한다.

MASC 리뷰 요청의 라우팅 담당자는 현재 코드 리뷰 전문 Keeper의 이름과 역할, 자신의 사용 가능한 도구를 확인하고, 필요한 관점의 각 Keeper에게 MASC 내부 Board·Broadcast·Message로 요청을 전달한다. Keeper 호출자는 `masc_keeper_delegate`에 `target={kind:"keeper",name:"<Keeper>"}`와 `prompt`를 넣는다. 운영자·외부 클라이언트는 자신의 도구 표면에 노출된 경우 `masc_keeper_msg`의 `name`과 `message`를 사용할 수 있다. 요청에는 PR 링크, 현재 head/base와 Native Stack 범위, 맡길 관점, 검증 근거와 미검증 범위를 적는다. 공통 Board 게시물에 범위를 모아도 되지만, 대상 Keeper에게 전달됐는지 확인할 수 없다면 자신에게 사용 가능한 직접 메시지 경로로 각 Keeper에게 게시물 ID와 요청을 보낸다. 같은 게시물과 이를 가리키는 메시지는 하나의 요청으로 취급한다.

게시 후 Board 본문을 읽거나 `masc_keeper_delegate_status`에 원래 target과 operation ID를 넣어 메시지 operation을 재조회하고, 대상·게시물 ID 또는 operation ID·확인된 상태를 기록한다. 접수나 `queued`는 제출 사실이며, 검토 착수·완료·공식 승인과 구분한다. 결과가 불명확하면 기존 게시와 operation을 먼저 확인하고, 미전달이 확정되기 전에는 같은 요청을 무작정 재전송하지 않는다. GitHub 계정에 리뷰어를 배정하는 것만으로 Keeper 내부 전달을 마쳤다고 보고하지 않는다.

Broadcast는 구조화된 응답의 `request_id`, `seq`, `mention`, `mention_delivery`, `fanout_state`를 읽고 원문대로 기록한다. 한 Broadcast가 라우팅하는 mention은 한 대상이므로 본문의 다른 `@` 표기까지 개별 전달됐다고 세지 않는다. 요청한 대상과 응답의 mention이 일치하고 `mention_delivery.kind`가 `accepted` 또는 `already_accepted`일 때만 그 대상의 접수로 기록한다. passive·pending·deferred·rejected는 각각 그대로 남기며 `ok=true`나 `fanout_state=finished`만으로 개별 접수를 확정하지 않는다. 공통 안내로 Broadcast를 쓴다면 각 Keeper의 요청은 사용 가능한 직접 메시지 operation과 재조회로 확인한다. 불확실한 요청을 다시 보내기 전에는 기존 효과부터 확인한다.

GitHub 계정 배정에는 `scripts/review/review-worklist.py --repo OWNER/REPO --reviewer LOGIN`을 사용한다. 여러 독립 GitHub 계정은 `--reviewer`를 반복한다. 이 목록은 Keeper 내부 전달이나 렌즈별 리뷰 본문을 대신하지 않으므로 실제 리뷰 이력도 모든 페이지에서 읽는다. 기본은 읽기만 하고, `--request`를 붙인 명시적 실행만 누락된 GitHub 리뷰 요청을 게시하고 재확인한다. 사용자·팀의 기존 요청은 지우지 않는다. 새로운 타이머나 상시 실행기를 추가하지 않는다.

전체 작업 목록 수집이 시간 초과되거나 실패하면 전수 확인이나 빈 목록으로 보고하지 않는다. 이번 작업 범위가 허용하는 직접 요청 또는 오래된 후보 한 건의 현재 PR·모든 리뷰와 댓글 페이지·head/base/Native Stack을 직접 읽고 그 범위의 리뷰를 계속할 수 있다. 부분 관측으로 전체 목록이 완성된 것처럼 대량 요청을 게시하지 않는다.

## 관점별 COMMENT와 판정

- 직접 받은 요청과 이미 맡은 Task의 범위를 우선한다. 여러 PR을 요청받았다면 각 PR에서 확인한 결과와 막힌 사유, 남은 목록을 기존 Task나 턴 기록에 남기고 다음 PR로 이어 간다.
- COMMENT 전담자는 자신의 렌즈로 diff와 필요한 원문·직접 소비자를 읽는다. 같은 변경 범위에 대해 자신이 같은 렌즈로 제출하고 재조회한 COMMENT 리뷰가 있고 새 직접 검증 근거·지적이나 미검토 범위가 없으면 중복 게시하지 않는다. 자신의 일반 issue comment가 같은 범위의 근거를 이미 담고 있다면 형식만 바꾸어 다시 게시하지 않는다. 명시적 재검토 요청은 읽고 그 결과를 답하며, 새 근거가 있으면 기존 검토와의 관계를 밝힌다. 기존 리뷰를 참고하되 독립 판정자는 필요한 범위를 직접 검토하고 계정별 독립성을 구분한다.
- 렌즈 검토에서 새로운 근거·미해결 쟁점 또는 명시적 요청에 대한 답을 제출할 때 GitHub PR reviews API에 `event=COMMENT`와 검토한 head의 `commit_id`를 넣어 제출한다. 실제로 읽은 범위와 근거, 확인하지 못한 사항을 적는다. 막음 의견을 찾지 못했다면 해당 렌즈의 결과로 밝힌다. 막음 COMMENT는 공식 변경 요청이 아니므로 내용을 읽고 필요한 조치를 정한다. 현재 계정의 담당자나 명시적으로 인계받은 판정자의 인증 계정이 PR 작성자 계정과 다른지, 실제 리뷰 세션에서 해당 변경을 작성하거나 push하지 않았는지, 판정 권한이 있는지 확인한다. 커밋 author·committer 계정의 일치만으로 참여 여부를 판단하지 않는다. 가능하면 그 담당자에게, 불가능하면 독립적인 다른 담당자에게 근거를 인계한다. 재판정 확인 전까지 미해결로 기록하고, 독립적인 담당자를 확인하지 못하면 미확인으로 둔다. 일반 issue comment와 스레드 답글은 제출된 COMMENT 리뷰와 구분한다.
- COMMENT 본문은 검토 의견이나 인계로 표현하고 공식 APPROVE나 CHANGE REQUEST를 이미 제출한 것처럼 쓰지 않는다. 제출한 리뷰의 ID·`state=COMMENTED`·`commit_id`와 현재 변경 범위를 다시 확인한다. 어느 범위라도 바뀌었다면 제출한 리뷰는 그때의 이전 범위로 기록한다. 제출 결과가 불명확하면 실행 영수증과 기존 리뷰를 확인한다. 리뷰가 보이지 않는다는 조회만으로 미게시를 단정하지 않는다. 성공이 확인되면 기존 게시를 기록하고, 효과가 발생하지 않았음이 확정되기 전에는 같은 게시를 재시도하지 않는다. 읽지 못한 범위나 인증·실행 장애는 완료로 보고하지 않는다.
- 최종 판정자는 리뷰 내용과 수정 사항이 맞으면 검토한 head를 `commit_id`로 지정해 GitHub에 직접 APPROVE를 게시한다. 문제가 남으면 변경 요청을 낸다. 소스 리뷰 승인은 CI를 기다리지 않고 낼 수 있으며 Release 병합·게시 때 전체 CI를 따로 확인한다. 게시 직전 head·base·전체 diff를 다시 보고 바뀐 범위는 검토한다. Draft나 작성자 계정 때문에 판정을 제출할 수 없어도 새 검토 근거나 직접 요청에 대한 답이 있으면 COMMENT로 남긴다. 공유 커밋 계정은 리뷰 참여 여부의 증거가 아니다. GitHub 리뷰만으로는 세션 독립성이나 당시 base·전체 diff를 증명하지 못한다. COMMENT는 승인이나 변경 요청을 대신하지 않는다.
- 아티팩트를 읽을 때 성공적으로 받은 동일 `sha256`·`offset`·`max_bytes` 페이지는 현재 턴의 결과를 재사용한다. 이어 읽어야 할 때만 응답의 `next_offset`으로 진행한다. 다른 길이의 요청이나 실패 응답은 동일한 성공 페이지로 취급하지 않는다.
