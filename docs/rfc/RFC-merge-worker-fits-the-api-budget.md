# RFC — 자동 병합 worker 가 API 한도 안에서 돈다

- Status: **구현됨.** D1·D2 는 #51609, D3 은 #51600 이 넣었다. 운영자가 고른 것은 §6 에 있다.
- 대상: `.github/workflows/approval-merge-request.yml`, `.github/workflows/approval-auto-merge.yml`,
  `scripts/review/approval-auto-merge.py`.
- 관련 이슈: #51479(한도에 걸린 worker 가 runner 를 쥐고 기다린다), #51465(같은 계정의 반복 승인).

## 0. 요약

- 자동 병합 worker 는 리뷰·PR 이벤트마다 한 번 돈다. 바쁜 시간에는 한 시간에 588번 돈다.
  worker 가 쓰는 Actions 토큰의 REST 한도는 한 시간에 5,000회다(§6.1 의 실측. 처음에는 문서의 1,000회로 적었다).
- 한도가 차면 worker 는 한도가 풀릴 때까지 runner 를 쥔 채 기다린다. 그동안 required check 가 시작하지 못하고,
  승인을 받은 PR 이 병합되지 않는다.
- worker 가 포기하지 못하는 이유는 이벤트 하나가 그 병합의 유일한 기회이기 때문이다.
- 이 RFC 는 세 가지를 정한다.
  - D1: 병합 보장을 이벤트에서 떼어, 정해진 주기의 확인 한 번에 둔다.
  - D2: worker 는 한도에 걸리면 기다리지 않고 끝난다.
  - D3: worker 는 스택 층의 상태를 스택 목록 한 번으로 읽는다.

## 2. 왜 이렇게 되는가

1. **호출 수가 이벤트 수에 비례한다.** 한 시간 588회에 한 번당 2 ~ 16회면 1,176 ~ 9,408회다. 한도는 5,000회다.
   스택이 섞이면 한 번이 65회를 넘으므로(§1.3) 588회가 아니라 77회만으로도 한도를 넘는다.
2. **스택에서는 층 수의 제곱이다.** 층마다 온 이벤트가 worker 를 하나씩 깨우고, 깨어난 worker 는 범위 전체를 읽는다.
   12층 스택의 모든 층이 승인을 받으면 worker 한 번이 약 65회를 쓴다.
3. **이벤트 하나가 유일한 기회다.** 마지막 승인의 worker 가 실패하면 그 PR 은 다음 이벤트가 올 때까지 병합되지 않는다.
   그래서 worker 는 한도에 걸려도 끝나지 못하고 기다린다.

## 3. 설계

### D1. 병합 보장은 주기적인 확인이 한다

- 정해진 주기로 도는 job 하나가 "병합 조건을 채웠는데 병합되지 않은 범위"를 찾는다.
- 찾는 방법은 열린 PR 과 리뷰 상태를 한 번에 읽는 GraphQL 질의다. 호출 수가 PR 수에 비례하지 않는다.
- 찾은 범위마다 지금의 worker 입장 판정과 병합 요청을 그대로 쓴다. 판정 규칙은 바꾸지 않는다.
- 이벤트로 깨어나는 worker 는 남긴다. 한도에 여유가 있을 때는 지금처럼 승인 직후에 병합된다.
- 주기는 `Main minimal build` 가 이미 쓰는 30분이다. 새 숫자를 고르지 않는다.

### D2. worker 는 한도에 걸리면 끝난다

- 입장 판정 단계에도 `deadline` 을 둔다. 한도에 걸리면 `rate_limited` 를 기록하고 끝난다.
- 병합 요청을 이미 접수한 뒤의 추적(`follow()`)은 지금 그대로 둔다. 접수한 요청의 UUID 는 놓치면 안 된다.
- 병합 요청이나 Auto-merge 예약을 보낸 뒤의 확인 읽기도 지금처럼 기다린다. 쓰기의 결과를 읽는 자리라서다.
- 한도에서 끝난 실행의 종료 코드는 75 다. D1 의 확인은 이 코드를 보면 멈추고, 남은 범위는 다음 회차가 맡는다.
- D1 이 없으면 D2 를 넣지 않는다. 놓친 이벤트를 주울 것이 없으면 승인받은 PR 이 멈춘다.

### D3. worker 는 스택의 층을 스택 목록에서 읽는다

- 층마다 `pulls/N` 을 읽지 않는다. `stacks/N` 목록이 층마다 state, draft, merged_at, head, base, user 를 준다.
  고른 PR 하나만 따로 읽고, 목록의 값과 같은지 대조한다.
- 리뷰 목록은 층마다 두 번 읽는다. 입장 판정 때 한 번, 읽는 동안 바뀌지 않았는지 볼 때 한 번이다.
- #51600 이 잰 호출 수는 5L + 7 에서 2L + 9 로 준다. 12층 67 → 33, 24층 127 → 57,
  승인 안 된 층이 하나 있는 24층은 39 → 11 이다.

## 4. 넣지 않는 것

- **PR 번호별 concurrency group**: 같은 PR 의 worker 는 하나로 줄지만, 서로 다른 PR 의 worker 가 한꺼번에
  기다리는 것(§1.5)은 그대로다. §2 의 1 ~ 3 을 하나도 없애지 않는다.
- **다른 토큰(PAT, GitHub App)으로 한도 늘리기**: 한도가 다섯 배가 되어도 §1.1 의 추세면 다시 찬다.
  비밀값 하나가 병합 권한을 갖게 된다.
- **worker 의 읽기를 GraphQL 로 옮기기**: 운영자가 2026-11-12T07:5xZ 에 REST 안에서 줄이기로 골랐다(§6).
- **이벤트를 더 거르기만 하기**: #51459 가 요청의 70%를 걸렀다. 남은 30%로도 한 시간 176회이고,
  병합 가능한 스택이 섞이면 한도를 넘는다.

## 5. 확인하는 방법

"재는 것"과 "목표" 열은 구현 전에 고정한다. 구현하는 쪽이 바꾸지 않는다. "구현 뒤" 열은 구현한 뒤에 잰 값이다.

| 재는 것 | 구현 전 | 목표 | 구현 뒤 |
|---|---|---|---|
| 30분 넘게 진행 중인 `Approval auto-merge` 실행 수 | 28 (2026-11-12T02:05Z) | 0 | 0 |
| `API rate limit exceeded for installation` 으로 끝난 worker 실행 | 표본 12회 중 6회 | 0 | 4 (08:32 ~ 08:33Z), 그 뒤 0 (한도가 찬 적 없음) |
| 승인 조건을 채운 뒤 병합까지 걸린 시간의 최댓값 | 재지 않음 | 주기 한 번 + worker 한 번 | 152초 |
| 병합 가능한 12층 범위에서 worker 한 번의 호출 수 | 약 65 (식으로 계산) | 층 수와 무관 | 33 |

"구현 뒤"는 2026-11-12T08:30Z ~ 12:15Z 의 값이고, 셈은 §6.3 에 있다. 셋째 값은 구현 전에 재지 못했다.
둘째 줄의 넷은 옛 코드 worker 가 07:33 ~ 08:33Z 창의 한도를 다 쓴 뒤의 꼬리다. artifact 를 내려받는 단계에서 끝났다.
그 뒤의 0 은 한도가 찬 적이 없어서 나온 값이다. 목표를 채웠다는 뜻이 아니다(§7).
셋째 줄의 목표는 GitHub 가 예약 실행을 늦게 시작하는 것을 셈에 넣지 않았다. 예약 회차 사이 간격은 최대 35분 39초였다.
이벤트 쪽이 놓친 PR 은 이 간격이면 목표보다 약 6분 더 기다린다(§6.4).
넷째 줄은 목표를 못 채웠다. 리뷰 목록 2L 이 남는다(§3 D3).

## 6. 운영자가 고른 것

1. **D1 의 주기 실행을 더할지.** 더한다(2026-11-12). 헌법은 운영자 요청 없이 주기 CI 를 더하지 않는다.
   대가는 하루 48회의 짧은 실행이고, 한도가 찬 시간에는 병합이 최대 30분 늦는다.
   실제로는 GitHub 가 예약 실행을 늦게 시작해서 그만큼 더 늦는다(§6.4).
   `.github/workflows/approval-merge-sweep.yml` 이 매시 22분과 52분에 돈다.
   D1 과 D2 는 같은 PR(#51609)로 넣었다. D2 만 먼저 들어가면 한도에 걸려 끝난 worker 의 PR 을 주울 것이 없다.
2. **D3 을 어떻게 할지.** GraphQL 로 옮기지 않고 REST 안에서 줄인다(2026-11-12T07:5xZ). #51600 이 넣었다.

### 6.1 한도 (2026-11-12 실측)

GitHub 문서는 Actions 의 `GITHUB_TOKEN` 한도를 REST·GraphQL 모두 저장소마다 한 시간 1,000 으로 적고, 둘을 따로 센다고 적는다
(`docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api`,
`docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api`, 2026-11-12 확인).

확인 실행이 Actions 토큰으로 읽은 `rate_limit` 은 REST `limit` 5,000, GraphQL `limit` 5,000 이다(run 43199287322).
문서의 1,000 과 다르다. 왜 5,000 이 적용되는지는 확인하지 않았다.
한도가 다섯 배여도 §2 의 구조는 같다. 07:33 ~ 07:44Z 에는 worker 약 70회가 한 시간 한도를 다 썼다(#51600 의 측정).
GraphQL 은 connection 요청 수를 100으로 나눈 점수를 쓴다. 열린 PR 51개를 읽는 질의 한 번이 1점이었다(사용자 토큰).

같은 토큰이 한 시간 창에 쓴 REST 호출이다. 확인 실행 summary 의 잔량과 reset 시각으로 계산했다.
08:33Z 창은 09:33:17Z worker 실패 응답의 `x-ratelimit-remaining: 2807`(reset 09:33:27Z)로 계산했다.

| 한 시간 창 | 쓴 호출 |
|---|---|
| 08:33 ~ 09:33Z | 2,193 (첫 9분에 1,517) |
| 09:33 ~ 10:33Z (부분 창) | 10:27Z 까지 1,255 |
| 10:37 ~ 11:37Z (부분 창) | 11:27Z 까지 814 |

08:33Z 창의 첫 9분은 한도를 기다리던 옛 코드 worker 들이 reset 직후 한꺼번에 다시 읽은 것으로 보인다(추정).
그 뒤 45분은 540회였다. 이 창들의 PR type-check 는 시간당 13 ~ 90회였다.
오늘 가장 바빴던 04Z 는 195회였다. 호출이 부하에 비례한다면 그 시간에는 한도에 닿는다. 비례하는지는 재지 않았다.

### 6.2 D1 의 확인이 하는 일

D1 의 확인이 worker 를 돌리는 범위는 다음과 같다.

- main 을 base 로 하고, 서로 다른 두 계정이 지금 head 를 승인했고, Draft·`release/*`·충돌 상태가 아닌 PR.
- 그 PR 위에 쌓인 열린 PR 이 있으면 전부 같은 조건을 채워야 한다. 하나라도 못 채우면 그 PR 이 Native Stack 인지
  REST 한 번으로 읽는다. Stack 이면 건너뛰고, 아니면 그 PR 만 worker 에 넘긴다.
- Auto-merge 예약이 걸린 단독 PR 은 건너뛴다. GitHub 가 직접 병합한다.

확인 job 은 열린 PR 목록을 GraphQL 로 읽는다. worker 의 읽기는 REST 그대로다(§6 의 2).
확인의 비용은 고정된 GraphQL 질의와, 범위마다 worker 한 번이다. 승인은 받았는데 required check 가 실패한 스택은
확인 때마다 worker 가 다시 읽는다. 이런 스택이 몇 개인지는 재지 않았고, summary 의 `candidates` 로 본다.

확인은 병합 뒤 남은 브랜치도 지운다(#51661, #51676). 첫 회차에 89개를 지웠고, 그 뒤 회차마다 0 ~ 2개다.

## 7. 확인하지 못한 것

- 구현 뒤 창에는 08:34Z 부터 한도가 찬 적이 없다. exit 75 로 끝난 worker 를 아직 못 봤다.
  D2 의 그 경로는 시험과 "보류가 생기지 않았다"는 사실로만 확인했다. 확인이 후보를 찾은 회차는 12:22Z 에 한 번 봤다(§6.4).
- GitHub 문서는 부하가 높으면 예약 실행이 늦어지고, 부하가 더 높으면 대기 중인 job 이 빠질 수 있다고 적는다.
  문서는 매시 정각을 부하가 높은 때로 꼽는다. 확인 job 의 22분·52분은 정각을 피한다
  (`docs.github.com/en/actions/writing-workflows/choosing-when-your-workflow-runs/events-that-trigger-workflows` 의 `schedule` 절, 2026-11-12 확인).
  회차가 빠지면 놓친 PR 은 그다음 회차까지 기다린다. 빠진 회차는 아직 못 봤다.
- `actions/download-artifact` 단계의 한도 실패는 스크립트보다 앞이라 D2 가 닿지 않는다. 이 실패는 runner 를 쥐지 않고
  바로 끝나고, 놓친 이벤트는 D1 이 줍는다.
- 쓰기 뒤의 확인 읽기는 한도에서 기다린다(§3 D2). `auto_merge_default` 의 `after = pull(...)`, `submit` 의 `pull(...)`,
  병합 뒤 `emit` 이 부르는 `delete_merged_heads` 의 읽기다. `after = pull(...)` 은 예약이 이미 있어 쓰기를 보내지 않은
  때에도 읽는다. 한도가 찬 순간 이 자리에 있던 worker 는 runner 를 쥔다. 몇 개인지는 재지 않았다.
- §1.5 의 28개가 한도 대기 중이었다는 것은 추정이다.
- push(`synchronize`) 이벤트에 worker 가 꼭 돌아야 하는지 확인하지 않았다. push 는 GitHub 가 기존 승인을 해제하므로
  병합할 것은 없다. Auto-merge 예약을 다시 걸어야 하는 경우가 있는지는 읽지 않았다.
