### Fixed
- A Muse Keeper session resumes against the completed-turn count the host last reported instead of a count MASC guessed from its own claim ordinal. After a retryable failed turn the resume expects the count from before that turn, since the host does not count a failed turn. After a dispatched turn whose ending MASC did not see, the resume admits that count or one more. Such a turn is one an owner stop cancelled, a graceful server shutdown among them, or one a host stop settled. These resumes no longer fail with `retained session completed-turn count changed` and no longer throw the retained session away. A hard restart during a turn still ends in recovery and a fresh session. An operator's `retry_previous` still expects exactly the count from before the failed turn. (#44265)

### Changed
- A Muse official-client session binding that names a session but records no host turn count no longer decodes. This covers settled bindings, active or in-flight claims, and claims or recovery rows that would resume an earlier settlement. On 2026-10-20 at 11:22 UTC that was 13 of the 17 live Muse bindings: 12 settled and 1 in flight. No recovery row or claim that resumes an earlier settlement was live. Ready Muse bindings, recovery rows without an earlier settlement, and every Codex, Claude Code and Antigravity binding still decode. The deploy preflight and boot list the undecodable bindings, `--accept-store-quarantine` moves them aside, and the next claim starts a fresh Muse session. A recovery row that would resume an earlier settlement is moved aside as well and loses `retry_previous`. An earlier build refuses every binding this build wrote with a host turn count, so a rollback moves those aside too. (#44265)
