## Evidence path

1. The actual targeted runner publishes its resolved alias array as JSON in the Test step's `resolved_aliases` output, before invoking any suite or returning a resolution failure. All five capture families use that array for their source/binary verification, capture and upload gates, so supported spaces and path spellings select the same capture as the runner. This includes Surface (`test_tui_surface_studio_pty`), Usage (`test_tui_usage_studio_pty`), Primary list (`test_tui_board_heading_width`), Navigation (`test_tui_lane_visual_pty`) and this retry witness. No capture-side CSV normalization, regular expression or basename rule is added. The parent's `captured_tui` step reads the actual checked-out HEAD and the built TUI's static `--build-commit`, requires equality, then hashes that executable. Each family's existing capture command, PASS marker, artifact and failure handling remain unchanged.
2. The retry capture step reads the canonical record parser from `scripts/capture-tui-ci-frames.py`. It selects only this suite's `STUDIO_CAPTURE` records, requires the recorded `STUDIO_BINARY_COMMIT` set to equal the verified checkout, and requires all recorded binary hashes to equal the verified executable hash. A missing or conflicting identity refuses replay.
3. `run.json` and `capture-input.json` record actual run/source identity, verification state, available frame count and the exact suite PASS-marker observation. These do not claim that replay or the suite succeeded. The input record remains `unverified` if an identity or missing-frame check fails.
4. The canonical replay command receives `--suite test_tui_claude_agent_retry_pty`, the exact PASS marker, `--expected-head` and `--expected-binary-sha256`. It writes original `.ansi` frames, checks xterm cells and geometry, and records independent frame and screenshot digests. Its existing failure path retains raw ANSI plus replay diagnostics rather than treating a diagnostic image as a verified frame.
5. The upload step runs even after test, verification or replay failure. It includes the capture directory and original `ci-run-tests.log`. The artifact name contains the actual run ID and verified source SHA, or `unverified` when source/binary verification never completed. A caller's SHA is not substituted as tested source.

The intended successful witness has eighteen frames: nine states at 80×36 and 140×36. Partial frames remain useful diagnostics with `suite_pass_seen: false`; they cannot establish a passing suite. If compilation prevents the binary identity read, no screenshot replay is attempted and the raw runner log is still uploadable. Browser setup is limited to an explicitly selected retry capture.

Full-suite mode does not run the targeted resolver and therefore does not publish selected aliases; all five families retain the prior explicitly targeted capture policy. A missing output is an empty selection, never a successful capture. When the runner resolves a capture alias and later fails (including another unresolved token, a missing execution prerequisite or compilation), the output remains available for evidence handling. A failure before resolution cannot establish that selected scope; the workflow's existing unconditional full runner-log upload remains the diagnostic path. No separate resolve-only or test-only parser mode is introduced.

The screenshot is a replay of a controlled fixture PTY running the compiled candidate. It is not a live Claude call, installed binary, deployed TUI, or production observation. Runtime ownership and stale-clear rejection remain the runtime fixture's authority.
