## 1. 문제

keeper들이 실측 실패를 모아 규범을 만든다. 그 규범이 관측자에게 돌아가지 않는다.

`config/prompts/corrective-grammar-v0.3.md`(PR #35315)가 그 증거다. 하룻밤 사이 재현된
같은 실수 계열을 6명분 원장에서 29건 모아 17행 카탈로그로 정리했다. v0.2에서 v0.3으로
승격하는 데 PR 두 건이 들었다. 그런데 이 파일은 코드 어디에서도 읽히지 않는다.

```
$ rg -n "corrective.grammar|corrective_grammar" -g '!config/prompts/*'
(0건)
```

`category: reference`는 26개 프롬프트 중 이 파일 하나다. 나머지(keeper/tool/judge/
verification)와 달리 렌더 슬롯이 없다. `Prompt_defaults.bootstrap_runtime`이 디렉터리를
스캔해 레지스트리에 등록은 하지만, 등록된 것을 호출하는 자리가 없으면 모델에게 가는
바이트는 0이다. 규범을 만든 keeper의 다음 턴 시스템 프롬프트는 규범이 없던 때와 같다.

승격 경로가 git PR인 것도 같은 문제의 다른 면이다. 세계에서 일어난 일을 규범으로 올리는
데 저장소 리뷰와 머지, 그리고 재설치가 필요하다. 규범은 세계마다 다른데 저장소는 하나다.

한편 **개인 단위로는 이 루프가 이미 돈다.** Memory OS가 관측을 쌓고
(`keepers_dir/<keeper_id>`), 프롬프트로 렌더하고(`Keeper_memory_os_render.render_facts`),
librarian이 회수·인용·개정으로 굳히거나 버린다(RFC-0418). 빠진 것은 스코프 하나다.
여러 keeper가 **같은 세계에서** 겪은 것을 공유 규범으로 올릴 자리가 없다.

## 2. 이미 있는 것

새로 만들 것을 줄이기 위해 현재 자산을 먼저 적는다.

| 자산 | 위치 | 스코프 |
|---|---|---|
| base_path별 프롬프트 디렉터리 | `Prompt_defaults.resolve_prompt_markdown_dir ~base_path` | world |
| durable override와 부팅 시 replay | `<base_path>/.masc/prompt_overrides.json` (`prompt_registry.mli`) | world |
| 관측 축적에서 프롬프트 렌더까지의 루프 | Memory OS (`keeper_memory_os_current`, `_render`) | keeper 1명 |
| 철회와 승계 | librarian claim / drop / `supersedes` (RFC-0418) | keeper 1명 |
| 합의 도구 | board post·comment·vote (`docs/spec/11-board.md`) | world |
| 추가 지시 슬롯 | `keeper.instructions.custom` (`prompt_names.ml:107`, `keeper_prompt.ml:37`) | operator가 채움 |

합의 엔진도, durable 저장소도, 프롬프트 주입 경로도 이미 있다. 셋이 서로 안 이어져 있다.

## 3. 제안

### 3.1 발의와 합의는 여기서 하지 않는다

조항을 제안하고, 따지고, 합의하는 일은 board와 채팅에서 이미 일어난다. 그것을 코드로 다시
모델링해서 얻는 것이 없다. `Proposed`와 `Ratified` 사이의 상태는 절차가 지나가라고 만든
자리인데, 그 절차는 이미 다른 데서 끝난 대화다.

투표로 승격시키는 안은 중복보다 나빴다. masc는 Keeper 간 요청에 응답·대기 의무를 만들지
않기로 했으므로, 정족수는 아무도 도달할 의무가 없는 문턱이다. 아무도 투표하지 않은 제안은
영원히 제안으로 남는다. 초안은 이 저장소가 금지하는 바로 그것을 요구하고 있었다.

남는 것은 대화가 스스로 할 수 없는 한 걸음이다. 합의된 문장을 세계의 모든 keeper가 읽는
자리에 놓는 것.

### 3.2 조항과 원장

조항은 문장, 쓴 사람, 쓴 시각이다.

```ocaml
type t = private {
  id : Article_id.t;
  text : string;            (* 프롬프트에 그대로 실리는 바이트 *)
  author : string;
  at : float;
  evidence : evidence list; (* 비어도 된다 *)
}
```

원장은 `<base_path>/.masc/constitution/articles.jsonl` 하나다. 한 줄이 한 번의 이동이고,
이동은 둘뿐이다.

```ocaml
type entry =
  | Added of t
  | Removed of { id : Article_id.t; by : string; at : float }
```

세계가 지금 들고 있는 규범은 그 줄들을 순서대로 접은 결과다. 조항 수는 아래 바이트 상한에
묶여 있으므로 파일 전체를 읽는 것이 읽기 경로이며, 맞춰줄 파생 스냅샷을 두지 않는다.

남이 쓴 조항을 지우는 비용은 쓰는 비용과 같다. 어떤 규범이 쓰였다 지워졌다 다시 쓰이면 그
왕복 자체가 불일치의 기록이고, 따로 분쟁 절차를 둘 이유가 없다. 이미 들고 있는 조항을 다시
쓰면 제자리에서 고쳐지고, 지워진 조항을 다시 쓰면 맨 뒤로 온다. 세계가 마음을 바꾼 시점이
거기이기 때문이다.

근거는 선택이다. 조항을 만든 대화는 누군가 그 좌표를 붙여넣든 말든 board에 있고, 필수로
만들면 논쟁이 도구 호출 안으로 옮겨올 뿐이다.

조항 하나는 한 줄이다. 개행을 품은 텍스트는 만들 때 거부한다. 렌더가 한 줄에 하나씩 찍으므로
텍스트 안의 개행은 `- [a-<32 hex>] ...` 모양을 한 줄 더 만들 수 있고, 그건 아무도 쓰지 않은
조항으로 읽힌다. 그 id는 세계가 들고 있지 않으니 지울 수도 없다.

디코딩되지 않는 줄은 줄 번호와 함께 보고하고 건너뛰지 않는다. 줄은 파일에 남는다. 아무도
읽지 못하는 규범도 누군가 쓴 규범이고, 조용히 버리는 reader는 세계가 자기 역사를 못 읽게
만들면서 그 사실조차 알리지 않는다.

### 3.3 주입과 상한

`keeper.instructions.custom` 옆에 `keeper.constitution` 슬롯을 둔다.
`Keeper_prompt.build_keeper_system_prompt`가 원장을 접은 결과를 렌더한다. 조항이 0개인
세계에서는 프롬프트 바이트가 변하지 않는다.

조항 텍스트는 이스케이프해서 넣는다. 같은 자리에 끼워지는 identity·workspace 블록이 이미
그렇게 하고, 조항은 셋 중 유일하게 operator가 아니라 모델이 쓴 바이트다. 그냥 넣으면
`</system>` 한 조각으로 조립기가 열지 않은 태그를 닫을 수 있다.

브레이크는 상한 둘이다. 조항 하나의 바이트 상한과, 조항 전체의 렌더 바이트 상한.

앞의 것이 없으면 빈 세계에서도 전체 상한을 넘는 글을 쓸 수 있고, 그때 "하나 지우고 다시
쓰라"는 답이 돌아간다. 지울 게 없는 세계에 따를 수 없는 지시를 주는 것이라, 모델은 같은
호출을 반복한다. 한 조항이 한 문장이면 이 답이 필요 없다.

뒤의 것에 닿은 세계는 새 조항을 받지 않고, 누군가 무엇을 지울지 정해야 한다. 자동 만료를
두지 않는 이유는 조용한 삭제보다 막힌 추가가 낫기 때문이다. 무엇이 빠졌는지 아무도 모르는
것보다, 무엇을 뺄지 정하는 편이 세계에 보인다.

상한 판정은 읽고-재고-쓰는 절차다. 그 사이가 비어 있으면 두 keeper가 같은 세계를 읽고 각자
통과한 뒤 둘 다 붙일 수 있고, 렌더 경로에는 다시 재는 자리가 없으므로 세계는 상한을 넘긴
채로 남는다. 그래서 읽기는 원장이 끝난 지점을 함께 돌려주고, 쓰기는 그 지점을 받는다. 그
사이에 누가 붙였으면 쓰기는 거부되고, 읽은 것이 낡았다는 사실이 호출자에게 간다.

### 3.4 keeper가 부르는 도구

keeper가 조항을 쓰고 지울 수 있어야 이 루프가 자율적이다. 지금 프롬프트를 고치는 경로는
`set_override_persisted`를 부르는 HTTP 라우트 하나뿐이고 그건 operator 대시보드다. keeper
쪽은 비어 있다. 이 RFC가 채우는 빈칸이 정확히 그 자리다.


## 4. 감시자는 코어가 아니라 Add-on이다

조항이 지켜지는지 보는 일은 Lane Add-on이 맡는다. 코어에 넣지 않는 이유가 둘 있다.

**첫째, 계약이 이미 맞다.** `docs/design/lane-addon-v0.md`는 이렇게 규정한다.

> attach, detach, Add-on 장애는 기존 Keeper의 권한·도구·진행 중 작업을 축소하지 않는다.
> 추가 근거는 활용·보류·무시할 수 있다. 승인이나 응답을 원래 활동의 선행조건으로 만들지 않는다.

감시자를 여기 두면 "Gate가 되지 않는다"가 배치로 보장된다. 헌법이 행동을 강제하는 장치로
자라는 경로가 설계에서 막힌다.

**둘째, 코어 변경이 필요 없다.** 원천 어댑터 3종(`snapshot_file`, `msx_capture`,
`browser_document`) 중 `snapshot_file`이 installer가 바인딩한 파일의 바이트와 해시를
store에 보존한다. 헌법 원장과 턴 원장을 여기 물리면 새 어댑터가 필요 없다. 스펙은
"새 의미 패키지를 붙이려고 서버 dispatcher, TUI 메뉴, Dashboard 컴포넌트를 수정해야 하면
실패"라고 못 박아 뒀다.

감시자는 조항이 쌓인 뒤에 만든다. 무엇을 관측할지는 어떤 조항이 어떤 식으로 안 지켜지는지
보고 정하는 것이고, 조항이 0개인 지금 대상을 고르면 전부 추측이다. 원장 안쪽 통계(왕복 횟수
같은 것)를 내는 것도 아직 아니다 — 왕복은 지금은 보이기만 하면 되고, 세기 시작하면 그때부터
장치다.

감시자 패키지는 `Observe` contribution만 갖는다. **"위반"을 판정하지 않는다.** 조항 id와
겹치는 관측 행(row)을 낼 뿐이다. 위반인지 아닌지는 keeper들이 그 행을 근거로 vote할 때
정해진다. 판정을 패키지 안에 넣으면 그것이 곧 semantic string matching이 되고, 그건
저장소가 금지한 패턴이다.

여기서 루프가 닫힌다. 감시자가 낸 행이 다음 조항의 `evidence`가 되고, 조항이 자주 어겨진다는
관측은 조항을 고치거나 폐기하는 vote의 근거가 된다. 강제 없이 규범이 자란다.

## 5. 하지 않는 것

- 위반을 차단하지 않는다. 조항은 도구 권한, 턴 승인, 검증 게이트를 바꾸지 않는다.
- 승격 절차, 정족수, 투표를 두지 않는다. 합의는 board와 채팅에서 끝난다.
- 분쟁 절차를 두지 않는다. 지우기가 쓰기만큼 싸고, 왕복은 원장에 남는다.
- 자동 만료를 두지 않는다. 상한에 닿으면 사람이나 keeper가 무엇을 뺄지 정한다.
- 과거 조항을 scheduling Gate로 쓰지 않는다.
- 레거시 필드와 마이그레이션 코드를 만들지 않는다. 원장이 없는 세계는 조항 0개다.
- `config/prompts/`의 저장소 프롬프트를 대체하지 않는다. 저장소 프롬프트는 제품 기본값이고
  조항은 세계가 스스로 덧붙인 것이다. 층이 다르다.

## 6. 위험

**오염 증폭.** Memory OS는 사실이 틀려도 blast radius가 keeper 한 명이다. 조항은 세계
전체가 같이 틀린다. 근거를 선택으로 돌리면서 이 위험은 초안보다 커졌다. 남은 완화는 둘뿐이다
— 지우기가 쓰기만큼 싸다는 것, 그리고 누가 언제 무엇을 썼고 지웠는지가 원장에 남는다는 것.
"다수가 동의한 틀린 규범"은 여전히 제거되지 않는 잔여 위험이다.

**프롬프트로 코드를 덮는 통로.** corrective-grammar 항목 중 "게시 전 id 인용"은 도구가
게시 전에 id를 노출하는 코드 문제일 수 있다. 조항 문장으로 "인용하지 마라"를 넣으면
워크어라운드의 프롬프트 판이 된다. 감시자가 같은 조항의 관측 행을 반복해서 내면 그것을 코드
결함 후보로 읽는다.

**토큰 성장.** 조항은 매 턴 모든 keeper에게 실린다. 상한이 이 위험을 흡수한다.

## 7. 검증

- 조항 0개인 세계의 시스템 프롬프트 바이트가 도입 전과 같다.
- 문장이 비었거나, 쓴 사람이 없거나, 여러 줄인 조항이 거부된다.
- 조항 텍스트의 `</system>` 같은 조각이 프롬프트에 태그로 도달하지 않는다.
- 도구로 쓴 조항이 실제 턴 프롬프트에 지울 id와 함께 나타나고, 지우면 사라진다.
- 지운 조항이 다음 부팅 프롬프트에 없다.
- 지웠다 다시 쓴 조항이 다시 실리고, 원장에 세 줄이 남는다.
- 한 조항의 바이트 상한을 넘는 글이, 빈 세계에서도, 무엇을 고치면 되는지와 함께 거부된다.
- 전체 바이트 상한에 닿은 세계에서 새 조항 추가가 거부된다.
- 낡은 읽기를 근거로 한 쓰기가 거부되고, 원장은 먼저 쓴 쪽만 들고 있다.
- 디코딩 안 되는 줄이 도구 응답에 줄 번호와 함께 돌아온다.
- 도구 스키마가 선언한 `article_id` 모양이 `Article_id`가 만드는 모양과 같다.
- 감시자 패키지의 실패와 detach가 keeper 턴 진행에 영향을 주지 않는다.
- 감시자 추가에 서버 dispatcher, TUI, Dashboard 수정이 들어가지 않는다.
