# MCP 2026-07-28 parity: source audit and remaining work

Audit date: 2026-10-27. The source baseline was `origin/main` at
`03a55e82460911c9367b8808cc1a3d7205854007` when the audit began; it later
advanced, and the working branch was rebased to
`101515ad465ed0fe9b9d3dc86a9792907e90e680`. The working changes accompanying
this note have not been built or deployed as a complete MASC binary.
The latest released specification checked was
[MCP 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28).
Its [base protocol](https://modelcontextprotocol.io/specification/2026-07-28/basic)
requires the base, versioning and message patterns; tools, prompts, resources,
authorization and extensions are modular. “All optional features implemented”
and “a conforming implementation of the features actually advertised” are
separate claims. This audit establishes neither full claim.

## Source observations

| Area | Source evidence and boundary |
| --- | --- |
| Server discovery and surfaces | `lib/mcp_server_eio_protocol.ml` handles `server/discover`, tool, resource and prompt requests. `lib/mcp_transport_protocol/mcp_subscriptions.ml` and the HTTP/stdio adapters contain subscription paths. These are source observations, not a complete interoperability test. |
| Modern HTTP client | `lib/mcp_client/mcp_client.ml` probes `server/discover`, sends per-request metadata and standard routing headers, reads tool pages and mirrors declared `x-mcp-header` parameters. A legacy handshake remains available after an unrecognized probe. `Mcp_client` remains a tool-oriented HTTP client, not a client for every MCP feature. |
| Routing and approval | The HTTP header validator decodes the `Mcp-Name` sentinel and rejects duplicate routing headers. For bound Keeper calls in either protocol era, the offered schema and read-only hint are recorded in the Gate input and compared with the live catalog before the tool request. A versioned fingerprint binds the provider declaration to the approved input and is checked before replay's Gate decision. These comparisons have not yet been exercised through a complete Keeper approval/replay. |
| Results | The client checks response identity and rejects ambiguous result/error fields. Modern complete results require `resultType`; modern tool schemas require an object root. `input_required` is retained as a typed incomplete result, not a successful tool execution. A new in-memory client API can explicitly continue state-only rounds with the original request, a new ID and a fresh catalog comparison. Structured content is retained; model-facing text and machine-facing original text are separate. A tool-reported or post-send protocol error no longer proves that an external effect did not happen. |
| Authorization | Server OAuth metadata, authorize and token routes exist in source. A 401 and 403 remain distinct in the client; a 403 retains its selected Bearer challenge. The presence of routes or a challenge parser is not proof of end-to-end OAuth compliance. |
| Server admission | Modern stdio and HTTP requests are checked for required per-request metadata and JSON-RPC identity. HTTP/1, HTTP/2 and stdio do not pass a legacy session identity into an admitted modern request. Unissued modern continuation fields are rejected before tool, resource or prompt execution, while identically named legacy extension fields remain accepted. A legacy stdio lifecycle, ping and legacy counter-offer remain distinct. Both HTTP routes pass listen requests through common admission before opening streams. These are changes in source, not full transport verification. |
| Subscription boundary | Source changes serialize acknowledgement and notification delivery per subscription, allow cancellation of the per-subscription acknowledgement lock, release registrations on cancellation, and validate the required filter. An explicitly supplied `MASC_TOKEN` is carried into the stdio authorization gate, which checks the full endpoint's read permission. The actual launcher and real HTTP endpoints have not yet been exercised with these changes. |
| External effect authority | All attached MCP tools go through the configured external-service Gate; the provider's `readOnlyHint` does not grant bypass or prove that an uncertain effect is safe to repeat. Internal post-send tool retries were removed, while a 401 known to precede the tool request may still refresh credentials. These source changes do not prevent a model from issuing a new call or prove an actual approval/replay flow. |

## Known gaps

- **MRTR:** The client has an explicitly invoked, in-memory API for state-only
  rounds, including single-send claims, but does not fulfill server input
  requests or send `inputResponses`. Keeper still reports an incomplete result
  without a durable continuation, so a server that answers with only
  `requestState` ends the call as a failure. Its existing Ask and model-input
  mechanisms do not validate MCP elicitation schemas or bind responses to the
  original operation and approval. The server needs no
  [MRTR](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr)
  producer: its duties apply only when it sends a server-to-client request,
  and the MASC server sends none (`rg '"(elicitation/create|sampling/createMessage|roots/list)"' lib bin`
  matches nothing). The proposed client behavior is in
  `docs/rfc/RFC-mcp-mrtr-client-continuation.md` (#46355).
- **Notifications and streaming:** The client has no `subscriptions/listen`
  API. The current HTTP transport buffers an SSE response until the body closes,
  so an already-sent final response on a still-open stream may time out, and
  progress is not delivered incrementally. Cancellation and long-lived streams
  need end-to-end transport handling. On the server, same-event fan-out still
  waits sequentially for each subscriber; an unread stdio stdout can hold a
  cancellation-protected write; and server-initiated graceful subscription
  closure does not yet send the recommended final response.
- **Server transport validation:** The HTTP server's validator does not
  enforce `x-mcp-header` parameter mirrors. No tool the MASC server lists
  declares that annotation (`rg x-mcp-header lib bin config` matches only
  `lib/mcp_client/mcp_client.ml`), so this has no effect today and becomes a
  requirement the first time the server declares one. Legacy stdio
  advertises change notifications but has no notification sink, and ordinary
  stdio requests run synchronously so an in-flight call cannot be cancelled.
  Subscription fan-out also needs an explicit workspace and caller authority
  boundary. Source fixes for ID correlation and common admission still need
  real HTTP/1, HTTP/2 and stdio integration tests.
  [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)
  specifies the routing-header rules.
- **Schema and content:** Modern tool discovery screens invalid header
  annotations, but this is not a general JSON Schema 2020-12 validator. The
  client does not retain/validate `outputSchema`; non-text blocks are retained
  in the client result but the Keeper adapter still projects them to text.
  Full schema dialect, reference and multimodal validation remain open.
- **Client feature surface:** `Mcp_client` exposes tools, not client APIs for
  resource/prompt retrieval, notifications or elicitation. Those server/client
  features are optional individually, but their absence rules out a claim of
  supporting every feature of the specification.
- **Approval identity:** A pending approval now binds a digest of the provider
  endpoint and credential declaration, but not the actual account principal.
  Reconnecting an OAuth identity or changing the active `gh` account under an
  unchanged declaration can therefore change the account. Approvals created
  before the declaration fingerprint or schema binding do not authorize a
  call and need a new approval. The replay host retires such a stale grant
  after the pre-effect rejection; it does not preserve it for later reuse.
  Direct identity replay tests for approval, grant consumption, catalog
  recheck and a recorded outgoing call have been written but not run. Host
  settlement, restart and a real provider have not been verified end to end.
- **HTTP profile response:** A syntactically valid streaming tool call may
  open HTTP/1 SSE with status 200 before the profile denies that tool. HTTP/2
  currently reports the denial as a 404 JSON response. Whether this particular
  tool-level denial requires a specific HTTP status is distinct from the
  specification's 404 rule for an unimplemented RPC method; the behavior is
  inconsistent and needs an authority-aware admission path and real tests.
- **Other compatibility:** A legacy endpoint that silently ignores the modern
  probe can exhaust the current per-request transport deadline without a
  handshake fallback. A reused modern client does not yet subscribe to catalog
  changes or perform the specification's suggested re-discovery after a
  header-mismatch error. Each pagination request has a separate deadline but
  there is no cumulative lifetime bound: a server that immediately returns
  endless pages can hold a caller indefinitely. Cursor values remain opaque;
  the missing boundary is cancellation/lifetime, not a cursor heuristic.
- **Conformance:** No official conformance suite, real modern/legacy server,
  actual OAuth flow, installed binary or production runtime was tested in this
  worktree. Full support requires these checks as well as implementing the gaps.

## Focused checks

The client module and `test/test_mcp_client.ml` were compiled with `ocamlfind`
against the actual changed source, actual `Www_authenticate` parser, and small
stand-ins for the HTTP transport, build version and protocol constants. The
header encoding functions came from the changed source. These tests do not link
the full repository or contact a server. A separate isolated check compiled the
actual HTTP header-validation source with stand-ins for surrounding server
modules and exercised sentinel values and duplicate headers. OCaml parsing and
`git diff --check` are separate source checks. The repository contract forbids
local Dune builds for this coding session; none was run.

The isolated client run passed 37 cases. The other isolated checks passed eight
protocol/subscription cases, five HTTP admission cases, three stdio loop cases,
three Keeper error/refresh boundary cases, two provider declaration binding
cases and one replay preflight case. The replay preflight check compiled the
complete changed Gate implementation and interface against the actual provider
and client modules, with stand-ins for the Gate decision and effectful Keeper
dependencies; it checked that a changed declaration stops before either stub
is called. The other checks use actual protocol, subscription, client and
provider modules, plus extracted transport and Keeper logic, with stand-ins
for surrounding server, auth dispatcher and workspace dependencies. Pipe-based
credential, H1/H2 listener and focused Gate tests,
including direct identity replay with a recorded HTTP transport, are written
but have not run. Host replay settlement through an actual provider has not
been verified. These checks do not establish that the complete server, Keeper
approval/replay or Z.ai consumer builds or runs.
