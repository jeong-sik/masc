# RFC compaction-anchor-names-a-turn-atom: 압축 지점은 목록 위치가 아니라 Keeper 턴 안의 atom을 가리킨다

- 상태: **제안(2026-11-26).**
- 11-26 저녁 masc 서버가 CPU를 계속 점유해 운영자가 서버를 멈췄다(21:03 SIGTERM).
- 운영자는 원인을 근본에서 고치라고 했다(「제대로 찾아서 올바른 방향으로 개선 및 최적화를 부탁한다」).
- 고정 ID 방향(A안)을 승인했다(「이거 버그가 없게 행랴함 고고」).
- 코드 좌표는 `origin/main` `a26795cff182c`에서 읽었다.
- 11-27: #55004 리뷰가 찾은 결함을 반영했다. 목록 종류(D2~D6), 끊긴 턴의 경계(D2), §1.1과 §5.1을 고쳤다.
- 11-27 2차 리뷰: 요약과 소비자는 두 종류의 마지막 경계 중 더 앞선 곳을 본다(D3, D5, §5.1). ACP 롤오버가 대신 압축하는 목록과 압축 저장소 오류의 이름도 고쳤다(D4).
- 11-27 3차 리뷰: 경계의 턴이 목록에 없는 경우를 따로 다룬다(D3, D5, §5.4). ACP 넘침 재시도도 다음 세션이 시작할 목록을 압축한다(D4). 메시지 기록의 턴 안 경계는 정식 턴 목록에서 행에 프롬프트가 있을 때만 그 사용자 메시지를 덮는다(D3, §5.1). watermark의 빈틈은 #55049로 남겼다(§6).
- 11-27 4차 리뷰: 인계 목록이 비었으면 ACP 생산자는 기록의 atom을 모두 압축한다. 압축 뒤 새 세션이 요약 하나로 시작하기 때문이다(D4, §7). 요약이 담은 턴의 행이 모두 ACP 임시 ID면 「마지막 사용자 요청」이 뒤로 갈 수 있다고 고쳐 적었다(§0, D3, §5.4, #55026).
- 11-27 5차 리뷰: 요약이 아직 없으면 ACP 생산자는 기록에서 첫 행보다 앞선 턴을 요약한다. 전에는 Fresh state 뒤 첫 롤오버가 그 앞 기록을 요약하지도 보내지도 않았다(D4, §7). 메시지 기록의 턴 안 경계가 최종 답에 닿을 수 있다고 고쳐 적었다(D3).
- 11-27 6차 리뷰: 그 요약 뒤에 행이 있는 턴이 오면 인계 목록도 압축해, 새 세션이 최근 행만 받는다. 정식 턴 저장소를 읽지 못하면 다시 최근 atom을 남긴다(D4).
- 11-27 7차 리뷰: 기록의 어느 턴에도 행이 없을 때 행을 압축하지 않는 이유를 바로잡았다. 요약을 커밋한 뒤 인계 목록 압축이 실패해도 그 요약을 돌려준다. 기록을 지운 뒤의 요약과 watermark 범위 문장을 좁혔다(D4, #55049, #55051).
- 11-27 8차 리뷰: 요약 뒤 인계 목록을 압축하지 못하면 넘침 재시도가 시작을 압축한 것으로 세지 않는다. 7차 변경이 만든 결함이다(D4).

## 0. 요약

- 압축 지점(compaction anchor)은 덮은 범위의 끝을 `atom-<번호>-<내용 해시 16자>`로 적는다.
- 번호는 생산자가 받은 목록 안의 위치다. 생산자는 일곱 곳이고 받는 목록이 서로 다르다.
- 매 턴 도는 소비자는 checkpoint 기록에서 이 번호를 찾는다. 위치가 맞지 않으면 번호 뒤 모든 atom을 JSON으로 직렬화하고 SHA-256으로 해시한다.
- ACP 압축 지점은 정식 턴 저장소에서 다시 만든 목록을 기준으로 한다. 실제 기록과 내용이 달라 해시가 절대 맞지 않는다. 그래서 매 턴 수만 개 atom을 해시하고도 아무것도 자르지 못한다.
- 이 RFC는 atom의 이름을 바꾼다. 이름은 「그 atom이 속한 Keeper 턴의 ID」와 「그 턴 안에서 몇 번째 atom인지」다.
- 턴 ID는 이미 메시지 메타데이터에 있다. 새로 찍는 값은 없다.
- 비교는 메타데이터만 읽고, 턴 ID가 같은지만 본다. 직렬화, 해시, 문자열 접두어 비교를 모두 없앤다.
- 압축 지점은 어떤 종류의 목록에서 썼는지도 적는다. 순번의 뜻이 목록 종류마다 달라서, 생산자는 같은 종류의 덮은 범위만 이어받는다(D3, §5.1).
- 요약과 소비자는 두 종류의 마지막 경계 중 더 앞선 곳을 본다. 두 경계의 턴이 목록에 있으면 요약은 옛 턴으로 돌아가지 않고, 소비자가 자르는 곳은 뒤로 물러나지 않는다(D3, D5).
- 경계의 턴이 목록에 없으면 그 자리는 하한일 뿐이다. 요약은 이미 담은 턴을 한 번 더 담을 수 있다. 요약이 담은 턴이 목록에 하나라도 있으면 「마지막 사용자 요청」은 옛 턴으로 돌아가지 않는다. 소비자는 덜 자를 뿐이다(§5.4).
- 옛 `atom-*` 압축 지점은 읽지 않는다(하드컷). 운영자가 두 SQLite 파일을 지운다(§7).

### 1.5 ACP 턴 ID는 압축 시점에 아직 임시 값이다

- ACP 런타임은 턴이 끝나면 정식 턴 행을 `acp:<session>:<turn_count>` ID로 쓴다(`provider_turn_identity`).
- 이 행은 finalize의 `bind_turn_ref`가 나중에 Keeper 턴 ID로 바꾼다.
- 롤오버 압축(`compact_for_rollover`)은 그 사이에 돈다. 그래서 압축이 받는 목록의 마지막 턴은 임시 ID를 단다.
- finalize가 세션을 `Settled`로 보지 못하면 행은 임시 ID로 남는다.

## 2. 원인

### 2.1 생산자마다 목록이 다르다

| 생산자 | 받는 목록 | 번호의 기준 |
|---|---|---|
| Agent Core(`keeper_turn_driver_try_provider.ml`) | 에이전트 기록 전체 | 전체 기록 |
| Claude Code·Codex·Antigravity | 시작 seed(`offered`) | seed |
| ACP 롤오버·overflow(`keeper_acp_runtime.ml`) | `load_handoff_context`가 정식 턴 저장소에서 다시 만든 목록 | 마지막 watermark 뒤의 턴 |

- ACP 목록의 메시지는 `messages_of_canonical_turn`이 만든다. 한 턴이 사용자 메시지 하나와 어시스턴트 요약 하나다. 실제 기록의 같은 턴과 내용이 다르다.

### 2.2 소비자는 매 턴 checkpoint 기록 전체를 훑는다

- `keeper_tools_agent_core_bundle.ml:807`이 `live_history_after_latest_anchor`를 부른다. 런타임과 상관없이 모든 Keeper가 매 턴 부른다.
- 결과는 도구 이어 붙이기(`History_carry`)에만 쓰지만, 배치 정책을 보기 전에 매 턴 계산한다.
- `messages_after_anchor`는 압축 지점의 번호 자리 atom 하나를 해시해 비교한다.
- 맞지 않으면 그 번호 뒤 모든 atom을 `encode_messages`(JSON)와 SHA-256으로 해시하며 찾는다. 결과를 저장하지 않아 다음 턴에 다시 한다.
- ACP 압축 지점은 다시 만든 목록의 해시라 실제 기록에서 절대 맞지 않는다. 리더는 매 턴 atom 수만 개를 해시하고 기록 전체를 그대로 돌려받는다.

### 2.3 같은 뿌리의 다른 증상

- 생산자도 부를 때마다 버린 atom 전부를 해시한다(`canonical_turns_of_evicted_messages`). msx는 요청마다 수천 개다.
- 해시가 겹치면 `-ep<epoch>-<n>` 꼬리를 붙인다. 이것을 문자열 접두어로 다시 가른다(`turn_id_matches_target`, `parse_atom_turn_id`).
- 정식 턴 저장소는 압축 지점을 정식 턴 번호(seq)로 바꿀 때 ID부터 비교한다. `atom-*`는 정식 턴 ID와 같을 수 없어 이 비교는 늘 실패한다. 그래서 메시지 글자를 차례로 맞춰 본다(`find_cutoff_seq_for_evicted_turns`의 `index_messages`·`match_turn_from`).
- 글자 비교는 턴의 사용자 메시지만 버려져도 그 턴의 행을 지운다. watermark는 행을 실제로 지운다(`prune_turns_through_seq_in_tx`). 요약에 없는 어시스턴트 답이 handoff에서 사라질 수 있다.
- 11-25 #54812는 정확 일치 단계만 줄였다. 같은 자리의 두 번째 성능 수정이라 구조를 바꾼다.

## 3. 결정

### D1. atom의 이름은 턴 ID와 턴 안 순번이다

```ocaml
type name =
  | Leading of int
      (* 목록 맨 앞, 어떤 턴 ID보다 앞선 atom. 0부터 센다. *)
  | In_turn of { turn : Ids.Turn_id.t; ordinal : int }
      (* turn 안에서 ordinal번째 atom. 0부터 센다. *)
```

- atom 경계는 지금처럼 `Runtime_model_input_tail_window.annotate`가 정한다. Pinned 메시지는 atom이 아니다.
- atom을 여는 메시지의 메타데이터에서 턴 ID를 읽는다. `canonical_turn_id`를 먼저 보고, 없으면 `masc.bridged_turn_ref`를 본다. 공백이 아닌 문자열만 턴 ID다.
- 턴 ID는 같은지만 비교한다. `Ids.Turn_ref`로 읽지 않는다. ACP 임시 ID(§1.5)도 Keeper 턴 ID와 같은 규칙으로 다룬다.
- 턴 ID가 있으면 그 턴의 다음 순번이다. 순번은 목록 안에서 턴마다 따로 센다. 같은 턴이 뒤에서 다시 나와도 이어서 센다. 그래서 한 목록 안에서 이름이 겹치지 않는다.
- 턴 ID가 없으면 바로 앞 atom의 턴에 붙어 다음 순번이 된다. 앞에 턴이 없으면 `Leading`이다.

**처음 승인한 A안과 다른 점**

- A안은 agent_core가 메시지를 붙일 때 단조 번호를 찍는 안이었다.
- ACP 목록은 정식 턴 저장소에서 다시 만든 메시지라 그 번호가 없다. 다시 만든 목록과 실제 기록에 함께 있는 값은 턴 ID뿐이다.
- 그래서 새로 찍지 않고 있는 값을 쓴다. agent_core는 바꾸지 않는다.
- 턴 번호(`absolute_turn`)로 앞뒤를 가리는 안도 버렸다. ACP 임시 ID에는 그 번호가 없다.
- 장점: 이미 쌓인 기록 대부분(msx는 4,042번째 atom부터)이 바로 이름을 가진다. 기록을 다시 쓰지 않는다.
- 단점: 턴 안 순번은 표현마다 다르다. 실제 기록의 3번째 atom과 다시 만든 목록의 1번째 atom은 다른 것이다. §5.1에서 다룬다.

### D2. 압축 지점은 「앞에서부터 이어 덮은 끝」과 「그 뒤에 따로 보관한 atom」을 적는다

```ocaml
type extent =
  | Whole_turn
  | Up_to of { ordinal : int; settled : Ids.Turn_id.t option }

type through =
  | Through_leading of int
  | Through_turn of { turn : Ids.Turn_id.t; extent : extent }

type coverage =
  { through : through option  (* 목록 앞에서부터 이어서 덮은 끝 *)
  ; beyond : name list        (* through 뒤에 있지만 이미 보관한 atom *)
  }
```

- 생산자는 자기 목록과 함께 버린 atom을 넘긴다. 앞에서부터 이어진 개수(`prefix`)와 그 뒤에서 따로 버린 번호(`later`)다.
- 앞에서부터 이어진 부분의 마지막 atom이 `through`다.
- 아래 넷이 모두 맞으면 `Whole_turn`이다. 하나라도 아니면 `Up_to`다. 진행 중인 턴을 다 덮었다고 하지 않는다.
  - 경계 뒤에 atom이 더 있다.
  - 경계 턴의 atom이 경계 뒤에 다시 나오지 않는다.
  - 경계 턴의 atom이 그 턴의 첫 atom부터 경계까지 끊기지 않는다. D3은 `Whole_turn`을 그 턴의 첫 이어진 구간으로 읽는다. 다른 턴이 사이에 낀 턴을 `Whole_turn`으로 적으면 읽는 쪽이 덜 덮고, 다음 압축이 나머지를 다시 보관한다.
  - 경계 턴보다 먼저 시작한 턴도 경계 뒤에 atom이 없다.
- `Up_to`의 `settled`는 모든 atom이 덮인 마지막 턴이다. 경계 턴보다 먼저 시작한 턴을 앞에서부터 보며, 경계 뒤에 atom이 있는 턴을 만나기 전까지의 마지막 턴이다. 그런 턴이 없으면 같은 종류의 이전 epoch의 settled를 이어받는다. 정식 턴 저장소가 이 값으로 cutoff를 정한다(D6).
- `Whole_turn`이면 경계 턴 자체가 settled다.
- 이어지지 않는 나머지는 `beyond`에 적는다. Agent Core는 크기 거절 뒤 현재 턴의 끝난 도구 왕복을 골라 버린다(`droppable_current_turn_tool_atoms`). 이 atom들이 여기로 간다.
- 새 경계가 이전 경계보다 앞이면 이전 경계를 그대로 둔다. 덮은 범위는 줄지 않는다.
- 새 경계가 덮게 된 `beyond` 항목은 지운다. 지금 목록에 없는 `beyond` 항목도 지운다.
- epoch마다 어떤 종류의 목록에서 썼는지(`frame`)를 함께 적는다.

```ocaml
type frame =
  | Message_history  (* Agent Core 기록, 공식 클라이언트 seed, ACP overflow의 시도 입력 *)
  | Canonical_turns  (* ACP 롤오버가 정식 턴 저장소에서 다시 만든 목록 *)
```

- `Leading` 위치와 턴 안 순번은 한 목록 안에서 센다. 같은 종류의 목록은 같은 기록을 같은 규칙으로 읽으므로 이름의 뜻이 같다. 종류가 다르면 같은 이름이 다른 atom을 가리킨다(§5.1).

### D3. 목록에서 덮인 앞부분을 찾는다

- 생산자는 같은 종류(`frame`)의 마지막 epoch이 적은 덮은 범위만 이어받는다. 같은 종류의 epoch이 없으면 덮인 것이 없다고 본다.
- 요약은 종류와 상관없이 마지막 epoch 위에 쌓는다. epoch 번호도 종류와 상관없이 하나로 센다.
- 경계 하나가 목록에 놓이는 결과는 셋 중 하나다.
  - `Covers_none`: 아무것도 덮지 않는다.
  - `Covers_through i`: 목록의 `i`번째 atom까지 덮는다.
  - `Not_in_list`: 경계의 턴이 목록에 없다. 덮은 것이 없다는 뜻이 아니다(§5.4).
- `Through_leading k`: 맨 앞 무명 atom 중 `Leading j`(`j ≤ k`)가 덮인다.
- `Through_turn {turn = b; extent}`: 목록에서 `b`의 첫 atom을 찾는다.
  - 찾지 못하면 `Not_in_list`다.
  - 찾으면 그 앞의 atom은 모두 덮인다. 기록은 뒤에 붙기만 하므로 `b`보다 앞선 atom은 `b`보다 먼저 버려졌다.
  - `Whole_turn`이면 `b`의 첫 이어진 구간이 덮인다.
  - `Up_to {ordinal = k}`이면 순번이 `k` 이하인 `b`의 atom 중 마지막 것까지 덮인다. 그 사이에 낀 다른 턴의 atom도 덮인다.
- 다른 종류의 경계는 턴으로 읽는다.
  - 정식 턴 목록의 경계는 `Whole_turn`이거나 순번 0의 `Up_to`다(D5). 둘 다 메시지 기록에서 같은 자리다.
  - 메시지 기록의 경계가 턴 T 안(`Up_to {T; k}`)이면 T의 최종 답 앞에서 멈췄을 수 있다. 순번 k는 최종 답 앞의 도구 왕복일 수 있다.
  - 그래서 정식 턴 목록에서는 T의 사용자 메시지까지만 덮였다고 본다. 행의 프롬프트가 비어 T에 사용자 메시지가 없으면, T 앞의 턴까지만 덮였다고 본다(§5.1).
  - 경계가 최종 답까지 닿았다면 그 답은 요약에 한 번 더 들어간다(§5.1).
- 요약의 앞(front)은 두 종류의 마지막 경계가 목록에서 덮는 곳 중 가장 뒤다.
  - 요약에는 앞보다 뒤에 있는 새 atom만 더한다. 그 앞의 새 atom은 보관만 한다. 요약이 이미 지나간 턴이라서, 더하면 옛 턴이 새 턴 뒤에 붙는다(§5.1).
  - 한 경계라도 `Not_in_list`면 앞은 하한(`Front_at_least`)이다. 요약이 실제로 담은 곳은 더 뒤일 수 있다. 그래서 앞보다 뒤의 새 atom에 요약이 담은 턴이 섞일 수 있다.
  - 그 atom도 요약에 더한다. 다만 「마지막 사용자 요청」은 따로 지킨다.
  - 직전 압축 지점의 관찰이 이름을 부른 턴이 요약이 담은 턴이다. 목록에서 그 턴들의 마지막 atom을 찾는다.
  - 그 atom과 그 앞의 atom은 「마지막 사용자 요청」을 바꾸지 않는다. 목록은 턴 순서를 지키므로, 그 앞의 요청은 요약의 요청보다 새롭지 않다.
  - 목록에 그런 턴이 하나도 없으면 막는 것이 없다. 덮인 행이 지워진 정식 턴 목록은 새 턴만 담으므로 그래도 맞다. 요약이 담은 턴의 행이 모두 ACP 임시 ID로 남았으면 옛 요청이 마지막 요청이 될 수 있다(§5.4, #55026).
  - 같은 턴이 목록 뒤에 다시 나오면 그 턴의 마지막 atom을 쓴다. 관찰 이름은 어느 턴을 담았는지만 말하고, 그 턴의 어느 구간을 담았는지는 말하지 않는다. 첫 구간 끝에서 멈추면, 요약이 뒤 구간까지 담았을 때 사이에 낀 턴의 옛 요청이 더 새 요청을 덮는다. 지금 규칙은 요청을 낡게 둘 수는 있어도 뒤로 돌리지 않는다.
  - `beyond`에 적힌 atom의 관찰은 세지 않는다. 진행 중인 턴의 도구 왕복이라, 요약이 그 턴의 요청은 아직 담지 않았다.
- `beyond`에 있는 atom은 생산자에게만 덮인 것이다. 소비자는 잘라 내지 않는다(D5).

### D4. 생산자는 새로 버린 atom만 인코딩한다

- 생산자 일곱 곳은 `~evicted_messages` 대신 `~messages`와 버린 atom(`prefix`, `later`)을 넘긴다.
- 목록 종류(`~frame`)도 넘긴다.
- ACP 생산자 둘(롤오버, 넘침 재시도)은 다음 새 세션이 시작할 목록을 압축한다. 넘침 재시도도 `force_fresh_retry`로 새 세션을 연다. 새 세션은 인계 목록(handoff list)에 무엇이든 있으면 그 목록에서 시작한다(`prefer_handoff_for_start`).
  - 요약이 있으면 인계 목록(요약과 행)을 `Canonical_turns`로 압축하고 최근 atom을 남긴다. 요약이 없어도 행이 기록의 첫 atom부터 있으면 같다. 새 세션은 요약과 settled 턴 뒤의 행으로 시작한다. atom이 둘 이하인 목록은 압축하지 않는다.
  - 요약이 없고 기록이 첫 행보다 앞선 턴을 담으면, `initial_messages`를 `Message_history`로 압축한다. 압축하는 곳은 행이 있는 턴의 첫 atom 앞까지다. Fresh state 뒤의 Keeper가 이 경우다.
    - 인계 목록은 행만 담고, 첫 행보다 앞선 턴은 담지 않는다. 그 턴은 요약으로만 새 세션에 닿는다.
    - 이 경계의 settled 턴에는 행이 없다. 그래서 watermark는 행을 지우지 않고, 인계 목록은 요약과 모든 행을 담는다.
    - 이어서 그 인계 목록을 요약이 있을 때처럼 압축하고 최근 atom을 남긴다. 새 세션은 요약과 최근 행으로 시작한다. 이 압축이 없으면 넘침 재시도가 행을 줄이지 못한다. 한 번의 실행에서 압축은 한 번뿐이라, 다음 재시도는 시작 창에서 오래된 행을 그냥 뺀다(#55004 6차 리뷰).
    - 요약을 커밋한 뒤 인계 목록을 읽거나 압축하지 못하면, 경고를 남기고 행을 그대로 둔다. 요약이 적용되지 않을 때(그 사이 기록을 지움)도 같다.
    - 생산자는 이 결과를 시작을 압축한 것으로 세지 않는다. 그래서 넘침 재시도는 다음 줄이기 때 다시 압축한다. 그때 요약이 적용되면 인계 목록을 압축한다. 생산자가 오류를 받으면 커밋된 epoch이 없다.
    - 행의 턴은 턴 ID가 같은지로 찾는다. 행이 ACP 임시 ID면 찾지 못한다. 그 턴은 요약에 들어가고 행으로도 한 번 더 간다(§1.5, #55026).
    - 기록에 있는 턴의 행부터는 요약한 턴보다 새롭다. 그보다 앞선, 기록에 없는 ID의 행만 압축되면 「마지막 사용자 요청」이 더 옛 요청으로 갈 수 있다(#55026). 다음 압축에서도 같은 일이 생겨서 여기서 따로 막지 않는다.
  - 요약이 없고 기록의 어느 턴에도 행이 없으면 `initial_messages`의 atom을 모두 압축한다. 행이 없거나, 행이 기록에 없는 ID(현재 턴의 ACP 임시 ID 등)만 달고 있는 경우다. 새 세션은 요약과 모든 행으로 시작한다.
    - 그 행은 압축하지 않는다. 행이 어느 턴인지 알 수 없다. 요약이 담은 턴을 ACP 임시 ID로 단 행일 수도 있고, 현재 턴이나 기록에 없던 턴의 행일 수도 있다.
    - 앞의 경우 행을 압축하면 그 턴을 한 번 더 담고, 「마지막 사용자 요청」이 더 옛 요청으로 갈 수 있다(§5.4, #55026).
    - 그래서 이 경우 넘침 재시도는 행을 줄이지 못한다. 재시도가 또 넘치면 다음 재시도가 시작 창에서 오래된 행을 뺀다. 요약이 담은 턴의 행이면 그 턴의 도구 호출·결과·답은 요약에 있다. 사용자 요청은 「마지막 사용자 요청」 하나만 요약에 남는다. 기록에 없던 턴의 행이면 그 세션은 그 턴을 보지 못한다.
  - 전에는 행이 있으면 인계 목록을 압축했다. Fresh state 뒤 첫 턴의 롤오버는 atom 둘짜리 목록이라 아무것도 압축하지 않았고, 새 세션은 그 한 턴으로 시작했다. 행이 없으면 최근 4분의 1을 남겼고, 그 atom은 요약에도 새 세션에도 들어가지 않았다. main도 같았다.
  - 정식 턴 저장소를 읽지 못하면 `initial_messages`를 `Message_history`로 압축하고 최근 atom을 남긴다. 저장소를 계속 못 읽으면 새 세션은 기록을 보낸다. 이유를 경고로 남긴다.
    - watermark는 seq만 읽어 생산자가 못 읽은 저장소에서도 돌 수 있다. 그러면 경계의 settled 턴까지 행을 지운다. 그 범위에 있는 기록에 없던 턴의 행은 요약 없이 사라진다(#55049).
    - 최근 atom을 남기면 이 범위가 남긴 atom 앞의 settled 턴까지로 줄어든다. 기록 전체를 압축하면 기록의 마지막 settled 턴까지 넓어진다. 범위를 줄일 뿐 없애지는 못한다.
    - 그 뒤 정식 턴 파일만 지워져 빈 저장소로 읽히면, 새 세션은 요약 하나로 시작하고 남긴 atom은 checkpoint 기록에만 있다. §7의 절차는 두 파일을 함께 지우므로 이 경우가 생기지 않는다.
  - 인계 목록에 요약만 있으면(덮인 행이 모두 지워졌다) 압축할 atom이 없다. 행이 있는 턴 뒤에 오면서 정식 턴 행이 없는 기록 턴(커밋 실패)은 요약에도 새 세션에도 들어가지 않는다. main의 롤오버도 같았다.
  - 압축 저장소를 읽지 못하면(`Compaction_store`) 압축을 건너뛰고 경고를 한 번 남긴다. 압축도 같은 저장소에서 실패하기 때문이다.
  - 그래서 요약이 적용되는 동안 ACP epoch은 정식 턴 목록에 쓰인다. 정식 턴 저장소를 읽지 못할 때만 메시지 기록에 쓰인다.
  - 기록을 지운 뒤 다음 압축 전까지는 그 전 요약이 적용되지 않는다. 다음 압축은 그 전 요약을 이어받아 새 epoch을 쓴다. 새 epoch은 적용되므로 지우기 전 관찰이 다시 새 세션에 간다(#55051).
  - 전에는 넘침 재시도가 메시지 기록을 압축했다. 그러면 재시도가 시작할 인계 목록은 watermark로만 줄었다. 행이 ACP 임시 ID를 달고 있으면 watermark도 움직이지 않는다(§1.5, #55049).
- 롤오버는 시작 창(`prepared.messages`)을 대신 압축하지 않는다. 경계는 그 앞을 모두 덮으므로, 창 앞의 턴이 보관된 것으로 셈해지고 watermark가 그 행을 지운다(#55004 2차 리뷰).
- 정식 턴 저장소는 압축 저장소를 읽다 실패하면 그 오류를 `Compaction_store`로 감싸 돌려준다. 전에는 정식 턴 저장소 오류에 `compaction.` 접두어를 붙였다. 그래서 압축 DB의 `Schema_not_current`가 정식 턴 저장소의 것처럼 보였다.
- 이름 짓기는 목록 전체를 한 번 훑는다. 메타데이터만 읽는다.
- 같은 종류의 이전 압축 지점이 덮은 atom과 `beyond`에 있는 atom은 건너뛴다. 새로 버린 atom이 없으면 `Ok None`이다.
- 새로 버린 atom만 JSON으로 인코딩해 보관한다.
- 쓰지 않던 `?blob_store` 인자를 없앤다. 생산자가 그 값을 만들려고 부르던 `require_reader` 확인도 없어진다.

### D5. 소비자는 메타데이터만 한 번 훑는다

- `messages_after_front`는 두 종류의 마지막 경계 중 더 앞선 곳(D3)과 inline 압축 지점 위치 중 뒤쪽 바로 다음부터 돌려준다.
- `beyond` atom은 잘라 내지 않는다. 덮인 구간 뒤에 있으므로 지금 epoch의 기록이다.
- 직렬화, 해시, 문자열 접두어 비교를 하지 않는다.
- 소비자는 두 종류 각각의 마지막 epoch 경계를 checkpoint 기록에서 찾아 더 앞선 곳에서 자른다. 두 경계의 턴이 기록에 있으면, 뒤처진 종류의 epoch이 가장 최근이어도 자르는 곳이 물러나지 않는다.
- 경계의 턴이 기록에 없으면 그 경계로는 자르지 않는다. 그래서 자르는 곳이 이전 호출보다 앞일 수 있다. 덜 자를 뿐, 요약이 담지 않은 것을 자르지는 않는다(§5.4).
- 두 읽기는 트랜잭션 밖에서 돈다. 사이에 커밋이 끼어도 둘 다 커밋된 epoch의 경계다. 그래서 더 앞선 곳도 어떤 epoch이 덮은 곳이다.
- 정식 턴 목록은 턴마다 atom이 둘 이하(사용자, 어시스턴트)다. 롤오버는 atom을 둘 이상 남긴다. 그래서 그 목록에서 쓴 경계는 `Whole_turn`이거나, 사용자 메시지까지 덮은 순번 0의 `Up_to`다. 둘 다 checkpoint 기록에서 같은 자리를 가리킨다.
- 저장소를 읽지 못하면 오류를 돌려준다. 도구 묶음은 경고를 남기고 기록 전체에서 도구를 이어 붙인다.

### D6. 정식 턴 저장소의 cutoff는 settled 턴으로 정한다

- cutoff는 `turn_id`가 압축 지점의 settled 턴과 같은 행의 seq다.
- settled 턴이 없거나 그 행이 없으면 cutoff를 바꾸지 않는다.
- epoch의 종류와 상관없이 그 epoch의 settled 턴을 쓴다. settled 턴의 atom은 같은 종류의 epoch들이 자기 목록에서 모두 보관했다.
- 보관 atom을 읽지 않고 메시지 글자를 맞춰 보지 않는다. `find_cutoff_seq_for_evicted_turns`와 `load_handoff_context`의 보관 atom 우회 경로를 지운다.

### D7. 저장소를 하드컷한다

- `<keeper>.compaction.db`에 `PRAGMA user_version`을 둔다. 표가 있는데 값이 다르면 `Schema_not_current`로 거절한다.
- 표: `compaction_epochs(epoch_id, frame, anchor_json, trigger_json, previous_epoch_id)`, `archived_atoms(epoch_id, sequence_ord, atom_json, messages_json)`. `frame`은 `message_history`와 `canonical_turns`만 받는다(`CHECK`). 기본 키는 `(epoch_id, sequence_ord)`다. 해시가 겹칠 일이 없어 `-ep` 꼬리를 붙이지 않는다.
- `compaction_epochs`에 `(frame, epoch_id)` 색인을 둔다. 도구 목록을 만들 때마다 종류별 마지막 epoch을 읽는다. 색인이 없으면 epoch이 없는 종류를 찾을 때 표 전체를 훑는다.
- `covers_through_turn` 열, `evicted_turn_ids_json` 열, `active_microcompacted_handles` 표를 지운다. 앞의 둘은 `anchor_json`과 `archived_atoms`에서 얻는다. 마지막 표는 운영 경로가 쓰지 않는다(D8).
- `<keeper>.canonical-turns.db`에도 `user_version`을 둔다. 이 저장소의 `history_resets.reset_after_anchor_epoch`, `compaction_watermarks.epoch_id`, `canonical_turns.compaction_epoch_id`는 압축 epoch 번호를 기억한다. 압축 DB만 새로 만들면 epoch가 1부터 다시 세어진다. 그러면 새 압축 지점이 리셋 전 것으로 무시되고, 같은 번호의 옛 watermark와 섞인다.
- 정식 턴 저장소에 남은 옛 열 추가 코드(`ALTER TABLE ... last_turn_id`)도 지운다.
- 옛 파일을 고치거나 옮기는 코드는 만들지 않는다.

### D8. 운영 경로가 부르지 않는 압축 파이프라인을 지운다

- `compact_and_project`, `project_for_provider`, `microcompact_turns`, `commit_epoch`, `list_epochs`, `load_archived_turn`과 이것만 쓰는 타입·표를 지운다.
- `keeper_compaction.mli`도 「운영 턴 드라이버는 `compact_evicted_messages`를 쓴다」고 적는다. `lib/`·`bin/`에서 부르는 곳이 없다(시험만 부른다).
- D6 뒤에는 `load_archived_turns_for_epoch`도 운영에서 부르는 곳이 없다. 같이 지운다.
- 이름 타입이 바뀌므로, 지우지 않으면 아무도 부르지 않는 코드를 새 타입에 맞춰 고쳐야 한다.

## 4. 바뀌는 동작

- 리더처럼 ACP로 도는 Keeper는 압축 지점 앞의 도구 호출을 더 이상 이어 붙이지 않는다. 지금은 해시가 맞지 않아 기록 전체의 도구를 이어 붙인다. `History_carry`의 원래 뜻(「압축 경계를 넘으면 깨끗하게 다시 시작한다」, `keeper_identity_tool_search.mli`)으로 돌아간다.
- 모델이 보는 압축 지점 글의 `covers_through=`와 `[turn:…]` 표시가 `covers=`와 `[atom:…]`로 바뀐다.
- 대시보드 API의 `covers_through_turn` 필드는 문자열로 남는다. 내용만 새 이름의 표시 문자열로 바뀐다. TUI는 이 문자열을 그대로 보여 준다.
- 턴 일부만 버린 압축은 그 턴의 정식 턴 행을 지우지 않는다(§2.3의 마지막 증상이 없어진다).
- 압축 저장소를 읽지 못하면 도구 묶음이 매 턴 경고를 남긴다. 전에는 아무 말 없이 기록 전체를 썼다.

## 5. 경계 조건과 한계

### 5.1 종류가 다른 목록의 덮은 범위는 이어받지 않는다

- 턴 안 순번은 목록 종류마다 다른 atom을 가리킨다. Agent Core 기록에서 턴 T의 순번 1은 첫 도구 왕복일 수 있다. ACP 롤오버 목록에서 T의 순번 1은 최종 답이다.
- 그래서 생산자는 같은 종류의 마지막 epoch만 이어받는다(D3). 다른 종류를 이어받으면 이런 일이 생긴다(#55004 리뷰).
  - Agent Core가 T의 도구 왕복까지 덮었다(`Up_to {T; 1}`). ACP 롤오버가 이 범위로 자기 목록을 보면 T의 최종 답이 덮였다고 보고 보관하지 않는다. 다음 롤오버가 그 뒤 턴을 settled로 적으면 T의 행이 지워진다. 답은 어디에도 남지 않는다.
  - ACP 롤오버가 T까지 다 덮었다. Agent Core가 이 범위로 기록을 보면 T의 도구 왕복을 건너뛴다. 정식 턴 행에는 도구 왕복이 없으므로 아무 데도 보관되지 않는다.
- 대가: 두 종류가 같은 턴을 한 번씩 보관한다. 보관한 atom은 잃지 않는다.
- 요약은 따로 지켜야 한다. 뒤처진 종류가 이미 지나간 턴을 보관하면서 요약에도 더하면 이런 일이 생긴다(#55004 2차 리뷰).
  - 옛 턴의 관찰이 새 턴 뒤에 붙는다.
  - 예산을 넘으면 앞 항목부터 지우므로 최근 턴이 먼저 빠진다.
  - 「마지막 사용자 요청」이 옛 턴으로 돌아간다.
- 그래서 요약에는 두 종류 중 더 앞선 경계 뒤의 새 atom만 더한다(D3). 그 앞의 atom은 보관만 된다. 요약은 원래 줄여 담는 글이라, 순서를 지키는 편을 고른다.
- 메시지 기록의 경계가 턴 T의 최종 답까지 덮은 `Up_to`였다면, 정식 턴 목록이 T의 최종 답을 요약에 한 번 더 넣을 수 있다. 한 턴의 답이 두 번 들어갈 뿐 순서는 지킨다.
- 메시지 기록의 경계가 턴 T 안이면 정식 턴 목록에서는 T의 사용자 메시지까지만 덮였다고 본다(D3). 행의 프롬프트가 비면 그 목록의 T는 최종 답 하나뿐이다.
  - 이때 T의 첫 atom까지 덮였다고 보면, 최종 답은 보관만 되고 요약에는 들어가지 않는다. 메시지 기록의 경계가 답에 닿지 않았다면, 답은 요약 어디에도 없게 된다(#55004 3차 리뷰).
  - 그래서 T 앞의 턴까지만 덮였다고 본다.
- Agent Core 창이 진행 중인 턴에서 버린 도구 왕복(`later`)은 버릴 때 요약에 더한다. 그래서 나중에 앞부분을 버리면, 그 도구 왕복보다 앞선 atom이 요약에서 뒤에 붙는다. main도 버릴 때 요약에 더했다(`evicted_messages_for_drop`). 이 RFC는 이 순서를 바꾸지 않는다.
- 관찰의 이름은 그 atom을 접은 목록 안의 이름이다. 이름에는 목록 종류가 없어서, 같은 순번이 종류마다 다른 atom을 가리킬 수 있다. 「마지막 사용자 요청」을 지키는 규칙(D3)은 순번을 보지 않고 턴 ID만 본다. 맨 앞 무명 atom은 위치로 보지만 새 기록에는 없다(§5.3).
- 요약은 종류와 상관없이 마지막 epoch 위에 쌓는다. 정식 턴 저장소의 cutoff는 종류와 상관없이 그 epoch의 settled 턴을 쓴다(D3, D6).

### 5.2 턴 중간의 참조 없는 사용자 메시지

- 지금 턴의 다음 순번이 된다(§1.4의 740개).
- 턴 ID 없이 시작한 턴이 있다면 앞 턴의 atom으로 센다. 생산자와 소비자는 같은 메시지를 같은 규칙으로 읽으므로 같은 목록에서는 이름이 어긋나지 않는다.

### 5.3 맨 앞 무명 atom

- 턴 ID를 찍기 전의 기록이다. 새 기록의 사용자 입력은 모두 턴 ID를 단다.
- 이름은 목록 맨 앞에서부터의 위치다. 같은 기록을 받는 생산자와 소비자는 같은 위치를 본다. Pinned 메시지는 세지 않는다. 그래서 공식 클라이언트가 앞에 붙이는 과거 작업 참조(System 메시지)는 위치를 바꾸지 않는다.

### 5.4 경계 턴이 목록에 없을 때

- 그 경계는 `Not_in_list`다(D3).
- 소비자는 그 경계로 자르지 않는다. 다른 종류의 경계가 기록에 있으면 그 경계로 자른다.
- 생산자는 같은 종류의 이전 경계가 목록에 없으면 덮인 것이 없다고 보고, 버린 atom을 모두 보관한다. 새 경계는 지금 목록 안에서만 정한다.
- 요약의 앞은 하한이다. 요약이 담은 턴이 관찰에 한 번 더 들어갈 수 있다. 「마지막 사용자 요청」은 요약이 담은 턴의 마지막 atom 뒤에서만 바뀐다(D3).
- 덜 자르거나 한 번 더 담을 수는 있어도, 덮지 않은 것을 잘라 내지는 않는다.
- 이런 경우가 있다.
  - 기록을 비운 뒤: 새 기록에는 옛 경계 턴이 없다. 자르지 않는 것이 맞다.
  - ACP가 다시 만든 목록: watermark 뒤의 행만 담는다. 경계 턴이 다 덮였으면 그 행은 지워져 목록에 없다. 목록은 그 턴 뒤에서 시작하므로, 새 atom은 요약이 담지 않은 턴이다. 요청을 지키는 규칙은 막는 것이 없다.
  - 경계 턴의 행이 없을 때: 그 턴의 정식 턴 커밋이 실패했거나, 행이 아직 ACP 임시 ID를 달고 있다(§1.5, #55026). watermark가 움직이지 않아 덮인 행이 목록에 남는다(#55049). 그 행들은 관찰에 한 번 더 들어간다. 요약이 담은 다른 턴의 행이 목록에 있으면 요청은 바꾸지 않는다. 요약이 담은 턴의 행이 모두 임시 ID로 남았으면 막을 것이 없다. 그 행들의 요청이 마지막 요청이 될 수 있고, 예산이 모자라면 오래된 턴의 중복 관찰이 남고 더 새 턴의 관찰이 먼저 빠질 수 있다(#55026).
  - 공식 클라이언트 seed가 경계 턴보다 뒤에서 시작할 때: 버린 atom을 한 번 더 보관한다. 지금(`drop_covered_turns`가 못 찾으면 전부 보관)과 같다.

## 6. 하지 않는 것

- `hydrate_missing_turns`의 글자 비교는 압축 지점을 읽지 않는다. #55025로 남겼다.
- ACP 정식 턴 행을 처음부터 Keeper 턴 ID로 쓰는 일. ACP 런타임에 턴 ID를 넘기는 경로가 없어 따로 다룬다(#55026). 이 RFC는 임시 ID와 함께 동작한다(§1.5). 임시 ID로 남은 행이 생기는 일은 §5.4에 적었다.
- watermark를 settled 턴 하나로 정하는 방식은 그대로 둔다. 그 턴의 행이 없으면 멈추고, 압축한 목록에 없던 행은 보관 없이 지운다. 바꾸면 지우는 범위가 달라져서 #55049로 따로 다룬다.
- `atom_hash` 밖의 `Utf8_sanitize` 15회(§1.1)는 배포 뒤 다시 재고 판단한다.
- checkpoint 저장 시간(11-26 로그 7,141건, p50 111 ms, p99 5,354 ms)은 #55034로 남겼다.
- `History_carry` 계산을 배치 정책 확인 뒤로 미루는 일. D5로 비용이 작아져 이 RFC에서는 하지 않는다.

## 7. Fresh state required

서버를 모두 멈춘 뒤 Keeper마다 아래 파일을 지운다.

- `<base>/.masc/config/keepers/<keeper>.compaction.db`와 옆의 `-wal`, `-shm`, `-journal`
- `<base>/.masc/config/keepers/<keeper>.canonical-turns.db`와 옆의 `-wal`, `-shm`, `-journal`

지우면 이렇게 된다.

- 모든 Keeper가 압축 요약을 잃는다.
- Agent Core와 Claude Code·Codex·Antigravity Keeper는 다음 압축 때 checkpoint 기록에서 요약을 다시 만든다. checkpoint 기록은 앞에서 잘리지 않았다(§1.2).
- ACP Keeper도 지운 뒤 첫 롤오버나 넘침 재시도 때 checkpoint 기록에서 첫 행보다 앞선 턴을 요약한다. 새 세션은 그 요약과 지운 뒤 쌓인 최근 행으로 시작한다(D4). ACP 에이전트 자신의 세션은 그대로다.
- 아직 덮이지 않은 정식 턴 행(11-26 기준 리더 3행, code-reviewer 1행, msx 18행)이 사라진다.

지우지 않으면 새 빌드는 두 저장소를 `Schema_not_current`로 거절하고 경고를 남긴다. 압축은 커밋되지 않는다. 소비자는 기록을 자르지 않는다. 서버는 멈추지 않는다. blob 정리는 옛 압축 DB에서 멈춘다(참조를 읽지 못하면 지우지 않는다).

## 8. 검증

### 8.1 feature 시험

- 다시 만든 목록(ACP)으로 만든 압축 지점이 실제 기록을 그 턴 뒤에서 자른다.
- ACP 임시 ID를 단 마지막 턴이 있는 목록도 압축된다. 경계는 그 앞 턴이다.
- Agent Core의 현재 턴 도구 왕복 버리기(앞부분이 아닌 버리기) 뒤 같은 목록으로 다시 커밋하면 `Ok None`이다. 다음 앞부분 버리기는 이미 보관한 atom을 다시 보관하지 않는다.
- 경계 턴이 목록에 없으면 소비자는 자르지 않는다.
- 턴을 다 덮은 압축 지점은 정식 턴 저장소의 그 턴 행까지 지운다. 일부만 덮었으면 바로 앞 턴까지다.
- 옛 형식(`user_version` 0, 표 있음) 압축 DB와 정식 턴 저장소는 `Schema_not_current`로 거절된다.
- 맨 앞 무명 atom만 버린 뒤 턴 atom을 버리면 무명 atom을 다시 보관하지 않는다.
- Agent Core가 턴 T를 일부만 덮은 뒤 ACP 롤오버가 압축하면, 롤오버가 T의 최종 답을 자기 목록에서 보관한다. T의 행은 그 뒤에 지워진다.
- ACP 롤오버가 T까지 덮은 뒤 Agent Core가 압축하면 T의 도구 왕복을 보관한다.
- 다른 턴이 사이에 낀 턴은 `Up_to`로 적힌다. 덮인 끝이 경계와 같고, 다음 압축은 새 atom만 보관한다.
- 압축 여섯 개가 도메인 풀에서 동시에 돌아도 쓰기 충돌 없이 epoch 여섯 개를 만든다.
- ACP 롤오버가 앞선 뒤 메시지 기록이 그보다 뒤처진 자리까지 압축하면, 보관은 하되 요약과 「마지막 사용자 요청」은 그대로다. 소비자는 여전히 롤오버 경계에서 자른다. 롤오버 경계를 넘는 다음 압축은 넘는 턴만 요약에 더한다.
- Agent Core가 턴 T를 일부만 덮은 뒤의 롤오버는 T의 최종 답을 요약에도 더한다.
- ACP 롤오버와 넘침 재시도가 압축하는 목록:
  - 요약 없이 최근 턴에만 행이 있으면(Fresh state 뒤) 메시지 기록에서 첫 행보다 앞선 턴까지만 압축하고, 이어서 인계 목록을 압축해 마지막 행을 남긴다. 「마지막 사용자 요청」은 요약한 행의 것이다. 새 세션은 요약과 마지막 행으로 시작한다.
  - 그 뒤 압축은 인계 목록만 압축한다.
  - 인계 목록이 행 하나뿐이면 기록만 압축하고, 행 뒤에 현재 턴의 행이 있으면 그 행을 남긴다.
  - 행이 기록에 없는 ACP 임시 ID만 달고 있으면 기록을 모두 압축하고, 행은 하나도 지우지 않는다. 「마지막 사용자 요청」은 기록의 마지막 요청이다.
  - 넘침 재시도는 시작 목록을 압축했을 때만 그 실행을 압축한 것으로 적는다. 남은 atom이 둘이면 아무것도 커밋하지 않는다.
  - 요약을 커밋한 뒤 인계 목록을 못 읽거나, 요약이 적용되지 않거나, 압축이 실패하면 행을 모두 남기고 시작을 압축한 것으로 세지 않는다.
  - 행이 기록의 첫 턴부터 있으면 인계 목록을 압축한다.
  - 행이 없으면 받은 메시지 기록을 모두 압축하고, 새 세션은 요약 하나로 시작한다.
  - 정식 턴 저장소를 읽지 못하면 기록을 압축하되 최근 atom을 남기고, 새 세션은 기록으로 시작한다.
  - 압축 저장소를 읽지 못하면 압축하지 않는다.
- 정식 턴 저장소가 압축 저장소를 읽다 실패하면 `Compaction_store`로 돌려준다.
- 경계가 목록에 놓이는 결과는 덮은 것 없음, 어디까지 덮음, 목록에 없음으로 나뉜다.
- 메시지 기록의 턴 안 경계는 정식 턴 목록에서 그 턴의 사용자 메시지까지 덮는다. 프롬프트가 빈 행이면 그 앞 턴까지만 덮는다. 다른 경계가 목록에 없으면 앞은 하한이다.
- 프롬프트가 빈 행의 최종 답은 롤오버 요약에 들어간다.
- 경계 턴의 행이 없을 때, 그 앞까지의 롤오버는 「마지막 사용자 요청」을 바꾸지 않는다. 그 턴 뒤까지의 롤오버는 바꾼다. 메시지 기록에 없던 행도 요청을 되돌리지 않는다.

### 8.2 측정

- 수정 전: §1.1의 `sample` 결과.
- 수정 후: 같은 Keeper 구성으로 서버를 띄운 뒤 같은 명령으로 30초를 뜬다. `live_history_after_latest_anchor` 아래 inclusive 샘플 수와 `atom_hash` 유무를 비교한다. `Utf8_sanitize`의 inclusive 샘플 수도 비교한다.
- 명령: `sample <masc pid> 30 -file <out>`. 운영자가 새 빌드를 설치하고 Fresh state를 마친 뒤 돌린다.
