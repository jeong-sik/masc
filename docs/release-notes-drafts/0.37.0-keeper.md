# v0.37.0 release notes — keeper · Librarian · memory-health

Draft for the release owner (task-1690). Covers the 13 numbers in the task:
keeper `#37793 #37821 #37855 #37875 #37879 #37901 #37933`, librarian ·
memory-health `#37362 #37840 #37856 #37870 #37896 #37941`.

Two of the thirteen are **issues, not PRs** — `#37793` (open) and `#37362`
(closed by `#37941`). They are cited below where they are the tracking record

Do not merge this file into `CHANGELOG.md`; the release owner composes that in

## Added

- The keeper memory health screen now says how far the Librarian's snapshot
  lags the position it has actually read to. The request a keeper sends starts
  at the snapshot's cut and carries the atoms up to the read position as raw
  text, so the distance between the two numbers is what that turn pays — but
  the screen carried only the cut, and an ordinary one-turn lag looked the
  same as a lag built up by a day of failed passes. `context_cycle` now carries
  `read_position` from `librarian-progress.json`, `read_position_read_error`
  when that file cannot be read (so a keeper that read nothing is told apart
  from one whose position is unknown), and `rewriting_through` while a snapshot
  is being rewritten from atom 0. The TUI `Context saved` line reads
  `read to atom 12887, 5193 atoms past the cut`. The difference is computed,
  never stored, so the three values cannot drift apart. Measured on
  2026-09-22: `goo-yang-bong` cut at 7694 and read to 12887 — 5,193 atoms —
  while its keeper turn looked healthy (`origin=librarian_progress
  atoms=1/12888`). The continuity lag is also shown beside the durable lag,
  read directly from the two files rather than from a value a pass publishes,
  so a keeper that has not run since boot still shows its lag. A lag that
  cannot be measured (no snapshot, an unreadable file, two different traces,
  or a snapshot ahead of the position) answers `null`, never `0` — `0` means
  caught up — and the fleet total adds only what it measured, with
  `librarian_continuity_unmeasured` beside it so the sum cannot read as "the
  fleet is fine" (#37840, #37856).
  UPGRADE: the memory health JSON gained fields, and both decoders
  (`tui_decode`, the dashboard's `exactKeys`) reject an object with an unknown
  key rather than ignoring it. A new server with an older TUI or dashboard
  cannot draw the Memory screen; roll the server and the clients back together.
- The official-client lanes (Claude Code, Antigravity) decide in one place,
  before sending, whether a request carries the Librarian working state
  (`Keeper_official_client_host.compose_librarian_range`). The working state is
  carried only when the composed request still holds the newest atom and as
  many atoms as the same request without it; otherwise the request goes without
  the working state and the turn is not refused, with a WARN naming the first
  atom and
  `masc_keeper_librarian_working_state_not_carried_total{keeper,runtime,reason}`
  where `reason` is `displaces_atoms`, `leaves_no_turn` or `does_not_fit`. This
  removes the second cut `#37821` added (it dropped the atoms just after the
  working state, leaving a band that was neither covered nor sent) and the
  front-specific `allow_empty_history` of `#37835` (a request with no turn to
  answer is now stopped by the "newest atom" rule). Two Antigravity
  off-by-ones are fixed with it: a dropped preamble was counted as a durable
  atom, and a preamble already in the range was cut again (#37879).
  UPGRADE: a request that used to carry the working state may now go without
  it when it would displace atoms, so the request composition — and with it the
  token profile — changes for those turns.

## Fixed

- A continuity pass whose request was refused for size now carries its
  narrowed width to the next pass, and the size verdict is taken over the whole
  walk instead of its last slot. `goo-yang-bong` walked
  `12,756 → 6,378 → 3,189` and started over at `12,756` on the next pass 96
  times in one day: the narrowed width was not remembered, and the verdict hung
  on the last slot, so a GLM `context_overflow` followed by a DeepSeek
  `invalid_request` read as "not a capacity refusal" and ended the pass one
  step short of fitting. The width is now remembered per keeper in the loop's
  memory, and a pass narrows only when every failure in the walk is one that
  would be refused at any size; a refusal that is not about size (a quota,
  overload, server or network failure, an operator refusal, or a failure that
  never reached the provider) keeps the width. A failed pass is not retried in
  place — it records the width and waits for the next signal — and the width is
  released only when the backlog was read to its end. The verdict is positive
  (`walk_shows_size`, `List.exists`) rather than negative (`List.for_all`),
  which removes the empty-list default that narrowed the width when no failure
  had been seen at all — a snapshot commit failing on a CAS or disk error used
  to halve the read width and log `no provider attempt settled the pass`. The
  `Completion_failed` classification this depended on is carried by the
  `#38108` entry already in `[Unreleased]`; this entry is the width carry and
  the verdict polarity. Live confirmation: after `#37855` merged, the next pass
  read the carried width 1,594 instead of restarting at 12,756 (#37855,
  #37875). Reported by `#37793`.
- The tool-call log's recorded result is read by one rule. `#37487` removed the
  top-level `success` field from `.masc/tool_calls/*.jsonl` — the result is now
  in `disposition` and `wire_outcome` — but four OCaml readers still read
  `success`, so from 2026-09-21 06:47Z every successful call showed as
  `-> REJECTED` in the keeper's own "Your Recent Actions" (with the input
  attached, since only refusals carry it), every file change read
  `succeeded=false`, the trust timeline read "outcome unknown", and
  `masc_trace` drew `-`. On 2026-09-22, 17,664 of 17,664 rows had no `success`
  while `wire_outcome` was `ok` on 17,225 (97.5%). `Tool_result.recorded_call_outcome`
  is now the one rule: `disposition` first (`completed` success, `failed`
  failure, `deferred` kept apart), then `wire_outcome` (`ok`/`error`/`unknown`),
  with a wrong type or unknown spelling as `Recorded_malformed` rather than a
  guess. Deferred and unknown rows no longer carry their input in Recent
  Actions. In the TUI, `kc_success : bool` becomes
  `kc_outcome : Tool_result.recorded_call_outcome`, so a deferred call draws
  `◌` and an unknown one `?` instead of being drawn as success or rejecting the
  whole keeper-calls screen (#37901).
- The media decision's public projection keeps the two values that say what
  happened. `image_occurrences` (on a `delegated` row) and
  `required_modalities` (on a `degrade_unavailable` row) were not in
  `decision_public_allowlist`, so a public view such as the dashboard kept only
  the routing action and the runtime id — how many images were converted, and
  which input blocked the turn, were gone. Both keys are now in the allowlist,
  and the `degrade_unavailable` comment is corrected to say the branch is
  reached only when the scan, the image conversion and the strip disagree
  (#37933).
- The continuity lag and the read position are read from the runtime keepers
  directory. `#37856` and `#37840` read `librarian-progress.json` from the
  config keepers directory, but the Librarian writes it under
  `Workspace.keepers_runtime_dir` — the journal and snapshot live flat under
  config, the position lives per keeper under runtime. Both arguments were
  named `keepers_dir`, so the wrong root type-checked: live, all 13 keepers
  read `continuity_unread_atoms: null` and all 19 read `read_position: null`
  while `goo-yang-bong` had read to 12984. Both handlers now pass
  `runtime_keepers_dir`, and the tests write to the runtime root and assert the
  two roots differ first, so a future mix-up fails in the test rather than in
  the live server (#37870, #37896).
- The Librarian reads a trace that sits between the one it stopped on and the
  current one. When a keeper is recreated, its trace changes; if the Librarian
  was stopped on trace A and the keeper moved through B to C, the hand-off knew
  only A and C, so B's turns were never read even though B's checkpoint was
  still on disk. The hand-off now reads the traces that started after A, in the
  order their first line appears in `turn-boundaries.jsonl`, each from 0 and
  stopping at the current trace; a trace with nothing to read or a checkpoint
  from a discarded version is passed in the same pass, while a damaged
  checkpoint stops it and names the trace. The lower boundary for the other
  party's speech is kept separate from the atom position, so it survives the
  hand-off. No operator action is needed: on 2026-09-23 all 14 keepers with a
  turn-boundary record had the same trace in their progress file and their meta
  (#37941, closes #37362).

## Not shipped changes in this set

- `#37821` (Claude Code re-cuts the carried range at the declared ceiling when
  the working state is carried) was merged and then removed by `#37879`, which
  decides the same question in one place before sending. Its behavior did not
  reach any tag; the `#37879` entry above is the shipped behavior.
- `#37793` is an open issue, not a PR: it reports that a continuity pass that
  keeps failing grows the snapshot lag without bound and that the screen did not
  show it. The screen half is `#37840`/`#37856`; the feedback loop itself is
  still open and is not in this release.
