### Fixed

- An Antigravity login names its account by its email alone. masc reads the
  email once as email text and no longer requires the CLI's `auth_method` and
  `token` keys, which it never reads. A login keychain item is read the way
  go-keyring's `Get` reads it, in the managed HOME check and in setup's
  import: spaces trimmed, then `go-keyring-encoded:` as hex,
  `go-keyring-base64:` as base64, and any other value as the login itself.
  An item with a byte outside printable ASCII is refused, because
  `security -w` hands `Get` such an item as hex text.
  An item that decodes to a blank login asks for sign-in and changes nothing,
  as a blank login file does. When setup reopens a private account whose
  saved login masc cannot read, its message says so instead of naming an
  unavailable private directory (#49313).

### Changed

- A login whose `id_token` or `id_token_email` holds an empty string next to
  the other key is refused for holding both keys. Before, an empty string
  counted as no value (#49313).
- Setup's import copies a keychain item decoded and trimmed, as go-keyring
  reads it, and refuses an item that does not decode or holds a byte outside
  printable ASCII. Before, it copied the item as it was (#49313).

### Known issues

- masc cannot read a keychain item agy wrote, because its ACL admits only
  `/usr/bin/security`. A managed HOME's keychain account is never compared
  with the selected account, and setup's import from a keychain that holds an
  agy item always stops with `Keychain_unavailable` (#49313, #49243).
- The login-capture path (`runtime_setup_login_client.ml`) still reports
  every private-account preparation error as `Import_failed`, including the
  new `Unrecognized_managed_credential` (#49313).
- An address Google gives to another account selects the previous holder's
  account generation, and that generation's managed credential stays in use
  (#49313).
