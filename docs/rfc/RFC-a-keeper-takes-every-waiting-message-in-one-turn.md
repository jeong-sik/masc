# RFC: 기다리던 메시지는 한 턴에 전부 들어간다 — 큐는 업무 종류를 모른다

11-13~16 사흘 동안 Keeper 채팅 작업이 큐에서 기다린 시간은 934.8시간이다. 바로 앞 사흘은 14.2시간이었다.
늘어난 몫의 대부분은 리뷰 Keeper 일곱이다. 여러 세션이 같은 Keeper 에게 메시지를 보내면, 메시지마다 실행을 하나씩 따로 돈다.
이 RFC 는 claim 때 기다리던 메시지 전부를 도착 순서대로, 메시지마다 봉투를 단 채 한 턴에 넣자고 제안한다.
답은 요청마다 따로 간다. 큐는 업무 종류를 모르고, 묶는 기준은 업무와 관계없는 사실뿐이다.
묶음을 넓히기 전에 큐가 멈추는 경로 넷을 먼저 고친다.

- 다루는 것: 채팅 작업 줄(`Chat_operation_store.claim_next`)의 묶음, 요청별 답, 실행 슬롯이 멈추는 경로.
- 다루지 않는 것: 업무 종류별 갈래, 도는 턴을 끊는 일(`RFC-backlog-never-preempts-a-running-turn` 이 정했다), 끝나지 않는 턴(§7 열린 질문).
- 근거 기준: main `706704b625a5`(2026-11-16)에서 읽었다. 인용한 파일은 이 브랜치의 base `15e3c60e915c` 에서도 같다.
- 측정: [`docs/evidence/chat-queue-wait-2026-11-16/`](../evidence/chat-queue-wait-2026-11-16/README.md). 2026-11-16 02:10Z~02:40Z 에 읽었다. 같은 창도 읽는 시각에 따라 합이 달라진다(README 「Limits」).

## 0. 요약

- **[사실]** 큐 대기 합은 765건 14.2시간에서 875건 934.8시간이 됐다. 리뷰 Keeper 일곱이 898.0시간이다.
- **[사실]** 리뷰 Keeper 일곱의 채팅 작업 772건은 실행 686개로 돌았다. 다른 작업의 실행에 묶여 돈 작업은 86건(11%)이다.
- **[사실]** 채팅 작업 한 건의 평균 실행 시간이 2~6분에서 10~19분으로 늘었다. 같은 때 runtime 이 glm-5.3-flash 계열로 바뀌었다. 원인은 확인하지 못했다.
- **[사실]** 리뷰 Keeper 는 슬롯 시간을 자율 턴 155.1시간, 직접 턴 171.7시간으로 나눠 썼다. 큐에 채팅이 있는데 채팅이 안 돈 117.1시간 중 56.9시간은 자율 턴이 슬롯을 잡고 있었다.
- **[결정]** 큐는 업무 종류를 모른다. 리뷰를 따로 다루지 않는다(§1).
- **[제안]** 1단계: 큐가 멈추는 경로 넷을 고치고, 실행 구간을 사실로 남긴다(§4.1).
- **[제안]** 2단계: claim 때 기다리던 메시지 전부를 봉투째 한 턴에 넣는다(§4.2).
- **[제안]** 3단계: 답을 요청마다 따로, 각자의 답할 곳으로 보낸다(§4.3).
- **[사실]** 117.1시간 중 35.5시간은 기록된 어느 턴과도 겹치지 않는다. 그중 22.6시간은 디스크 가득 참, 서버 다운, 재시작으로 끝나 기록이 없는 턴이다(§3.2). 12.9시간은 나누지 못했다.

## 1. 운영자 결정 (2026-11-16)

1. **큐는 업무 종류를 모른다.** 리뷰만 따로 다루면 하드코딩이 생긴다. 다음엔 배포 요청, Jira 요청도 같은 식으로 늘어난다.
   큐가 아는 것은 도착 순서, 보낸 사람, 답할 곳, 지시뿐이다. 업무 종류를 가르는 코드가 있으면 지운다.
2. **메시지는 한 번에 쭉 들어간다.** 어느 메시지가 낡았는지, 무엇을 먼저 할지는 Keeper 가 함께 읽고 고른다.
3. **휴리스틱과 숫자 장치를 두지 않는다.** 글자·의미 유사도·LLM 분류기로 메시지를 가르지 않는다. debounce, 개수 상한, cooldown, 라운드 상한도 두지 않는다(constitution `magic_number`, `string_matching`, `budget_gate`).
4. **가장 중요한 것은 멈추지 않는 것이다.** 메시지는 Keeper 턴이 계속 끝나는 한 결국 어떤 턴에 닿아야 한다.

정하지 않은 것: 끝나지 않는 턴을 어떻게 받을지(§7-1).

## 2. 지금 모양

### 2.1 한 번에 하나만 돈다

- `claim_next` 는 `running` 행이 하나라도 있으면 아무것도 꺼내지 않는다(`keeper_chat_operation_store.ml:2008-2012`).
- `semantic_executions` 에도 `running` 은 하나뿐이다(unique index `semantic_single_running`).
- 자율 턴과 직접 턴은 owner 의 슬롯 하나(`turn_in_flight`)를 나눠 쓴다. 도는 턴을 끊지 않는다(#51221, #47961).

### 2.2 묶음은 같은 출처의 연속 구간뿐이다

- `select` 는 맨 앞 작업과 출처 전체, 답할 곳, 지시, `surface_context` 가 같은 작업만 모은다(`keeper_chat_operation_batch.ml:12-14`, `:52-54`).
- 다른 작업을 만나면 거기서 멈춘다(`:60`). 그래서 연속 구간만 묶인다.
- 묶인 메시지는 `"\n\n"` 으로 이어 붙인 문자열 하나가 된다(`:67`). 메시지마다의 출처와 받은 시각은 실행 입력에서 사라진다.
- store 는 멤버를 claim 트랜잭션에서 고정하고, 원래 입력을 `admitted_input_json` 에 남긴다(`keeper_chat_operation_store.ml:1978-1989`). 묶음이 claim 뒤에 커지지는 않는다.
- 이어 받는 작업(continuation)을 만나면 구간이 끝난다(`:1943-1958`).

### 2.3 실행은 맨 앞 작업의 출처로 돌고, 같은 답을 모두에게 보낸다

- 실행기는 맨 앞 작업의 `source` 로 payload 를 만든다(`server_routes_http_keeper_stream.ml:2596-2601`, `:2871`).
- Keeper 가 보낸 요청이면 같은 종단 결과(`Delegate_replied` 또는 `Delegate_no_reply`)를 멤버마다 보낸다(`:2805-2830`).
- `event_for_member` 는 실행의 stream 이벤트를 멤버마다 복사한다. 도구 이벤트와 `Text_delta` 도 복사된다(`keeper_chat_operation_batch.ml:73-85`).

### 2.4 큐를 멈추게 하는 경로

1. **실패 뒤 `Running` 이 남는다.** 턴이 예외, 저장소 오류, 배달 실패로 끝나고 native call 이 열려 있으면, 정책은 `Leave_active_call_for_restart` 를 고른다(`keeper_owner.ml:957-975`).
   그러면 행이 `Running` 으로 남는다(`:1797-1805`). `claim_next` 는 재시작 전까지 다음 작업을 꺼내지 않는다. wake 를 더 보내도 풀리지 않는다.
   11-10~11-16 로그에는 이 경고가 0번 나왔다. 지금은 잠재 경로다.
2. **runtime 재시도는 옛 순번을 그대로 쓴다.** 협력 checkpoint 는 새 `sequence` 를 받아 줄 뒤로 간다(`keeper_chat_operation_store.ml:2801-2808`).
   runtime 재시도는 `requeue_continuation_with_db` 만 부르고 순번을 바꾸지 않는다(`:2675-2687`). `not_before` 가 지나면 줄 맨 앞을 다시 차지한다.
3. **슬롯이 비면 채팅이 먼저 받는다.** owner 는 턴이 끝나면 `start_child_if_needed` 로 채팅을 먼저 꺼낸다. 자율 턴은 남은 슬롯만 받는다(`keeper_owner.ml:585-599`, `:1828-1832`).
   채팅이 계속 들어오면 이벤트 큐의 결과 알림(`Tool_result_ready`, `Delegate_completed`, 일정 영수증)이 밀린다. 반대로 자율 턴이 돌 때 온 채팅은 그 턴이 끝날 때까지 기다린다.
4. **배달이 끝날 때까지 슬롯을 잡는다.** 실행기는 턴이 돌아온 뒤 `Eio.Promise.await delivery` 를 기다린다(`server_routes_http_keeper_stream.ml:2895`). 외부 채널 배달이 늦으면 다음 실행도 늦어진다.

### 3.3 끝나지 않는 턴

모델이 라운드마다 닫는 말을 쓰고 도구를 다시 부르면 턴이 끝나지 않는다. 지금 이 턴을 멈추는 길은 운영자 턴 중단(`POST /api/v1/keepers/turn/interrupt`)뿐이다.
`RFC-arrived-stimuli-reach-the-running-turn` 은 이 버릇을 다루지 않는다고 적었다. 이 RFC 도 고치지 않는다(§7-1).

## 4. 제안

### 4.1 1단계 — 큐가 멈추는 경로 넷을 고치고, 실행 구간을 남긴다

1단계는 묶음과 관계없이 먼저 들어간다. 묶음을 넓히면 한 실행이 더 많은 요청을 안는다. 그 실행이 멈추면 더 많은 요청이 같이 멈춘다.

1. **실패한 실행은 슬롯을 놓는다.** child 가 끝났다는 사실과 정확한 native call 을 대조해 정산한다. 재시작을 기다리지 않는다.
   시간이 지났다는 이유로 죽은 실행으로 판정하지 않는다(constitution `no_wall_clock_death`). 결과를 모르는 외부 효과는 `Effect_uncertain` 같은 사실로 남기고, 다시 실행할 근거로 쓰지 않는다.
   이전 실행이 결과를 늦게 써 넣지 못하게 실행 정체(execution identity)로 막는다.
2. **실행 기회 순번을 접수 순번과 나눈다.** 원래 접수 순서(`sequence`)는 그대로 둔다. 실행 기회를 다시 받는 사건마다 새 순번을 붙인다.
   runtime 재시도, 입력 대기, 재시작 재개도 협력 checkpoint 처럼 줄 뒤로 간다. 실패 횟수로 벌점을 주는 일은 아니다. 이미 실행 기회를 쓴 작업과 아직 한 번도 입력에 닿지 못한 작업을 옛 순번으로 경쟁시키지 않는다.
3. **슬롯이 비면 먼저 온 쪽이 받는다.** 채팅 작업은 `created_at` 을, 이벤트 큐 행은 `arrived_at` 을 가진다. 슬롯이 비면 두 줄에서 가장 오래 기다린 입력이 있는 쪽이 턴을 시작한다.
   가중치나 우선순위가 아니라 도착 순서다. 지금 슬롯 해제 알림(`notify_turn_slot_released`)은 "채팅이 먼저 가져가고 남으면 알린다"는 뜻이다. 이 알림의 뜻도 같이 바뀐다.
4. **배달은 슬롯 밖에서 한다.** 실행의 종단 결과와 요청별 배달 의도를 같은 트랜잭션에 쓴다. 슬롯은 그때 놓는다. 배달은 그 기록을 읽어 따로 진행한다.
   배달이 끝나기 전에 서버가 죽으면 기록이 남아 있으므로 모델을 다시 돌리지 않고 배달만 다시 한다.
5. **실행 구간을 사실로 남긴다.** 작업이 슬롯을 잡은 구간마다 시작과 끝(정산, 실패, 재시작으로 끊김)을 덧붙여 쓴다. `started_at` 을 덮어쓰지 않는다.
   관측용 사실이고 다음 행동을 정하는 데 쓰지 않는다. §3.2 의 uncle 9시간처럼 재시작으로 끊긴 실행도 다시 셀 수 있게 된다.

### 4.2 2단계 — claim 때 기다리던 메시지 전부를 봉투째 넣는다

- claim 은 맨 앞 작업부터 이어 받는 작업을 만나기 전까지, 기다리던 새 작업 전부를 도착 순서대로 고른다. 보낸 사람, 답할 곳, 채널이 달라도 함께 고른다.
- 멤버는 지금처럼 claim 트랜잭션에서 고정한다. 그 뒤에 온 메시지는 다음 claim 으로 간다.
- 메시지를 문자열 하나로 잇지 않는다. 실행 입력은 봉투의 목록이다. 봉투 하나에는 다음 칸이 있다.

  | 칸 | 출처 |
  |---|---|
  | `operation_id` | 작업 |
  | `received_at` | `created_at` |
  | `submitted_by`, `sender_keeper`, `surface`, `channel` | `decoded_source` |
  | 답할 곳 | `continuation_channel` |
  | 본문, `user_blocks`, 첨부 | `decoded_input` |

  업무 종류 칸은 없다. PR 번호, head, 「리뷰 요청」 표시도 없다.
- 묶음을 끊는 자리는 둘이다. 둘 다 업무와 관계없는 사실이다.
  1. 이어 받는 작업. 이미 시작한 실행을 잇는 작업이라 새 묶음에 들어가지 않는다(지금과 같다).
  2. provider 가 크기로 거절했다는 typed 사실. 그때만 순서를 지키며 앞에서부터 나눈다. 같은 입력을 그대로 다시 보내지 않는다.
- `A1, B, A2` 처럼 다른 출처가 끼어도 셋을 순서대로 모두 넣는다. B 를 건너뛰고 A1·A2 만 앞당기지 않는다. 전부 넣으므로 건너뛸 일이 없다.
- 지시(`turn_instructions`, `surface_context`)가 다른 작업을 어떻게 다룰지는 정하지 않았다(§7-2). 정하기 전까지는 지시가 바뀌는 자리에서도 묶음을 끊는다.

리뷰 상황은 일반 규칙으로 풀린다. 리뷰 요청(n), 「head 가 바뀌었다」(n+1), 「병합됐다」(n+2), 「앞 메시지 정정」(n+3)이 한 턴에 같이 보인다.
어느 요청이 낡았는지는 Keeper 가 읽고, 필요하면 GitHub 를 직접 보고 고른다.

### 4.3 3단계 — 답은 요청마다 따로 간다

- Keeper 는 답을 요청 ID 에 묶어 낸다. 자유문 답을 나중에 글자로 나누지 않는다. 묶는 방법(도구 하나, 또는 typed 구조 출력)은 구현 RFC 에서 정한다.
- 답은 그 요청의 `continuation_channel` 로 간다. 맨 앞 작업의 답할 곳을 다른 요청에 물려주지 않는다.
- 답하지 않은 요청에는 `No_reply_emitted` 라는 사실만 남긴다. 실패도, 답할 의무도 아니다. 다시 큐에 넣지 않는다.
- 요청별 stream 에는 묶였다는 사실(`Batch_bound`)과 자기 답만 간다. 도구 이벤트는 실행 journal 한 곳에 남긴다. `event_for_member` 의 복사는 없어진다.
- Keeper 사이 요청은 지금처럼 일반 메시지다. 답, 대기, 재시도 의무를 만들지 않는다.

## 5. 멈추지 않는다는 논증

| 불변식 | 뜻 |
|---|---|
| `NoLostAccepted` | 받은 작업은 대기, 실행에 묶임, 끝남 중 어디에 있는지 늘 찾을 수 있다. |
| `FrozenMembership` | claim 뒤에 묶음 멤버와 입력이 늘거나 바뀌지 않는다. |
| `OldestIncluded` | 새 묶음은 늘 가장 오래 기다린 새 작업을 포함한다. |
| `UniqueOwner` | 한 작업을 두 실행이 동시에 갖지 않는다. 재개는 같은 실행을 잇는다. |
| `ReplyBoundToRequest` | 답은 그 요청의 답할 곳으로만 간다. |
| `NoMessageWaitEdge` | 일반 메시지는 Keeper 사이에 기다림을 만들지 않는다. 그래서 메시지만으로 생기는 순환 대기는 없다. |

**진행 척도.** 작업 m 의 실행 기회 순번보다 앞선 순번의 수다.

- m 이 들어온 순간 앞선 순번은 유한하다.
- 실행 하나가 끝나면 앞선 순번 하나 이상이 소비된다. 2단계에서는 한 실행이 앞선 새 작업을 모두 소비한다.
- 재시도와 재개는 새 순번을 받아 m 뒤로 간다(4.1-2). 새로 들어오는 작업도 m 뒤로 간다.
- 묶음은 claim 때 고정되므로 새 유입이 진행을 되돌리지 못한다.

**가정.** 각 실행이 유한한 시간에 끝난다. 저장소와 provider 가 결국 다시 쓸 수 있게 된다. 슬롯이 비면 두 줄 중 먼저 온 쪽이 받는다(4.1-3).
provider 가 잠깐씩만 열리는 경우에는 "가끔 가능했다"만으로 claim 이 따라오지 않는다. 열린 동안 실제로 실행 기회를 배분한다는 더 강한 공정성이 필요하다.

**보장하지 않는 것.**

- 끝나지 않는 턴이 있으면 슬롯 하나 구조에서 다음 claim 은 영원히 일어나지 않는다. 묶음, 순번, 공정성 모두 이 조건을 바꾸지 못한다(§7-1).
- 유입이 처리량을 계속 넘으면 줄은 커진다. 굶주림이 없다는 것과 줄이 안 커진다는 것은 다른 성질이다.
- 모델이 입력을 받은 직후 기록 전에 프로세스가 죽으면 같은 입력을 다시 볼 수 있다. 다시 보는 것과 같은 효과를 두 번 내는 것은 다르다. 이 RFC 는 뒤의 것만 막는다.
- 외부 채널은 받는 쪽의 중복 제거나 조회 없이 무손실과 무중복을 함께 보장할 수 없다. 그때는 `Delivery_uncertain` 으로 남긴다.

## 6. 하지 않는 것

- 업무 종류 갈래(`Review_request` 같은 variant), `(repo, pr, head)` 같은 업무별 키, claim 때 GitHub 조회, 업무별 우선순위.
- 메시지 본문에서 PR 번호나 「정정」을 찾는 일. LLM 으로 큐를 미리 분류하거나 정렬하는 일.
- debounce, 개수 상한, cooldown, 라운드 상한, 행동을 바꾸는 timeout.
- 도는 턴을 강제로 끊는 일.
- 응답 본문을 자동으로 합치거나 요약하는 일.

## 7. 열린 질문

1. **끝나지 않는 턴.** 둘 중 하나를 고른다.
   - (가) 지금처럼 운영자 턴 중단만으로 푼다. 도는 턴에는 `RFC-arrived-stimuli-reach-the-running-turn` 대로 새 메시지가 보이게 한다. 보이기만 하고 종료는 보장하지 않는다.
   - (나) 실행 lane 을 나누는 RFC 를 쓴다. constitution `when_stuck` 은 "Lane 을 늘리는 제3의 방법"을 권한다. 나눈 lane 도 끝나지 않을 수 있고, 공유 checkpoint 를 여러 실행이 덮어쓰지 않게 설계해야 한다.
2. **지시가 다른 작업.** 지시를 봉투 안으로 옮기면 묶음이 끊기지 않는다. 대신 지시의 무게가 시스템 지시에서 메시지 내용으로 내려간다.
3. **이벤트 큐 행도 같은 턴에 넣을지.** 리뷰 Keeper 는 슬롯 시간의 47%를 자율 턴에 썼다(§3.2). 턴 하나가 채팅 작업과 이벤트 큐 행을 함께 받으면 두 줄이 번갈아 기다리는 일이 줄어든다. `RFC-event-queue-admit-all-ready` 와 겹치는 범위를 먼저 읽는다.
4. **`RFC-backlog-never-preempts-a-running-turn` 3단계.** Jev 가 큐 묶음에 `need_now`, `can_wait`, `superseded` 라벨을 붙이고 순서를 정하는 설계다. §1-1·§1-3 결정과 맞지 않는다. 구현은 없다. 그 RFC 의 3단계를 `Dropped` 로 바꿀지 정한다.
5. **나누지 못한 12.9시간.** 공백 856개의 합이다. 한도 쉬기, admission 닫힘, 정산 대기를 나누려면 4.1-5 의 실행 구간 기록이 먼저 있어야 한다.

## 8. 검증

feature 시험은 constitution `testing` 에 따라 기능 단위로 쓴다.

1. 서로 다른 보낸 사람 셋이 답할 곳을 달리해 작업 k 개를 넣는다. 그동안 턴 하나가 돈다. 다음 claim 이 k 개 전부를 도착 순서대로 봉투째 넣는지 본다.
2. 1 의 실행이 끝나면 보낸 사람마다 자기 답만 받는지, 답하지 않은 요청에 `No_reply_emitted` 만 남는지 본다.
3. 실행 중에 서버를 재시작한다. 멤버가 그대로이고, 이미 정산한 답을 다시 보내지 않는지 본다.
4. runtime 재시도로 돌아온 작업이 그 사이 들어온 작업 뒤로 가는지 본다.
5. child 가 예외로 끝나도 행이 `Running` 으로 남지 않고 다음 작업이 시작하는지 본다.
6. 채팅 작업과 이벤트 큐 행이 번갈아 들어올 때, 슬롯이 먼저 온 쪽으로 가는지 본다.

상태 기계는 TLA+ 로 옮긴다. `Next` 는 §5 불변식을 지킨다. 다음 `BugAction` 을 더한 `NextBuggy` 는 반드시 불변식을 어겨야 spec 이 유효하다.

- claim 뒤에 멤버를 더한다(`FrozenMembership` 위반).
- 재시도가 옛 순번으로 돌아온다(진행 척도 증가).
- 실패한 실행이 `Running` 을 남긴다(다음 claim 불가).

배포 뒤에는 같은 스크립트로 다시 잰다. 작업 수 대비 실행 수, 큐 대기 합과 아래 경계, 채팅이 안 돈 시간의 이유별 나눔, 보낸 사람별 첫 입력까지의 시간을 본다.
평균 묶음 크기가 커졌다는 것만으로 성공이라 하지 않는다.

## 부록 A. 독립 검토 두 건

같은 질문지를 서로 다른 모델 둘(gpt-6.1-sol, gpt-6-astra, reasoning max, 읽기 전용)에게 따로 줬다. 두 답이 같게 짚은 것은 다음과 같다.

- "메시지 하나 = 실행 하나 = 답 하나" 를 풀어야 한다. claim 때 고정한 유한 집합을 원래 봉투 그대로 넣는다.
- 지금 출처에는 인증된 권한 칸이 없다. 화면용 `Owner` 를 권한 근거로 쓰면 안 된다.
- `event_for_member` 의 복사 때문에 답만 나눠서는 요청별 답이 되지 않는다.
- §2.4 의 1·2 경로. 둘 다 끝나지 않는 턴은 슬롯 하나·비선점·숫자 상한 없음으로는 진행을 보장할 수 없다고 답했다.

두 검토 모두 처음에는 리뷰 요청에 `(repo, pr, head)` 칸을 붙이는 안을 냈다. §1-1 결정으로 이 RFC 는 그 안을 쓰지 않는다.
전부를 도착 순서대로 넣으면 출처끼리 순서를 건너뛰는 문제가 생기지 않는다. 그래서 권한 칸으로 묶음을 나눌 필요도 없다. 남는 조건은 답을 요청마다 따로 보내는 것 하나다.
