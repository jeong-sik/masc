# 다계정 프로세스가 Keeper 엔진을 띄우고, 엔진은 사람의 Keeper 를 그 사람의 계정으로 돌린다

- 이슈: #52989
- 사실의 근거: [연구 기록](../design/people-into-a-running-installation.md) §10~§22. main `1805632f31f6` 에서 읽었다(§19 와 §20 은 `40b3ae4da`, §21 은 `62900e072`, §22 는 `e25fdb1a`). 그 뒤에 병합된 PR 은 번호로 적었다. 띄워 보지 않았다.
- 아래에서 "설계"는 다계정 OIDC·Runtime 권한 설계(#46428), "계획"은 그 구현 계획(#46469)이다.
- 연구 기록 §8 의 빈 곳 넷 가운데 ①(엔진을 띄우는 층)과 ②(이름과 주인을 잇는 규칙)를 정한다. ③(Board)과 ④(경로마다 누구의 것을 읽는지)는 정하지 않는다.
- **정한 데까지**: 틀(§3.1~§3.3), Keeper 의 Runtime 을 찾는 길(§3.4), 턴이 들고 가는 것과 끝난 턴을 읽는 곳(§3.5). 사용자가 정할 것이 여섯이다(§6).

## 읽기 전에 — 말의 뜻

| 말 | 뜻 |
|---|---|
| 엔진 | 단일 사용자 서버가 띄우는 Keeper 실행부 |
| 계정 서버 | 다계정 boot 가 띄우는 서버. 사람, 로그인, 구독, 사람의 Keeper 기록이 여기에 있다 |
| 로그 | 권한 로그 `authz.jsonl` |
| 엔진 이름 | 엔진이 Keeper 를 찾는 이름. 이 RFC 가 새로 정한다 |
| 정의 | 엔진이 Keeper 하나를 띄우려고 읽는 TOML 파일과 실행 기록 |
| 실행 표 | 엔진이 Runtime 과 Keeper 의 배정을 읽는 전역 표 |
| 판정 | `Runtime_account_access.authorize`. CLI 가 어느 계정에서 시작해도 되는지 답한다 |
| 계정의 호출 | 한 계정에서 한 번에 하나만 도는 호출 |
| 이음매 | 엔진이 운영자 한 사람을 전제로 만든 타입. 사람이라는 축을 넣어야 하는 자리다 |

## 0. 요약

**엔진이 Keeper 를 이름으로 찾는 방식은 그대로 두고, 그 이름과 정의와 Runtime 이 로그에서 오게 한다.**

- 다계정 boot 는 계정 서버와 엔진을 한 프로세스에 띄운다. 계정 접근 값은 `Multi_account` 하나다.
- 엔진이 읽는 것은 셋이다. 정의, Keeper 의 Runtime, 판정이다. 셋이 로그에서 온다.
- 로그가 권한이다. 정의와 Runtime 값은 누구의 Keeper 인지 정하지 않는다. 턴마다 판정이 로그로 본다.
- 엔진은 그대로가 아니다. 이음매가 셋이다.

| 이음매 | 지금 | 넣는 것 |
|---|---|---|
| boot 의 인자(§3.1) | 단일 사용자를 받아 접근 값을 올린다 | 부르는 쪽이 접근 값을 올리고 올린 값을 넘긴다 |
| Keeper 의 Runtime 을 찾는 길(§3.4) | `runtime.toml` 에서 만든 표 하나 | 로그의 Runtime 과 배정 |
| 턴이 들고 가는 것과 돌려주는 것(§3.5) | Keeper 이름을 들고 가고, 거절을 문자열로 돌려준다 | 주인·채널·허락받은 범위를 들고 가고, 거절을 타입으로 돌려준다 |

- 이 RFC 에서 턴을 시작하는 원인은 둘이다. 주인의 메시지와 정기 턴이다.
- 사람의 메시지는 엔진의 대화 연산으로 들어간다. 지금의 직접 호출(`Server_preview_keeper_turn`)은 지운다.

## 1. 지금 동작

| 사실 | 연구 기록 |
|---|---|
| 한 boot 는 두 서버 중 하나를 띄운다. 계정 접근 값은 한 번만 올린다. 한 프로세스에 엔진은 하나다 | §10.1, §10.2 |
| 엔진은 Keeper 를 이름 하나로 찾는다. 로그는 (주인, id)로 찾는다 | §10.3 |
| 엔진이 띄울 이름을 읽는 곳은 autoboot, supervisor sweep, boot 의 credential 이다. 모두 정의 파일의 이름을 읽는다 | §11.1 |
| 엔진은 Runtime 을 세 걸음으로 묻는다. Keeper 의 route, route 의 후보, id 의 값이다. 셋째 걸음은 Keeper 를 모른다. 조회 함수는 모두 `runtime.ml` 에 있다 | §11.2, §14.1 |
| 실행 표는 `runtime.ml` 안의 한 함수가 통째로 바꿔 넣는다. 설정을 commit 할 때도 올린다. 읽는 곳은 여러 domain 이다 | §12.1, §12.8 |
| 사람의 Runtime 은 계정의 호출 안에서만 만든다. 계정의 호출은 서버 라이브러리에 있고, 잡지 못하면 거절한다 | §11.3, §12.1, §12.6 |
| 사람의 Runtime 값은 만들 때 계정 폴더의 파일을 읽는다. key 계정의 값은 key 를 든다 | §12.4 |
| 표를 나열하는 함수는 quota 와 Dashboard 로 간다. 사용량 기록은 모두 운영자의 작업 공간 파일로 간다. 배정이 없는 Keeper 는 default route 로 간다 | §12.5, §12.8 |
| 지금 사람의 턴은 `admit`, 계정의 호출, 판정 순서다. 거절 종류마다 답을 고른다. 도는 client 는 Claude Code 하나다 | §12.2, §12.8 |
| 엔진의 턴은 dispatch 전에 턴 번호를 쓰고, 판정의 거절을 문자열로 편다. 깨운 원인은 판정까지 오지 않는다 | §11.4, §12.2 |
| 엔진의 대화 연산은 실패를 닫힌 여덟 종류와 문자열로 적는다. 이어진 연산은 `source` 가 같으면 한 턴으로 묶는다. 연속이 있는 연산은 재시작 뒤 다시 줄을 선다 | §12.8 |
| 엔진에는 턴이 실패한 까닭을 드는 닫힌 타입과 codec 이 있고, 연산을 돌리는 코드가 그것을 문자열로 접는다. 그 타입은 지금 사람의 턴이 가르는 일곱 종류 가운데 넷을 서로 가르지 못한다 | §13.2, §16.1 |
| 성공한 턴의 답은 대화 기록의 줄에 있고, 연산의 기록은 그 줄을 찾는 턴 ref 만 든다. 실패한 턴의 줄은 글 하나를 든다. 대화 기록은 기간으로 지우지 않는다 | §17 |

| 다계정 판정은 `Keeper_turn` 을 로그로 정하고, 운영자의 호출과 호스트 계정과 내장 도구를 거절한다 | §11.6 |

## 2. 목표와 하지 않는 것

목표다.

1. 다계정 프로세스에 엔진이 떠 있다.
2. 사람이 만든 Keeper 가 엔진에서 돈다. 지시문을 갖고, 주인의 메시지에 답하고, 주인이 켜면 스스로 턴을 시작한다.
3. 그 턴은 주인의 계정에서만 돌고, 계정의 호출을 지킨다.

하지 않는 것이다.

- MASC 도구. 사람의 Keeper 는 도구 없이 돈다. 도구는 Board 와 작업 공간의 것을 읽고 쓰므로 ③, ④ 와 같이 정한다.
- 내장 도구. 다계정에서 꺼진 채다(계획 D3c). 격리된 실행(설계 §7.2)은 다루지 않는다.
- 곁에서 부르는 호출(Librarian, vision, 목표 검증, Fusion). 거절된 채다(§3.7).
- Claude Code 밖의 client. 다계정에서 Codex 의 턴은 시작 전에 거절된다(연구 기록 §12.8). 내장 도구를 모두 끄는 값이 Codex 에 생긴 뒤에 다룬다.
- 다른 Runtime 으로 넘어가기(failover), 남의 Runtime 쓰기(계획 D5).
- 이미 돌던 설치의 Keeper 를 사람에게 넘기는 일(설계 §10.3, 계획 F4).
- 단일 사용자 boot. 그대로다.

## 3. 설계

### 3.1 한 프로세스에 계정 서버와 엔진을 띄운다

- 다계정 boot 는 `Server_accounts.run` 으로 간다. 계정 서버가 zone 을 열고 `Multi_account` 를 올린 뒤, 올린 접근 값을 부르는 쪽(`Server_runtime_bootstrap.run`)이 준 함수에 넘긴다. 그 함수가 엔진을 띄운다. 계정 서버가 엔진 boot 를 직접 부르면 두 모듈이 서로를 가리킨다(연구 기록 §19.2).
- 엔진은 단일 사용자 서버가 하듯 띄운다(연구 기록 §20.1). 접근 값이 올라간 뒤 fiber 에서 초기화한다. 준비 전에 실패하거나 시작 감시의 시간 안에 준비되지 않으면 프로세스를 끝낸다. 계정 서버의 순서는 바꾸지 않는다. 로그인과 설정은 엔진을 기다리지 않는다. 준비 신호(`/health/ready`)는 엔진이 준비된 뒤에야 200 이다. 그래야 `masc restart` 가 곧 끝날 서버를 준비됐다고 적지 않는다(연구 기록 §22.1).
- 띄우는 것은 네 단계와 시작 감시다. 네 단계는 owner state 초기화, 활성화, 준비 표시, 준비 뒤 lane 이다. stdio 서버도 이 넷을 띄우지만 시작 감시는 띄우지 않는다(연구 기록 §21.1). 시작 감시는 준비 표시까지만 시간을 잰다. 단일 사용자 서버의 보조 구성(`Server_auxiliary_startup.run_all`, 구성 22개) 가운데 엔진이 띄우는 것은 준비 뒤 lane 하나다. 엔진이 넷째 단계로 직접 띄운다. gateway, gRPC, WebSocket, refresh loop 들을 포함한 나머지 21개는 띄우지 않는다. server state 도 공개하지 않는다. 준비 뒤 lane 의 background maintenance 는 Dashboard snapshot source 의 worker 들과 runtime probe loop 를 띄운다(연구 기록 §22.1).
- 판정을 지나는 호출은 host 의 자격으로 모델을 부르지 못한다. 다계정 판정이 운영자 요청과 host 의 API key provider 를 거절한다(연구 기록 §21.2). 판정을 지나지 않는 길은 §4 에 적는다.
- 엔진을 띄우는 함수(`initialize_owner_state_blocking`)는 단일 사용자를 받지 않는다. 부르는 쪽이 접근 값을 먼저 올리고, 올린 접근 값(`Runtime_account_access.published`)을 넘긴다. 그 값은 올리는 함수만 만든다. 함수는 base path 를 거기서 꺼낸다. 부르는 쪽은 셋이 된다. 단일 사용자 서버, stdio 서버, 다계정 boot 다.
- 경로표는 계정 서버의 것이다. 단일 사용자 서버의 경로는 열지 않는다(④).
- S1 의 엔진은 Keeper 의 턴을 CLI 로 돌리지 못한다. 엔진이 턴에 만드는 요청 둘을 다계정 접근 값이 거절한다(연구 기록 §19.4). 엔진 이름(§3.2)이 드는 S2 에서 풀린다.
- `runtime.toml` 의 설정 값을 적용하지 못하면 엔진 초기화가 실패한다. 적용은 됐지만 실행 표를 만들지 못하면 엔진은 지금처럼 빈 표로 서고 Keeper 를 띄우지 않는다. 사람의 Keeper 도 그동안 돌지 않는다(연구 기록 §20.2).
- 다계정 boot 는 정의 폴더를 본다. 로그에 없는 이름의 정의 파일이 있으면 boot 를 거절하고 그 이름을 말한다. 폴더의 상태를 읽지 못해도 거절한다. 다계정 boot 는 Keeper 정의를 스스로 만들지 않는다. config root 가 없는 설치는 prompt 와 내장 `runtime.toml` 만 받는다(연구 기록 §21.4, §22.2).
- 엔진의 첫 단계는 끝나지 않은 Keeper 설정 변경을 journal 에서 읽어 되돌린다. 되돌리기는 정의와 `runtime.toml` 을 다시 쓰거나 지운다. 다시 쓴 정의는 로그에 없는 정의다. 그래서 다계정 boot 는 Keeper 설정 journal 이 있으면 거절한다. 어느 프로세스가 남긴 journal 이든 같다. 엔진은 journal 이 decode 되지 않거나 대상 검사(Keeper 이름과 이 설치의 경로)를 지나지 못하면 되돌리지 않고 시작하지 않는다. 되돌리다 실패해도 시작하지 않는다. 그때는 일부만 되돌렸을 수 있다. 운영자의 길은 둘이다. journal 을 지우면 정의와 `runtime.toml` 은 지금 그대로 남는다. 계정을 끄고 config 에서 다계정 요청을 빼면 단일 사용자 boot 가 같은 첫 단계를 돈다. 그 boot 도 엔진처럼 받아들이지 못한 journal 과 되돌리기 실패에서 멈춘다. 끈 계정은 다시 켜지 못한다(연구 기록 §22.2).
- 다계정 엔진 boot 는 admin token 과 internal Keeper token 을 프로세스 environment 에 내보내지 않는다(#53877). 프로세스를 띄운 셸이 넣은 값은 남고, 엔진은 그 값을 자기 token 으로 쓴다. 사람 경로와 사람 MCP 경로의 gate 는 두 token 을 legacy credential 로 읽고 거절한다. 로그인 경로는 cookie 만 보고, health 와 console 은 credential 을 읽지 않는다(연구 기록 §21.3, §22.3).
- 사람의 CLI 자식은 builder 가 정한 이름을 받는다. Codex 의 capture 는 홈의 `config.toml` 이 적은 이름도 넘긴다. 턴과 observe 에서는 판정(#53704)이 이름을 하나라도 적은 홈을 거절한다. 로그인 자식은 판정을 거치지 않고 늘 새로 만드는 홈에서 뜬다. 새 홈은 이름을 적지 않는다(연구 기록 §22.3). 남는 위험은 §4 에 적는다.

고르지 않은 길이다.

| 길 | 고르지 않은 까닭 |
|---|---|
| 사람마다 엔진 하나 | 두 번째 설치를 거절하는 전역이 일곱이다(연구 기록 §10.2, 하나는 조사만 함) |
| 엔진을 다른 프로세스로 띄운다 | 로그를 쓰는 프로세스와 판정을 하는 프로세스가 갈린다. 판정은 같은 프로세스의 zone 을 읽는다 |
| 엔진이 이름을 읽는 곳마다 로그로 거른다 | 읽는 곳이 셋 이상이다(§11.1). 하나를 빠뜨리면 로그에 없는 Keeper 가 뜬다 |

### 3.2 엔진 이름

- 로그의 Keeper 기록이 엔진 이름을 갖는다. Keeper 를 만드는 기록에 적는다. 바뀌지 않는다.
- 서버가 뽑는다. 정책 id 를 뽑는 것과 같은 방식이다(`lib/auth_preview_keeper.ml:145`). 사람이 고르지 않는다.
- 설치에서 하나뿐이다. 로그가 지킨다. 이미 쓰인 엔진 이름을 적은 기록은 거절한다.
- 로그 상태는 두 방향으로 찾는다. (주인, id)에서 엔진 이름을, 엔진 이름에서 (주인, id)를 찾는다.
- 엔진 이름 문자열에서 주인이나 id 를 읽는 코드를 두지 않는다.
- 로그는 엔진 이름을 문자열로 든다. 정의를 쓰는 서버가 `Keeper_name.t` 로 읽는다. 권한 라이브러리가 Keeper 라이브러리에 기대지 않는다.

| 엔진 이름이 보이는 곳 | 보는 이 | 이 RFC 에서 |
|---|---|---|
| 디스크, 로그 줄, metric label | 운영자 | 그대로 보인다. 엔진 이름으로 주인과 id 를 찾는 명령을 둔다 |
| 지시문의 "당신은 {{keeper_name}}이다" | 모델 | 서버가 쓰는 정의의 지시문 앞에 주인이 지은 id 를 적는다 |
| 도구 호출의 행위자, Board 작성자, `@이름` | 다른 사람 | 도구가 없어서 생기지 않는다. ③ 이 정한다 |

고르지 않은 길이다.

| 길 | 고르지 않은 까닭 |
|---|---|
| 엔진의 식별자를 (주인, id) 타입으로 바꾼다 | 타입이 구분을 강제하는 장점이 있다. 그런데 이름을 쓰는 곳이 11,647곳이고(연구 기록 §9), 디스크 구조와 경로와 metric label 이 같이 바뀐다 |
| id 가 비어 있으면 id 를 엔진 이름으로 쓴다 | 먼저 만든 사람만 읽기 좋은 이름을 갖는다. 엔진 이름을 보고 남이 그 id 를 썼는지 알 수 있다 |

### 3.3 정의

- 사람이 Keeper 를 만들면 서버는 로그에 기록을 쓴 뒤 엔진의 `keeper_up` 을 부른다. `keeper_up` 이 정의 파일과 실행 기록을 쓰고 Keeper 를 띄운다. Keeper 를 만드는 길을 새로 두지 않는다.
- 서버는 Runtime id 를 주지 않고 부른다. 그러면 `keeper_up` 은 배정을 쓰지 않는다(연구 기록 §12.3). 배정은 로그가 정한다.
- 정의 파일을 쓰는 것은 서버뿐이다. 사람이 정하는 값은 둘이다. 지시문과 방식(`on_demand`, `autonomous`)이다. 기본 방식은 `on_demand` 다.
- 나머지 값은 서버가 고정해 쓴다.
  - `tools.native` 는 없음이다. 다른 값은 판정이 거절한다.
  - MASC 도구는 붙이지 않는다. 지금 정의에는 도구를 통째로 끄는 키가 없다. `keeper.tools` 표에 하나 더한다.
  - `mention_targets` 와 `board_interests` 는 비운다.
- 로그의 기록은 들어갔는데 `keeper_up` 이 실패하면 Keeper 는 로그에만 있다. boot 와 다음 만들기 요청이 로그의 Keeper 가운데 정의가 없는 것을 다시 만든다.
- 주인이 Disabled 가 되면 서버가 그 사람의 Keeper 를 내린다(`keeper_down`). 이미 시작한 CLI 는 끝까지 돈다. 다음 시도는 판정이 거절한다.

### 3.4 이음매 — Keeper 의 Runtime 을 찾는 길

지킬 것이다. 오른쪽은 그것을 강제하는 사실이다(연구 기록 §12.4, §12.5, §12.8).

| 지킬 것 | 까닭 |
|---|---|
| 조회는 운영자의 표를 쓰지 않는다 | 올리는 함수는 표를 통째로 바꿔 넣는다. 설정의 commit 과 겹치면 한쪽이 덮인다 |
| 사람의 Runtime 과 그 사용량은 운영자의 나열, 문서, 파일에 나오지 않는다 | 나열은 quota scope 목록, Dashboard 문서, exact-output catalog 로 간다. 사용량 기록은 모두 운영자의 작업 공간 파일로 간다 |
| 사람의 Runtime 값은 key 의 내용을 들지 않는다. 계정 폴더의 파일은 판정이 허락한 뒤 계정의 호출 안에서 읽는다 | 지금 값은 만들 때 key 를 읽어 든다 |
| 사람의 Runtime 값은 로그의 기록과 운영자의 표를 만든 설정으로 만든다. 어느 하나가 바뀌면 다음 조회가 새 값을 본다 | 지금은 부를 때마다 디스크의 `runtime.toml` 을 다시 읽고, login 계정의 integration 은 영수증 파일에서 읽는다. 로그의 head 는 상태 전체의 판 번호가 아니다 |
| binding 이 같은 값은 다시 만들어도 같은 backpressure 칸을 든다 | 엔진은 그 칸이 같은 물건인지로 dispatch 가 바뀌었는지 본다 |
| 사람의 Keeper 의 배정은 로그에서만 온다. 없거나 로그를 읽을 수 없으면 default route 로 가지 않는다 | 지금 조회는 배정이 없으면 호스트의 default route 로 보낸다(사용자 결정 2026-11-08). 그 코드가 일곱 자리에 있고 동작이 서로 다르다(연구 기록 §14.2) |

셋째 줄을 지키는 방식이다.

- 사람의 Runtime 값이 든 봉인은 계정의 이름이다. client 와 계정 id 다. 홈의 내용, key, CLI 에 넘기는 environment 를 들지 않는다. 지금은 값을 만들 때 key 파일과 프로세스의 environment 를 읽어 봉인에 넣는다(연구 기록 §18.1).
- 판정이 로그로 홈과 지금 세대의 key 파일을 적는다. 허락한 뒤 계정의 호출 안에서 그 파일을 읽고 environment 를 만들어 CLI 에 넘긴다. 지금의 맞춰 보기(`own_home`, `own_key`)는 적기로 바뀐다. 배정이 로그와 다르면 판정이 거절한다.
- 로그의 login 계정 기록이 integration 을 든다. S2 의 로그 형식에 넣는다.

첫째와 둘째 줄을 지키는 방식이다(연구 기록 §14.1).

- 사람의 Runtime 값은 운영자의 표 옆에 따로 둔 자리에 든다. `runtime.ml` 안이다. 그 자리를 쓰는 길은 운영자의 표를 쓰지 않는다.
- 그 자리를 읽는 것은 하나를 찾는 조회 넷뿐이다. Keeper 이름으로 찾는 둘(`runtime_id_for_keeper`, `keeper_dispatch_snapshot`)과 id 로 찾는 둘(`get_runtime_by_id`, `resolve_assignment_in`)이다. 넷 다 `runtime.ml` 에 있어서 부르는 곳은 그대로다. 나열하는 함수는 그 자리를 읽지 않는다. id 로 찾는 조회가 든 까닭은 엔진의 후보 단계가 Keeper 를 모르는 채 id 로 묻기 때문이다.
- 배정은 따로 두지 않는다. 조회가 로그의 Keeper 기록에서 읽는다.

넷째와 다섯째 줄을 지키는 방식이다(연구 기록 §15, §18.1). 값이 드는 것 전부와 그것이 온 곳이다.

| 값이 드는 것 | 온 곳 | 조회가 견주는가 |
|---|---|---|
| id, 모델, provider 행 | 그 Runtime 의 로그 기록, 운영자의 표를 만든 설정 | 둘 다 견준다 |
| 봉인. client 와 계정 id | 그 계정의 로그 기록 | 견준다 |
| 홈, key 파일, quota scope 의 경로 | 주인의 membership 기록이 든 namespace, 계정 기록, base path | membership 기록을 견준다. base path 는 프로세스에 하나다 |
| CLI 의 위치 | 디스크. 값을 만들 때 찾는다 | 견주지 않는다. 운영자의 표도 올릴 때 한 번 찾는다 |
| backpressure 칸 | binding 이 같은 앞선 값 | 이어받는다. 운영자의 표가 다시 올라갈 때와 같은 조건이다 |

- 조회는 만든 값을 견준 넷과 같이 둔다. 다음 조회는 넷이 그때와 같은 물건이면 그 값을 주고, 아니면 다시 만든다. 로그의 상태는 바뀐 칸만 새로 만들므로 같은 물건이면 내용이 같다. 만들지 못한 것은 두지 않는다.
- 표는 자기를 만든 설정을 같이 든다. 지금은 표로 바꾼 뒤 버린다. 설정 없이 올라간 표에서 사람의 조회는 없다고 답한다.
- 조회는 문이 아니다. 삭제가 시작돼도 계정의 기록은 그대로라 조회는 값을 준다. 막는 것은 판정이다.
- 조회는 판정 모듈이 든 zone 에서 상태를 읽고 잠금을 잡지 않는다. 로그를 쓰는 곳은 아무것도 알리지 않는다. 기다리는 턴은 조회로 다시 확인한다.

### 3.5 이음매 — 턴이 들고 가는 것과 돌려주는 것

들고 가는 것이다.

- `walk_owner` 에 사람의 갈래를 더한다. 주인, Keeper id, 채널, 허락받은 범위를 든다. `account_request` 가 그것을 `Keeper_turn` 으로 바꾼다.
- 주인과 Keeper id 는 로그에서 엔진 이름으로 찾는다. 찾지 못하면 턴을 시작하지 않는다. 다계정 프로세스에서 `Fleet_keeper_turn` 은 만들지 않는다.
- 대화 연산은 요청이 허락받은 범위를 든다. 설계의 `stored_scope` 다. 재시도에서도 채널과 범위는 그대로다(설계 397행).
- 시도마다 판정은 그 범위와 원래 채널로 묻는다. 주인이 Active 인지와 배정은 로그에서 다시 본다.
- 요청을 인증한 PAT 는 `admit` 이 본다. 줄을 선 뒤에는 다시 보지 않는다. 그래서 요청 뒤에 없앤 PAT 가 줄 세운 턴은 돈다. 연속이 있는 연산은 재시작 뒤에도 다시 줄을 서서 돈다(§6 의 4).
- 범위를 든 연산이 "인증된 주인이 보냈다"는 표시다. 엔진의 `Owner` 는 인증 사실이 아니라서 쓰지 않는다. 범위는 엔진이 연산을 묶을 때 견주는 `source` 에 둔다. 그래서 범위가 다른 두 요청은 한 턴이 되지 않는다. 필드의 모양은 S2 에서 정한다. 범위가 판정까지 가려면 세 층을 지난다. 연산 id 는 이미 그 길을 간다(연구 기록 §13.1).

채널은 턴이 생긴 곳마다 하나다. 닫힌 `match` 로 쓴다.

| 턴이 생긴 곳 | 채널 |
|---|---|
| 인증된 주인의 대화 연산 | `Direct` |
| 자극 없는 정기 턴(`Proactive_tick`), `Bootstrap` 만 든 `Woken` | `Autonomous` |
| 그 밖의 `Woken`(빈 것 포함), 주인이 아닌 이의 대화 연산 | 턴을 시작하지 않는다 |

- 셋째 줄을 `Autonomous` 로 묻지 않는다. 설계 396행은 바깥에서 온 일정, Board, 위임에 DelegatePolicy 를 요구한다. 그 채널은 그 정책을 여는 문서가 정한다(2단계).

돌려주는 것이다.

- 사람이 읽는 것은 턴이 끝난 종류다. 닫힌 타입이고, 지금 사람의 턴이 가르는 것 전부다(`server_preview_keeper_turn.ml:85`). key 가 거절됐다, 한도가 없다, 로그인이 풀렸다가 든다. 문자열을 견주어 가르지 않는다.
- 엔진의 실패 값(`Keeper_request_failure.t`)이 그 종류를 모두 가르게 고친다. 지금은 넷을 한 갈래로 든다. 로그인이 풀렸다, key 가 거절됐다, 한도가 없다, 시작하지 못했다이다(연구 기록 §16.1).
- 실패 값을 종류로 바꾸는 곳은 닫힌 `match` 하나다. 실패 줄을 쓸 때 한 번 바꾼다.

끝난 턴을 읽는 곳이다(연구 기록 §17, §18.2). 기다리던 요청도, 나중에 연산 id 로 읽는 요청도 여기서 읽는다.

| 물음 | 읽는 곳 |
|---|---|
| 연산이 끝났는가, 어떻게 끝났는가 | 연산의 끝 기록. 지금 그대로다 |
| 답이 무엇인가 | 대화 기록에서 그 연산의 끝 줄. 지금 그대로다 |
| 턴이 왜 실패했는가 | 같은 끝 줄이 든 종류. 줄에 종류가 없으면 연산의 끝 종류 |

- 줄에 칸 하나가 는다. 값은 종류의 이름 하나다. 글이 없어서 가릴 것이 없다. 실패 값 전체는 지금처럼 walk evidence 에만 남는다.
- 줄에 종류가 없는 때는 셋이다. 줄 없이 끝난 연산(취소, 멈춤, 재시작, 줄 쓰기 실패), 칸이 없는 옛 줄, 값을 풀 수 없는 칸이다. 풀 수 없는 칸은 턴 ref 처럼 그 칸만 없는 것으로 읽는다.
- 실패 줄을 쓰는 함수는 하나이고 부르는 곳이 여섯이다. 엔진이 돌린 턴의 실패는 그중 실패 값을 들지 않는 하나로 온다. 턴을 돌리는 함수가 값을 글로 바꿔 돌려주기 때문이다(`server_routes_http_keeper_stream.ml:755-798, 2042-2043`). 그 함수가 값을 돌려주게 고친다.
- 그 줄은 연산 id 와 자리로 찾는다. 위임 상태 도구의 읽기(`lib/keeper/keeper_tool_surface_ops.ml:1050-1072`)는 턴 ref 로 먼저 거르고 실패 줄에는 턴 ref 가 없는 것이 있어서 그대로 쓰지 못한다.
- 사람이 읽는 대화에는 실패 줄의 글 대신 종류의 문장이 나간다. 줄의 글은 서버 경로를 들 수 있다.
- 연산 저장소는 바뀌지 않는다. 운영자의 Keeper 의 실패 줄도 같은 칸을 든다. 옛 빌드는 그 칸이 든 줄을 만나면 그 Keeper 의 대화 기록에 더 쓰지 못한다(§4 의 hard cut).

순서다.

1. 서버가 요청을 받으면 `admit` 에 묻는다. 연산을 넣기 전이다. 거절될 token 은 아무것도 남기지 않는다.
2. 엔진이 연산을 돌린다. dispatch 마다 계정의 호출을 기다려 잡고, 판정을 받고, CLI 를 시작한다.
3. 계정의 호출을 지키는 등록부는 서버 라이브러리에서 runtime 라이브러리로 내린다. 서버의 여덟 파일과 엔진이 같은 등록부를 쓴다.

계정이 바쁠 때다(설계 §9.1).

- 엔진의 dispatch 는 기다린다. 계정마다 온 순서대로다. 거절하면 한 구독을 쓰는 두 Keeper 가 서로를 실패한 턴으로 만든다.
- 기다림은 턴을 멈추면 같이 멈춘다. 새 시간 값은 만들지 않는다.
- 기다리다 시작하지 못한 턴은 Keeper 의 실패로 세지 않는다.
- key 바꾸기 같은 관리 요청은 기다리지 않는다. 지금처럼 409 로 답한다.

### 3.6 사람의 메시지

- `POST /api/v1/auth/keepers/turn` 과 `masc_my_keeper_turn` 은 메시지를 엔진의 대화 연산으로 넣는다.
- 요청은 연산이 끝날 때까지 기다리고 답을 돌려준다. 기다리는 시간의 상한은 지금 값(120초, `lib/server/server_preview_keeper_turn.ml:11`)이다. 넘으면 연산 id 를 돌려주고, 사람은 대화에서 답을 읽는다.
- `Server_preview_keeper_turn` 의 직접 호출과 `turns.jsonl` 은 지운다. 대화는 엔진의 기록이 갖는다. 옛 대화를 옮기는 코드를 두지 않는다.
- 사람의 대화 도구 셋(`masc_my_keeper_conversation`, `…_new`, `…_delete`)은 엔진의 대화 기록을 읽고 지운다.

## 4. 남는 위험

읽지 않은 것이다. 제목 뒤 괄호는 그것을 읽어야 하는 단계다. "조사만 함:" 은 그 줄 끝까지, 문장 끝의 "(조사만 함)" 은 그 문장에만 걸린다. 표시가 걸린 것은 이 RFC 를 쓴 세션이 코드에서 확인하지 않은 조사 결과다.

- **긴 대화**(S2). 대화 요약은 Librarian 이 하고 Librarian 은 거절된다. 대화가 창을 넘은 턴이 어떻게 되는지 읽지 않았다. 실패하면 Librarian 을 주인의 계정으로 돌리는 규칙이 S2 앞에 든다.
- **엔진 boot 가 다계정 설치에 남기는 것**(S2). auth 폴더에 `admin` 이름의 Admin credential 과 `auth/agents/` 가 생기고, internal Keeper token 의 hash 가 쓰인다. 만료된 agent credential 은 하루 한 번 지워진다. `runtime.toml` 이 없던 설치에는 내장 `runtime.toml` 이 생긴다. Auto 모드면 boot 마다 내장 Skill 을 `.masc/skills/` 에 맞춘다. tool blob sweep 은 사람 폴더를 범위에 두고 그 안을 읽지 않는다. 볼륨 GC 는 보고만 하고 지우지 않는다. config root 가 없던 설치는 seed 가 복사하던 항목을 받지 않는다. 조사만 함: 볼륨 GC 보고는 같은 기계의 다른 서버가 쓰는 Keeper 볼륨을 읽는다. authz 로그와 사람 폴더를 고치는 lane 은 없다. seed 에서 빠지는 항목은 identity, themes 같은 것이다(연구 기록 §21.3~§21.5, §22.2, §22.4, §22.6).
- **Keeper 앞의 정리**(S2). 단일 사용자 boot 가 Keeper 앞에 도는 정리 넷은 다계정이면 건너뛴다. Keeper 가 쓰기 시작하는 S2 에서 다계정 boot 도 돌린다(연구 기록 §20.1, §21.5).
- **environment 의 운영자 token**(S2). 다계정 엔진은 두 token 을 environment 에 내보내지 않지만, 프로세스를 띄운 셸이 넣은 값은 남는다(#53877). 사람의 CLI 자식이 그 이름을 받지 않는 것은 builder 마다의 허용 목록과 판정, 새 로그인 홈에 기댄다. Codex 의 capture 는 environment 를 통째로 읽고 홈이 적은 이름을 넘긴다. 로그인 자식은 판정을 거치지 않는다. 지금은 로그인 홈이 늘 새것이라 닿지 않는다. 그 조건을 고정하는 시험은 없다(연구 기록 §21.6, §22.3). 다계정 boot 가 셸이 넣은 값을 비우면 이 길들이 함께 사라진다. 두 이름을 이름으로 읽는 곳은 boot 의 credential 단계, 설정 snapshot, health 응답의 `internal_mcp_auth` 셋이다(연구 기록 §21.3).
- **판정을 지나지 않는 호출**(S2). host 의 자격으로 모델을 부르지 못한다는 것은 모든 호출이 판정을 지난다는 데 기댄다. lane add-on 은 읽지 않았다. S1 의 엔진은 boot 때 실행 표를 만든다. 조사만 함: 실행 표를 만들 때 공식 client 값이 host 계정 파일을 읽어 봉인한다. 판정 받은 값을 받는 실행 함수, 사용량 읽기, Dashboard probe 는 판정을 지난다. 판정 밖에서 host 의 것을 쓰는 곳으로 셋이 나왔다. 실행 표의 공식 client 값, reader Keeper 의 token 을 쓰는 GitHub pull reader, `gcloud` 를 부르는 Vertex 의 credential 값이다(연구 기록 §21.6, §22.5).
- **계정 서버의 검사 밖에서 서는 Keeper**(S2). 계정 서버는 boot 때 한 번 정의 폴더를 보고, 실행 기록(`.masc/keepers/*.json`)은 보지 않는다. supervisor sweep 은 돌 때마다 그 폴더를 다시 읽고, 실행 기록이 없고 방식이 `manual` 이 아닌 정의 파일을 keepalive 후보로 올린다. 그래서 boot 뒤 폴더에 생긴 정의 파일도 방식이 `manual` 이 아니면 후보가 된다. 엔진은 boot 때 실행 기록으로 owner 를 세운다. 그렇게 선 Keeper 의 턴은 다계정 판정이 거절한다. 판정은 운영자 Keeper 의 턴을 모두 거절한다. 실행 기록만 있는 Keeper 가 도는지는 읽지 않았다. 조사만 함: 후보는 Keeper 를 만들고, 그 길이 Keeper 설정 journal 을 쓴다(연구 기록 §22.2).
- **Board 로 가는 알림**(S2). 볼륨 damage watch 는 Keeper 볼륨의 손상을 Board 에 쓴다. 사람의 Keeper 가 생기면 그 알림이 Board(③)로 간다(연구 기록 §22.6).
- **엔진의 server state 를 얻는 길**(S2). stdio 서버는 state 를 전역에 올리지 않는다. 사람의 메시지 경로가 엔진의 state 를 어떻게 얻는지 정하지 않았다.
- **사람의 Runtime 을 만드는 일**(S2). 값 하나를 만드는 데 드는 시간을 재지 않았다. 만들 때마다 inventory JSON 과 release catalog 를 다시 읽는다는 것, 운영자가 설정을 저장하면 모든 사람의 값을 다시 만든다는 것은 조사만 했다. 경로의 real root 는 디스크에서 읽어서(`Unix.realpath`) 폴더가 먼저 있어야 한다. 지금은 조회 쪽이 폴더를 만든다(조사만 함). 조회가 디스크에 쓰지 않으려면 계정을 등록할 때 만들어야 하는데 그 자리를 읽지 않았다. 쉬는 경로에서 기다리는 턴을 얼마나 자주 다시 확인하는지 읽지 않았다(연구 기록 §15, §18.1).
- **로그를 읽을 수 없을 때의 조회**(S2). zone 은 믿을 수 있을 때만 상태를 준다(조사만 함). 조회 넷의 답에는 "모른다"가 없다. 그때 Keeper 이름으로 찾는 조회가 사람의 Keeper 를 default route 로 보내지 않게 하는 길을 읽지 않았다.
- **넷을 가르는 방식**(S2). Claude Code 의 실패가 agent-core 오류가 되는 곳은 조사만 했다. 원인을 새로 두는지, MASC 오류를 나르는 길에 싣는지는 그 자리를 읽고 정한다. 끝 줄의 자리는 연산마다 하나이고 먼저 쓴 줄이 남는다(조사만 함). 실패 줄을 쓴 연산이 다시 도는지, 줄을 쓴 뒤 연산의 끝 기록을 쓰기 전에 서버가 죽으면 어떻게 되는지 읽지 않았다. 사람이 대화를 읽는 route 가 줄의 글을 어디서 바꿔 내는지도 읽지 않았다(연구 기록 §17.2, §17.5, §18.2).
- **턴 밖에서 계정 홈을 쓰는 것**(S2). dispatch 가 끝난 뒤에도 도는 사용량 읽기가 Claude Code 에 있는지, 엔진의 대화 지우기가 계정 홈의 vendor session 을 지우는지 읽지 않았다.
- **기다린 턴의 결과**(S2). 시작하지 못한 시도를 엔진이 어떻게 세는지, Runtime 의 턴 시간 제한이 기다림에도 걸리는지 읽지 않았다. 계정이 거절한 시도는 지금 보낸 것(`Dispatched`)으로 적힌다(연구 기록 §16.2).
- **sandbox**(S2). 정의 파일에 `sandbox_profile` 이 꼭 있어야 한다. 도구 없는 Keeper 의 값을 읽지 않았다.
- **대화 도구**(S2). 지금 사람은 대화를 여러 개 만들고 지운다. 엔진의 대화는 Keeper 마다 하나다.
- **엔진 연산의 답 모양**(S2). 지금 경로가 사람에게 주는 답과 맞는지 읽지 않았다.

정해진 것이다.

- **hard cut 의 범위.** Keeper 기록의 형식이 바뀌면 옛 로그 전체가 재생되지 않는다. 사람, 초대, 구독 연결, PAT 를 다시 만든다. 계정의 홈(`.masc/accounts`)도 지운다. S2 의 빌드가 실패 줄을 하나라도 쓴 Keeper 는 옛 빌드에서 대화 기록에 더 쓰지 못한다. 운영자의 Keeper 도 같다(연구 기록 §18.2).
- **저장소의 자리.** 엔진의 저장소는 `<base path>/.masc/keepers/<엔진 이름>/` 이다. 사람의 폴더 아래가 아니다. 다계정에서 그것을 내주는 경로는 없다(④).

| 엔진이 준비 전에 실패하면 프로세스가 끝난다 | 엔진 초기화가 거절하는 store 를 놓고 boot 한다. 프로세스가 0 이 아닌 값으로 끝난다 |

| 다계정 boot 는 Keeper 정의를 만들지 않는다 | config root 가 없는 설치를 boot 한다. 정의 폴더에 파일이 없다 |

| 두 사람의 같은 id 는 두 Keeper 다 | 두 사람이 같은 id 로 만든다. 엔진 이름이 다르고, 엔진에 둘이 뜬다 |
| 사람의 메시지에 지시문을 가진 Keeper 가 답한다 | 가짜 CLI 로 턴을 돌린다. CLI 가 받은 system prompt 에 지시문이 있다 |
| 턴은 주인의 계정에서만 돈다 | 가짜 CLI 가 받은 홈과 key 가 로그가 적는 주인의 것이다. 표의 배정을 남의 Runtime 으로 바꿔 놓으면 CLI 가 시작하지 않는다 |
| 표에 key 가 없다 | key 계정의 Keeper 를 만든 뒤 표의 값을 본다. environment 에 key 변수가 없다 |
| 운영자 쪽은 그대로다 | 사람의 턴을 한 번 돌린다. `get_runtimes`, quota scope 목록, 운영자의 사용량 파일, 표의 판 번호가 그대로다 |
| 로그가 바뀌면 다음 조회가 새 값을 본다 | Keeper 의 배정을 바꾼 뒤 조회한다. 새 Runtime id 가 나온다. key 를 바꾼 뒤의 턴은 새 key 로 돈다. 로그인 기록만 쓰인 뒤의 조회는 앞의 값과 같은 물건을 준다 |
| 사람의 Runtime 과 운영자의 표는 같은 설정을 본다 | 디스크의 `runtime.toml` 을 고치고 다시 올리지 않는다. 조회한 값이 표를 만든 설정의 것이다 |
| 끝 까닭은 타입으로 읽힌다 | 배정을 바꾼 직후의 턴과 key 가 거절된 턴을 돌린다. 기다리던 요청, 연산 id 를 받은 뒤의 대화 읽기, 재시작 뒤의 대화 읽기가 같은 종류(`Runtime_reassigned`, `Key_refused`)를 말한다. 사람이 받는 답과 사람이 읽는 대화에 서버 경로가 없다 |
| 까닭이 없는 실패 줄은 그대로 읽힌다 | 칸 없이 쓴 실패 줄이 든 대화 기록을 읽는다. 줄이 남고, 사람은 연산의 끝 종류를 읽는다 |
| 범위가 다른 두 요청은 한 턴이 되지 않는다 | 범위가 다른 연산 둘을 줄 세운다. 턴이 둘 돈다 |
| 한 계정에서 한 번에 하나만 돈다 | 엔진의 dispatch 가 도는 동안 key 바꾸기가 409 를 받는다. 같은 계정의 둘째 Keeper 는 기다렸다가 돌고, 실패 횟수가 늘지 않는다 |
| 채널이 없는 곳에서 생긴 턴은 시작하지 않는다 | 일정 자극을 넣는다. CLI 가 시작하지 않는다 |
| 단일 사용자는 그대로다 | 기존 시험이 통과한다 |

## 6. 열린 결정

사용자가 정한다.

1. **엔진 이름을 따로 두는가, 엔진의 식별자를 (주인, id) 타입으로 바꾸는가.** 이 RFC 는 앞의 것을 골랐다(§3.2).
2. **사람이 정하는 값을 지시문과 방식 둘로 두는가.**
3. **기본 방식을 `on_demand` 로 두는가.** `autonomous` 가 기본이면 만든 순간부터 주인의 구독으로 정기 턴이 돈다.
4. **요청 뒤에 없앤 PAT 가 줄 세운 턴을 돌게 두는가.** 이 RFC 는 설계 397행대로 돌게 뒀다(§3.5). 주인이 멈추는 길은 대화 지우기, 배정 바꾸기, Disabled 다. 막으려면 연산이 PAT 의 id 를 들고 판정이 시도마다 로그에서 다시 읽는다. 판정의 요청 타입이 바뀐다. 재시작 뒤에 다시 줄을 선 턴도 같다. 설계 679행은 재시작 때 직접 요청이 `Cancelled_before_effect` 를 본다고 적었는데, 엔진의 연산으로 넣은 메시지는 재시작을 넘는다.
5. **운영자가 사람의 계정 사용량을 보는가.** 이 RFC 는 보지 않는 쪽이다(§3.4 둘째 줄).
6. **엔진이 서지 못하면 프로세스를 끝내는가.** 이 RFC 는 끝내는 쪽이다(§3.1). 단일 사용자 서버가 지금 그렇다. 그러면 `runtime.toml` 의 설정 값을 적용하지 못하거나 Admin credential 이 어긋난 설치는 띄울 때마다 엔진이 실패하고 프로세스가 끝난다. 계정 서버는 엔진을 fiber 로 띄우고 곧바로 경로를 연다. 그래서 엔진이 실패할 때 끝나지 않은 로그인과 요청은 프로세스와 함께 끊긴다(연구 기록 §22.1). 반대쪽은 계정 서버만 남기는 것이다. 그러면 엔진이 없는 상태를 사람의 메시지 경로와 운영자가 따로 알아야 한다.

## 7. 단계

| 단계 | 하는 일 | 끝나면 보이는 것 |
|---|---|---|
| S0 | 계정의 호출 등록부를 runtime 라이브러리로 내리고 기다리는 길을 더한다. 엔진을 띄우는 함수의 인자를 바꾼다 | 없다. 동작이 그대로다. 기존 시험이 본다 |
| S1 | 다계정 boot 가 네 단계와 시작 감시를 fiber 에서 띄운다. Keeper 정의를 스스로 만들지 않는다. 로그에 없는 정의, 읽지 못하는 정의 폴더, 남은 Keeper 설정 journal 은 boot 를 멈춘다 | boot 를 마치고 엔진이 서는 설치에서 로그인은 그대로다. boot 를 멈추는 설치는 로그인을 받지 않는다. 엔진이 서지 못하는 설치는 프로세스가 끝나고, 그때 끝나지 않은 로그인이 끊긴다. `masc restart` 는 엔진이 준비된 뒤에 준비됐다고 적는다. `runtime.toml` 이 없던 설치에는 내장 `runtime.toml` 이 생긴다. 다계정 boot 시험이 엔진의 state 를 읽는다 |
| S2 | 엔진 이름, 정의, 이음매 둘(§3.4, §3.5), 메시지의 길. 채널은 `Direct`, 방식은 `on_demand` 만 받는다. 직접 호출을 지운다 | 사람의 Keeper 가 지시문을 갖고 답한다 |
| S3 | 정기 턴이 채널 `Autonomous` 로 묻는다. 방식 `autonomous` 를 받는다 | 주인이 켠 Keeper 가 스스로 턴을 시작한다 |

- S2 부터는 엔진이 서는 설치에서도 사람에게 보이는 것이 바뀐다. S2 는 로그의 형식을 바꾸는 hard cut 이고 한 번에 배포한다.
- S0 과 S1 은 boot 를 마치고 엔진이 서는 설치에서 사람에게 보이는 것을 바꾸지 않는다. S1 부터 boot 를 멈추는 설치는 로그인을 받지 않는다. 엔진이 서지 못하는 설치는 엔진이 실패할 때까지 로그인을 받고, 그때 프로세스가 끝나며 끝나지 않은 로그인이 끊긴다. S2 와 이어서 한다.
