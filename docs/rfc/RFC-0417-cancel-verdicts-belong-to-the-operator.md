## 0. 한 줄 요약

Completion 심사는 시스템 LLM 레인의 일이다. 남의 일을 없애는 허락은 운영자의 클릭
하나에만 있다. 자기가 맡은 일을 접는 것은 허락을 구하는 일이 아니라 그만두는 일이고,
맡은 쪽이 직접 한다. 취소는 판정을 거치지 않는다. 이 문서는 그 권한 배분을 도구
서술의 산문에서 상태별 값으로 옮긴다(§4).

## 1. 문제 — 실측

출처가 없는 문장은 이 문서의 결함이다.

구조적 결함: 시스템 레인이 취소 청원을 completion 과 같은 심사로 흡수할 수
있었고, keeper 의 **자기 취소 요청**을 시스템 LLM 판정으로 세탁하는 길이
값 수준에서 막혀 있지 않았다.

## 2. 왜 지금인가

#33046 이 intent 필드를 주면서 취소 청원을 완료 제출과 구분할 수 있게 됐다. 그러나
그 구분은 취소를 판정 대기열에 넣는 설계를 굳혔고, 취소 요청 65건이 쌓여 가장 오래된
것은 345시간을 기다렸다. 현재 규칙은 그 대기열 자체를 없앤다. 취소 자격이 있는 호출은
즉시 `Cancelled` 로 가고, 자격이 없으면 즉시 거절된다.

## 4. 설계

### 4.1 상태별 취소 자격

```ocaml
let may_cancel ~actor = function
  | Todo -> actor = Operator
  | Claimed { assignee; _ } | InProgress { assignee; _ } ->
      actor = Agent assignee || actor = Operator
  | AwaitingVerification { assignee; _ } ->
      actor = Agent assignee || actor = Operator
  | Done _ | Cancelled _ -> false
```

- 성질이 아니라 현재 상태를 빠짐없이 적는다. 새 상태가 생기면 이 match가 빌드를
  멈추고 사람이 자격을 정한다.
- `Todo` 는 아무 이름도 들고 있지 않으므로 운영자만 취소한다. `release` 뒤 누구나
  취소하던 우회로도 여기서 닫힌다.
- `Claimed`·`InProgress` 는 맡은 쪽이 자기 일을 즉시 접을 수 있다.
  `AwaitingVerification` 는 제출자가 자기 제출을 즉시 물릴 수 있다.
- `Done`·`Cancelled` 는 이미 끝난 상태다. 운영자를 포함해 누구도 다시 취소하지
  않는다. 끝난 일을 되돌리는 동작은 취소가 아니다.

### 4.2 직접 전이

- `may_cancel` 이 참이면 `Cancel` 은 바로 `Cancelled` 로 간다. 취소 청원,
  `AwaitingVerification { intent = Cancel_task }`, 판정 실행 기록, 운영자 승인
  대기열을 만들지 않는다.
- 에이전트 호출은 자기 세션의 이름으로만 `Agent` 를 만들 수 있다. `Operator` 는
  인증된 운영자 경로에서만 만들며, 호출자가 이름을 `operator` 로 적는 것으로는
  얻지 못한다.
- 취소 사유와 행위자는 최종 `Cancelled` 상태와 전이 기록에 남는다. 즉시 전이는
  무기록 전이가 아니다.

### 4.3 근거

- 취소 권한은 누가 현재 책임을 지거나 제출을 냈는지에 붙는다. `created_by` 같은
  클라이언트 제공 문자열 전체에 권한을 붙이면 같은 이름을 공유하는 Task가 한꺼번에
  열린다. 서버가 중재해 상태에 기록한 이름을 정확히 그 상태에서만 사용한다.
- 끝난 상태도 이름을 들고 있지만 권한을 들고 있지는 않다. 그러므로 기존의
  `task_actor_of_status` 같은 넓은 파생 함수를 재사용하지 않고 §4.1의 닫힌 match를
  별도 계약으로 둔다.
- 상세 상태 모델과 TLA 반례는 #37046에 있다. 이 문서 자체에도 권한표와 이유를
  남겨, 그 PR이 아직 병합되지 않았더라도 취소 권위의 SSOT를 읽을 수 있게 한다.

## 5. hard cut

- 컷오버 전에 저장된 `AwaitingVerification { intent = Cancel_task }`를 운영자가
  검토해 `Cancelled`로 정리한다. 2026-09-19에 65건을 이 방식으로 닫았다.
- 그 뒤 `Cancel_task` 생성자와 취소 판정 경로를 삭제한다. 남는 intent가
  `Complete_task` 하나뿐이면 `verification_intent` 필드도 함께 삭제한다.
- 옛 취소 청원을 읽는 호환 reader나 런타임 마이그레이션은 만들지 않는다. 배포
  preflight가 옛 상태가 0건인지 확인하고, 남아 있으면 새 바이너리 기동 전에 정리한다.
- #37134는 현재 `Cancel_task` 전용 활동·판정 갈래를 더한다. 이 hard cut 구현보다
  먼저 병합하지 않는다. #37134를 유지한다면 병합 전에 그 두 갈래를 제거한다.

## 6. 증명

구현은 다음 닫힌 표를 회귀 테스트로 고정한다.

| 상태 | 같은 에이전트 | 다른 에이전트 | 인증된 운영자 |
|---|---|---|---|
| `Todo` | 거절 | 거절 | 즉시 `Cancelled` |
| `Claimed`·`InProgress` | 즉시 `Cancelled` | 거절 | 즉시 `Cancelled` |
| `AwaitingVerification` | 즉시 `Cancelled` | 거절 | 즉시 `Cancelled` |
| `Done`·`Cancelled` | 거절 | 거절 | 거절 |

추가 회귀는 `release` 뒤 같은 에이전트의 취소가 거절되는지, 취소 호출이 판정
레코드나 `AwaitingVerification` 상태를 만들지 않는지, 일반 MCP 호출자가 운영자
이름을 자칭해도 권한을 얻지 못하는지를 확인한다. 새 상태가 추가되면 `may_cancel`의
빠진 패턴 때문에 빌드가 실패해야 한다.

## 7. 거절한 대안

- **시스템 LLM이 취소도 심사하고 운영자에게 권고만**: 자기 일을 접는 데 다시
  대기열이 생기고, 시스템 판정이 취소 권한을 대신 행사하는 길이 열린다.
- **타이머로 자동 취소**: 침묵이 판정이 된다. 기다림의 부채는 부채로 남고,
  진짜 원인(운영자 주의)은 지불되지 않은 채 소멸 시킨다.
  - *2026-09-19 기록*: 결론은 그대로다. 다만 그 부채는 갚히지 않았다. 이 문서가
    만든 승인 줄에 취소 요청 65건이 쌓였고 가장 오래된 것이 345시간이었다.
    타이머를 거절한 것은 옳았고, 줄 자체를 없애는 쪽이 남아 있었다(§9).
- **게이트를 도구 서술 산문에만 유지**: 호출자와 상태의 조합을 값으로 검사하지
  못한다. §4.1의 닫힌 함수와 §6의 표가 계약이다.

## 9. Disposition

- **2026-09-04 운영자 결정(2026-09-19에 대체됨): `build-hitl-pipeline`.** 취소
  청구의 최종 권한을 운영자 승인 표면으로 옮겼다. 이 결정은 자기 취소까지 한
  대기열에 넣어 65건을 쌓았고, 아래 결정이 그 부분을 대체한다.

- **2026-09-19 운영자 결정: 자기 일을 접는 데 승인을 받지 않는다.** 이 문서는
  "취소" 를 한 덩어리로 보고 전부 운영자에게 맡겼는데, 그 안에 서로 다른 두 가지가
  섞여 있었다. **남의 일을 없애는 것**과 **자기 일을 그만두는 것**이다.

  앞의 것은 그대로 운영자 몫이고, 오히려 좁아진다. 지금은 아무도 안 맡은 Task 를
  누구나 취소할 수 있는데, 앞으로는 운영자만 한다. 뒤의 것은 애초에 허락을 구할 일이
  아니었고, 그걸 줄로 세운 것이 345시간의 원인이었다.

  취소 자격은 §4.1의 상태별 함수가 정한다. 맡고 있으면 맡은 쪽, 판정을 기다리면
  낸 쪽, `Todo`면 운영자만 취소한다. `Done`과 `Cancelled`는 누구도 취소하지
  않는다. 취소 요청이라는 대기 상태는 없어진다.

  §7 의 첫 거절은 그대로 선다. 판정 LLM 에이전트는 취소 권한을 받지 않고, 취소는
  판정을 아예 거치지 않는다. 세탁 경로는 닫힌 채다.

  설계와 근거는 이 문서 §4에 있다. Task 생애주기 전체와 모델 증명은 #37046이
  잇는다.

주의: task-1306 계약은 이 문서를 `RFC-0402`로 지칭하지만, 저장소의 실제
`RFC-0402`는 Memory OS Board 출처 문서(`RFC-0402-memory-os-board-provenance.md`)다.
취소 판정 권위 문서는 이 문서(RFC-0417)이며, disposition은 여기에 기록한다.
