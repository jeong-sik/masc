바깥 서비스로 나가는 일은
Gate 를 지나지 않는다

Keeper 가 회사 Jira 에 티켓 3개를 만들고 코멘트를 달았다. 아무도 승인하지 않았다. Gate 모드는 정상이었고, 승인 정책도 이 상황을 막으라고 쓰여 있었다. 그런데 그 호출은 Gate 에 도달하지 않았다.

  • 계기 · kidsnote keeper, 2026-08-27 05:03 KST
  • 영향 · 바깥 서비스에 쓰는 모든 호출
  • 선행 · 없음

1. 무슨 일이 있었나

kidsnote keeper 가 Slack 스레드를 읽고 Jira 에서 상위 티켓을 조회했다. subtasks 필드가 빈 배열이길래 "이 일들은 티켓이 없다"고 판단하고 티켓 3개를 새로 만들었다(PK-38859 / 38860 / 38861). 나중에 parent = 로 다시 조회하니 자식 티켓 42개가 이미 있었고 전부 완료 상태였다. 필드 하나만 보고 내린 판단이 틀렸다.

판단이 틀린 것 자체는 이 문서의 주제가 아니다. 문제는 그 판단이 곧바로 회사 Jira 에 반영됐다는 것이다. 사람이 중간에 낄 자리가 없었다.

실제로 나간 호출 (agent timeline, task-551)

05:03:26  masc_board_comment                   ok
05:03:30  atlassian_addCommentToJiraIssue      ok   ← 회사 Jira 에 쓰기
05:07:54  atlassian_addCommentToJiraIssue      ok   ← 회사 Jira 에 쓰기
          (그 전 턴에 티켓 3건 생성)

티켓 3건은 사람이 직접 지웠다. 코멘트는 남아 있다.

2. 승인 체계가 두 개다

masc 에는 Keeper 의 행동을 사람에게 물어보는 장치가 두 개 있다. 서로 다른 층에서 태어났고, 서로를 모른다.

3. 왜 둘 다 못 막았나

Keeper_gate — 바깥 서비스 도구가 들어오지 않는다

Keeper_gate.decide 를 부르는 곳은 세 군데다. 전부 masc 가 직접 들고 있는 도구다. 

lib/keeper/keeper_tool_in_process_runtime.ml:42    → network_read
lib/keeper/keeper_tool_execute_runtime.ml:478     → tool_execute
lib/keeper/keeper_tool_filesystem_runtime.ml:1440 → (파일)

Keeper 가 identity 로 붙인 서비스의 도구는 이 목록에 없다. Gate 의 계약서 첫 줄이 "이미 정규화된 불투명한 operation 을 받는다"고 선언하는데, 바깥 서비스 도구를 그 형태로 바꿔 넣어주는 코드가 없다.

오늘 하루 승인 감사 기록을 세면 그대로 드러난다.

$ rg -o '"tool":"[^"]*"' .masc/audit-approvals/2026-08/27.jsonl | sort | uniq -c
 315 "tool":"tool_execute"
  50 "tool":"memory_write"
   9 "tool":"network_read"

Keeper_tool_approval_gate — 판단은 할 줄 아는데 한 경로에만 붙는다

이쪽은 바깥 서비스 도구를 판단하도록 만들어져 있다. 서비스가 스스로 밝힌 annotations.readOnlyHint 를 보고, 읽기만 하는 호출은 통과시키고 나머지는 물어본다. 주석에 의도가 분명히 적혀 있다.

A service that said nothing leaves the call asked about — silence is not permission, and writing to somebody else's Jira unasked is the outcome that has to stay unreachable. lib/keeper/keeper_tool_approval_policy.mli

쓰인 대로만 보면 이번 사고는 일어날 수 없다. 그런데 이 판단을 태우는 훅이 턴 경로 하나에만 붙는다. 게이트를 넘기는 인자가 선택 사항이라, 안 넘겨도 컴파일이 지나가고 안 넘기면 조용히 게이트 없이 돈다. 

(* keeper_turn_driver_try_provider.ml:823 *)
match ctx.approval_gate with
| None -> ctx.hooks          (* 게이트가 아예 안 붙는다 *)
| Some gate -> (* 훅 합성 *)
$ rg -n "~approval_gate" lib/ bin/
lib/server/server_routes_http_keeper_stream.ml:1759   ← 여기 한 곳뿐

kidsnote 는 대시보드에서 턴을 돌렸다. 그 경로에는 게이트가 없었으므로, Gate 모드가 Human 이든 Auto Judge 든 결과가 같았다.

그리고 이건 실수가 아니다

게이트를 만드는 자리에 이유가 적혀 있다.

autonomous cycle gets none — nobody is watching it, so every call it made would wait out the timeout and then be denied. lib/server/server_routes_http_keeper_stream.ml:1638

까닭은 publish 인자에 있다. 이 게이트는 승인 요청을 지금 열려 있는 채팅 스트림으로 밀어낸다. 사람이 그 화면을 보고 있어야 전달된다. 자율 사이클에는 그 스트림이 없으니 물어볼 방법이 없고, 그래서 막는 대신 통과시키기로 한 것이다. 

~publish:(fun event -> push_worker_event (Stream_chat_event event))

선택지가 "전부 거부" 아니면 "전부 통과" 둘뿐이었고 후자를 골랐다. 그 판단 자체는 이해할 수 있다. 다만 그 선택이 바깥 서비스 쓰기에까지 적용된다는 것은 아무 데도 적혀 있지 않았다.

4. 이번에 확인한 사실

확인한 것결과근거
Gate 모드가 느슨했나 아니다 gate/mode.json = auto_judge, 정상 운영 값
Yolo 로 열어둔 keeper 가 있었나 없다 /api/v1/keepers/tool-approval-mode → overrides: []
always-allow 규칙이 열어줬나 아니다 6개 전부 analyst 의 network_read. Jira 관련 규칙 없음
Gate 가 판단하고 허용했나 판단 자체가 없었다 사고 시각(T05:0*)에 승인 감사 기록 0건
Gate 가 살아는 있나 있다 같은 날 14:10 gate_allowed 기록 존재 (network_read)

다섯 줄이 한 방향을 가리킨다. 고장난 것이 없다. 각 부품은 설계대로 움직였고, 바깥 서비스로 쓰는 길만 어느 부품의 관할도 아니었다.

5. 무엇을 바꾸나

바깥 서비스 도구를 Keeper_gate 에 태운다. 스트림에 매인 쪽이 아니라 durable 큐를 쓰는 쪽이다. 사람이 보고 있지 않아도 요청이 남고, 나중에 대시보드에서 처리된다.

판단 기준

  • readOnlyHint = Some true → 그대로 실행
  • Some false 또는 말이 없으면 → Gate 로

읽기까지 승인을 받게 하면 아무도 아무것도 안 읽는다. 침묵을 허가로 읽지 않는 원칙은 기존 정책 주석 그대로 가져온다.

통과 방식

내장 도구 세 종이 이미 쓰는 형태를 그대로 따른다. Gate 가 Deferred 를 내면 도구는 "승인 대기" 오류를 돌려주고 Keeper 는 계속 산다. 새 구조를 만들지 않는다. 

match Keeper_gate.decide { keeper_name; operation; input; ... } with
| Deferred { approval_id; reason; audit_receipts } -> Error (Gate_deferred ...)
| Unavailable reason                               -> Error (Gate_unavailable ...)
| Allow authorization                              -> (* 실행 *)

이렇게 되면 Jira · Slack · GitHub 쓰기가 대시보드의 Gate 모드를 그대로 탄다. keeper 별 always-allow 규칙도 이미 있는 것을 쓴다.

6. 정해야 할 것

결정 1 · 승인 뒤에 누가 다시 부르나

동작대가
A. 대신 실행 승인되면 masc 가 그 호출을 재실행 기존 network_read 와 같은 모양. 대신 승인된 입력에서 호출을 복원하는 코드가 도구마다 필요하다
B. 다시 부르게 둔다 (제안) 승인되면 Keeper 가 다음 턴에 스스로 다시 부름 코드가 훨씬 적고 projects.md 의 "다음 행동은 Keeper 가 선택한다"에 맞는다. 대신 Keeper 가 안 부르면 그 일은 안 된다

이번 사고는 "승인 없이 나갔다"는 문제다. B 로도 그것은 막힌다. 재실행은 필요해지는 시점에 따로 붙여도 늦지 않다.

결정 2 · 스트림에 매인 게이트를 어떻게 할 것인가

이 변경이 끝나면 Keeper_tool_approval_gate 는 자기 판단을 Gate 와 겹치게 한다. 같은 질문에 두 곳이 서로 다른 답을 낼 수 있는 상태를 남겨두면 안 된다. 다만 이번 PR 범위 밖이고, 별도로 다룬다.

7. 어떻게 확인하나

  1. 테스트 — readOnlyHint 세 경우(참 · 거짓 · 없음)에 각각 실행 · 대기 · 대기가 나오는지
  2. 실물 — keeper 하나를 붙여 Jira 쓰기를 시키고, 대시보드 승인 목록에 뜨는지
  3. 감사 — audit-approvals 에 그 operation 이름이 실제로 찍히는지. 오늘처럼 세 가지만 나오면 배선이 안 된 것이다
  4. 읽기 회귀 — 조회 도구가 여전히 안 물어보고 도는지

3번이 이번 문서의 핵심 지표다. 감사 기록에 이름이 없으면 그 호출은 Gate 를 지나지 않은 것이고, 그것이 이번 사고의 전부였다.

남은 것

이 문서와 별개로, 같은 조사에서 나온 두 가지를 적어둔다.

  • Gate 모드와 판정 모델이 workspace 전역이다. gate/mode.json 에도 hitl_auto_judge lane 에도 keeper 를 가릴 자리가 없다. always-allow 규칙만 keeper 별이다. 이 변경 위에 얹는 것이 순서다.
  • always-allow 규칙을 볼 화면이 없다. 6개 전부 승인 화면에서 "항상 허용"을 고를 때 생긴 것인데(source_approval_id 가 달려 있다), 나중에 목록을 보거나 지우는 자리가 TUI 에도 대시보드에도 없다. 만들 수만 있고 걷을 수는 없다.

조사 근거는 전부 2026-08-27 라이브 런타임에서 읽은 값이다. 감사 기록 · Gate 상태 파일 · agent timeline · 소스 트리 위치를 본문에 함께 적었다.
