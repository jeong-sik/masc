# RFC-0467 — durable 회차는 연속성 따라잡기 뒤에 줄 서지 않는다

## 1. 문제

Keeper 하나의 Librarian 레인은 작업 단위를 하나씩 돌린다. 단위는
`run_durable` → `run_continuity` → 큐 회차 순서다
(`lib/keeper/keeper_librarian_queue_refresh.ml` 의 `run`).

- `run_continuity` 는 회차가 커밋하는 동안 스스로 다시 돈다(`if !saved then next ()`).
  `RFC-librarian-lifecycle` §4.3 의 "성공하면 다시 본다" 다.
- 연속성 회차는 한 번에 턴 하나를 읽는다. 폭을 좁히지 않아도 그렇다. 범위의 끝을 시작점
  뒤 첫 자름 자리로 잡는다(`keeper_librarian_continuity.ml` 의 `prepare_source`,
  `List.find_opt (fun cut -> cut.cut_end_atom > start_atom) cuts`). 좁힌 폭은 그보다 짧게만 자른다.
- 레인은 대기 자리 하나에 새 단위를 덮어쓸 뿐 도는 단위를 끊지 않는다(`keeper_memory_lane.ml`
  의 `Queue_latest`·`Replace_latest`).

그래서 연속성이 뒤처져 있으면, 단위 하나가 따라잡기 내내 끝나지 않는다. 그 사이 턴이 끝나 들어온
단위는 대기 자리에서 기다리고, 그 단위의 durable 과 도는 단위의 큐 회차가 모두 굶는다. 턴이 회차
하나(수 분)보다 자주 끝나면 따라잡기는 끝나지 않는다.

2026-09-23 msx-retro-mania 실측(#38249).

| 시각 | durable 위치 | 연속성 위치 | 일어난 일 |
|---|---|---|---|
| 13:36 | 17967 | 16183 | 단위 시작. durable 커밋 뒤 연속성 반복에 들어감 |
| 13:46:21 | 17967 | 16223 | 턴 끝(atom 18026). 새 단위는 대기 자리에만 들어감 |
| 13:44~13:57 | 17967 | 16262 | 연속성 회차 7번, 각 한 턴·약 2분, 모두 `skipped_context_only` |
| 13:59:32 | — | — | 서버 재시작으로 반복이 끊김 |
| 14:03:15 | 18105 | 16272 | 새 단위의 durable 이 17967→18105 를 한 번에 읽고 커밋 |

- 연속성은 durable 보다 72턴 뒤(`#2327` 대 `#2399`)에 있었다.
- 그동안 keeper 가 쓴 위치 스냅숏이 정리되지 않고 쌓였다(22개).
- 오늘 durable 이 돈 때는 대부분 연속성 회차 하나가 커밋하지 못해 반복이 끊겼거나, 서버가
  재시작했을 때였다. 기억 정리가 실패와 재시작에 기대고 있었다.

## 2. 결정

**연속성 회차가 커밋한 뒤, 레인에 기다리는 단위가 있으면 반복을 멈추고 단위를 끝낸다.**

```
run_continuity:
  연속성 회차 하나
  커밋했고 레인에 기다리는 단위가 없으면: 다시
  커밋했고 기다리는 단위가 있으면: 끝 (큐 회차로)
  못 했으면: 끝
```

- 기다리는 단위는 곧바로 돈다. 그 단위는 durable → 연속성 → 큐 순서로 돌고, 연속성은 같은
  위치와 같은 폭(`limited_widths` 는 프로세스 메모리)에서 이어간다.
- durable 은 지금처럼 새 신호(턴 끝·받은 일 변경·기동)가 만든 단위의 첫머리에서만 돈다. 실패한
  durable 이 신호 없이 다시 돌지 않는다는 §4.3 규칙이 그대로 선다.
- 도는 모델 호출을 끊지 않는다. 멈추는 자리는 회차와 회차 사이다.
- 큐 회차도 같은 이유로 굶지 않는다. 멈춘 단위가 큐 회차까지 돌고 끝난다.
- 기다리는 단위가 있는지는 레인이 안다(`drain.latest`). 레인이 그 사실을 읽는 함수 하나를 내준다.
  숫자나 시간 조건은 넣지 않는다.

## 3. 바꾸지 않는 것

| 그대로 | 왜 |
|---|---|
| 연속성이 한 턴씩 걷는 것 | 자름 자리 규칙이다. 이 RFC 는 걸음 사이에 반복을 계속할지만 바꾼다. |
| 연속성이 durable 이 저장한 범위도 걷는 것 | working state 는 스냅숏이 덮는 앞부분 전체를 요약해야 한다. 그 범위의 회차가 기억 판단을 만들지 않게 하는 것은 #38246 이다. |
| 레인의 대기 자리 하나, 도는 단위를 끊지 않는 것 | 위치 저장의 원자성을 지킨다. |
| 실패 뒤에는 신호를 기다린다 | §4.3. 이 RFC 는 durable 을 더 자주 돌리지 않는다. 신호가 온 단위를 기다리게 두지 않을 뿐이다. |
| 턴이 끝나야 durable 이 읽는 것 | 끝나지 않은 턴 안에서 keeper 가 쓰는 스냅숏은 쓰는 쪽의 `supersedes`(#38122)가 다룬다. 2026-09-23 msx 는 13:59 이후 4시간 넘게 턴이 끝나지 않아 이 경우였다. |

## 4. 대안

- **연속성 회차가 커밋할 때마다 durable 을 다시 비운다.** 첫 초안이었다. 실패한 durable 이 신호
  없이 회차마다 다시 돌아(§4.3 위반) 모델 호출이 늘 수 있고, 큐 회차는 여전히 굶는다.
- **연속성이 durable 이 저장한 범위를 건너뛴다.** 복구 요약에 구멍이 난다.
- **durable 과 연속성을 다른 레인에서 돌린다.** 한 Keeper 에 실행 줄이 둘이 된다.
  `RFC-librarian-lifecycle` §5 가 막은 모양이다.
- **도는 단위를 새 턴 끝에 끊는다.** 도는 모델 호출이 버려지고, 턴이 자주 끝나면 연속성이 한 걸음도
  못 나간다.
- **연속성 반복에 횟수 상한을 둔다.** 근거 없는 숫자다.

## 5. 비용

- 모델 호출 수는 늘지 않는다. 기다리던 단위의 durable 은 지금도 결국 돌 회차다. 앞당겨질 뿐이다.
- 단위를 끝내고 새로 시작하는 비용은 durable 확인(읽을 턴이 없으면 파일 읽기만)과 큐 회차의
  입력 비교다.
- 연속성의 따라잡기는 새 단위의 durable 이 끼는 만큼 늦어진다. 대신 기억은 턴을 따라간다.

## 6. 검증

단위 테스트(레인의 "기다리는 단위" 조회를 주입할 수 있게 한다):
- 연속성 회차가 커밋했고 기다리는 단위가 있으면 반복을 멈추고 큐 회차로 간다.
- 기다리는 단위가 없으면 지금처럼 다시 돈다.
- 연속성 회차가 커밋하지 못하면 지금처럼 끝난다.
- 기다리던 단위가 이어서 돌 때 연속성은 같은 위치와 폭에서 시작한다.

라이브:
- 연속성이 durable 보다 뒤처진 keeper 에서, durable 위치가 턴 끝을 연속성 회차 하나 안에 따라간다.
  `librarian-progress.json` 의 `end_atom` 과 `turn-boundaries.jsonl` 의 마지막 턴 끝을 나란히 본다.
- 재시작 없이도 durable 커밋이 이어진다.

## 7. 열린 항목

- 연속성이 72턴 뒤처진 것 자체는 이 RFC 가 줄이지 않는다. 회차마다 한 턴을 읽으므로 턴이 회차보다
  자주 끝나는 한 차이는 줄지 않는다. #37857 이 입력을 줄이면 회차가 빨라져 차이가 덜 벌어질 뿐이다.
  한 회차가 여러 턴을 읽게 하려면 §4.3 의 폭 규칙과 함께 따로 설계해야 한다.
