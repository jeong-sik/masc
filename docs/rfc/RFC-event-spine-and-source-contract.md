# RFC: 사건 척추와 이벤트 소스 계약

- 관련: RFC-0439 (MSX lane · §6.2 티커) · PR #35228 (게임 스킬 착지, composition
  문법 규칙 기록) · RFC-keeper-self-authored-skills
- 통합: 실시간 티커(RFC-0439 §6.2) · 감시자 이벤트 스트림 · 애드온 레인 — 따로
  만들려던 셋을 하나의 계약으로 모은다.

## 사무실 (사람이 읽는 서두)

이 시스템은 이미 사무실이다. 게시판(Board)이 있고, 쪽지(keeper_msg)가 있고,
휴게실에 오락기가 한 대 있으며(MSX — 공유, 호출 직렬화, 인계 에티켓), 교대
알람(스케줄러)이 있고, 각자 수첩(keeper memory)과 사내 매뉴얼(스킬)이 있다.
없는 것은 셋이었다 — 사무일지, 야간 경비, 벽의 공지. 실제 사고 하나가 그
부재를 증명한다: 429 레이트 리밋을 키퍼가 '게임 스톨'로 오독했을 때, 공지가
없는 사무실에서 직원이 건물 문제를 자기 일로 오해한 것이다. 이 RFC는 그
세 가지를 세운다.

## 배경 — 이산 사건 시스템으로 읽는다

- 기계들은 이산 사건 시스템(DIS)이다. MSX는 호출될 때만 프레임이 진행한다
  (사건과 사건 사이엔 아무 일도 없다). 스케줄러는 미래 사건 큐(event
  calendar)다. DES 문법이 원형이라는 관찰에서 출발했다.
- 전파는 뙇(edge)이어야 한다. 변화 순간에만 전파하고, 레벨(매 틱 폴링)은
  소비자를 태운다. `Screen_change`(PR #34892)가 이미 그 검출기다 — 6프레임
  간격 지문, 커서 깜빡임 무시, 변화 순간에만 참.
- 경제의 실측: 토큰 절감 논법은 현재 규모에서 성립하지 않는다(msx-retro-mania
  615턴 총 $4.02, 턴당 입력 79k 토큰 중 99.3% 캐시 히트). 희소자원은 토큰이
  아니라 운영자 주의력과 키퍼의 정확성이다(오독 1건 = 사람 세션 하나).
  다만 척추 번호는 지금 안 찍으면 소급 부여가 불가능하므로 계측만은 1단에
  둔다.

## 계약

### 이벤트 소스 (event source)

```
event source = { 커서(상태 지문) · 이벤트(뙇) · 능력 비트(관측 / 구동) }
```

- 관측 소스는 붙이기만 한다. 구동 소스는 경합과 직렬화가 따라온다(MSX가
  그렇다).
- 바깥 세상(status page, git)은 폴링으로는 레벨 신호다. 레벨→엣지 변환은
  어댑터의 책임이고, 그 패턴이 `Screen_change`다(커서 비교, 변화 시에만 뙇).
- 현재 멤버는 둘 — msx(`Screen_change`, 머지됐고 미부착)와 스케줄러(시간
  엣지). 셋째(경비, 아래 1단)가 계약을 실증하기 전까지 이 계약은 가설이다.

### 명명 — "Lane"은 원시 개념이 아니다

- lane은 기존 그대로 둔다: `msx_lane` 등 모듈명(재명명 없음), 타임라인 뷰의
  시각 트랙(swimlane).
- 계약의 이름은 event source, 순서의 이름은 사건 척추. 창작 도구(DAW 등)는
  자기 어휘(트랙·트랜스포트)를 쓰고 계약만 입는다. 추상은 사실을 따른다 —
  멤버 셋이 같은 계약을 필요로 하는 것이 확인된 뒤에도 명사 확장은 별도
  논의다.

### 사건 척추 (spine) — 사무일지

- 모든 사건에 단조 증가 번호를 매긴다(전순서). 사건들이 서로 "몇 번째냐"로
  비교 가능해지면 교차 상관이 수사에서 조회로 바뀐다.
- 값은 둘: 발생 시각(원격)과 꿰임 순서(spine seq). 외부 소스는 도착 순서로만
  꿴다.
- 저장은 통합 로그가 아니라 번호 부여다. 각 저장소(board_posts,
  activity-events, 입력 원장 등)는 자기 장부를 유지하고 사건에 척추 번호를
  함께 찍는다(godfile 회피).
- 벽시계는 배경지가 아니라 가장 많이 구독되는 이벤트 소스다(스케줄러·타임아웃·
  캐던스·TTL). 축은 척추(순서)이고 벽시계는 기준 트랙(각인)이다. 재생은
  척추 위에서만 가능하다 — 같은 벽시각에 사건이 다시 일어날 수는 없으므로.
  경과 측정은 monotonic 서비스가 담당한다(wall-clock 오염 사고 #34929).

### 구독 — 월드 컨텍스트의 설계

- 월드 = 구독 중인 이벤트 소스들의 흐름. `keeper_world_observation`이 이미
  그 자리다 — 지금은 소스가 컴파일 시간에 고정돼 있을 뿐이다.
- 키퍼 프로필 = 스킬 선택 + 이벤트 소스 구독. 소비 다이얼(레벨이면 매 틱,
  엣지면 뙇)과 생산 다이얼(행위가 어느 소스에 사건을 만드나).
- 컨텍스트 설계는 역할이 아니라 기능이다. 다이얼은 운영자·창작자의 손에
  있고, 척추 재생이 그 선택의 품질을 측정한다. 반사실("그 시점에 status
  구독이 있었다면")도 척추 위에서 검증 가능하다.

### 레이어링 원칙

- 기계는 서버 프로세스 안(L1)에 공유 1대 — 아케이드라는 정체성 자체. 애드온
  샌드박스로 내리지 않는다. 기계가 하나라 검출기도 축마다 하나면 족하고,
  한 번 나온 뙇은 복사 비용 0으로 퍼진다(자연독점은 코어에 산다).
- 엣지 검출기는 축마다 L1에 산다(msx는 `Screen_change`, 시간은 스케줄러).
  소비자는 조합한다 — keeper wake · Board · 애드온 관측 모두 이미 존재한다.
- `lane_addon`의 관측 소스(msx_capture, browser_document)는 이 계약의 첫
  걸음(능력 비트가 관측으로 고정된 형태)이다.

## 1단 (승인 시)

1. **척추 계측** — 사건에 단조 번호. 저장소 통합 없이 각 장부에 병기.
2. **경비(감시자)** — `Screen_change`를 msx에 부착해 `settled` / `input` /
   `reset` 세 이벤트를 발행한다. 결정론 스크립트(비전 아님 — 커서·프레임·
   incarnation으로 판정). 소비는 keeper wake부터.
3. 2단 후보는 자리만: 티커(Executor pool 503 해소 전제, RFC-0439 §6.2),
   status 소스(벽의 공지), git 소스.

## 범위와 상품 경계

- 이 문서는 내부 아키텍처 RFC다. 대기 3항목을 하나의 계약으로 통합하는 것만
  으로 정당화된다.
- 상업 베팅은 보류. 재검토 신호: 외부 수요 3회 / 척추가 예방한 실사고 n≥3 /
  플랫폼이 ambient context를 내놓지 않음 — 셋 중 둘이 오면 다시 연다.
- 컨텍스트 설계를 새 직업(컨텍스트 디자이너)으로 만들지 않는다. 좌석 배치는
  사무실 주인의 몫이다.

## 열린 질문

- 척추 번호의 할당 단위(사건 1개? 저장소 쓰기 1개?)와 단조성 보장 위치
  (서버 단일 할당이 전제인가).
- 구독의 표현 — 키퍼 프로필 어디에 사는가(`skills.names` 옆?).
- 경비의 1단 형태: 서버 안(계약 정통) vs 애드온 파일럿(503 무관, 계약은
  관례가 됨). 본 RFC는 서버 안을 권고하고 파일럿 병행을 허용한다.
- DOS 파일 표면(.dsk 안의 파일 관리)은 이 계약 밖의 `msx_lane` 도구로
  별도 진행한다 — 캠페인 운영에 즉시 필요하나 레인이 아니라 도구다.
