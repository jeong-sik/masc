[RFC-keeper-recall-reaches-the-turn](../../rfc/RFC-keeper-recall-reaches-the-turn.md) 층 0 의 측정 1(Jev 용량)과 2(반복 일치)를 Keeper 둘로 처음 해 본 결과다. `won-chik` 로 조각 요청과 반복 일치를, `goo-yang-bong` 로 한도를 넘는 요청을 봤다.

## 무엇을 했나

- `scripts/keeper-recall-jev-probe.py` 로 `won-chik` 의 현재 사실 56개(claim 66KB)를 RFC §4.2 모양의 요청으로 Jev 에 보냈다. 운영자가 04:1xZ 무렵 직접 실행했다. 정확한 시각은 기록하지 않았다.
- 명령:

  ```bash
  python3 -I scripts/keeper-recall-jev-probe.py ~/me/.masc/config/keepers/won-chik.memory-current.json \
    --send --allow-send-for won-chik --runtime-toml ~/me/.masc/config/runtime.toml --timeout 60 --repeat 3
  ```

- 후보는 실제 사실이고 목적(turn input)은 합성 문장이다("리뷰어가 열린 PR 의 판정을 요청한다"). 실제 턴 입력이 아니다.
- 출력 원문은 [won-chik.txt](won-chik.txt) 다. `won-chik` 는 이미 Jev 로 기억 판정 요청을 보내는 20명 중 하나다.

## goo-yang-bong: 한도를 넘는 요청

`goo-yang-bong`(사실 73개, claim 149KB)의 후보 전체를 조각으로 나누지 않고 한 요청으로 보냈다(`--piece-kb 400`). 이것도 운영자가 직접 실행했고 이미 Jev 로 기억 판정 요청을 보내는 20명 중 하나다. 출력 원문은 [goo-yang-bong.txt](goo-yang-bong.txt) 다.

| 요청 | 후보 | 요청 본문 | `state` | 결과 | 입력 토큰 | 시간 |
|---|---|---|---|---|---|---|
| 전체 | 73 | 197.7KB | 159.7KB | HTTP 400 (스크립트가 용량 거절로 판단해 반으로 나눔) | - | 0.28초 |
| 앞쪽 반 | 36 | 96.6KB | 77.9KB | HTTP 200 | 31,752 | 0.35초 |
| 뒤쪽 반 | 37 | 101.4KB | 82.1KB | HTTP 200 | 32,980 | 0.52초 |

- 거절된 요청은 용량 거절이다. 스크립트는 HTTP 400 이고 `detail.error_type` 이 `max_tokens_exceeded` 일 때만 반으로 나누고, 다른 400 이면 멈춘다. 거절 응답의 본문은 이번 출력에 없다. 다음 실행부터 본문을 출력한다.
- 거절된 요청의 입력 토큰은 받아들여진 두 반쪽의 밀도(3.04~3.07바이트)로 나눠 추정하면 `state` 만 약 52k, 본문 전체 약 65k 다. 질문당 한도(32k)는 확실히 넘고 요청당 한도(64k)는 걸쳐 있다. 어느 쪽이 걸렸는지는 이 거절 하나로 가를 수 없다.
- 입력 토큰당 요청 본문은 3.04바이트와 3.07바이트다. `won-chik` 의 2.97바이트와 비슷하다. 작은 판정 요청 1,623건의 중앙값은 2.04바이트였다.
- 받아들여진 가장 큰 요청은 `state` 82.1KB, 본문 101.4KB, 입력 32,980토큰이다. 질문 37개를 합친 입력이 32k 토큰을 넘었는데도 받아들여졌다. 그래서 32k 는 질문을 모두 합친 입력에 거는 한도가 아니다. `state` 와 질문 하나에 거는 한도라는 문서의 설명과 어긋나지 않는다. 이 요청의 `state` 와 질문 하나는 입력 토큰으로 약 27k 일 것으로 추정한다. 질문별 토큰 수는 재지 못했다.
- 두 반쪽을 앞쪽부터 차례로 보내서 전체 시간이 1.18초였다. 동시에 보내면 약 0.5초다.

## Jev 문서가 말하는 것 (2026-10-28 확인)

- 선택 질문(`choice`)의 답에는 `choice`(확률이 가장 높은 선택지), `probabilities`(선택지별 확률), `confidence`(확률이 한 곳에 몰린 정도, 0~1)가 있다. 확률이 고르게 퍼지면 0 이다. 확신도 페이지는 낮을 때 "Do not act" 라고 한다. 출처는 `https://docs.typesafe.ai/confidence.md` 와 `https://docs.typesafe.ai/primitives/choice.md` 다.
- 같은 요청이 같은 답을 내는지에 대한 설명은 models, confidence, choice 세 페이지에 없다. 온도나 시드 같은 설정도 적혀 있지 않다.
- 선택지 설명(`criteria`)은 모델에 같이 보내진다. 선택지끼리 구분되게 쓰고, 비슷한 선택지는 무엇을 포함하고 무엇은 아닌지 적으라고 한다.
- 예/아니오 질문(`noul`)의 답은 확률 하나(`noul`, 0~1)이고 확신도 필드가 따로 없다. 문서는 0.7 이상이면 예, 0.3 이하이면 아니오, 그 사이는 사람에게 보내는 시작 기준을 예로 든다. 코드가 확률 숫자를 비교하는 방식이라 이 설계에는 쓰지 않는다. 같은 페이지가 값이 실행마다 얼마나 안정적인지 재는 예제(cookbook "Self-consistency: nouls")를 링크하지만 결과는 적지 않는다. 출처는 `https://docs.typesafe.ai/primitives/noul.md` 다.
