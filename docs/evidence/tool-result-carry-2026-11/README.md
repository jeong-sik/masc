# 요청에 실린 도구 결과 바이트 (2026-11)

저장된 요청이 도구 결과를 얼마나 싣는지 도구별로 세요. 결과가 자리표시자(블롭 참조)로 바뀐 몫과, 요청에 실리지 않는 저장용 사본의 몫도 같이 나눠요.

바이트는 토큰이 아니에요. 재는 크기는 저장된 JSON 의 크기라서 요청에 실리는 크기와 다를 수 있어요. 어디가 다른지는 아래 "저장용 사본"에 적었어요. 제공자 캐시에서 읽힌 몫은 재지 않았어요.

## 다시 돌리는 법

```
docs/evidence/tool-result-carry-2026-11/measure_tool_result_carry.py --base-path ~/me \
    --from-date 2026-10-29 --to-date 2026-11-04 \
    --json-out docs/evidence/tool-result-carry-2026-11/result-2026-10-29_11-04.json
python3 -m unittest discover -s docs/evidence/tool-result-carry-2026-11
```

`--top` 은 표에 찍을 도구 수예요(기본 20). 스크립트는 `.masc` 를 읽기만 해요. 저장된 요청은 10-29 부터 있어요.

정의는 스크립트 머리말에 있어요. 줄여 쓰면 이래요.

- 저장된 요청: `keepers/*/provider-inputs` 에 남은, 턴당 하나의 요청. 같은 턴의 다른 요청은 저장되지 않아요.
- 도구 메시지: 저장된 요청이 싣는 `role == "tool"` 메시지. sha256 으로 서로 구분해요. 저장된 크기는 `tool_blobs` 파일 길이예요.
- 실린 바이트: 저장된 크기 × 그 메시지를 실은 저장된 요청 수. 기록이 길면 같은 결과가 요청마다 또 실려요.
- 결과: 도구 메시지 안의 `tool_result` 블록 하나. 도구 이름은 도구 호출 장부에서 같은 `tool_use_id` 를 가진 줄의 `tool` 이에요. 없으면 `<unmapped>` 예요. 블록 밖 바이트(role, origin, 호출 id)는 첫 결과에 붙여서, 한 메시지의 결과를 더하면 저장된 크기가 돼요.
- 저장용 사본: `tool_result` 블록의 `text_content` 필드. 타입이 있는 블록으로 오는 결과는 저장할 때 블록(`content`)과 평문 사본이 같이 쓰여요(`packages/agent_core/lib/base/history.ml` 의 `content_block_to_json`). 요청에는 블록만 실려요(`llm_provider/api_common.ml` 의 `tool_result_wire_fields_with`, `backend_openai_serialize.ml` 의 `tool_result_content_string`).
- 자리표시자: 결과 텍스트가 `[masc:blob sha256=` 로 시작하는 것. 오래된 결과를 참조로 바꿀 때 `Tool_output.encode_for_agent_core` 가 쓰는 표시예요. 표시 안의 `bytes=N` 은 바꾸기 전 텍스트 크기예요.

## 찾은 것

- `masc_dos_*` 아홉 도구의 결과 4,804개가 실린 바이트의 42.8%(1.711 GB, 본문의 14.8%)예요. 이 중 자리표시자로 바뀐 결과는 16개뿐이에요. `Keeper_model_input_demotion.demotable_body` 가 `content_blocks = Some` 인 결과를 건너뛰기 때문이에요. 블록이 있으면 `content` 는 직렬화되지 않아서, `content` 를 표시로 바꿔도 요청이 줄지 않는다는 이유를 RFC-0363 §3.1 조건 1 이 적었어요. 블록으로 오는 도구 결과는 오래돼도 줄지 않고 기록이 끝날 때까지 실려요. 같은 조건에 든 "이미지·문서를 담아서 표시로 바꿀 수 없다"는 이유는 텍스트 블록만 있는 결과에는 해당하지 않아 보여요. 이 스크립트는 블록 종류를 세지 않아서 텍스트 블록만 있는 결과가 얼마나 되는지는 몰라요.
- 저장용 사본은 0.936 GB 이고 그중 99.9% 가 `masc_dos_*` 예요. `masc_dos_press` 는 저장된 크기의 67% 가 사본이에요. 사본을 빼면 `masc_dos_*` 는 0.776 GB(본문의 6.7%)예요. 저장된 크기로 본문 몫을 말하면 DOS 쪽이 두 배쯤 크게 보여요.
- 자리표시자가 실린 바이트의 33.2% 예요. 서로 다른 자리표시자는 23.3 MB 인데 평균 57번 실려요. 자리표시자 하나는 저장된 JSON 으로 평균 596 B 이고, 바꾸기 전 텍스트는 평균 3,043 B(`bytes=N` 의 평균)였어요. 앞의 값은 JSON 이스케이프가 들어간 크기라서 둘의 비는 대략이에요.
- `Execute` 는 자리표시자 20,788개가 0.751 GB 로, 살아 있는 `Execute` 결과 0.343 GB 의 2.2배예요.
- `Execute` 와 `masc_dos_press` 두 도구가 실린 바이트의 51.9% 예요.

## 스크립트가 재지 않은 관찰

- 열어 본 `Execute` 자리표시자의 `preview`(앞 200자)는 `{"ok":true,"status":{"kind":"exit","code":0},"cwd":"/masc-work/…","execution_location":{"cwd":"/masc-wo` 처럼 `ok`, `status`, `cwd`, `execution_location` 같은 고정 항목만 담고 끝났어요. `output` 까지 닿지 못했어요. 표본 하나를 읽은 것이고, 모든 자리표시자가 그런지는 재지 않았어요.

## 한계

- 저장된 크기는 요청에 실리는 크기와 달라요. 이 스크립트는 사본만 따로 빼고, 그 밖의 차이는 재지 않아요.
- 저장된 요청은 턴당 하나예요. 실린 횟수는 저장된 요청 기준이고, 한 턴의 다른 요청은 세지 않아요.
- 도구 이름은 장부 기간 안의 호출에서만 찾아요. 기간 앞에 부른 결과는 `<unmapped>` 예요.
- 한 메시지에 결과가 여럿이면 블록마다 도구를 나눠요. 블록 밖 바이트는 첫 결과에 붙어서, 그 도구가 조금 크게 잡혀요.
- 블롭은 공백 없는 JSON 으로 읽고 크기를 다시 계산해요. 다시 계산한 길이가 파일 길이와 다르면 `reserialization_mismatch` 로 세요. 이번 기간은 0 이에요.
- 기간과 시점에 따라 값이 달라요. 서버 바이너리가 바뀌면 같은 명령으로 다시 재야 해요.

## DOS 화면 공백 재생

`masc_dos_*` 도구는 결과마다 `screen_text` 를 돌려줘요. 글자 화면 25줄 × 80칸이고, 빈 칸은 공백으로 채워요. 그래픽 모드로 그리는 게임은 이 화면이 비어 있는데도 공백 2 KB 쯤이 결과마다 실려요. 줄마다 끝 공백을 떼고 끝의 빈 줄을 떼면 저장된 요청이 얼마나 줄었을지 다시 계산해요. 도구 코드는 건드리지 않았어요.

```
docs/evidence/tool-result-carry-2026-11/measure_dos_screen_trim.py --base-path ~/me \
    --from-date 2026-10-29 --to-date 2026-11-04 \
    --json-out docs/evidence/tool-result-carry-2026-11/result-dos-screen-trim-2026-10-29_11-04.json
```

저장된 요청, 도구 메시지, 실린 바이트, 장부에서 도구 이름을 찾는 방법은 위와 같아요. 더한 정의는 이래요. 자세한 건 스크립트 머리말에 있어요.

- DOS 결과: 장부의 도구 이름이 `masc_dos_` 로 시작하고, 결과 텍스트가 문자열 `screen_text` 를 가진 JSON 객체인 `tool_result` 블록.
- 줄인 화면: 줄마다 끝의 공백(U+0020)을 떼고, 그다음 끝의 빈 줄을 뗀 화면. 줄은 `\n` 으로 나뉘어요. 중간의 빈 줄은 남아서 줄 위치는 그대로예요.
- 화면 바이트: 화면이 요청 본문에서 차지하는 바이트. 결과 텍스트는 메시지 안에서 JSON 문자열이라, 화면의 JSON 을 한 번 더 이스케이프한 길이예요.
- 내용 바이트: 블록의 `content` 를 공백 없는 JSON 으로 쓴 길이. 저장용 사본(`text_content`)은 빼요.
- 아낀 바이트: 실린 화면 바이트에서 줄인 화면의 실린 바이트를 뺀 값.

### 찾은 것

- 화면 4,764개가 모두 공백과 줄바꿈뿐이에요. 비디오 모드는 `12h` 가 4,763개, `03h` 가 1개예요. `03h` 인 화면도 비어 있었어요.
- 줄여도 지워지는 글자는 공백과 줄바꿈뿐이에요(`changed_pages` 0). 빈 화면은 줄이면 `""` 이 돼요.
- 아낀 바이트는 DOS 결과 내용의 35.25%, 모든 요청 본문의 2.30%예요.
- `files`(DOS 기계에 붙여 둔 파일 이름 목록)도 모든 결과에 실려요. 목록은 하나뿐이고 DOS 내용의 11.42%예요. 이 스크립트는 `files` 를 줄이지 않고 크기만 재요.

### 한계

- 바이트는 토큰이 아니에요. 공백 덩어리가 입력 토큰으로 얼마인지는 못 쟀어요. 보고서(`docs/reports/2026-11-05-tool-efficiency.md`)에 따르면 입력 토큰의 90.3%는 제공자 캐시에서 읽은 토큰이라, 토큰으로 본 몫은 위 바이트 몫보다 작을 수 있어요.
- 화면 바이트는 결과 텍스트가 메시지 안에 JSON 문자열 하나로 들어간다고 보고 센 값이에요. 제공자별 요청 모양은 열어 보지 않았어요.
- 이 기간의 화면은 모두 비어 있어서, 글자가 찬 화면에서 아끼는 양은 몰라요. 줄인 화면은 끝 공백만 떼기 때문에 글자가 있는 줄과 칸 위치는 그대로예요.
- 어떤 DOS 프로그램의 화면인지는 세지 않았어요.
- 도구 이름은 장부 기간 안의 호출에서만 찾아요. 이름을 못 찾은 화면은 이번 기간에 0개예요.
- 기간과 시점에 따라 값이 달라요. 서버 바이너리가 바뀌면 같은 명령으로 다시 재야 해요.
