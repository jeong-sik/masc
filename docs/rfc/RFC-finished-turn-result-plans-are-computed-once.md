# RFC finished-turn-result-plans-are-computed-once: 끝난 턴의 메시지는 Keeper 마다 한 번만 잰다

- 상태: **초안(2026-11-27).**
- 11-27 18:35 에 다시 띄운 masc 서버에서, 11분 뒤 CPU 풀 스레드 둘이 5초 표본 내내 쉬지 않았다.
- 두 스레드는 끝난 턴의 큰 도구 결과를 요청마다 다시 직렬화해서 크기를 잰다.
- 이 RFC 는 그 측정을 끝난 메시지 하나에 한 번으로 줄인다.

## 0. 요약

- Keeper 는 provider 요청을 보낼 때마다 `Keeper_model_input_demotion.plan` 으로 durable 기록 전체를 훑는다.
- 끝난 턴에서 2,048바이트를 넘는 도구 결과를 만나면 preview 를 만든다.
- 그다음 요청 본문을 직렬화해서 marker 로 바꾼 쪽이 더 작은지 잰다.
- Agent Core lane 은 잰 크기를 provider 시도(attempt) 하나 동안만 기억한다. 시도가 바뀌면 처음부터 다시 잰다.
- 공식 클라이언트 lane(Claude Code·Codex·Antigravity·ACP)은 잰 크기를 기억하지 않는다.
- 끝난 턴의 메시지는 다시 바뀌지 않는다. 메시지만 읽는 인코더의 측정값은 메시지로만 정해진다.
- 결정
  - D1. 바이트 동일성이 확인된 측정값은 Keeper 런타임이 인코더별로 보관한다.
  - D2. 공식 클라이언트 lane 네 곳은 인코더가 하나라서 표 하나를 같이 쓴다.
  - D3. Keeper별 한도와 프로세스 전체 보관 힙 한도를 함께 적용한다. 한도를 확보하지 못하면 측정값만 돌려준다.
  - D4. provider 설정을 읽는 wire 인코더의 측정과 preview 는 2단계다. 설정을 키로 쓸 투영을 먼저 정한다.
- 바뀌지 않는 것: 어떤 결과가 marker 가 되는지, marker 글자, 요청 크기, durable 기록, checkpoint.

### 1.4 기억에 드는 값 (11-27 20~22시)

- run 을 시작할 때 넘겨받은 checkpoint 가 없으면 디스크에서 다시 읽는다(`keeper_run_context.ml:192-203`).
  - 그래서 앞 run 의 메시지 값은 이번 run 의 메시지와 문자열을 나눠 쓰지 않는다. 표의 키는 사본 하나를 붙잡는다.
- 기록을 셌다. 11-26 이후 snapshot 을 쓴 trace 14개의 history segment 와 turn bundle 을 읽었다.
  - 도구 결과 글이 2,048바이트 이상인 메시지: Keeper 하나에 많게는 3,295개(저장 JSON 28.6MB), 14개를 합치면 19,905개(206.1MB).
  - 이 서버(PID 98020)의 RSS(`ps -o rss`)
    - 띄운 지 1시간 59분: 8,045,856KiB(7.7GiB)
    - 3시간 12분(21:47): 10,642,176KiB(10.1GiB)
- history 인코더(`Keeper_context_core.message_measurer`)는 측정기 하나에 버퍼 하나를 둔다(`keeper_context_core_message_json.ml:169-189`). 측정기는 걸음 하나의 것이다.
- `Provider_config.t` 의 `credential_source` 는 `Refreshable_credential of (unit -> …)` 를 담는다.
  - `Stdlib.compare` 는 함수 값에서 예외를 낸다. 설정 값을 통째로 표의 키로 쓸 수 없다.
  - 응답 캐시는 필드를 빠짐없이 펼쳐(warning 9) 고른 값만 키에 넣는다(`packages/agent_core/lib/llm_provider/cache.ml`).

## 2. 원인

- 끝난 턴의 메시지는 durable 기록에서 바뀌지 않는다.
- history 인코더와 공식 lane 인코더의 측정값은 메시지로만 정해진다.
- 그런데 Agent Core lane 은 측정값을 provider 시도 하나 동안만 기억한다. 공식 클라이언트 lane 은 기억하지 않는다.
- 그래서 CPU 는 새로 끝난 결과 수가 아니라 「durable 기록에 쌓인 큰 결과 수 × 시도 수」를 따라 는다.
- Fresh state 뒤에는 끝난 턴이 없어서 `plan` 이 497-498 에서 바로 끝난다. 15:10 에 이 경로가 없던 까닭이다.
- 18:35 재시작 뒤에는 11분 만에 나타났다. 비용이 가동 시간이 아니라 남은 기록을 따른다는 뜻이다.

## 3. 결정

### D1. Keeper 런타임이 인코더별 측정값을 보관한다

- Keeper 런타임 상태가 표를 소유한다. 삭제·개명·런타임 해제 때 해당 상태의 표와 예약을 반환한다. 프로세스 전역에서 Keeper 이름으로 메시지 사본을 보관하는 레지스트리를 두지 않는다.
- 표에는 인코더, 메시지 키, 측정값만 연결한다. 표의 키 비교가 같은 값으로 판단한 메시지는 인코딩 길이도 같아야 한다. 인코더에서 이 성질을 보장할 수 없는 값은 표를 조회하거나 갱신하지 않고 직접 잰다. 구조 비교가 같다고 보는 raw JSON의 양·음의 0과 비정상 부동소수점은 이 경로에 포함한다.
- 해시와 키 비교는 같은 키 규칙을 따른다. 비슷한 머리말을 공유하는 큰 본문이 한 버킷으로 몰리는지 확인한다. 길이와 본문 일부는 해시에 쓸 수 있지만, 적중 시 전체 키 비교가 필요하다.
- 값 키 대신 턴·메시지 순번과 내용 다이제스트를 쓰면 이전 실행의 메시지 사본을 보관할 필요가 줄어든다. 이 경우 같은 위치에서 바뀐 내용과 인코더 변경을 구별해야 한다. durable 기록 형식을 바꾸지 않는 현재 범위에서는 기록을 읽을 때 기존 메시지 경계로 안정적인 키를 구성할 수 있는지 먼저 확인한다.
- 걸음은 기록 한 번 순회다. Agent Core는 provider 시도, 공식 레인은 턴이 단위다. 걸음마다 측정 버퍼를 새로 만든다. 표의 잠금 안에서 걸음 번호를 할당하고, 적중 또는 동시 삽입 확인 때 마지막 사용 번호에 더 큰 값을 보존한다. 키 교체도 같은 잠금에서 한다.
- 붙잡은 값이 없으면 잠금 밖에서 잰 뒤 잠금 안에서 다시 조회한다. 겹친 걸음은 같은 값을 두 번 잴 수 있지만 항목과 힙 예약은 한 번만 넣는다. 두 걸음 기준은 종료 순서가 아니라 부여한 번호와 항목의 마지막 사용 번호로 정한다.
- provider 설정을 읽는 wire 측정은 D4를 따른다.

### D2. 공식 클라이언트 레인은 인코더 하나로 표를 같이 쓴다

- 네 런타임의 측정 식이 같다(§1.3). 공유 인코더는 그 인코딩을 정의한 모듈에서 한 번 만들고 토큰은 모듈 인터페이스에서 불투명하게 둔다. 레인이 토큰을 직접 구성하거나 다른 측정기를 대입할 수 없게 한다.
- 공유 식이 달라지는 레인은 기존 토큰을 재사용하지 않는다. 별도의 인코더를 정의하고 바이트 동일성을 따로 확인한다.
- `start_range_projection`이 걸음을 연다. 런타임이 측정기를 따로 넘기지 않게 인자를 없앤다.

### D3. Keeper와 프로세스에서 보관 힙의 한도를 적용한다

- 프로세스 한도는 모든 활성 Keeper가 유지하는 모든 인코더 표의 합계에 적용한다. 각 표의 상한과 별개로 삽입 때 프로세스 예약을 먼저 확보하고, 퇴출 또는 소유자 해제 때 반환한다. 한도를 확보하지 못하면 값을 재서 돌려주고 표에는 넣지 않는다.
- 키의 문자열뿐 아니라 힙 블록 헤더, 포인터 슬롯, 키·값 레코드와 해시 테이블의 저장 공간을 포함하는 보수적 추정치를 사용한다. 직렬화 길이는 작업량을 비교할 때만 쓴다. 상한과 추정치는 배포 전 §8의 힙 실측으로 비교한다.
- 자리가 모자라면 이번 걸음과 바로 앞 걸음에서 모두 사용하지 않은 항목부터 뺀다. 한 걸음에서 표를 한 번만 훑는다. 작업 집합이 상한을 넘는 경우에도 가장 오래된 조회 순서대로 항목을 교체하지 않는다.
- #55268과 #55397의 초안은 Keeper 이름으로 생존하는 표와 표당 64MiB 직렬화 길이만 사용한다. 소유자 해제와 프로세스 보관 힙 한도, 키 동일성 검증을 갖추기 전에는 이 두 구현을 배포하지 않는다.

### D4. wire 측정과 preview 는 2단계에서 다룬다

- wire 측정기는 `Provider_config.t` 에 따라 다르다. 설정을 키로 쓰려면 §1.4 의 `cache.ml` 처럼 필드를 펼쳐 고른 투영이 필요하다.
- preview(`Tool_blob_store.make_preview`)는 본문으로만 정해진다. 그러나 시도를 넘어 기억하려면 본문 사본이나 다른 키가 필요하다.
- 이 둘은 D1~D3 를 배포해서 잰 뒤 다룬다. 17:30 표본에서 wire 는 memo 아래 369 중 112 다.

## 4. 바뀌는 동작

- 같은 메시지에서 marker 선택과 요청 크기가 직접 측정과 일치해야 한다. 캐시 키가 인코딩 길이의 동일성을 보장하는 경우에만 재사용한다.
- Keeper의 첫 걸음은 값을 직접 잰다. 다음 걸음은 보관된 키와 일치할 때 표에서 값을 읽는다. 키가 빠졌거나 힙 예약 한도를 넘으면 값을 다시 잰다.
- 11-27 기록에서 전체 표본의 직렬화 길이는 약 206MB였다. 이 수치는 프로세스가 보관하는 힙 크기의 측정값으로 사용하지 않는다.

## 5. 경계 조건과 한계

- 구조 비교만으로 raw JSON의 `0.0`과 `-0.0`을 합치면 1바이트 차이로 marker와 창 선택이 바뀔 수 있다. 기존 시도 단위 memo가 그 경우를 허용했어도, 새 교차 걸음 표의 일치 조건에는 포함하지 않는다.
- 조회마다 해시와 비교 비용이 생긴다. 비슷한 큰 결과에서 충돌과 비교 비용이 이득을 상쇄하는지는 §8에서 확인한다.
- 4,096바이트 이하 결과는 #54361 뒤로 줄지 않는다. preview 가 본문 전체라 marker 가 더 크다.
  - 그래도 `plan` 은 그 결과를 재고, 표는 그 크기를 담는다. 11-27 기록으로 측정 대상의 37.6%(7,492개)다.
  - 하한을 preview 경계에 맞추는 일은 #55296 이 다룬다. 이 RFC 의 표와 함께 쓸 수 있다.
- 18:46 표본은 경로가 잘려서 직렬화의 호출자를 다 보여 주지 않는다.
  - 근거는 17:30 표본의 경로와 코드다. 확신도는 Medium 이다.

## 6. 하지 않는 것

- 어떤 결과를 marker 로 바꿀지의 규칙(`tool-results-age-out-of-context`)은 바꾸지 않는다.

## 8. 검증

- 기준선
  - 같은 Keeper 기록과 인코더로 변경 전후의 요청 수, 걸음 수, 실제 측정과 직렬화 호출 수, 한 걸음의 wall time을 기록한다. 18:46 표본은 후속 운영 참고로 사용한다.
- 동작
  - 같은 Keeper의 다음 걸음에서 인코딩 길이가 같은 메시지는 값을 재사용한다. 다른 Keeper와 인코더는 표를 공유하지 않는다.
  - signed zero와 캐시에서 제외되는 값으로 2,048바이트 및 창 경계에 걸리는 입력을 만들어, 직접 측정과 marker 및 범위 결과를 대조한다.
  - 공통 머리말을 가진 큰 도구 결과를 넣어 최대 버킷 길이와 조회 시간을 기록하고, 값 키와 안정 식별자 후보를 동일 기록에서 비교한다.
  - 두 걸음을 겹치고 한 키를 동시에 놓치게 해, 항목과 예약이 한 번만 생기고 늦게 끝난 걸음이 마지막 사용 번호를 되돌리지 않는지 확인한다.
  - 여러 Keeper를 채워 프로세스 상한에 도달한 뒤에도 측정값이 반환되는지, 삭제·개명·해제 뒤 해당 표의 힙 예약을 반환하는지 확인한다. 추정한 보관 힙과 실측 힙을 같은 기록에서 비교한다.
- 운영
  - 배포 뒤 11분과 2시간 무렵에 CPU 표본과 RSS를 관측한다. 요청 바이트는 같은 기록으로 직접 측정했을 때와 대조한다.
