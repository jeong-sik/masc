# Candle Grade 검토 초안 — ASSISTANT PROPOSAL

아래 등급은 **코딩 assistant의 해석 제안**이다. 사람이 매긴 기준 등급,
모델 측정 결과, 채택된 운영 규칙이 아니다. 커밋된 20개 사례를 해석한 기록이다.
측정 당시에는 사람 등급이 입력되지 않았지만, 현재 트리의 별도 사람 기준 파일에는
결과 공개 뒤 운영자가 지정한 사례 19의 `epic` 등급 한 건이 있다. 아래 표 전체를
사람 기준으로 채웠다는 뜻은 아니다.
RFC의 사람 기준 눈금 검증과 합격선 결정은 여전히 미완료다.

## 먼저 볼 다섯 가지 예

아래 표는 측정 당시 동결한 후보 프롬프트의 다섯 등급을 해석한 기록이다.
이후 수정한 미측정 후보에는 이 등급 표를 그대로 적용하지 않는다. 예제 수가
다섯이라는 뜻이며, 다섯 등급 사이의 인접 경계는 네 개다.

| 사례 | 제안 | 약속한 결과와 판정 이유 | 바로 옆 등급과의 경계 |
|---|---|---|---|
| 01: Preferences 탭의 오타 수정 | `trivial` | 기존 동작을 유지하며 표시 문구를 바로잡는다. | `small`: 상태 보존이나 조작 동작까지 바꾸는 약속은 없다. |
| 04: 필터된 지출 보고서의 CSV 내보내기 | `small` | 필터 결과를 CSV로 받는 한 가지 제한된 기능이다. | `medium`: 제목을 풀어 쓰거나 승인 시험을 24개 적었다고 별도 결과가 늘지는 않는다. |
| 11: 프로필 이미지 업로드·저장·보호된 조회·설정 미리보기 | `medium` | 이미지 등록, 보관된 이미지 접근, 설정 화면 확인을 함께 약속한다. | `small`: 이것들을 통상적인 이미지 업로드 한 기능의 완료 조건으로 보는 해석도 가능하다. **아직 모호한 예다.** |
| 15: Candle 구매부터 착용까지 도구·API·초상화에서 일치 | `large` | 구매로 생긴 소유 상태와 착용으로 생긴 외형 상태를 연결하는 결과다. | `medium`: 구매·착용 전체를 하나의 상점 기능으로 묶을 수 있다. 화면 수만으로 `large`가 되는 것은 아니다. |
| 20: workspace·회원·Goal·Task·Board·Keeper·예약·관측을 갖춘 hosted 제품 | `epic` | 서로 다른 기능군을 포함한 제품 전체의 사용 흐름을 약속한다. | `large`: 이 범위에서 일부 기능군을 임의로 빼지 않는 한, 하나의 통합 기능으로 보기 어렵다. |

01과 04, 20은 제안의 양 끝과 작은 기능을 설명하기 좋다. 11과 15는
`small`/`medium`/`large` 경계가 이미 확정됐다는 증거로 쓸 수 없다.

## 적용한 해석

- 입력은 실제 사례의 **title, metric, target_value 세 필드**다. 작업 시간,
  구현 난도, 변경 파일 수, 보안 중요도, Task 수, 비용은 등급 근거에 넣지 않는다.
- `trivial`은 사소한 국소 조정, `small`은 제한된 수정이나 단일 기능,
  `medium`은 명시된 여러 연결된 결과를 묶은 기능으로 읽는다.
- `large`는 여러 기능에 걸친 상당한 공동 결과, `epic`은 여러 기능군에
  걸친 제품·시스템 결과로 읽는다. 이는 후보 프롬프트의 문장을 적용한
  해석이며, 기능 수를 세는 별도 공식이나 고정 문턱을 추가하지 않는다.
- 같은 결과를 자세히 풀어 쓴 것과 별도 결과를 추가한 것을 구별한다.
  예를 들어 기억하기와 재시작 후 복원하기는 사례 05에서 하나의 약속이다.
  HTTP/MCP, 서버/대시보드/TUI처럼 제공 경로가 여러 개라는 이유만으로 올리지 않는다.
- `0`, `100%`, 시험 `24`/`30`/`40`/`50`개는 각 가상 Goal에 적힌 성공 조건이다.
  그 숫자를 범위 점수나 이번 평가의 합격선으로 사용하지 않는다.
- 아래의 인접 등급은 **같은 문구에 가능한 다른 해석**을 드러낸다.
  상상한 추가 요구사항을 원래 Goal에 붙여 더 높은 등급을 정하지 않는다.

## 20개 사례별 제안

입력 요약은 읽기 쉽게 옮긴 것이며 원본 입력을 대체하지 않는다.
`human-reference-*`는 기존 사례 ID일 뿐, 아래 제안을 사람의 답으로 만들지 않는다.

| 기존 사례 ID | 입력의 약속·metric → target 요약 | Assistant 제안 | 이유 | 검토할 인접 등급·불확실성 |
|---|---|---|---|---|
| human-reference-01 | Preferences 탭 오타 수정. 잘못된 표기의 출현 → `0`. | `trivial` | 표시 문자열의 국소 조정이며 지원 동작은 같다. | `small`: 동작 변경이 명시되지 않아 경계의 모호성이 작다. |
| human-reference-02 | 잘못된 Goal 기한 오류에 `YYYY-MM-DD`와 예시 표시. 형식·예시가 있는 오류 응답 → `100%`. | `trivial` | 기존 거절 응답을 이해할 수 있게 설명을 보강한다. 새 날짜 판정이나 입력 기능은 약속하지 않는다. | `small`: 오류 표현 변경을 단일 기능 개선으로 보는 해석은 가능하지만, 현재 결과는 국소 안내 문구다. |
| human-reference-03 | priority만 편집할 때 저장된 due date 보존. 기한이 변한 priority-only 편집 → `0`. | `small` | 저장 동작의 한 가지 불변식을 고치는 제한된 행동 변화다. | `trivial`: 수정 코드가 짧더라도 데이터 보존 동작이 달라진다. 구현 크기 때문에 내릴 근거는 없다. |
| human-reference-04 | 필터된 지출 보고서 CSV 내보내기. CSV 승인 시험 통과 → `24`. | `small` | 기존 필터 결과를 내보내는 제한된 새 기능 하나다. | `medium`: 새 기능이라는 사실과 시험 수만으로 여러 독립 결과가 되지 않는다. CSV 제목 장황화도 범위를 바꾸지 않는다. |
| human-reference-05 | 마지막 workspace 탭을 기억하고 재시작 후 복원. 탭 복원이 되는 재시작 시나리오 → `100%`. | `small` | 기억과 복원이 함께 하나의 사용자 상태 지속성을 이룬다. | `medium`: 두 동사를 별도 결과로 세면 올라가지만, 원문에서 기억만 하고 복원하지 않는 것은 약속의 완료가 아니다. |
| human-reference-06 | 기존 Goal 편집기에서 키보드만으로 Task 검색·선택. 마우스가 필요한 선택 여정 → `0`. | `small` | 기존 편집기의 Task 선택 흐름을 키보드로 완수하는 제한된 기능이다. | `medium`: 검색 기능 자체와 선택 기능 자체를 새로 약속한 것인지, 같은 선택 흐름의 키보드 조작인지 분리 정보가 부족하다. |
| human-reference-07 | 동일 이름 credential 갱신과 만료 game-controller 회수의 HTTP/MCP 원자성. 갱신된 유효 holder를 해제한 통제된 동시 실행 → `0`. | `small` | 명시된 결과는 갱신된 holder를 잘못 회수하지 않는 하나의 동시성 보장이다. 어렵거나 중요한 수정이라는 추측은 더하지 않는다. | `medium`: credential과 controller를 각각 독립 기능 결과로 볼 수 있으나, 이 입력은 두 경로가 공유할 하나의 원자성 조건을 측정한다. 경계 검토가 필요하다. |
| human-reference-08 | 저장된 Goal의 unknown field 거절과 서버·대시보드·TUI의 일관된 unavailable 표시. 조용한 수용 또는 빈 목록 표시 → `0`. | `small` | 권위 있는 Goal 데이터를 읽을 수 없다는 한 상태를 거절과 관측에 일관되게 보존한다. 제공 화면 수를 범위에 가산하지 않는다. | `medium`: 엄격한 저장소 판정과 사용자용 실패 표현을 별도 결과로 묶은 기능이라는 해석도 가능하다. 현재 입력만으로 경계가 확정되지는 않는다. |
| human-reference-09 | 기존 원장에서 Keeper 자신의 잔액과 구매 아이템을 읽는 도구. 타인 귀속 또는 현재 가격 재계산 → `0`. | `small` | 이미 있는 원장의 자기 계정을 정확히 조회하는 단일 읽기 기능이다. 구매나 가격 결정은 약속하지 않는다. | `medium`: 잔액과 아이템을 별도 결과로 나눌 수도 있지만 이 문구는 한 계정 조회 응답을 요구한다. |
| human-reference-10 | 아이템 목록, 각 아이템의 초상화 미리보기, 해제 시 기본 외형. 미리보기·기본 복귀가 없는 목록 항목 → `0`. | `medium` | 무엇을 고를 수 있는지 보는 목록과 선택한 외형을 확인하는 미리보기를 연결한다. 기본 복귀는 미리보기의 종료 조건으로 본다. | `small`: 목록 탐색부터 미리보기 해제까지를 제한된 미리보기 기능 하나로 볼 수도 있다. 이 사례는 경계가 특히 모호하다. |
| human-reference-11 | 프로필 이미지 업로드·파일 검증·리사이즈 보관·인증 조회·설정 미리보기. 업로드부터 재로드까지 승인 시나리오 → `30`. | `medium` | 등록, 저장된 결과에 대한 보호된 접근, 설정 화면 확인을 명시적으로 함께 제공한다. 시험 수는 근거가 아니다. | `small`: 나열된 결과가 일반적인 이미지 업로드 한 기능의 필수 완료 조건일 수 있다. 제목을 줄여도 같은 약속이면 같은 등급이어야 한다. |

## 이 묶음이 아직 구별하지 못하는 것

1. **모든 경계의 대조쌍이 없다.** 같은 분야에서 결과 하나만 추가하여
   `trivial`→`small`→`medium`→`large`→`epic`을 비교하는 구성은 아니다.
   서로 다른 분야의 20개 설명을 순서대로 둔 것만으로 눈금이 고정되지는 않는다.
2. **`medium` 부근이 특히 약하다.** 10·11·13의 나열 항목이 독립 결과인지
   한 기능을 끝냈다는 설명인지 두 해석이 가능하다. 이 세 사례에 붙인
   `medium`은 그 구별을 검토하기 위한 제안이지 확정 답안이 아니다.
3. **큰 단일 약속의 처리도 남아 있다.** 07의 원자성은 어려워 보이지만
   명시된 결과는 하나다. 17·19처럼 공통 실행·저장 기반은 한 subsystem이면서
   여러 기능군을 가로지른다. 후보 프롬프트만으로 이 경계가 해결됐다고
   주장할 수 없다.
4. **성공 조건이 범위를 모두 정의하지 않는다.** 11·18·20의 승인 시험
   개수는 그 시험 내용을 주지 않는다. 13의 operator controls 역시 구체적인
   조작 목록이 없다. 빈 부분을 추측해서 등급의 근거로 쓰지 않았다.
5. **독립된 사람 기준이 아니다.** 모든 사례는 assistant가 만든 가상 입력이다.
   특히 04는 이미 측정한 CSV 사례와 같은 입력이므로 보지 못한 검증 사례로
   취급할 수 없다. 이전 12×20 결과는 동일 CSV 약속의 문구 차이 개선만
   보여 주며, 이 표의 다른 등급이나 다섯 등급 전체의 정확도를 증명하지 않는다.

별도의 20사례 범위 조사에서 모델을 반복 호출하더라도 얻는 것은 사례별
등급 분포와 반복성이다. 이 표와의 일치율을 사람 기준 정확도로 계산하지
않으며, 실패 응답을 빼서 시도 횟수를 바꾸거나 지급 준비 완료로 해석하지 않는다.
