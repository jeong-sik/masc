# RFC-0472 — 용어집은 한 줄 색인과 도메인 파일로 나눈다

## 1. 문제

`docs/spec/00-glossary.md` 는 파일 하나에 모든 용어를 담고 있고, 계속 커지고 있다.
아래는 2026-10-07 기준 origin/main 에서 잰 값이다.

| 값 | 측정 |
|---|---|
| 파일 크기 | 298,162 바이트 (3,383 줄) |
| 항목 수 | 236 개 (6개 절: Core 116, Continuity 50, Collaboration State 33, Task Lifecycle 15, Repository Execution 13, Skills 9) |
| 절별 크기 | Core 144,362B · Continuity 80,699B · Collaboration State 42,805B · Repository Execution 13,564B · Skills 8,792B · Task Lifecycle 7,713B |
| 성장 | 10-04 287,029B·229개 → 10-07 298,162B·236개. 3일에 +11,133B·+7개(하루 평균 약 +3.7KB), 같은 기간 이 파일을 고친 커밋 16개 |
| 큰 항목 | 2KB 를 넘는 항목 39개(17%). 가장 큰 항목 Exact-output route 7,256B |

한 항목을 확인하려고 파일 전체를 읽는 일이 Keeper 와 검토자의 매일이다. 하루 약 +3.7KB 씩
커지는 파일을 통째로 읽는 비용은 성장과 함께 매일 다시 낸다. 이 성장 자체는 나쁘지 않다 —
"용어집은 코드에 있는 말만 싣는다"는 원칙 아래 새 기능마다 항목이 붙는 것이 맞다. 문제는
**한 파일에 전부 담는 모양**이다.

10-01 감사(D16a-13)도 큰 항목에 대해 "결정 A(한두 문장 + 코드 링크)면 줄인다"를 이미 적었지만
실행되지 않았다. 항목 축소와 파일 구조는 별개 문제이므로 이 RFC 는 구조만 다룬다(열린 질문 4).

## 2. 지금 용어집은 어떻게 참조되나

링크를 깨뜨리지 않으려면 참조 모양을 알아야 한다. 문서 트리 전체에서 잰 값이다.

| 참조 모양 | 수 | 깨지는가 |
|---|---|---|
| 경로 참조 `00-glossary.md` (14개 문서) | 14 | 색인 전환 후에도 유지 가능 |
| 앵커 참조 `00-glossary.md#...` | 0 | 해당 없음 |
| 줄번호 참조 `00-glossary.md:837` 형식 | 16 (4개 문서: 감사 3개, RFC-every-lane 1개) | 이동하면 깨진다 |

앵커 참조가 0이라는 뜻은, 오늘 기준으로는 분할이 링크를 깨뜨리지 않는다는 뜻이다. 줄번호
참조 16곳은 감사 기록(과거 문서)과 RFC 하나다. 줄을 옮기면 깨지므로 열린 질문 3 에서 다룬다.

## 3. 다른 문서 체계는 어떻게 하나

[Diataxis](https://diataxis.fr/reference/) 는 참조 문서(reference)를 정보 지향 문서로 보고,
"제품이 다루는 구조를 따라 조직하라"고 쓴다. 참조 문서는 사용자의 학습 순서가 아니라 대상의
구조(여기서는 masc 의 도메인)를 따라 나뉜다. Python 공식 문서와 MDN 도 용어 색인(glossary
index)을 긴 참조 문서와 별개 파일로 두고, 색인 한 줄이 본문 항목으로 이어진다.

masc 용어집에 그대로 옮길 수 있는 모양은 두 가지다.

- **한 줄 색인**: 항목마다 "이름 — 한 줄 뜻 + 링크" 한 줄. 용어를 찾는 사람은 색인만 읽고 끝낸다.
- **도메인 파일**: 정의 본문은 다루는 도메인(Core, Continuity …)별 파일에 둔다. 이미 있는 6개
  절이 도메인 경계이므로 새 분류를 만들지 않는다.

## 4. 제안

### 4.1 한 줄 색인

`docs/spec/00-glossary.md` 를 **한 줄 색인 파일**로 바꾼다(열린 질문 1). 항목마다 한 줄:

```markdown
- [Lane](glossary/core.md#lane) — 모델이 도는 exact-output 작업을 위한 고정 실행 경로
```

236줄이면 35KB 안쪽이 될 것으로 보지만(항목당 평균 1.26KB → 한 줄 약 120B), 구현 후 실측으로
확인한다. 새 항목이 붙을 때 색인에는 한 줄만 더해지므로 하루 +3.7KB 성장이 색인에는 약
+0.3KB 로 줄어든다. 색인 한 줄의 뜻은 "무엇인지 딱 한 단계 더 읽을지 말지"를 정하게 해준다.

### 4.2 도메인 파일 분할

정의 본문을 기존 6개 절과 1:1 로 옮긴다. 새 분류를 만들지 않는다.

```
docs/spec/glossary/core.md                  (116개 항목)
docs/spec/glossary/collaboration-state.md   ( 33개)
docs/spec/glossary/task-lifecycle.md        ( 15개)
docs/spec/glossary/skills.md                (  9개)
docs/spec/glossary/repository-execution.md  ( 13개)
docs/spec/glossary/continuity.md            ( 50개)
```

각 항목은 지금과 같은 `**용어**\n: 정의` 모양을 유지한다. 기존 워크플로(`grep '^\*\*용어\*\*'`,
항목별 Read)는 도메인 파일에서 그대로 동작한다. 이동 순서는 용어 이름 기록으로 남긴다.

### 4.3 새 항목 규칙

분할 뒤 새 기능의 용어는 (a) 해당 도메인 파일에 정의 본문, (b) 색인에 한 줄. 리뷰에서 확인할
것은 "색인 한 줄이 있는가"로 줄어든다.

### 4.4 항목 축소는 별개 단계

2KB 를 넘는 39개 항목의 PR 번호·route·값 이름을 `.mli` 주석이나 해당 RFC 로 옮기고 용어집에는
한두 문장 + 코드 링크만 두는 일(10-01 감사 D16a-13 결정 A)은 이 RFC 와 **별개 단계**로 한다.
불변식 문장이 `docs/spec/02-types-and-invariants.md` 와 용어집에 중복돼 있으면 그때 옮긴다.

## 5. 열린 질문

1. 색인을 `00-glossary.md` 자리에 둘지, 새 파일로 두고 `00-glossary.md` 에 한 줄 안내만 남길지.
   어느 쪽이든 경로 참조 14곳은 유지된다. 전자는 SPEC-INDEX 의 번호 체계(00-)와 "색인" 역할이
   어긋나고, 후자는 문서 하나가 더 늘어난다.
2. Core 144KB 는 하나의 도메인 파일로도 크다. 절( subsection ) 단위 2차 분할 기준(예: Keeper /
   Board / Task / Lane 로 나누는 등)은 Core 분할 단계에서 정한다.
3. 줄번호 참조 16곳을 어떻게 하나. 감사 문서는 과거 기록이라 그대로 두고 열린 RFC 1개만
   용어 이름 참조로 고치는 안과, 분할 PR 에서 전부 고치는 안이 있다.
4. 항목 축소(39개)를 이 RFC 의 구현 순서에 넣을지 별도 RFC 로 둘지. 10-01 감사는 별개 항목으로
   적었고, 섞으면 단계가 커져서 되돌리기 어렵다.
5. `SPEC-INDEX.md` 와 `02-types-and-invariants.md` 의 Dependencies 표기("00-glossary.md 에
   의존")를 분할 뒤 어떻게 고치나.

## 6. 검증

- 색인 236개 링크가 각자 항목으로 이동하는지 — 링크 검사(파일 존재 + 앵커 존재)를 CI 또는
  스크립트로 확인한다.
- 경로 참조 14곳이 여전히 뜻을 가리키는지 — `grep -rln '00-glossary' docs` 결과를 하나씩 연다.
- `grep '^\*\*용어\*\*'` 와 항목별 Read 워크플로가 도메인 파일에서 그대로 동작하는지.
- 이동 후 총 내용이 줄지 않았는지(삭제가 아니라 이동인지) — 옮기기 전후 용어 수(236)와
  바이트 총합을 대조한다.
- 색인 파일만으로 "용어 찾기"가 끝나는지 — 색인 파일 바이트를 실측하고, 색인에서 임의 용어
  10개를 골라 이동 클릭 없이(한 줄 뜻만으로) 알아볼 수 있는지 본다.

## 7. 구현 순서

한 번에 하나씩 쪼갠다. 각각 독립적으로 되돌릴 수 있다.

1. 색인 파일 만들기(내용 이동 없음). 가장 좁은 첫 단계이고, 이것만으로 "전체 읽기" 비용이
   색인 하나로 줄어든다.
2. 색인 전환 또는 안내 문장(열린 질문 1 결정 뒤).
3. 도메인 파일 6개 분할(내용 이동). 용어별 이동 기록을 PR 본문에 남긴다.
4. 줄번호 참조 정리(열린 질문 3 결정 뒤).
5. 항목 축소(열린 질문 4; 별도 RFC 가능).

## 8. 하지 않는 것

- 용어의 뜻을 이 RFC 에서 바꾸지 않는다. 이동과 색인만 다룬다.
- 코드 변경은 없다. `.mli` 로의 이전은 열린 질문 4/별도 RFC 다.
- 영어 용어를 한국어로 바꾸지 않는다(#41446 이 확정한 대로 코드·필드 이름은 영어 그대로 둔다).
- 용어집을 줄여서 "성장을 막는다"는 목적이 아니다. 성장 비용이 전체 파일이 아니라 색인 한 줄에
  머물게 하는 것이 목적이다.
