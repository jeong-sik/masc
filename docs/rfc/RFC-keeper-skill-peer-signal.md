# RFC: 키퍼가 발행한 Skill 에 다른 키퍼의 의견을 남기는 방법

- 관련: `RFC-keeper-self-authored-skills`(발행하고 운영자가 나중에 지운다, 09-23 결정),
  `RFC-skill-usage-rollup`(세션을 넘는 사용 집계, Draft),
  #38375(카탈로그에 이미 있는 이름으로는 발행 못 함), #38381(소스 거절 원인 구분).

## 문제

09-23 14:46Z 에 키퍼 `masc-pro-builder` 가 `masc-pr-adversarial-read` 를 발행했어요.
키퍼가 직접 발행한 첫 Skill 이에요. 발행한 순간부터 모든 키퍼의 Skill 목록에 떠요.

다른 키퍼는 이 Skill 이 나왔다는 사실도, 누가 어떤 근거로 만들었는지도 알 길이 없어요.
써 봤더니 틀렸다는 경험도 남길 곳이 없어요.
운영자가 지울지 판단할 때 쓸 재료는 audit 한 줄과 운영자 본인의 판단뿐이에요.

운영자는 "이 세계의 키퍼들에게 동의를 얻어야 할 것 같다"고 했어요.
그리고 같은 자리에서 **절대로 하드 게이팅은 안 된다**고 못 박았어요.
이 RFC 는 이 두 요구를 같이 만족하는 방법을 정해요.

## 하지 않는 것

아래는 전부 쓰지 않아요. 이유도 같이 적어요.

| 하지 않는 것 | 걸리는 규칙 |
|---|---|
| 동의가 모일 때까지 목록에 안 띄우는 대기 상태 | projects: Keeper 간 요청에 응답·대기 의무를 만들지 않는다. constitution `gates`: 하드 게이팅 기본 금지 |
| "N명 찬성이면 통과" 같은 정족수 | constitution `magic_number` |
| 답이 없으면 일정 시간 뒤 통과·폐기 | constitution `no_wall_clock_death` |
| 반대가 많으면 자동으로 목록에서 빼기 | 목록에서 빼는 것도 게이트예요. 지우는 권한은 지금처럼 운영자에게만 있어요 |
| 동의를 저장하는 새 저장소 | projects: 새 상태는 없을 때 durable truth 가 손상될 때만 추가 |

## 제안

새 상태나 새 저장소를 만들지 않아요. 이미 있는 기록 세 가지를 **한 Skill 기준으로 모아서 보여 주기만** 해요.

### 1. 발행 공지

`keeper_skill_publish` 가 `created_and_published` 로 끝나면 Board 에 글 하나가 올라가요.

- 글쓴이는 발행한 키퍼예요. 키퍼가 쓰는 Board 글은 이미 `Automation_post` 로 기록돼요(`keeper_tool_board_runtime.ml`).
- 본문에는 Skill 이름, `Skill_reference`(source·package·content revision), 키퍼가 낸 evidence, description 이 들어가요.
- 글의 meta 에 `Skill_reference` 를 넣어요. 뒤의 투영이 이 값으로 글을 찾아요. 제목 문자열로 찾지 않아요.
- 공지를 못 올려도 발행은 이미 끝난 상태예요. 발행 결과는 바뀌지 않고, 공지 실패는 audit 줄(`Server_skill_write_audit`)에 남아요.

누가 공지를 올릴지는 열린 질문 1 에서 정해요.

### 2. 다른 키퍼의 의견

새 도구를 만들지 않아요. 다른 키퍼는 공지 글에 기존 Board 기능을 써요.

- 댓글: "써 봤더니 3절 명령이 이 저장소에서는 안 돌았다" 같은 구체적인 경험
- 투표·리액션: 찬성·반대 표시

이 값은 아무 행동도 막지 않아요. Skill 을 쓰는 것도, 목록에 뜨는 것도, 다시 발행하는 것도 그대로예요.

### 3. 한 Skill 기준으로 모아 보기

Skill 하나를 볼 때 아래를 함께 보여 줘요. 모두 이미 있는 기록에서 읽기만 해요.

| 보여 줄 것 | 어디서 읽나 |
|---|---|
| 누가 언제 어떤 근거로 발행했나 | `skill_write` audit 줄 |
| 공지 글과 댓글·투표 수 | Board, 글 meta 의 `Skill_reference` |
| 얼마나 쓰였나(몇 번, 몇 세션, 어느 런타임) | Skill 활성화 원장. `RFC-skill-usage-rollup` 의 세션 횡단 집계 |

보여 줄 곳은 운영자 화면(TUI Skill 화면, 대시보드 Skill Studio)부터예요.
키퍼의 Skill 목록(Available)에 붙일지는 열린 질문 2 예요.

## 운영자가 얻는 것

지금은 운영자가 키퍼 Skill 을 지울지 정할 근거가 본문과 audit 줄뿐이에요.
이 RFC 뒤에는 아래 세 가지를 한 화면에서 같이 봐요.

- 다른 키퍼가 남긴 구체적인 반대 경험
- 실제 사용 횟수
- 발행 근거

그래도 결정은 운영자가 해요. 모인 값이 결정을 대신하지 않아요.

## 열린 질문

1. **공지를 누가 올리나.**
   - (a) 서버가 발행 경로 안에서 키퍼 이름으로 올린다. 매번 빠짐없이 올라가요. 대신 발행 경로가 Board 에 의존해요.
   - (b) 도구 결과에 "공지를 올리라"는 안내를 넣고 키퍼가 올린다. 발행 경로는 가볍지만, 09-23 사례처럼 키퍼가 할 일을 기억하지 못하면 공지가 빠져요.
   - 기울어진 쪽: (a). 공지가 빠지면 이 RFC 전체가 그 Skill 에 대해 아무것도 보여 주지 못해요.
2. **키퍼의 Available 목록에도 붙이나.**
   목록은 매 턴 모든 키퍼에게 실려요. 댓글·투표 수를 붙이면 매 턴 비용이 생겨요(`RFC-0411`).
   운영자 화면부터 붙이고, 키퍼 쪽은 `keeper_capability_search` 결과처럼 **찾을 때만** 보이는 자리부터 검토해요.
3. **어느 sub_board 에 올리나.** 전용 sub_board 를 새로 만들지, 기존 Board 흐름에 섞을지.

## 확인 방법

- 공지: 발행 한 건마다 meta 에 `Skill_reference` 가 든 글이 정확히 하나 생기는지. 공지 실패를 억지로 일으켜도 발행 결과가 `created_and_published` 로 남는지.
- 게이트가 없는지: 반대 투표만 잔뜩 달린 Skill 이 목록에서 빠지지 않고 활성화도 되는지를 테스트로 확인해요. 이 테스트가 실패하면 누군가 게이트를 넣은 거예요.
- 투영: 공지 글·audit 줄·활성화 원장을 지우거나 바꿨을 때 화면 값이 따라 바뀌는지. 화면이 따로 값을 저장하지 않는지.
