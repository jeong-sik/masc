# RFC: Keeper 창은 Librarian 이 흡수한 지점부터 싣고, 요청이 너무 큰지는 공급자가 판정한다

- 상태: Active. §1 은 결정, §2~§9 는 문제 정의와 적대적 검토, §10~§12 는 설계·이행·측정, §13 은 §1 의 근거와 코드에 넣는 순서다.
- 작성: 2026-09-15. §2~§9 는 코드 origin/main 5fb0fbe190 대조와 논문·업계·기억 구조 조사(§6.2~6.4)를 거쳤다. §1 의 1·2·5·6 과 §13 은 2026-09-18 라이브 실측(§13.1)을 보고 적었다.
- 관련: RFC #26534 (Memory OS 2.0 bounded working set), RFC-0363 (옛 도구 결과 강등), #26545, #26800, #24838, #27320, #28845, #31684

## 1. 결정 (운영자)

이 RFC 의 결정은 이 절에만 적는다. 다른 절은 근거와 설계다.

1. 창 크기를 숫자로 정하지 않는다. 요청은 Librarian 이 마지막으로 흡수한 지점부터 지금까지를 싣는다. Librarian 이 대화 이력까지 정리하므로, 그 앞은 다시 보내지 않는다. `context-high-water-tokens`·`context-low-water-tokens`·`max-prompt-bytes` 는 두지 않는다(§13.2, §13.6). Librarian 자신의 입력은 여기서 제외한다. Librarian 은 `keeper_librarian_runtime` 의 `prompt_max_messages` 로 자기 입력을 메시지 수로 자른다. 흡수 지점을 옮기는 쪽이 자기 흡수 지점에 묶이면, 한 번 못 도는 크기가 된 뒤로 영영 못 돈다.
2. 요청이 너무 큰지는 공급자가 판정한다. masc 는 바이트 상한을 선언하지도, 요청을 보내기 전에 재지도 않는다. 거절은 오류로 올리고, 범위를 좁혀 다시 보내지 않는다. 시작할 자리를 모를 때 이력 전체를 보내지 않는다(§13.3, §13.4).
3. masc 에는 컴팩션(LLM 요약)이 없다. librarian 이 수시로 기억을 정리하고, 창은 최근 원문만 담는다. 그래서 librarian 이 창 밖으로 밀려난 것 중 무엇이 살아남을지를 결정한다.
4. 입력할 자료 자체가 많은 경우를 빼면, 턴마다 보내는 컨텍스트는 가능한 한 줄인다. 컨텍스트가 커질수록 효율이 급격히 떨어진다고 본다. 근거는 §6.2~6.4 에 있다. 증거가 받쳐 주는 형태는 "관련 없는 것은 빼고, 필요한 것은 넣는다"이다. 모든 과제에 맞는 길이 기준은 증거에 없다.
5. 한 사실은 한 곳에만 적는다. 같은 사실이 두 곳 이상에 있으면 두 번째부터 지운다(§13.0). 모델의 창 상한은 카탈로그에 적고, 배포 바인딩의 `max-context` 는 그보다 좁은 선택만 적는다. 둘의 로드 규칙은 `RFC-runtime-two-layers` 규칙 4 한 곳이 정한다. `agent-core-models-overlay.toml` 은 두 값을 복제하지 않는다(§13.8).
6. 1·2 를 코드에 넣기 시작하는 때는 Librarian 생명주기 RFC(`RFC-librarian-lifecycle.md`) §7 (라)가 정하고, 그 전에 밀림 표시(같은 RFC 의 I4)가 화면에 떠 있어야 한다(§13.7).

- **캐시 영향을 나누지 않았다.** 지연 p50 은 토큰이 8배가 돼도 거의 그대로였다. 캐시가 앞부분 비용을 흡수했다는 해석과 맞는다. p90·최대가 늘어난 게 창 크기 때문인지, 캐시 실패 요청·rate limit 폴백·재시도 때문인지는 캐시 입력 토큰으로 나누기 전에는 말할 수 없다.
- **구간별 Keeper·런타임 구성이 다르다.** 10:00 이후에는 glm rate limit 과 kimi 주간 한도 소진으로 deepseek 폴백이 몰렸다.
- **답 품질은 재지 않았다.**

## 3. 현재 동작

HTTP 경로(`runtime_model_input_tail_window.ml`, `keeper_turn_driver_try_provider.ml`):

```
C  = max-request-body-bytes
C' = (Keeper, 런타임)이 마지막으로 성공한 용량이 C 이하면 그 값, 아니면 C
     (성공마다 기록, 프로세스 메모리, 재기동하면 사라짐 — keeper_context_overflow_shrink_state.ml)
R  = 도구 스키마 바이트 + 시스템 프롬프트 바이트 + C' / 10
U  = 고정 메시지(System, extra-system-context — 브리핑 포함) 바이트 + 생략 안내문 바이트
A  = C' − R − U

d = { 0, 60, 120, … } 중 남은 atom 바이트 합 ≤ A 인 가장 작은 값
    (없으면 1 단위로 다시 찾는다)
보내는 atom = N − d
그다음 RFC-0363 강등이 옛 atom 을 줄이고, 줄어든 크기로 다시 자른다.
공급자가 ContextOverflow 를 돌려주면 C' 를 절반으로 줄여 같은 런타임에 다시 보낸다.
```

- 토큰 수와 모델 창(`max-context`)은 이 계산에 들어가지 않는다.
- **C 를 선언하지 않은 바인딩에는 창이 아예 없다.** `uncapped_model_input_projection` 은 이력을 전부 보낸다(`keeper_turn_driver_try_provider.ml:902-908, 1137-1146`). 2026-09-08 기준 저장소 바인딩 155개 중 117개가 상한을 선언하지 않았다(`keeper_vision_tool.ml` 주석). 즉 지금은 창이 있느냐 없느냐부터 C 가 정한다. 라이브 설정은 HTTP 바인딩 8개 전부에 C 가 있다.
- 설계(RFC #26534 §3.1)는 전송 창을 "최근 K턴 원문, 구성상 유계"로 정했다. 구현(#26545 atom 수 → #26800 측정 바이트)은 "본문 바이트 상한까지 채우기"로 들어갔다. atom 무게가 0.3KB~8.7KB 로 달라 atom 수로는 요청 크기를 막을 수 없다는 이유였다.
- 그 결과 창 크기는 명시된 적 없이, 7월 사고(#24838) 때 넣은 거절 방지 상한의 부작용으로 정해져 왔다.

### 4.1 곳별 적대적 판정

**1·1a. 이력 창**
- 부당한 이유: 창 크기는 의도(토큰)인데 전송 한도(바이트)로 정해진다. 상한이 없으면 창이 사라지고, 상한을 스펙으로 올리면 창이 넓어진다.
- 반론: 창이 C 를 넘으면 요청이 거절되므로 C 는 창의 위 한계여야 한다.
- 재반론: 위 한계와 크기를 정하는 값은 다르다. 토큰 창을 바이트로 환산한 값이 C 를 넘으면 설정이 모순된 것이다. 이 모순은 드러내야 한다. 조용히 줄이면 숨은 결합이 다시 생긴다.
- 예비분 `C'/10` 도 부당하다. 측정하지 못한 필드의 크기는 상한이 아니라 실제 보내는 내용에 비례한다. 상한이 512KB 에서 4MB 가 되자 예비분은 52KB 에서 419KB 가 됐다.

**2. 브리핑**
- 1번과 **같은 결합**이다. 브리핑은 고정 메시지로 붙어 U 에 들어가고, 그만큼 A 를 줄인다(`agent_turn.ml:34-52`).
- 부당한 이유:
  - 브리핑 크기는 정보 설계이지 전송 한도가 아니다.
  - 창과 다른 모수(C 의 share)라서, 창을 토큰으로 바꿔도 브리핑은 여전히 C 를 따라간다.
  - Claude Code 는 masc 가 HTTP 본문을 만들지 않는데도 C 가 들어간다.
- 반론: 브리핑은 창에서 자를 수 없으니 예산이 없으면 창을 잡아먹는다.
- 결론: 예산은 필요하다. 다만 같은 토큰 창 안의 토큰 예산이어야 한다.

**3. HTTP overflow shrink**
- 부당한 이유:
  - **생성자 하나(`ContextOverflow`)가 두 가지를 싣는다.** 하나는 공급자의 모델 창(토큰) 초과이고, 다른 하나는 masc 가 자르지 못해 스스로 거절한 바이트 초과다(`limit = None`, `runtime_model_input_tail_window.ml:72-86`, `try_provider.ml:838`). shrink 는 둘 다 C' 절반으로 대응한다.
  - 공급자의 본문 크기 초과(`Request_body_too_large`)는 따로 분류돼 shrink 를 타지 않는다(`keeper_turn_driver_try_runtime.ml:98-116`).
  - 성공마다 기록되는 기억 값은 설정 밖의 숨은 상태다. 상한을 올려도 창이 넓어지지 않고, 재기동하면 갑자기 넓어진다(§2). 운영자는 설정만 봐서는 지금 창이 어떤 크기인지 알 수 없다.
- 반론: 모델 창이 잘못 선언된 경우를 버티는 안전장치이고, #31684 처럼 기억 값이 틀리면 `forget` 한다.
- 결론: 안전장치는 유지할 가치가 있다. 먼저 오류 두 종류를 타입으로 나누고, 토큰 초과는 토큰 창으로 대응해야 한다.

**4·5·6. 공식 클라이언트 경로**
- `max-prompt-bytes` 는 공식 클라이언트에 넘길 때의 실제 전송 한도일 때만 판정 근거가 된다. Antigravity 는 typed overflow를 보내지 않는다. 2,078,915 바이트가 끝까지 간 실측만으로 상한을 없앤 뒤, 세 장기 Keeper가 매번 21.9~48.5MB를 fresh session에 실어 첫 턴 전에 실패했다(#37123, 2026-09-19). 따라서 이 레인은 성공이 확인된 전송 크기를 명시하고, 그 안에서 이력을 자른다. 선언이 없으면 추측하지 않고 admission에서 거절한다.
- 2026-09-20부터 Antigravity와 Claude Code의 fresh-session 이력은 먼저 §10.4의 검증된 씨앗 앞머리에서 시작한다. 각 레인의 선언 창이 더 깊게 자르면 그 뒤쪽 자리가 이기며, 씨앗이 없거나 현재 이력이 같은 atom을 열지 않으면 전체 이력에서 레인 창을 적용한다.
- Antigravity 합성 순서는 durable 이력에서 씨앗 앞머리 승인 → Gate replay reference 추가 → 선언 바이트 창 적용 → durable 이력 좌표로 관측 기록이다. Gate reference는 실제 전송 한도에는 포함하지만 다음 checkpoint 이력의 앞머리 atom으로 기록하지 않는다.
- 부당한 부분:
  - 그 한도를 창 크기 결정에 쓴다.
  - Claude Code 에는 HTTP 본문이 없는데 C 가 섞인다.
  - Codex 는 overflow 뒤 바이트로 자른 값을 기억한다.

**8. librarian 입력**
- 1판의 "타깃 바이트 상한까지 채운다"는 틀렸다. 실제로는 메시지 수 상한에서 시작해 바이트로만 줄인다.
- 실제 결함: **쓸 수 있는 사다리 슬롯 전부**의 상한에 맞춰야 한다(`:348-359, 437`). 그래서 실제로 쓰일 슬롯의 상한이 크더라도, 사다리에서 가장 작은 상한이 librarian 프롬프트 크기를 정한다.
- 타깃 상한은 overlay `[[targets]]` 의 별도 선언이다. runtime.toml 바인딩 상한과 맞추는 코드는 찾지 못했다(미확인).
- 창을 작게 할수록 librarian 이 더 중요해진다(결정 3). 그런데 librarian 자신이 보는 입력이 가장 작은 슬롯의 바이트 상한에 묶여 있다. 이 부분은 Keeper 창보다 먼저 봐야 할 수 있다.

**9. Vision 이미지**
- 이미지는 그대로 전송 바이트다. 상한에 맞춰 줄이는 것은 전송 적응에 가깝다.
- 전역 크기 한도가 이미 있다(`MASC_KEEPER_VISION_MAX_DIMENSION`, 기본 1568, `env_config_keeper.ml:410-420`).
- 반론: 줄이면 모델이 보는 내용이 조용히 바뀐다. Claude Code 는 요청이 너무 크면 이미지·문서를 빼고 재시도한다고 문서에 적는다(code.claude.com/docs/en/errors#request-too-large).
- 결론: 해상도는 모델 스펙과 전역 한도가 먼저 정하고, 상한에 맞춰 줄였다면 그 사실을 기록할 때만 정당하다.

## 5. 결정 자체에 대한 적대적 검토

결정을 뒤집자는 것이 아니다. 결정이 풀어야 할 난점을 숨기지 않으려는 것이다.

**A. chat-completions 호환 공급자는 보내기 전에 토큰을 셀 수 없다.**
- agent_core 는 Anthropic `count_tokens`, OpenAI Responses `input_tokens`, Gemini `countTokens` 로는 보내기 전에 센다(`input_token_count.mli`).
- glm, deepseek, kimi, ollama 같은 chat-completions 호환 공급자는 받은 뒤에야 알려준다.
- 이런 공급자에서는 토큰 창이 추정에 기반한 목표이지 보장이 아니다. 조사한 다섯 에이전트 모두 추정한 뒤 넘치면 사후 처리한다.
- "추정 계수를 코드에 박지 않는다"를 지키면, 첫 턴이나 모델 교체 직후처럼 실측이 없는 요청을 무엇으로 자를지 정해야 한다.

**B. 앞부분이 생각보다 덜 고정돼 있다.**
- 60 atom 양자화는 R, U, 강등 크기가 고정일 때만 앞부분을 지킨다.
- 브리핑은 한 턴의 첫 라운드에만 붙는다(`prompt_block_id.ml:67-69`). 그래서 같은 턴 안에서 라운드 1과 2의 A 가 달라져 자르는 위치가 움직일 수 있다.
- 강등 경계는 턴마다 움직여 남은 atom 크기를 줄이므로, 자르는 위치가 뒤로 갈 수도 있다.
- 토큰 예산을 턴마다 바뀌는 실측 비율로 환산하면 흔들림이 더 커질 수 있다.
- 요청마다 자르는 위치가 얼마나 자주 바뀌는지 먼저 재야 한다.

**C. 창 선언 위치와 폴백.**
- C 는 이미 바인딩별이라, 오늘도 폴백하면 창이 바뀐다(`runtime_adapter.ml:698`). 바인딩별 토큰 창이 새 비용을 만드는 것은 아니다.
- 다른 공급자로 폴백하면 창 크기와 상관없이 프롬프트 캐시가 사라진다. 같은 공급자 안에서 폴백할 때만 창 크기 차이가 새 비용이 된다.
- 창의 필요량은 모델보다 Keeper 의 일에 가깝다. pr-updater 는 41K 로도 돌았다. 선언 위치는 따져 볼 여지가 남아 있다.

**D. 85K 는 체감이다.**
- 측정한 것은 지연과 사용량뿐이고, 캐시 영향도 나누지 않았다(§2.1).
- 창 크기별 답 품질을 비교하는 하네스가 필요하다.

**E. 창이 작은 모델이 있다.**
- local-granite 의 창은 131,072 토큰이다. 85K 에 브리핑·도구 스키마·출력 예약을 더하면 넘을 수 있다.
- 토큰 창은 모델 창에서 고정 부분을 뺀 값을 넘지 못해야 한다. 이는 토큰 대 토큰 결합이라 결정 2와 부딪히지 않는다.

**F. librarian 의 틈.**
- librarian 은 전송 절단과 무관하게 checkpoint 를 읽는다(RFC #26534 §3.2). cadence 는 3턴이다(§3.3).
- 그래서 Keeper 창을 줄여도 librarian 이 읽는 재료는 줄지 않는다.
- 틈을 실제로 넓히는 것은 librarian 자신의 입력이 가장 작은 슬롯 상한에 맞춰 줄어드는 것이다(§4.1 8번).

**G. 바이트 상한은 계속 필요한가.**
- 조사한 다섯 곳 중 요청 전에 막는 바이트 상한이 있는 곳은 Claude Code(32MB)뿐이다. 나머지는 413 을 사후 처리한다.
- masc 는 ollama.com 이 5.7MB 에서 이유 없는 400 을 내서(#24838) 상한을 두었다.
- (2026-09-16 개정) 상한은 없앴다(§1 2, §11 1e). 그 이유 없는 400 은 이제 열린 자리다: §10.5 의 공급자 트리거는 "넘쳤다고 하면"이고, 사유 없는 400 은 `Unknown_invalid_request` 로 걸음 없이 턴을 끝낸다(RFC-0353 #24838 행: 비재시도·비회전, 41/41 같은 런타임). 상한·저수위를 선언한 바인딩은 토큰으로 먼저 비우므로 그 크기에 닿지 않는다. 선언이 없거나 냉시동으로 전부 실린 요청은 닿을 수 있다. 사유 없는 거절도 걸음의 트리거로 볼지는 §8 의 13 이 답한다.

**H. 큰 창이 싸 보이는 경우.**
- polisher #3887 은 입력의 99.3% 가 cache read 였다. 공급자가 캐시 토큰을 싸게 받거나 사용량에 덜 세면, 큰 창의 비용 논거는 약해진다.
- 반대 방향의 논거는 다르다. 캐시는 입력 재계산 비용과 첫 토큰 지연만 줄이고, 모델이 긴 입력을 다루는 어려움은 줄이지 않는다(§6.3). 결정 4의 근거는 비용이 아니라 효율과 품질이다(§6.2).

**I. 창을 줄이면 librarian 이 아직 안 적은 사실이 먼저 빠질 수 있다.**
- F 는 librarian 이 읽는 재료가 줄지 않는다고 했다. 그러나 재료를 읽는 것과 사실을 이미 적어 둔 것은 다르다.
- RFC #26534 §3.2 는 절단과 librarian 사이의 동기화 장치(watermark)를 두지 않았다. 근거는 librarian 이 절단과 무관하게 checkpoint 를 읽는다는 것이다.
- 조사(§6.4)는 정리가 늦으면 점수가 떨어진다고 보고한다. 창의 하한을 "librarian 이 아직 안 읽은 턴"으로 두라는 결론도 있다(직접 잰 논문은 없음).
- 평소에는 틈이 작다. cadence 가 3턴이고 85K 창에는 보통 그보다 많은 턴이 들어간다.
- 틈이 커지는 때는 두 경우다. 턴 하나가 커서 창에 3턴이 안 들어갈 때, 그리고 librarian 이 밀릴 때다. librarian 런타임이 실패하거나 사용량 한도에 걸리면 밀린다. 2026-09-15 에 ollama cloud 한도가 34번 났다.
- 이 틈이 실제로 사실을 잃게 하는지는 아직 재지 않았다. 잰 뒤에야 §3.2 를 다시 볼지 정할 수 있다. 동기화 장치는 새 상태를 추가하는 일이라, masc 원칙(없으면 durable truth 가 손상될 때만 추가)을 먼저 따져야 한다.

### 6.3 업계 권고와 비용 (2026-09-15 확인)

- Anthropic(2025-09-29)은 "가장 작은, 신호가 강한 토큰 집합"을 권한다. 100턴 웹검색 평가에서 context editing 으로 토큰 −84%, 성능 +29%, memory tool 병행 시 +39% 였다(claude.com/blog/context-management).
- Chroma Context Rot(2025-07, 18개 모델): LongMemEval 요약본(~300 토큰)이 전체본(~113K)보다 성능이 높았다.
- Manus(2025-07-18)는 KV 캐시 적중률을 가장 중요한 지표로 본다. 앞부분을 고정하고 뒤에만 붙인다.
- 턴당 몇 토큰을 권하는 곳은 없다. 나온 수치는 요약 트리거 기본값(Anthropic 100K·150K, OpenAI 예시 200K)뿐이고, 요약이 있는 구조를 전제로 한다.
- Prefill: Llama3 405B 에서 128K → 1M(7.8배)에 TTFT 3.8초 → 77초(약 20배)(arXiv 2411.01783). 100K 대 700K 직접 비교값은 없다.
- 캐시는 입력 재계산 비용과 TTFT 만 줄인다. 모델이 긴 입력을 다루는 어려움은 그대로라는 게 공급자 문서의 공통 설명이다(Anthropic·OpenAI 문서). §5 H 의 비용 논거는 효율 논거를 대신하지 못한다.
- ollama cloud:
  - 신규 요금제(2026-08-31)는 캐시 토큰도 cached 단가로 사용량에 넣는다.
  - 레거시 요금제는 5시간·주간 한도가 있고 "캐시를 공유하면 덜 쓴다"고만 적는다.
  - 2026-09-15 에 받은 "session usage limit" 은 레거시 5시간 한도로 보인다(추정).

- **원문이 창에 들어가면 원문이 더 정확하다**(여러 벤치 일치). 창을 줄이면 정확도 일부를 잃는다고 보고 설계해야 한다. 그 손실을 librarian 과 원문 조회로 메워야 한다.
- **사실은 원문을 대신하지 말고 원문을 가리켜야 한다.** 원문 보관본을 필요할 때 찾는 경로가 있어야 한다.
- **갱신과 모순 처리가 가장 약하다**(벤치 3개 일치). 유효 구간·출처 턴·사유 있는 drop 이 대응책으로 제시되지만, 효과를 따로 잰 증거는 약하다.
- **정리가 늦으면 점수가 떨어진다.** 조사 결론은 "원문 창의 하한은 librarian 이 아직 안 읽은 턴 전부"다. 이를 직접 잰 논문은 없다.
- **정리는 항목 단위로 조금씩 고쳐야 한다.** 통째 재작성은 내용이 무너진다(사례 1건). 우리 librarian 계약(retain / drop+사유 / new_claim)은 이 방향이다.

## 7. 어떤 해결이든 지켜야 할 것

1. 상한과 저수위는 토큰으로, 요청 전체 기준으로 선언되고, 요청 본문 상한 값이나 상한 선언 여부에 따라 변하지 않는다. (2026-09-16 개정: 작업 창 W 는 없다)
2. (2026-09-16 개정) 요청 본문 상한은 없다. 본문이 너무 큰지는 공급자가 판정하고, masc 는 그 거절에 걸음으로 답한다.
3. **예외 후보**: atom 하나가 그 자체로 C 를 넘는 경우(#28845 현재 턴 강등, Vision 축소)는 어떤 토큰 창으로도 풀리지 않는다. 이때 바이트가 "강등할지 거절할지"를 고르는 것까지 허용할지, 그런 요청은 거절할지 정해야 한다.
4. 창 크기와 요청 본문 상한 사이의 모순은 조용히 줄이지 않고 드러낸다.
5. 공급자 프롬프트 캐시를 위해 전송 앞부분의 흔들림을 재고, 그 이상 늘리지 않는다.
6. 도구 결과는 호출보다 먼저 비워질 수 있고, 그 자리는 남는다. 호출이 빠지면 결과도 빠진다. 그 반대는 없다. (2026-09-16 개정. 이전: 같이 남거나 같이 빠진다)
7. 컴팩션(LLM 요약)을 되살리지 않는다.
8. 추정 계수를 코드에도 시드 설정에도 두지 않는다. 바이트당 토큰(밀도)도 추정 계수다.
9. 모델 창을 넘는 토큰 창은 허용하지 않는다(토큰 대 토큰).
10. 운영자가 설정만 보고 지금 창 크기를 알 수 있어야 한다. 성공 용량 기억 같은 숨은 상태가 창을 바꾸면 그 사실이 보여야 한다.

## 8. 열린 질문

1. chat-completions 호환 공급자에서 실측이 없는 요청(첫 턴, 모델 교체 직후)은 무엇으로 자르나. → 답(2026-09-16): 자르지 않는다. 들어가는지는 공급자가 판정하고, 원장은 첫 usage 부터 선다. Unmeasured 부트스트랩 경로는 예외로 좁혀 답한다(결정 2026-09-16, task-1589 Fusion 심의 `kmsg-97ac093dc84309f12224ee760cf10fa8`): 부트스트랩 뷰(`project_newest_atom`)는 pinning된 문맥에 더해 원본 chat-operation이 연 최초 User atom(atom 0)과 최신 atom을 함께 보낸다. 이전 동작은 최신 atom 하나만 남겨 원본 지시를 생략 프리앰블로 치환했고, resume이 처음 쓰는 런타임으로 넘어가는 순간 그 지시가 모델에 도달하지 않았다(test_keeper_direct_runtime_resume가 잡은 결함). 측정된 창 경로와 공급자 overflow shrink는 바꾸지 않는다.
2. 토큰 예산으로 자르면서 앞부분 흔들림을 어떻게 지금 이하로 유지하나. 지금 흔들림은 얼마인가. → 답: 덧붙이기만 하고 비움·F 변경을 한 턴에 모은다. 흔들림은 usage 의 cache_hit 로 매 턴 잰다.
3. 창을 바인딩별로 둘지, Keeper별로 둘지.
4. 브리핑 예산을 토큰 창 안에서 어떻게 나누나. 폴백 뒤 다시 맞추나.
5. `ContextOverflow` 의 두 경우(공급자 토큰 초과, masc 바이트 거절)를 어떻게 나누나. 토큰 초과 뒤 줄인 창을 기억할지. → 답: 토큰 초과는 비우기 사다리, 바이트 거절은 전송 상한 그대로. 줄인 창 기억은 없다. 원장이 있다.
6. librarian 입력은 사다리의 가장 작은 슬롯이 아니라 무엇에 맞춰야 하나. overlay 타깃 상한과 바인딩 상한의 이중 선언을 어떻게 하나.
7. Vision 해상도는 모델 스펙과 전역 한도 중 무엇을 기준으로 하나.
8. 85K 가 맞는지 판단할 품질 하네스를 무엇으로 만드나. 캐시 입력을 나눈 지연 측정을 어떻게 붙이나. → 답: 85K 는 질문이 아니었다. 하네스는 상한·저수위의 효과(§12)를 잰다.
9. 상한을 선언하지 않은 바인딩(창 없음)에 토큰 창을 새로 적용하는 것은 동작 변경이다. 이행을 어떻게 하나.
10. 창의 하한을 librarian 진행 위치로 둘지(§5 I). 둔다면 RFC #26534 §3.2 를 어떻게 고치나. → 답: 둔다. Librarian 이 읽은 묶음만 비울 수 있다(§10.5). #26534 §3.2 개정은 §11 5단계.
11. Keeper 가 창 밖 원문을 필요할 때 찾는 경로가 지금 있나. 없다면 창을 줄이기 전에 필요한가. → 답: 없다. 원문 열기 도구가 §11 5단계이며, 사다리 2단계 전에 있어야 한다.
12. 창 크기 하네스는 무엇을 재나. 후보는 Keeper 과제 성공률, 지연(캐시 입력 분리), 사용량, librarian 사실의 갱신·모순 오류다. → 답: §12.
13. (2026-09-16) 사유 없는 거절(400/422 를 읽었지만 원인을 못 세운 `Unknown_invalid_request`)을 걸음의 트리거로 볼지. 지금은 걸음 없이 턴이 끝나고 다음 사이클이 같은 요청을 다시 보낸다. 상한·저수위를 선언한 바인딩은 그 크기에 닿지 않지만, 선언이 없거나 냉시동으로 전부 실린 요청은 닿을 수 있다(ollama.com 5.7MB, #24838). 후보는 둘이다. (a) 거절의 사유와 무관하게 "공급자가 이 요청을 거절했다"를 걸음으로 답한다. 사다리는 유한하다(묶음 → 반감 → atom 하나 → 최후 수단 → 거절이 선다). 크기와 무관한 400 도 log2(N) 번 줄여 보낸 뒤 같은 거절로 끝나고, 그 사이 앞이 움직인다. (b) 지금대로 두고 선언을 필수로 한다. 로컬 ollama 처럼 거절 대신 조용히 자르는 공급자는 어느 쪽이든 선언으로만 막힌다. → 답: 둘 다 아니다. 어떤 거절도 범위를 좁혀 다시 보내는 트리거가 아니고, 거절은 오류로 올린다(§1 의 2).

### 10.1 한 줄로

요청은 고정 접두사 F, 이력 묶음, 꼬리, 새 입력 순서로 덧붙이기만 한다. 묶음의 토큰 수와 요청 전체의 토큰 수는 공급자 usage 에서 정확히 나온다. 전체가 선언한 상한을 넘으면 Librarian 이 읽은 묶음에서 도구 결과부터, 그다음 묶음째로, 저수위까지 한 번에 비운다. 밀도도, 바이트당 토큰도, 반감 재시도도 없다.

### 10.2 정확한 값과 정책

| 값 | 출처 | 성격 |
|---|---|---|
| 묶음 토큰 | 꼬리 T 를 싣지 않은 연속한 두 표본의 `usage.input_tokens` 차분 | 정확 |
| 전체 (F + 이력) | T 를 싣지 않은 마지막 표본의 `usage.input_tokens` − 뺀 묶음 | 정확 |
| 접두사 적중 | `prompt_cache_hit_tokens` (DeepSeek), `cache_read_input_tokens` (Anthropic), `usage.input_tokens_details.cached_tokens` (OpenAI) | 정확, 단위 반올림. 관측용 |
| 들어가나 | count 엔드포인트(Anthropic·Kimi, agent_core `Require_exact_fit`) 또는 공급자의 ContextOverflow | 공급자 판정 |
| `max-context` | 모델 선언 | 선언 |
| 상한, 저수위 | 운영자 선언, 요청 전체 기준 토큰 | 정책 |
| 비우지 않는 도구 | 운영자 선언, 도구 이름 목록 | 정책 |
| bytes/token, 밀도, 반감 | — | 쓰지 않는다 |

상한과 저수위를 "이력만" 이 아니라 "요청 전체" 기준으로 두는 이유는 정확성이다. F 만 따로 떼는 값은 count 엔드포인트 없이는 없지만, F + 이력은 T 를 싣지 않은 마지막 usage 가 곧 그 값이다. T 와 새 입력은 전체에 들지 않는다. 상한과 `max-context` 사이의 여유가 그것을 담고, 모자라면 공급자 거절이 판정한다(§10.5).

### 10.3 묶음과 원장

- 묶음(block)은 연속한 두 usage 응답 사이에 이력에 덧붙은 atom 들이다. atom 은 §3 의 정의 그대로다(assistant 메시지 하나와 그것이 부른 도구 결과, 또는 user 메시지 하나).
- 요청의 `input_tokens` 는 F + 이력 + T 다. T 는 턴의 첫 요청에 실린다. 도구 결과 뒤 라운드에는 운영자 메모 블록만 남고(`Prompt_block_id.injected_on_post_tool_round`), 메모가 실린 라운드도 T 를 실은 요청이다.
- 두 요청의 차분이 그 사이에 덧붙은 묶음의 토큰이 되는 조건은 셋이다. F 해시가 같고, 그 사이에 뺀 묶음의 토큰을 더해 주고, 두 요청 모두 T 를 싣지 않았다. 이 조건을 채우는 usage 를 표본이라 부른다.
- T 를 실은 요청의 usage 는 표본이 아니다. 아래의 usage 없는 응답과 똑같이 다룬다. 턴 경계에 걸친 atom(직전 턴 마지막 응답, 새 입력, 이번 턴 첫 응답)은 이번 턴의 첫 도구 뒤 라운드가 한 묶음으로 잰다.
- 요청이 한 번뿐인 턴은 표본을 남기지 않는다. 그 턴의 atom 은 다음 표본이 잴 때까지 크기를 모르고, 그동안 전체는 마지막 표본의 값에 머문다. 원장이 늦게 아는 만큼은 공급자 거절이 받는다.
- 생략 preamble 은 앞이 0 에서 처음 움직일 때 요청에 생긴다. 앞이 0 에 있는 동안 가장 오래된 묶음은 크기를 모르는 냉시동 묶음이라, 0 을 떠나는 이동은 늘 전체를 모르게 만든다. preamble 의 토큰은 다음 표본이 전체를 새로 세울 때 같이 들어간다. 따로 둔 규칙은 없다.
- 도구 결과 강등 경계(RFC-0363)는 턴의 첫 atom 이라 턴마다 한 번 움직인다. 직전 턴의 도구 결과는 그때부터 마커로 실리고, 그 묶음은 잰 크기보다 가벼워진다. 표본의 강등 경계가 전체를 잰 표본과 다르면, 낮은 경계부터의 묶음과 그 뒤 덧붙은 atom 을 한 묶음으로 합친다. 크기는 합친 묶음들이 알던 크기 + 차분이다. 차분이 정확히 "덧붙은 atom + 다시 실린 atom 의 변화" 라서 그 합이 지금 크기이고, 차분이 음수여도 같다. 한 번도 재지 않은 묶음이 섞이면 크기를 모른다.
- F 해시가 다른 연속 응답 사이의 차분은 원장에 넣지 않는다. 그 턴은 캐시도 깨지므로, F 변경(툴 스키마·시스템 프롬프트)은 비우는 턴에 맞춘다.
- usage 가 없는 응답도 실린 범위는 원장에 적는다. 토큰 크기는 모르며, 다음 usage 표본이 그 사이 atom 전부를 한 묶음으로 잰다. usage 를 한 번도 주지 않는 레인은 토큰 측정으로 상한을 판정할 수 없고, 화면은 추정 대신 그 사실을 보인다.
- 원장은 프로세스 메모리다. 재기동 뒤 첫 응답부터 다시 쌓인다. 첫 응답 전에는 아무것도 비우지 않는다.
- 전역 원장은 응답에서 관측한 범위를 유지한다. 턴 경계의 상한 판정과 거절 뒤 이동은 후보 안의 작업값에만 적용하고, 응답이 오면 그 관측으로 전역 원장과 작업값을 함께 갱신한다. 후보가 실패하거나 취소돼도 거절된 범위를 다음 턴의 원장으로 남기지 않는다. 거절 앞머리는 §10.4처럼 같은 턴의 다음 후보에도 전달하지만, 런타임별 상한·저수위 이동은 그 후보 안에 둔다. 디스크 턴 레코드의 씨앗 계약은 이 원장의 수명과 별개다.
- 원장이 잰 묶음은 그 atom 들이 지금 이력에 그대로 있을 때만 맞다. 그래서 원장 요청은 앞과 끝(마지막 atom)을 여는 메시지의 digest 를 같이 적고, 조립 때 지금 이력에서 원장 앞 번호·원장 끝 번호 자리의 digest 를 대 본다. 둘 중 하나라도 다르거나 그 번호가 없으면(이력이 원장 끝보다 짧아짐) 조립 때 원장을 지운다. 지운 원장은 그 조립도, 이어지는 거절 재시도도 이끌지 않는다. 다음에 받아들여진 응답이 새 원장을 시작하고, 그 전에 온 공급자 거절은 §10.4 의 반 자르기가 씨앗으로 푼다. 줄어든 꼬리만 잘라 남은 묶음을 살리는 규칙은 두지 않는다. 앞과 끝 digest 가 같아도 purge 가 가운데를 지웠을 수 있고, 가운데를 증명할 값은 없다. 같은 수의 atom 이 다른 메시지로 바뀐 경우(저장 안 된 시도 뒤 다음 턴이 같은 번호에 새 입력을 덧붙임)도 끝 digest 가 가린다. 수만 보던 원장은 그 묶음을 잰 것으로 착각했다.

### 10.4 요청 구성 (HTTP 레인)

```
F   = 시스템 프롬프트 + 도구 스키마 (순서 고정, 해시로 변경 감지)
H   = 고정 머리 (세션 첫 묶음) + 이력 묶음 (오래된 것부터, 덧붙이기만)
T   = 꼬리: recall, 브리핑, 시각처럼 매 턴 바뀌는 것 (이력에 남기지 않음)
N   = 이번 턴 새 입력
요청 = F ++ H ++ T ++ N
```

- 자르지 않는다. 60 atom 양자화, target 자르기, floor 요청, 가장 새 atom 규칙은 없어진다.
- 실린 범위는 (Keeper, 런타임) 쌍의 원장 앞에서 시작한다. 원장이 없으면(부팅 뒤 첫 턴, 이 런타임의 첫 턴) 같은 이력(trace) 위에서 마지막으로 완료된 턴 레코드가 실은 atom 범위에서 시작한다. 어느 런타임이 쟀든 같은 위치다: atom 은 체크포인트 이력의 위치이고, 요청은 그 어휘로 먼저 조립한 뒤 wire 프로젝션(추론 블록 삭제, 빈 assistant 메시지 삭제)을 실린 범위에만 건다. 프로젝션을 먼저 걸면 atom 수가 모델 방언의 것이 되어 다른 런타임이 잰 앞이 "이력이 줄었다"로 읽힌다. 공식 클라이언트 레코드도 같은 이력을 센다. masc 가 재는 자름은 Agent Core 경로가 자르는 그 목록(`agent.state.messages`) 위에서 돌고, 클라이언트가 그 목록을 받아 무엇을 하든 레코드에는 들어가지 않는다(`keeper_claude_code_runtime.ml:85-99`, `keeper_codex_runtime.ml:116-127`, `keeper_antigravity_runtime.ml:158-181`, `pipeline_stage_prepare.ml:148-154`). 자기 목록을 센 것이라 읽지 않던 규칙은 2026-09-18 에 그 대가가 드러났다. claude_code 로 20턴을 돈 code-reviewer 가 Agent Core 로 돌아온 첫 턴(4059)에 씨앗을 하나도 못 찾아 이력 전체 13MB 를 후보마다 보냈다. 카탈로그에 없는 런타임의 레코드만 읽지 않는다 — 무엇을 센 건지 말할 근거가 없다. 둘 다 없으면 마지막으로 끝난 턴의 경계부터 싣는다(§13.4). 조립 때 요청을 어떤 크기에도 대 보지 않는다. 몸체 크기는 서버가 알아서 판정할 일이고, 그 판정(413)은 넘침과 같은 걸음으로 답한다.
- 원장은 (Keeper, 런타임, 세션) 마다 하나이고 씨앗은 (Keeper, 세션) 에 하나다. 세션은 atom 위치가 가리키는 이력(trace)이고, recovery worker 의 턴은 자기 세션이라 Keeper 본 세션의 앞을 읽지도 쓰지도 않는다. 가장 새 atom 하나로 접혀 영구히 좁아지는 길은 없다.
- 위치는 번호와 그 자리 atom 을 여는 메시지(user 또는 assistant 메시지 하나)의 digest 로 같이 다닌다. 여는 메시지만 쓰는 이유는, 뒤따르는 도구 결과가 나중에 같은 atom 에 붙어도 위치가 바뀌지 않아야 해서다. 씨앗과 원장의 앞은 지금 이력의 같은 번호 자리를 여는 메시지의 digest 가 같을 때만 쓴다. 다르거나 그 번호가 없으면 버리고 씨앗 없는 첫 요청처럼 시작한다. atom 수는 판정에 쓰지 않는다. 이력이 줄어드는 길이 둘이라서다(§10.12). 저장되지 않은 시도의 꼬리가 빠지면 이력은 줄지만 앞은 같은 메시지를 가리키고, 체크포인트 purge 는 앞보다 뒤에서 여러 atom 을 지우면 수가 줄어도 앞이 같을 수 있고 앞보다 앞에서 지우면 같은 번호가 다른 메시지를 가리킨다. 남는 틈은 purge 가 중복을 지워 같은 번호에 바이트가 같은 메시지가 오는 경우 하나다. 그때 이어 보내는 범위의 첫 메시지 내용은 같다.
- 거절이 옮긴 앞머리는 그 시도의 것이 아니라 그 턴의 것이다. 레인이 다음 후보로 걸어가도 같은 이력이므로 그 위치가 그대로 선다. 후보 안에 두면 걸음마다 사라지고, 다음 후보가 이력 전체를 다시 싣는다(2026-09-18: pr-updater 가 한 후보에서 16MB→3.7MB 로 줄인 뒤 다음 후보에 16MB 를 보냈다).
- 반 자르기와 묶음 비우기는 모두 턴의 앞머리를 남긴다. 다음 후보가 이미 원장을 갖고 있어도 그 앞이 더 오래되면 거절이 옮긴 위치를 쓴다. 원장이 지금 요청보다 오래된 범위를 셌으면, 그 원장의 묶음을 빼는 일이 실제 요청을 줄이는지 먼저 본다. 줄이지 못하면 지금 요청의 범위를 반으로 좁힌다.
- 끝나지 못한 턴의 레코드도 사실을 하나 남긴다. 그 턴이 어디까지 범위를 좁혔는지다. 거절이 옮긴 앞머리는 그 턴의 모든 후보가 함께 쓰므로(위 줄), 끝나지 못한 레코드의 앞머리는 그 턴이 실제로 시도한 가장 좁은 범위다. 그래서 다음 조립은 그 자리에서 그대로 시작한다. 여기서 앞머리를 한 번 더 옮기지 않는다. 턴이 끝나지 못한 이유는 크기와 무관할 수 있고(쿼터 답, 끊긴 연결) 그런 이유는 반복되므로, 이력이 제자리인 동안 범위만 0 을 향해 줄어든다(2026-09-18: polisher 가 쿼터 소진 네 턴 만에 7,537 atom 중 1,885 → 236 으로 줄었다. 이력은 7,537 에서 하나도 늘지 않았다). 다음 거절은 턴 안 사다리가 답한다. 완료된 레코드가 더 새것이면 그것이 씨앗이다. 받아들여진 범위가 더 새로운 증거다. 이 규칙이 없으면 씨앗을 잃은 Keeper 는 매 턴 이력 전체를 다시 보낸다(2026-09-18, Keeper 다섯).
- 씨앗을 읽다가 해석하지 못한 턴 레코드는 없는 셈 치지 않는다. 몇 개였고 첫 사유가 무엇인지 그 턴의 관측에 남긴다. 씨앗을 못 찾은 이유가 "레코드 없음" 인지 "읽지 못함" 인지는 운영자가 가려야 할 일이다.
- usage 가 세어지기 전의 거절(공급자 넘침, 바이트 거절, 그리고 이유를 우리 타입으로 못 읽는 거절)은 뺄 묶음이 없다. 이유가 없는 거절도 공급자가 이 요청을 읽고 물렸다는 사실은 같아서, 같은 바이트를 다시 보내면 같은 답이 온다. 그래서 줄이는 것 말고 할 수 있는 일이 없다(2026-09-18: ollama_cloud 가 문장만 담긴 400 으로 물렸고, 그 문장을 읽는 것은 문자열 분류라 하지 않는다). 그때는 범위를 가장 새 atom 쪽으로 절반씩 좁혀 같은 후보에 다시 보내고, atom 하나가 남으면 거절을 그대로 돌려준다. 묶음이 하나뿐인 원장도 같다. 비우기든 반 자르기든 앞머리를 지금보다 뒤로 옮기지 못했으면 다시 보내지 않고 거절을 돌려준다. 같은 요청을 다시 보내면 같은 거절이 끝없이 돌아온다. 크기 추정이 아니라 공급자 판정에 대고 위치를 이분하는 것이며, 첫 usage 가 세어진 뒤로는 묶음 걸음만 쓴다.
- 매 턴 바뀌는 문장은 F 에 두지 않고 T 로 옮긴다. 세 공급자 문서(§10.7)가 같은 배치를 권한다.
- #28845 의 현재 턴 강등은 거절 뒤로 옮긴다. 뺄 묶음도 좁힐 범위도 없으면(가장 새 atom 하나가 거절됐으면) 그 턴의 도구 결과에 강등할 것이 있을 때만 마커로 바꿔 한 번 다시 보낸다. 조립 때 크기를 보고 미리 하지 않는다.

### 10.5 비우기 사다리

트리거는 둘이다.

- 원장: 시도의 첫 요청을 조립하기 직전에 원장의 전체가 상한을 넘었으면, 저수위까지 비우고 조립한다. 판정은 턴 경계에서만 한다. 응답 직후에 앞을 옮기면 같은 턴의 다음 요청부터 접두사가 달라져 캐시가 깨진다. 턴 도중에 전체가 상한을 넘으면 다음 턴까지 기다린다. 거절된 요청은 없다.
- 턴 도중의 공급자 거절은 같은 실행에서 비우고 다시 보내지 않는다. 도구 경계의 checkpoint 가 에이전트 상태를 바꾼 뒤라 같은 실행 재시도가 막힌다(`same_run_retry_allowed`). 그 턴은 실패하고, 다음 턴 경계에서 원장 판정이 비운다. 그래서 상한과 `max-context` 사이의 여유가 한 턴 안에서 늘어나는 양보다 커야 한다. 2026-09-15~17 keeper 턴에 쓰인 바인딩의 턴 안 증가량(둘째 요청부터 마지막까지)은 p99 56K~77K, 최대 600,612(deepseek-v4.1-flash 1 회)였고 여유는 모두 900K 이상이었다. 여유가 31,072 인 local-granite-42-8b 와 162,144 인 kimi-k2-7-code 는 그동안 요청이 셋 이상인 턴에 쓰이지 않았다.
- 공급자: 넘쳤다고 하면 즉시 저수위까지 비우고 다시 보낸다. 그래도 넘치면 묶음 하나씩 더 뺀다. 뺄 묶음이 없으면 새 입력이 혼자 넘친 것이다. #28845 강등이 있으면 그것, 없으면 typed 거절이다.

자격과 순서.

1. 비울 수 있는 묶음은 Librarian 이 읽고 기억에 쓴 묶음뿐이다(§5 I, §6.4). 안 읽은 묶음은 상한에 닿아도 못 뺀다.
2. 고정 머리(세션 첫 묶음: 목표와 지시)는 빼지 않는다. 자리로 정해지는 것만 머리다. "중요해 보이는 것" 을 고르는 규칙은 없다.
3. 1단계, 결과 비움: 자격 있는 묶음 안의 도구 결과 본문을 고정된 꼴의 포인터 한 줄로 바꾼다(묶음 id, 결과 id, 도구로 열 수 있음). 호출, assistant 본문, thinking 은 남긴다. 도구 메시지는 남는다. 호출 id 마다 결과 메시지가 있어야 하고, DeepSeek 은 reasoning 을 되돌려 보내야 한다. 운영자가 선언한 도구 이름 목록은 비우지 않는다.
4. 2단계, 묶음 빼기: 그래도 저수위 위면 머리 바로 뒤의 연속 구간을 통째로 뺀다. 빈 자리에 고정된 꼴의 표시 한 줄을 둔다(빠진 묶음 범위, 기억 항목, 도구로 열 수 있음). 5단계 전까지는 잘린 자리의 생략 preamble 이 그 자리를 알리고, 범위와 기억 항목을 담은 표시는 5단계와 같이 들어온다.
5. 1·2단계와 F 변경은 같은 턴에 한 번에 한다. 접두사 캐시는 첫 번째로 바뀐 자리 앞까지만 살고, 다시 계산되는 양은 남긴 꼬리 크기다. 저수위의 수는 "비울 때 한 번 다시 계산할 토큰" 이라는 뜻을 가진다.
6. 뺀 크기는 전부 원장이 아는 정확한 수다. 반감은 없다.

thinking 은 공급자 규칙에 따른다(§10.7). DeepSeek 은 `tools` 를 쓰면 이전 턴 reasoning 까지 되돌려 보내야 하므로 2단계로만 준다. Anthropic 레인은 `clear_thinking` 으로 최근 N 턴만 남기는 선언을 둘 수 있다. 별도 이행이다.

역압. Librarian 이 못 따라오면 자격 있는 묶음이 없고 전체는 상한에 닿는다. 그때는 안 읽은 묶음을 손실로 기록하고 빼거나, 턴을 멈추고 기다린다. 어느 쪽인지는 선언이고, 어느 쪽이든 원장에 남는다. 조건은 Librarian 처리량이 이력 증가율보다 크다는 것이며 둘 다 매 턴 잰다.

### 10.6 Librarian 과 recall

- Librarian 은 비울 때 부르는 게 아니라 묶음이 덧붙을 때마다 선 밖에서 읽는다. 비움은 원장 작업일 뿐이다.
- 기록 형식은 §6.4 의 결론이다. 사실은 원문을 대신하지 않고 가리킨다(묶음 id, 결과 id, 유효 구간, 출처 턴).
- recall 은 매 턴 꼬리 T 에 새로 고른다. 이력에 남기지 않는다. 다음 턴의 접두사는 지난 턴의 T 자리에서 갈라지지만 그 앞은 그대로 읽힌다.
- 원문 열기는 Keeper 가 당긴다. 사실이 가리키는 묶음이나 결과를 도구로 열면 그 원문은 이번 턴의 도구 결과로 덧붙고 다음 묶음에 세어진다. 비용은 그 턴에 쓰고, 맥락은 Keeper 가 필요하다고 한 만큼 돌아온다.
- 전송 이력 가운데를 고치는 일은 없다. 컴팩션은 없다(§7.7).

아래 항목은 모두 같은 조치다 — **두 번째 벌을 지운다.**

`system_log_2026-09-18.jsonl` 과 `provider-inputs/2026-09/18.jsonl` 기준.

| `halved_after_refusal` | 거절 연쇄 56개에서 재조립 101회, 연쇄당 1.80회 (`#1` 56 · `#2` 44 · `#3` 1) |

중앙값 131 B 와 최대 45 MB 는 같은 분포가 아니다. 정상 턴은 사실상 아무것도 싣지 않고, 씨앗을 잃은 턴이 이력 전체를 싣는다.

### 13.2 창 크기를 숫자로 정하지 않는다

`context-high-water-tokens` / `context-low-water-tokens` 를 없앤다. 라이브는 11개 바인딩 중 9개가 `100000` / `70000` 을 적고 있었고, 그 값을 고른 근거는 어디에도 없다.

같은 이유로 `max-prompt-bytes` 를 없앤다. 이 값이 없는 두 바인딩(`claude_code.claude-sonnet-5`, `antigravity_subscription.gemini-3-8-flash-high`)에만 eviction mark 가 없었다 — 밀어내기가 없는 자리에 바이트 캡을 대신 박아 둔 것이고, 대체재로 동작하지 않았다. `critic` 은 `undroppable_bytes=169,918 > capacity_bytes=131,072` 로 2시간 동안 30턴이 실패했다(04:12:53Z~06:11:44Z, `system_log_2026-09-18.jsonl` 의 `turn terminal` 줄 30개. 턴마다 로그가 네 줄씩 남아 줄 수로는 120 이다). 이력을 0으로 잘라도 들어갈 수 없는 상태였다.

두 값이 사라지면 그 값을 나눠 쓰던 중간값도 사라진다. `runtime_model_input_tail_window` 한 모듈에 `*_bytes` 이름이 20종 있고 전부 `int` 다. `capacity - reserved - undroppable` 을 `capacity - undroppable` 로 잘못 써도 컴파일러가 잡지 않는다.

### 13.3 거절에 범위를 반씩 좁혀 다시 보내지 않는다

§10 은 "이유를 우리 타입으로 못 읽는 거절"을 근거로 범위를 절반씩 좁히기로 했다. 이 추론에 비약이 있다. **거절 사유를 못 읽는 것과 크기를 모르는 것은 다르다.**

```ocaml
let halve ~first_atom ~atom_count =
  let carried = atom_count - first_atom in
  if carried <= 1 then None else Some (first_atom + (carried / 2))
```

인자에 바이트가 없다. 거절은 바이트 때문인데 자르는 것은 atom 개수다. 큰 도구 결과 하나와 작은 atom 8,000개가 있으면 반으로 접어도 범인이 남고 무관한 대화만 버려진다.

호출자는 `measure_message_bytes` 를 이미 받고 있고, 직전에 성공한 요청의 크기도 안다. 그리고 §4 의 3번은 HTTP 층의 "C' 절반"을 이미 **부당**으로 판정했다 — §10 은 같은 모양을 atom 축에 복제했다.

탐색 비용도 비대칭이다. 한 번 틀릴 때마다 22.7 MB 를 올려 보내고 거절을 받는다.

`halve`, `Halved_after_refusal`, `Refused_range`, `last_resort` 를 없앤다. 거절은 오류로 올린다.

### 13.4 앞머리가 없으면 이번 턴만 싣는다

흡수한 지점은 둘 중 하나다: 맞는 스냅숏(하던 일과 위치, `Librarian_snapshot`), 그것이 없으면 Librarian 의 읽은 위치(`librarian-progress.json`, 위치만, `Librarian_progress`; §13.6). 스냅숏이 이력과 맞지 않아도 읽은 위치는 맞을 수 있어서 두 번째 갈래가 있다(2026-09-22 goo-yang-bong: 스냅숏은 맞지 않고 위치는 맞았다. 16.4 MB → 169 KB). 스냅숏 파일을 못 읽거나, 턴 끝 기록을 못 읽어 확인할 수 없거나, 덮은 구간의 바이트가 바뀐 스냅숏(`Prefix_changed`)도 맞지 않는 스냅숏으로 본다(#37762). 턴은 스냅숏 없이도 나갈 수 있고, 턴을 거절하면 Librarian 회차도 돌지 않는다. `Prefix_changed` 인 스냅숏은 Librarian 이 다시 쓴다. 파일이나 턴 끝 기록을 못 읽는 경우는 Librarian 도 같은 파일에서 멈추므로, 운영자가 그 파일을 고칠 때까지 남는다. 경고가 그 파일을 말한다. 턴 끝 기록을 못 읽으면 턴 경계도 0 이 되어, 위치가 없는 Keeper 는 이력 전체를 싣는다. 스냅숏이 없는 Keeper 가 그 경우에 원래 하던 것과 같다(`turn_start`). 발송 도중에 거절하는 경우는 둘이다. 덮은 구간이 바뀌었을 때와 읽은 위치의 자리가 바뀌었을 때다(`validate_continuity`). 둘 다 이 이력의 자리가 아니고 씨앗도 없으면 요청은 이 이력에서 마지막으로 끝난 턴의 경계(`Keeper_carried_front.Turn_start`)부터 싣는다. 이번 턴의 원문만 나가고, 그 앞은 Librarian 의 다음 회차가 스냅숏으로 채운다. 끝난 턴이 없는 이력은 그 경계가 0 이라 갖고 있는 전부를 싣는데, 그것은 새 Keeper 의 짧은 이력이다. 공식 클라이언트 레인도 씨앗이 없으면 같은 자리에서 시작한다(`Keeper_official_client_host.carried_start_range` 의 `turn_start`).

"시작할 자리가 없다"를 "전부 보낸다"로 접지 않는다. `software-development.md` §AI 코드 생성 안티패턴 2 가 금지하는 형태다 — unknown 을 편리한 기본값으로 압축하지 않는다. 경계는 고른 숫자가 아니라 일어난 일(턴 끝 기록의 위치)이고, 지금 이력과 digest 로 맞춰 본 값만 쓴다(`Keeper_turn_driver_try_provider.turn_start`). 경계 저장소를 못 읽었거나 어떤 경계도 지금 이력과 맞지 않으면 그 값은 `Turn_boundary_unknown` 이다. 그때 요청은 가장 새 atom 하나만 싣고 `origin` 이 `Turn_start_unknown` 으로 그 이유를 말한다. 모르는 시작을 0 으로 접어 이력 전체를 보내지 않는다.

틀리는 비용도 한쪽으로만 크다. 작게 틀리면 맥락이 조금 모자라고 다음 턴에 보태면 된다. 크게 틀리면 22.7 MB 를 올리고 거절당하고 턴이 죽고 다음 턴에 같은 일이 반복된다(2026-09-22 goo-yang-bong: 스냅숏이 이력과 맞지 않아 16 MB 를 보냈고 44 사이클 연속 실패).

`origin` 은 앞머리가 *어디서 왔는지*만 말한다: `Carried of source`, `Librarian_snapshot`, `Librarian_progress`, `Turn_start`, `Turn_start_unknown`.

### 13.6 남는 설계

§1 의 1·2 를 이렇게 짓는다.

- 보내는 범위는 librarian 이 마지막으로 흡수한 지점부터 지금까지다. 그 지점은 Librarian 이 빠짐없이 읽은 턴만 지나간다(Librarian RFC §4.5 I1·I3).
- 그 앞은 다시 보내지 않는다. 그 앞이 기억에 남는 것은 Librarian RFC §7 (라)가 끝난 뒤다. 지금 Librarian 은 턴 진행과 현재 상태를 facts 에 적지 않고(`config/prompts/librarian.md` §남길 지식과 증거), 도구 결과는 `[tool result omitted: …]` 한 줄로만 읽는다(`keeper_librarian.ml` `text_of_content`). §1 의 6 이 그 조건을 기다리는 이유다.
- 도구 결과는 조립 시점에 늘 마커로 나간다 (이력 바이트의 71%). 끝난 턴의 결과는 이미 그렇게 나간다(RFC-0363, `keeper.model_input_demotion_enabled` 기본 `true`). 지금 턴의 결과는 거절 경로의 `last_resort` 에서만 마커가 된다. #28845 의 강등을 조립 시점에서 거절 경로로 옮긴 것(§11 1d)을 되돌려, 지금 턴의 결과도 조립 때 마커로 나가게 한다.
- 거절은 오류로 올린다. 범위를 좁혀 다시 보내지 않는다.

경계가 고른 숫자가 아니라 **일어난 일**이라는 점이 핵심이다. `context-high-water-tokens = 100000` 은 왜 10만인지 아무도 답하지 못한다. "librarian 이 흡수한 지점"은 고를 것이 없다. 그 지점이 읽지 않은 턴을 넘어가지 않는 한 틀리지도 않는다.

지우는 것은 *전송*이지 *기록*이 아니다. durable 이력은 evidence 로 남긴다. 달라지는 것은 이미 기억으로 옮겨진 것을 매 턴 다시 실어 보내지 않는다는 것뿐이다.

### 13.7 선행 조건

13.2·13.3 을 걷어내기 시작하는 때는 Librarian 생명주기 RFC(`RFC-librarian-lifecycle.md`) §7 (라)가 정한다. 그 조건과 진행은 그 RFC 에만 적는다. 순서를 바꾸면 대체할 것이 없는 상태에서 45 MB 가 아무 제지 없이 나간다.

조건이 하나 더 있다. 밀림 표시(같은 RFC 의 I4)가 창이 그 위치에 기대기 전에 화면에 떠 있어야 한다. Librarian 이 서면 이력은 자라고 요청은 결국 provider 한도에서 거절되는데(§13.9), 표시가 없으면 화면에는 실패한 턴만 보이고 원인은 보이지 않는다.

### 13.8 overlay 를 비우고 `max-context` 결정을 한 곳에 둔다

2026-09-18 당시 `agent-core-models-overlay.toml` 은 모델 사실, provider 선언, 배포 레인 배선을 `runtime.toml`·카탈로그와 중복해서 들고 있었다. #37016 이 `[[models]]` 를 카탈로그로, `[[providers]]`·`[[targets]]` 를 `runtime.toml` 로 옮기고 overlay 파일을 지웠다. 행 수와 섹션 수는 움직이는 중간 상태였으므로 이 RFC 가 다시 고정하지 않는다.

남은 질문은 바인딩의 `max-context` 와 카탈로그 상한이 다를 때 누가 이기는가다. 이 RFC 는 그 규칙을 정하지 않는다. `RFC-runtime-two-layers` 규칙 4가 한 곳에서 정한다.

- 카탈로그는 모델의 창 상한을 소유한다.
- 배포 바인딩의 `max-context` 는 더 좁은 창을 선택할 수 있다.
- 바인딩이 카탈로그보다 큰 값을 적으면 조용히 clamp 하거나 선언을 이기게 하지 않고 로드에서 거절한다.

따라서 이 절의 옛 clamp 제거 순서는 폐기한다. `runtime.ml` 의 `Override_clamped_by_capability` 를 어떻게 걷어낼지도 `RFC-runtime-two-layers` 의 구현이 소유한다. 이 RFC 의 구현은 그 줄을 반대 방향으로 바꾸지 않는다.

### 13.9 §1 이 닫지 않는 것

- 이력을 빼고 남는 부분(`pinned` 메시지: 매 턴 새로 붙는 system·facts·브리핑 블록)이 혼자 provider 한도를 넘는 경우. 13.2 가 바이트 창을 없애면 이것을 알려 주는 것은 provider 의 typed 거절뿐이다. 턴은 그 오류로 끝나고(13.6), 다음 사이클도 같은 요청으로 같은 거절을 받는다. §1 에는 그 반복을 멈추는 장치가 없다. 줄일 것은 이력이 아니라 그 부분이고, facts 는 Librarian 의 `absorbs`·`dropped` 가 줄인다(Librarian RFC §6).
  - `critic` 의 30턴(13.2)은 이 경우가 아니었다. 거절한 쪽은 provider 가 아니라 `antigravity_subscription.gemini-3-8-flash-high` 레인의 masc 바이트 창(`max-prompt-bytes` 131,072)이었고, 그 모델의 `max-context` 는 1,048,576 토큰이다(`<base-path>/.masc/config/runtime.toml` 의 `[models.gemini-3-8-flash-high]`). 그 레인은 지금 이력을 자르지 않고 넘긴다(§4 의 5번).
- Librarian 이 서 있을 때. 창이 보는 위치가 움직이지 않는 동안 이력은 자라고, 좁혀 다시 보내는 길은 13.3 이 지웠다. 그래서 요청은 끝내 provider 한도에서 거절되고 턴마다 오류로 끝난다. 시간 상한은 두지 않는다. 실패한 Librarian 은 타이머 재시도 없이 다음 신호를 기다리고, 원인별로 푸는 방법은 Librarian RFC §4.3·§4.10 이 소유한다. 이 fail-closed 대가를 바꾸는 결정도 그 RFC 에만 적는다. 밀림 표시를 먼저 띄우는 조건은 §1 의 6 과 §13.7 에 있다.
