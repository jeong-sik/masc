# RFC: 보이는 창에 닿는 보유 로그만 블록으로 투영한다 (tui-lazy-block-projection)

## 1. 요약

채팅 화면은 보유 로그마다 블록(`log_block`)을 만들고, 그 뒤에 화면에 보이는 행만 잘라 내요.
처음 투영되는 로그 하나가 중앙값 약 7ms를 쓰는데, 스크롤로 이전 기록을 불러오면 화면 밖의 로그가 한꺼번에 처음 투영돼요.
이 RFC는 블록의 `lb_entries`를 필요할 때만 만드는 구조로 바꾸자는 제안이에요.
근거는 §2의 측정이고, 효과는 아직 재지 못했어요(§6).

## 2. 문제와 측정

### 2.1 어디서 시간이 나나

실제 TUI(라이브 서버 `~/me`, keeper `e-masc-the-leader`, 60×200)에서 PageUp 80회, PageDown 80회, PageUp 80회를
보내고 `MASC_TUI_FRAME_TIMING`의 단계 계측으로 쟀어요(2026-10-10).

| 단계 | p50 | p95 | max |
|---|---|---|---|
| `chat.blocks` (#42193까지의 스택) | 0.14~0.36ms | 27.4~30.2ms | 34~68ms |
| `chat.blocks` (#42197까지의 스택) | 0.14~0.20ms | 12.3~14.3ms | 20~25ms |
| `chat.layout_entries` | 0.08ms | 0.7~4.1ms | 12~23ms |
| `chat.merge`, `chat.window`, `chat.rows` | 0.06~0.5ms | 0.6~1.8ms | 12ms 이하 |

`chat.blocks`의 중앙값은 0.14ms예요. 메모가 맞으면 거의 공짜이고, 처음 투영되는 프레임에서만 시간이 나와요.
콜드 로그 하나의 `log_projection`은 중앙값 7ms(최대 12~47ms)였고, 그중 `Keeper_chat_transcript.drawn`이 4.5~4.9ms였어요.

### 2.2 왜 화면 밖 로그가 투영되나

`render_keeper_message`는 이 순서로 일해요.

1. 보유 로그 전부의 블록을 만든다 (`settled_blocks`, `observed_blocks`, `other_live_blocks`).
2. 블록 항목을 커밋된 행 사이에 끼워 넣어 `layout_entries`를 만든다 (`merge_blocks`).
3. `Message_layout.clamped_scrolled_rows`가 가장 새 항목부터 `requested + height`행을 채울 때까지만 걷는다.

3번은 이미 필요한 만큼만 걸어요(`count_rows_until`). 1번과 2번은 걷기 전에 전부 만들어요.
이전 기록 페이지가 들어오면 그 페이지의 로그가 화면 위쪽 훨씬 밖에 있어도 1번에서 투영돼요.

### 2.3 이미 해 본 것과 결과

| 시도 | 결과 |
|---|---|
| 서버 `limit`으로 페이지를 작게 (#42202) | 스텁 A/B 3회에서 첫 구간 p95/p99가 달라지지 않았어요 |
| 파싱·디코드를 워커 도메인으로 | 번갈아 3회 비교에서 일관된 이득이 없었어요 |
| 파싱 뒤 `Eio.Fiber.yield` | 변화 없음 |
| 블록 메모 검증을 "읽는 세 값"으로 | p95 변화 없음 |
| 유니코드 속성표 일반화 | 변화 없음 |

효과가 있었던 것은 같은 계산을 여러 번 하던 곳을 없앤 변경들이에요(#42184~#42199).
남은 비용은 "처음 한 번 하는 계산"이라서 같은 계산을 줄여서는 더 내려가지 않아요.
처음 하는 계산 자체를 화면에 닿지 않는 로그에서 건너뛰는 방법이 이 RFC예요.

## 3. 제약

블록의 항목(`lb_entries`)을 건너뛰려면 다음이 항목을 만들지 않고도 답해져야 해요.

| 필요한 것 | 지금 어디서 | 항목 없이 답할 수 있나 |
|---|---|---|
| 블록이 비었는지 | `block.lb_entries <> []` 세 곳 (`render_chat.ml`) | 아니요. `drawn`의 어느 항목이 행이 되는지 판정이 필요해요 |
| 삽입 슬롯과 시각 | `chat_log_timeline_context` (#42189) | 예. 이미 항목과 무관해요 |
| 턴 레일의 모서리 | `merge_blocks`의 `request_of`와 `close_run` | 부분적으로. 요청 ID는 블록이 알지만 `close_run`은 항목 수와 위치를 써요 |
| 이웃 항목(`previous`) | `entry_rows_at`이 다음 오래된 항목을 읽어요 | 걷기가 닿는 가장 오래된 항목의 이웃 하나만 필요해요 |
| 마크다운 성장 캐시 키 | `Markdown_growing {keeper_name; request_id; entry_index}` | 예. 키에 항목 수가 필요 없어요 |
| 스크롤 고정(pin) | 고정 이후 도착한 행 수 `rows_since_pin` | 고정 아래의 항목만 세면 돼요 |

가장 어려운 것은 첫 번째(빈 블록 판정)와 세 번째(레일 모서리)예요.

## 4. 제안

세 단계로 나누고, 단계마다 기존 구현과 같은 결과임을 테스트로 묶어요.

### 4.1 단계 1 — 항목 수를 투영 없이 알려 준다

`Keeper_chat_transcript`가 `drawn`의 어느 항목이 행을 만드는지(`entry_count`와 `is_empty`)를 항목 본문을 만들지 않고 답해요.
`log_projection`의 `List.filter_map`이 `None`을 돌려주는 조건(`Drawn_error` 중 상태 줄이 이미 있는 경우 등)을 한곳으로 모아서
투영과 개수 계산이 같은 조건을 써요. 이렇게 하면 두 곳이 어긋날 수 없어요.

검증: 생성한 이벤트열(도구 호출, 스킬, 오류, 취소, 재시도)에서 `entry_count = List.length (eager lb_entries)`.

### 4.2 단계 2 — 블록 항목을 지연 평가로

`log_block.lb_entries`를 `log_entry list Lazy.t`로 바꾸고 `lb_entry_count`를 더해요.
`merge_blocks`와 `close_run`은 개수로 레일 모서리를 정하고, 항목은 걷기가 닿을 때 만들어요.

검증: 기존 `held turn blocks merge among committed rows by clock`과 배치 테스트가 그대로 통과하고,
무작위 시나리오에서 지연 평가 결과가 즉시 평가 결과와 같음을 비교해요.

### 4.3 단계 3 — 걷기가 닿은 블록만 평가

`clamped_scrolled_rows`는 이미 항목을 새 쪽부터 걸어요. 입력을 `Seq` 또는 "항목 수와 항목 thunk의 배열"로 받게 해서
닿지 않은 블록의 `Lazy.t`는 평가되지 않게 해요.

## 5. 하지 않는 것

- 서버 응답 형태는 바꾸지 않아요. #42202의 스텁 측정에서 효과가 없었어요.
- 블록 메모(`settled_block_memo`)의 키와 검증은 그대로 둬요.
- 별도 도메인이나 스레드는 쓰지 않아요.

## 6. 효과와 성공 기준

효과는 측정하지 못했어요. 이 제안이 줄이는 것은 "화면에 닿지 않는 로그의 첫 투영"이고,
그 몫이 `chat.blocks` p95 12~14ms 중 얼마인지는 프로토타입으로 재야 해요.

성공 기준(프로토타입 단계에서 확인):

1. 실제 TUI에서 `chat.blocks` p95가 현재의 12~14ms에서 눈에 띄게 내려가야 해요(세 번 이상 번갈아 잰 값, 같은 부하).
2. 입력→첫 출력 p99(첫 PageUp 구간)가 현재의 25~50ms에서 내려가야 해요.
3. 모든 기존 TUI 테스트와 새 동치 테스트가 통과해야 해요.

기준 1이 맞지 않으면 이 RFC는 폐기해요. 화면에 닿는 블록이 많아서 건너뛸 몫이 작다는 뜻이에요.

## 7. 위험

| 위험 | 완화 |
|---|---|
| 빈 블록 판정과 투영의 조건이 어긋남 | 4.1에서 조건을 한 함수로 모아 두 곳이 같이 쓰게 해요 |
| 지연 평가가 변경 사이에 어긋난 값을 평가 | 블록은 로그 리비전으로 메모되고, `Lazy.t`는 같은 프레임 안에서만 쓰여요 |
| `previous` 이웃이 아직 평가되지 않음 | 걷기가 닿은 가장 오래된 항목의 이웃 한 블록만 추가로 평가해요 |
| 스크롤 고정이 건너뛴 블록의 행 수를 필요로 함 | 고정 아래만 세므로 닿지 않은 블록은 필요 없어요. 테스트로 확인해요 |

## 8. 결정이 필요한 것

- 위 성공 기준으로 프로토타입(단계 1과 2의 일부)을 해 볼지.
- 하지 않는다면 현재의 #42184~#42199로 이 작업을 마무리하고, 첫 이전 기록 구간의 p99 약 25~50ms를 목표 밖으로 기록할지.
