# 긴 답은 화면에 닿는 끝 블록부터 그리고, 전체는 CPU domain 에서 센다

- 코드 좌표는 `origin/main` `c41d6e3e7232` 에서 읽었다.
- 이 글은 열린 PR 두 개를 바탕으로 한다.
  - #54080: Markdown 렌더가 블록 표(블록마다 첫 byte·첫 줄)를 주고, frame 이 읽는 줄이 든 블록만 다시 그린다.
  - #54096: 바뀌지 않은 답은 frame 마다 다시 배치하지 않는다.
- 두 PR 이 병합되기 전에는 이 글의 구현 단계를 시작하지 않는다.

## 0. 결정

- 긴 답을 처음 그리는 frame 은 답 전체를 그리지 않는다.
  - 원문을 한 번 앞에서부터 훑어 블록 경계만 찾는다. 줄을 감싸거나 꾸미지 않는다.
  - 화면이 보여 줄 블록만 그린다. live edge 에서는 끝 블록들과 첫 블록들이다.
- 답 전체는 CPU domain 에서 그린다. 다 그리면 UI fiber 가 렌더 캐시에 넣고, 다음 frame 이 정확한 줄 수를 쓴다.
- 아직 세지 않은 줄 수는 타입으로 드러낸다. 추정값을 숫자로 그리지 않는다.
  - `Viewport_gap` 의 `hidden_rows : int` 를 `hidden_rows : hidden_rows` 로 바꾼다.
  - `type hidden_rows = Counted of int | Counting` 이다.
  - `Counting` 인 틈은 `⋯ PgUp` 처럼 개수 없이 그린다.
- 위로 스크롤하면 필요한 만큼 블록을 뒤에서부터 더 그린다. 전체 렌더가 끝나면 그것을 쓴다.

## 1. 지금

- `bin/masc_tui_render_chat.ml:244` `cached_chat_markdown_with_preview` 가 답 본문 전체를 `render_streaming` 으로 그린다. 결과는 렌더 캐시에 남는다.
- `bin/masc_tui_message_layout.ml:2234` `rows_of_entry` 가 그 줄 전부를 배치한다.
- `bin/masc_tui_message_layout.ml:2519` `newest_entry_window` 는 화면보다 긴 마지막 답에서 첫 줄들, 틈 한 줄, 마지막 줄들만 남긴다.
  - 틈은 `Viewport_gap { hidden_rows }` 이고, `viewport_gap_text`(2425행)가 숨은 줄 수를 정확히 적는다.
  - 그래서 지금은 화면에 수십 줄만 보이는데도 답 전체를 그리고 배치한다.
- 측정(macOS, 머신 부하 약 170~190, CPU 시간 `Sys.time`, 8회 최솟값, 2026-11-21):

  | 원문 1MB(문단·목록·코드 fence 반복) | 시간 |
  |---|---|
  | `render_streaming` 전체 | 75.7ms |
  | 마지막 8KB 만 `render_streaming` | 0.53ms |
  | 블록 경계만 찾는 앞 훑기(시제품, 줄마다 `String.sub` 3byte) | 3.4ms |

- #54080·#54096 을 합친 가지에서 1MB 답을 처음 여는 frame 은 101~118ms 다. 그중 Markdown 그리기와 배치가 각각 약 3분의 1 이다(sample 120 frame).

## 2. 기대는 성질

- **블록은 혼자 그려도 같다.** fence·표 밖의 줄은 줄마다 한 블록이다.
  한 블록의 byte 를 다음 블록 앞 줄바꿈만 빼고 혼자 그리면, 원문 전체에서 그 블록이 그린 줄과 같다.
  - #54080 의 시험 「each block renders alone」이 섞인 원문의 모든 prefix·모든 블록에서 이것을 대조한다.
- **블록 경계는 그리지 않고 찾을 수 있다.** 경계를 바꾸는 것은 fence 와 표뿐이다.
  - fence 는 여는 줄과 닫는 줄의 표시만 보면 된다.
  - 표는 `|` 가 있는 줄과 다음 구분 줄만 보면 된다.
  - 앞 훑기는 이 둘만 본다. 블록 표와 같은 답을 내는지 시험으로 대조한다(§5).
- **스크롤 위치는 원문 위치에 묶인다.** 붙잡은 위치는 `Durable_position` 이다.
  그래서 전체 렌더가 끝나 줄 수가 바뀌어도 화면이 보던 원문을 계속 본다.
- **live edge 에서 센 줄은 아래에서부터 정확하다.** 끝 블록부터 그린 줄은 답의 마지막 줄부터 센 번호가 전체 렌더와 같다.

## 3. 설계

### 3.1 처음 여는 frame

1. 앞 훑기로 블록 시작 byte 목록을 얻는다. 결과는 본문 identity 와 폭으로 기억한다.
2. 끝에서부터 블록을 그려 화면 높이만큼 줄을 채운다.
3. 첫 블록부터 `newest_entry_window` 가 보여 줄 만큼 그린다.
4. 그 사이는 `Viewport_gap { hidden_rows = Counting }` 한 줄이다.
5. CPU domain 에 전체 렌더를 맡긴다. 이미 같은 본문·폭·palette 세대의 일이 돌고 있으면 새로 맡기지 않는다.

### 3.2 전체 렌더가 끝났을 때

- UI fiber 가 결과를 렌더 캐시에 넣는다. CPU domain 은 캐시를 쓰지 않는다.
- 본문·폭·palette 세대가 그새 바뀌었으면 결과를 버린다. /find 가 세대 번호로 하는 것과 같다(#54043).
- 다음 frame 은 지금처럼 캐시의 줄과 블록 표를 쓴다. 틈은 `Counted n` 이 된다.

### 3.3 전체 렌더 전에 스크롤할 때

- 아래에서부터 센 스크롤 거리만큼 블록을 뒤에서부터 더 그린다. 그린 블록은 frame 사이에 기억한다.
- 붙잡은 위치로 돌아갈 때는 그 위치가 든 블록까지 뒤에서부터 그린다.
  비용은 그 위치가 끝에서 떨어진 거리에 비례한다.
- 맨 위로 가기(Home)처럼 전체 길이가 필요한 이동은 전체 렌더를 기다린다. 기다리는 동안 틈이 `Counting` 으로 보인다.

### 3.4 바뀌지 않는 것

- 렌더 캐시가 이미 전체를 가진 답은 지금과 같다.
- 짧은 답은 지금과 같다. 앞 훑기와 끝 블록 그리기는 본문이 정한 크기(예: 64KB)보다 클 때만 쓴다.
  크기는 측정으로 정하고 이름 있는 상수로 둔다.
- /find 는 지금처럼 전체 색인을 쓴다.

## 4. 단계

각 단계는 Draft PR 하나다. 앞 단계가 병합된 뒤에 다음을 연다.

1. `Viewport_gap` 의 `hidden_rows` 를 `Counted | Counting` 으로 바꾼다. 처음에는 `Counted` 만 만든다.
   → 확인: 기존 시험 통과, 틈 문구 시험에 `Counting` 경우 추가.
2. 블록 경계 앞 훑기를 `Masc_tui_markdown` 에 더한다. 그리는 경로는 아직 그대로다.
   → 확인: 무작위·섞인 원문의 모든 prefix 에서 앞 훑기 결과가 `render_streaming` 의 블록 표와 같다.
3. 긴 답의 처음 frame 이 끝·첫 블록만 그리고, CPU domain 이 전체를 그린다.
   → 확인: 1MB 여는 frame bench, 전체 렌더 전후 화면이 같은 원문 위치를 보는 시험, 세대가 바뀌면 결과를 버리는 시험.
4. 전체 렌더 전 스크롤이 뒤에서부터 블록을 더 그린다.
   → 확인: 스크롤 거리별 frame 비용 bench, 전체 렌더가 끝난 뒤와 같은 줄을 보이는지 대조.

## 5. 평가 기준(구현 전에 고정)

- **같은 화면.** 전체 렌더가 끝난 뒤의 화면과, 끝 블록만 그린 화면의 보이는 줄이 같다. 틈 줄만 `Counting` 과 `Counted n` 으로 다르다.
- **같은 경계.** 앞 훑기의 블록 시작 목록이 `render_streaming` 의 블록 표와 같다. 대조 corpus 는 #54080 의 시험 corpus 에 fence 안 빈 줄, 닫히지 않은 fence, 표 바로 뒤 문단을 더한 것이다.
- **비용.** 1MB 답을 처음 여는 frame 이 #54080·#54096 을 합친 가지의 101~118ms 에서 20ms 아래로 내려간다. 같은 bench(`bench_open`, CPU 시간, 번갈아 두 번)로 잰다.
- **회귀 없음.** 짧은 답 500개 frame, 스트리밍 frame, 첫 스크롤 frame 이 측정 범위 안에 머문다.

## 6. 남는 위험

- **두 번 그림.** 처음 frame 이 한 앞 훑기(1MB 약 3.4ms)와 끝 블록 그리기(약 0.5ms)를 CPU domain 이 전체 렌더 안에서 다시 한다. 대신 UI fiber 에서 전체 렌더 약 75ms 가 빠진다.
- **링크 카드.** 링크 미리보기가 붙는 답은 본문 뒤에 카드 줄이 붙는다. 첫 단계에서는 카드가 붙는 답을 지금처럼 전체로 그린다.
- **줄 수가 정해지는 frame.** 전체 렌더가 끝나면 스크롤바 길이와 틈 문구가 바뀐다. 보던 원문 위치는 그대로라 본문 줄은 움직이지 않는다.
- **열린 질문.** 크기 기준 64KB 는 측정 전 값이다. 30KB·100KB·300KB 답의 처음 frame 을 재고 정한다.
