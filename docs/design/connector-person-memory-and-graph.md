# 커넥터 인물 기억과 관계 그래프

이 설계는 Discord 멘션에서 시작한 대화를 다른 화면에서도 이어가고, 같은 사람과 다시 대화할 때 근거가 있는 기억을 사용할 수 있게 한다. 계정·대화·메시지의 정체성은 MASC Core가 관리한다. 인물에 관한 사실은 기존 Keeper Memory에 저장한다. Lane Add-on은 권한이 확인된 사실과 근거를 읽어 관계 그래프를 만든다.

## 현재 경로

[#54760](https://github.com/jeong-sik/masc/pull/54760)은 Discord 메시지를 받을 때 길드·채널·스레드 좌표와 당시 닉네임을 남기고, Librarian에 발화자 ID와 원본 대화·메시지 좌표를 전달한다. [Memory OS](../spec/12-memory-systems.md)의 현재 fact ID는 문장의 정확한 바이트에 대한 SHA-256이다. 모델이 같은 문장을 두 계정의 선호로 제안하면 저장소에서 그 두 사실을 기계적으로 구분할 필드가 필요하다.

[Lane Add-on 소스](../../lib/lane_addon/lane_addon_sources.mli)는 현재 명시적으로 연결된 파일, Fusion, 머신·브라우저 관측, 다른 Lane 출력을 읽는다. 계정별 Memory를 읽는 소스는 이 설계의 후속 단계에 추가한다.

## 식별자와 범위

| 값 | 구성과 의미 |
|---|---|
| 외부 계정 | 커넥터 종류, 커넥터가 보장하는 ID 발급 범위, 제공자가 확인한 사용자 ID. 사람이 이름을 바꿔도 계정은 같다. |
| 인물 | 운영자가 검증한 계정 연결이 있을 때 부여하는 지속적인 내부 ID. 계정을 추가하거나 연결을 철회해도 인물 ID는 유지한다. 연결 근거가 없으면 Graph에 개별 계정만 표시한다. |
| 대화 | 커넥터가 확인한 서버 또는 워크스페이스, 채널 또는 방, 실제 스레드 또는 토픽의 조합. 기존 `Surface_ref`와 커넥터의 원본 좌표를 사용한다. |
| 원본 메시지 | 대화 주소와 그 범위에서 유효한 메시지 ID. 한 메시지가 채팅 기록과 외부 관측에 함께 보이면 이 주소로 같은 근거임을 확인한다. |
| 기억 적용 범위 | 기억을 현재 대화에 다시 쓸 수 있는 범위. 최초에는 근거가 있는 원래 대화로 한정한다. 계정이 여러 방에 보이더라도 기억의 범위는 자동으로 커지지 않는다. |
| 관측 이름 | 원본 메시지를 받을 때 보인 닉네임 또는 표시 이름. 대화·관계의 설명에 사용한다. |

발급 범위와 기억 적용 범위는 서로 다르다. 같은 Discord 계정이 두 길드에 나타나도 계정 키는 같을 수 있다. 두 길드에서 얻은 선호·약속은 각 대화의 범위를 유지한다. MASC 워크스페이스 경계는 계정 ID의 일치 여부와 관계없이 저장과 조회에서 적용한다.

대화 키에는 주소를 결정하는 ID만 쓴다. 예를 들어 Discord 스레드의 현재 채널 ID와 스레드 ID가 같더라도 상위 채널은 별도 좌표로 남긴다. `Surface_ref`의 채널 표시 이름은 관측에 보존한다. 방 이름이 바뀔 때 새 대화 키를 발급할 필요는 없다. 같은 외부 메시지의 처음 수신과 재전달은 같은 원본 주소를 가져야 한다.

### 커넥터별 근거

| 커넥터 | 계정 식별에 필요한 증거 | 대화 주소에 필요한 증거 |
|---|---|---|
| Discord | Gateway가 보낸 기본 메시지·답글의 정규 사용자 snowflake. 시스템 이벤트·봇·웹훅 메시지, 다른 채널에서 온 교차 게시본, 전달된 메시지에는 사용자 계정 참조를 부여하지 않는다. 길드 닉네임은 메시지에 붙인다. | 실제 채널 ID, 확인된 길드·상위 채널·스레드 ID. DM에는 길드가 없다. |
| Slack | 발화자 사용자 ID와 해당 ID를 발급한 범위. Slack Connect에서는 수신 앱의 워크스페이스와 발화자의 소속을 각각 확인한다. 발급 범위가 확인되지 않으면 계정 결속을 생략한다. | 수신 워크스페이스, 채널 ID, 스레드 루트의 `thread_ts`. 스레드의 `ts` 값은 문자열로 보존한다. |
| Telegram | Bot API의 `from.id`와 발화자 종류. `sender_chat`으로 보낸 글은 채팅 주체의 발언으로 유지한다. | 원래 봇·채팅 ID, 토픽 또는 DM 토픽 ID, 채팅 안의 메시지 ID. 음수 채팅 ID와 큰 정수는 원형으로 보존한다. |
| iMessage | Messages 원본에서 확인된 서비스와 핸들. 연락처 이름은 표시 이름이고, 여러 핸들을 같은 인물로 연결하려면 별도의 확인이 필요하다. | 원래 Messages 방의 식별자와 로컬 원본 메시지 참조. 현재 전송 어댑터가 확보하지 못한 필드는 미확인으로 둔다. |

발급 범위와 대화 주소를 확보하지 못한 과거 기록은 기존 관측으로 읽을 수 있게 유지한다. Discord가 다른 채널로 전달한 교차 게시본을 원 발화로 사용하려면 후속 단계에서 원본 주소를 조회하고 확인한다. [Discord snowflake](https://docs.discord.com/developers/reference#snowflakes), [Discord Message의 발화자와 웹훅](https://docs.discord.com/developers/resources/message#message-object), [Discord 교차 게시본](https://docs.discord.com/developers/resources/message#example-crossposted-message), [Slack Message 이벤트](https://docs.slack.dev/reference/events/message/), [Telegram User·Message](https://core.telegram.org/bots/api#user)

### SHA-256의 역할

계정의 기준 값은 타입을 가진 원본 키다. 저장 엔진이나 Graph 교환 포맷에서 한 문자열이 필요하면, 도메인명과 버전을 붙인 고정된 순서의 필드를 충돌 없이 인코딩해 SHA-256을 계산한다. 필드 종류 태그와 UTF-8 바이트 길이를 함께 넣고, 일반 JSON 객체의 키 순서나 문자열 연결에 의존하지 않는다.

해시를 도입하는 단계에서 인코딩을 고정하고 경계값을 테스트한다. 예를 들어 `masc.connector.account.v1`과 `masc.memory.external_fact.v1`은 분리된 도메인으로 둔다. 두 도메인 모두 필드를 정해진 순서로 쓰고, 가변 길이 값 앞에 바이트 길이를 붙인다. 선택 필드는 부재와 존재를 각각 표현하며, Discord snowflake는 검증된 10진수 문자열로 쓴다. 사용자가 보는 표시 이름이나 해시 출력 자체에서 원본 좌표를 복원하지 않는다.

- 계정 노드 키의 입력은 계정 종류·발급 범위·사용자 ID다. 닉네임과 대화 좌표는 입력에서 제외한다.
- 인물 노드의 내부 ID는 승인된 첫 계정 연결에서 발급하고 이후 보존한다.
- 인물 기억의 중복 판정은 계정 키·적용 범위·정확한 claim 바이트를 사용한다. 근거 메시지는 같은 기억의 출처로 보존한다. 대화나 인물이 다른 경우 같은 문장에 서로 다른 기억 ID가 나온다.
- 기존 일반 기억은 현재의 claim 기반 ID를 그대로 사용한다. 해시는 출처 확인이나 계정 연결 승인의 증거가 되지 않는다.

## Core 저장과 조회

1. 인증된 커넥터 수신기가 원본 채널·메시지와 구조화된 발화자 필드를 해석한다. 확인된 계정 참조를 원본 관측 행에 보존한다. 메시지 본문, 닉네임, 임의의 Gate 주소는 계정 참조를 발급할 수 없다.
2. Librarian 질문에 원본 행의 계정 참조와 대화·메시지 좌표를 함께 넣는다. 여러 사람이 말한 단위에서 모델이 인물 기억을 제안하려면 원래 질문에 보낸 정확한 행을 선택한다. 호스트는 제안이 가리킨 단위·행을 해석하고 그 행에 있던 계정과 범위를 결속한다.
3. 후속 fact 형식은 기존 Keeper Memory fact 안에서 계정·적용 범위·원본 근거를 표현한다. Writer가 스냅샷 리비전과 원본 근거를 확인한 뒤 기존 단일 writer의 log → snapshot 순서로 커밋한다. `seen`, `revise`, `merge`는 같은 계정과 적용 범위를 유지한다. 혼합된 원본, 불명확한 행 또는 기존 문장만으로 특정 계정에 기억을 붙일 수 없다.
4. 회상은 실제 현재 대화에 결속된 계정과 허용 범위로 대상을 선택한 뒤 그 안에서 본문 검색을 사용한다. 같은 이름의 다른 계정, 다른 방에 묶인 일반화, 철회된 기억은 개인화 입력에 들어가지 않는다.
5. 검증된 계정 연결은 별도 명시적 작업으로 다룬다. 누가 어떤 근거로 연결을 승인했는지 기록한다. 연결을 철회하면 Graph는 연결을 제거하지만 계정별 원본 기록과 기억을 그대로 보존한다.

예를 들어 같은 스레드에서 계정 A와 B가 각각 “한국어로 요약해 주세요”라고 했다면, 두 행을 제안한 결과에서 계정 A의 `claim`과 계정 B의 `claim`은 별도 fact다. A가 같은 범위에서 같은 말을 다시 하면 A의 fact에 근거가 하나 더 붙는다. A가 다른 스레드에서 같은 말을 하면 그 스레드의 fact가 생긴다. Librarian이 근거로 인용한 행에 계정 또는 원본 좌표가 없으면 계정별 저장 제안은 거절된다. 다음 회상 때 현재 입력이 검증된 계정 A와 그 대화에 결속되어야 해당 fact를 읽을 수 있다.

기존 Memory 행은 계정 확인 없이 읽을 수 있다. 후속 스키마 변경은 버전이 있는 코덱과 저장소 사전점검에서 구버전 writer와의 관계를 다룬다. 기존 fact ID를 바꾸거나 닉네임에서 subject를 역추정하는 일괄 마이그레이션은 필요하지 않다. 첫 구현은 원본 관측과 Librarian 질문의 `actor.account`에 `{"kind":"discord_user","version":1,"user_id":"900000000000000001"}` 형태의 참조를 전달한다. 기존 기록과 봇·웹훅 관측에서는 `actor.account` 필드가 빠진다.

외부 관측을 읽는 버전이 계정 종류나 버전을 아직 지원하지 않으면 원래 행을 수정하지 않고 관측만 읽는다. 그 행은 계정별 기억의 근거로 제시하지 않는다. 지원하는 형식의 계정 필드가 손상된 경우에는 읽기 오류로 드러낸다. 중복 검사 범위 안에서 Gateway가 같은 메시지를 재전달하면 최초에 기록한 관측을 그대로 돌려준다. 그 행에 비어 있던 계정 근거를 재전달로 채우지 않는다.

전달 메시지를 구분하기 전에 쓴 관측에는 전달 여부가 저장되지 않았다. 그런 기록을 계정별 Memory에 사용할 때는 원본 메시지에서 발화 근거를 다시 확인한다. 원본을 확인할 수 없으면 일반 관측으로만 사용한다.

## Lane Add-on Graph

Core가 조회 권한과 현재 스냅샷 리비전을 확인한 다음 범위가 제한된 읽기 전용 관측을 전달한다. Add-on은 `계정 → 발언 → 대화`, `계정 → 근거 있는 기억`, `인물 → 확인된 계정`을 그래프로 표현한다. 판정에 필요한 ID, 관측 범위, 원본을 열 수 있는 참조만 전달한다. 닉네임은 별칭으로 그리며, 원본 비공개 메시지나 커넥터 인증 정보가 Graph 데이터를 통해 퍼지지 않게 한다.

인물 노드와 기억 간 관계는 각 근거로 추적할 수 있어야 한다. 그래프 결과는 스냅샷 리비전과 범위에 붙는다. 권한 변경, 기억 철회, 계정 연결 취소가 읽히면 기존 결과를 다른 범위에 재사용하지 않는다. Add-on이 지워져도 원본 기억은 유지되고 같은 권한의 입력에서 그래프를 다시 만들 수 있다.

첫 Graph는 입력 한 번으로 순수하게 계산할 수 있다. 자동 갱신이 필요해지면 기존 Lane의 명시적 관측 경로와 source revision을 사용한다. 원본 파일의 경로나 닉네임에 맞춘 폴링을 전제하지 않는다.

## TUI·Dashboard의 대화 계속하기

사용자가 멘션을 열 때 화면은 원본 메시지의 주소를 잡아 `#채널 › 스레드`를 보여준다. 서버는 보낸 사람 권한, 선택한 원본 메시지, 현재 커넥터 바인딩과 실제 목적지의 일치를 확인한다. 스레드에서는 그 스레드에 보내고 채널 메시지에는 원래 메시지의 답글을 보낸다. 운영자 입력의 출처와 Discord로 전달할 목적지는 별도 필드로 보존한다. 주소나 권한이 불명확하면 초안을 보존하고 거절 사유를 표시한다.

두 화면은 서버가 발급한 같은 발송 작업 ID로 접수, 전송 중, 전달 확인, 실패 또는 결과 미확인을 읽는다. 전달을 확인할 때는 Discord가 반환한 메시지 주소를 영수증에 남긴다. 응답이 끊겨 서버가 이미 전송했는지 알 수 없는 작업은 그 사실을 표시한다. 같은 작업 ID를 재사용할 때 서버가 저장한 결과를 먼저 조회하며, 커넥터에서 중복 방지가 확인된 방식으로만 자동 재시도한다. SSE나 WebSocket 재연결 뒤에도 저장된 작업 상태를 다시 읽는다.

텍스트 왕복 경로가 검증되면 이미지·음성이 같은 목적지와 전송 영수증을 사용한다. 이미지 수신은 읽기 권한을 확인한 바이트와 콘텐츠 형식으로 모델 및 미리보기에 전달한다. 음성 메시지는 사용자가 녹음 파일을 보내기로 선택한 경우에 전송한다. 받아쓰기 초안과 실제 오디오 전송은 별도 사용자 동작이다.

수신한 첨부물은 원본 메시지 주소와 커넥터 첨부 ID로 식별한다. URL이 갱신되거나 만료될 수 있으므로 원본을 다시 열 때도 권한을 확인한다. 업로드는 첨부 형식과 크기를 서버에서 검증하고, 기능 지원 여부를 실제 목적지 커넥터에서 확인한다. 사용자에게는 전송 완료와 첨부 처리 실패를 각각 보여 준다.

## 구현 순서와 확인 항목

| 단계 | 기존 경로에서 확인할 동작 |
|---|---|
| 1. Discord 계정 근거 | 정상 사용자 메시지에 버전이 명시된 계정 참조를 남긴다. 닉네임 변경·동명이인·다른 길드·봇/웹훅·기존 행을 구분한다. 계정이 원래 발화자와 대화·메시지 좌표에 맞지 않으면 저장 행을 거절한다. |
| 2. 계정별 Memory | 내용이 같은 두 계정의 선호와 같은 계정의 두 대화 범위를 따로 저장하고 찾는다. 오래된 사실의 exact ID로 조회와 철회가 계속 된다. |
| 3. 읽기 전용 Graph Add-on | 허용된 계정과 기억·출처만 가져와 동일 입력에서 같은 관계를 만든다. 워크스페이스 전환·권한 철회 후 이전 결과가 보이지 않는다. |
| 4. 커넥터 답장과 미디어 | 두 화면에서 같은 원본 스레드·메시지에 텍스트가 도착하고 중복 전송 없이 영수증이 남는 것을 확인한다. 같은 경로를 이용해 이미지와 음성을 검증한다. |

작은 회귀 검사는 저장과 조회의 ID·범위·원본 근거를 검증한다. 실제 채널 왕복과 Graph 표시 검증은 접근이 허용된 테스트 워크스페이스에서 수행한다.
