Keeper 제품 기능·실행 흐름·Runtime·SSOT 감사

작성일 2026-08-11 KST · source main@78a9d48b5c27058a5246223b1bfcf8e5793fd507 · 작업 트리에는 기존 사용자 변경이 다수 존재함

방법: OCaml source의 producer → durable store/owner → runtime adapter → Agent.run → finalization/consumer 순서를 정적 추적. 이 문서의 source 판정은 live 배포 성공 증명이 아니며, 이번 감사에서 live state를 변경하지 않았다.

요약 판정. 일반적인 direct chat과 active Keeper의 autonomous heartbeat happy path는 소스상 성립한다. 둘은 Keeper_agent_run.run_turn, checkpoint sink, response finalization, execution receipt를 공유하지만, admission·stimulus intake·prompt·retry·meta commit·event settlement가 완전히 같지는 않다.

따라서 제품 목표는 “100% 같은 구현”이 아니라 공통 실행 코어 + 채널별 정책 + 하나의 durable authority로 정의하는 것이 맞다. 현재 가장 큰 일관성 위험은 Runtime이 세 계층(env/boot TOML/Runtime_params)으로 나뉜 사실 자체보다, 어떤 knob가 부팅 고정이고 어떤 knob가 hot인지 표면에서 동일하게 보이는 점이다. 그 다음은 production consumer가 확인되지 않는 일부 knob와 direct/autonomous 외곽 orchestration의 중복이다.

SOURCE-COMPLETE소스 경로와 종결 계약이 확인됨 SOURCE-PLAUSIBLEhappy path는 성립하지만 live E2E는 별도 CONSISTENCY-RISKauthority 또는 적용 시점이 분리됨 ORPHAN / GAPconsumer가 없거나 proof가 부족함

1. 감사 범위와 증거 규칙

확인한 것

direct invocation, autonomous heartbeat, typed event queue, Keeper Owner 직렬화, runtime assignment, Agent Core 실행, checkpoint/replay, Gate/HITL continuation, receipt/metrics/Activity projection, Runtime 설정 precedence.

확인하지 않은 것

현재 배포 binary가 이 HEAD와 같은지, 실제 provider가 응답하는지, 실제 dashboard가 모든 projection을 표시하는지, 장시간 restart/crash/replay가 통과하는지는 live probe/E2E가 없으므로 확정하지 않는다.

증거 등급

S는 source fact, I는 source에서 도출한 plausibility, U는 이 turn에서 live 검증하지 않은 주장이다. report의 “성공”은 live green이 아니라 source contract complete라는 뜻이다.

Serena navigation skill을 적용하려 했으나 이 세션에는 Serena MCP tool이 노출되지 않아 rg/nl -ba로 동일한 symbol-to-line 추적을 수행했다. GitHub connector는 OAuth 재인증 오류가 있어 공개 GitHub 원본 페이지를 직접 확인했다.

5. 실제 happy path의 논리적 plausibility

Direct message

  1. Keeper가 존재하고 runtime이 해석된다.
  2. Owner가 admitted request를 하나 claim한다.
  3. 현재 task/channel context와 checkpoint history로 prompt를 만든다.
  4. provider가 text 또는 tool progress를 반환하고 tool effect가 닫힌다.
  5. response가 history/checkpoint에 저장되고 post-turn lifecycle이 계산된다.
  6. Owner meta가 atomic commit되고 reply JSON과 turn_ref가 반환된다.

SOURCE-PLAUSIBLE keeper_turn.ml:759-913에 trajectory finalize → lifecycle → Owner commit → metrics/broadcast → reply 조각이 순서대로 있다. 다만 실제 provider/channel delivery는 이번 감사의 증거가 아니다.

Autonomous heartbeat

  1. heartbeat가 presence/snapshot을 갱신하고 lifecycle admission을 확인한다.
  2. typed queue에서 exact source를 하나 consume하고 world observation을 만든다.
  3. reactive trigger가 있으면 reactive, 없고 proactive gate가 켜져 있으면 scheduled autonomous를 선택한다.
  4. Owner idle claim 뒤 runtime/prompt/Agent.run을 수행한다.
  5. 성공이면 unified success가 meta/metrics/activity/decision/FSM을 기록한다.
  6. 성공 또는 terminal failure evidence에 따라 source를 ACK/terminalize하고 다음 sleep으로 간다.

SOURCE-PLAUSIBLE heartbeat가 실제로 provider까지 도달하려면 active lifecycle, owner, initialized runtime, valid queue, provider availability가 모두 필요하다. keeper_world_observation.ml:1391-1420은 proactive가 켜졌을 때 cadence 자체를 run signal로 삼는다.

검증 한계. 이 코드는 “정상 입력이면 정상 경로가 존재한다”는 논리 검증이다. 실제 happy path proof에는 fresh Keeper 생성 → runtime assignment → provider response → chat/queue terminal receipt → process restart 후 readback을 한 번에 수행하는 E2E가 필요하다. 특히 schedule/fusion은 wake dispatch와 final completion을 분리해 검사해야 한다.

Direct/autonomous outer flow 중복복잡도 위험공통 Agent.run은 같지만 direct는 자체 FSM/meta/reply, autonomous는 unified success/queue terminalization을 각각 갖는다. 기능상 분리는 맞지만 drift surface가 크다.한 개의 post-run typed result/finalization contract를 만들고, 채널별 consumer만 얇게 남긴다. 당장 무리한 대형 merge는 금물.
Manifest + receipt + TurnRecord + Activity + metrics + raw trace조건부각각 operator, replay, usage, timeline, telemetry 목적이 있으면 정당하다. consumer/retention이 없는 산출물은 동일 사실의 중복 저장이다.field-level provenance table과 retention/consumer owner를 문서화하고 orphan artifact는 삭제한다.
Runtime env/TOML/Runtime_params 3층가장 큰 위험durable routing과 hot tuning을 모두 지원하려다 적용시점과 precedence가 섞였다. orphan knob까지 있어 “설정 가능”과 “실제 효과”가 어긋날 수 있다.routing은 runtime.toml, hot tuning은 Runtime_params, env는 startup/test override로 역할을 고정하고 UI에 source/effective/applied-at을 표시한다.
Proactive always-on cadence정책 선택현재 proactive gate가 켜지면 heartbeat 자체가 wake라 backlog/idle threshold 없이 매 cadence turn을 시도한다. resident agent에는 합리적이지만 비용·provider slot을 계속 소비한다.always-on을 correctness invariant로 만들지 말고 mode로 노출한다. disabled/paused/owner-busy는 명시적 skip reason으로 남긴다.
“direct와 autonomous가 100% 동일”잘못된 목표direct는 user reply latency/turn_ref가, autonomous는 stimulus ACK/continuation/heartbeat가 종착점이다. 동일화하면 각 채널의 효과를 삭제하게 된다.공통 invariants만 동일: Owner, runtime, tool/Gate, checkpoint, receipt schema, terminal FSM. 정책과 consumer는 다르게 둔다.
가장 구체적인 gap. turn.max_output_tokens, turn.cli_subprocess_idle_sec, turn.capacity_limit는 config/test surface가 있지만 이 감사의 production lib 검색에서는 기대한 consumer가 확인되지 않았다. 이것은 “기능이 확실히 죽었다”는 runtime 판정은 아니지만, SSOT/feature census에서 즉시 consumer proof를 붙이거나 hard-cut해야 하는 orphan 후보이다.
