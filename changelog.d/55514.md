### Changed

- **Keeper model input**: on the direct HTTP lane, the tool results and verified arguments of a turn that ended now go as markers from the next turn's first request, whether the carried window stayed or moved (RFC tool-results-age-out-of-context, 2026-11-24 decision J). A window the size signal watched used to keep them whole until the window moved, so a request carried every ended turn's results up to the declared limit. A window that stays now rewrites its prompt cache once a turn, from the first result of the turn that just ended. It still sends markers below the atom its last request did, so a dispatch that cannot name the turn boundary, or one that follows a size refusal inside the open turn, keeps that boundary. Results under 2,048 bytes stay whole below it, and a range that opens elsewhere reads the turn boundary alone (#55514).
- **Keeper size signal**: the next turn's peak is read from the count that turn builds on. When its first request leaves the turn before it as markers, that is the count the turn before opened at, not the count it ended at, and a turn's growth is measured from the same count. The logged ledger reports `turn_opened_at` and `largest_turn_growth`; `next_turn_peak` is no longer a ledger field and stays on the line that reports a window move. A dispatch that takes up an open turn again sends the turn context a second time; the ledger now records the turn boundary each request ran under (`turn_boundary`) and reads such a request as part of the open turn, not as a new one (#55514).
