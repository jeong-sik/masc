# Keeper 기억 recall: 2026-10 추가 조사 (r2)

- 날짜: 2026-10-28 (KST). 외부 자료는 같은 날 확인했다.
- 범위: [r1](2026-10-28-keeper-recall-prior-art-r1.md) 뒤에 운영자가 가져온 LambdaDB 글(2026-10-25)과, 그 글이 건드리는 쟁점인 쓰기 전략, 전체 이력 대 검색, 맞게 찾고도 안 쓰는 문제, 다자 대화를 다룬다.
- 방법: 페이지는 웹 가져오기 도구로 읽었다. 이 도구는 작은 모델이 페이지를 요약해 주므로 수치는 요약이 인용한 문장이고 원문 표와 대조하지 못했다. 검색 결과 요약만 본 것은 따로 표시했다. 우리 코드와 라이브 설정은 직접 읽었다.
- 확신도: H 는 공식 문서·소스를 직접 읽음, M 은 한 번 요약을 거친 1차 자료나 공개 저장소 문서, L 은 벤더 블로그나 검색 결과 요약.
- 이 문서는 조사다. 결정은 [RFC-keeper-recall-reaches-the-turn](../rfc/RFC-keeper-recall-reaches-the-turn.md) 에 있다.

## 1. 요약

- 읽은 자료에는 호스트가 골라 싣는 것과 모델이 도구로 당기는 것을 맞붙여 잰 것이 없다. RFC 의 D1(호스트가 고른다)과 D2(판정은 Jev 가 한다)를 바꾸는 근거는 없다. LambdaDB 글은 참고 자료로만 둔다. 벤더가 개발에 쓴 데이터로 직접 잰 수치라서 결정 근거로 쓰지 않는다(§3.7).
- 바뀌는 것이 넷이다. 1~2 는 Jev 공식 문서가 근거이고 3~4 는 보조 근거다.
  1. Jev 를 별칭이 아니라 버전으로 고정한다. 문서가 별칭은 새 릴리스로 옮겨 가서 코드를 안 바꿔도 답이 바뀐다고 한다.
  2. Jev 의 입력 한도를 설계에 적는다. 요청당 문맥은 `state` 와 모든 질문의 합 64k 토큰이고, 질문당 문맥은 `state` 와 질문 하나의 합 32k 토큰이다. 후보를 모두 `state` 에 넣으면 32k 토큰이 한도다. 입력 토큰당 바이트에 따라 후보가 있는 Keeper 42명 중 15명(3.0바이트)에서 23명(2.04바이트)이 후보를 한 요청에 못 보낸다(RFC §4.2).
  3. 쓰기 경로를 다시 본다. 주된 근거는 Keeper 다섯의 보고와 우리 측정(Librarian 레인 실패 42%)이다. 외부 자료는 보조다. 쓸 때 LLM 을 안 쓰는 원문 저장이 대등하거나 낫다는 보고가 여럿이지만, 갱신된 사실을 다루는 도구 사용 과제에서는 쓸 때 구조화하는 쪽이 이겼다.
  4. "실렸지만 안 쓴 비율"을 따로 잰다. 올바르게 검색된 값을 행동에 쓴 비율이 55% 라는 프리프린트 한 편이 있다. PO 의 R2 와 같은 방향이다.
- 전체 노출 팔(D)은 이미 RFC 에 있어서 바꾸지 않는다.
- 도구를 쓰는 과제에서 기억 활용을 재는 벤치마크가 둘 있다(Mem2ActBench, MERIT). 기억이 필요하다는 것을 스스로 알아차렸는지를 직접 재는 것은 못 찾았다.

## 3. 해석

### 3.1 검색이 쓰기보다 크다

Yuan 등은 검색 방식이 정확도를 20점 움직이고 쓰기 전략은 3~8점 움직인다고 했다. LambdaDB, Couchbase, Tigerdata 도 같은 방향이다. 질문마다 검색을 해서 답하는 설정에서 원문 보존은 LLM 이 추려 쓴 사실보다 못하지 않다.

우리 쪽에서 읽는 법은 둘이다. 하나는 사실의 98%를 LLM(Librarian)이 쓰는데 그 레인이 최근 14일 시도의 42% 를 실패했다는 점이다([RFC §2.6](../rfc/RFC-keeper-recall-reaches-the-turn.md)). 쓰기 때 LLM 에 기대는 비용이 크다. 다른 하나는 MERIT 의 결과다. 갱신된 사실이 있는 도구 사용 과제에서는 갱신 시점에 구조화한 방식이 임베딩 검색보다 안정적이었다. 낡은 값을 고치고 지우는 Librarian 의 일은 이 쪽에 해당한다. 그래서 "Librarian 이 의미 없다"는 결론은 이 자료로 나오지 않는다. 의미가 있다면 갱신과 정리에 있고, 추려 쓰는 일 자체는 아니다.

### 3.2 전체 이력 대 검색은 답변 모델에 달렸다

LambdaDB 에서 전체 이력(105K 토큰)과 검색(5K 토큰)의 차이는 500문항 중 4문항이다. 대등하다고 읽어야 하고 보고서도 우월성을 부인한다. 같은 규모의 이력에서 Zep 의 2025년 실험은 GPT-4o 로 63.8% 대 71.2% 였고, Hindsight 는 20B 모델로 39.0% 대 83.6% 였다. 답변 모델이 강해지면 전체 이력이 따라잡는다. 우리 키퍼는 백엔드가 여럿이라 RFC §7 의 팔 D(전체 노출)를 런타임별로 따로 본다. MERIT 는 전체 리플레이가 달러당 효용이 낮다고 했지만, 우리 헌법은 비용을 판단 기준에 넣지 않는다.

### 3.3 맞게 찾아도 안 쓴다

MERIT 는 갱신된 사실에서 올바르게 검색된 값을 에이전트가 행동에 쓴 비율이 55% 라고 했다. Mem2ActBench 도 기억을 도구 인자에 반영하는 쪽이 약하다고 했다. 실렸다고 쓰이는 것은 아니다. RFC 의 R2(실린 기억 중 인용·사용된 수)를 판정 품질과 따로 재야 하는 근거다. 둘은 사전 등록된 설정이 아니고, 한 편은 프리프린트다.

### 3.4 다자 대화와 갱신된 사실

GroupMemBench 에서 가장 약한 범주가 지식 갱신(27.1%)이다. 키퍼가 일하는 Board 는 다자 대화이고 낡은 값이 가장 큰 위험이라고 Keeper 열다섯이 답했다. 단순 BM25 가 대부분의 시스템과 같거나 낫다는 결과는 정확한 식별자가 중요하다는 의견(wkbl-data, kidsnote-qa-hub-manager, code-reviewer-uncle)과 맞는다. 우리 설계는 후보를 미리 줄이지 않고 판정이 전부 본다. 이 자료가 말하는 검색 병목을 판정 단계로 옮긴 셈이라, 판정의 놓침을 오프라인 재생으로 재야 한다는 RFC §7 의 요구가 더 중요해진다.

### 3.5 벤더 수치는 서로 비교할 수 없다

같은 BEAM 1M 에서 Mem0 는 64.1, past.dev 는 90.65, LambdaDB 는 86.62 를 보고한다. 답변 모델, 판정 모델, 히스토리, 질문이 다르다. LambdaDB 의 점수는 Jev 판정에 기대는데, 판정 정확도는 독립 검증되지 않았고 5번 반복에서 500개 중 2개가 흔들렸다. 어느 쪽 수치도 우리 효과 크기의 근거로 쓰지 않는다. RFC 는 이미 합격선을 미리 정하지 않고 우리 질문 묶음으로 잰다.

### 3.6 이 벤치마크들이 재지 않는 것

LongMemEval, LoCoMo, BEAM, GroupMemBench 는 질문이 과거를 직접 묻는다. 에이전트가 기억이 필요하다는 것을 스스로 알아차려 도구를 부르는지는 재지 않는다. 우리 0.80% 가 바로 그 문제다. Mem2ActBench 와 MERIT 가 가장 가깝지만 기억 도구를 부를지 말지의 결정을 따로 재지는 않는다. 그래서 외부 정확도는 "찾은 뒤"의 품질에 쓸 수 있고, "찾으려 했는가"에는 쓸 수 없다. 호스트가 고르는 설계가 후자를 없애는 방식이다.

### 3.7 LambdaDB 글은 얼마나 믿을 수 있나

참고 자료로만 둔다. 이유는 다섯이다.

- 개발에 쓴 같은 영어 데이터로 평가했다. 청크 800자, 후보 200, 반환 50, 토큰 예산 4,096 같은 값을 정한 방법이 문서에 없고 held-out 결과가 아니다. 보고서가 4문항 차이는 우월성을 입증하지 않는다고 적는다. 같은 50문항 부분집합에서는 전체 이력이 96%, 검색이 90% 였다.
- 정답 판정을 공식 방식(GPT-4o)에서 Jev 로 바꿨다. 결정이 10-17, 평가가 10-22, 글이 10-25 이다. 판정 정확도는 독립 검증이 없고 사람 검수도 없으며 5번 반복에서 500개 중 2개가 흔들렸다. 공식 리더보드 점수와 비교할 수 없다.
- 질문 유형별 점수, 오답 원인 분석, 필요한 사실의 재현율이 없고 질문별 응답이 비공개라 감사할 수 없다.
- "95% fewer tokens" 는 답변 모델 입력만 센다. 질문당 리랭킹 입력이 약 29K~115K토큰(모델링 값)이고 임베딩이 약 103K토큰이라 처리한 총 토큰은 전체 이력(105K)보다 많다. "Without Graphs" 는 그래프 시스템과 비교한 결과가 없고, "Without LLM bookkeeping" 은 내장 요약 기능과 50문항 부분집합 비교뿐이다. 비용은 추정이고 글과 보고서 숫자가 서로 다르다(내장 벡터 저장 $29.42 대 $14.12, 전체 이력 $105.53 대 $131.83).
- 천장 효과가 있다. 전체 이력이 이미 95.2% 라서 이 벤치마크로는 좋은 시스템끼리 구분이 안 된다.

타당한 부분은 좁다. 이력 약 115K토큰 규모에서 최신 답변 모델로 하이브리드 검색과 리랭킹이 전체 이력과 비슷한 정확도를 낸다는 것, 쓰기 전략보다 검색이 크다는 방향(Yuan 등과 맞음), 32K 로 자르면 크게 나빠진다는 것이다. 우리 설계에는 쓰지 않는다. 우리 질문(질문 없이도 기억이 턴에 닿는가)과 다르고, 규모가 훨씬 작고, 점수 순위와 상위 N 과 어휘 검색은 헌법과 충돌한다. 가져올 것은 판정 관행(버전 고정, 원시 확률 기록, 유리한 사례만 재판정하지 않기)뿐이다.

## 4. RFC 에 준 영향

- 설정: `[typesafeai]` 의 `model` 에 `jev-latest` 대신 버전 id 를 적는다. 코드는 `Typesafeai_types.model` 이 `Custom of string` 을 이미 받는다(`lib/typesafeai/typesafeai_types.mli:4`). 기본값은 `jev-latest` 이고(`lib/runtime/runtime_schema.ml:551`) 라이브 설정에 `model` 줄이 없다.
- 한도와 가격: 후보를 보내기 전에 조각으로 나누고, 그래도 거절되면 반으로 나눈다(RFC §4.2, §4.6). 긴 맥락 헤더는 쓰지 않는다. 입력 100만 토큰당 $0.042 이고 이미 보낸 요청에서 입력 한 토큰이 2.04바이트였으므로 질문 문구까지 더하면 하루 약 $11 이다(RFC §4.8). 조직별 초당 요청·토큰 한도를 넘으면 429 가 온다.
- 측정: Jev 반복 일치율의 선행 값으로 498/500(5회 반복, 예/아니오 판정 작업, 벤더 측정)이 있다. 우리 질문 모양에서는 모른다. 같은 버전으로 재생해야 한다.
- 쓰기 경로: 승인 대기열이 헌법의 Gate 기준(없어도 durable truth 가 유지되면 제거 대상)에 맞는지 묻는다. RFC §2.6 과 §8.
- 평가: R2(실렸지만 안 쓴 것)와 판정 품질을 따로 센다. 전체 노출 팔은 런타임별로 본다.

## 5. 확인하지 못한 것

- 요약 도구를 거친 수치는 원문 표와 대조하지 못했다. 특히 MERIT 의 55% 는 "갱신된 사실, 임베딩 검색 조건"의 값으로 읽었다.
- 검색 결과 요약만 본 자료(Zep, Hindsight, Mem0, Couchbase, Tigerdata, MemMachine)는 원문을 열지 않았다.
- Jev 가 같은 입력에 같은 답을 내는지 공식 문서에 없다.
- 이 자료들은 모두 대화나 과제 한 가지를 단일 사용자나 합성 다자 설정에서 잰다. 여러 Keeper 가 한 저장소를 쓰는 우리 상황과 같은 설정은 없다.
