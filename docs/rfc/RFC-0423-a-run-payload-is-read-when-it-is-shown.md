## 1. 문제

`exact_lane_run_registry` 가 살아있는 힙의 **498MB** 를 차지한다. 2026-09-05 측정,
서버 live 2.58GB 중 단일 최대 항목이다.

무엇이 그 안에 있는지는 파일이 답한다. `~/.masc/exact-lane-runs-v5.jsonl`,
347MB / 12,079행:

| 필드 | 크기 | 비중 |
|---|---|---|
| `registration.input` | **340MB** | **98%** |
| `completion.output` | 10MB | 2% |
| 나머지 전부 | ~0MB | |

`input` 은 레인에 보낸 프롬프트 전문이고, `output` 은 모델 응답 전문이다.

보유 정책은 `completed_retention = \`Latest 2000` 에 `retention_group = lane_key`,
즉 **레인당 2000행**이다. 레인이 넷이니 8,000행이 상시 메모리에 있다.

### 목록은 그것을 읽지 않는다

이 저장소를 읽는 길은 둘이고, 이미 나뉘어 있다.

```ocaml
(* 목록: t.projection 에 캐시된다 *)
let projected_run_of_entry _ (entry : Store.entry) =
  { run_id = entry.id
  ; lane = entry.registration.lane
  ; actor = entry.registration.actor
  ; started_at = entry.started_at
  ; input = Exact_input `Null      (* 버린다 *)
  ; status = ... output = `Null    (* 버린다 *)
  }

(* 상세: 한 번에 하나 *)
let get t ~run_id = ... full_run_of_entry ... (* 페이로드를 준다 *)
```

투영은 이미 옳다. 문제는 그 아래다 — **`Store` 가 원본 `entry` 를 통째로 들고 있고,
그 안에 8,000개의 프롬프트 전문이 있다.** 상세 조회는 한 번에 하나를 보는데.

API 투영을 재보면 행당 **286바이트**다. 저장이 투영의 250배다.

### 이것이 지연으로 이어진다

메모리 자체보다 그 결과가 문제다. OCaml 5 의 minor GC 는 모든 도메인을 멈추는
배리어이고, major GC 는 live 에 비례한다. live 가 2.58GB 인 서버에서 그 19%가
아무도 읽지 않는 프롬프트다.

2026-09-05 측정: `/health` 최대 지연이 9,744ms 였고, 네 번의 수정(#33334, #33340,
#33343, #33360) 뒤 0.53ms 가 됐다. 그 넷은 **할당** 축이었다. live 축은 아직
손대지 않았다.

## 2. 무엇을 하려는가

**페이로드를 메모리에서 빼되 데이터는 잃지 않는다.**

- 파일은 그대로 둔다. 보유 상한도 그대로 둔다.
- `Store` 의 메모리 표현에서 `registration.input` 과 `completion.output` 을 뺀다.
- 그 자리에 **파일 오프셋**을 둔다.
- `get` 이 그 오프셋으로 한 행을 읽어 페이로드를 채운다.

목록은 바뀌지 않는다 — 이미 버리고 있었다. 상세는 디스크 읽기 한 번이 는다.

### 왜 상한을 깎지 않는가

레인당 2000 → 200 이면 메모리는 같은 정도로 줄지만 **90%의 실행 기록을 잃는다.**
그 기록은 지금 무엇을 보내고 무엇을 받았는지 되짚는 유일한 근거다. 손해 없는
개선이 가능한데 손해를 볼 이유가 없다.

## 3. 설계

### 3.1 저장 표현

```ocaml
type payload_ref =
  | Inline of Yojson.Safe.t
      (** 아직 파일에 없는 것: 방금 등록되어 append 대기 중인 행. *)
  | At of { offset : int }
      (** 이 행이 시작하는 파일 오프셋. 읽으면 그 행의 JSON 이 나온다. *)
```

`entry` 는 `registration`/`status` 안의 페이로드를 `payload_ref` 로 바꾼다.
목록 투영은 이 필드를 아예 안 보므로 영향이 없다.

### 3.2 오프셋은 어디서 오나

`replay` 가 이미 파일을 한 줄씩 읽는다(`fold_appended_lines`). 각 행의 시작
오프셋을 그때 기록한다 — 이미 순회하고 있으므로 추가 I/O 가 없다.

append 경로는 쓰기 직후의 오프셋을 안다. `Inline` 으로 시작해 쓰기가 성공하면
`At` 으로 바꾼다. 쓰기가 실패하면 `Inline` 으로 남는다 — 디스크에 없는 것을
디스크에서 읽으려 하지 않는다.

### 3.3 읽기

```ocaml
val get : t -> id:string -> entry option
(* 계약은 그대로. 페이로드가 [At] 이면 그 오프셋에서 한 행을 읽어 채운다. *)
```

읽기는 `Fs_compat.read_slice ~path ~from ~len` 로 한 행을 가져와 파싱한다.
길이는 다음 행의 오프셋에서 나온다(마지막 행은 파일 끝까지).

### 3.4 압축이 오프셋을 무효화한다

`compact_replay_log` 가 파일을 다시 쓰면 모든 오프셋이 틀려진다. 압축은 이미
`replay` 안에서 일어나고 그 직후 상태를 만드므로, **압축 뒤에 오프셋을 다시
기록**하면 된다. 압축이 쓴 결과를 그대로 순회한다.

압축 밖에서 파일이 바뀌는 경로는 append 뿐이고, append 는 앞을 건드리지 않는다.

### 3.5 파일이 사라지거나 잘리면

`At` 오프셋에서 읽었는데 그 행이 이 `id` 가 아니면 **`None` 이 아니라 페이로드
없는 `entry`** 를 준다. 상세 화면은 "이 실행의 요약은 있고 페이로드는 읽을 수
없다"를 말할 수 있어야 한다. 조용히 빈 페이로드를 주면 "프롬프트가 비어 있었다"와
구분이 안 된다.

## 4. 무엇을 하지 않는가

- **보유 상한을 바꾸지 않는다.** 지금 8,000행 그대로.
- **파일 형식을 바꾸지 않는다.** 기존 파일이 그대로 읽힌다.
- **`verification_runs`, `fusion_runs`, `goal_verification_runs` 는 그대로 둔다.**
  같은 코어를 쓰지만 각각 live 1MB 이하다. 코어에 `payload_ref` 를 두되 그들은
  `Inline` 만 쓰면 동작이 지금과 같다.
- **목록 투영을 바꾸지 않는다.** 이미 옳다.

## 5. 검증

| 무엇 | 어떻게 |
|---|---|
| 목록이 안 바뀐다 | 같은 저장소에서 `list_runs` 결과가 변경 전후 동일 |
| 상세가 페이로드를 준다 | append → `get` → `input`/`output` 이 쓴 것과 같다 |
| 압축 뒤에도 읽힌다 | 압축을 강제하고 그 뒤 `get` 이 옳은 페이로드를 준다 |
| 오프셋이 어긋나면 말한다 | 파일을 손으로 잘라 놓고 `get` 이 페이로드 없음을 표시 |
| 메모리가 준다 | 8,000행 픽스처에서 `Gc.full_major` 후 live 비교 |

마지막 것이 이 RFC 의 이유이므로 숫자로 기록한다. 목표는 **498MB → 20MB 이하**다.

## 6. 위험

**상세 조회가 I/O 를 하게 된다.** 지금은 메모리 조회다. 한 행이 최대 1.3MB 이고
읽기는 seek 한 번이므로 밀리초 단위일 것이나, 측정하지 않았다. 상세 화면은 한 번에
하나를 보므로 목록의 지연에는 영향이 없다.

**압축과 읽기의 경쟁.** 압축 중에 `get` 이 옛 오프셋으로 읽으면 다른 행이 나온다.
3.5 의 id 대조가 이것을 잡는다 — 틀린 행을 주는 대신 페이로드 없음이 된다.

## 7. 대안

**(a) 상한을 깎는다.** 가장 싸지만 데이터를 잃는다. 4절의 이유로 채택하지 않는다.

**(b) 페이로드를 압축해서 메모리에 둔다.** 340MB 를 zstd 로 줄이면 수십 MB 가 될
수 있다. 데이터를 안 잃고 I/O 도 없다. 다만 압축/해제 비용이 CPU 로 옮겨가고,
지금 문제가 GC 배리어라 live 를 줄이는 것이 목적인데 압축본도 live 다. 오프셋보다
효과가 작고 복잡도는 비슷하다.

**(c) 그냥 둔다.** live 2.58GB 중 498MB 다. 나머지 축(272MB × 2, 203MB …)을 먼저
보고 판단할 수도 있다. 다만 이것이 단일 최대이고 원인이 가장 분명하다.
