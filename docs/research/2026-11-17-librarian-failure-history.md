# Librarian 이 여섯 달 동안 고치고 다시 고장 난 자리 — RFC 22개, 커밋 785개, 이슈 577개를 읽은 기록

- 날짜: 2026-11-17
- 범위: Librarian RFC 와 그 구현 PR, 2026-06-01 ~ 2026-11-17 의 Librarian 경로 커밋, `librarian` 으로 찾은 이슈와 닫힌 PR 이다.
- 근거 폴더: [셈 기록](../evidence/research/2026-11-17-librarian-failure-history/README.md). 2절의 표는 그 폴더의 표를 옮긴 것이다.
- 코드 사실: main `fa5aead0d999`(2026-11-17 21:55 KST)에서 읽었다. 커밋 수와 코드 크기는 이 커밋에서 셌다. 이슈와 PR 수는 2026-11-17 22:10 KST 무렵의 GitHub 상태다.
- 관련 결정: [Librarian 재설계 RFC](../rfc/RFC-librarian-call-only-proposes-and-one-writer-per-keeper-commits-in-one-line.md)
- 이 문서는 연구 기록이다. 무엇을 만들지는 RFC 가 정한다.

## 0. 요약

- Librarian 은 Keeper 의 끝난 턴을 읽어 Memory 를 고치는 모델 호출이다. 그 호출을 준비하고 답을 적는 코드도 함께 가리킨다. 한 번 도는 일을 pass 로 부른다.
- 2026-06-01 부터 11-17 까지 Librarian 경로에 커밋 785개가 들어갔다. 337개(43%)가 fix 다. 고른 785개 중 제목이 revert 인 커밋은 0개다(2.1).
- 11-09 ~ 11-17(W46 ~ W47)에는 fix 가 60개, feat 가 20개였다. feat 하나에 fix 가 셋이다.
- 2026-11-17 00:09 KST 에 Librarian 이 읽지 않은 턴이 8,031개였다. 턴은 시간당 약 90개 끝났다(11-16 의 24시간). Memory 를 고치는 pass 의 답은 시간당 약 4.9개 왔다(11-16 00:00 ~ 13:23Z 의 13시간 23분). 두 값은 잰 창이 달라 비율로 읽지 않는다(2.6).
- 다섯 시기가 같은 순서를 밟았다. 고장을 쟀다. 장치를 더했다. 그 뒤에 다음 고장을 쟀다. 사슬 셋이 대표다.
  - Memory 에 적는 규칙(1기, 5기). 답에서 빠진 fact 를 지웠다. → 모든 fact 를 어떻게 할지 답에 적게 했다. → 08-29 까지 거절 517건 중 513건이 목록을 잘못 적은 것이었다. → 바뀐 것만 적게 했다. → fact 를 합칠 때 지식을 잃었다. → 바깥 판정자를 뒀다. → 11-16 에 판정자가 거절하자 pass 하나가 50 ~ 303초 걸렸다.
  - 읽은 위치(2기). 어디까지 읽었는지를 이력의 번호로 적었다. → 09-22 에 이력을 줄이는 정리(purge)가 그 번호를 바꿨다. → 읽는 범위를 좁혔다. → 11-16 에 Memory 를 고치는 요청 하나가 답을 받기까지 중앙값 717.5초 걸렸다(2.6).
  - 원본(3 ~ 5기). 원본은 모델 요청 하나를 남긴 불변 기록이다. → 끝나지 못한 원본 하나가 그 Keeper 의 Memory 정리를 세웠다. → 끝내는 규칙을 원인마다 하나씩 더했다.
- 2026-11-17 의 코드는 54,690줄이다. OCaml 모듈 122개가 53,945줄이고 `addons/` 의 파일 여섯이 745줄이다. 시험은 `test_case` 줄 수로 약 1,783개다.
- 뿌리는 둘로 읽힌다.
  - 첫째. pass 하나가 판정, 커밋, 진행의 단위를 겸했다. 한 곳이 실패할 때마다 pass 전체를 어떻게 할지 다시 정해야 했다.
  - 둘째. "결과를 모르면 모델을 다시 부르지 않는다"는 규칙을 Librarian 호출에 적용했다. Librarian 호출은 Memory 에 적을 것을 제안만 한다. 적는 일은 서버가 한다. 이 규칙이 온 곳은 3.3 에 적었다.
- 두 뿌리가 설명하지 못하는 것도 있다. 합칠 때 잃는 지식(F4), 본문을 크기 한도가 있는 통로로 나르는 일(F6 의 일부), 번호로 적은 읽은 위치(F8), 운영자에게 보이지 않던 밀림(F13), 서버와 worker 의 버전 어긋남(F15)이다.
- 8절의 가설 아홉은 결론이 아니다. 재설계가 확인하거나 버릴 질문이다.
- 전문을 읽은 RFC 는 22개다. 인용된 절만 본 RFC 는 1.4 에 적었다.

## 1. 무엇을 어떻게 읽었나

### 1.1 낱말

| 낱말 | 뜻 |
| --- | --- |
| pass | Librarian 이 한 번 도는 일. 읽을 범위를 고르고, 모델에 묻고, Memory 에 적고, 읽은 위치를 옮긴다 |
| fact | Memory 에 든 기억 하나. 이 문서는 기억과 fact 를 같은 뜻으로 쓴다 |
| claim | Librarian 이 새로 적는 fact 문장 |
| 출력 계약 | 모델 답을 Memory 에 옮기는 규칙 |
| atom | Keeper 이력(checkpoint)의 자리를 세는 단위. 턴과 같지 않다 |
| 읽은 위치 | Librarian 이 이력의 어디까지 읽었는지 적은 값. atom 번호로 적는다 |
| 공식 클라이언트 턴 | 공식 클라이언트로 돈 턴. 이력에 atom 이 없다 |
| 턴 끝 줄 | 턴이 끝난 자리를 적는 log 줄 |
| purge | 이력에서 atom 을 덜어 내는 정리 |
| 대기 칸 | 다음에 돌 일을 하나만 담는 자리. 새 일이 오면 앞의 것을 덮어쓴다 |
| 대기줄 | Keeper 하나의 Librarian 일이 차례로 도는 줄. 앞의 일이 끝나야 뒤가 돈다 |
| durable pass | 끝난 턴을 읽어 Memory 의 fact 를 고치는 pass |
| durable 시도 | durable pass 가 보낸 요청 하나가 답으로 끝나기까지의 일 |
| continuity pass | Keeper 요청에 싣는 작업 상태(`working_state`)를 만드는 pass |
| admission | Keeper 가 직접 적은 기억 후보를 Memory 에 들일지 정하는 pass |
| 소비자 | 같은 이력을 읽는 pass 종류. durable 과 continuity 둘이다 |
| receipt | 읽은 범위와 Memory 커밋을 묶은 기록 |
| 좁혀 읽기 | 요청이 실패하면 다음에 읽는 범위를 줄이는 일. 줄인 크기가 좁힌 폭이다 |
| 메시지 바닥 | 더 좁힐 수 없을 때 메시지 하나씩 읽는 길. 한 번이 바닥 걸음이고, 걸음을 이은 것이 바닥 사슬이다 |
| gate | 합친 claim 이 옛 fact 를 전하는지 바깥 판정자(Jev)에게 묻는 단계 |
| Lane Add-on | 모델 호출을 컨테이너 worker 에 맡기는 층. lane 은 그 층이 맡는 일의 한 종류다 |
| worker | Lane Add-on 의 컨테이너 프로세스. Librarian 요청의 대기열을 든다 |
| host | 모델을 부르는 서버 쪽. 자격 증명을 가진다 |
| frame | worker 가 답 하나에 실을 수 있는 크기. 4,194,304B 다 |
| `capacity_wait` | worker 가 요청을 접수하지 않을 때 주던 답. 2026-10-22 에 들어와 11-17 에 빠졌다 |
| 원본(original) | 모델 요청 하나를 host 가 남긴 불변 기록. 진행은 사건 줄로 따로 쌓는다 |
| frontier | 한 Keeper 에서 아직 끝나지 않은 history 원본. 하나만 허용한다 |
| settle | 끝난 원본을 archive 로 옮기는 일 |
| fence | 원본의 답이 Memory 에 적용되지 못하게 막는 표시 |
| inventory | pass 가 남은 기록을 세는 일 |
| Exact 기록 | host 가 모델을 부르기 전과 뒤에 적는 실행 기록 |
| 선언 | Lane Add-on 패키지를 가리키는 운영자 설정. revision 이 바뀌면 선언 교체다 |
| 장부 | Librarian 이 무엇을 읽고 적었는지 남긴 기록. 읽은 위치, receipt, 원본이 든다 |
| 기록 01 ~ 06 | 이 조사가 시기마다 쓴 작업 기록. 저장소에는 넣지 않았다 |

### 1.3 어떻게 셌나

- 커밋: `git log --no-merges --since=2026-06-01` 을 경로 넷으로 걸렀다. `lib/keeper/keeper_librarian_*`, `lib/lane_addon/`, `addons/keeper-librarian/`, `addons/exact_worker.py` 다. 766개다.
- `lib/keeper/keeper_memory_*` 만 건드린 커밋은 제목에 `librarian` 이나 `사서` 가 있을 때만 넣었다. 19개다. 합쳐 785개다.
- 커밋 종류는 제목 앞머리(`fix(...)`, `feat(...)`)로 정했다. 앞머리가 없으면 `other` 다. 날짜는 git 이 적은 committer 날짜를 그대로 썼다. 785개 중 60개는 UTC 로 적혀 있다. KST 로 바꾸면 달과 주의 칸 몇 개가 1씩 바뀐다(9월 fix 87, 10월 fix 119, W47 fix 28).
- fix 주제는 fix 제목 337개에 키워드 정규식 23개를 돌려 붙였다. 제목 하나가 여러 주제에 들 수 있다. 270개가 하나 이상에 들었고 67개는 들지 않았다.
- 이슈는 `gh issue list --search "librarian" --state all --limit 3000` 으로 찾았다. 577개다.
- 닫힌 PR 은 같은 말로 찾았다. PR 을 만든 날짜로 일곱 구간에 나눠 받았다. 검색 하나가 1,000개에서 잘리기 때문이다. 1,912개다.
- 명령과 스크립트는 근거 폴더에 있다.

### 1.4 읽지 않은 것

- 운영 서버와 그 로그는 이 조사에서 다시 읽지 않았다. 운영 수치는 모두 RFC 와 이슈가 적은 값이다.
- 코드는 RFC 와 이슈가 가리킨 줄만 읽었다. 효과가 나가는 경로를 모두 따라가지 않았다.
- 22개 밖의 RFC 는 인용된 절만 봤다. [RFC-0498](../rfc/RFC-0498-settled-archive-keeps-only-markers-a-live-record-names.md), [RFC-0521](../rfc/RFC-0521-the-next-turn-reads-the-refusal-left-in-its-turn-record-to-pick-its-start.md), [서버가 worker 패키지를 싣는 RFC](../rfc/RFC-server-carries-its-exact-worker-packages.md) 가 그렇다.
- 2026-11-17 의 정지가 어느 원본에서 왔는지는 다시 조사하지 않았다.
- 조사를 맡긴 쪽이 시작할 때 관측값 몇 개를 줬다. Keeper 약 20개의 정지, pool 을 차례로 거치는 12 ~ 15번, inventory 18 ~ 50초, 로그를 한 번만 적는 줄이다.
  이 조사는 그 값을 다시 확인하지 않았다. 아래에서는 「넘겨받은 관측값」으로 적는다.

## 3. 시기별 흐름

시기마다 표 하나를 둔다. 칸은 셋이다. 잰 고장, 더한 장치, 그 뒤에 잰 고장이다.
「그 뒤에 잰 고장」은 기록이 「다음에 깨진 것」으로 적은 것이다. 장치가 낸 고장도 있고, 장치가 막지 못한 고장도 있다.
한 행의 「그 뒤에 잰 고장」이 다음 행의 「잰 고장」이 되면 사슬이다. 3.1 과 3.2 는 대부분 그렇게 이어진다.
3.3 과 3.5 는 줄기가 여럿이라 행 첫머리에 줄기 이름을 적었다. 수치와 번호는 표 아래에 행마다 적었다.

10-22 ~ 10-23 에 Librarian 의 모델 호출이 Lane Add-on worker 로 옮겨 갔다. 원본이 이때 생겼다(#45093, #45324, #45325, #45337, #45338).
이 시기의 RFC 다섯은 원본을 들이지 않았다. 원본은 Lane Add-on 을 떼어 내는 설계 문서에서 왔다.
그 문서는 같은 호출을 되풀이하면 돈이 두 번 나가는 lane 을 먼저 보고 쓴 것이다.
규칙은 셋이다. 결과를 모르면 모델을 다시 부르지 않는다. 보내기 전에 의도를 적는 것도 이 규칙에 든다.
Memory 커밋은 맞는 receipt 가 있을 때만 한다. Keeper 하나에 끝나지 않은 frontier 는 하나다(#45338).

| 때 | 잰 고장 | 더한 장치 | 그 뒤에 잰 고장 |
| --- | --- | --- | --- |
| 10-05 ~ 10-06 | [되풀이] 끝나지 못한 턴의 atom 을 다음 턴들이 그대로 실었다 | [요청 이력 RFC][carries] 의 제안 셋 | 구현되지 않았다. 재시작은 범위 밖에 뒀고 11-06 에 끊긴 원본으로 돌아왔다 |
| 10-26 | [보관] history 원본이 쌓여 서버가 1시간 넘게 코어 6개쯤을 썼다 | [원본 옮기기 RFC][settles]. 끝난 원본을 archive 로 옮긴다(settle) | archive 가 비용이 됐다 |
| 10-27 | [보관] 살아 있는 힙의 70% 쯤이 원본 읽기였다 | [읽은 범위 RFC][holds]. 원본은 읽은 범위만 담는다 | 재는 중에 4MB 이상 범위가 모델에 닿지 못하는 것이 드러났다(#46398) |
| 10-27 ~ 10-29 | [크기] worker frame 보다 큰 한 턴이 pass 마다 거절된다 | [메시지 바닥 RFC][floor]. 메시지 하나에 원본 하나를 만들어 사슬로 잇는다 | 턴 하나의 비용이 메시지 수의 세제곱이었다 |
| 11-03 ~ 11-05 | [재시작] 사흘에 부팅이 45번이고 원본 29개가 끊긴 채 끝났다 | [RFC-0500][r0500]. 서버가 멈춰 끊긴 원본은 옮기고 다시 준비한다 | 원인이 `cut` 이면 여전히 선다 |

- [되풀이]. sangsu 가 9시간쯤에 토큰 13.3억 개를 썼다. 10-06 00:00 ~ 15:00Z 에 재시작이 11번이었다. 되풀이는 다른 RFC 가 고쳤다(#41398).
- [보관] 10-26. 11시간에 history 원본이 355개(1,400MB) 쌓였다. 같은 본문이 세 곳에 있었다.
  settle 은 #46244 다. gate 요청은 부모를 digest 로 가리킨다(#46247, hard cut).
  그 뒤 부팅이 3 ~ 5분 걸렸다(#46541). 11-05 에 archive 가 파일 24,912개, 18GB 였다(#48946).
  끝나지 않은 원본은 여전히 pass 마다 다시 검증했다(#51281).
- [보관] 10-27. 살아 있는 힙은 7 ~ 9GB 였다. gate 기록 하나가 30.7MB 였다. 출처는 `{count, digest}` 로 가리킨다(#46394, #46397, hard cut).
  RFC §7.1 에서 이미 읽은 이력이 1 ~ 20MB 일 때 pass 가 남기는 양이 166KB 가 됐다. 읽은 범위가 1MB 이면 3.33MB 가 남았다(#46399).
- [크기]. #46408 뒤로 생긴 고장이다. 사슬은 #46568 ~ #46690 이다.
  벤치(`1:5`, 16KiB 메시지, 부하 15 ~ 95)에서 약 330개짜리 턴이 7,200초에 134걸음까지 가고 끝나지 않았다(#46717).
  #46742, #46744 가 제곱으로 낮췄다. 재현하지 못한 의심 다섯이 열려 있다(#46716).
- [재시작]. 원본 29개는 `outcome_unknown`, 원인 `interrupted` 로 끝났다. Keeper 여섯의 admission 이 섰다. 11-05 에 대기 로그가 1,463줄이다.
  수리는 #49002, #49006 이다. host 가 공급자 허가를 기다리기 전에 `started` 를 적었다(#51250).
  바닥 걸음에는 끊긴 원본을 다시 준비하는 길이 없다. 선언이 바뀌면 원본이 멈춘다(#51278, 열림).

표 밖의 일도 있다.

- 기록 03 은 원본의 상태 전이를 49행으로 적었다. 서버 정지, 크기 거절, worker 교체, Memory 변경이 없어도 남는 행은 14개다.
  21행은 서버 정지, 충돌, 취소를 넘기려고 있다. 행마다의 분류는 그 기록의 판단이다.
- 원본마다 종류가 다르다. history, admission, gate, 바닥 걸음, 바닥 걸음의 gate 다. 종류마다 저장 자리, 찾기, 옮기기, 복구가 따로 있다.
  옮기기는 history 만 다뤘다. RFC-0500 은 admission 과 history 만 다뤘다.
- 메시지 바닥 RFC 는 4MB 를 넘는 턴이 "드물다"고 봤다. 그 경로를 열 층으로 나눠 만들었다.
  4MB 를 넘는 턴이 얼마나 있는지는 재지 않았다. 운영에서 돌았는지도 확인하지 못했다.

### 3.4 4기: fact 계약과 기다리는 원본 (11-06 ~ 11-16)

두 줄기가 같이 갔다. 하나는 끝나지 못하는 원본이다. 다른 하나는 답의 품질([RFC-0517][r0517])이다.
표는 첫 줄기만 담는다. 둘째 줄기는 표 아래에 적었다.

| 때 | 잰 고장 | 더한 장치 | 그 뒤에 잰 고장 |
| --- | --- | --- | --- |
| 11-06 ~ 11-10 | history 원본 둘이 재시작 사이에 걸려 두 Keeper 의 Memory 가 섰다 | [해소 RFC][unknown]. fence, 새 ID 의 자식 요청, 운영자가 부르는 API 를 뒀다(#50947, #50972) | 운영자가 불러야 풀린다. 원본과 자식과 해소 기록을 pass 마다 다시 읽는다 |
| 11-11 | 끝나지 않은 원본의 본문을 pass 마다 다시 검증한다(#51281) | [기다리는 pass RFC][waiting]. 기다리는 길은 본문을 읽지 않고 기록의 `summary` 만 읽는다 | 구현은 11-14 ~ 11-15 에 들어갔다. 그 사이 다음 행의 일이 있었다 |
| 11-12 ~ 11-13 | 운영자가 둘을 풀자 해소 쌍이 검증 시간 대부분을 썼다 | 기록끼리 계보를 견준다. 본문 없이 기다린다 | 기다리는 pass 는 싸졌다. 전체 pass 시간은 거의 그대로다 |
| 11-15 ~ 11-16 | worker 가 "없다"고 한 원본이 일곱 개 더 생겼다 | Memory lane 이 해소를 스스로 시작한다(#52476) | 선언이 바뀐 원본은 이 길에 들지 못한다(#51278) |
| 11-16 | 비용이 다른 갈래로 옮겨 갔다 | 11-17 에 `capacity_wait` 를 없앴다(3.5) | 3.5 로 이어진다 |

- 11-06 ~ 11-10. 의도는 적혔고 답은 적히지 않았다. worker 는 "없다"고 답했다.
  pr-updater 에 1,342턴, code-reviewer 에 2,424턴이 쌓였다(#50828). 경보 수는 0 이었다.
- 11-11. 7시간에 멈춘 원본 둘이 검증 시간의 59% 를 썼다.
- 11-12 ~ 11-13. 해소 쌍이 검증 시간의 84%(764.7 / 911.1초)를 썼다. pass 마다 부모를 6번, 자식을 3번, 해소 기록을 5번 읽었다.
  자식 둘은 22시간에 972번, 928번 거절됐다(`capacity_wait`, #51280).
  계보는 #51888, #51922, #51950, #51955 다. 본문 없는 기다림은 #52246, #52268, #52300 이다.
  기다리는 pass 는 p50 15ms 가 됐다. 전체 pass 의 p50 과 p90 은 685, 4,511ms 에서 630, 3,293ms 가 됐다.
- 11-15 ~ 11-16. 일곱 중 하나는 59.9MB 다. 푸는 길은 운영자가 부르는 API 하나였다. 불렀다는 기록은 찾지 못했다.
  e-masc-the-leader 의 요청 입력이 11-14 293,531 에서 11-16 788,607 토큰이 됐다. 그 Keeper 의 binding 이 선언한 context window 는 500,000 토큰이다(#50828 댓글, #52357).
  해소는 worker 가 "없다"고 답한 원본만 받는다. 선언이 바뀐 원본은 worker 에 묻기 전에 거절된다.
- 11-16. 거절된 본문을 pass 마다 다시 보냈다(#51280). gate 사슬을 읽을 때마다 다시 검증했다(#51655).

표 밖의 일도 있다.

- 두 원본은 "의도는 적혔고 답은 안 적힌" 틈을 296번, 601번 지났다. 크기 거절마다 의도를 새로 적었기 때문이다. 2026-11-04 ~ 11-10 에 서버 시작 로그가 81번이다.
- RFC-0517 은 판정 단어 대신 답이 남긴 Memory 로 답을 채점하게 했다. 같은 답의 점수가 0.838 에서 0.909 가 됐다. 심어 둔 낡은 상태 101개 중 80개가 Memory 에 남았다.
- 프롬프트는 2026-08-06 에 7,812바이트였다. RFC-0517 이 잴 때는 48,034바이트였다.
  정리한 프롬프트(#51190)에는 재지 않은 문단 셋이 섞여 들어갔다. 다음 날 측정에 쓴 프롬프트와 바이트가 같게 되돌렸다(#51325).
- 따로 학습한 모델 후보 A 는 기준 가운데 지연(G5)만 통과했다. 배포하지 않았다.
- 후보가 뒷받침하지 않아도 지우기와 합치기를 받게 넓혔다(#51823). admission 이 막혀 있어 운영에서 효과를 볼 수 없었다. 11-11 17:45 KST 뒤로 끝난 admission 요청이 없었다(#49910).
  Keeper 일곱의 admission 은 11-07 09:52Z 부터 pass 마다 `Unavailable` 로 끝났다. 후보 261개가 기다렸다(#51485). health 는 둘 다 보여 주지 않았다.

### 3.5 5기: 선언 교체와 거절 (11-11 ~ 11-17)

요청을 받는 쪽에서 일 셋이 한 주에 겹쳤다. 판정 서버가 거절했다. worker frame 이 찼다. worker 선언이 바뀌었다.

| 때 | 잰 고장 | 더한 장치 | 그 뒤에 잰 고장 |
| --- | --- | --- | --- |
| 11-16 | [판정] 판정 서버가 402 로 거절하자 gate 가 pass 마다 다시 묻고 기록을 하나씩 더했다(#52382) | [gate 대기 RFC][gatewait]. 거절 원인이 받는 서버의 상태면 새 시도를 만들지 않는다(#52392, #52399) | 재시작마다 원본 하나에 시도가 하나 생긴다 |
| 11-17 00:09 | [크기] frame 의 24% 이상인 요청 기록은 하나도 접수되지 못했다 | [읽기 폭 RFC][readwaits]. 목록을 여러 장으로 낸다. 접수는 요청 하나의 크기만 본다 | 0.2.6 의 목록이 RFC 의 크기 계산과 81바이트 어긋났다 |
| 11-17 17:02 ~ 17:11 | [배포] #52731 을 실은 서버가 옛 worker 와 9분 돌았다 | 배포 순서를 뒤집었다(#52762). 서버가 worker 패키지를 싣는 RFC 를 썼다(#52782) | 17:11 에 선언이 0.2.6 으로 바뀌었다. 위 원본들이 다음 행의 빠진 경우에 들었다 |
| 11-11 ~ 11-17 | [선언] 선언의 revision 이 바뀌면 끝나지 않은 원본이 pass 마다 거절된다(#51278) | [선언 교체 RFC][replaced] 와 PR 여섯 | worker 에 기록이 없는 `Dispatch_pending` 원본은 이 RFC 가 범위에서 뺀 경우다 |

- [판정]. gate 기록이 약 820개가 됐고 800개가 다시 물은 것이다. 기록이 15 ~ 71개인 Keeper 의 pass 가 50 ~ 303초 걸렸다. CPU 가 400% 를 넘었다.
  장치를 둔 뒤에도 받는 서버의 상태는 프로세스 메모리에 있다. 요청 자체가 거절되면 기록이 여전히 늘 수 있다(#52402, 열림).
  pass 마다의 사슬 검증은 범위 밖이다(#52389, 열림).
- [크기]. 그때 worker 는 기다리는 요청 전부를 답 하나(4,194,304B)에 실었다.
  987,955B(frame 의 24%) 이상인 요청 기록은 하나도 접수되지 못했다. 요청 기록 아홉이 3 ~ 392번 거절됐다.
  거절이 한 번 나면 원인이 무엇이든 다음 읽기를 한 턴으로 좁혔다.
  장치는 #52728, #52729, #52731 이다. `capacity_wait` 도 지웠다. 폭을 반씩 줄이는 부분은 구현되지 않았다.
  0.2.6 은 목록의 장마다 `next` 키 81바이트를 더 실었다. RFC §4.5 가 크기 한도를 넘지 않는다고 보인 계산이 그만큼 어긋났다. #52778 이 request id 커서로 바꿨다(0.2.7).
  명시적 admission 이 durable 걷기 뒤에서 1.5시간 넘게 기다린다(#52823, 열림).
- [배포]. 옛 worker 는 `capacity_wait` 로 답했다. 새 서버는 그 답을 읽지 않았다. 원본이 worker 기록 없이 `Dispatch_pending` 이 됐다.
- [선언]. 이 RFC 는 장애를 보고 쓴 것이 아니다. 코드를 따라가 미리 썼다. PR 은 #52621, #52622, #52674, #52695, #52608, #52684 다.
  실행을 막는 규칙은 있고 끝내는 규칙이 없었다. 11-17 에 Keeper 약 20개가 범위에서 뺀 자리에서 섰다(넘겨받은 관측값).

표 밖의 일도 있다.

- 선언 교체 하나에 장치 16개가 들어갔다. PR 일곱(위의 여섯과 #51343)에 +7,938줄, −1,069줄이다. 시험을 포함한 수다. 장치를 세는 기준은 기록 05 가 정했다.
- `Settled_if_replaced` 는 11-17 14:14 에 들어가(#52695) 20:20 에 빠졌다(#52608). 여섯 시간이다. RFC 본문은 그날 네 번 고쳤다.
- keeper-librarian worker 는 약 26시간에 revision 다섯을 냈다. 0.2.3-oversize, 0.2.4, 0.2.5, 0.2.6, 0.2.7 이다. 넷이 크기나 capacity 처리를 바꿨다.
  revision 을 적용할 때마다 선언 교체가 된다. 크기를 고치는 일이 교체를 부르고, 교체 규칙은 크기 장치에 예외를 둬야 했다.
- 하루에 배포 순서가 셋이었다. 서버 먼저, worker 먼저, 서버를 멈추고 0.2.7 이다.
- Keeper 약 20개라는 수는 넘겨받은 관측값이다(1.4). 원본 하나하나가 어디서 왔는지는 확인하지 못했다(9절).

## 5. 계속 깨진 가정

RFC 들이 적지 않고 기댄 가정 여섯이다. 가정마다 깨진 근거와 횟수를 적는다. 횟수는 기록 01 ~ 05 가 적은 사건을 센 것이다.

### A1. pass 하나가 판정, 커밋, 진행의 단위다

- 한 곳이 실패하면 pass 전체를 어떻게 할지 다시 정해야 한다. 기록 01 은 그런 부분 실패를 다섯 가지로 적었다.
  답의 한 곳이 틀렸다. 판정자가 내려갔다. 쓰기가 실패했다. 서버가 재시작했다. 선언이 바뀌었다.
- 답의 한 곳: 거절 517건(08-29). 실수 하나가 맞게 적은 부분까지 버렸다.
- 쓰기: pass 758개가 Memory 의 앞 상태가 달라져 쓰지 못했다(09-03, #32871). pass 가 Memory 전체를 다시 썼기 때문이다.
- 판정자: 실패 정책을 세 가지로 바꿔 가며 정했다(09-21, 09-22, 09-28). 마지막 정책은 pass 를 통째로 미룬다. 11-16 에 판정 서버가 거절하는 동안 Memory 정리가 섰다.
- 그때마다 메우는 층이 하나 더 붙었다. 엄하게 한 때와 느슨하게 한 때는 7.1 에 적었다.

### A2. 보낸 요청은 반드시 타입 있는 끝 결과에 닿는다

- 이 가정 위에서 "결과를 모르면 모델을 다시 부르지 않는다"는 규칙을 Librarian 에 적용했다. 이 규칙이 온 곳은 3.3 에 적었다.
- 기록 03 은 끝 결과에 닿지 못한 원본을 여섯 부류로 적었다.
  먼저 나온 둘은 frame 보다 큰 한 턴(10-27)과 서버 정지로 끊긴 호출(11-06)이다. 뒤의 넷은 바뀐 선언, 끊긴 호출 `cut`, worker 의 "없다"(`worker_absent`), 보낸 뒤 결과를 찾을 수 없는 것(`missing_after_dispatch`)이다.
- 부류마다 RFC 나 PR 묶음이 하나씩 들었다. 규칙에 예외를 세 번 뒀다. RFC-0500, 해소 RFC, 11-17 의 선언 교체 PR 들이다.
- 원본 상태 표 49행 중 21행이 서버 정지, 충돌, 취소를 넘기는 행이다. 기록 03 은 그 행들을 이 규칙에서 온 것으로 읽었다. 확신은 중간이라고 적었다.

### A3. Keeper 마다 차례로 읽는 reader 하나가 번호 붙은 이력을 따라잡는다

- 번호: 이력의 번호가 바뀐다. clear, 버전 교체, 읽지 못하는 checkpoint, purge, 수리, trace 재생성이 번호를 바꾼다. 09-22 의 purge 가 F8 이다.
- 끊을 자리: 모든 턴이 턴 끝 줄을 남기지 않는다. #37102 는 2026-09-19 부터 11-17 23:11 KST 까지 열려 있었다. 09-22 goo-yang-bong 의 log 159줄 중 134줄에 atom 위치가 없었다.
- 속도: 첫 측정(09-17)에서 커밋 484번에 덮어쓰기가 4,910번이었다. 11-16 에는 시간당 90.3턴에 답 4.9개였다. 두 값은 창이 다르다(2.6).
- 한 대기줄에서 앞이 막혀 뒤가 굶는 일이 세 번 났다. 09-22 에 continuity 가 선 채 durable 만 갔다. 09-23 에 durable 이 continuity 뒤에서 굶었다. 11-17 에 admission 이 durable 뒤에서 기다렸다.

### A4. 본문을 크기 한도가 있는 통로로 날라도 된다

- worker 가 답 하나에 실을 수 있는 크기는 4,194,304B 다. 11-17 전에는 목록이 답 하나였다. 기다리는 요청 전부가 그 안에 들어야 했다.
- `capacity_wait` 는 2026-10-22 에 들어와(#44911) 11-17 에 빠졌다(#52731).
- 11-17 에 987,955B 이상인 기록은 하나도 접수되지 못했다. 11-15 20:00 ~ 22:42 KST 의 거절 627번에 본문 크기를 곱하면 약 7.3GB 를 다시 읽은 셈이다.
- 서버는 그 본문을 이미 갖고 있다. 11-16 에 본문 910개, 325MB 였다. worker 는 그 본문을 받아 다시 넘기기만 한다(기록 05 의 분석).
- 크기 주제의 fix 가 12주에 31개다(2.2).

### A5. 커밋 경로의 바깥 판정자는 늘 답한다

- 생명주기 RFC(09-18)는 판정만 하는 모델을 운영 경로에 두지 않는다고 정했다. 사흘 뒤 absorb gate(09-21)가 Jev 를 그 경로에 뒀다.
- 깨진 것은 두 번 기록됐다. 11-15 에 닫힌 #52304 는 402 가 46시간 이어졌다고 적었다. 11-16 의 #52382 가 F5 다.
- 판정자가 답할 때는 합치기 대부분을 거절했다. 09-23 에 흡수율이 16% 였다.

### A6. worker 의 "없다"는 믿을 수 없다

- Keeper 는 보낸 뒤 worker 가 "없다"고 하면 결과를 모르는 것으로 둔다. 다시 보내지 않는다.
- 기록 04 가 worker 코드를 읽었다. worker 는 받은 요청을 답하기 전에 fsync 한다. 같은 id 와 digest 에는 같은 상태를 돌려준다. 기록을 지우지 않는다. 늦어도 2026-10-23 부터 그랬다.
- 그러면 같은 저장소의 "없다"는 "접수한 적 없다"다. 요청이 닿지 않았거나, 옛 revision 이 저장하지 않던 `capacity_wait` 로 답한 경우다. 이것은 기록 04 의 분석이다. 저장소가 그대로였다는 것을 Keeper 가 확인할 길은 지금 없다.
- 다시 보낼 때 같은 바이트가 되지도 않는다. 요청이 Memory 의 revision 과 fact 를 품기 때문이다. 그래서 새 ID 가 필요했고, ID 가 둘이라 fence 가 필요했다.
- worker 가 "없다"고 답한 원본은 두 번 생겼다. 둘(11-06 ~ 11-07)과 일곱(11-15 ~ 11-16)이다.
  11-17 에 선 Keeper 약 20개는 다른 부류다. 선언이 바뀐 원본은 worker 에 묻기 전에 거절돼 "없다"에 닿지 않는다(기록 04).
  그 원본들이 worker 저장소에 기록이 없었으리라는 것은 기록 05 의 추정이다.

## 6. 지킬 불변식

  앞의 둘은 Memory 가 지켜야 할 사실로 봤다. 세 번째는 비용 규칙을 물려받은 것으로 봤다. 확신은 중간이라고 적었다.

## 7. 뿌리 둘

3 ~ 5절의 사슬을 거슬러 가면 결정 둘에 닿는다. 이것은 이 조사가 읽은 것이다. RFC 가 그렇게 적은 것은 아니다.

### 7.1 pass 하나가 판정, 커밋, 진행의 단위였다

- pass 는 모델에 한 번 묻고, 답 전체를 검사하고, Memory 를 쓰고, 위치를 옮긴다. 넷이 한 덩어리다. 하나가 실패하면 넷이 같이 선다(A1).
- 3.1 의 행마다 이 덩어리를 엄하게 하거나 느슨하게 했다. 엄하게 하면 진행을 잃었다. fact 목록(F2, F3)과 판정 실패 때 범위를 통째로 남기는 정책(F5)이 그렇다.
  느슨하게 하면 지식을 잃거나 Memory 가 불었다. 합치지 못해도 claim 을 적용한 것(F4 의 사본)이 그렇다.
- 3.2 에서는 진행이 pass 에 묶였다. pass 하나가 범위 하나를 읽고, 그때마다 fact 전부를 싣는다. 11-16 의 code-reviewer 한 턴 요청 하나는 296,740B 였고 그중 217,200B 가 Memory 였다(F12).
- 일이 다른 pass 셋(durable, continuity, admission)이 Keeper 의 한 대기줄에 선다. 앞의 pass 가 끝나야 뒤가 돈다(F7).
- 이 읽기의 확신 수준은 기록에 없다. A1 의 사건은 기록 01 에 날짜와 번호로 있다. pass 를 쪼갰을 때 같은 실패가 나지 않는지는 재지 않았다.

### 7.2 "결과를 모르면 모델을 다시 부르지 않는다"를 제안만 하는 호출에 적용했다

- 이 규칙이 온 곳은 3.3 에 적었다.
- Librarian worker 는 제안만 한다. 자격 증명, 입력 고르기, gate, Memory, 위치, ACK 는 host 가 가진다.
  기록 03 과 04 는 한 번만 일어나야 하는 효과를 Memory 커밋 하나로 읽었다. 그 읽기로는 커밋이 앞 상태 견주기와 범위 receipt 로 이미 막혀 있다.
  효과가 나가는 경로를 모두 따라가 본 것은 아니다(H1).
- 다시 물을 수 없으니 끝나지 못한 원본은 남아야 한다. 남은 원본이 Keeper 의 대기줄을 세운다(F9).
  원본을 끝낼 까닭을 원인마다 따로 증명해야 했다. `interrupted`, worker 의 "없다", `cut`, 바뀐 선언이다(A2, F11).
- 남은 원본은 pass 마다 다시 검증됐다(F10). 바닥 사슬은 메시지마다 원본을 하나씩 만들었다(F6 의 일부).
- 확신은 중간이다. 기록 03 은 효과가 나가는 경로를 모두 따라가지 않았다고 적었다.

### 7.3 실패마다 어느 뿌리가 닿는가

「주로」는 그 뿌리가 없었으면 그 실패가 그 모양으로 나지 않았다는 읽기다. 「일부」는 그 뿌리가 실패를 키웠다는 읽기다. 둘 다 잰 값이 아니고 판단이다.

| 실패 | 뿌리 1 | 뿌리 2 | 두 뿌리 밖 |
| --- | --- | --- | --- |
| F1 놓친 턴 | 일부. 읽는 범위가 pass 빈도에 묶였다 | | 메시지 72개 한도와 대기 칸 하나 |
| F2, F3 목록 계약 | 주로 | | |
| F4 합칠 때 잃는 지식 | 일부. 거절돼도 claim 을 적용했다 | | 합치기 자체가 지식을 잃는다. 모델과 계약의 품질이다 |
| F5 판정자의 거절 | 주로. 판정 실패가 pass 를 통째로 세웠다 | | 커밋 경로의 바깥 서버(A5) |
| F6 크기 | 일부 | 일부. 걸음마다 원본, 거절마다 새 의도 | 본문을 worker frame 으로 나른다(A4) |
| F7 한 대기줄에 선 일 | 주로 | | |
| F8 번호 위치 | | | 바뀌는 이력을 번호로 가리켰다(A3) |
| F9 재시작이 남긴 원본 | | 주로 | 재시작이 잦았다. 사흘에 부팅 45번이다 |

| F11 선언 교체 | | 주로. 끝내는 규칙이 필요한 까닭이다 | 권한과 보관이 서로 다른 값을 본다 |

| F13 보이지 않음 | | | 커밋만 세는 계측 |
| F14 두 번 보냄 | 일부 | | 같은 이력을 읽는 소비자가 둘이다 |

- 추정이다. 판정자를 커밋 경로에서 빼면 F5 는 없어질 것으로 읽는다. 대신 F4 가 돌아올 수 있다. 10-30 ~ 11-06 에 판정자는 585쌍 중 110쌍을 거절했다. 지식을 잃는다는 까닭이었다(H6).
- 추정이다. 이 읽기로는 두 뿌리를 다 고쳐도 F4, F8, F13, F15 와 F6 의 frame 은 남는다. 재설계는 이것들을 따로 다뤄야 한다.

## 8. 재설계가 확인할 가설

아래 아홉은 재설계가 확인할 질문이다. 결론이 아니다. 「버리게 하는 것」이 나오면 그 가설을 버리거나 고친다.

| 가설 | 물을 것 | 기댄 근거 | 버리게 하는 것 | 아직 모르는 것 |
| --- | --- | --- | --- | --- |
| H1 | Librarian 의 모델 호출은 다시 물어도 되는가. 그러면 앞 상태를 견주는 커밋과 범위 receipt 가 원본, fence, 계보, 해소를 대신하는가 | 7.2, A2 | host 밖으로 효과가 나가는 경로가 하나라도 있다. 다시 묻는 비용이 받아들일 수 없는 크기다 | |
| H2 | 요청을 (범위, Memory 의 앞 상태, 선언)의 함수로 만들고 보내기 전에 나눠 크기를 정할 수 있는가 | F6. 10-27 의 durable 요청 897개는 최대 2.72MB 였다 | 턴 하나나 Memory 만으로 context window 를 넘는 Keeper 가 있다 | 4MB 를 넘는 턴의 빈도는 잰 적이 없다 |
| H3 | worker 경계로 본문 대신 참조만 넘기거나 대기열을 서버가 가지면 frame 거절이 없어지는가 | A4. 서버가 본문을 이미 갖고 있다 | 같은 규약을 쓰는 다른 Add-on 때문에 바꾸지 못한다 | frame 이 공급자의 context window 보다 먼저 걸리는지는 잰 값이 없다 |
| H4 | 명시적 admission 과 뒤에서 읽는 일을 다른 대기줄로 가르거나 타입 있는 순위를 주면 서로 굶기지 않는가 | F7 | 두 대기줄이 같은 Memory 를 쓰면 한쪽의 커밋이 다른 쪽의 쓰기를 실패하게 한다. 09-03 까지 pass 758개가 Keeper 의 쓰기와 겹쳐 그렇게 실패했다 | |
| H5 | 선언 교체에 따로 장치가 필요 없는가. 요청의 digest 에 선언을 넣는다. 옛 요청의 답은 기록하고 버린다. 그 범위를 다시 묻는다 | F11 | 버리는 답이 많다. 11-17 까지 약 26시간에 revision 이 다섯 나왔고 durable 시도 하나에 중앙값 717.5초가 든다. I4 의 "받은 답은 버리지 않는다"와도 부딪친다 | |
| H6 | 바깥 판정자를 커밋 경로에서 빼거나 조언으로만 쓸 수 있는가 | F5, A5 | 판정 없이 합친 Memory 가 지식을 잃는다(F4). 운영자가 정할 일이다 | |
| H7 | 읽은 위치를 atom 번호 대신 바뀌지 않는 턴 id 로 적으면 purge 를 넘기는가 | F8, A3 | id 를 받지 못하는 턴이 남는다. #38827 이 열려 있다 | #37102 는 history 줄의 `turn_ref` 로 풀렸다며 11-17 23:11 KST 에 닫혔다. 그 `turn_ref` 가 purge 를 넘기는 id 인지는 확인하지 않았다 |
| H8 | 공용 Lane Add-on 층이 호출을 다시 물어도 되는 것과 한 번만 해야 하는 것으로 타입을 가를 수 있는가 | 7.2 | 한 호출이 두 성질을 다 갖는다. 다시 물어도 된다고 적은 호출에서 효과가 나간다 | |
| H9 | Memory 내용과 원문 턴은 남기고 Librarian 의 장부만 새로 시작할 수 있는가 | 운영자 결정(hard cut, fresh state) | 장부 없이는 Memory 가 어느 턴까지 읽은 결과인지 알 수 없다. Memory 내용도 끊을지는 운영자가 정할 일이다 | |

- H1 과 H8 은 근거가 같다. 기록 03 의 "제안만 한다"는 읽기가 틀리면 둘 다 버린다.
- H2 는 2026-10-06 의 운영자 결정과 닿는다. 그 결정은 바이트 숫자로 미리 자르지 않는다는 것이었다. 선언된 context window 는 맞춘 상수가 아니지만 RFC 가 따로 정해야 한다(기록 05).
- H3 을 읽기 폭 RFC 는 이미 한 번 검토하고 받지 않았다. 위 표의 H3 행에 적은 두 가지가 그 RFC 가 든 까닭이다.

## 9. 한계

**재지 않은 것**

- 운영 수치는 이 조사가 다시 재지 않았다. RFC 와 이슈가 그때그때 다른 조건에서 잰 값이다.
- 시간당 90.3턴과 답 4.9개는 창이 다르다(2.6). 종합 기록(기록 01 ~ 06 을 한 장으로 묶은 작업 기록)은 이 둘을 18배로 적었다. 이 문서는 비율을 적지 않았다.
- 09-18 의 pass p50 21초와 11-16 의 717.5초가 같은 것을 잰 값인지 확인하지 못했다.
- 턴 끝 줄이 빠지는 빈도는 잰 적이 없다. 바닥 사슬이 운영에서 돌았는지도 모른다. RFC-0456 과 RFC-0500 을 배포한 뒤의 측정은 찾지 못했다.
- 11-17 에 선 원본이 어디서 왔는지 하나씩 보지 않았다. 17:02 ~ 17:11 의 9분, 그 전의 "없다" 원본, 잃은 답 가운데 어느 것인지 모른다.
- A6 은 worker 저장소가 그대로였다는 전제에 기댄다. 그 저장소가 컨테이너 재시작과 정리 도구를 넘겨 남는지 확인하지 못했다.

**기록끼리 다른 곳**

- 코드 줄 수. 종합 기록은 `keeper_librarian_*` 를 69파일, 23,876줄로 적었다. 기록 06 은 `.ml` 69개를 23,873줄로 셌다. 이 문서는 기록 06 을 따랐다.
- 바닥 사슬의 비용. 기록 02 는 pass 하나의 비용을 제곱으로, 기록 03 은 턴 하나의 비용을 세제곱으로 적었다. pass 가 메시지 수만큼 도니 두 값은 맞는다. #46742, #46744 뒤로 턴 하나가 제곱이 됐다.
- 읽은 커밋. 기록 06 은 `fa5aead0d999` 에서 셌다. 기록 02 ~ 04 를 쓰는 동안 main 이 `a3c3c71ffc22` 가 됐다. 종합 기록은 `0542d471eedf` 를 적었다. 읽은 RFC 파일은 그 사이 바뀌지 않았다.
- 402 의 길이. 기록 01 은 #52304 의 46시간을 적었다. 기록 05 는 gate 대기 RFC §1.1 의 「02:06~10:13Z」를 옮겼다. 뒤의 값은 같은 절의 다시 채운 시각(약 02:15Z)과 맞지 않는다. 오타일 수 있다.
- 받은 답. 기록 05 의 불변식과 가설 H5 가 맞지 않는다(6절 I4).

**찾는 조건에 달린 수**

- RFC 수. 이 문서는 기록 01 ~ 05 가 전문을 읽었다고 적은 22개(10, 1, 5, 3, 3)만 센다.
- 커밋 785개는 경로 넷과 제목의 `librarian`, `사서` 로 골랐다. 이슈 577개와 PR 1,912개는 제목이나 본문에 `librarian` 이 있는 것이다. 상관없는 것이 섞였는지 하나씩 보지 않았다.
- fix 주제는 정규식으로 붙였다. 오탐 비율은 재지 않았다. ±10% 는 추정이다. 67개는 어느 주제에도 들지 않았다.
- 판단으로 센 수가 있다. 상태 표 49행의 분류(14, 21), 선언 교체의 장치 16개, 끝나지 못한 원본의 부류 여섯이다. 세는 기준은 기록 03 과 05 가 정했다.
