# RFC — 자동 병합 worker 가 API 한도 안에서 돈다

- Status: **D1·D2 구현.** 운영자가 2026-11-12 에 §6-1 을 "더한다"로 골랐다. D3 은 구현하지 않았다.
- 대상: `.github/workflows/approval-merge-request.yml`, `.github/workflows/approval-auto-merge.yml`,
  `scripts/review/approval-auto-merge.py`.
- 관련 이슈: #51479(한도에 걸린 worker 가 runner 를 쥐고 기다린다), #51465(같은 계정의 반복 승인).

## 0. 요약

- 자동 병합 worker 는 리뷰·PR 이벤트마다 한 번 돈다. 바쁜 시간에는 한 시간에 588번 돈다.
  worker 가 쓰는 Actions 토큰의 REST 한도는 한 시간에 1,000회다.
- 한도가 차면 worker 는 한도가 풀릴 때까지 runner 를 쥔 채 기다린다. 그동안 required check 가 시작하지 못하고,
  승인을 받은 PR 이 병합되지 않는다.
- worker 가 포기하지 못하는 이유는 이벤트 하나가 그 병합의 유일한 기회이기 때문이다.
- 이 RFC 는 세 가지를 정한다.
  - D1: 병합 보장을 이벤트에서 떼어, 정해진 주기의 확인 한 번에 둔다.
  - D2: worker 는 한도에 걸리면 기다리지 않고 끝난다.
  - D3: worker 는 병합 범위 전체를 질의 한 번으로 읽는다.

## 1. 지금 일어나는 일 (측정)

모든 시각은 UTC 다.

| 하루에 main 에 들어간 커밋 | 평균 344, 최고 547 | 같은 기간, `git log origin/main` |

| 주별 main 커밋 | 1,041 / 1,670 / 958 / 2,105 | 10-12 주부터 네 주 |

### 1.2 worker 가 도는 횟수

| 2026-11-09 | 4,970 | 488 |

시간별 `total_count` 24개를 더한 값이다. 하루 단위 조회는 2,500 에서 끊긴다.
요청 실행마다 `Approval auto-merge` 가 하나씩 따라 돈다.

### 1.3 worker 한 번이 쓰는 REST 호출

2026-11-12T02:30Z 에 `gh` 호출을 세는 래퍼를 끼우고 worker 를 `--dry-run` 으로 돌렸다.

| 경우 | 호출 수 |
|---|---|
| 닫혔거나 Draft 라서 바로 보류 | 2 ~ 4 |
| 병합 범위가 main 을 향하지 않아 보류 | 8 |
| 두 층 스택, 병합 가능 | 16 |

`--dry-run` 은 Auto-merge 예약 읽기와 병합 요청을 건너뛴다. 실제 실행은 이보다 많다.
병합 가능한 범위에서는 층마다 PR 한 번, 리뷰 목록 두 번, 범위 스냅샷 두 번에 한 번씩을 읽는다.
층 수를 L 이라 하면 약 5L + 5 회다(두 층에서 15, 측정값 16).

2026-11-12T02:26Z 에 열린 PR 123개를 base 브랜치로 이었다.

| 이어진 길이 | 묶음 수 |
|---|---|
| 1 | 17 |
| 2 | 3 |
| 4 | 1 |
| 12 | 1 |
| 84 | 1 |

열린 PR 123개 중 96개가 길이 12 이상인 묶음에 있다. 이 길이는 base 브랜치를 따라간 값이고
Native Stack 하나의 크기와 같지 않을 수 있다.

### 1.5 한도가 찼을 때

- 2026-11-12T02:05Z: `Approval auto-merge` 28개가 진행 중이었다. 모두 01:35:24Z ~ 01:35:41Z 에 시작했다.
  평소 worker 는 중앙값 31초에 끝난다. 같은 시각 `Approval merge request` 56개, `PR type-check` 11개,
  `Changelog fragments` 14개가 대기 중이었다.
- worker 최근 100회 중 34회가 실패로 끝났다. 실패 12회의 로그를 읽었고, 6회가 요청 artifact 를 받다가
  `API rate limit exceeded for installation` 으로 끝났다.
- `scripts/review/github-get.py` 의 `wait_for_quota` 는 `deadline` 이 없으면 서버가 알려 준 시각까지 `sleep` 한다.
  `deadline` 은 `follow()` 안에서만 정해진다. 진행 중인 실행의 로그는 읽을 수 없어서,
  28개가 그 `sleep` 안에 있었다는 것은 코드와 시작 시각으로 추정한 것이다.

### 1.6 이미 들어간 것

- #51459: 병합 판정을 바꿀 수 없는 이벤트(Draft, 병합 없이 닫힘, 제목·본문 수정, 리뷰 수정)에는 요청 job 이 건너뛴다.
  병합 뒤 28분 동안 요청 67회 중 47회가 건너뛰었다.
- #51475(리뷰 중): required check `changes` 가 REST 호출 없이 바뀐 파일을 읽는다.

둘 다 호출 수를 줄인다. §2 의 구조는 그대로다.

## 2. 왜 이렇게 되는가

1. **호출 수가 이벤트 수에 비례한다.** 한 시간 588회에 한 번당 2 ~ 16회면 1,176 ~ 9,408회다. 한도는 1,000회다.
2. **스택에서는 층 수의 제곱이다.** 층마다 온 이벤트가 worker 를 하나씩 깨우고, 깨어난 worker 는 범위 전체를 읽는다.
   12층 스택의 모든 층이 승인을 받으면 worker 한 번이 약 65회를 쓴다.
3. **이벤트 하나가 유일한 기회다.** 마지막 승인의 worker 가 실패하면 그 PR 은 다음 이벤트가 올 때까지 병합되지 않는다.
   그래서 worker 는 한도에 걸려도 끝나지 못하고 기다린다.

## 3. 설계

### D1. 병합 보장은 주기적인 확인이 한다

- 정해진 주기로 도는 job 하나가 "병합 조건을 채웠는데 병합되지 않은 범위"를 찾는다.
- 찾는 방법은 열린 PR 과 리뷰 상태를 한 번에 읽는 GraphQL 질의다. 호출 수가 PR 수에 비례하지 않는다.
- 찾은 범위마다 지금의 worker 입장 판정과 병합 요청을 그대로 쓴다. 판정 규칙은 바꾸지 않는다.
- 이벤트로 깨어나는 worker 는 남긴다. 한도에 여유가 있을 때는 지금처럼 승인 직후에 병합된다.
- 주기는 `Main minimal build` 가 이미 쓰는 30분이다. 새 숫자를 고르지 않는다.

### D2. worker 는 한도에 걸리면 끝난다

- 입장 판정 단계에도 `deadline` 을 둔다. 한도에 걸리면 `rate_limited` 를 기록하고 끝난다.
- 병합 요청을 이미 접수한 뒤의 추적(`follow()`)은 지금 그대로 둔다. 접수한 요청의 UUID 는 놓치면 안 된다.
- D1 이 없으면 D2 를 넣지 않는다. 놓친 이벤트를 주울 것이 없으면 승인받은 PR 이 멈춘다.

### D3. worker 는 범위 전체를 한 번에 읽는다

- 병합 범위의 모든 층에 대해 PR 상태, head, base, 리뷰 목록을 GraphQL 질의 한 번으로 읽는다.
- 입장 판정의 "읽는 동안 바뀌지 않았는지" 확인은 같은 질의를 한 번 더 보내 두 답을 비교한다.
- 호출 수가 약 5L + 5 에서 상수로 바뀐다.

## 4. 넣지 않는 것

- **PR 번호별 concurrency group**: 같은 PR 의 worker 는 하나로 줄지만, 서로 다른 PR 의 worker 가 한꺼번에
  기다리는 것(§1.5)은 그대로다. §2 의 1 ~ 3 을 하나도 없애지 않는다.
- **다른 토큰(PAT, GitHub App)으로 한도 늘리기**: 한도가 다섯 배가 되어도 §1.1 의 추세면 다시 찬다.
  비밀값 하나가 병합 권한을 갖게 된다.
- **이벤트를 더 거르기만 하기**: #51459 가 요청의 70%를 걸렀다. 남은 30%로도 한 시간 176회이고,
  병합 가능한 스택이 섞이면 한도를 넘는다.

## 5. 확인하는 방법

구현 전에 고정한다. 구현하는 쪽이 바꾸지 않는다.

| 재는 것 | 지금 | 목표 |
|---|---|---|
| 30분 넘게 진행 중인 `Approval auto-merge` 실행 수 | 28 (2026-11-12T02:05Z) | 0 |
| `API rate limit exceeded for installation` 으로 끝난 worker 실행 | 표본 12회 중 6회 | 0 |
| 승인 조건을 채운 뒤 병합까지 걸린 시간의 최댓값 | 재지 않음 | 주기 한 번 + worker 한 번 |
| 병합 가능한 12층 범위에서 worker 한 번의 호출 수 | 약 65 (식으로 계산) | 층 수와 무관 |

셋째 값은 지금 재지 않았다. D1 을 넣기 전에 먼저 잰다.

## 6. 운영자가 고를 것

1. **D1 의 주기 실행을 더할지.** 헌법은 운영자 요청 없이 주기 CI 를 더하지 않는다.
   권하는 쪽은 더하는 것이다. 대가는 하루 48회의 짧은 실행이고, 한도가 찬 시간에는 병합이 최대 30분 늦는다.
   더하지 않으면 D2 도 넣을 수 없고 §1.5 가 그대로 남는다.
2. **D3 을 D1 보다 먼저 할지.** 권하는 쪽은 D1, D2, D3 순서다. D1 과 D2 가 runner 를 쥐는 문제를 먼저 없앤다.
   D3 은 읽기 경로를 다시 쓰는 일이고, `scripts/review/test_approval_auto_merge.py` 의 가짜 GitHub 가
   REST 경로에 맞춰져 있어 시험도 같이 바뀐다.
3. **GraphQL 한도.** Actions 토큰의 GraphQL 한도가 REST 한도와 따로 계산되는지, 한 시간에 얼마인지는
   확인하지 않았다(확인 필요). D1 과 D3 은 이 값에 기대므로 구현 전에 공식 문서와 실제 응답 헤더로 확인한다.

### 6.1 고른 것과 확인한 것 (2026-11-12)

- §6-1: 운영자가 주기 실행을 더하기로 했다. `.github/workflows/approval-merge-sweep.yml` 이 매시 22분과 52분에 돈다.
- §6-2: D1 과 D2 를 같은 PR 로 넣었다. D2 만 먼저 들어가면 한도에 걸려 끝난 worker 의 PR 을 주울 것이 없다.
- §6-3: GitHub 문서는 Actions 의 `GITHUB_TOKEN` GraphQL 한도를 저장소마다 한 시간 1,000점으로 적고,
  REST 한도와 따로 센다고 적는다(`docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api`,
  2026-11-12 확인). 점수는 connection 요청 수를 100으로 나눈 값이다.
  열린 PR 51개를 읽는 질의를 사용자 토큰으로 한 번 보냈고 1점이 줄었다. 한 번의 확인은 PR 100개마다 약 1점을 쓴다.
  Actions 토큰으로 잰 값은 확인 실행의 summary 에 남는 `quota_before`·`quota_after` 로 본다.

D1 의 확인이 worker 를 돌리는 범위는 다음과 같다.

- main 을 base 로 하고, 서로 다른 두 계정이 지금 head 를 승인했고, Draft·`release/*`·충돌 상태가 아닌 PR.
- 그 PR 위에 쌓인 열린 PR 이 있으면 전부 같은 조건을 채워야 한다. 하나라도 못 채우면 그 PR 이 Native Stack 인지
  REST 한 번으로 읽는다. Stack 이면 건너뛰고, 아니면 그 PR 만 worker 에 넘긴다.
- Auto-merge 예약이 걸린 단독 PR 은 건너뛴다. GitHub 가 직접 병합한다.

확인의 비용은 고정된 GraphQL 질의와, 범위마다 worker 한 번이다. 승인은 받았는데 required check 가 실패한 스택은
확인 때마다 worker 가 다시 읽는다. 이런 스택이 몇 개인지는 재지 않았고, summary 의 `candidates` 로 본다.

## 7. 확인하지 못한 것

- §1.3 의 5L + 5 는 두 층 측정값 하나와 코드에서 센 값이다. 12층 이상에서 재지 않았다.
- §1.5 의 28개가 한도 대기 중이었다는 것은 추정이다.
- push(`synchronize`) 이벤트에 worker 가 꼭 돌아야 하는지 확인하지 않았다. push 는 GitHub 가 기존 승인을 해제하므로
  병합할 것은 없다. Auto-merge 예약을 다시 걸어야 하는 경우가 있는지는 읽지 않았다.
