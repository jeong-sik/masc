# RFC-0477 — 승인된 관측은 저널에 있고, 확정된 사실은 흡수 상태다

## 0. 한 줄 요약

경계(Resume·Start·재생·tool-reply·중단·재시작·내보내기)를 넘을 때 승인된 관측이 사라지는
버그 클래스를 줄이기 위해 도메인별 기록 경계와 컴파일러가 강제하는 계약을 제안한다.
새 공용 런타임은 제안하지 않는다.

## 1. 문제

초안 작성 때 최근 500 커밋의 fix 202건 중 29건이 "retain/preserve/keep X across Y"
유형이라는 집계를 인용했다. 현재 근거 묶음에서 당시 기준 커밋·정규식·29건 목록을
찾지 못해 이 수와 비율을 재현하지 못했다. 29/202 ≈ 14.4%는 당시 주장에 대한 산술값일 뿐, 검증된 기준선이
아니다. 빠진 원자료를 찾거나 새 감사로 다시 정하기 전에는 철회 판정에 쓰지 않는다.

별도 재현 가능한 탐색은 기준 `3fd6e38bd224f55f7901095c563637d4cf8b01fa`에서 500개 중
fix 제목 177건과 retain/preserve/keep 제목 후보 48건을 찾았다. 이는 원래 집계의
재현이 아니다. 키워드 후보에는 화면 배치 등 이 클래스 밖의 수정도 들어가고, 키워드가
없는 수정은 빠진다. 방법·제한·후보 목록은
[근거 README](../evidence/2026-10-29-observation-retention-review/README.md)에 있다.

초안에서 사례로 인용한 8건(원래 29건 표본의 대표인지는 확인하지 못했다.
개별 분류에는 추가 감사가 필요하다):

| 커밋 | 무엇이 어디서 사라졌나 |
|---|---|
| #45853 | 태스크 승인·거절 관측의 상관 키가 tool reply 뒤 재조립에서 |
| #45791 | 현재 Goal 판정·측정이 tool 요청과 held-session Resume에서 |
| #45950 | reasoning 전문이 스트리밍 경계와 재생에서 |
| #46327 | provider retry 관측이 turn 실패 처리에서 가려짐 |
| #46132 | 실행 소유권이 중단에서, 원본 판정이 회복 경로에서 |
| #46168 | 선언된(부팅 전) Apple guests가 서버 재시작에서 |
| #46169 | 확인된 저장이 잠금 해제 실패 뒤 덮어짐 |
| #46098 | 브라우저 읽기·snapshot 활동 미기록과 TUI 갱신 부재. 새 갱신은 선택·대기 중 읽기를 보존해야 함 |

초안 작성 당시 #46595는 열려 있었다. 제어기 실패 뒤에도 원본 작업 권한·취소·결과를
유지하는 사례이며, 2026-10-29 04:04 UTC에 병합됐다. `Committing_launch` 추가는 §8
감사 후보지만, 원래 목록을 복원하지 못했으므로 "30번째"라는 순번은 검증하지 못했다.

사이트별 수정이 관측 종류와 경로마다 반복될 수 있다는 것이 이 제안의 문제의식이다.
각 수정이 정말 그 비용 구조에서 비롯됐는지는 §8의 개별 감사가 필요하다.

## 2. 재분류

초기 분류(재구축/중단/동시쓰기/새로고침 4개)에 대한 외부 리뷰 5건(§7)을 참고해
이 초안은 두 원인과 프레이밍 하나를 제안한다. 리뷰마다 분류와 처방이 다르므로 공통된
확정 판정으로 보지 않는다.

- **I1 저널 갭·재유도 누락** — 원천에 사실이 없거나 재구축이 이를 읽지 못한다는
  가설이다. #45853, #45791, #46168, #45950의 재생 절반을 사례 후보로 둔다.
- **I2 비단조 전이** — 늦게 오거나 실패한 쓰기가 더 확정된 사실을 덮는다.
  #46327, #46132, #46169, #46595.
- **E 청크 결합법칙 위반** — #45950의 스트리밍 절반. `fold(분할)` ≠ `fold(연속)`.
- **별도 조사** — #46098은 browser lane의 활동 기록과 TUI의 독립 갱신·선택 보존을
  함께 다뤘다. 클라이언트 상태만의 문제로 단정하지 않는다. 이 RFC의 durable projection
  적용 여부와 server_view/local_ui 분리 후속 추적 항목은 확인하지 못했다.

"중단/재시작"은 독립 메커니즘이 아니다. 재시작은 가장 극단적인 rebuild(I1)이고,
중단은 종말로 잘못 모델링된 전이(I2)다.

## 3. 불변식

**I1 (fold 동등성, 제안).** 각 도메인에서 지정한 durable projection `P`에 대해,
같은 초기 상태와 같은 기록 접두사·시점을 기준으로 `P(live) = P(fold(log))`를 본다.
여기서 log는 그 도메인의 권위 있는 재구축 원천이다. 진단 로그를 모두 저널로 간주하지
않는다. 기록되지 않은 in-flight 결과는 이 등식과 구분한다.

- 대상 후보는 대화 transcript, Goal·Gate 판정, 실행 소유권이다. 이 목록은 적용이
  입증된 목록이 아니다. 각각의 원천·기록 경계·소비자·재구축 입력을 먼저 확인해야
  어떤 투영에 I1을 적용할지 정할 수 있다.
- **이 제안에서 durable accepted의 정의: 권위 있는 원천에 기록되었다.** "live
  상태에 있다"로 정의하면 순환이다. 다른 주체에게 durable accepted로 알리기 전에
  쓰기가 성공해야 한다(write-before-accept). 스트리밍의 in-flight 관측은 별도로
  선언한다. intent-before 패턴(#46599)은 관련 사례다.
- 정의만으로 기록 순서가 강제되지는 않는다. 기록 전 실패와 기록 성공 후 응답 전
  실패를 구분해 소비자에게 무엇이 보이는지 검증해야 한다.
- live-only UI와 post-tool·held-session 전송 결정은 자동으로 durable accepted가
  아니다. `lib/types/prompt_block_id.mli`의 수명 분류는 별도 계약이다.

**I2 (흡수 상태, 제안).** 확정된 저장·판정·소유권 결과는 에러·정리·중단만으로
덮지 않는다. 정당한 취소·이전·새 판정은 도메인이 명시한 End/retire 또는 이전 사실을
식별하는 대체 전이로 표현한다. 각 도메인의 전이와 이력 보존은 따로 확인한다.

**E (결합법칙).** 어떤 분할에서도 `fold(분할된 스트림) = fold(원본)`.
절단·비식별화가 두 경로에 같이 적용되는지가 #45950의 본체였다.

## 4. 의도적 손실 등록부

"의도적으로 끝났다"는 문구만으로는 검사 오라클이 없다. 기존 사례 작성자의 의도를
전수 확인하지는 못했다. 의도적 손실 경계를 등록해 감사하는 방안을 제안한다.

현재 아는 경계: 컨텍스트 compaction, 컨텍스트 절단(토큰 예산), TTL, 비식별화,
TUI viewport.

- 등록된 경계만 지정된 범위에서 손실을 만들 수 있다는 제안이다.
- 등록 항목에는 대상 사실·원천·소비자·경계·손실 사유·범위·담당자를 적어야 한다.
  저장 위치와 기존 계약을 재사용할지는 아직 정하지 않았다. 제2의 권위를 만들지 않는다.
- 등록되지 않은 경로를 어떻게 검사할지는 구현에서 정해야 한다. 의도만 적는 것으로
  실제 보존이 증명되지는 않는다.

## 5. 강제 — 컴파일러가 먼저

산문만으로 유지하지 말고 컴파일러가 강제할 수 있는 부분을 우선한다. 아래는 제안이며
실제 강제 범위는 각 대상과 빌드 설정을 확인해야 한다.

1. 소유한 관측 종류를 닫힌 variant로 두고 각 rebuild fold를 exhaustive match로 쓴다.
   새 생성자가 빠진 match가 빌드 오류가 되려면 해당 경고를 켜고 오류로 취급해야
   한다. 외부 타입이나 확장 가능한 variant까지 이 보장이 자동 적용되는 것은 아니다.
2. 경계 생성자(Resume·Start·replay·restore)의 운반·버림 결정을 명시한다.
   전체 record expression에서 필드를 빠뜨리면 OCaml은 컴파일 오류를 낸다.
   `{ default with ... }`는 기본값에서 새 필드를 물려받아 그 결정을 강제하지 않는다.
   전체 expression 사용을 지키는 수단은 별도 결정이 필요하다. warning 9는 record
   pattern의 누락 필드에 대한 경고이지 expression의 필드 누락 경고가 아니다.
3. 적합한 도메인에서는 live setter 대신 이벤트 적용 함수를 인터페이스로 노출한다.
4. 소유한 variant의 FSM 전이는 생성자를 명시해 새 경우를 검토한다. 루트 `dune`은
   warning 4를 켜지만 `test/dune`은 끈다. 모든 wildcard가 금지되는 것은 아니며,
   대상 stanza의 설정을 확인해야 한다.
5. 기능 경계와 연결된 검사는 다음을 구분한다.
   - I1 차등 비교: 같은 이벤트를 live와 저널→rebuild에 넣는다. 두 경로가 같은
     관측을 함께 빠뜨리면 비교가 통과하므로, 이것만으로 보존을 증명하지 못한다.
     별도로 입력·기록의 관측 식별자와 소비자가 보아야 할 구체 결과를 확인한다.
   - 기록 전 실패와 기록 후 응답 전 실패를 주입해, 소비자가 확정으로 본 결과와
     복구 결과를 대조한다.
   - I2의 도메인별 전이·실패 순서와 E의 분할 입력은 해당 경계의 실제 계약에 맞춰
     검증한다. 결정적 스케줄 사용 여부도 해당 시나리오에서 정한다.

기존 선례를 확장한다. `test_tui_keeper_chat_transcript`의 fold 고정이 I1 검사의
형태다. 수명 분류는 `prompt_block_id.mli`가 이미 하고 있다(post-tool/held-session
동작 선택). 경계 소유권의 타입 계약은 RFC-0099가 지목한 `tool_result.mli`(3치
failure effect disposition)와 `keeper_gate_replay.mli`다. 본 RFC는 새 권위를 만들지
않고 이 자리에 얹는다.

## 6. 런타임 변경 — 경로 조사 후 판단

첫 실무 질문은 **같은 권위 있는 기록에서 같은 소비자 context를 만드는 경로가
몇 개인가**이다. 서로 다른 입력·소비자의 렌더러 개수를 합해 통합 대상을 결정하지
않는다.

기준 head `a2c58248d48efad21fb1abd7abdcf0e4cf120b31`에서 직접 확인한 조립 경로는
`Keeper_unified_prompt.project_prompt`와 `Keeper_direct_turn_context.project_partition`
두 곳이며, 각각 `Keeper_context_layers.assemble_prepared`와 `assemble`을 쓴다.
둘은 준비된 관측을 조립한다는 근거이지, 같은 저널을 읽는 재구축 함수 두 개라는
증거가 아니다. `Keeper_replay_checkpoint.checkpoint_for_replay_persistence`는 체크포인트
투영·가지치기 경로다. 전체 log→context 경로 수와 원천·소비자는 아직 조사하지 못했다.
따라서 "1개면 변경 없음 / 2개면 통합"이라는 결론은 지금 내리지 않는다.

같은 원천·소비자의 중복이 실제로 발견되면 공통 적용 함수와 fold로 통합하는 방안을
검토한다. 공용 journal을 새로 만드는 안은 제안하지 않는다. 각 도메인의 기존 권위 있는
저장소와 기록 여부부터 확인한다. RFC-0412의 편입 사례는 참고이며 전면 이관의 증거가
아니다.

## 7. 이력과 근거

최초 판정(단일 불변식 `rebuild ⊇ accepted` + 경로별 round-trip 의무)에 대한 응답
5건은 모두 원안의 부족한 점을 지적했다. 하나는 재유도 계열에서 `⊇` 검사를 유지하되
별도 전이 불변식을 추가하자고 했으므로, 5건이 모두 `⊇` 자체를 기각했다고 단정하지
않는다. 두 응답의 헤더에는 동일한 `glm-5.3[1m]` unrecognized_model 경고가 있다.
이는 응답을 생성한 실제 provider/model이나 서로 다른 모델 수를 증명하지 않는다.

- ⊇는 부활·중복·훼손·우선순위 역전을 통과시킨다(약함). 동시에 권위 있는 빈 관측의
  정당한 대체를 금지한다(강함).
- "의도적으로"에 검사 오라클이 없다.
- 트리거("경계를 바꿀 때")는 실제 재발 경로(live 경로에 관측 종류 추가)를 놓친다.
- 채택된 기각 사유와 증거는 `docs/evidence/2026-10-29-observation-retention-review/`
  에 원문으로 보관한다. 요청·경고와 실제 응답 모델을 구분한 출처 한계도 그곳에 적었다.

## 8. 감사와 철회 조건

**감사 제안.** 원래 29건 목록은 아직 복원하지 못했다(§1). 재현 가능한 표본과 분류
기준을 확정한 다음 (a) derivation 수정, (b) carry-over 필드 추가, (c) FSM 상태 추가를
사례별로 검토한다. 필드나 상태의 존재만으로 결함 또는 헌법 위반이라고 단정하지
않는다. 기존 권위 있는 원천과 소비자, 중복 상태의 실패 경계를 함께 확인한다.
이 문서가 말하는 헌법은 `docs/constitution.xml`이며, 예컨대 `engineering/effects`,
`engineering/types`와 `evidence`가 관련 원칙이다. 특정 carry-over 필드가 일률적으로
위반이라는 조항은 이 근거에서 확인하지 못했다.

**철회 조건 초안.** fix 100건당 클래스 비율과 절대 건수를 함께 추적하고 6개월 내
감소가 없으면 철회를 검토한다. 29/202는 미검증의 과거 주장이라 기준선이 아니다.
기준 커밋, 표본·분류 방법, 담당자, 기록 위치, 관측 창과 감소 판정 기준은 채택 전에
정해야 한다. 정해지기 전에는 이 조건으로 성공·실패를 판정하지 않는다.
