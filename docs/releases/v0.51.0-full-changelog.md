## [0.51.0] - 2026-10-10

### Upgrade notes

1. **Keeper chat transcripts need fresh state (#41899).** Transcripts written by v0.50.0 hold a `terminal_assistant` slot that this version no longer reads, so Keeper replies are not saved (`transcript_persist_failed: ... unsupported transcript slot kind "terminal_assistant"`) and the server starts without a warning when installed with `scripts/install-local-build.sh`. Restarting the server does not clear it. Stop the server, back up and remove `<base-path>/.masc/keeper_chat/*.jsonl` (the path does not depend on `MASC_CLUSTER_NAME`; `<name>.jsonl.lock` files may stay and are recreated on the next write), then start the new server. All Keeper conversation history is removed. If `keeper_chat_events/` is kept, `chat-journal-audit ... Missing_terminal_row` errors may be logged for up to a few hours after the reset; they do not block saving. `scripts/deploy.sh` refuses to continue on old transcripts; `scripts/install-local-build.sh` does not check, so remove them before installing. Going back to an older binary has not been verified; back up and reset before going back as well.
2. **DOS checkpoints from earlier builds cannot be restored (#42145, #42147).** The DOS snapshot format version rises; restore refuses older checkpoints, typed and untouched. Keep the old worker beside checkpoints you still need, or use the game's own saves with the new worker.
3. **`claude-opus-5` is removed from the model catalog (#41880).** A `runtime.toml` that still binds `claude-opus-5` has that runtime disabled at boot. Switch the binding to `claude-opus-5-5` or delete it. Opus 5 through OpenRouter (`anthropic/claude-opus-5`) is unchanged.
4. **Authoritative recall pins are retired (#41837).** An offline preparation and rollback procedure for existing pins ships with the change; follow `docs/guides/RECALL-PIN-PUBLICATION-UPGRADE.md` before deploying.
5. **`[browser.live.bidi]` (#42125).** Write the table only after deploying a server that reads it.
6. **BiDi host shutdown (#42043).** A SIGTERM that arrives after another handled signal now ends a BiDi host immediately; the Firefox session may be left behind and need a restart before it can be attached again.

It starts only what is missing: no Firefox when the port already answers, and no host while one holds the host lock. It starts Firefox only together with a host, because Firefox's port lets any local process drive it: nothing is started while the browser lane is not installed as its installation wrote it, or a host holds the lock (it attaches to Firefox only when it starts), whether on this port, on another one, or with a record that cannot be read. A host that wrote its ending and is still giving up the lock is waited for, up to 5 seconds, before another is started. The host is not given the server's `MASC_HTTP_BASE_URL` or `MASC_HTTP_PORT`. `[browser.live] enabled = false` starts nothing. The dashboard's Browser activity editor reads the table and keeps it. A server starts no Keeper Firefox over a record whose group may still run, or over one it cannot read. A server that loaded no runtime configuration stops nothing. Before each signal a group stop checks that the group's number still names the group it meant, and a stop that reaches SIGKILL waits up to a second for the group to empty; a group whose processes this account may not signal is never taken for gone (#42170).
- When a Keeper asks for work only a WebDriver BiDi connection does, such as hover or drag, and no listed connection can do it, the MASC server starts the Keeper Firefox and its BiDi host and waits up to 15 seconds for the connection to be listed. It does so only when the workspace's `runtime.toml` has `[browser.live.bidi]` and its live lane is on, read at each request. The request itself is not sent on: its answer keeps its `error` and adds `bidiConnection` (the connection, and `started`: `firefox_and_host`, `host_only` or `nothing`) or `bidiStartFailed` (`kind`: `operator_needed`, `start_failed` or `not_listed_in_time`, and `message`), with a `retry` that says what to do next. One start runs at a time, and requests that arrive during it get its answer. A host that ends before its connection is listed is a failed start: the Keeper Firefox started for it is stopped and its record removed (#42178).
- A start of the Keeper Firefox and its BiDi host, at a server start or for a Keeper's hover or drag, whose port answers after a last host that ended on that port with its BiDi session left in Firefox, or with Firefox refusing it one, now restarts that Firefox when `.masc/browser-lane/keeper-firefox.json` shows MASC started it and it started no later than that host ended: Firefox refuses every new host while it holds that session. The profile is kept, so logins stay; open tabs close. The new Firefox is started once the stopped one's process group is empty and its port no longer answers, waited for up to 5 seconds. Any other Firefox on the port is left running, the server log says why, and a host is started for it all the same (#42186).
