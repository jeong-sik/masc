# 같은 턴 안에서 되풀이되는 도구 결과 (2026-11-01 ~ 11-07, UTC)

한 턴이 같은 도구를 불러 같은 결과를 받으면, 그 결과가 요청에 두 번 실리고 턴이 끝날 때까지 모든 요청이 둘 다 날라요.
`measure_repeated_results.py`가 이 반복의 바이트를 두 곳에서 세요. 둘 다 읽기만 하고 아무것도 쓰지 않아요.

- 저장된 요청(`.masc/keepers/*/provider-inputs`)과 그 메시지 blob(`.masc/tool_blobs`): 요청 하나가 싣고 있는 바이트예요.
- 도구 호출 장부(`.masc/tool_calls`): 호출 하나가 돌려준 바이트예요. 호출을 한 번씩만 세요.

읽은 때는 2026-11-07T03:29Z ~ 03:35Z예요. 11-07은 하루가 다 차지 않았어요. 거리(`requests.distance`)를 더하려고 요청 기록 JSON 8개는 같은 스크립트로 05:31Z ~ 05:42Z에 다시 읽었어요. 거리를 뺀 값은 03시 값과 같았고, `skipped`의 건너뛴 행 수만 그동안 자란 파일만큼 달라요. 장부 JSON은 03시 값 그대로예요. 숫자는 바이트이고 토큰이 아니에요. 모델이 반복 결과를 어떻게 읽는지는 재지 않았어요.
이 폴더는 규칙을 넣자는 주장이 아니에요. RFC-0510이 기대는 크기를 보여 줘요.

## 세는 단위

- 결과는 `tool_result` 칸 하나예요. 도구를 한꺼번에 부르면 도구 메시지 하나에 칸이 여럿 들어요. 크기는 칸 글자를 UTF-8로 센 바이트예요.
- 턴은 `origin == "conversation"`인 user 메시지에서 시작해요.
- 같은 턴 반복은 같은 턴의 앞선 결과와 글자가 같은 결과(`--match text`)예요. 1 KB 이상인 칸만 세요.
- 스텁으로 줄 바이트는 반복 바이트에서 반복 칸마다 350 B를 뺀 값이에요. 350 B는 마커 글자의 크기에서 왔어요. 저장된 요청 9개의 마커 535개는 348~461 B였어요.
- 거리는 같은 요청 안에서 센 메시지 개수예요. 같은 호출(Keeper, 세션, `tool_use_id`)은 처음 실은 요청의 값 하나만 세요. 호출 번호가 없는 반복은 실릴 때마다 세요.

- RFC-0510 은 병합됐고 상태는 아직 `초안`이에요. 이 숫자는 그 RFC 가 기대는 크기를 24시간으로 늘려 본 값이고, 수락·변경·폐기는 소유자가 정해요.

## 읽는 법과 한계

- 요청 기록의 한 행은 턴마다 하나이고, 그 턴의 첫 요청이 아닐 수도 있어요. 프롬프트 MB는 보낸 요청 전부의 합이 아니라 저장된 요청의 합이에요.
- 턴은 `origin == "conversation"`인 user 메시지에서 시작해요. 앞 요약(`agent_instruction`), `recovery_instruction`, 맨 뒤 `system_context`는 턴을 열지 않아요. 읽을 수 없는 user 메시지는 턴 시작으로 봐요. 이렇게 하면 같은 턴 반복이 적게 나오는 쪽으로만 틀려요.
- `--match answer`는 장부 행과 이어져야 해요. 이어지지 않은 결과는 `unmatched_results`에 세고 비교하지 않아요. 장부는 `--from-date`부터 읽어요.
- 스텁 크기 350 B는 가정이에요. 마커 글자는 348~461 B였어요. 스텁이 더 작으면 줄어드는 몫이 커져요. `--min-bytes 512 --stub-bytes 300`이면 1.41%예요.
- 반복 결과를 스텁으로 바꾸면 모델은 두 번째 결과의 글자를 못 봐요. `--match text`에서는 두 결과의 글자가 같으니 첫 결과가 보여 준 것을 잃지 않아요. `--match answer`에서는 글자가 달랐을 수 있고, 달랐다면 그 차이(영수증 칸)를 잃어요. 모델이 그 차이를 필요로 하는지는 재지 않았어요.
- 장부의 `result_bytes`는 이미지가 든 결과의 이미지까지 세고, 요청 쪽은 미디어가 붙은 메시지를 세지 않아요. `masc_dos_screen`이 장부에만 크게 나오는 까닭이에요.
- 거리는 요청에 실린 메시지로 세요. 꼬리창이 첫 결과를 잘라낸 요청에서는 그 요청에 남은 첫 결과부터 재요. 사이 프롬프트는 저장된 메시지 blob의 바이트라서 공급자로 간 글자 수와 조금 달라요.
- blob이 지워져 못 읽은 메시지는 `missing_blobs`에 세요. 이번 측정은 0이에요.
- 첫 구간은 17시간 8분이에요. 반복의 90.5%가 Keeper 하나에서 나와서, 이 값을 다른 날이나 다른 Keeper의 값으로 옮기면 틀려요(장부 날짜별 표).

## 다시 재는 명령

```bash
python3 docs/evidence/repeated-tool-results-2026-11/measure_repeated_results.py \
    --base-path ~/me --from-date 2026-11-01 --to-date 2026-11-07 \
    --since 2026-11-06T09:52:00 --until 2026-11-07T03:00:00 --top 12 \
    --json-out docs/evidence/repeated-tool-results-2026-11/result-2026-11-06T09_52_to_11-07T03_00.json
python3 -I -m unittest discover -s docs/evidence/repeated-tool-results-2026-11
```

다른 구간은 `--since`와 `--until`만 바꿔요. `--exclude-keeper`로 Keeper를 빼고, `--match answer`로 장부의 답 지문이 같은 결과까지 세고, `--view ledger`로 장부만 읽어요.
`--from-date`는 읽을 파일의 첫 날이에요. `--since`보다 며칠 앞으로 두어야 요청이 싣고 있는 옛 턴의 호출이 장부와 이어져요.
