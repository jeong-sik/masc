# RFC: 보낸 요청 앞부분은 창이 옮겨질 때만 바꾼다

## 0. 요약

Kimi Coding Plan 의 사용량이 빨리 찬다.
11-11 주의 주간 창은 리셋 2.6일 전에 100% 가 됐다.
11-18 주는 16시간 만에 27% 다.

Kimi 쪽 버그는 아니다.
Kimi 는 캐시에 맞은 입력을 거의 세지 않고, 미적중 입력과 출력을 센다.
MASC 가 이미 보낸 요청 앞부분을 턴마다 바꾸는 경우가 있다. 이 변화는 서로 다른 턴 사이의 캐시 미적중 후보 원인이다.
2026-11-18 10:00Z ~ 2026-11-19 01:40Z 사이 회귀에 포함된 102개 구간의 Kimi 5시간 창 증가 합은 57.0% 다. 사용량 기록에서 턴 첫 요청 미적중의 몫은 21.9%p 로 추정했다. 원인별 분류는 턴 마지막 요청 스냅샷을 비교한 대리 값이다.

이 RFC 의 규칙은 하나다.

> 이미 보낸 요청 앞부분은 창이 옮겨질 때만 바꾼다.
> 턴마다 달라지는 것은 요청 끝에 싣는다.

앞부분을 다시 쓰는 곳은 셋이다(§3).
운영자가 정할 것은 셋이다(§6).

- D1: 창을 옮기는 신호로 provider 가 센 입력 토큰을 쓸지
- D2: Librarian 지점이 앞으로 가도 창을 붙잡을지
- D3: 채팅 요청의 출처 관찰을 System 밖 어디에 실을지

## 1. 측정

근거 묶음은 [2026-11-19-kimi-prefix-rewrites](../evidence/research/2026-11-19-kimi-prefix-rewrites/README.md) 다.
회귀와 첫 요청 비용의 집계 창은 2026-11-18 10:00Z ~ 2026-11-19 01:40Z 다. 운영 런타임 기록을 읽기만 했다. 다른 집계 창은 결과 옆에 적는다.

### 1.1 Kimi 가 세는 것

Kimi 사용량 창(`/usages`)의 10분 구간 102개를 요청 토큰에 회귀했다.

| 토큰 | 5시간 창 % / 백만 토큰 |
|---|---|
| 캐시 미적중 입력 | 2.25 ~ 2.5 |
| 출력 | 25 |
| 캐시 적중 입력 | 0.01 이하 |

- R² 는 0.855 ~ 0.868 이다.
- 적중 입력 계수를 0.05 로 두면 R² 가 0.651 로 떨어진다.
- 그래서 적중 입력은 미적중의 1/200 이하로 센다.
- 공식 문서는 「actual token consumption」까지만 적는다. 이 식은 측정값이고 신뢰도는 Medium 이다.

### 1.2 Kimi 캐시는 정상이다

같은 턴 안의 연속 요청 1,729쌍 가운데 앞 요청을 절반도 못 읽은 것은 9쌍(0.5%)이다. 2026-11-17~19 UTC 사용량 일별 파일을 읽은 `within_turn_prefix_loss.txt` 결과다.
Claude 계정 레인은 0.4~1.2% 다.
캐시를 잃는 곳은 턴과 턴 사이다.

### 1.3 턴 첫 요청을 미적중으로 만드는 곳

2026-11-18 10:00Z ~ 2026-11-19 01:40Z 의 사용량 기록이 있는 Kimi 턴 111개다(`first_request_causes.txt`). 첫 요청 미적중은 사용량 기록에서 센다. 원인은 연속 두 턴의 마지막 요청 스냅샷에서 처음 달라진 위치로 분류했다. 스냅샷과 사용량 기록은 턴 번호로 연결했으며, 두 번호의 대응을 원본에서 별도로 검증하지 않았다.

| 처음 달라진 곳 | 가능한 설명 | 턴 | 5시간 창 %p | 첫 요청 적중 |
|---|---|---|---|---|
| 이력 첫 메시지 | 창 시작이나 하던 일 메시지의 변경. Librarian 지점 이동은 가능한 원인이다 | 45 | 7.8 | 29% |
| 이력 가운데 | 끝난 턴의 결과·인자를 마커로 바꾼다 | 31 | 5.2 | 40% |
| system 프롬프트 | 채팅 턴과 스스로 깬 턴이 번갈아 온다. 도구 배열도 같이 바뀐다 | 17 | 5.0 | 17% |
| 도구 배열 | 도구 한두 개가 들고 났다 | 9 | 2.4 | 24% |
| 런타임 | 레인이 다음 후보로 넘어갔다 | 3 | 0.9 | 25% |
| 바뀐 곳 없음 | 덧붙기만 했다 | 4 | 0.4 | 63% |

- 짝을 못 찾은 턴 2개가 0.2%p 다.
- `first_request_causes.py` 는 백만 토큰당 미적중 2.5, 출력 20, 적중 0.01을 가정한다. 턴 안 미적중은 18.4%p, 출력은 14.4%p, 적중 읽기는 4.0%p 로 추정되며 전체 추정은 58.6% 다. 다른 계수를 고정하고 출력만 §1.1의 적합값 25로 두면 출력은 약 18.0%p, 합계는 약 62.2% 다.
- 턴 안 미적중은 새 도구 결과다. 일 자체의 몫이라 이 RFC 밖이다.

system 과 도구 배열의 상세 변경은 같은 시간 범위로 자른 provider 입력 기록의 연속 110쌍에서 셌다(`prefix_change_sources.txt`). 위 표의 111턴은 사용량 기록 기준이다. 별도 탐색 결과인 `turn_pair_changes.txt` 의 121쌍은 11-18~19 UTC 일별 파일에서 시간 범위를 따로 자르지 않고 비교한 수다.

- system 이 바뀐 20쌍은 모두 `### Admitted Request Source` 절이 붙거나 떨어졌다.
  - 그중 3쌍은 사용량 기록이 없는 턴이라 위 표의 system 줄(17턴)에 없다.
- 같은 20쌍에서 `keeper_tool_search` 설명의 이름 목록에 `keeper_receipt_wait` 가 들고 났다.
- 둘 다 그 턴이 채팅 요청을 받았는지에 따라 정해진다(§3.2).
- 도구 배열만 바뀐 9쌍은 다른 도구 한두 개가 들고 났다.

### 1.4 앞부분이 그대로였던 턴

system·도구가 같고 이력이 덧붙기만 한 턴의 첫 요청 적중이다.

| 레인 | 턴 | 적중 |
|---|---|---|
| Claude (`claude_account_A`) | 138 | 91~92% |
| GLM (`glm-coding`, 직전 턴과 30분 안) | 78 | 68~80% |
| Kimi (`kimi_coding`, 10분 안) | 3 | 76~79% |

Kimi 는 10분 이내에 해당한 턴이 3개뿐이다. `stable_prefix_hits.txt`에는 10~30분 간격 한 건(적중률 41%)도 있다. 이 표본으로 턴 사이 캐시 수명을 추정하기 어렵다.

### 1.5 크기 거절

Kimi 의 크기 거절은 HTTP 400 문장으로만 온다(#50020).
agent_core 는 그 문장을 넘침으로 바꾸지 않는다. 그래서 창을 당기는 사다리가 돌지 않고 턴이 실패한다.

| 날짜 | 이 거절로 끝난 턴 | Keeper |
|---|---|---|
| 11-13 | 1,011 | `wkbl-web-leader` 1,009 |
| 11-14 | 550 | `wkbl-web-leader` |
| 11-18 | 5 | `code-reviewer-sister` |

`wkbl-web-leader` 의 요청은 1,048,968 ~ 1,106,320 토큰이었다. 모델 한도는 1,048,576 이고 binding 의 `max-context` 는 500,000 이었다.
masc 는 보내기 전에 크기를 재지 않는다(RFC-keeper-context-window-in-tokens §1 결정 2).

## 2. 규칙

### 2.1 한 문장

이미 보낸 요청 앞부분은 창이 옮겨질 때만 바꾼다.
턴마다 달라지는 것은 요청 끝에 싣는다.

### 2.2 낱말

- **앞부분**: 지난번 받아들여진 요청이 보낸 바이트다. system 프롬프트, 도구 배열, 실어 보낸 이력이다.
- **창**: 요청이 싣는 이력의 범위다. 시작 atom 으로 부른다.
- **창이 옮겨진다**: 이번 요청의 시작 atom 이 지난번 받아들여진 요청과 다르다.
  - 같은 (Keeper, 런타임)의 `Keeper_model_input_ledger` 의 `last.first_atom` 과 견준다.
  - ledger 가 없으면 옮겨진 것으로 본다. 재시작 뒤나 그 런타임의 첫 요청이 그렇다.

### 2.3 창이 옮겨지는 까닭

| 까닭 | 지금 | 이 RFC 뒤 |
|---|---|---|
| Librarian 지점이 창 시작보다 앞으로 갔다 | 옮긴다(RFC-keeper-context-window-in-tokens §1 결정 1) | D2 를 따른다 |
| provider 가 typed 크기 거절을 했다 | 옮긴다(같은 §1 결정 2 의 사다리) | 그대로 |
| provider 가 센 입력 토큰이 `max-context` 에 닿는다 | 없다 | D1 을 따른다(§4) |
| ledger 가 없다 | 새로 고른다 | 옮겨진 것으로 본다 |

### 2.4 옮겨질 때와 그대로일 때

- 창이 옮겨지는 요청은 앞부분을 새로 짠다. 어차피 처음부터 미적중이다.
  - 하던 일 메시지, 끝난 턴의 마커를 이 요청에 모은다.
- 창이 그대로인 요청은 지난번 요청의 앞부분을 바이트 그대로 싣고 뒤에 덧붙인다.
- system 과 도구 배열은 그 턴이 무엇으로 깼는지에 따라 달라지지 않는다.
  - 그 턴에만 해당하는 관찰은 요청 끝에 싣는다.
  - 그 턴에 쓸 수 없는 도구는 빼지 않는다. 부르면 쓸 수 없는 까닭을 답한다.

## 3. 곳마다 바꾸는 것

### 3.1 끝난 턴의 결과·인자 마커

지금 하는 일:

- 턴이 끝나면 다음 턴의 첫 요청에서 그 턴의 결과(2,048 B 이상)를 마커로 바꾼다.
- 끝난 호출의 인자도 바꾼다(11-17 운영자 지시, #52700).
- 창 시작이 그대로면 이력 가운데가 바뀐다. §1.3 의 5.2%p 다.

바꾼 뒤:

- 마커로 바꾸는 경계(`demote_before`)는 창이 옮겨질 때만 움직인다.
- 창이 옮겨진 요청은 지금처럼 그 턴의 경계를 쓴다.
- 창이 그대로인 요청은 ledger 의 `last.demote_before` 를 쓴다. ledger 는 이 값을 이미 적는다.
- 인자도 같은 경계 아래 것만 바꾼다.
  - 시도마다 턴 경계로 한 번 묶는 것(`bind_completed_arguments ~completed_before`)은 그대로다.
  - 묶은 인자 가운데 그 경계 아래 것만 고른다(`arguments_before`).
- 턴 첫 요청은 §4 의 신호가 창을 볼 때만 붙잡는다.
  - ledger 가 없거나, 한 턴이 자란 양을 모르거나, `max-context` 선언이 없으면 지금처럼 턴 경계를 쓴다.
  - 신호 없이 붙잡으면 창은 provider 가 거절할 때까지 자란다.
  - 턴 가운데 요청은 그 턴 첫 요청이 정한 경계를 따른다.
- 크기 거절에 답하는 재전송(`Current_turn_demoted`)은 그대로다.
  - 그 경계는 다음 턴으로 이어진다.
  - 재전송이 마커로 바꾼 2,048 B 아래 결과는 다음 턴 첫 요청에서 원문으로 돌아온다. 지금도 그렇다.

[RFC-tool-results-age-out-of-context](RFC-tool-results-age-out-of-context.md) 와의 관계:

- 그 RFC 는 이 비용을 프롬프트 바이트의 1.0% 로 잡았다. 직전 턴 결과가 이력 끝에 있다고 봤다.
- 같은 RFC 는 「front 가 움직일 때만 바꾸는 방법은 재지 않았다」고 적었다. 이 절이 그 방법이다.
- 같은 RFC 의 손익분기 c(적중 읽기 값 ÷ 미적중 값)는 턴당 요청 5개에서 0.4% 다. Kimi 는 0.5% 이하로 쟀다.
- 같은 RFC 는 「적중이 내려가면 규칙을 되돌려요」라고 적었다. §1.3 이 그 측정이다.
- 지난 인자를 보관하라는 지시는 지킨다. 보관하는 때만 창이 옮겨질 때로 바뀐다.

이 절은 D1 과 함께 켠다.
마커를 미루면 창 시작이 오래 그대로인 Keeper 의 요청이 빨리 자란다.
D1 이 없으면 Kimi 에서는 §1.5 의 실패가 더 일찍 온다.

### 3.2 채팅 턴과 스스로 깬 턴

지금 하는 일:

- 채팅 요청을 받은 턴은 System 관찰 `Direct_input_source` 를 싣는다(#50718). `Active_goals` 바로 뒤다.
- 같은 턴은 `keeper_receipt_wait` 도 받는다. 채팅 실행이 없는 턴에는 이 도구를 빼고 준다(`Keeper_run_tools_setup.descriptors_for_run`).
- 이 도구는 deferred 라서 `keeper_tool_search` 설명의 이름 목록이 바뀐다.
- 그래서 두 종류의 턴이 번갈아 오면 system 과 도구 배열이 함께 바뀐다. §1.3 의 system 줄 5.0%p 다.

바꾼 뒤:

- `Direct_input_source` 를 System 에서 뺀다. 어디에 실을지는 D3 이다(§6).
  - 막는 것: 도구 결과 뒤에 붙는 User 끝 문맥은 모델에게 「누가 다시 말했다」로 읽힌다(task-514, `Prompt_block_id.injected_on_post_tool_round`). #50718 은 그래서 출처를 System 에 두고 도구 라운드 내내 보이게 했다.
  - (가) 첫 요청 끝 문맥에만 싣는다. 가장 단순하다. 도구 라운드 뒤에 새로 붙지 않는다.
    - Anthropic 은 예외다. 서명된 thinking 이 붙은 응답이면 첫 요청 끝 문맥을 이력에 남긴다(`Historical_system_context`, RFC-AC-041).
    - 그 문맥은 다음 요청에서 제자리에 다시 간다. 그래서 그 레인에서는 출처가 도구 결과 앞, 첫 자리에서 계속 보인다.
  - (나) 모든 요청 끝에 싣는다. 출처가 계속 보인다. 채팅 턴마다 도구 결과 뒤에 User 끝 문맥이 붙는다.
  - (다) 입력 메시지와 함께 typed 메타데이터에서 그린다. 바이트가 턴마다 같고 계속 보인다. 출처가 User 메시지 안에 들어가 위조와 구별하기 어려워진다.
- `keeper_receipt_wait` 는 모든 턴에 준다. 채팅 실행이 없는 턴에서 부르면 typed 오류로 「기다릴 채팅 실행이 없다」고 답한다.

지키는 것:

- #50718 의 목적(받아들인 요청을 누가 보냈는지 모델이 안다)은 세 갈래 모두 지킨다. 도구 라운드 뒤에도 보이는지는 갈래마다 다르다.
- 두 가지는 같은 20쌍에서 함께 바뀐다. `keeper_receipt_wait` 만 바꾸면 System 이 여전히 바뀌어 적중이 오르지 않는다.
- 원래 User 메시지와 checkpoint 형식은 바꾸지 않는다.
  - Anthropic 레인의 checkpoint 는 이력에 남긴 첫 요청 끝 문맥을 담는다. 이제 그 안에 출처도 있다(L1 #53316 에서 확인).
- 요청 끝의 글은 요청마다 다시 읽힌다. 출처 JSON 은 수백 바이트라 system 뒤를 전부 다시 읽는 것보다 작다.
- 공식 클라이언트 경로는 바꾸지 않는다. 그 경로는 세션을 이어 쓴다.

§1.3 의 도구 배열 줄(2.4%p)은 다른 도구 한두 개가 들고 난 9번이다(`masc_keeper_delegate_cancel`, `cloudflare_whoami` 등).
원인을 하나씩 확인하지 않았다. 같은 규칙(턴 상태로 넣고 빼지 않는다)으로 고칠 수 있는지는 구현 층에서 잰다.

### 3.3 Librarian 지점 (D2)

지금 하는 일:

- 요청은 Librarian 이 마지막으로 흡수한 지점부터 싣는다(RFC-keeper-context-window-in-tokens §1 결정 1).
- 그래서 Librarian 이 한 턴을 읽을 때마다 창이 옮겨진다.
- 맨 앞 하던 일 메시지(`working_state_message`)도 함께 바뀐다. §1.3 에서 이력 첫 메시지 변경으로 분류한 몫은 7.8%p 다. Librarian 만의 원인으로 검증한 값은 아니다.

D2 를 받으면:

- 창은 seed 에서 시작한다. seed 는 지난번 받아들여진 요청의 시작이다.
- D1 신호가 오면 창을 Librarian 이 읽은 곳의 끝으로 옮긴다.
- 하던 일 메시지는 창 맨 앞에 두고, 창이 옮겨질 때만 바꾼다.
  - 창이 그대로면 지난번 요청의 그 메시지를 바이트 그대로 싣는다.
  - 그사이 일은 날것 이력에 있다.
- 읽은 곳의 끝이 seed 보다 뒤가 아니면 옮길 곳이 없다. 그때는 지금의 사다리를 탄다.
- Memory 와 날것 창이 겹치는 구간이 생긴다. Memory 에도 요청에도 없는 구간은 생기지 않는다.
- 창을 붙잡는 조건은 §3.1 의 마커와 같다.
  - 턴 첫 요청은 §4 신호가 창을 볼 때만 붙잡는다. 신호 없이 붙잡으면 창은 거절할 때까지 자란다.
  - 턴 가운데 요청은 그 턴 첫 요청이 연 자리를 붙잡는다.
  - seed 는 지금처럼 턴 기록과 이 턴이 붙잡은 앞에서 읽는다. ledger 는 창이 그 자리에서 열렸는지만 본다.
- 하던 일 메시지 없이 열린 창은 그대로인 동안 계속 없이 간다. 붙잡을지는 글이 아니라 창 시작으로 정한다.
- 신호가 창을 읽은 곳의 끝으로 옮기면 그 턴 나머지 요청도 그 자리를 붙잡는다. Librarian 이 턴 가운데 더 읽어도 창은 그대로다.
- ledger 는 프로세스 안에만 있다. 재시작 뒤 첫 턴과 ledger 가 없는 다른 런타임 후보는 지금처럼 Librarian 지점에서 연다.

Librarian 재설계(#53148)와의 관계:

- D2 는 #53148 §11.2 의 「읽은 끝과 seed 중 뒤쪽」을 seed 유지 규칙으로, §11.4 의 매 턴 하던 일 구성을 창 이동 때만 바꾸는 규칙으로 대체한다.
- L8 을 구현하기 전 D2 결정과 #53148 의 두 절 개정을 확인한다. 이 PR 은 #53148의 파일을 수정하지 않는다.
- 지금 코드에서는 `Keeper_turn_driver_try_provider.choose_range_start` 가 바뀐다.

### 3.4 범위 밖

- 런타임이 바뀌는 턴(0.9%p)은 provider 캐시가 다르다. 고칠 것이 없다.
- `prompt_cache_key` 는 보내지 않는다. 턴 안 손실이 0.5% 라 주원인이 아니다.

## 4. 창을 옮기는 신호 (D1)

지금은 provider 의 거절만이 창을 당긴다. Kimi 와 Ollama 의 거절은 typed 가 아니라서 턴이 실패한다(§1.5, #50020).

제안:

- 창이 그대로일 때, 다음을 더해 binding 의 `max-context` 를 넘으면 창을 옮긴다.
  - 지난번 받아들여진 요청의 입력 토큰. provider 가 센 값이다.
    - 턴 첫 요청의 값도 쓴다. 도구를 안 부른 턴은 그 요청이 턴에서 가장 크다.
    - ledger `last_usage` 는 표본만 담아서 턴 문맥이 실린 요청을 건너뛴다. 그래서 ledger 가 이 값을 따로 적는다(`growth.last_input`).
  - ledger 가 열린 뒤 한 턴 동안 가장 크게 자란 입력 토큰.
    - 한 턴이 자란 양은 그 턴에서 가장 큰 요청의 값에서 앞 턴 마지막 요청의 값을 뺀 것이다.
    - 창이 옮겨진 그 턴은 앞 값이 그 창에 없어서 재지 않는다.
    - 창이 옮겨져도 이 값은 남긴다. 한 턴이 자라는 양은 창이 어디서 열리든 같다.
    - 그래서 신호는 옮긴 바로 다음 턴에도 창을 본다. ledger 가 처음 연 창만 둘째 턴이 열린 뒤부터 본다.
    - provider 가 세지 않은 요청이 있는 턴은 재지 않는다.
- 신호는 턴 첫 요청(턴 문맥이 실린 요청)에서만 본다.
  - 턴 가운데 요청의 값은 그 턴이 자란 몫을 이미 담고 있다.
  - 옮긴 창은 그 턴 끝까지 붙잡는다. 다음 턴부터는 ledger 와 턴 기록이 그 시작을 읽는다.
- 옮기는 곳은 Librarian 이 읽은 곳의 끝이다. 그 끝이 창 시작보다 뒤가 아니면 지금의 사다리 첫 단계(턴 경계)다.
  - 턴 경계도 창 시작보다 뒤가 아니거나 모르면 옮기지 않는다. 그때는 지금의 사다리가 받는다.
- 값 하나라도 모르면 신호가 없다. ledger 가 없거나, `max-context` 선언이 없을 때다.
- 이 신호는 보내기를 막지 않는다. 창을 일찍 옮길 뿐이다.
- 다음 요청 예측(`Keeper_next_request_forecast`)도 같은 ledger 와 같은 선언으로 같은 규칙을 묻는다.

고르지 않은 것:

- 비율이나 여유분 숫자(예: 「`max-context` 의 80%」). 근거가 없는 숫자다.
- 바이트로 토큰을 추정하는 것. provider 가 센 값만 쓴다.
- 거절 문장을 읽어 넘침으로 바꾸는 것(#50020 이 고르지 않은 것과 같다).

## 5. 대가

- 창을 옮기기 전까지 요청이 크다.
  - D2 를 받으면 요청은 `max-context` 근처까지 자란다. 운영자가 binding 마다 정한 값이다.
  - RFC-keeper-context-window-in-tokens §1 결정 4(턴마다 컨텍스트를 줄인다)와 부딪힌다. 큰 창이 모델 품질에 주는 영향은 재지 않았다.
- 적중 입력에도 값을 매기는 provider 는 들고 다니는 바이트만큼 낸다.
  - 손익은 적중 계수 c 에 달렸다. Kimi 는 0.5% 이하로 쟀고, 다른 provider 는 배포 뒤 같은 방법으로 잰다.
- 끝난 턴의 결과를 원문으로 더 오래 싣는다. 마커를 되읽는 호출은 줄 수 있다. 재지 않았다.
- §3.2 의 요청 끝 글은 요청마다 미적중이다. 출처 JSON 크기만큼이다.

## 6. 운영자가 정할 것

| | 정할 것 | 권하는 쪽 | 바뀌는 결정 |
|---|---|---|---|
| D1 | 창을 옮기는 신호로 provider 가 센 입력 토큰을 쓴다(§4) | 쓴다 | RFC-keeper-context-window-in-tokens §1 결정 2 |
| D2 | Librarian 지점이 앞으로 가도 D1 신호 전까지 창을 붙잡는다(§3.3) | 붙잡는다 | 같은 RFC §1 결정 1·4 |
| D3 | 출처 관찰을 (가)·(나)·(다) 중 어디에 싣는다(§3.2) | (가) 첫 요청 끝 | #50718 의 「도구 라운드 내내」 |

- D1 을 권하는 까닭: §1.5 의 실패를 막는다. §3.1 을 켜려면 필요하다.
- D2 를 권하는 까닭: §1.3 의 7.8%p 다. 대가는 §5 의 첫째다.
- D3 을 (가)로 권하는 까닭: 기존 끝 문맥 규칙(첫 요청만)과 같고, 도구 라운드에 User 끝 문맥을 늘리지 않는다. 대가는 도구 라운드 뒤 출처가 안 보이는 것이다.
- 2026-11-19 운영자 결정: D2 는 붙잡는다, D3 은 (가)다.
  - D2 는 D1 이 있어야 Kimi 에서 안전하다. 붙잡은 창을 옮길 신호가 typed 거절뿐이면, Kimi 에서는 창이 거절될 때까지 자라고 턴이 실패한다(§1.5).
- 같은 날 운영자 결정: D1 은 쓴다. 기준은 성능과 효율이 오르는 쪽이다.

## 8. 검증

시험(층마다):

- 창이 그대로인 연속 두 턴의 요청에서 앞부분이 바이트까지 같다.
- 창이 옮겨진 요청에서만 앞부분이 바뀐다.
- 규칙을 되돌린 변이에서 위 시험이 실패한다.
- L1: 채팅 턴과 스스로 깬 턴의 system 과 도구 배열이 같다. 채팅 실행 없는 `keeper_receipt_wait` 는 typed 오류다.
- L2: 입력 토큰이 신호를 넘는 ledger 로 창이 옮겨진다. 넘지 않으면 그대로다.

배포 뒤:

- 근거 묶음의 `first_request_causes.py` 로 같은 표를 다시 잰다.
- 층이 맡은 줄이 0 에 가까워졌는지 본다.
- Kimi 5시간 창이 같은 일에서 덜 오르는지 `quota_regression.py` 로 본다.
- 되돌림 조건: 한 층을 켠 뒤 provider 의 턴 첫 요청 적중이 같은 간격 구간에서 내려가면 그 층을 되돌린다.

## 9. 모르는 것

- Kimi 사용량 계산식은 측정값이다(신뢰도 Medium). 사용량 창의 해상도는 1% 이고 masc 밖 사용이 섞인다.
- Kimi 캐시가 턴 사이에 얼마나 오래 남는지 모른다(표본 셋).
- Claude·GLM·Ollama 구독 한도가 적중 입력을 어떻게 세는지 모른다.
- 큰 창이 모델 품질에 주는 영향을 재지 않았다.
- §3.2 의 나머지 도구 변화 9번의 원인을 하나씩 확인하지 않았다. 불러온 도구가 붙거나(6) 은퇴한(3) 모양이다.
- provider 입력 기록은 턴의 마지막 요청이다. 요청마다 `Keeper_attempt_request_evidence.observe_wire` 가 앞 기록을 바꾼다.
  - 그래서 §1.3 은 앞 턴과 다음 턴의 마지막 요청을 견줬다.
  - 다음 턴 가운데 불러온 도구(붙은 6턴)는 턴 경계를 깨지 않았을 수 있다. 그러면 도구 배열 줄 2.4%p 의 일부는 다른 줄의 몫이다.
  - 첫 요청 미적중 합계 21.9%p 는 사용량 기록에서 셌으므로 바뀌지 않는다.
- Anthropic 레인은 지난 턴의 출처를 이력에 남긴다(§3.2). 모델이 그것을 지금 턴의 출처로 잘못 읽는지는 재지 않았다.
  - 지금 턴의 끝 문맥은 그 턴이 받은 요청의 출처만 싣는다. 받은 요청이 없는 턴에는 출처 칸이 없다.
  - 공식 클라이언트 경로도 지난 System 바이트를 지우지 않는다. `direct_source_absent` 는 보관 영수증만 거둔다.
