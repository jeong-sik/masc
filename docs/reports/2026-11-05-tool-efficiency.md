## 1. 측정

### 1.1 방법

- `scripts/measure-tool-efficiency.py`(#48223)가 `<base>/.masc/tool_calls/YYYY-MM/DD[.NNN].jsonl` 의 `tool_call` 행을 읽어요. 날짜별로 병렬로 읽고, 결과는 `--json-out` 으로 남겨요.

### 1.3 읽을 때 주의

- 재조회는 줄일 수 있는 양의 상한이 아니에요. "새 정보가 없었던 호출"의 수예요. Codex 같은 official client 레인은 턴마다 새 컨텍스트로 시작할 수 있어서 그 레인에는 필요한 재조회가 섞여 있어요. 재조회 중 모델이 꼭 필요했던 비율은 재지 못했어요.
- 도구 시간은 호출마다 `duration_ms` 한 값이에요. 이 값은 Agent Core 가 호출마다 재서 넘겨요(`lib/keeper/keeper_hooks_agent_core.ml:754-756`). 실행 시간과 기다린 시간이 섞였는지는 이 저장소 안에서 못 가려요. 10초 이상 걸린 호출이 4,106행(2.8%), 100초 이상이 433행이에요.

- 모델이 한 응답에 호출 하나만 담은 경우(`batch_size` 1)가 141,419호출(98.1%)이고, 둘 이상 담은 호출은 2,764호출(1.9%)이에요. 시스템은 한 응답에 담긴 호출을 도구 descriptor 로 직렬이나 병렬로 정해 실행해요(`Tool.ordinary_descriptor`, `packages/agent_core/lib/base/tool.mli`). 그런데 겹쳐 돌 호출이 거의 안 생겨요. 한 턴에서 앞 호출이 끝나기 전에 다음 호출이 시작된 쌍은 134,311쌍 중 3,174쌍(2.4%)이에요. 원장에는 모델이 없어서(`model` 이 상수예요) 모델별로는 못 나눴어요.
- `execution_mode` 는 serial 85,098호출(99.2시간)과 concurrent 59,085호출(2.2시간)이에요. concurrent 호출은 평균 0.13초예요.
- 허용은 계정이 동시에 받는 요청 수의 한도예요(`packages/agent_core/lib/llm_provider/provider_admission.mli`). 요청은 끝날 때까지 허용 하나를 쥐고 있어서, 모델 요청이 줄거나 요청 하나의 처리 시간이 줄면 같은 계정을 쓰는 모든 Keeper 의 줄이 짧아질 것으로 보여요(추정). 호출 수와 결과 바이트를 줄이는 수정(§5)이 이 줄에 얼마나 닿는지는 배포 뒤 같은 방식으로 다시 재서 봐야 해요.
- 그래서 이 보고서가 줄이는 재조회와 넘침은 주로 결과 바이트(컨텍스트)를 줄여요. 턴 시간에서 도구가 차지하는 몫은 11.2%이고, 가장 큰 몫(57.0%)은 호출 사이에 있어요. 결과가 줄면 모델 요청이 짧아져 호출 사이 시간이 줄 수도 있지만 그 크기는 재지 못했어요.
- 이 절의 도구 시간과 호출 사이 시간은 도구 호출 원장에서 오고, 나누는 턴 시간은 trace 파일(첫 줄~끝 줄 구간)에서 와요. 그래서 몫은 원장의 시간 중 그 Keeper 의 턴 구간에 든 초만 세요. 원장 전체를 그대로 나누면 도구 시간 101.3시간 중 21.9시간, 호출 사이 시간 510.1시간 중 105.8시간이 구간 밖이라서 몫이 실제보다 크게 나와요.
- 구간 밖 도구 시간 21.9시간은 세 덩어리예요. 첫째는 trace 파일이 없는 턴의 `direct` 호출 16.0시간(21,458호출)이에요. 그 Keeper 에는 trace 파일이 있고, 턴 구간 안의 초는 잰 값으로 0이에요. 둘째는 trace 파일이 하나도 없는 Keeper 2명의 호출 4.4시간(1,657호출)이에요. 턴 구간이 없어서 안의 시간이 정의상 0이에요. 셋째는 trace 파일이 있는 턴인데 호출이 구간 밖에 통째로 놓인 `direct` 호출 1.5시간(1,097호출)이에요.

- 11-05T05:00Z 까지 창의 `Execute` 는 117.15시간 중 26.16시간(22.3%)이 구간 밖이고, 그중 24.72시간이 trace 파일이 없는 턴의 호출이에요(`docs/evidence/lane-time-2026-11/result-2026-11-01_11-05.json` 의 `turn_time.calls_without_trace_file`).

### 1.6 도구 스키마와 스킬 목록이 요청마다 싣는 것

같은 저장된 요청 3,217개에서 도구 스키마와 시스템 프롬프트 크기를 읽고, 스킬 목록은 스키마 blob 을 열어 행마다 길이를 쟀어요. 호출 수는 도구 호출 원장에서 세요. 스크립트와 정의는 §1.5 와 같은 폴더에 있어요.

- 요청 하나에 도구 스키마가 중앙값 93,177바이트(도구 45개, 최대 60개), 시스템 프롬프트가 중앙값 121,419바이트 실려요. 둘을 합친 몫은 본문의 17.6%(요청별 중앙값)예요.
- 도구 스키마 중 `keeper_skill` 하나가 중앙값 22,093바이트이고 3,213개 요청(99.9%)에 실려요. 모든 도구 스키마 바이트의 22.5%예요. 다음으로 큰 상시 도구는 `BrowserSession`(4,725바이트, 4.7%)이에요. `BrowserInteract` 는 25,659바이트로 스키마가 가장 크지만 요청의 15.5%에만 실려요.
- `keeper_skill` 설명 끝의 스킬 목록(`Available:` 블록)은 중앙값 19,425바이트예요. 행이 중앙값 50개(최대 56개)이고, 행 하나는 identity JSON 평균 103바이트와 스킬 설명 평균 287바이트예요. 블록의 26.1%가 identity, 73.1%가 설명이에요. 서로 다른 목록이 20개라서 Keeper 와 시점에 따라 목록이 달라요.
- 같은 기간 `keeper_skill` 호출은 1,235번이에요(Keeper 27명, 스킬 40종). `usage` 이벤트가 있는 Keeper 의 1,052번을 모델 요청 35,684개로 나누면 100요청에 2.95번이에요. 목록을 실은 Keeper 23명은 모두 한 번 이상 불렀어요.
- 호출은 몰려 있어요. Keeper 일곱 명이 호출의 84.4%를 불렀고, 스킬 셋(`masc-pr-adversarial-read`, `masc-pr-review-grades`, `masc-guard-approval`)이 58.6%예요. `msx-retro-mania` 는 모델 요청 4,463개에 31번(100요청에 0.69번)이에요.
- 이 비용은 `RFC-0411` 이 다루는 값이에요. RFC 는 스킬 14개일 때 목록이 3,605바이트였고(§4.1 적용 뒤) 카탈로그가 자라면 비용도 따라 자란다고 적었어요(§1.4). 지금은 행 중앙값 50개, 19,425바이트예요. RFC 에 이 측정을 덧붙였어요(§1.6). 매 요청에 싣는다는 결정(§8.1)을 되돌리는 일이라서 이번에는 목록을 줄이지 않고 측정만 했어요.
- 바이트와 토큰은 달라요. 이 목록이 제공자 캐시에서 읽히는 토큰의 몫인지는 못 쟀어요.

### `_blob` 흉내

도구 호출의 `input` 에 `_blob` 키가 든 행이 10-19~11-04T19:10Z 에 2,816건이에요. 스크립트와 정의는 `docs/evidence/blob-input-2026-11` 에 있어요.

- `_blob` 하나뿐인 호출(`alone`)이 2,464건이고 2,463건이 실행 전에 거절됐어요(`disposition` 이 없고 `wire_outcome` 이 `error`). 거절된 호출은 도구가 실행되지 않았지만 모델이 그 호출을 만든 응답 한 번을 썼어요.
- 다른 키와 섞인 호출(`mixed`)은 352건이에요. 진짜 인자 옆에 `_blob` 키를 하나 더 붙인 모양이고, 257건이 실행됐어요. 도구가 모르는 키를 무시해서요.
- `alone` 의 `_blob` 값은 봉투(`bytes`, `mime`, `preview`, `sha256` 네 필드)가 1,344건, 진짜 인자를 `_blob` 아래에 넣은 것이 784건, 객체가 아닌 것이 336건이에요.
- 도구는 `masc_board_comment` 1,221건, `Write` 478건, `Execute` 305건, `keeper_memory_write` 154건 순이에요. Keeper 는 `masc-productor-owner` 520건, `wkbl-front` 457건, `code-reviewer` 372건 순이에요.

**모델이 이 모양을 보는 길.** 이슈 본문은 Recent Actions 가 거절된 호출의 인자를 다시 보여 줘서 생긴다고 적었어요. 요청 기록을 열어 보니 더 큰 길이 있었어요.

- 시스템이 이미 끝난 호출의 인자를 `{"_blob": {"sha256", "bytes", "mime", "preview"}}` 로 줄여서 모델에 보냈어요(RFC-0363 의 `Keeper_model_input_demotion`, `with_reference`, `keeper_model_input_demotion.ml:167`). 모델이 보는 지난 호출이 도구 스키마에 없는 모양이 돼요. 줄인 원본은 blob 으로 저장하므로, 저장소에 같은 크기의 blob 이 있는 줄인 인자를 "저장된 강등"이라고 불러요.
- 저장된 요청 5,244개 중 4,371개(83.4%)에 저장된 강등이 있어요. `masc-productor-owner`(deepseek-v4.1-flash)는 요청의 95.4%에 중앙값 334개가 들어 있고, 줄인 바이트의 중앙값이 366 KB(본문의 29.9%)예요. 이 Keeper 의 요청 하나를 열어서 assistant 메시지의 `masc_board_comment` 호출 `input` 이 `{"_blob": {"sha256": "4f394ce0…", "bytes": 4698, …}}` 인 것을 확인했어요.

**모델마다 따라 하는 정도가 달라요.** 같은 Keeper 의 저장된 요청 두 개 사이에 든 `_blob` 하나뿐인 호출을, 뒤쪽 요청이 끝낸 턴의 호출로 세어서 모델별로 나눴어요.

저장된 강등이 없는 턴 845개에서는 어느 모델도 호출을 만들지 않았어요. 읽을 때 조심할 것이 셋이에요.

- 모델마다 쓰는 Keeper 가 달라서 모델 차이만으로 읽을 수는 없어요.
- 턴을 끝낸 요청에는 그 턴 앞쪽 호출의 줄인 인자도 들어 있어요. 호출이 많은 턴에 저장된 강등이 더 많이 보일 수 있어서, 이 표는 같이 나타난다는 것까지만 보여 줘요.
- 호출 2,464건 중 표에 든 것은 977건이에요. 나머지 1,487건은 10-28T11:08Z 까지의 호출이라, 그때는 그 Keeper 의 저장된 요청이 아직 없었어요.

**언제 멈췄나.**

- 저장된 강등이 마지막으로 보인 시각은 deepseek-v4.1-flash 11-04T01:50Z, glm-5.3 08:09Z, nemotron 08:39Z, glm-5.3-flash 08:59Z 예요. 11-04T09:00Z 부터 19:10Z 까지는 저장된 요청 531개에 저장된 강등이 하나도 없어요. 이미 보낸 메시지를 다시 쓰지 않게 한 RFC-0363 §3.4.1 개정(#48123)과 코드(#48124)가 11-04T08:53Z 에 병합됐어요. 서버를 언제 다시 띄웠는지는 기록에서 못 찾았어요.
- `_blob` 하나뿐인 호출의 마지막은 11-04T03:54Z 예요. deepseek-v4.1-flash 의 마지막 호출은 00:21Z 이고, 마지막 3건(03:41~03:54Z)은 nemotron 이에요. 호출이 병합보다 5시간 먼저 멈춰서, 멈춘 이유를 이 수정으로 설명할 수 없어요. 그 무렵 호출을 만들던 `masc-productor-owner` 와 `wkbl-front` 는 저장된 요청의 모델이 deepseek 에서 GLM 과 nemotron 으로 바뀌었어요. 2시간 단위로 센 값이고 스크립트에 넣지 않은 일회성 집계예요.

**베낀 것이 아니라 지어낸 값.** 봉투 1,344건 가운데 `sha256` 의 blob 이 저장소에 있는 것은 7건이고 1,337건(99.5%)은 없어요. 요청 기록에서 본 강등된 인자의 해시는 12,855개 중 12,313개(95.8%)가 blob 이 같은 크기로 있어요. 기록에서 복사한 해시라면 대부분 있어야 해서, 모델이 봉투 모양을 따라 해시와 크기를 지어낸 거예요(`config/prompts/keeper.md` 문단이 "해시를 지어내지 않는다" 고 적은 일이에요). 예: 11-04 00:16Z `masc-productor-owner` 가 `masc_board_comment` 를 `{"_blob": {"bytes": 2905, "sha256": "a5bc9d78…", …}}` 로 불러 거절됐고, 그 해시의 blob 은 저장소에 없어요. 6.8초 뒤 같은 글을 제대로 된 인자로 다시 보내서 실행됐어요.

**Recent Actions.** 이슈가 제안한 수정(거절된 호출의 인자를 다시 보여 주지 않기)은 만들지 않았어요. 줄인 인자가 사라진 11-04T09:00Z 뒤에 deepseek-v4.1-flash 의 저장된 요청이 294개 있는데 `_blob` 하나뿐인 호출은 0건이에요. 이 요청들이 큰 쓰기를 하는 Keeper 의 것인지는 따로 보지 않았어요. 큰 쓰기를 하는 Keeper 가 deepseek 로 다시 돌 때 호출이 돌아오는지 보면, 이 수정이 필요한지 알 수 있어요.

**프롬프트 문단.** `config/prompts/keeper.md` 에 `_blob` 을 새 호출의 인자로 쓰지 말라는 문단이 있어요(#46216, 10-27 10:45 KST 에 main 에 들어갔고 배포 시각은 확인하지 못했어요). `_blob` 하나뿐인 호출은 10-26 413건, 10-27 405건이었다가 10-28 32건, 10-30 19건, 10-31 4건이 됐고 11-01 에는 한 건도 없어요. 11-02 에 610건으로 돌아왔어요. 10-28 까지의 호출은 저장된 요청이 없어 모델을 알 수 없어요. 문단의 효과라고는 못 해요.

**남은 일(코드는 안 썼어요).**

- 모양을 지키는 강등(긴 문자열 값만 줄임)은 거절을 실행으로 바꿔요(추론, 재지 않았어요). 모델이 지난 호출을 베끼면 줄어든 값이 그대로 실행돼서 글이 잘린 채 게시되고 파일이 잘린 채 써져요. 지금의 실행 전 거절이 안전한 쪽이에요.
- RFC-0363 §3.4.1 은 줄인 인자가 요청에 들어가는 길이 둘 남아 있다고 적었어요. 크기 거절 뒤 재전송과 Official client host 의 인자 투영이에요. 둘 다 11-04T09:00Z 뒤 저장된 요청에는 안 보였어요.
- 증거는 `RFC-0363` §3.4.2 에도 옮겼어요. 표현을 바꾸는 일은 해시를 인용하는 계약과 캐시에 닿아서 RFC 로 정할 일이에요.

- Keeper 한 명이 실행 하나를 기다린 것을 한 개로 세면 188개예요. 기다림 188개 중 117개(62.2%)는 폴링 한 번으로 끝났어요. 폴링(실행 번호가 든 `sleep` 호출)은 277번이에요. 기다림 하나에 막힌 시간은 중앙값 7.1분, p90 17.0분, 최대 46.7분이고, 폴링 시간을 한 번씩만 더한 합계는 27.41시간이에요(Execute 시간의 23.4%. 턴 구간 안은 24.75시간이고 턴 시간의 3.1%).
- 기다림 188개 중 명령에 저장소 이름이 보이는 156개는 `jeong-sik/masc` 95개(11.83시간)와 `jeong-sik/wkbl` 61개(11.07시간)예요. 32개(4.52시간)는 이름이 안 보여요.
- Keeper 가 자기를 깨우는 일정 240건 중 81건(Keeper 와 실행 번호 쌍으로 68쌍)의 메시지에 실행 번호가 있어요. 깨우는 시각(`due_in_sec`)은 중앙값 1,500초(25분), p10 900초, p90 3,600초예요. `wkbl-data`, `masc-productor-owner`, `sangsu`, `wkbl-front`, `e-masc-the-leader` 다섯 명은 `sleep` 기다림과 이 일정을 둘 다 가졌어요. 같은 실행에 둘 다 썼다는 뜻은 아니에요.
- 날마다 달라요. 60초 이상 걸린 `sleep` 호출의 시간은 11-01 이 0.44시간, 11-02 가 12.88시간, 11-03 이 8.10시간, 11-04 가 11.18시간이에요.
- 같은 창에서 기다리는 동안 쌓인 일도 `measure_lane_time.py` 로 다시 쟀어요. 위임·채팅 작업이 시작 전에 기다린 6,703.7분 중 같은 Keeper 의 60초 이상 Execute 와 겹친 것은 216.8분(3.2%)이고, 일정 깨움이 기다린 482.2시간 중 겹친 것은 21.6시간(4.5%)이에요. 아래 "기다리는 동안 다른 일이 쌓였는지"의 11-04T19:10Z 까지 값(1.9%, 3.8%)보다 커요.
- 같은 기다림을 푸는 길이 둘이에요. 하나는 Keeper 체크아웃에서 `gh run watch` 같은 감시 프로세스를 띄우고 끝나면 깨우는 길이에요. microvm·remote_ssh 에서는 RFC §8 의 3·4층이 필요해요. 다른 하나는 서버가 GitHub 실행의 끝을 보고 Keeper 를 깨우는 길이에요. 체크아웃의 프로세스는 필요 없지만 서버가 GitHub 를 읽을 신원이 있어야 해요. 뒤쪽을 `docs/rfc/RFC-0379-keeper-monitor-event-wake.md` §6 에 제안으로 적었어요. 이 측정은 어느 쪽이 나은지 가르지 못해요.

### 기다리는 동안 다른 일이 쌓였는지

위임·채팅 작업은 Keeper 하나가 한 번에 하나만 돌려요. 11-01~11-04T19:10Z 에 만들어진 1,220건 중 시작한 1,217건의 대기를 §1.4 와 같은 스크립트로 쟀어요.

- 시작 전에 기다린 시간이 합계 6,271.3분이에요. 그중 같은 Keeper 가 60초 이상 Execute 를 돌던 시간과 겹친 것은 119.4분(1.9%)이에요.
- Execute 가 도는 중에 만들어진 작업은 17건이고, 모두 그 Execute 가 끝난 뒤에야 시작했어요. 대기는 중앙값 223.2초, 합계 85.8분이에요.
- 같은 Keeper 의 턴과 겹친 시간은 1,401.8분(22.4%)이에요. 나머지 대기는 그 Keeper 의 턴이 돌지 않을 때 생겼어요. 이유는 가리지 못했어요. trace 파일이 없는 Keeper 는 겹침이 0으로 잡혀요.
- 일정으로 깨우는 이벤트(`schedule_due`)도 같은 방식으로 쟀어요. Keeper 의 reaction 원장(`keepers/<이름>/reaction-ledger/v7`)에 같은 기간 이벤트 4,823건이 있고 모두 `schedule_due` 예요. 3,241건은 턴이 시작됐고 1,567건은 큐에서 취소됐고 15건은 턴이 시작되지 않았어요. 턴이 시작된 3,241건이 큐에 들어와서 시작되기까지 기다린 시간은 중앙값 3.6초, p90 494.3초, 합계 458.6시간이에요.
- 그 기다림 중 같은 Keeper 가 60초 이상 Execute 를 돌던 시간과 겹친 것은 17.6시간(3.8%)이고, 같은 Keeper 의 턴이 돌던 시간과 겹친 것은 249.0시간(54.3%)이에요. 30분 이상 기다린 173건이 388.5시간(84.7%)이에요. Keeper 별로는 `e-masc-the-leader` 121.8시간(26건), `sangsu` 91.5시간(22건), `masc-productor-owner` 42.1시간(33건), `wkbl-front` 37.3시간(24건), `wkbl-data` 21.8시간(14건)이에요.
- 비동기 Execute 가 일정 깨움의 기다림에서 줄일 수 있는 크기는 많아야 17.6시간(3.8%)이에요. 그 시간에 다른 턴을 돌려도 모델 요청이 같은 계정의 허용 수에 걸릴 수 있어서 실제로는 이보다 작을 거예요(추정, §1.4). 30분 넘게 기다린 이유(다른 턴을 돌았는지, 그 이벤트를 나중에 골랐는지)는 가리지 못했어요. Board 멘션으로 깨운 턴은 이 원장에 없어서 못 쟀어요.
- 턴이 취소된 일도 쟀어요. `Turn_cancelled` 로 끝난 작업 106건 중 같은 Keeper 의 Execute 가 도는 중에 취소된 것은 3건이고, 그때 날아간 Execute 시간은 합계 37.1초예요. 60초 이상 Execute 가 도는 중에 취소된 작업은 없어요. 턴이 끝나도 Execute 를 이어 가게 해서 건질 시간이 이 경로에서는 거의 없어요.

### 막힌 곳

- 조사가 낸 가장 작은 조각은 "Docker 프로필 한정 Workspace process 시작 도구"예요. 설정 43개 중 1개에만 닿고, 위 5명에게는 닿지 않아요. 이 조각만 내면 수요에 대한 효과를 못 재요.
- microvm·remote_ssh 에 닿으려면 RFC §8 의 3·4층(엔드포인트가 프로세스 수명을 가지는 프로토콜과 microVM·SSH 어댑터)이 필요해요. 시작 도구만으로는 안 돼요. 호스트에서 프로세스를 띄우거나 전송을 백그라운드로 돌리는 것은 엔드포인트 수명을 구현한 것이 아니라고 RFC §2 가 말해요.
- 시작은 Execute 와 같은 Gate 입구를 지나야 해요(RFC §2). 그런데 Execute 본문(`handle_tool_execute_typed`, `lib/keeper/keeper_tool_execute_runtime.ml:353-1296`)이 약 940줄짜리 한 함수예요. 안에 `redact` 가 17곳, `Remote_ssh` 가 10곳, `Gate` 가 5곳 있어요(`rg` 로 센 값). 시작과 결과 읽기를 따로 떼려면 이 함수를 먼저 나눠야 해요.
- Execute 를 서버 fiber 에서 돌리는 조각은 코드로는 나눌 수 있어요. 나누는 지점은 Gate 가 Allow 를 돌려준 뒤(`keeper_tool_execute_runtime.ml:781`)부터 `Execute_shell_ir.dispatch` 호출(`:975`) 앞까지예요. 막는 곳은 세 군데예요.
  - 위의 한 함수.
  - `Execute_shell_ir.dispatch` 가 거절 검사(typed gate, 경로 검사)와 실행을 한 번에 해서(`lib/keeper_tooling/execute_shell_ir.mli:49-63`), 서버 fiber 로 넘기면 거절이 턴이 끝난 뒤에야 알려져요.
  - Gate 모드가 `auto_judge` 이면 명령이 Gate 안에서 끝나요(`keeper_gate.ml:1825`). 라이브 Gate 는 10-17 부터 `always_allow` 라서 지금은 안 걸려요(`~/me/.masc/gate/mode.json`).
- 그래도 이 조각은 RFC 의 수명 요구를 못 채워요. 실행 셈(shim)에는 떼어 내는 기능이 없고, 입력 채널이 닫히면 취소로 읽어요(`lib/exec_shim/exec_shim.ml:1060-1068`). 서버가 죽으면 명령도 같이 죽을 거예요(추정, 실험은 안 했어요). `Keeper_msg_async` 는 워커 없이 복구된 미완료 요청을 `Lost` 로 둬요(`lib/keeper/keeper_msg_async.mli`). RFC 는 프로세스 수명을 엔드포인트가 가진다고 요구해요(§2, 시험 A02·A03·A11).
- 기존 `keeper_owned_job_completion_wake` 를 복사해 두 번째 wake 를 만들면 N-of-M 패치예요. 공통부를 뽑거나 payload 를 일반화해야 해요.
- `RFC-0290` 은 코드 0건이고 동시 실행 상한이 Workaround Rejection Bar 와 부딪혀요. `RFC-spawn-a-process-that-outlives-the-call` 은 Execute 에 background 플래그를 다는 안을 거절하고, 스폰이 턴을 넘겨야 하는지를 열어 둬요.

### 시작하지 않은 이유

RFC 는 이미 진행 중인 계획(`goal-keeper-async-fleet-20261026`)이에요. 이 변경은 Gate, 프로세스 수명, 재시작 복구를 함께 건드려요. 이 저장소 규칙은 로컬 dune 빌드 없이 CI 로만 확인하라고 하는데, type-check 한 번이 8분 30초 걸려요(run 41895911884). 여러 층에 걸친 변경을 그 속도로 맞추면서 RFC 의 시험 A02·A03·A05(§9)를 증명할 수는 없었어요.

이 보고서가 RFC 에 더하는 것은 세 가지예요. 수요가 microvm·remote_ssh 에 있으니, 효과를 재려면 3·4층에서 microVM 한 종류와 remote_ssh 를 먼저 지원해야 해요. 그리고 Execute 를 기다리는 시간으로 얻을 수 있는 크기는 작아요. 11-04T19:10Z 까지 창에서는 `sleep`·반복 폴링이 턴 시간의 4.0%였고, 그 사이 쌓인 위임·채팅 작업의 대기는 1.9%, 일정 깨움의 기다림은 3.8%였어요. 11-05T05:00Z 까지 창에서는 실행 번호가 든 폴링이 막은 시간 중 턴 구간 안이 턴 시간의 3.1%(GitHub 호출 전체는 4.5%)이고, 쌓인 일의 대기는 위임·채팅 3.2%, 일정 깨움 4.5%예요. 마지막으로 오래 걸린 호출의 대부분은 GitHub 실행을 기다리는 것으로 보여서(위 "무엇을 기다리나"), 같은 수요를 서버가 실행의 끝을 보고 깨우는 길로도 풀 수 있어요. 이 길은 `docs/rfc/RFC-0379-keeper-monitor-event-wake.md` §6 에 제안으로 적었어요. RFC 가 겨냥하는 다른 것(재시작 복구, 위임 상호 대기, A07~A17)의 수요는 이 측정에 들어 있지 않아요. 닿은 뒤의 확인은 `blocked_waits.wait_time_pct_of_execute`(§9)와 위 5명의 60초 이상 Execute 시간으로 해요.

## 7. Delegate

### 호출

- `masc_keeper_delegate` 394호출 중 375호출(95.2%)을 받아들였어요. 10-05~10-31 에는 1,362호출 중 187건(13.7%)이 실패했어요.
- 11-01~11-04 실패 19건은 이름 오류 11건, 입력 모양 오류 7건, 서버가 막 재시작한 직후 1건이에요. 이름 오류는 `keeper not found: <이름>` 이고, 이름이 에이전트 식별자(`masc-pro-builder`, `claude-8241c5b1`)이거나 `root`, `admin` 이에요. 입력 모양 오류는 `prompt` 대신 `message` 를 쓴 호출 4건, `target` 안에 `keeper_name` 을 쓴 호출 1건, 빈 입력 1건, `_blob` 모양 입력 1건이에요. 모두 실행 전에 거절돼서 비용은 호출 한 번이에요.
- 개선 후보는 "없는 이름이면 가능한 이름을 알려 준다"와 "`message` 로 보내면 `prompt` 를 쓰라고 알려 준다"예요. 하지만 4.8%의 실패에서 호출 하나씩을 아끼는 정도라서 이번에는 하지 않았어요.
- 이 도구는 이미 비동기예요. 제출은 곧바로 돌아오고, 요청을 받은 Keeper 가 그 턴을 마치면 제출한 Keeper 를 완료 알림으로 깨워요(`keeper_delegate_completion_wake`). 남은 비용은 아래 상태 조회였어요.

### 받아들인 위임이 끝난 모습

작업 DB(§1.4 와 같은 스크립트)로 받아들인 위임 375건의 끝을 봤어요. 제출을 받아들인 호출 수와 같아요.

- 305건(81.3%)이 성공했고 68건이 실패, 2건이 취소됐어요. 위의 95.2%는 제출이 받아들여졌다는 뜻이고, 위임한 일이 성공했다는 뜻이 아니에요.
- 실패 68건은 `Turn_cancelled` 36건과 `Turn_exception` 32건이에요. `Turn_cancelled` 중 35건의 사유는 "Keeper owner stopped the active turn"이에요(`lib/keeper/keeper_owner.ml:1779`). `Turn_exception` 중 21건은 auth status JSON 파싱 오류이고 5건은 제공자 사용량 한도예요.
- 받은 Keeper 에서 시작 전 대기는 중앙값 0.1초, p90 586.4초예요. 돌아간 시간은 중앙값 109.7초, p90 807.7초예요. 실패·취소 70건이 돌아간 시간은 합계 661분이에요.
- 이 실패는 도구 설명이나 입력 모양으로 고칠 수 있는 것이 아니에요. 턴을 멈춘 것과 런타임·제공자 오류예요.

### 상태 조회(#48343)

- `masc_keeper_delegate_status` 는 164호출이에요. 위임 호출 394건의 42%예요. 결과는 저장된 위임 기록 전체였어요. 호출한 Keeper 가 직접 보낸 요청 본문(`input`), 보낸 사람 정보(`source`), 해시 둘이 대부분이에요.
- #48343 은 상태, 그 시각, 실패 사실, 성공했을 때의 `completed_reply` 만 돌려줘요. 같은 164호출을 다시 돌려 보면 결과가 430,806바이트에서 154,211바이트로 줄어요(64.2%).

## 8. 아직 모르는 것

- 이 개선이 실제 Keeper 의 호출 수와 결과 바이트를 얼마나 줄이는지는 배포 뒤에야 알아요. 재생 값은 하나의 스케줄에서 나온 추정이에요.
- 재조회 중 모델이 꼭 필요했던 비율, Official client 레인의 필요한 재조회 몫.
- `keeper_artifact_read` 중 글자를 찾으려고 여러 쪽을 읽은 호출이 몇 건인지. 줄바꿈이 있는 글을 같은 턴에서 여러 위치로 읽은 3,776건(22%)이 상한이에요.
- `masc_dos_press` 결과가 모델 입력에 한 벌만 들어가는지, `content` 와 `structuredContent` 가 모두 들어가는지. Keeper 쪽 코드는 `content` 블록(텍스트와 이미지)을 모델용으로 넘기고 전체 결과를 `data` 로 로그에 남겨요(`lib/keeper/keeper_lane_addon_runtime.ml:49-51`). 그 뒤 모델 요청에 실제로 실리는 모양은 확인하지 못했어요.
- Execute 호출 시간의 p99 가 47초인데, 이 값이 실행 시간인지 기다림인지(Agent Core 가 재서 준 값이에요).
- 통계 화면의 실서버 응답과 브라우저 확인(#48240 배포 뒤).
- 제공자 승인 대기 479.6시간이 호출 사이 시간과 첫 호출 전 시간 중 어디에 들어가는지(같은 요청끼리 짝짓기), 그리고 허용 수(permit)를 늘리거나 Keeper 를 다른 계정으로 옮길 때의 효과.
- 위임·채팅 작업이 시작 전에 기다린 시간의 78%가 그 Keeper 의 턴이 돌지 않을 때 생긴 이유, 일정 깨움이 30분 넘게 기다린 이유, 그리고 Board 멘션으로 깨운 턴의 대기(§6).
- "무엇을 기다리나"(§6)의 "그 밖" 195건(12.48시간)과 `gh` 를 쓰지만 실행 번호가 없는 204건(11.88시간)이 무엇을 기다리는지.
- 실행 기다림 188개 중 32개가 어느 저장소의 실행인지, 그리고 기다린 실행이 PR 의 checks 인지 PR 에 붙지 않은 실행인지(§6).
- 도구 통계 저장소에 `failure_class` 를 넣는 것은 스키마 변경이라 하드 컷 규칙을 정해야 해서 하지 않았어요.
- 이미지 한 장이 입력 토큰으로 얼마인지. `msx-retro-mania` 본문은 다른 Keeper 의 6~11배인데 요청당 평균 입력 토큰은 1.15~1.53배예요(§1.5). 같은 턴의 `usage` 와 저장된 요청의 이미지 수를 맞춰 보면 알 수 있어요.
- `keeper_skill` 목록이 제공자 캐시에서 읽히는 토큰의 몫. 스크립트가 구분하는 값이 아니에요(§1.6).
- 호출이 모델 요청보다 많은 Keeper(`code-reviewer-sister` 는 호출 121, 모델 요청 42)가 한 응답에 `keeper_skill` 을 여러 번 부르는지, `usage` 이벤트가 일부 턴에 없는지.
- 저장된 요청 본문이 그 턴의 어느 요청(첫 요청인지 마지막인지)인지. 턴마다 하나만 저장돼서 모델 요청의 9.0%만 보여요.
- `msx-retro-mania` 8339~8361번 턴이 `sse_stream_incomplete` 로 끝난 이유(요청 크기인지 런타임 쪽인지), 그리고 8362번 턴에서 본문이 113 MiB 에서 2.9 MiB 로 줄어든 이유.
- 큰 쓰기를 하는 Keeper 가 deepseek 로 다시 돌 때 `_blob` 하나뿐인 호출이 돌아오는지. 줄인 인자가 사라진 11-04T09:00Z 뒤 deepseek-v4.1-flash 의 저장된 요청 294개에서는 0건이었어요.
- 저장된 요청에 크기 거절 뒤 재전송 요청과 Official client host 의 인자 강등이 들어오는지. 11-04T09:00Z 뒤 저장된 강등이 0이라 이 구간에서는 안 보였어요.

## 9. 배포 뒤 다시 재기

```bash
scripts/measure-tool-efficiency.py --base-path <base> --from-date <배포 다음 날짜> --to-date <기준선과 같은 일수가 되는 날짜> --json-out after.json
```

기준선 JSON 과 같은 항목을 `after.json` 에서 비교해요. 기준선과 같은 일수로 재야 하고, 모델이 새 인자를 쓰기 시작하기까지 시간이 걸릴 수 있어요(추정). 비교할 행:

## 부록: #47642 에 달 코멘트 초안

원장을 10-19 ~ 11-04T19:10Z 로 넓혀 다시 세고, 요청 기록을 열어 `_blob` 이 모델 눈에 들어오는 길을 확인했어요. 이슈 본문에 적힌 원인 가운데 Recent Actions 는 두 번째 길이에요.
