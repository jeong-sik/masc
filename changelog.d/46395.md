### Changed

- Fresh state required: each browser source now has its own Lane Add-on package and worker: `browser-automation`, `browser-stagehand`, `browser-firefox`, `browser-ego` and `browser-external`. A failure of one source ends only its own worker. The `browser` package that served every source in one worker is removed, and `browser_backend` is required in a browser package's `lane.toml`. Before deploying, detach the old `browser` instance and confirm `released`, remove `browser.toml` and `.masc/packages/browser`, and move `[runtime.addon_exact_lanes.browser.locate]` to `browser-automation.locate` and `[runtime.addon_exact_lanes.browser.stagehand]` to `browser-stagehand.stagehand`; `masc browser-lane-setup` refuses while the old declaration is there and names each old exact-output table with the table to move it to. Old native cleanup descriptors are not read. (#46395)
- `masc browser-lane-setup` declares one browser Add-on per source the workspace runs, by the rule the runtime starts a worker by: automation, the owned Firefox and ego when runtime.toml has their table or the run writes it, Stagehand when `[browser.stagehand]` is present, each only while its lane is not switched off with `enabled = false`, and external hosts when the run installs a native host or one is installed. It writes the mode's tables before declaring, refuses a runtime.toml that does not parse, and lists the sources it declared before a refusal. A source whose table is missing or whose lane is switched off does not start, and its package row says which. (#46395)
- The deployment preflight refuses a workspace where two enabled declarations serve the same browser source, since the host uses neither. (#46395)
