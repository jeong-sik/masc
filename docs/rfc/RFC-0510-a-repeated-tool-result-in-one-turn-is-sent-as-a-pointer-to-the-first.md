# RFC-0510: 한 턴에서 같은 도구 결과가 되풀이되면 두 번째부터는 첫 결과를 가리키는 짧은 결과로 보낸다

- 상태: 초안
- 이슈: #49559
- 근거: §2 의 수치는 `docs/evidence/repeated-tool-results-2026-11` 의 스크립트로 2026-11-07T03:29Z ~ 03:35Z 에 쟀다. 바이트이고 토큰이 아니다. 모델이 스텁을 어떻게 읽는지는 재지 않았다. §3 의 코드는 `origin/main` `ece6574053d` 이다.
- 먼저 있는 결정: `tool-results-age-out-of-context`(#49185)는 끝난 턴의 큰 결과를 마커로 바꾼다. 지금 턴의 결과는 건드리지 않는다. 이 RFC 는 그 빈자리, 곧 지금 턴 안의 반복만 다룬다.

## 0. 요약

한 턴이 같은 도구를 불러 같은 결과를 받으면, 두 번째 결과가 첫 결과와 같은 바이트를 한 번 더 요청에 싣는다. 턴이 끝날 때까지 모든 요청이 둘 다 나른다. 끝난 턴의 결과는 마커 규칙이 줄이지만, 끝나지 않은 턴에는 줄이는 규칙이 없다.

11-06 09:52Z ~ 11-07 03:00Z 에 저장된 요청 599개(턴마다 하나, 프롬프트 995.7 MB)를 세었다. 같은 턴의 앞 결과와 글자가 같은 1 KB 이상 결과 칸이 2,633개, 11.83 MB 이고 프롬프트 바이트의 1.19% 다. 스텁이 350 B 이면 프롬프트의 1.10% 가 준다.

- 평균은 작고 꼬리가 크다. 요청 599개 중 29개만 반복을 싣는다. 요청 하나가 줄 수 있는 몫은 p50 과 p90 이 0 이고, p99 가 36.7%, 최대가 48.7% 다.
- 반복의 90.5% 가 Keeper 하나(`kidsnote-incoming-dd-manager`)의 것이다. 그 Keeper 의 요청 19개에서 34.9% 가 반복이다. 이 Keeper 와 `e-masc-the-leader` 를 빼면 0.02% 다.
- 시간으로도 쏠린다. 14:00Z 앞 4시간 8분은 5칸(0.00%), 뒤 13시간은 4.73% 이고, 11-07 01Z 한 시간은 21.7% 다.
- 장부(호출을 한 번씩 센다)에서 `BrowserRead` 871번 중 832번이 같은 턴 안에서 앞 호출과 같은 답이다. `masc_board_post_get` 과 합치면 장부 반복 바이트의 99.4% 다. 날짜별 몫은 0.25% ~ 6.96% 로 크게 달라지고, 앞서는 도구도 날마다 다르다.
- 도구가 선언한 답의 지문으로 세어도 2,634칸으로 한 칸 차이다. 영수증 칸(시각, 실행 시간) 때문에 글자가 달라진 반복은 이 구간에 거의 없었다.

이 RFC 는 두 번째부터 첫 결과를 가리키는 짧은 결과(스텁)를 보낸다. 켜는 단위는 도구 TOML 이고, 처음엔 읽기만 하는 도구 둘이다. 반복을 끊거나 턴을 끝내거나 Keeper 에게 말을 얹지 않는다. 반복이 일어나는 까닭(§2.4)은 건드리지 않는다. 바뀌는 것은 반복 하나의 크기다. `BrowserRead` 결과 5,478 B 가 약 350 B 가 된다.

함대 평균 1.19% 만으로는 이 RFC 를 받을 이유가 약하다. 이득은 반복이 길어진 Keeper 에 몰린다. 그 Keeper 의 요청이 3 MB 까지 자랐고(#49559) 마지막 저장된 요청의 397칸 1.72 MB 가 반복이다. 스텁은 이 기울기를 줄일 뿐 만드는 까닭을 없애지 못한다.

## 1. 결정

- D1. 같음은 두 `tool_result` 칸의 글자가 바이트까지 같음이다. 같은 Keeper·같은 세션·같은 턴 안에서만 센다. 도구가 선언한 답의 지문(`Keeper_tool_answer`)은 쓰지 않는다(§3.1).
- D2. 같은 턴의 첫 결과는 그대로 보낸다. 글자가 같은 두 번째부터는 스텁을 보낸다. 가리키는 곳은 늘 그 턴의 첫 결과다. 앞 턴의 결과는 가리키지 않는다.
- D3. 스텁은 사실만 적는다. 필드는 첫 결과의 `tool_use_id`, 원래 바이트 수, 글자의 sha256 이다. 지시문과 권고 문장은 없다. 형식은 §5-1 의 열린 질문이다.
- D4. 2,048 B 미만의 결과는 바꾸지 않는다. 마커 규칙의 문턱이다. 새 숫자를 만들지 않고 그 상수를 쓴다. 이 구간의 같은 턴 반복은 모두 2 KB 이상이라서 1 KB 문턱과 값이 같다(2,633칸 11.83 MB).
- D5. 바꾸는 곳은 공급자로 가는 사본이다. 요청을 만들 때마다 같은 턴의 앞 메시지만 보고 정하는 순수 함수다. 그래서 결과가 처음 요청에 실릴 때부터 스텁이고, 뒤 요청에서도 같은 스텁이다. 공급자가 이미 쥔 메시지를 다시 쓰지 않는다(§3.2). 장부와 기록은 원본 그대로다.
- D6. 켜는 곳은 도구 TOML 이고 기본은 꺼짐이다. 처음 후보는 읽기만 하는 도구 `BrowserRead` 와 `masc_board_post_get` 이다(§2.3). `Execute` 같은 부작용 도구는 후보가 아니다.
- D7. 새 상태, 새 필드, 새 Gate 를 더하지 않는다. 스텁은 기록에서 요청마다 다시 계산하는 파생 값이다.
- D8. 코드는 이 RFC 가 받아들여진 뒤에 쓴다.

### 1.1 동작

```
요청을 만들 때, 지금 턴의 메시지를 앞에서부터 한 번 훑는다.
  first = {}                              # 글자의 sha256 -> 첫 결과의 tool_use_id
  각 tool_result 칸에 대해:
    도구가 꺼져 있거나, 미디어가 붙었거나, 글자가 2,048 B 미만이면 그대로 둔다
    key = sha256(글자)
    key 가 first 에 있으면 칸의 글자를 스텁(first[key], 바이트 수, key)로 바꾼다
    없으면 first[key] = 이 칸의 tool_use_id 로 적고 그대로 둔다
```

시험 케이스는 다음과 같다. 위치는 구현 PR 에서 정한다.

| 입력 | 기대 |
|---|---|
| 글자가 같은 결과 둘 | 첫째는 그대로, 둘째는 스텁 |
| 글자가 같은 결과 셋 | 둘째와 셋째가 모두 첫째를 가리킨다 |
| 한 바이트만 다른 결과 둘 | 스텁 없음 |
| 2,048 B 미만 | 스텁 없음 |
| 같은 글자가 앞 턴과 지금 턴에 하나씩 | 스텁 없음(지금 턴의 첫 결과다) |
| 한 메시지 안의 칸 둘이 같은 글자 | 앞 칸 그대로, 뒤 칸 스텁 |
| 도구가 꺼져 있음 | 스텁 없음 |
| 첫 결과가 요청에 없음 | 남은 결과가 그대로 간다 |
| 같은 기록에 같은 함수를 두 번 | 출력이 같다 |
| 기록 뒤에 메시지를 덧붙임 | 앞 부분의 출력이 바뀌지 않는다(접두 성질) |

## 2. 지금 모습

### 2.1 저장된 요청

기본값(글자가 같음, 1 KB 이상, 스텁 350 B)으로 잰 값이다. 표 전체와 다른 구간은 README 에 있다. 스텁 350 B 는 마커 글자의 크기에서 왔다. 저장된 요청 9개의 마커 535개가 348 ~ 461 B 였다.

| 구간 | 요청 | 프롬프트 MB | 같은 턴 반복 칸 | 반복 MB | 프롬프트 몫 | 스텁으로 줄 몫 |
|---|---:|---:|---:|---:|---:|---:|
| 11-06 09:52Z ~ 11-07 03:00Z | 599 | 995.7 | 2633 | 11.83 | 1.19% | 1.10% |
| 11-06 09:52Z ~ 14:00Z | 380 | 746.1 | 5 | 0.03 | 0.00% | 0.00% |
| 11-06 14:00Z ~ 11-07 03:00Z | 219 | 249.6 | 2628 | 11.79 | 4.73% | 4.36% |
| 첫 구간에서 dd-manager·leader 뺌 | 498 | 855.9 | 19 | 0.14 | 0.02% | 0.02% |
| 11-05 03:00Z ~ 11-06 03:00Z | 824 | 1768.1 | 630 | 4.37 | 0.25% | 0.23% |

512 B 이상을 세고 스텁이 300 B 이면 첫 구간의 줄어드는 몫이 1.41% 로 는다. 문턱이 낮고 스텁이 작을수록 는다.

11-05 03:00Z ~ 11-06 03:00Z 는 마커 규칙이 들어가기 전 하루다. 이날은 앞 턴에서 온 반복(0.43%)이 같은 턴 반복(0.25%)보다 컸다. 규칙이 들어간 뒤 앞 턴 반복은 0.02% 다. 같은 턴 반복은 그 규칙이 못 건드리는 몫이다.

### 2.2 한 Keeper

`kidsnote-incoming-dd-manager` 는 11-06 14:15Z 부터 자율 턴이 길어졌다(#49559). 마지막 저장된 요청(턴 2323, 02:49Z)은 메시지 1,044개이고 본문이 2.97 MB 다. 요청 안에 끝난 턴 다섯 개(69 ~ 423개 메시지)와 막 시작한 턴이 있다. 1 KB 이상 도구 결과 칸 412개 중 397개(1.72 MB)가 같은 턴의 앞 결과와 글자가 같다.

이 Keeper 의 장부 반복 832번은 모두 `BrowserRead` 다. 같은 페이지를 읽은 결과가 대부분 5,478 B 다.

### 2.3 도구

장부는 호출을 한 번씩 센다. 1 KB 이상 결과의 같은 턴 반복이다. 11-01 ~ 11-07 전체가 4,871번, 50.27 MB, 결과 바이트의 4.52% 다.

| 도구 | 호출 | 반복 | 반복 MB | 반복 몫 |
|---|---:|---:|---:|---:|
| `keeper_artifact_read` | 17345 | 1623 | 24.88 | 11.7% |
| `masc_schedule_notes_list` | 20530 | 710 | 8.02 | 3.5% |
| `masc_board_list` | 3082 | 395 | 6.32 | 66.1% |
| `BrowserRead` | 2718 | 955 | 4.23 | 24.4% |
| `masc_board_post_get` | 8329 | 406 | 2.55 | 4.6% |
| `Execute` | 93392 | 239 | 0.82 | 0.4% |

날마다 앞서는 도구가 다르다. `keeper_artifact_read` 의 24.88 MB 중 19.32 MB 는 11-01 하루의 값이다. 11-06 09:52Z 이후의 장부 반복 바이트는 `BrowserRead`(3.58 MB)와 `masc_board_post_get`(1.57 MB)이 99.4% 다. 날짜별 반복 몫은 11-03 의 0.25% 에서 11-06 의 6.96% 까지다.

### 2.4 반복이 일어나는 까닭

이 RFC 는 까닭을 모른다. 이슈 #49559 에 따르면 dd-manager 의 11-07T02:16Z 요청에서 어시스턴트 메시지 518개 중 513개가 같은 문장으로 시작한다. 이 Keeper 의 요청 기록은 한도 전(11-06 01:05Z ~ 14:15Z)에도 `glm-5.3-flash` 였다(08:59Z 한 번은 `ollama_cloud` deepseek). 이슈는 바뀐 것이 한 턴이 부르는 도구 횟수라고 적는다. 14:15Z 무렵 무엇이 바뀌었는지는 확인하지 못했다.

### 2.5 이미 있는 것

- 마커: 2 KB 이상의 큰 결과를 `[masc:blob sha256=… bytes=… mime=… answer_sha256=… preview=""]` 로 바꾼다. 끝난 턴에만 적용한다.
- `Keeper_model_input_demotion`: 끝난 턴의 결과를 그 턴이 끝난 뒤 첫 요청에서 한 번 마커로 바꾼다. 이 치환은 공급자가 이미 쥔 메시지를 다시 쓰므로 프롬프트 캐시 비용이 든다. 그래서 요청하는 곳이 둘뿐이다. 끝난 턴의 결과와, 크기 거절에 답하는 재전송이다(그 모듈 주석). 바뀌는 것은 공급자로 가는 사본이고 기록은 그대로다.
- `Keeper_tool_answer`: 도구마다 자기 출력에서 답을 읽는 법을 선언한다. 시각이나 실행 시간 같은 영수증 칸은 답이 아니다(`a-tool-declares-what-its-answer-is`, 구현됨).
- `Keeper_tool_progress_identity.digest_tool_io`: 호출의 입력·출력 지문. 장부의 `output_fingerprint` 가 이 값이다. 같은 지문은 같은 답이라는 뜻이다. 도구가 다루는 앱이 진전이 없다는 증거도, 턴을 끝낼 근거도 아니다(`.mli` 주석).

## 3. 왜 이 모양인가

### 3.1 답의 지문이 아니라 글자

두 기준을 쟀다. 글자가 같음은 2,633칸 11.83 MB 이고, 도구 답의 지문이 같음은 2,634칸 11.84 MB 다. 장부와 이어지지 않은 결과 11개는 지문 쪽에서 뺐다. 차이는 한 칸(12.6 KB)이다.

글자가 같으면 스텁이 가리키는 첫 결과가 두 번째 결과의 글자를 모두 이미 보여 준다. 잃는 것이 없다. 지문이 같을 뿐 글자가 다르면 영수증 칸이 다를 수 있고, 스텁은 그 칸을 모델에게서 가린다.

지문에도 장점이 있다. 저장소가 이미 쓰는 같은 답의 정의이고, 영수증 칸 때문에 글자가 어긋난 반복도 잡는다. 단점은 요청을 만드는 쪽이 도구마다 답 선언을 알아야 한다는 것이다. 다른 날 영수증 칸이 글자를 가르는 도구가 반복을 많이 만들면 이 선택을 다시 본다(§5-4).

### 3.2 캐시와 시점

`Keeper_model_input_demotion` 의 주석대로 공급자가 이미 쥔 메시지를 바꾸면 프롬프트 캐시가 깨진다. 이 RFC 의 스텁은 결과가 처음 요청에 실릴 때 이미 스텁이다. 정하는 데 쓰는 것이 그 앞의 같은 턴 메시지뿐이므로 뒤 요청에서도 같은 자리에 같은 스텁이 나온다. 메시지를 덧붙여도 앞 부분은 바뀌지 않는다(§1.1 의 접두 성질).

끝난 턴의 큰 결과는 마커 규칙이 첫 요청에서 한 번 마커로 바꾼다. 스텁(약 350 B)은 마커 문턱(2,048 B) 아래라서 마커 규칙이 건드릴 것이 없다.

### 3.3 가리키는 곳은 같은 턴의 첫 결과

앞 턴의 결과는 끝난 턴의 규칙으로 마커가 되어 있을 수 있다. 마커를 가리키면 모델이 원문을 보려고 한 번 더 읽어야 한다. 같은 턴의 첫 결과는 마커 규칙이 건드리지 않으므로 원문으로 요청에 남아 있다. 크기 거절 뒤의 재전송만 예외다.

가리키는 곳이 멀 수 있다. dd-manager 의 한 턴은 메시지 423개까지 길어졌다. 스텁은 첫 결과의 `tool_use_id` 를 적고, 위치를 찾는 일은 모델이 한다. 반복과 첫 결과 사이의 거리와 그때 모델의 행동은 재지 않았다.

### 3.4 대안

- 아무것도 하지 않고 Sonnet 이 돌아오는 2026-12-01 을 기다린다. 비용은 그동안 dd-manager 류 요청이 3 MB 로 간다는 것이다. 14:15Z 이후 길어진 까닭을 모르므로 Sonnet 이 돌아와도 같은 일이 안 생긴다고 말하지 못한다.
- 도구 안에서 한다. `BrowserRead` 가 앞 호출과 글자가 같으면 스스로 짧은 결과를 돌려준다. Claude Code 2.1.319 의 `Read` 가 이렇게 한다(바이너리 문자열 "File unchanged since last read"로 시작하고, 뒤에 앞 결과를 참조하라는 지시가 붙는다). 장점은 도구가 자기 결과를 가장 잘 안다는 것이다. 단점은 도구마다 구현해야 하고 턴 경계를 도구가 알아야 한다는 것이다. 이 RFC 는 하네스 쪽에서 한 번에 처리하는 길을 택한다. 스텁에는 지시를 담지 않는다.
- 기다림을 일정으로 넘긴다(`masc_schedule_create`). 이 도구는 지금 `defer_loading` 이다. 풀면 모든 Keeper 요청에 약 4 KB 가 얹힌다. 이 RFC 와 겹치지 않는다. 반복의 까닭이 기다림이면 그 길이 근본이다.
- 턴을 끊는 규칙. 하지 않는다. Keeper 의 행동을 정하는 장치는 더하지 않는다.

## 4. 측정

받아들여지면 구현 전에 같은 스크립트로 기준을 고정한다.

- 기준: `measure_repeated_results.py` 를 11-06 09:52Z 부터 24시간 구간에서 돌린 값. 요청 기록의 같은 턴 반복 MB 와 프롬프트 몫, 장부의 도구별 반복 몫. 구간이 차면 README 에 덧붙인다.
- 구현 뒤: 같은 명령을 켠 도구에 대해 돌린다. 저장된 요청에는 공급자로 간 사본이 남는다(마커가 거기에 보인다). 스텁도 거기에 보인다. 켠 도구의 2 KB 이상 같은 턴 반복 칸은 0 에 가까워야 한다. 스텁이 문턱 아래라서 스크립트가 반복으로 세지 않는다.
- 결과 지표: 켠 Keeper 의 요청 본문 바이트(`wire.body_bytes`), 턴당 도구 호출 수. 호출 수가 늘면(스텁을 받은 모델이 더 읽으면) 이 RFC 는 효과가 없는 것이다.
- 안 재는 것: 과제 성공률. 이 RFC 로는 잴 방법이 없다. 한 Keeper(dd-manager)에서 먼저 켜고 그 Keeper 의 턴을 읽어 확인한다.

## 5. 열린 질문

1. 스텁의 형식. 마커에 속성(`same_as=<tool_use_id>`)을 더하는 안과 새 형식(`[masc:same-result …]`)이 있다. 마커는 `sha256=` 로 보관소의 blob 을 가리키는데, 반복 결과를 blob 으로 또 저장하면 디스크가 는다. 디스크는 11-06 에 98% 였다. 스텁이 blob 없이 `bytes=` 와 sha256 만 적는 쪽이 후보다.
2. 같은 글자가 세 번째 올 때 가리키는 곳은 첫 결과인가 바로 앞 결과인가. 이 RFC 는 첫 결과로 두었다. 바로 앞이면 가깝지만 스텁을 가리키는 사슬이 생긴다.
3. 첫 결과가 요청에서 빠진 경우(압축이나 크기 거절 뒤의 재전송). 남은 결과가 그대로 가면 그 요청에서 같은 칸이 스텁에서 원문으로 바뀌어 캐시가 그 자리부터 깨진다. 압축은 어차피 그 뒤를 다시 쓰므로 문제가 없다고 보지만 확인하지 못했다.
4. 켤 도구 목록을 TOML 에 두면 새 읽기 도구는 꺼진 채로 시작한다. 목록을 데이터로 정하는 방법(주기적으로 재서 반복 몫이 큰 도구를 보여 주는 것)이 필요한가. 영수증 칸이 글자를 가르는 도구가 나오면 D1 도 다시 본다.
5. `keeper_artifact_read` 를 후보에 넣는가. 일주일 합계는 가장 크지만(24.88 MB) 날마다 다르고, 결과가 파일 내용이라 스텁을 받은 모델이 다시 읽는지 알 수 없다.

## 6. 하지 않는 것

- 반복 호출을 막거나 턴을 끝내거나 Keeper 에게 문장을 보낸다.
- 장부의 기록 형식을 바꾼다.
- 앞 턴의 결과를 가리킨다. 끝난 턴은 마커 규칙의 일이다.
- 코드를 쓴다. 받아들여질 때까지 이 RFC 와 측정 스크립트뿐이다.
