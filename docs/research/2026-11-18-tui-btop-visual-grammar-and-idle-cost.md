# btop 의 화면 문법과 쉬는 TUI 가 쓰는 비용

운영자 요청(2026-11-17): btop 처럼 보기 좋고 자세한 화면으로 TUI 표현력을 올리고, 성능도
잡는다. 이 문서는 btop 소스에서 확인한 것, 운영자 btop 화면에서 본 것, MASC TUI 를 쉬게 두고
잰 것을 적는다. 결정은 [한 화면 문법 RFC](../rfc/RFC-tui-one-screen-grammar.md)와
[RFC-0515](../rfc/RFC-0515-keepers-list-gets-views-a-story-sheet-and-half-hour-pulse-slots.md)
개정에 있다. 이 문서의 제안은 결정이 아니다.

## 관측 범위

- btop: 릴리스 `v1.4.8` 의 `src/btop_config.cpp`, `src/btop_draw.cpp`, `src/btop_input.cpp`,
  `src/btop_theme.cpp`. 2026-11-18 00:44 KST 에 받아 읽었다. 빌드하거나 돌리지 않았다.
- 운영자 btop 화면 한 장(2026-11-17 16:07 KST, 3840×2160). 프로세스 목록과 주소가 들어 있어
  저장소에 넣지 않았다. 아래 2절은 화면의 짜임만 옮긴다.
- MASC TUI: main `c43fd13` 빌드, 160×46 PTY. 운영 서버 앞에 읽기 전용 중계를 두고 TUI 를
  붙였다. 중계는 쓰기 요청을 모두 거절했고, 거절한 요청은 0건이었다. 중계는 요청 경로, 바이트
  수, SSE 이벤트 이름만 기록했다. 본문은 기록하지 않았다. 측정 시각은 2026-11-17 22시부터
  11-18 00시 KST 까지다.
- 화면 15개를 화면마다 새 TUI 프로세스로 열고 20초 동안 아무 키도 누르지 않았다. 호스트
  부하는 같이 재지 않았다. CPU 는 그 프로세스가 쓴 CPU 시간(`ps -o time=`)의 차이다.

## 1. btop 이 하는 것

| 기능 | 동작 | 근거 |
|---|---|---|
| 상자 | 모서리가 둥근 상자가 기본이다 | `btop_config.cpp:320` `rounded_corners` 기본 `true` |
| 상자 번호 | 상자 이름 앞 위첨자 숫자는 그 상자를 켜고 끄는 키다 | `btop_draw.cpp:290` 이 번호를 위첨자로 그린다. `btop_input.cpp:239-252` 는 숫자 한 글자를 받으면 그 번호의 상자를 토글한다 |
| 그래프 기호 | 기본은 점자(braille)다. `block`, `tty` 도 고를 수 있다 | `btop_config.cpp:105`, 기본값 `:276` |
| 갱신 간격 | 기본 2000 ms. 설명은 "그래프 표본을 위해 2000 ms 이상 권장"이다. 100 ms 보다 짧게 둘 수 없다 | `btop_config.cpp:123`, 기본값 `:385`, 하한 `:577` |
| 미터 색 | 칸 색은 그 칸이 막대 안 어디에 있는지(0~100%)로 고른다. 값은 0~100 으로 자른다. 값이 클수록 막대 끝이 높은 쪽 색에 닿는다 | `btop_draw.cpp:403-415` |
| 그래프 색 | 한 줄 그래프는 열마다 그 값(0~100)의 색을 칠한다. 여러 줄 그래프는 줄마다 그 높이(0~100)의 색을 칠한다. 어느 쪽이든 색은 0~100 축 위의 자리를 말한다 | `btop_draw.cpp:465`, `:483-484` |
| 기본 테마 CPU 경사 | `#77ca9b` → `#cbc06c` → `#dc4c4c` (초록 → 노랑 → 빨강) | `btop_theme.cpp:71-73` |
| 색 수 | truecolor 를 끄면 24비트 색을 256색 6×6×6 정육면체로 바꾼다 | `btop_config.cpp:81` |
| 목록 흐림 | 프로세스 목록은 고른 줄에서 멀수록 어두워진다. 고른 줄이 없으면 위에서 아래로 어두워진다 | `btop_config.cpp:134` `proc_gradient`, 기본값 `:324`, 계산 `btop_draw.cpp:2083-2104` |

btop 의 미터는 언제나 0~100% 다. 막대에서 칸의 위치가 곧 "한도 대비 얼마"다. 그래서 경사 색이
상태를 말한다. 막대 끝이 빨강에 닿으면 한도에 가깝다는 뜻이다.

## 2. 운영자 btop 화면에서 본 것

- 위 테두리: 상자 이름(`¹cpu`), 메뉴(`menu`, `preset`), 가운데 시각, 오른쪽에 배터리 미터와
  갱신 간격 `- 2000ms +`. 낱말 안의 키 글자만 다른 색으로 칠한다(`menu` 의 `m`).
- 아래 테두리: 그 상자에서만 되는 동작(`select`, `info`, `terminate`, `kill`, `signals`)과
  위치 `0/1340`.
- 오른쪽 테두리: 스크롤 막대와 `↑` `↓`.
- 본문에는 데이터만 있다. 이름, 값, 줄마다 작은 그래프.
- 줄마다 작은 그래프: 메모리 항목과 프로세스 CPU. 0 인 구간은 바닥에 점선으로 남는다.
- 네트워크는 위아래 거울 그래프다. 받기는 위로, 보내기는 아래로 그린다. 축의 최대값을 흐린
  글자로 적는다(`123K`).
- 숫자는 오른쪽 정렬이고 단위가 붙는다.

## 3. MASC TUI 에 가져올 것

| btop | MASC | 이유 |
|---|---|---|
| 테두리에 이름, 상태, 개수, 키, 위치 | 가져온다 | 본문에 데이터만 남는다. 줄을 더 쓰지 않는다 |
| 위첨자 상자 번호 | 가져오지 않는다 | btop 에서는 상자 토글 키다. MASC 엔진 카드의 `¹²³` 은 어떤 카드로도 가지 않는다. 같은 화면에서 `1` `2` `3` 은 카드와 상관없는 구역(fleet, resources, tools)을 연다(`masc_tui.ml:40647-40653`). 한 화면 문법 RFC §3.1 은 숫자를 번호 붙은 것 고르기에만 남긴다 |
| 경사 미터 | 선언된 한도가 있는 미터에만 | btop 미터처럼 막대 끝의 위치가 한도 대비 비율일 때만 색이 상태를 말한다. 도구별 호출 수, 몫, 완료 비율에는 그런 100% 가 없다 |
| 점자 그래프 | 가져온다 | 한 칸에 점 8개라 같은 폭에 시간 칸이 두 배다. 0(바닥 점선), 표본 없음(빈칸), 아직 못 읽음(`◌`)을 따로 그린다 |
| 거울 그래프 | 가져온다 | 호출과 실패, 받기와 보내기를 한 축에서 본다 |
| 고정 갱신 간격 | 화면 전체에는 가져오지 않는다 | MASC 는 보이는 값이 바뀔 때만 그리게 바꾼다(한 화면 문법 RFC §8). 지금은 그렇지 않다(4절). 엔진 화면의 시간 그래프만 화면이 열린 동안 2초마다 표본을 모은다. btop 기본 간격과 같다 |
| 고른 줄에서 멀수록 흐리게 | 가져오지 않는다 | 값 자리의 흐림은 이전 관측이라는 뜻이다(한 화면 문법 RFC §6.4). 줄 위치로 흐리게 하면 그 뜻과 섞인다 |

1차 btop 스택(#52763·#52770·#52781·#52791, 이슈 #52755)은 칸 위치로 색을 고르는 btop 방식
미터를 여덟 곳에 그린다. 도구 호출 그래프 한 곳은 시간 칸마다 값으로 색을 고른다.

| 곳 | 무엇 | 지금 경사 | 선언된 한도 |
|---|---|---|---|
| `render_metrics.ml:249`, `:457` | GC 점유율(live / heap) | Pressure | 없다. heap 은 GC 가 키운다 |
| `render_metrics.ml:291` | 작업 완료 / 전체 | Progress | 없다. 완료 비율이다 |
| `render_metrics.ml:877` | 키퍼별 기억 수 / 전체 | Progress | 없다. 몫이다 |
| `render.ml:248`, `:255` | 실행 중 / 띄울 수 있는 수, 반응 여력 | Progress | 확인 필요: 띄울 수 있는 수가 넘을 수 없는 상한인지 |
| `usage_calls.ml:376` | 도구별 호출 수 / 화면의 최대 | Progress | 없다. 상대 크기다 |
| `ansi.ml:843-857` `ctx_bar`(키퍼 상세의 실시간 컨텍스트) | 쓴 토큰 / 최대 | Pressure | 있다. 컨텍스트 창 |
| `usage_calls.ml:198-226`(그래프, 값으로 색) | 시간 칸별 호출 수 / 최대 | Progress, Pressure | 없다. 상대 크기다 |

Progress 경사(파랑 → 청록 → 초록)는 "하는 중" 색(`status.info`)을 지난다. 그래서 진행 막대가
"하는 중"으로 읽힌다. 선언된 한도가 분명한 막대는 계정 한도(쓴 양 / 한도)와 컨텍스트
창(쓴 토큰 / 최대)이다. 컨텍스트 창 막대는 이미 Pressure 경사를 쓴다. 계정 한도 막대는 창마다
색 하나로 그린다(`overview_providers.ml` `window_tone`).

키 지연은 화면이 0.2초 동안 조용할 때만 쟀다. 조용해지지 않아 건너뛴 키는 화면마다 0~13개다.

CPU 는 그리기보다 받는 데이터에서 나온다.

- 도구 호출 화면은 20초 동안 두 번 썼는데 CPU 는 10.2% 다.
- macOS `sample` 로 운영 화면을 약 8초 찍었다(1 ms 간격). 맨 위 함수 기준으로 기다림(조건
  변수, 타이머)과 PTY 쓰기를 뺀 표본 1,330개 중 876개(66%)가 JSON 해석이었다
  (`caml_lex_engine`, `Bytes.get_utf_8_uchar`, Yojson `Safe` 해석 루프). 해석은 화면을
  그리지 않는 OCaml domain 에서 돈다.
- 출력 스레드는 같은 8초 중 약 2.1초를 PTY `write` 에서 기다렸다. 측정 도구가 PTY 를 읽는
  속도 때문일 수 있어서 위 계산에서 뺐다. 실제 터미널에서도 그런지는 재지 않았다.
- 운영 화면 대기 25.7초 동안 받은 것:

| 경로 | 이벤트 | 수 | 바이트 |
|---|---|---:|---:|
| SSE `/mcp?sse_kind=observer` | `execution_snapshot` | 5 | 4,874,250 |
| | `keeper_turn_stream_event` | 9,647 | 1,710,224 |
| | `keeper_chat_operation_event` | 563 | 296,172 |
| | `workspace_dataset_changed` | 1,268 | 263,265 |

SSE 만 25.7초에 7.36 MB, 초당 약 286 KB 다. `execution_snapshot` 은 한 번에 약 1 MB 를 약 5초마다 통째로 보낸다.
턴 진행 조각(`keeper_turn_stream_event`)은 모든 키퍼 것이 초당 375개 온다. 채팅을 열지 않아도
온다.

그리기 쪽에서 가장 큰 것은 0.1초 단위로 늘어나는 나이다. 운영 화면 대기 10초 동안 프레임
77개 중 73개가 32번째 줄 하나만 바꿨다. 그 줄은 오른쪽 Activity 창의 머리줄
`… · 진행 중 · 마지막 이벤트 16.4s` 이고, 바뀔 때마다 160칸 줄을 통째로 다시 쓴다(프레임 평균
552 B). 처음에는 `진행 중` 표시의 150 ms 움직임을 원인으로 봤다. 코드를 보면 Activity 창은 움직임을
기록하지 않는다(`note_motion_if_visible` 은 키퍼 목록 셋과 채팅 둘에만 있다). 그 추정은 틀렸다.

프레임 만들기 시간은 TUI 가 프로세스마다 앞 512 프레임만 남긴다. 바쁜 화면은 대기 구간 전에
512 프레임을 넘겨서 대기 구간을 못 쟀다. 잰 화면은 계정 한도(build p50 0.67 ms, p99 9.5 ms)와
도구 호출(p50 0.26 ms, p99 2.0 ms)이다.

## 5. 남는 것

- 계정 한도의 느린 키 지연(p50 155 ms)은 build 시간(p99 9.5 ms)으로 설명되지 않는다. 저장소,
  키퍼 목록, 키퍼 기억은 대기 구간의 build 시간을 못 쟀다.
  키를 누를 때 하는 읽기를 따로 봐야 한다.
- 받는 데이터를 줄이는 일은 서버를 같이 바꾼다. 따로 RFC 로 낸다.
- 측정 도구(PTY 캡처, 읽기 전용 중계, 화면별 대기 측정)는 저장소에 없다. 같은 값을 다시 재려면
  도구를 `scripts/` 로 올리는 일이 먼저다.
- 운영 서버는 측정하는 동안에도 일을 했다. 도는 키퍼 수가 화면마다 달라서 화면 사이 값은
  같은 조건이 아니다.
