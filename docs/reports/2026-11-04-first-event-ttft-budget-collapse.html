1무슨 일이었나

보드가 운영자 주의 항목으로 올린 것은 이 문구였다.

Board attention · 2026-11-04 Provider timeout during first_token (provider_error_timeout:first_token): Provider 'opencode_go' timeout phase=first_token: no response headers before the first-event budget ran out; keeper can soft-fail and retry with provider cooldown.

조사 결과 이것은 provider 결함이 아니었다. 첫 토큰까지의 침묵을 재던 예산 180초가, 정상적으로 느린 대형 prefill 을 잘라버린 것이다. 잘린 턴은 매번 180초를 태우고 턴 상실로 끝났고, 다음 레인 슬롯에서 같은 prefill 을 처음부터 다시 보냈다. 복구 기계(soft-fail · 레인 이월 · 다음 사이클 재시도)는 설계대로 동작했고 한 번도 엉키지 않았다. 고장은 회복 로직이 아니라 예산값이었다.

보드 문구는 opencode_go 를 지목했지만 실제 분포는 달랐다. 8일 동안 first_token 으로 끝난 45턴 중 glm-coding 직행이 35턴, opencode_go 5턴, kimi_coding 4턴, openrouter 1턴이었다. 특정 게이트웨이 문제가 아니라 GLM 계 앞에서 벌어지는 공통 현상이었다.

2-2. 요청이 클수록 더 자주 잘렸다

함대의 요청은 거의 다 크다. 8일 동안 완료된 요청 약 7만 5천 건 중 65%가 20만 토큰 이상이었고, 5만 토큰 미만은 33건뿐이었다. 그래서 "가벼운 키퍼는 안 걸렸다"는 비교할 표본이 없어 근거가 되지 못한다. 근거는 크기에 따른 기울기다. 컷마다 같은 키퍼가 바로 앞에 완료한 요청의 토큰 수를 그 요청의 크기로 잡았다.

2-3. 버스트의 순간, provider 는 살아 있었다

3결정 — 휴리스틱 제거

문제 제기는 사용자의 한 문장이었다: "이 타임아웃이 필요한 건가", "휴리스틱하기 싫다, 불필요한 제약인가". 검토 결과 불필요한 제약은 침묵 상한 전체가 아니라 TTFT 만의 더 조인 상한이었다. 침묵을 어딘가에서 끊어야 하는 건 correctness 요구사항이고, 그 역할은 이미 진행 없음 watchdog(provider_call_deadline_sec = 900)이 한다. 모델이 얼마나 오래 생각할지 추측해 자르는 두 번째 칼만이 휴리스틱이었다.

3-1. 코드에는 900초 상한이 셋 남는다

값을 하나로 맞췄지만 타이머는 하나가 되지 않았다. 셋이 같은 900초로 동시에 돈다.

상한세기 시작하는 시점잘렸을 때 로그
admission (큐)권한 대기 시작. 값은 deadline 을 그대로 씀phase=queue
AGENT_CORE first_event권한을 받은 순간. count-tokens 왕복 포함phase=first_token
MASC 진행 없음 watchdogbefore_turn 진행 기록. 15초마다 검사phase=wall_clock: made no progress for 900s

코드 위치: admission 값 lib/keeper/keeper_turn_driver_try_provider.ml:2334 · watchdog 같은 파일 817·898행 ·first_event 창 packages/agent_core/lib/llm_provider/prepared_completion_request.ml:215

900초 넘게 조용한 prefill 이 어느 이름으로 잘릴지는 경합으로 정해진다. 요청 준비 시간과 15초 검사 주기 가운데 어디에서 끝나는지가 승패를 가른다. 큐 대기가 없으면 watchdog 이 먼저 터지기 쉽고, 큐 대기가 있으면 first_token 이 먼저 터지기 쉽다. 어느 쪽이 더 자주 이기는지는 측정하지 않았다.

  • 재시도는 같다. Runtime_attempt_fsm.should_try_next 는 TimeoutError 를 단계와 상관없이 다음 후보로 넘긴다.
  • 로그 정보는 다르다. watchdog 이 이기면 "헤더를 못 받음"과 "헤더는 받았지만 첫 토큰이 없음"이 구분되지 않는다. 실행 도중 900초 동안 멈춘 경우와도 같은 문장이 남는다.
  • 감시 지표가 바뀐다. first_token 만 세면 900초 넘는 꼬리가 wall_clock 으로 찍혔을 때 놓친다. 그래서 5절은 셋을 합쳐 센다.

  • 900초급 3턴은 모두 glm-coding 이 900초 동안 응답 헤더를 보내지 않은 경우다. 19:21:46Z(wall_clock)와 19:21:56Z(first_token)는 10초 차이라 한 사건으로 보고, 01:18:24Z(first_token)가 또 한 사건이다.
  • 기대치는 wall_clock·queue 기준 14턴/8일, 11.5시간이면 약 0.8턴이다. 그보다 많지만 사건이 2건뿐이라 아직 판단하지 않는다.
  • 예전 180초였다면 같은 경우를 180초에 끊었다. 지금은 720초를 더 기다린 뒤 끊긴다. 이 변경의 비용이 여기서 드러난다.
  • stream_idle 7턴 중 6턴은 같은 때 다른 연결도 함께 끊긴 공통 원인이라 따로 센다. 15:02:39Z 3건은 같은 초에 glm-coding 2건·opencode_go 1건이 잘렸다. 그 전 15:00:40 무렵부터 1분 동안 로그가 10초에 1~3줄로 줄었고, 15:01:38 에 heartbeat ack timeout 이 찍혔다(네트워크나 호스트, 확신 중간). 00:40:29~30Z 2건은 00:40:00Z 에 DNS 조회가 실패했고(getaddrinfo 결과 없음) 00:39 에 로그가 분당 81줄로 줄었던 때다. 01:04:01Z 1건은 01:02:10Z 연결 끊김, 01:04:13Z heartbeat ack timeout, 01:04:42Z 연결 시간 초과와 겹친다.

6남은 구조 과제

  • run 첫 요청 캐시 미적중 77~86% — 턴 경계에서 이미 보낸 기록을 다시 써서 provider 캐시가 빗나간다(#47788 측정). prefill 을 줄이는 근본 수정은 Draft 스택 #48123 · #48124. 병합·재측정이 남았다.
  • GLM 계정 고정 처리량 — 큰 요청 6건이 동시에 겹치면 첫 토큰이 10배 늦어진다. 동시 진입 제어는 사용자가 정한 방향(강제 규칙 금지)과 반대라 제외했다. prefill 축소로 완화된다.
  • TTFT 노브의 코드 레벨 정리 — 노브·freeze rule·테스트를 지우고 deadline 하나로 통합하는 정리는 별도 RFC 단위로 남긴다. 근거는 둘이다. runtime.toml 주석 "deadline 을 바꾸면 이 값도 같이 맞출 것"은 두 노브를 사람이 손으로 맞춰야 한다는 뜻이다. 그리고 같은 값의 상한 셋이 경합해 로그 이름이 흔들린다(3-1). 노브를 지우기 전에 watchdog 컷 기록에 "첫 토큰 전이었는지"가 남아야 한다. 그래야 헤더 유무로 가르던 진단이 없어지지 않는다.
