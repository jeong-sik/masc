### Added

- A workspace whose `runtime.toml` has `[browser.live.bidi]` (`firefox`, `profile`, `port`, default 9222) has its Keeper Firefox and BiDi host started by the MASC server when the server starts. It starts only what is missing: no Firefox when the port already answers, and no host while one holds the host lock. It starts Firefox only together with a host, because Firefox's port lets any local process drive it: nothing is started while the browser lane is not installed as its installation wrote it, or a host holds the lock (it attaches to Firefox only when it starts), whether on this port, on another one, or with a record that cannot be read. Both run apart from the server, so a restart leaves them up; they write to `.masc/browser-lane/keeper-firefox.log` and `bidi-host.log`, and each start moves the last run's log to `<name>.1`. A Firefox the server started and left with no host, because its port did not open within 30 seconds or its host could not be started, is stopped through its process group (SIGTERM, then SIGKILL after 5 seconds); a Firefox whose port already answered is never touched. A host that wrote its ending and is still giving up the lock is waited for, up to 5 seconds, before another is started. The host is not given the server's `MASC_HTTP_BASE_URL` or `MASC_HTTP_PORT`. `[browser.live] enabled = false` starts nothing. The dashboard's Browser activity editor reads the table and keeps it. Write the table only after deploying a server that reads it (#42125).
