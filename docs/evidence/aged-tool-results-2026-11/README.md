# 지난 턴의 도구 결과를 마커로 바꾸면 줄어드는 요청 크기 (2026-11-01 ~ 11-05, UTC)

저장된 요청이 지난 턴의 도구 결과를 원문으로 얼마나 싣고 있는지 세고, "현재 턴보다 앞선 도구 결과를 마커로 바꾸면" 요청이 얼마나 줄지 계산해요.
`measure_aged_tool_results.py`가 `.masc/keepers/*/provider-inputs`의 요청 4,344개(Keeper 25명, 프롬프트 8.19 GB)를 읽고, 메시지 크기만 더해서 바꾼 뒤의 크기를 구해요.
읽은 때는 2026-11-05T22:31Z예요. 11-05는 하루가 다 차지 않았어요.

숫자는 바이트예요. 토큰이 아니고, 모델이 마커를 되읽는 일은 재지 않았어요.
이 폴더는 규칙을 넣자는 주장이 아니에요. RFC-0363 §3.4.1 개정이 턴 경계 강등을 없앤 뒤 요청에 얹힌 몫의 크기를 보여 줘요. 아래 "이미 있는 결정과의 관계"를 같이 읽어요.

## 결과

| | 전체 | `msx-retro-mania` 제외 |
|---|---:|---:|
| 센 요청 | 4,344 | 4,061 |
| 프롬프트 바이트 | 8.19 GB | 6.10 GB |
| 도구 결과가 프롬프트에서 차지하는 몫 | 57.4% | 45.6% |
| 현재 턴보다 앞선 도구 결과의 몫 | 50.3% | 43.5% |
| 그중 2 KB 이상을 마커(596 B)로 바꿨을 때 줄어드는 몫 | 33.7% | 22.1% |
| 컷이 한 턴 움직일 때 다시 읽을 수 있는 최대 몫 | 4.1% | 4.2% |

`msx-retro-mania`를 따로 뺀 열을 둔 이유는 이 Keeper 하나가 프롬프트 바이트의 25.5%(2.09 GB)이고, 줄어드는 몫도 67.5%로 혼자 높아서예요.
이미지가 붙은 도구 결과는 전체 58,660개이고 그중 58,532개가 이 Keeper의 것이에요. 이미지 바이트는 프롬프트 바이트에 들어 있지 않아요.

### 문턱과 규칙에 따른 차이

줄어드는 몫이에요. 한 줄은 문턱 이상인 결과만 바꿨을 때예요.

| 문턱 | 앞선 턴 전부(전체) | 앞선 턴 전부(제외) | 한 턴 더 앞(전체) | 한 턴 더 앞(제외) |
|---|---:|---:|---:|---:|
| 1 KB | 35.7% | 24.8% | 34.6% | 24.0% |
| 2 KB | 33.7% | 22.1% | 32.6% | 21.4% |
| 4 KB | 30.7% | 18.0% | 29.7% | 17.5% |
| 16 KB | 23.6% | 8.7% | 22.9% | 8.4% |

- "앞선 턴 전부"는 마지막 user 메시지보다 앞의 도구 결과예요(`before_current_turn`). "한 턴 더 앞"은 그 앞 user 메시지보다 앞의 것이에요(`before_previous_turn`).
- 16 KB 이상만 바꾸면 `msx-retro-mania`를 뺀 몫이 8.7%예요. 2 KB로 낮추면 22.1%예요. 작은 결과 하나하나는 가벼워도 합이 커요. RFC의 열린 질문 2에 대한 답이에요.
- 마커 크기를 바꿔 봐도 크게 안 달라요. `msx-retro-mania`를 뺀 2 KB 문턱에서 마커가 372 B이면 22.9%, 596 B이면 22.1%, 1,024 B이면 20.7%예요. 596 B는 저장된 요청이 이미 싣고 있는 마커의 평균 크기예요(`docs/evidence/tool-result-carry-2026-11`).

## 이미 있는 결정과의 관계

RFC-0363 §3.4.1 개정(#48123 문서, #48124 코드, 11-04T08:53Z 병합)이 턴 경계 강등을 없앴어요. 컷이 턴마다 움직이면 턴마다 한 번 캐시를 버린다는 이유예요.
같은 절이 요청이 커지는 비용도 적었어요. 11-04 Keeper 13명의 마지막 요청에서 메시지 바이트가 0 ~ 153% 늘고, 늘어난 부분은 직전 요청과 같은 prefix라 캐시된다는 거예요.

- 이 폴더의 값은 그 비용을 요청 전체로 센 거예요. 컷 앞의 도구 결과가 프롬프트의 43.5 ~ 50.3%이고, 2 KB 이상만 마커로 바꾸면 22.1 ~ 33.7%가 줄어요.
- 같은 절은 GLM 두 모델의 run 첫 요청 캐시 적중 중앙값을 0 ~ 40%로 적었어요(11-03 ~ 04). 그 요청에서는 이 바이트가 캐시 읽기가 아니라 전액 입력이에요. run 첫 요청이 미적중 입력 토큰의 77 ~ 86%를 차지했어요.
- 같은 run 안의 요청은 캐시 적중이 96 ~ 99.5%였어요. 그 요청에서는 이 바이트가 캐시 읽기라서 값이 싸요.
- 그래서 이 바이트가 비싼지는 run 첫 요청의 캐시 적중에 달려 있어요. 적중이 오르면 이 몫의 값은 내려가요.
- 컷이 한 턴 움직일 때 제공자가 다시 읽을 수 있는 최대 몫은 "컷 이후 메시지 바이트 ÷ 프롬프트 바이트"예요. "앞선 턴 전부" 규칙에서 4.1%(제외 4.2%), "한 턴 더 앞" 규칙에서 6.3%예요. 계산상의 최대값이고, 제공자 캐시는 이 폴더에서 재지 않았어요.

## 마커로 바꾸면 캐시가 다시 읽는 바이트 (UTC)

위 표는 줄어드는 바이트만 세요. 제공자가 요청 prefix로 캐시하면 처음 바뀐 메시지부터 끝까지 다시 읽어요. RFC-0363 §3.4.1 개정이 턴 경계 강등을 없앤 이유가 이 비용이에요.
`measure_aged_rewrite_cost.py`는 "도구 결과를 만든 턴이 끝나면 마커로 바꾼다"는 규칙에서 다시 읽는 바이트를 재요.
저장된 요청마다, 이번에 처음 늙은 결과 중 가장 앞의 것부터 현재 턴이 시작하기 전까지를 세고, 마커로 바뀐 결과는 마커 크기로 쳐요. 현재 턴은 어차피 새 바이트라서 세지 않아요.

| 창 | 요청 | 프롬프트 | 줄어드는 몫 | 다시 읽는 몫 |
|---|---:|---:|---:|---:|
| 11-05T03:00 ~ 11-06T03:00 | 824 | 1.77 GB | 51.5% | 1.0% |
| 같은 창, `msx-retro-mania` 제외 | 810 | 1.63 GB | 49.4% | 1.1% |
| 11-04T12:00 ~ 11-06T03:00 | 1,650 | 3.23 GB | 48.2% | 1.3% |
| 같은 창, `msx-retro-mania` 제외 | 1,615 | 2.92 GB | 45.6% | 1.3% |

- 첫 창에서 요청마다 다시 읽는 몫은 p50 0.3%, p90 3.1%, p99 16.3%, 최대 63.3%예요. 앞 요청이 있는 요청의 71.8%에 새로 늙은 결과가 있어요.
- 다시 읽는 몫은 상한이에요. 제공자가 현재 턴 앞의 히스토리를 전부 캐시에 들고 있다고 치고 센 값이에요. 캐시가 만료됐으면 규칙과 상관없이 전부 다시 읽어요.
- 작은 이유는 새로 늙는 결과가 직전 턴이 만든 것이라 히스토리 끝쪽에 있어서예요. 처음 바뀐 메시지 뒤에는 직전 턴과 현재 턴뿐이에요.
- 63.3%는 `wkbl-growth`의 한 요청이에요. 직전 턴 하나가 메시지 약 1,180개를 만들었고 그 결과가 한꺼번에 늙었어요. 11-04T12:00 이후 다시 읽은 요청 1,293개 중 50%를 넘는 것은 이 하나뿐이에요.

### 가격에 대어 보면

한 턴이 요청을 K개 보내요. 캐시 읽기 값을 캐시 없는 읽기의 c배라고 해요. 한 턴에 마커는 `K × c × 줄어드는 몫`만큼 아끼고, 다시 읽기는 `(1 − c) × 다시 읽는 몫`만큼 더 써요.
K는 `measure_turn_requests.py`로 쟀어요. 같은 창에서 Agent Core 레인 턴 670개가 요청을 턴당 평균 17.0개(중앙값 6, p90 28) 보내요. `glm-5.3-flash`(365턴)는 중앙값 5예요.

| K | 손익분기 c | c = 0.1일 때 한 턴 순이득 |
|---:|---:|---:|
| 1 | 1.9% | 0.042 |
| 5 | 0.4% | 0.249 |
| 17 | 0.1% | 0.867 |

- 첫 창 값이에요. c가 손익분기보다 크면 마커로 바꾸는 쪽이 이득이에요.
- 순이득은 프롬프트 1개를 캐시 없이 읽는 값을 1로 센 값이에요. c = 0.1은 예로 든 값이에요. 제공자별 c는 재지 않았고 가격표에서 읽어야 해요.
- usage 이벤트가 없는 턴 2,547개는 K를 못 쟀어요.

### 턴 첫 요청의 캐시 적중

같은 창에서 Agent Core 레인 턴 670개예요. 적중은 첫 요청의 입력 토큰 중 캐시에서 읽은 몫이에요.

| 이전 턴이 끝난 뒤 간격 | 턴 | 첫 요청 적중 | 적중이 절반 미만인 턴 |
|---|---:|---:|---:|
| 1분 미만 | 305 | 73.2% | 23.9% |
| 1 ~ 5분 | 76 | 84.8% | 15.8% |
| 5 ~ 10분 | 41 | 68.0% | 24.4% |
| 10 ~ 30분 | 71 | 45.1% | 53.5% |
| 30 ~ 60분 | 79 | 18.5% | 79.8% |
| 60분 이상 | 4 | 2.6% | 100% |
| 알 수 없음 | 94 | 20.0% | 84.0% |
| 전체 | 670 | 57.9% | 41.6% |

- 간격이 10분을 넘으면 적중이 절반 미만인 턴이 10 ~ 30분에 53.5%, 30분 이상에 80% 안팎이에요. 이 턴은 마커로 바꾸든 안 바꾸든 히스토리를 거의 다 다시 읽으니까 다시 읽는 비용이 거의 없어요. "알 수 없음"은 읽은 파일에 앞선 턴이 없는 턴이에요.
- `glm-5.3-flash`(365턴)는 첫 요청 적중이 46.3%이고, 30 ~ 60분 간격에서는 2.2%예요. `glm-5.3`(137턴)은 같은 간격에서 66.5%라서 모델마다 캐시 수명이 달라요.
- 간격이 1분 미만인 턴도 23.9%는 적중이 절반 미만이에요. 히스토리가 달라졌는지 제공자가 캐시를 못 찾았는지는 이 스크립트가 못 가려요.

## 이 숫자가 말하지 않는 것

- 모델이 마커를 되읽는 빈도. 되읽으면 `keeper_artifact_read` 왕복과 토큰이 생겨서 줄어든 몫이 작아져요. RFC의 열린 질문 1이고 이 폴더는 답하지 못해요.
- 토큰. 바이트와 토큰의 비율은 도구 결과(JSON, 한글 섞인 글)와 시스템 프롬프트에서 달라요.
- 저장된 요청은 턴마다 하나예요. 한 턴의 다른 요청은 저장되지 않아요.
- 턴의 경계는 user 메시지로 잡아요. 한 턴 중간에 user 메시지가 끼면 "현재 턴"이 실제보다 늦게 시작한 것으로 읽혀서, 앞선 결과의 몫이 크게 잡혀요. 얼마나 끼는지는 세지 않았어요.
- 이미지가 붙은 도구 결과(전체 2,074,975개 중 58,660개)는 바꾸는 대상에서 빼요. 이미지 바이트는 프롬프트 바이트에 들어 있지 않아요.
- 이미 마커인 결과는 마커보다 작거나 비슷해서 줄어드는 몫에 들어가지 않아요.
- 다시 읽는 몫의 분모는 저장된 요청이에요. 한 턴은 요청을 평균 17개 보내고 저장된 것은 그중 하나라서, 분모는 어느 요청이 저장됐는지에 따라 달라져요. 처음 바뀐 위치는 한 턴 안에서 같아요.
- 이 재생은 RFC-0363 §3.4.1 개정 전 코드가 무엇을 다시 썼는지 말하지 않아요. 그 코드가 같은 규칙이었는지는 확인하지 않았어요.
- 모델이 마커를 되읽는 빈도, 강등된 호출 인자를 모방하는 문제(§3.4.2), 제공자별 캐시 가격, 작업 성공률은 재지 않았어요.
- 아직 배포된 것이 없어요. 줄어드는 몫과 다시 읽는 몫은 저장된 요청에서 센 값이고, 실제 요청에서 같은 값이 나오는지는 규칙을 넣은 뒤에 같은 스크립트로 봐요.

## 규칙을 넣은 뒤 (2026-11-06, UTC)

끝난 턴의 2 KB 이상 도구 결과를 마커로 보내는 규칙(#49185)은 09:44Z 에 병합됐어요. 서버는 09:50:51Z 부팅부터 이 규칙으로 돌아요. 서버 로그에 `model input references … finished_turn_results=markers` 줄이 09:51:36Z 부터 찍혀요.
규칙이 들어가기 전 창(08:00~09:50Z)과 들어간 뒤 창(09:52~11:17Z)에 같은 두 스크립트를 돌렸어요. 결과 파일 이름의 `pre-rules`가 앞 창, `with-rules`가 뒤 창이에요. 뒤 창은 11:50Z 와 13:30Z 까지 늘려서 다시 돌렸어요.

| | 앞 창 | 뒤 창 09:52~11:17 | 뒤 창 09:52~13:30 |
|---|---|---|---|
| 저장된 요청 | 103 | 136 | 374 |

- 마커는 JSON 문자열의 첫머리에 있는 것만 쳐요. 결과 본문 중간에 마커 글자가 인용된 경우(장부 행을 출력하는 명령 등)를 빼려는 거예요. 앵커를 빼고 돌린 값은 마커 19,253개 중 늙은 마커 17,943개, 읽힌 것 237개(1.32%)이고, 늘어난 몫은 대부분 만들 때부터 마커 쪽(1,310개)이에요. 읽힌 몫은 거의 같아요.
- 읽힌 몫은 끝난 턴에서 마커가 된 결과의 값이에요. 만든 턴 안에서 바꿨을 때 모델이 방금 만든 결과를 다시 찾는 몫은 이 측정으로 알 수 없어요.
- 저장된 요청은 한 시도가 마지막으로 보낸 요청이라서, 그 시도가 싣고 있던 마커만 보여요.
- 요청을 센 Keeper 의 `keeper_artifact_read` 3,788번 중 90% 가까이는 저장된 요청에 마커로 실린 적 없는 sha256 을 읽어요. 모델이 그 sha256 을 어디서 받았는지는 가리지 못했어요. 23번은 `sha256` 칸이 없어서(`answer_sha256` 오입력 등) 어느 마커의 읽기인지 이을 수 없었어요.
- 읽기는 시각으로 가르지 않았어요. 그 3일 안의 읽기면 마커가 실린 요청의 앞이든 뒤든 세요.
